## 可读性

代码的可读性很重要！或者正如 Python 所说，*readability counts*。你只写一次，但你（和其他人）很可能会读很多次。花额外几秒或几分钟思考明年试图阅读代码的可怜糊涂的人……很可能就是你。抽象（Don’t Repeat Yourself）和可读性之间存在平衡和张力：

- KISS（Keep It Simple, Stupid！）。
- *可读性：* 不要“聪明”，要清晰。
- 良好的命名至关重要！
- *始终使用头部。*
- 如果可能，对 -h、--help 和错误参数发出有用的信息！
  - 优先使用“here”文档（带前导 tab）而不是一堆 echo 行，因为以后需要更新和重新换行时摩擦更小。
- 使用 source（而不是 .，后者容易看不见且更难搜索）来包含配置文件，后者应以 .cfg（或 .conf 或你标准的任何名称）结尾。
- 如果可能，对所有内容都使用 ISO-8601 日期。
- 如果可能，保持事物列表按字母顺序排列；这可以防止重复并使添加或删除项目更容易。示例包括 IP 地址（使用 GNU sort -V）、主机名、要安装的包、case 语句，以及变量或数组/列表的内容。
- 如果可能，使用命令的长参数以提高可读性，例如使用 diff --quiet 而不是 diff -q，但要注意对非 GNU/Linux 系统的可移植性。
  - 如果任何选项简短或晦涩，请添加注释。
  - 强烈考虑记录你选择或需要选项的原因，甚至记录你考虑过但因某种原因未使用的选项。
  - 一定要记录任何看起来像个好主意但实际上可能导致问题的选项，尤其是你在其他地方常用到的。

对于变量命名，要注意像这样的通用变量名：

```
`${GREP} ${pattern} ${file}`
```

这很抽象，也许可复用，但也很缺乏上下文。我们已将旧的 `` 替换为更新且更易读（我们认为）的 $()，而且肯定更易嵌套，但更重要的是，变量噪音更少，因为我们省略了不必要的 ${} 并使用了有意义的名称：

```
$($GREP "$re_process_errors" $critical_process_daily_log_file)
```

过了一段时间，你和你的团队会发现某些（我们敢说）惯用的方式来表达你经常面对的概念和操作。那时就是写风格指南的时候了，如果你还没有的话。

另一方面，如果你正在提交补丁或维护代码，最好遵循该代码的约定，除非你要对整个代码进行重排和可能的重构。
