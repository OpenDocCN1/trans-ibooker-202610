

## 制定你的风格指南

本书的核心主题是编写符合惯用法且可读性强的 bash 代码，并保持一致的风格，我们希望已经提供了你所需的工具。风格只是“我们如何书写”的另一种说法。找到一些风格指南，写下来，然后坚持执行。本书涵盖了许多重要的风格考量，还有一些其他指南我们也想提及，在设计系统和编写代码时需要牢记的事情。你可以将本章作为你自己的风格指南的起点，也可以如果喜欢就直接采用。附录是去掉讲解点的相同材料，可用作“速查表”，你可以在本书的 GitHub 页面获取 Markdown 或 HTML 代码。

请牢记以下高层原则：

- 首先：KISS——Keep It Simple, Stupid！复杂性是安全的敌人，¹ 但它也是可读性和理解性的敌人。当然，现代系统和环境本身就很复杂，所以请尽力不要让情况变得更糟。
- 其推论，正如 Brian Kernighan  famously 所说，调试的难度是最初编写代码的两倍，所以如果你的代码已经聪明到你能做到的程度，那么——按定义——你就聪明不到足以调试它。
- 尽量不要重新发明轮子。你想做的事情很可能已经被做过，并且很可能有工具或库可用。如果该工具已经安装，就直接使用。无论你多努力，你都不可能匹配 rsync 所投入的努力和测试，所以就用它吧。如果你在互联网上找到随机代码……嗯，先想想这个问题吧。

1 实际上是：“复杂性是安全的最大敌人”（参见 https://oreil.ly/zMJLF）。

- 提前为特殊情况或覆盖做好计划，因为它们一定会发生。向 Linux 发行版打包系统学习，提供一个 `/etc/things/global.cfg` 用于可盲目覆盖的默认值，然后允许在 `/etc/things/config.d/` 或类似位置进行覆盖。参见第 93 页的“Drop-in Directories”。
- 如果不在版本控制中，就不存在！（而且迟早会丢失，然后 *真的* 不存在了。）
- 记录一切。（但你不必为此写一本书……哦等等……）为一年后加入团队的新人编写你的代码、注释和文档，那时你已经忘记了 *为什么* 要 *那样* 做。记录什么 *没* 起作用，以及可能的原因，并交叉引用，尤其是那些你能预见会伤害你的东西。（是的，`rm -rf /$undefined_variable` 证明是一个 *非常糟糕的主意*！）
- 保持代码和文档 DRY：Don’t Repeat Yourself。一旦你有了不止一个副本，它们迟早会不同步——唯一的问题是何时。用函数和库；不要 WET（We Enjoy Typing）。

“Python 之禅”在很大程度上也适用于 bash，这是一个不错的起点。尝试 `python -c "import this"` 或查看 Python 文档。

## bash Idioms 风格指南不可移植

本 *bash Idioms* 风格指南专门针对 bash，因此不能移植到 POSIX、Bourne、Dash 或其他 shell。如果你需要为这些 shell 编写代码，你需要测试并调整本指南以适应这些 shell 支持的语法和功能。

在 Docker 或其他容器中尤其要小心，其中 `/bin/sh` 不是 bash，而 `/bin/bash` 可能甚至不存在！这适用于物联网和其他受限环境，例如工业控制器。参见第 ix 页的“bash in Containers”和第 94 页的“Shebang！”。

深入细节，你的风格指南中应包含哪些类型的内容？我们将在以下各节中介绍其中的一些。

## 可读性

代码的可读性很重要！或者正如 Python 所说，*readability counts*。你只写一次，但你（和其他人）很可能会读很多次。花额外几秒或几分钟思考明年试图阅读代码的可怜糊涂的人……很可能就是你。抽象（Don’t Repeat Yourself）和可读性之间存在平衡和张力：

- KISS（Keep It Simple, Stupid！）。
- *可读性：* 不要“聪明”，要清晰。
- 良好的命名至关重要！
- *始终使用头部。*
- 如果可能，对 -h、--help 和错误参数发出有用的信息！
  - 优先使用“here”文档（带前导 tab）而不是一堆 echo 行，因为以后需要更新和重新换行时摩擦更小。
- 使用 source（而不是 .，后者容易看不见且更难搜索）来包含配置文件，后者应以 .cfg（或 .conf 或你标准的任何名称）结尾。
- 如果可能，对所有内容都使用 ISO-8601 日期。
- 如果可能，保持事物列表按字母顺序排列；这可以防止重复并使添加或删除项目更容易。示例包括 IP 地址（使用 GNU sort -V）、主机名、要安装的包、case 语句，以及变量或数组/列表的内容。
- 如果可能，使用命令的长参数以提高可读性，例如使用 diff --quiet 而不是 diff -q，但要注意对非 GNU/Linux 系统的可移植性。
  - 如果任何选项简短或晦涩，请添加注释。
  - 强烈考虑记录你选择或需要选项的原因，甚至记录你考虑过但因某种原因未使用的选项。
  - 一定要记录任何看起来像个好主意但实际上可能导致问题的选项，尤其是你在其他地方常用到的。

对于变量命名，要注意像这样的通用变量名：

```
`${GREP} ${pattern} ${file}`
```

这很抽象，也许可复用，但也很缺乏上下文。我们已将旧的 `` 替换为更新且更易读（我们认为）的 $()，而且肯定更易嵌套，但更重要的是，变量噪音更少，因为我们省略了不必要的 ${} 并使用了有意义的名称：

```
$($GREP "$re_process_errors" $critical_process_daily_log_file)
```

过了一段时间，你和你的团队会发现某些（我们敢说）惯用的方式来表达你经常面对的概念和操作。那时就是写风格指南的时候了，如果你还没有的话。

另一方面，如果你正在提交补丁或维护代码，最好遵循该代码的约定，除非你要对整个代码进行重排和可能的重构。

## 注释

关于注释的写法、时机、位置等已经写了很多。以下是与注释相关的风格指南：

- *始终使用头部。*
- 为一年后加入团队的新人写注释。
- 对你的函数进行注释。
- 不要注释你做了什么。注释你为什么做或不做某事。
  - 例外：当 bash 本身晦涩时，注释你做了什么。
- 考虑添加关于外部程序选项的注释，尤其是当它们简短或晦涩时。
- 在注释的第一词开头使用大写字母，但除非注释超过一句话，否则省略结束标点。

添加 *有用* 的注释来解释 *为什么* 你做某事以及你的意图！例如：

```
continue # To the next file in for loop
```

理论上，如果你写出清晰的代码，就不需要解释 *某物* 做什么。但有时 bash 本身就很繁琐或晦涩，例如变量替换（参见第 33 页的“Path or Prefix Removal”），像：

```
PROGRAM=${0##*/}  # Basename in bash
```

分隔符对于分隔代码的逻辑块通常很有用。但不要在底部添加结束分隔符来“框”住它；这只会增加混乱并减少你屏幕上的代码行数 1 行。不管怎样，*绝对不要* 在右侧用字符构建框！完全没有必要，你会浪费大量时间让它“看起来正确”。更糟的是，这会强烈阻碍以后修复或更新注释，因为你又得重新修复框。
