## 名称

命名 *很重要*。我们不能再强调这一点。`$file` 和 `$critical_process_daily_log_file` 之间的区别现在看起来除了多打字之外什么都不是 *现在*，当所有细节都在你脑海中时。但我们保证，如果你花额外的时间真正思考你命名的含义以及它在代码中读起来的样子，这很快就会得到回报，减少编码错误，并且在将来重读、调试和增强时也会有回报。以下是与名称相关的风格指南：

- 好的名字至关重要！
- 全局变量和常量使用大写。
  - 尽量不要更改全局变量，但有时这样做要简单得多（KISS）。
  - 对常量使用 `readonly` 或 `declare -r`。
- 其他变量使用小写。
- 函数使用 Mixed_Case。
- 使用 "_" 而不是 CamelCase 来代替空格（记住，“-” 不能用于变量名）。
- 谨慎使用 bash 数组；它们可能难以阅读（参见第 7 章）。`for var in $regular_var` 通常也同样有效。
- 尽快用可读的名称替换 $1, $2, .. $N。
  - 这样会使一切更易于调试和阅读，但也使设置默认值和添加或重新排列参数变得容易。
- 在指代类型之间进行区分，例如 $input_file 与 $input_dir。
- 使用一致的“FIXME”和“TODO”标签，如有必要加上名称和工单号。

考虑一下将这些混淆并使用（或出现差一错误）错误的一个有多容易：

```
file1='/path/to/input'
file2='/path/to/output'
```

这更直观易读，也更难打错：

```
input_file='/path/to/input'
output_file='/path/to/output'
```

另外，不要为了省打字而省略两个字符；请完整拼写出 $filename，以免以后出错。它是 $filenm 还是 $flname 还是 $flnm 还是别的什么？

## 函数

以下是与函数相关的风格指南：

- *始终使用头部。*
- 好的名字至关重要！
- 函数必须在被使用前定义。
  - 将它们分组放在顶部，并在每个函数之间使用两行空白和一个函数分隔符。
  - 不要在函数之间穿插代码！
- 使用 Camel_Case 和“_”使函数名与变量名区分开来。
- 使用 function My_Func_Name { 而不是 My_Func_Name() { 因为它更清晰，也更容易 grep -P '^\s*function '。
- 每个函数都应有注释，定义它做什么，输入（包括 GLOBALS）和输出。
- 当你有有用的、独立的代码片段，或任何时候你使用相同（或基本相似）的代码块超过一次时，将它们做成函数。如果它们很常见，比如日志记录或邮件发送，请考虑创建一个“库”，即一个你可以按需 source 的单一公共文件。
  - 为“库”函数加上前缀“_”，如 _Log 或其他前缀。
- 如果有意义，请考虑在参数中使用“填充”词以提高可读性，然后将其定义为本地 junk1="$2" # 未使用的填充，例如：
  - _Create_File_If_Needed "/path/to/$file" containing *important value*
- 在函数中设置变量时请使用 local 内置命令。
  - 但要注意，由于成功“本地化”，它会掩盖失败的返回码，因此如果使用命令替换，请将声明和赋值分开写，例如 local my_input 然后 my_input="$(some-command)"。
- 对于大约 25 行以上的任何函数，用 } # End of function MyFuncName 关闭它，以便在屏幕上更容易跟踪你在代码中的位置。对于少于 25 行的函数，这不是必须的，但鼓励这样做，除非变得过于杂乱。
- 不要使用 main 函数；它几乎总是多余的一层。
  - 话虽如此，使用“main”对 Python 和 C 程序员来说是有意义的，或者如果代码也用作库，并且如果你做大量单元测试时可能需要它。
- 考虑在主部分上方使用两行空白和一个主分隔符，尤其是在顶部有大量函数和定义时。

另外，在你的库中定义一个单一的日志函数（例如，_Log），并使用它！否则你最终会得到各种各样的日志函数、样式和目的地。理想情况下，正如我们之前所说，将日志记录到 syslog，让操作系统担心最终目的地、日志轮转等。

## 引用

引用很简单，直到它变得不简单，然后你就会头疼。我们知道这是怎么回事，有时我们仍然会做试错，尤其是尝试创建一行代码以 sudo 作为另一个用户运行或通过 ssh 在另一节点上运行时。添加一些 echo 行，小心行事。以下是与引用相关的风格指南：

- 请对变量和字符串加上引号，因为它使它们稍微突出并澄清了你的意图。
  - 除非变得过于杂乱。
  - 或它们需要不加引号以便展开。
- 不要引用整数。
- 除非需要插值，否则使用单引号。
- 不要使用 ${var} 除非需要；它太杂乱了。
  - 但有时确实需要，例如 ${variable}_suffix 或 ${being_lower_cased,,}。
- 请引用命令替换，例如 var="$(command)"。
- *始终* 对任何测试语句的两侧都加引号，例如 [[ "$foo" == 'bar' ]]。
  - 除非一侧是整数。
  - 并且除非你使用 ~=，在这种情况下你不能引用正则表达式！
- 考虑在 echo 语句中对变量使用单引号，例如 echo "cd to '$DIR' failed." 因为当变量意外未定义或为空时它会很明显。
  - 或 echo "cd to [$DIR] failed." 随你喜欢。
  - 如果使用 set -u，当变量未定义时你会收到错误——但如果变量已定义但只是意外为空则不会。
- 优先在 printf 格式周围使用单引号（参见第 56 页的“POSIX Output”和第 55 页的“Time for printf”其余部分）。

## 布局

以下是与布局相关的风格指南：

- 对齐！bash 中多个空格几乎无关紧要（= 两侧除外），并且对齐相似的命令使阅读更容易，也更容易看到相似性和差异。
- *不要允许尾随空白！* 这以后会在 VCS（版本控制系统）中造成噪音，当被移除时。
- 使用四个空格缩进，但在 here-documents 中根据需要使用 TAB。
- 在大约 78 列处断开长行，续行缩进两个空格，并在 | 或 > 之前断开，以便这些部分在向下扫描代码时突出。
- 打开块的代码放在一行中，例如：
  - if expression; then
  - for expression; do
- case..esac 中的列表元素缩进四个空格，关闭的 ;; 与该缩进级别相同。每个项目的块也缩进四个空格。
  - 一行元素应与 ;; 在同一行关闭。
  - 尽量对齐每个元素中的 )，除非变得杂乱或失控。
  - 请参阅示例代码中的 Example 8-4。

中断并且你不得不在 80 × 24 控制台上的 vi 中在火线调试时，你不会欣赏 200+ 列的代码。

断开你的行。

在重要部分之前断开它们，这样当你向下扫描列的左侧时，续行会跳出来。我们也喜欢对断开的行使用通常缩进的一半。我们无法在此书中做一个好的（坏的？）长行示例，因为它只会在奇怪的地方断开。但我们可以提供一个简单、我们认为可读的示例：

```

    | grep "$re_stuff_we_care_about" \
    | grep -v "$re_stuff_to_ignore" \
    | /path/to/email_or_log_command ...
...more code
```

## 语法

以下是与语法相关的风格指南：

- 编写 bash 代码时使用 #!/bin/bash - 或 #!/usr/bin/env bash，而不是 #!/bin/sh。
- 除非你非常确定需要 $*，否则使用 $@。
- 使用 == 而不是 = 进行相等比较，以减少与赋值的混淆。
- 使用 $( ) 而不是 `` 反引号/反引号。
- 使用 [[ 而不是 [（除非你需要 [ 用于可移植性，例如 dash）。
- 根据需要使用 (( )) 和 $(( )) 进行整数运算；避免使用 let 和 expr。
- 当简单且可读时，使用 [[ expression ]] && block 或 [[ expression ]] || block。不要使用 [[ expression ]] && block || block，因为它不做你认为它做的事情；对于这种情况，使用 if .. then .. (elif ..) else .. fi。
- 考虑使用“非官方 bash 严格模式”（参见第 96 页的“Unofficial bash Strict Mode”）。
  - set -euo pipefail 将防止或暴露许多简单错误。
  - 注意这一点，并谨慎使用它（如果你使用它）：IFS=$'\n\t'。
