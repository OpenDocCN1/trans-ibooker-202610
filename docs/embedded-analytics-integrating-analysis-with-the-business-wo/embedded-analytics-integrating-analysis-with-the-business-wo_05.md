# 第 4 章 嵌入式分析的数据

在构建将嵌入运营应用程序内的分析解决方案时，首先要问的问题之一是数据将从哪里来。答案并不总是简单。数据不一定来自运营应用程序本身。事实上，您通常希望使用来自其他系统的洞察来补充或增强该应用程序。

为此，您希望使用的每个数据源都需要考虑三件事：

- 数据来自哪里？哪个系统拥有最佳数据来支持您的决策，或支持您正在增强的应用程序？
- 您将如何连接到该数据？连接方式有多种（即使是同一个数据源），其中一些可能更适合或不太适合当前场景。
- 您将如何管理和控制与该数据源的连接的连通性、安全性和性能？

在本章中，我们将探讨几种对嵌入式分析有用的不同数据源，并考虑这些问题。

## CSV 和其他文本文件

在理论上，很少有像文本数据文件这样简单的数据源。文本文件在几乎每个企业的某些场景中都能找到，因为它们有一些很大的优势。首先，它们被从最简单的电子表格到最先进的数据科学工作台等各种数据分析工具广泛支持。逗号分隔值（CSV）文件作为导出格式也同样受到良好支持。连接到 CSV 文件通常只需要有权限读取其存储文件夹。因此，在许多情况下，它们是一个便捷的解决方案。

然而，这种便捷是有代价的：

## 安全性

CSV 文件唯一的安全机制是保护对其存储文件夹的访问。不支持行或列保护。因此，如果您将 CSV 文件用作数据源，必须在应用最严格的安全和隐私控制的情况下导出它们。请勿将敏感数据保存在这些文件中。

## 性能

大多数数据移动工具（例如用于数据仓库的提取、转换、加载（ETL）应用程序）都针对文本文件进行了一定程度的优化，特别是针对批量读取或写入数据。这些优化通常采用读写缓冲区的形式，将数据加载到内存中进行解析。BI 工具很少具备这些优化。它们可以轻松读取文本文件，但与本机应用程序驱动程序相比，性能可能较差。

## 解析

并非所有文本文件都是 CSV 文件。有些由制表符分隔，有些由管道或竖线字符分隔。高度自定义的分隔符很少见——而且具有讽刺意味的是，旨在成为标准的 ASCII 控制代码更加罕见——但您可能会遇到它们。数字方面可能出现许多问题，例如使用不同的小数分隔符（某些国家使用逗号）或千位分隔符的不寻常位置（例如印度编号系统，使用拉克和克罗尔）。如果您的分析环境不支持这些特性，则需要确保数据导出过程将文本文件呈现为易于读取的格式。

## 元数据

使用 CSV 文件时，如果我们只读取文件中的数据，则无法获得有关上次更新时间的元数据。例如，在金融领域，这些文件有时会在部门拥有所有可用数据时每周或每月手动更新一次。如果我们在电子表格中手动打开文件，可能会从文件名、某些标题单元格或文件中的嵌入式信息表中获取一些信息。但是，如果我们只是通过半自动化流程读取数据，则该元数据将丢失。此外，与数据库表不同，文本文件的人为错误风险更高，因为数字可以直接输入而无需验证。

## 运营数据源

运营数据源只是存储运营应用程序数据的位置。所有现代应用程序在某种程度上都会创建、存储和管理数据。例如，一个用于处理订单的应用程序会为每个订单生成数据，并可能链接每个客户的数据。这些数据需要持久化到某个地方。运营数据源专注于以一种方式集成这些数据，从而最大限度地提高应用程序性能并确保应用程序的完整性。在许多情况下，尤其是通过一个能够以良好性能持久化大量数据用于记录保存的强大数据存储，可以增强易用性，尤其是应用程序的响应能力。

许多应用程序对运营数据源采用非常简单的结构。例如，许多应用程序使用底层运营数据库。开发人员通常熟悉与该数据库的连接以及表结构，因为他们每天都在使用运营应用程序。而且，因为您直接连接到运营数据源，数据的一致性基本上得到了保证。

有时，您可以使用运营源的副本。例如，您可以利用复制等技术。对开发人员而言，其优势在于他们从事的分析工作不会影响运营应用程序本身。例如，您可以提取单个客户的所有记录，将它们聚合以进行一些分析，并



然后将其呈现给操作员。你不必在原始数据库中查找所有详细信息，因为你使用的是副本，这提高了性能并保留了原始数据源的一致性。

如前所述，运营数据结构针对效率和完整性进行了优化。但这意味着它们并未针对分析进行优化。在实际中，高度规范化数据库中表之间的连接可能非常复杂且难以导航，而且通常无法为分析提供最佳性能。在这种情况下，试图在这些表上执行分析会成为数据库的额外负载。

复制可以帮助解决这个问题，但如果复制延迟过大，你可能会发现运营与分析之间出现断续：刚在手机上下的订单在报表中不显示。

然而，连接到运营数据源通常很简单，因为你的运营应用程序已经连接到它。如果数据源是运营数据源的副本，连接仅略有不同，需要一个不同的连接字符串，但不需要其他更改。

如果试图结合两个运营系统——一个用于执行运营，另一个用于获取数据以增强分析——情况确实会变得稍微困难一些。

你可能有一个处理订单、发票以及订单到交付流程中各个方面的采购管理系统。客户数据可能位于不同的应用程序中，例如客户关系管理（CRM）系统或财务系统。将这两者结合在一起涉及将一个嵌入到另一个中，但它们都是运营系统，因此并非特别针对分析进行优化。

对于任何运营系统，通常有两种连接方式：通过大容量连接器或通过 API。大容量连接器针对提取大量数据进行了优化。示例是使用 OLE DB 或 JDBC 连接到支撑应用程序的运营数据库。使用此类连接器，你可以请求完整的表信息，或者一次请求多个表，并且可能针对其发出查询并返回结果集，结果集可能很小也可能很大。这种连接方式对于分析可能很有用，因为通常我们查看的是较大数据量以进行分析。

连接到运营系统的另一种方式是通过 API（如果支持）。Web 开发人员对此会很熟悉，因为大多数 Web 应用程序之间的连接都涉及 API 调用。然而，API 通常不是为返回大量数据而设计的：通常只返回单个记录或简单查询的答案，结果集可能作为 XML 文档而不是扁平表返回。更糟的是，API 调用中的数据量限制可能意味着开发人员必须分页查看数据，进行多次 API 调用以慢慢构建完整的结果集。

因此，我们在为分析选择要使用的连接类型时必须谨慎。OLE DB 连接器并不总是最佳选择。许多连接器非常简单，性能可能不佳。同样，API 也不总是不合适。某些 API 确实具有支持大容量数据提取的调用。换句话说，我们必须非常了解自己的系统，以了解我们试图提取的数据量、源系统的特性以及要求它执行的工作负载。

使用运营数据源的一种方式是向数据库架构添加新对象——视图和聚合表。聚合表和视图都是数据库设计中用于以有用方式组织和呈现数据的数据库对象。

聚合表包含汇总数据。它们可以预先计算并存储在数据库中，以提高查询性能并减少生成报表所需的时间。另一方面，视图是通过组合数据库中一个或多个现有表的数据创建的虚拟表。视图可以简化复杂查询，并为最终用户提供简化、有组织的数据视图。

## 分析数据源

## 数据仓库

最常见的分析数据源是 *数据仓库*，这是一种专门用于实现数据分析的架构。其数据是反规范化的，以简化查询并提高大型分析查询的性能。该架构旨在集成来自多个数据源的数据，因此不需要重复工作。最重要的是，数据仓库不仅代表数据结构，还代表商业模型。也就是说，它是企业运营方式的逻辑表示。

数据仓库将拥有一个 *客户维度*，用于表示企业对客户的看法，以及一个 *地理维度*，用于表示企业对其部门、办事处和商店或工厂的看法。数据仓库几乎总是包含一个 *时间维度*，用于表示与业务相关的日历、工作日、节假日和季节划分。它可能包含一个 *人员维度*，反映公司层次结构。所有这些预先设计和预填充的维度使开发人员的分析查询变得非常简单。更好的是，数据仓库应针对分析性能进行优化。

事实上，数据仓库——或其更简单、更专注的表亲，数据集市——是许多商业智能系统的主要来源，也是嵌入式分析的绝佳数据源。

但并非每个企业，当然也不是每个中小企业都拥有数据仓库。即使是拥有数据仓库的企业，也可能不希望将其提供给运营应用程序，因为在某些情况下，仓库专注于管理、财务或税务报告：即关键任务业务分析，这些分析可能很敏感或受到某种管理，企业不希望将数据直接提供给其他系统。

有时，我们可以通过创建特定主题领域以及我们经常使用的特定查询答案的下游复制来绕过这个问题。

## 内存引擎

我们熟悉的数据仓库技术自 20 世纪 90 年代起就已存在。大约在 2005 年，另一种技术开始出现，它具有数据仓库的许多优势，但提供了更高的性能和灵活性，并且对大中小企业都有好处。这就是 *内存引擎*，它利用内存相比于磁盘在执行复杂查询时的极高性能。随着 2000 年代中期 64 位系统（以及廉价内存芯片）的出现，公司可以在桌面上执行以前只能在最大型企业系统上才能进行的分析。

基于这些桌面功能，内存技术在自助式商业智能中非常流行，并且是许多最流行的自助式应用程序（例如 Microsoft Power BI、Salesforce Tableau 和 Qlik）的性能和灵活性的关键。在过去，自助式应用程序非常独立，专注于自身的分析能力。它们与其他系统的连接完全专注于将数据提取到自身的内存空间中，开发人员不太考虑如何将这些数据与其他系统共享。然而，如今可用的许多内存 BI 应用程序支持嵌入。因此，通常可以从 BI 工具获取图表并将其嵌入到运营应用程序中。这对开发人员在熟悉度、性能和简单性方面有好处，但也有一些限制，因为这些系统通常不是从一开始就设计为可嵌入的。相反，嵌入功能（和 API）可能是事后补救的，后期才添加的。尽管如此，对于熟悉这些系统的开发人员，以及系统已在业务或企业中部署的情况，这非常有吸引力



重用此功能并将其嵌入运营型应用程序中的提议。此场景通常得到工具及其用户社区的良好支持，是一个值得考虑的选项。

## 数据湖

像数据仓库一样，*数据湖*架构（以及其更现代的形态，*数据湖仓*）专注于大量数据的存储，这些数据可用于数据科学以及在某种程度上进行分析等目的。

与数据仓库不同，数据湖没有内置的业务模型——即代表企业如何看待自身的逻辑语义架构，包含规则、治理的明确定义流程，或易于导航的数据结构。事实上，数据湖的设计目的是*未经任何处理*地以最原始格式存储数据。这对数据科学家来说是一个巨大的优势，因为他们通常希望以原生状态查看数据，因为他们可以使用这些原始数据进行比在数据已被清理并构建为报告数据模型时更详细、更复杂的分析。

在数据湖中，数据科学家可以看到所有原始细节，包含其中的所有错误和复杂性。但业务用户可能会发现，在需要时很难集成和转换数据湖中的数据。

## 数据集成管道

嵌入式系统的另一个数据来源可能是*数据集成管道*的输出。也就是说，数据不是从内存系统、数据仓库或运营数据库中的表读取，而是从在数据科学环境中运行的管道读取。该管道可能会对来自任何来源的数据执行多种集成、清洗和准备操作。这是数据科学的常见场景。然而，对于嵌入式分析来说，其用途有限，因为管道更加动态和易变，仅在运行时提供数据，这使得过程比数据仓库或内存系统更脆弱、更难以治理。

此场景流行且有用的情况是数据在不断变化时，称为*流式数据*。这可能包括来自机器的数据，例如制造业中的自动车床，或来自电子商务订购系统的数据（每分钟可能下数百个订单），或来自环境传感器的数据。

在这种情况下，分析场景有些不同，性能仍需考虑。提供流式分析的应用程序必须包含处理流中断的方法。此外，它必须能够显示变化的值，而无需用户手动刷新显示。最后，治理和安全的方法可能与我们习惯的分析治理不同。

## 向源写回

关于嵌入式分析中的数据处理，还有一点需要说明。迄今为止，我们一直在讨论从源系统*提取*的数据，并在嵌入式分析环境中纯粹为了信息和增强目的而呈现。这是一个只读场景。然而，有时我们可能希望从嵌入式应用程序内部对分析系统进行更改——我们称之为*写回*。

写回常用于规划和模拟应用程序，我们希望插入代表未来销售、人员配置或增长预估的数字，或者我们正在围绕其进行规划的任何参数。对于设计用于分析的系统（例如数据仓库）来说，启用直接写回相对罕见。此类系统过于关注数据完整性、数据历史记录和合规性，不允许临时更改。但通常它们会允许向特殊表写回，这些表可以专门为此目的设置为参数表。

## 摘要

我们已经看到，嵌入式分析的数据可以来自许多不同类型的系统：运营型、分析型和流式。对于典型的嵌入式场景，没有唯一的最佳解决方案，但可以公平地说，大多数嵌入式应用程序开发人员如果组织内已有简单的数据仓库或数据集市场景，会先从该场景开始。

在这种情况下，您可能会发现从为您的目的定义并在运营数据库中托管的视图和汇总表开始很实际。管理员可以配置访问权限并确保安全和良好治理，性能应可接受，并且数据访问应通过合适的驱动程序实现。
