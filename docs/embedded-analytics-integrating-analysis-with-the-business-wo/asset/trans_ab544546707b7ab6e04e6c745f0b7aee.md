## 数据湖

像数据仓库一样，*数据湖*架构（以及其更现代的形态，*数据湖仓*）专注于大量数据的存储，这些数据可用于数据科学以及在某种程度上进行分析等目的。

与数据仓库不同，数据湖没有内置的业务模型——即代表企业如何看待自身的逻辑语义架构，包含规则、治理的明确定义流程，或易于导航的数据结构。事实上，数据湖的设计目的是*未经任何处理*地以最原始格式存储数据。这对数据科学家来说是一个巨大的优势，因为他们通常希望以原生状态查看数据，因为他们可以使用这些原始数据进行比在数据已被清理并构建为报告数据模型时更详细、更复杂的分析。

在数据湖中，数据科学家可以看到所有原始细节，包含其中的所有错误和复杂性。但业务用户可能会发现，在需要时很难集成和转换数据湖中的数据。

## 数据集成管道

嵌入式系统的另一个数据来源可能是*数据集成管道*的输出。也就是说，数据不是从内存系统、数据仓库或运营数据库中的表读取，而是从在数据科学环境中运行的管道读取。该管道可能会对来自任何来源的数据执行多种集成、清洗和准备操作。这是数据科学的常见场景。然而，对于嵌入式分析来说，其用途有限，因为管道更加动态和易变，仅在运行时提供数据，这使得过程比数据仓库或内存系统更脆弱、更难以治理。

此场景流行且有用的情况是数据在不断变化时，称为*流式数据*。这可能包括来自机器的数据，例如制造业中的自动车床，或来自电子商务订购系统的数据（每分钟可能下数百个订单），或来自环境传感器的数据。

在这种情况下，分析场景有些不同，性能仍需考虑。提供流式分析的应用程序必须包含处理流中断的方法。此外，它必须能够显示变化的值，而无需用户手动刷新显示。最后，治理和安全的方法可能与我们习惯的分析治理不同。

## 向源写回

关于嵌入式分析中的数据处理，还有一点需要说明。迄今为止，我们一直在讨论从源系统*提取*的数据，并在嵌入式分析环境中纯粹为了信息和增强目的而呈现。这是一个只读场景。然而，有时我们可能希望从嵌入式应用程序内部对分析系统进行更改——我们称之为*写回*。

写回常用于规划和模拟应用程序，我们希望插入代表未来销售、人员配置或增长预估的数字，或者我们正在围绕其进行规划的任何参数。对于设计用于分析的系统（例如数据仓库）来说，启用直接写回相对罕见。此类系统过于关注数据完整性、数据历史记录和合规性，不允许临时更改。但通常它们会允许向特殊表写回，这些表可以专门为此目的设置为参数表。

## 摘要

我们已经看到，嵌入式分析的数据可以来自许多不同类型的系统：运营型、分析型和流式。对于典型的嵌入式场景，没有唯一的最佳解决方案，但可以公平地说，大多数嵌入式应用程序开发人员如果组织内已有简单的数据仓库或数据集市场景，会先从该场景开始。

表 4-1 汇总了我们讨论过的方法的一些优点和缺点。

## 表 4-1. 嵌入式分析的数据源

| 数据源 | 优点 | 缺点 |
|---|---|---|
| CSV 文件 | 支持广泛，通常人类可读。 | 没有安全机制。可能难以解析。性能可能较差。易受用户错误影响。 |
| 运营数据库 | 开发人员熟悉连接和表结构。因为您连接到运营数据，所以一致性有保证。如果可用复制，您可以使用运营系统的副本进行分析。 | 运营表结构针对高效事务而非分析进行了优化。连接可能很复杂。分析是数据库的额外负载，可能影响性能，尽管复制可以提供帮助。 |
| 视图和聚合表 | - 由于连接是预先开发的，分析查询已简化。<br>- 过滤简单。<br>- 您可以简单地应用基于角色的访问规则，或将其构建到视图中。（如某些云数据仓库中的受保护视图。）<br>- 预先聚合数据可提高性能。 | - 如果底层连接复杂，响应时间可能较慢。<br>- 视图和聚合表必须与运营表分开维护：对管理员的另一项负担。<br>- 聚合表必须更新，通常使用触发器。更新必须仔细安排，否则会影响运营系统的性能。 |
| 数据集市或数据仓库 | • 高性能，因为架构和模式针对分析查询进行了优化。<br>• 与 BI 和分析工具集成简单，因为模式是为分析设计的。<br>• 降低了事务源系统的负载。 | • 使用 ETL 加载数据仓库是一种专业实践。<br>• 数据仓库的加载和刷新周期（通常安排在夜间运行）对于嵌入到运营应用程序中的分析可能太慢。<br>• 更改模式可能很复杂，需要冗长的指定、实施和测试过程。 |
| 内存引擎 | • 性能非常高。<br>• 应与嵌入式分析环境紧密集成。 | • 对向数据库写回的支持通常有限。<br>• 数据更新可能是偶发的，并且通常需要完整更新，而不是增量更新。 |
| 数据湖 | • 如果使用数据湖仓架构，您将发现许多与数据仓库相同的优点。<br>• 数据通常以其原生格式存储，这对预测分析有好处。<br>• 数据可能会持续更新。 | • 如果不使用湖仓架构，您可能会发现商业智能性能较差，因为需要大量转换来使数据符合规范并成型。<br>• 数据湖通常与数据科学家、数据工程师和分析人员共享。安全可能是一个问题。<br>• 使用原始数据会增加用户看到同一数据不同变体的风险，因为数据未像在数据仓库或数据集市中那样得到充分验证。 |

一般来说，如果组织架构中已存在数据集市或数据仓库连接，我们建议从中开始。您会发现它能为您的需求提供可访问性、性能和治理之间的最佳平衡。如果管理得当，数据湖或湖仓也提供一些类似的优势。然而，如果您尚未部署正式的数据仓库或湖仓，构建一个需要大量努力，很可能仅凭您的嵌入式分析项目无法承担。
