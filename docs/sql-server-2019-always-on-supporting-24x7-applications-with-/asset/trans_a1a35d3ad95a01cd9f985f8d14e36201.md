
如果在日志传送备份或复制作业正在进行时发生故障转移，则日志传送可能会不同步并需要人工干预。这意味着在故障转移后，您应检查日志传送作业的健康状况。

# 摘要
理解可用性的概念是为需要高可用性和灾难恢复的应用程序做出正确实施选择的关键。您应计算停机成本并将其与实施 `HA/DR` 解决方案选择的成本进行比较，以帮助企业了解每个选项的成本/效益概况（如第 [1](#394392_3_En_1_Chapter.xhtml) 章所述）。在选择技术实施时，您还应注意 `SLAs`，因为如果未满足 `SLAs`，可能会产生财务处罚。

`SQL Server` 提供了一整套高可用性和灾难恢复技术，使您能够实施最适合数据层应用程序需求的解决方案。对于高可用性，您可以实施集群或 AlwaysOn 可用性组（`AOAG`）。集群使用共享磁盘资源，故障转移发生在实例级别。`AOAG` 另一方面，通过维护数据库的冗余副本以及同步日志流，在数据库级别同步数据。

要实现灾难恢复，您可以选择实施 `AOAG` 或日志传送。日志传送通过备份、复制和还原数据库的事务日志来工作，而 `AOAG` 使用异步日志流同步数据。

还可以将多个 HA 和 DR 技术组合在一起，以实施最合适的可用性策略。其常见示例是为高可用性组合集群，并与 `AOAG` 或日志传送结合以提供 DR。

# 3. 实施集群
Peter A. Carter^([1](#394392_3_En_3_Chapter.xhtml#Aff2) ) (1) Botley, UK 结束摘要

工程师可能会发现构建和配置集群的过程很复杂，并且可以实施该模式的许多变体。虽然 DBA 可能并不总是需要自己构建集群，但他们确实需要熟悉该技术，并且通常需要为该过程提供意见。他们还可能参与排查集群中发现的问题。

因此，本章讨论如何在 Windows 级别构建集群并讨论一些可能的配置。本章中的演示使用预建环境，由两台服务器组成；`ClusterNode1` 和 `ClusterNode2`。两台服务器都位于名为 `AlwaysOn.com` 的域中。五个卷已从 `SAN` 呈现给节点，并在 `ClusterNode1` 上联机并格式化，其配置在表 [3-1](#394392_3_En_3_Chapter.xhtml#Tab1) 中详细说明。表 3-1

| --- | --- | --- | --- |

提示
您可能会惊讶于数据和日志文件分配了单个卷，因为 DBA 的自然本能是将这些文件分离到单独的驱动器。这里需要记住的重要一点是，我们正在使用 `SAN`，并且即使我们使用单独的卷，这些卷也很有可能位于相同的物理磁盘上，这意味着分离仅是逻辑上的。此外，如果要使用 SAN 快照，一些 SAN 可能要求数据和日志文件存储在同一卷上以确保数据一致性。

本章的场景要求我们构建一个具有磁盘见证的两节点故障转移集群。在此之前，我们需要配置 Windows 集群服务（`WCS`）。我们还需要配置一个 `MSDTC`（Microsoft Distributed Transaction Coordinator）集群角色，该角色将为 `SSIS`（`SQL Server Integration Services`）提供分布式事务协调。此外，我们需要配置：
* 将 `MSDTC` 角色配置为以高优先级故障转移（与同一集群上的其他角色相比）。
* 任何 24 小时期间允许三次故障转移。
* 允许立即回退。

因此，我们将执行的任务完整列表如下：
* 安装故障转移群集功能。
* 构建名为 `ALWAYSON-C` 的 Windows 集群。
* 正确配置仲裁。
* 为 `MSDTC` 创建集群角色，名为 `ALWAYSON-MSDTC-C`。
* 配置 `MSDTC` 角色的属性。
* 配置 `MSDTC` 角色的故障转移属性。

提示
如果您希望出于学习目的构建集群，但没有访问域或 `SAN`，那么集群的新功能允许您模拟非常相似的拓扑。可以使用两台虚拟机作为集群节点。第三台虚拟机运行 Windows 的 `iSCSI Target` 功能，可用于向这些节点中的每一个提供共享存储。甚至更好的是，`Windows Server 2016` 及更高版本允许在工作组上创建集群，这意味着无需创建额外的虚拟机用作域控制器。但是请注意，在工作组中创建集群仅在 `PowerShell` 中受支持，而不通过 `Failover Cluster Manager`。还需要注意的是，从 `SQL Server` 角度来看，可用性组在工作组集群上受支持，但故障转移群集实例不受支持。
