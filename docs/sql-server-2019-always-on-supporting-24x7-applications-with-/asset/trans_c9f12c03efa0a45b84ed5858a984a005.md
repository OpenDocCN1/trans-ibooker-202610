
## 仅读路由

在 `Read-Only Routing tab` 上，如 Figure [5-11](#394392_3_En_5_Chapter.xhtml#Fig11) 所示，我们将 `CLUSTERNODE4\READSCALE` 实例配置为可读的次要副本。发送到 `listener` 的只读请求将被重定向到此实例，而不是发送到 `primary replica`，后者将驻留在其他三个实例之一上。此配置的第一步是为可读次要副本添加 `Read-Only Routing URL`。这与我们为每个节点配置的 `Endpoint URL` 类似，不同之处在于它将处理只读请求。`Read-Only URL` 可以是 `IP address` 或 `FQDN`，并且必须包含实例正在监听的 `port`。这意味着在执行此配置之前，您必须确保实例正在静态 `port` 上监听。![图 5-11 ¶ 仅读路由选项卡 – 配置仅读路由 URL](images/394392_3_En_5_Chapter/394392_3_En_5_Fig11_HTML.jpg)

图 5-11 ¶ 仅读路由选项卡 – 配置仅读路由 URL

一旦 `Read-Only routing URL` 已添加到您计划配置的每个可读次要副本中，可读次要副本将出现在选项卡下半部分的 `Available Replicas` 窗口中。您现在可以为希望能够路由到可读次要副本的每个副本选择 `Read-Only Routing List` 单元格，并单击选项卡下半部分的 `Add` 按钮，以将其添加到 `Read-Only Routing List` 中，如 Figure [5-12](#394392_3_En_5_Chapter.xhtml#Fig12) 所示。![图 5-12 ¶ 仅读路由选项卡 – 配置仅读路由列表](images/394392_3_En_5_Chapter/394392_3_En_5_Fig12_HTML.jpg)

图 5-12 ¶ 仅读路由选项卡 – 配置仅读路由列表

此示例显示了一个简单的配置，其中所有节点（在托管 `primary replica` 时）都可以将读请求卸载到单个可读次要副本。但是更复杂的排列也是可能的。例如，您可以配置每个节点路由到单独的可读次要副本。如果您的可用性组分布在多个站点中，并且您希望确保每个节点将只读请求路由到同一站点的副本中，这将非常有用，从而提高读扩展的冗余性。

另外，您可以允许每个节点将只读请求路由到多个可读次要副本。在此场景中，您有两个选项。默认实现将始终将读请求发送到第一个可用的副本，因此您只是为可读次要副本添加了冗余。如果这是意图，则路由列表中的每个可读次要副本将用逗号分隔。更高级的实现是配置可读次要副本以进行只读请求的负载均衡。在此场景中，只读请求将使用轮询方式在负载均衡的集合中进行路由。负载均衡集合内的节点将用逗号分隔，集合用括号括起来。

您还可以在同一路由列表中配置多个负载均衡集合。在这里，请求将轮询第一个负载均衡集合，除非该集合中的节点变得不可用，在这种情况下，请求将轮询下一个集合。

例如，假设您希望只读请求在 `ServerA` 和 `ServerB` 之间进行负载均衡，但如果这些服务器变得不可用，您希望请求在 `ServerC` 和 `ServerD` 之间进行负载均衡。您的只读路由列表将采用以下形式：`((ServerA,ServerB),(ServerC,ServerD))`。

一旦我们创建了可用性组，我们需要创建可用性组侦听器。为此，我们从 `Sales Availability Group` 的上下文菜单中选择 `New Listener`，它现在应该在 `Object Explorer` 中可见。这会调用 `New Availability Group Listener dialog box`，可在 Figure [5-13](#394392_3_En_5_Chapter.xhtml#Fig13) 中看到。![图 5-13 ¶ 新建可用性组侦听器对话框](images/394392_3_En_5_Chapter/394392_3_En_5_Fig13_HTML.jpg)

图 5-13 ¶ 新建可用性组侦听器对话框

在此对话框中，我们首先输入侦听器的 `virtual name`。然后我们定义它将监听的 `port` 和将分配给它的 `IP address`。

### Tip

我们能够为两个侦听器以及 SQL Server 实例使用相同的 `port`，因为所有三个都使用不同的 `IP addresses`。

## Using T-SQL

现在我们已使用 `SSMS` 中的 GUI 方法创建了可用性组，让我们看看如何使用 T-SQL 创建可用性组。在本节中，我们将创建一个名为 `Accounts` 的可用性组，它将为 `Accounts` 数据库提供 HA 和 DR。如往常一样，我们需要做的第一件事是对数据库进行完整备份。我们可以使用 Listing [5-5](#394392_3_En_5_Chapter.xhtml#PC5) 中的脚本来实现。

```
BACKUP DATABASE HR TO DISK = N'C:\\Backups\\HR.bak' WITH NAME = N'HR-Full Database Backup' ;
GO
```

备份 `Accounts` 数据库

要创建可用性组，我们将使用 `CREATE AVAILABILITY GROUP` T-SQL 命令。此命令支持的 `WITH` 选项在 Table [5-1](#394392_3_En_5_Chapter.xhtml#Tab1) 中详细说明。

Table 5-1

`CREATE AVAILABILITY GROUP` with Options

| 选项 | 描述 |
| --- | --- |
| `AUTOMATED_BACKUP_PREFERENCE` | 指定应为备份使用哪个副本。可选选项为 `PRIMARY`，表示将始终使用主要副本；`SECONDARY_ONLY`，表示不应在主要副本上执行备份；`SECONDARY`，表示除非主要副本是唯一在线的副本，否则不应在主要副本上获取备份；以及 `NONE`，表示在选择要从中获取备份的副本时，将忽略每个副本的角色。 |
| `FAILURE_CONDITION_LEVEL` | 指定应导致可用性组自动故障转移的事件。可接受的级别为 1–5*。 |
| `HEALTH_CHECK_TIMEOUT` | 以毫秒为单位指定，集群在假设节点无响应并进行故障转移之前，将等待健康检查过程响应的持续时间。 |
| `DB_FAILOVER` | 当可用性组具有多个数据库时，确定可用性组中单个数据库移出 ONLINE 状态是否会触发故障转移。 |
| `DTC_SUPPORT` | 指定是否使用 DTC（分布式事务协调器）在可用性组内支持跨数据库事务。可接受的值为 `PER_DB` 或 `NONE`。 |
| `BASIC` | 用于创建基本可用性组。基本可用性组在第 [7](#394392_3_En_7_Chapter.xhtml) 章中讨论。 |
| `DISTRIBUTED` | 用于创建分布式可用性组。这在第 [7](#394392_3_En_7_Chapter.xhtml) 章中讨论。 |
| `REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT` | 可用于通过在继续之前强制在次要副本上提交来确保零 RPO。0 表示事务将被标记为 NOT SYNCHRONIZED，但副本将继续处理事务。 |
| `CLUSTER_TYPE` | 指定可用性组所在的集群类型。可能的值为 `WSFC`，表示 Windows 故障转移集群；`EXTERNAL`，表示非 Windows 集群，例如 Linux Pacemaker；或 `NONE`，表示无集群可用性组。 |
