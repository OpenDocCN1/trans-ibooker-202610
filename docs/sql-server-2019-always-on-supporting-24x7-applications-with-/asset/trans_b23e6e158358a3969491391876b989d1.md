# 前言

## 引言

*SQL Server 2019 AlwaysOn* 旨在成为 DBA 的快速入门指南，他们需要为其 SQL Server 工作负载实施高可用性和灾难恢复。

本书首先讨论高可用性概念和方法，然后对 HA/DR 技术进行高层次概述。随后进入细节。我们将讨论如何创建 Windows 集群，然后介绍如何创建 SQL Server AlwaysOn 故障转移群集实例。

本书的重点随后转向 AlwaysOn 可用性组。在这里，本书讨论如何在 Windows 和 Linux 操作系统上为高可用性和灾难恢复创建和配置可用性组。

我们随后将探讨 AlwaysOn 可用性组的非典型用例，例如无群集和域无关的可用性组，以及在 Azure IaaS 上配置可用性组和 SQL Server 标准版的基础可用性组。

最后，本书关注 AlwaysOn 的运维方面，其中章节涵盖该技术的管理、监控和故障排除。

# 1. 高可用性和灾难恢复概念

Peter A. Carter^([1](#394392_3_En_1_Chapter.xhtml#Aff2) ) (1) Botley, UK 结束摘要

在当今运行关键任务应用程序的 24×7 环境中，企业在很大程度上依赖于其数据的可用性。虽然服务器及其软件通常是可靠的，但硬件故障或软件错误仍有可能导致服务器宕机，从而带来风险。为了减轻这些风险，业务关键型应用程序通常依赖冗余硬件来提供容错能力。如果主系统发生故障，则应用程序可以自动故障转移到冗余系统。这就是高可用性（HA）的基本原理。

即使实施了 HA 技术，应用程序变得不可用的事件仍存在很小的风险。这可能是由于重大事故，例如自然灾害或恐怖行为导致数据中心丢失。也可能是由于数据损坏或人为错误导致应用程序数据丢失或损坏无法修复。

在这些情况下，一些应用程序可能会依赖于恢复最新的备份来尽可能多地恢复数据。然而，更关键的应用程序可能需要冗余服务器在二级位置保存数据的同步副本。这就是灾难恢复（DR）的基本概念。本章讨论 HA 和 DR 背后的概念。

## 可用性级别

解决方案可供终端用户使用的时长称为 *可用性级别*，或 *正常运行时间*。为了提供正常运行时间的真实图景，公司应从用户桌面衡量解决方案的可用性。换句话说，即使您的 SQL Server 已不间断运行超过一个月，用户仍可能因其他因素而经历解决方案的中断。这些因素可能包括网络中断或应用程序服务器故障。

然而，在某些情况下，您别无选择，只能在 SQL Server 级别衡量可用性级别。这可能是因为企业内部缺乏整体监控工具。最常见的是，在实例级别衡量可用性级别的要求是政治上的，而非技术上的。在 IT 行业，已成为一种趋势，即将数据中心的运营外包给第三方提供商。在这种情况下，负责管理 SQL 服务器的提供商可能不一定是负责网络或应用程序服务器的提供商。在这种情况下，您需要在 SQL Server 级别监控正常运行时间，以准确判断服务提供商的性能。
