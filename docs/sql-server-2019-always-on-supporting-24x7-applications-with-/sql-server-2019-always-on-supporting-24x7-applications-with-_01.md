# 1. 高可用性和灾难恢复概念

Peter A. Carter^(1 ) (1) Botley, UK 结束摘要

在当今运行关键任务应用程序的 24×7 环境中，企业在很大程度上依赖于其数据的可用性。虽然服务器及其软件通常是可靠的，但硬件故障或软件错误仍有可能导致服务器宕机，从而带来风险。为了减轻这些风险，业务关键型应用程序通常依赖冗余硬件来提供容错能力。如果主系统发生故障，则应用程序可以自动故障转移到冗余系统。这就是高可用性（HA）的基本原理。

即使实施了 HA 技术，应用程序变得不可用的事件仍存在很小的风险。这可能是由于重大事故，例如自然灾害或恐怖行为导致数据中心丢失。也可能是由于数据损坏或人为错误导致应用程序数据丢失或损坏无法修复。

在这些情况下，一些应用程序可能会依赖于恢复最新的备份来尽可能多地恢复数据。然而，更关键的应用程序可能需要冗余服务器在二级位置保存数据的同步副本。这就是灾难恢复（DR）的基本概念。本章讨论 HA 和 DR 背后的概念。

## 可用性级别

解决方案可供终端用户使用的时长称为 *可用性级别*，或 *正常运行时间*。为了提供正常运行时间的真实图景，公司应从用户桌面衡量解决方案的可用性。换句话说，即使您的 SQL Server 已不间断运行超过一个月，用户仍可能因其他因素而经历解决方案的中断。这些因素可能包括网络中断或应用程序服务器故障。

然而，在某些情况下，您别无选择，只能在 SQL Server 级别衡量可用性级别。这可能是因为企业内部缺乏整体监控工具。最常见的是，在实例级别衡量可用性级别的要求是政治上的，而非技术上的。在 IT 行业，已成为一种趋势，即将数据中心的运营外包给第三方提供商。在这种情况下，负责管理 SQL 服务器的提供商可能不一定是负责网络或应用程序服务器的提供商。在这种情况下，您需要在 SQL Server 级别监控正常运行时间，以准确判断服务提供商的性能。




## 可用性

可用性水平以应用程序或服务器可用时间的百分比来衡量。公司通常力求达到 99%、99.9%、99.99% 或 99.999% 的可用性。因此，可用性水平通常以 9 的数量来表示。例如，五個 9 的可用性意味着 99.999% 的正常运行时间，而三个 9 意味着 99.9% 的正常运行时间。

*所有值均向下舍入到最接近的秒。*

要计算其他可用性级别，您可以使用列表 1-1 中的脚本。在运行此脚本之前，将 `@Uptime` 的值替换为要计算的正常运行时间级别。您还应将 `@UptimeInterval` 的值替换为每周、每月或每年的正常运行时间。

```sql
DECLARE @Uptime DECIMAL(5,3); --Specify the uptime level to calculate
SET @Uptime = 99.9;
DECLARE @UptimeInterval VARCHAR(5); --Specify WEEK, MONTH, or YEAR
SET @UptimeInterval = 'YEAR';
DECLARE @SecondsPerInterval FLOAT; --Calculate seconds per interval
SET @SecondsPerInterval = (
    SELECT CASE
        WHEN @UptimeInterval = 'YEAR' THEN 60*60*24*365.243
        WHEN @UptimeInterval = 'MONTH' THEN 60*60*24*30.437
        WHEN @UptimeInterval = 'WEEK' THEN 60*60*24*7
    END
);
DECLARE @UptimeSeconds DECIMAL(12,4); --Calculate uptime
SET @UptimeSeconds = @SecondsPerInterval * (100-@Uptime) / 100;
--Format results
SELECT
    CONVERT(VARCHAR(12), FLOOR(@UptimeSeconds /60/60/24)) + ' Day(s), '
    + CONVERT(VARCHAR(12), FLOOR(@UptimeSeconds /60/60 % 24)) + ' Hour(s), '
    + CONVERT(VARCHAR(12), FLOOR(@UptimeSeconds /60 % 60)) + ' Minute(s), '
    + CONVERT(VARCHAR(12), FLOOR(@UptimeSeconds % 60)) + ' Second(s).';
```

### 实际可用性

现在我们了解了如何计算应用程序所需的可用性级别，我们还应了解如何计算应用程序的实际可用性。我们可以通过确定 MTBF（平均故障间隔时间）和 MTTR（平均恢复时间）指标来实现。

MTBF 指标描述了两次故障之间的平均时间长度。例如，假设我们正在审查过去一周的服务日志，发现 Foo 应用程序发生了三次中断。一周有 168 小时，发生了三次故障。我们只需将时间段内的小时数除以故障次数即可。这将产生我们的 MTBF。在这种情况下，我们的 MTBF 为 56 小时。

MTTR 实际上有两个不同的含义：平均恢复时间或平均修复时间。当没有部署 HA 或 DR 时，MTTR 指标描述的是损坏的东西被修复所需的平均时间长度。这可能是一个较长的时期，因为我们可能需要等待服务工程师更换故障硬件。然而，在考虑 HA 和 DR 时，我们使用 MTTR 指标来表示平均恢复时间，以记录停机的持续时间。例如，如果我们有一个三节点集群，其中一个节点出现硬件故障，当然我们需要修复此服务器，但从应用程序停机角度来看，我们只会有几秒钟或几分钟的停机时间，同时服务进行故障转移并且我们仍然具有弹性，这意味着应用程序的非功能性需求不受影响。因此，在本例中，我假设 MTTR 指的是“平均恢复时间”。

我们可以通过对我们期间内的总停机持续时间求和并除以故障次数来计算 MTTR。在这种情况下，在我们的 168 小时期间，我们发生了三次故障，总停机持续时间为 12 分钟。因此，我们的 Foo 应用程序的 MTTR 为 4 分钟。

现在我们知道了应用程序的 MTBF 和 MTTR，我们可以使用这些指标来计算应用程序的实际可用性。该公式为 `(MTBF/(MTBF+MTTR))*100`。因此，在这种情况下，我们首先需要将 MTTR 值转换为小时，以便我们的单位保持一致。四分钟是 0.06667 小时。因此，我们的计算将为 `(56/(56+0.6667))*100`。这使得我们实际的应用程序可用性为 99.8811%。

### 服务级别协议和服务级别目标

当第三方提供商负责管理服务器时，合同通常包括服务级别协议（SLAs）。这些 SLA 定义了许多参数，包括可接受的停机时间、故障情况下服务器可停机的最长时间以及故障发生时可接受的数据丢失量。通常，如果未满足这些 SLA，提供商将面临财务处罚。

如果服务器由内部管理，DBA 仍然有客户的概念。这些通常是应用程序的最终用户，主要联系人是业务负责人。应用程序的业务负责人是业务中委托该应用程序的利益相关者，并且负责签署资金增强等事项。

在内部管理场景中，仍然可以定义 SLA，在这种情况下，IT 基础设施或平台部门如果未满足这些 SLA，可能需要向业务团队收取费用。然而，在内部场景中，IT 部门更常见的做法是与业务团队协商服务级别目标（SLO），而不是 SLA。SLO 在性质上与 SLA 非常相似，但其使用意味着如果未满足，业务不会对 IT 部门施加财务处罚。

### 主动维护

重要的是要记住，停机不仅由故障引起，还由主动维护引起。例如，如果您需要使用最新的服务包为操作系统或 SQL Server 本身打补丁，则在安装期间必须有一定停机时间。

根据所应用的升级，此类场景中的停机时间可能相当可观——对于单台服务器来说可能需要数小时。在这种情况下，高可用性对于许多业务关键型应用程序至关重要——不是为了防止计划外停机，而是为了避免计划维护期间的长时间中断。

## 恢复点目标和恢复时间目标

应用程序的恢复点目标（RPO）表示在发生故障时可接受的数据丢失量。例如，对于支持报表应用程序的数据仓库，这可能是一个较长的时期，例如 24 小时，因为它可能每天仅由 ETL 过程更新一次，其余所有活动都是只读报表。对于高度事务性的系统，例如支持交易平台或 Web 应用程序的 OLTP 数据库，RPO 将为零。RPO 为零意味着不允许任何数据丢失。



## RPO 与 RTO

应用可能对高可用性和灾难恢复有不同的 `RPOs`。例如，出于成本或应用性能方面的原因，站点内故障转移可能需要零的 `RPO`。然而，如果同一应用故障转移到 DR 数据中心，五到十分钟的数据丢失可能是可以接受的。这是因为实现站点内可用性和站点间恢复所使用的技术存在差异。

应用的恢复时间目标（`RTO`）指定了在恢复完成且用户可以重新连接之前，应用最多可以停机的时长。计算应用可实现的 `RTO` 时，需要考虑许多方面。例如，集群从一个节点故障转移到另一个节点以及 `SQL Server` 服务恢复运行可能不到一分钟；然而，数据库的恢复可能需要更长的时间。数据库恢复所需的时间取决于许多因素，包括数据库的大小、实例中的数据库数量以及故障转移发生时有多少事务正在进行中。这是因为所有未提交的事务都需要回滚。

就像 `RPO` 一样，根据是站点内还是站点间故障转移，存在不同的 `RTOs` 是很常见的。再次，这主要是由于技术差异，但也考虑了如果主数据中心丢失，需要在 DR 数据中心启动整个环境所需的时间。

在数据损坏的情况下，应用的 `RPO` 和 `RTO` 也可能有所变化。根据损坏的性质以及已实施的 HA/DR 技术，数据损坏可能导致您需要从备份中恢复数据库。

如果必须恢复数据库，最坏的情况是可恢复点可能就是上次备份的时间。这意味着您必须将对特定 `RPO` 的严格业务要求纳入备份策略。然而，如果只有数据库的一部分损坏，您可能能够从实时数据库中挽救一些数据，并仅从已恢复的数据库中恢复损坏的数据。

数据损坏也可能对 `RTO` 产生影响。最大的影响因素之一是备份是存储在服务器本地，还是需要从磁带中检索。从磁带或甚至异地位置检索备份文件很可能会在恢复过程中增加大量时间。

### 注意

从 `SQL Server` 直接备份到磁带已被弃用。当本节提到从磁带检索备份时，它假设磁带驱动器是企业备份解决方案的目标，您的数据库备份已卸载到该目标。

另一个影响因素是损坏的原因。如果是由有故障的 IO 子系统引起，则可能需要考虑 Windows 管理员对卷运行磁盘检查命令（`CHKDSK`）所需的时间，以及可能更换磁盘所需的时间。然而，如果损坏是由用户意外截断表或删除数据文件引起，则不必担心。

## 停机成本

如果您询问任何企业主其应用可接受的停机时间和数据丢失量，答案无一例外都是零和零。当然，不可能保证零停机，一旦您开始解释不同可用性级别相关的成本，就更容易协商一个双方都能接受的服务水平。

决定应追求多少个 9 的关键因素是停机成本。停机涉及两类成本：有形成本和无形成本。有形成本通常相当容易计算。让我们以销售应用为例。在这种情况下，最明显的有形成本是收入损失，因为销售人员无法接单。无形成本更难以量化，但可能昂贵得多。例如，如果客户无法向贵公司下单，他们可能会向竞争对手下单且不再回头。其他无形成本可能包括员工士气下降，导致员工流失率升高，甚至公司声誉受损。由于无形成本本质上只能估算，业界的经验法则是将有形成本乘以三，并用该数字代表无形成本。

一旦您获得了应用停机总成本的每小时数值，您可以将其按应用的预测生命周期进行扩展，并比较实施不同可用性级别的成本。例如，假设您计算出应用的停机总成本为 $2,000/小时，且应用的预测生命周期为三年。表 1-2 说明了您应用的停机成本，比较了在考虑硬件、许可证、电力、布线、额外存储以及额外支持设备（如新机架、行政成本等）后，为实施每个可用性级别而计算的成本。这被称为解决方案的总拥有成本（`TCO`）。表 1-2

停机成本

| 可用性级别 || 停机成本（三年） || 可用性解决方案成本 |
| --- | --- | --- |
| 99% || $525,600 || $108,000 |
| --- | --- | --- |
| 99.9% || $52,560 || $224,000 |
| 99.99% || $5,256 || $462,000 |
| 99.999% || $526 || $910,000 |

在此表中，您可以看到实施五个 9 的可用性相比两个 9 的解决方案可节省 $525,074，但实施该解决方案的成本额外增加 $802,000，这意味着实施在经济上不可行。四个 9 的可用性相比两个 9 的解决方案可节省 $520,344，且实施成本仅额外增加 $354,000。因此，对于此特定应用，四 9 解决方案是最合适的服务水平设计目标。

## 总结

您应用的可用性级别以应用对用户可用时间的百分比来衡量。可用性级别通常以“九”来表示。例如，99.9% 的正常运行时间要求被称为三个 9 的可用性。正常运行时间要求越高，实施解决方案的成本越高。因此，您力求达到的正常运行时间级别应由 `SLAs` 和停机成本驱动。



恢复点目标是衡量在发生灾难时可以接受丢失多少数据的指标。例如，如果你的唯一灾难恢复解决方案是备份，并且备份安排每小时执行一次，你可以实现一小时的恢复点目标。恢复时间目标是衡量在故障后恢复解决方案所需时间的指标。例如，如果你的恢复时间目标为 30 分钟，那么你必须能够在半小时内恢复服务。

确定应用程序停机成本非常重要，因为这是决定可用性水平的主要驱动因素之一。停机成本包括有形成本和无形成本。有形成本可以计算，而无形成本需要估算。

冗余基础设施有助于维护应用程序和服务的可用性。冗余服务器将被分类为热备、温备或冷备。热备服务器是指与生产服务器保持同步并配置为允许自动故障转移的服务器。这适用于高可用性场景。温备服务器是指与生产服务器保持同步，但未配置为自动故障转移的服务器。相反，工程师必须手动执行故障转移。这适用于灾难恢复场景。冷备服务器未与生产服务器保持同步，因此无法自动故障转移。冷备服务器适用于所有数据均为只读且从不修改的灾难恢复场景。
