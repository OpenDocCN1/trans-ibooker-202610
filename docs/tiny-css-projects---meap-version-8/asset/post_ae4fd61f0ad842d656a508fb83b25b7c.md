## 10.7 Error handling

Under Name, Email, and Message controls is an error message. Currently it is unstyled and therefore not easily identifiable as such. Furthermore, we don’t want to show this error message until the user has interacted with the control. Nobody wants an error message yelling at them before they have even gotten started.

What we are going to do is style them to look like error messages, then we will hide them by default and only show them when appropriate. A bit of advanced warning, if you are coding along with this chapter and downloaded the starter files from Github you may have noticed a JavaScript file. This is where the code in that file is going to come into play. We will get more into details about that here shortly.

### 10.7.1 Styling error messages

Like most error messages on the web, we are going to make our text red. We will use the color we set in our --error custom property. We will also make the text bold and preface our error with the words "Error: " to clearly present it as such because as mentioned earlier in the chapter, we don’t want to use just color to convey meaning or intent. So that we can keep the wording consistent and not have to remember to include it everytime, instead of adding the verbiage at the beginning of each error, we will add it programmatically via CSS using the ::before pseudo element. We will also need to add a 2rem margin to the right of the error so that it can be aligned with the label and input text. Our rules to style our errors will therefore look as follows (Listing 10.25):

# Listing 10.25 Error Styles

```
.error {
  color: var(--error);  #A
  font-weight: bold;
  margin-left: 2rem;   #B
}

.error span::before { #C
  content: 'Error: '; #C
}                  #C
```

#A Make the text red
#B Align it with our input content and labels
#C Add "Error: " before each error

Notice how when we added the "Error: " verbiage before the text, we added it to the span and not the error div itself. That is because we are going to be showing and hiding the span inside of the error and the entire error div. Let’s take a closer look at the HTML to understand why. Listing 10.26 shows the complete control for the Name field including its label and error message. Notice how the error div has an id of nameError which is being referenced by the aria-describedby attribute on the input field. The aria-describedby attribute tells screen readers and assistive technologies that the element whose id it references contains extra information pertaining to the input field. If we hide the error div in its entirety using display:none, the element the aria-describedby is pointing to will not exist. We therefore only hide the contents (the span) in order not to break the programmatic connection between the element and its error. Since we will only be hiding the span, we need to apply the "Error: " verbiage to the span so that it can be hidden when we hide the error message.

# Listing 10.26 Name Field HTML

```
<label for="name">Your Name</label>
<input type="text" id="name" name="name" maxlength="250" required aria-describedby="nameError">
<div class="error" id="nameError">
  <span role="alert">
    Please let us know who you are
  </span>
</div>
```

Figure 10.35 Styled error messages

With our input fields styled, we can now handle only showing them when appropriate. In Figure 10.33 we see that the inputs have valid values, and yet the error messages still show. To hide only show them when the field is invalid, we will start by hiding the error message by default. We therefore apply a `display` property value of `none` to the `span` contained in the error `div`. Then we use the `:invalid` to conditionally show it only when the field is invalid.

As we previously touched on chapter 8, the validity of the field in this case is determined based on the properties we set on the field itself. Let’s look at the name input HTML again: `<input type="text" id="name" name="name" maxlength="250" required aria-describedby="nameError">`. We included a `required` and a `maxlength` attribute, therefore if there is no value in the field, or if the value’s length is greater than 250 characters, the field value will be invalid and styles applied to it using the `:invalid` pseudo class will be applied.

The email element (`<input type="email" id="email" name="email" maxlength="250" required aria-describedby="emailError">`) also has a `maxlength` and a `required` attribute so it would be invalid under the same conditions as the name field. It also has a type of `email` however. In HTML, some field types have validation built in. Email is one of those, therefore, if we were to enter an email address value of "myEmail", it would also show as invalid.

Using the `:invalid` pseudo class will help us prevent errors from being displayed when the field is valid but won’t prevent them from showing up if the field has not yet been interacted with. We currently don’t have a way in pure CSS to determine if the user has interacted with a field, also sometimes referred to as the field being "dirty". This is where we need a little help from JavaScript. The script attached to the file listens for on blur events. Blur events happen when an element loses focus. When we click or tab away from a field, an blur event occurs. Our script listens for these blur events and adds a class of dirty to the field which we have just navigated away from. This allows us to know which fields have been interacted with versus not. Those with a class of dirty have, those who do not have a class of dirty have not. When the "Clear" button is clicked, it clears the form and removes the class of dirty from any of the fields that may have had it, resetting the form to a clean state.

Since we have this dirty class, in conjunction with the :invalid attribute, we will only show the error message below controls that are not only invalid, but have also been touched by the user, preventing us from showing error messages before the user has a chance to fill out the form. We use the following selector: .dirty:invalid + .error span. We select the span contained in an element that has a class of error that is located immediately after an element that is both invalid and has a class of dirty.

Lastly we will also change the border color of the field to our error color when it is both invalid and dirty.

Listing 10.27 shows the full rules to show and hide the error messages.

# Listing 10.27 Error Handling CSS

```
.error span { display: none; } #A

.dirty:invalid + .error span { #B
  display: inline;      #B
}                       #B

:is(input, textarea).dirty:invalid { #C
  border-color: var(--error);  #C
}                           #C
```

#A Hide the error message by default
#B Show the error message when the field immediately before it in the HTML is dirty and invalid
#C Change input and textarea border color to red when invalid and dirty
