# Event-driven Serverless architectures

Events are everywhere. As we discussed in the previous section, an HTTP request can trigger the start of an application which can be idling when not used, which is consistent with the serverless execution model represented in Figure 7-1. But there are plenty of events out there, such as Kafka message, a database stream, or any event from Kubernetes, that an application may want to subscribe to.

A popular pattern in this scenario is the Publish-Subscribe messaging pattern⁶ where many senders can send messages to an entity on the server, often called a topic, and receivers can subscribe to said topic to get messages. According to the Serverless model, your application can be registered and connected to process incoming events. One example for Kubernetes is Knative Eventing component, which implements CloudEvents, a specification for describing event data from multiple protocols and formats (such as Kafka, AMQP, MQTT) in a common way⁷.

With Knative Eventing, event producers and event consumers are independent. A Knative Service is triggered by a source of events through a broker as you can see in Figure 7-5. The goal of the eventing framework is to decouple everything. The sender doesn’t directly call the subscriber or even know how many subscribers there are. Instead, brokers and triggers handle the communication.
