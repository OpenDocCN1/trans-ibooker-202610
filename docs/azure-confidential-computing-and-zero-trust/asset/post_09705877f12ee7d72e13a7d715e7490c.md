
## Supporting Services and Features for ACC

Azure offers several features and services that support TEE attestation and other aspects of Azure’s defense-in-depth strategy. All these features can be used with ACC VMs, while some are useful for confidential containers and other PaaS. Attestation-related services and features include the Microsoft Azure Attestation service, the guest attestation feature for confidential VMs, and Secure Key Release. The other services and features that support other aspects of defense in depth include trusted launch, confidential disk encryption using customer-managed keys, and Azure Key Vault Managed HSM (Hardware Security Module) service.

### Microsoft Azure Attestation

Microsoft Azure Attestation is a service that verifies the trustworthiness of evidence that a hardware platform and the software operating on it are as expected. This service enables both attestation of platforms supported by Trusted Platform Modules (TPMs) and attestation of the state of TEEs. This provides relying parties, such as a secrets manager, with assurance that the intended software is executing on trusted hardware before secrets are released and sensitive workloads are processed.

Attestation can follow one of two patterns:

- In the passport model, the application in the TEE (attester) passes evidence directly to the verifier (Azure Attestation or a third-party attestation service) and receives verification back from the verifier before requesting secrets from a relying party (Figure 3-4).
- In the background check model, the application in the TEE first requests secrets from a relying party by passing the evidence to that party, and it lets the relying party verify that the evidence is trustworthy before secrets are released to the TEE (Figure 3-5).

### Guest Attestation

Azure guest attestation software is the attestation support tool for confidential VMs on Azure. It lets users design their VM-based applications to verify the state of the underlying hardware and guest OS before secrets are exchanged and sensitive data is processed. It can be loaded onto a VM’s OS disk to provide cryptographically based proof that the VM is running in a hardware-based TEE with the necessary level of isolation and integrity. Guest attestation software can also provide a relying party, such as key management service, with evidence that both the TEE hardware and the software within the TEE are as expected before allowing the exchange of secrets. (See the next section for more details.)

Please read the article “What Is Guest Attestation for Confidential VMs?” for additional details.

### Secure Key Release

The goal of Secure Key Release (SKR) is to ensure that keys stay encrypted during their lifecycle and are released only to the authorized code/application. SKR enables the transfer of a key from a key management service to an attested TEE, such as a secure enclave, a VM-based TEE, or a confidential container group. SKR adds an additional layer of access protection to data decryption/encryption keys, allowing only the TEE to access the keys. Access to these keys is governed by the SKR policies defined prior to key issuance. ### Trusted Launch for Gen 2 VMs

The Azure trusted launch improves the security of Azure-hosted virtual machines (generation 2) by enabling a virtual Trusted Platform Module (vTPM) to protect against root kit and boot kit attacks. The vTPM is a virtualized version of a hardware Trusted Platform Module that adheres to the TPM 2.0 specification. The vTPM enables attestation by verifying the integrity of the virtual machine’s whole boot chain (UEFI, boot loader, OS, system, and drivers). Trusted launch utilizes vTPM to perform cloud-based remote attestation, which is used for platform health assessments and decisions based on trust. As a health check, trusted launch can cryptographically verify that virtual machine has successfully launched.

Please read the article “Trusted Launch for Azure Virtual Machines” for additional details.

### Disk Encryption with Customer-Managed Keys

Disk encryption with customer-managed keys is supported for Azure-managed disks (OS and data disks). It allows customers to encrypt individual disks with their own keys. In the case of a customer-managed key, this key is used to safeguard and limit access to the encryption key used to secure the data. Customers can store their managed keys in Azure Key Vault or Azure Key Vault Managed HSM.

By using their own keys, customers have total control over the keys, giving them the flexibility required in certain industries to meet compliance and regulatory requirements.

Please read the article “Server-Side Encryption of Azure Disk Storage: Customer-Managed Keys” for additional details.

### Managed HSM

Azure Key Vault Managed Hardware Security Module (MHSM) is a single-tenant, cloud-based, FIPS 140-2 level 3 validated key management service that ensures the highest protection of customer-owned keys. This “key sovereignty” means that a customer’s organization has full and exclusive control over who can access keys and change key management policies, as well as over what Azure services consume these keys.

After these decisions are made by the customer, Microsoft personnel are prevented through technical means from changing these decisions. The Managed HSM service leverages the capabilities of Azure confidential computing, operating within a TEE constructed on Intel Software Guard Extensions (SGX). Intel SGX provides heightened security measures against both internal and external threats by leveraging hardware-based isolation within application enclaves to safeguard data while it is actively in use. You can’t view data or code inside the application enclave, even with a debugger. If untrusted code tries to change content in the application enclave memory, Intel SGX disables the environment and denies the operation. These unique capabilities help you protect your cryptographic key material from being accessible or visible as clear text. Capabilities of Managed HSM include the following:

- Single tenant and fully managed.
- FIPS 140-2 level 3 validated.
- Highly available and zone resilient.
- Each HSM pool consists of multiple HSM partitions that span three servers on several racks in several data centers. In case of hardware failure, member partitions for the HSM will be automatically migrated to healthy hardware.
- Each HSM instance uses a separate customer-specific security domain that cryptographically isolates each customer’s HSM.

Please read the article “What Is Azure Key Vault Managed HSM?” for additional details.
