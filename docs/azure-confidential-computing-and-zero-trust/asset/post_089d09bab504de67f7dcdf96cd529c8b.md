
## Chapter 3. Azure Confidential Computing Portfolio

Azure confidential computing (ACC) consists of a portfolio of products and supporting services that enable customers to protect sensitive data while in use in accordance with the definitions and principles outlined in Chapter 1. This portfolio includes VMs, container-based platform as a service (PaaS), and other PaaS and software as a service (SaaS). The portfolio as of November 2023 is summarized in Figure 3-1.

This chapter is organized by grouping the ACC portfolio as follows:

- VMs, with both VM-level and code-level isolation
- Container-based PaaS, with VM-level, code-level, and container group-level isolation
- Supporting services and features such as attestation, trusted launch, and OS disk encryption with customer-managed keys
- Other ACC-enabled SaaS and PaaS

## ACC VMs

ACC VMs are building blocks for customers who want to migrate their existing VM workloads to Azure. They include confidential VMs, VMs with application enclaves, and confidential VMs with confidential GPUs.

### Confidential VMs

Confidential VMs offer strong security and confidentiality, as well as hardware-enforced boundaries, to meet the most stringent security requirements. Confidential VMs are particularly useful in scenarios where customers are migrating existing workloads and seeking to lift and shift applications without modifying code, while ensuring that the platform prevents the VM’s state from being read or updated by unauthorized entities. Confidential VMs can be paired with disks encrypted using customer-managed keys, helping to ensure that the customer controls access to their data at all times. The secure boot feature, part of trusted launch, is also enabled by default in all confidential VMs for additional integrity and protection.

### VMs with Application Enclaves

VMs with application enclaves (app enclaves) support code-level isolation using Intel Software Guard Extensions (SGX) technology. It is important, when creating application enclaves, to identify which part of the application operates within the enclave. The enclave isolates that portion of code from the remainder of the application. After the enclave has initialized the code and it has been loaded into memory, untrusted components are unable to read or modify the code, which is encrypted with a unique key generated by the underlying SGX firmware. ### Confidential VMs with Confidential GPUs

Microsoft Azure offers a preview of confidential VMs with confidential GPUs based on AMD CPUs with SEV-SNP technology and NVIDIA® H100 Tensor Core GPUs that use confidential computing.

The objective of confidential VMs with confidential GPUs is to establish a secure environment in Azure for running machine learning workloads that benefit from GPU acceleration, with an additional layer of security that ensures virtual machines boot and operate in a trusted environment. Data used for models, as well as the code for the models themselves, remains encrypted, while the VM takes advantage of the GPU’s enhanced performance for machine learning and AI-based applications.

Please read the article “Announcing Azure Confidential VMs with NVIDIA H100 Tensor Core GPUs in Preview” for additional details.

### ACC Container-Based PaaS

Azure currently offers four confidential container PaaS. Some have VM-level memory isolation (confidential VM node pools for AKS), some have code-level memory isolation (VM with app enclave node pools for AKS), and some have container group–level memory isolation (confidential containers on ACI and confidential containers on AKS). Table 3-1 summarizes this categorization of ACC container services by level of memory isolation.

### Confidential VM Node Pools for Azure Kubernetes Service (AKS)

Confidential node pools utilize VMs with a hardware-based trusted execution environment (TEE). They provide defense-in-depth capabilities to AKS by denying the hypervisor and other host management code access to VM memory and state, as well as protecting against cloud operator access. These features enable migration of highly sensitive container workloads to AKS without refactoring their code, while maintaining VM-level memory isolation.

Please read the article “Confidential VM Node Pool Support on AKS with AMD SEV-SNP Confidential VMs” for additional details.

### VM with App Enclave Node Pools for Azure Kubernetes Service (AKS)

VM with app enclave node pools enables the execution of containerized applications within AKS in a way that protects the code in the enclave from access not only by the operator or other tenants but also by the customer’s own tenant administrators. This is because memory isolation occurs at the code level.

Please read the article “Application Enclave Support with Intel SGX Based Confidential Computing Nodes on Azure Kubernetes Service” for additional details.

### Confidential Containers for Azure Container Instance (ACI)

Confidential containers on ACI provide container group–level memory isolation, with the CPU generating a unique encryption key for each container group. Confidential containers take advantage of the nested virtualization capabilities of AMD SEV-SNP processors, where each confidential container group runs within its own layer 2 utility VM, which is created by a hypervisor running on the base VM’s guest OS. As such, it protects against access not only by the cloud operator and other cloud tenants but also by the customer’s own tenant administrator, thus protecting the container group’s memory from insider threat as well. Since ACI is a “serverless” offering, the infrastructure supporting these container groups is hidden from the customer and managed by Azure. Microsoft provides an open source “sidecar” container image, which can be included in your confidential container group to facilitate the exchange of secrets with a relying party such a key management service.

Please read the article “Confidential Containers on Azure Container Instances” for additional details.

### Confidential Containers for Azure Kubernetes Service (AKS)

Confidential containers on AKS provide pod-level memory isolation, with each pod having its own unique encryption key generated by the CPU. Confidential containers take advantage of the nested virtualization capabilities of AMD SEV-SNP processors, where each pod runs within its own layer 2 utility VM created by a hypervisor running on the base VM’s guest OS. As such, they not only protect against cloud operator access and other cloud tenants, but also the customer’s own tenant administrator. Thus, they protect the pod’s memory from insider threat as well. These features enable migrating highly sensitive container workloads to AKS without refactoring their code, while taking advantage of pod-level isolation. Microsoft provides an open source “sidecar” container image that can be included in your confidential pod to facilitate the exchange of secrets with a relying party, such a key management service.

Please read the article “Public Preview: Confidential Containers on AKS” for additional details.
