## 第 12 章

## 函数式编程惯用法

编写代码很容易，但创建可维护的代码需要付出努力、自律、勤奋以及持续的审查和重构。这对任何范式都适用，包括函数式编程。

开发人员编写糟糕代码并非因为乐见团队受苦。几种不同的力量会影响不良实践。

有时，开发人员编写难以维护的代码，是因为他们尚未培养起真正的质量意识。他们可能从糟糕的示例中学习，缺乏迫切需要的同行评审来帮助他们纠正方向。不幸的是，不良实践可能会成为团队的编程模式，尽管他们承受着糟糕代码的后果，但可能无法识别并改变那些根深蒂固的习惯。

另一些时候，开发人员编写糟糕代码，是因为他们对实际（通常模糊）的需求理解不足。在这种情况下，他们可能会迅速确定自己认为能产生结果的解决方案，但实际上未能满足整体需求。随着对需求的更好理解逐渐显现，开发人员必须不断修复代码，而这些代码已经变成了糟粕，是一种会长期困扰他们的技术债务。

在本章中，我们将探讨编写函数式代码的一些做法和禁忌。我们将首先介绍如何正确编写 lambda 表达式的建议，然后讨论何时应优先使用方法引用而非 lambda 表达式。我们还将正确构建函数式管道，使用良好的参数名，使用类型推断，并在函数式代码中避免副作用。

本章中我鼓励的一些做法是表面功夫，影响代码的可读性和可维护性。其他做法的影响则是深远的，可能会影响代码的正确性。

请将本章中的建议作为检查自己代码的准则。然后利用这些建议指导你的团队创建更高质量、更易于维护的代码。




### 不要编写密集的 Lambda 表达式

编写代码时，我们很容易一头扎进去而忽略代码质量。这往往并非我们的错。我们正在努力理解需求、构思可能的解决方案、尝试不同的想法，有时还要费力地让代码按我们想要的方式运行。毕竟，编程涉及一系列小型实验，我们将一大堆未知变成已知。在此过程中，看到代码能运行我们会感到如释重负，但常常忘记了旅程中的下一步：花时间进行重构，以提高代码质量。

几个开发者中常见的不良做法之一是编写多行 Lambda 表达式。尽量避免这种情况，如果发现多行 Lambda 表达式，请立即诚恳地进行重构。

Java 为单行主体的 Lambda 表达式提供了简洁的语法。它还允许我们将主体放在 `{}` 之间来编写多行主体。仅仅因为编译器允许这样做，并不意味着我们应该允许这种编码方式。这里应该由我们的智慧来做主。

当我们编写多行 Lambda 表达式时，函数式代码的优雅性、可读性和易于理解等所有好处都会丧失。

让我们看一个说明这个问题的示例。快，瞥一眼下面的代码，写下它的功能以及你花了多少时间才弄明白：

```
return LongStream.rangeClosed(1, number)
    .filter(i -> { //Bad Code, don't do this
    long factor = 0;
    for(int j = 1; j < i; j++) {
    if(i % j == 0) {
    factor += j;
    }
    }
    return factor == i;
    })
    .boxed()
    .toList();
```

我们正在遍历从 1 开始的一组数字，并挑选……什么？！

哦！

这种延迟的“哦！”是代码质量差的标志。Lambda 表达式内的代码密度打断了流程，并使我们的目光从管道的处理上移开。

合理地怀疑代码的问题在于嵌入的命令式代码，如果将其重构为函数式风格，也许就没事了。让我们试一下。

```
return LongStream.range(1, number)
    .filter(i -> LongStream.range(1, i) //Not good
    .filter(j -> i % j == 0)
    .sum() == i)
    .boxed()
    .toList();
```

将 Lambda 表达式视为胶水代码。两行可能就太多了。

现在杂乱少了，但 filter 内部的细节仍然打断了流程。这还不够好。让我们重构代码以改善流程：

```
return LongStream.rangeClosed(1, number)
.filter(i -> sumOfFactors(i) == i)
.boxed()
.toList();
```

在传递给 filter 方法的 Lambda 表达式中，只有一行代码调用 sumOfFactors——方法名能迅速揭示意图，你可以进入下一步。你可以专注于大局——即管道中的流程。

除了改善流程之外，为计算命名能使代码模块化，并有助于遵守单一抽象层原则（SLAP）。代码的读者可以思考因数之和的含义，而无需阅读计算代码的实现。将计算代码提取到单独的方法 sumOfFactors 中，而不是将其嵌入到需要其计算结果的代码中，还有另一个好处。现在可以直接对计算代码进行正确性测试和验证，而无需处理使用计算结果的代码。

如果 Lambda 表达式打断了思维流程，或者可以提取到方法中以提高可读性和推理性，请重构它并将主体移动到单独的函数中。保持 Lambda 表达式为一行代码。确保代码不需要读者过度专注或注意。

作为一个快速练习，请花点时间重新审视《重构嵌套循环》中计算勾股数的代码，并重构函数式代码，使 Lambda 表达式符合我们刚才讨论的准则。

除了提高代码质量之外，保持 Lambda 表达式简短还可能帮助将其重构为方法引用，尤其是当它们变成仅传递参数的 Lambda 时。让我们接下来探讨这一点。

### 优先使用方法引用

简短的 Lambda 表达式很棒，但它们仍然需要人类的眼睛来解析以了解它们在做什么。如果可能，尽量用方法引用替换 Lambda 表达式，代码将变得更加易读和简洁——参见 [使用方法引用]。与相应的 Lambda 相比，方法名从上下文中使整个函数式管道更清晰。使用方法引用可以更轻松地查看代码并对其意图充满信心，并且维护代码所需的心智努力更少。

在可能用方法引用替换 Lambda 表达式的地方，应优先使用方法引用。以下代码在 Stream 管道的每个阶段都使用了 Lambda 表达式：

```
drivers.stream()
.filter(driver -> driver.getAge() > 21)
.filter(driver -> driver.isDriversLicenseValid())
.map(driver -> driver.getPrimaryCar())
.map(car -> car.getRegistration())
.forEach(registration -> System.out.println(registration));
```

这些 Lambda 表达式是简短的一行代码，但我们可以用方法引用替换那些仅仅传递参数的 Lambda。每一行都有一个小改动，给代码读者带来一小个好处。但当涉及多行代码时，这些小好处会累积，如本重构代码所示：

```
drivers.stream()
.filter(driver -> driver.getAge() > 21)
.filter(Driver::isDriversLicenseValid)
.map(Driver::getPrimaryCar)
.map(Car::getRegistration)
.forEach(System.out::println);
```

方法引用版本肯定更清晰、更少噪音、更易读、更易思考，相比于使用 Lambda 表达式的版本，它要求的心智努力更少。

不要刻意引入方法引用。例如，我们保持传递给第一个 filter 的 Lambda 表达式不变。将其封装成函数然后传递引用并没有实际好处。但是，如果 Lambda 只是传递参数并且可能被替换为方法引用，请抓住那个机会。

### 正确构建函数式管道

在你参与过的项目中，是否见过如下编写的代码？

```
//Please don't do this
names.stream().filter(name -> name.length() ==
4).map(String::toUpperCase)...
```

我在为专业软件开发人员教授的课程中会问这个问题，不幸的是，得到的“是”答案比例相当高。

鼓励你的开发人员改变这种做法。如果将多个函数（如 filter 和 map）放在同一行，会增加认知负荷。这使得代码难以阅读和理解。而且，如果我们需要进行修改，也会花费更多精力。

请你的同事开发人员垂直对齐点，如下所示：

```
names.stream()
.filter(name -> name.length() == 4)
.map(String::toUpperCase)
.forEach(System.out::println);
```

使用这种结构，可以轻松一目了然地了解管道所采取的整体步骤。对管道中的任何单个阶段进行修改也毫不费力。与之前结构不佳的代码相比，这种结构也使添加或删除管道阶段变得容易得多。

垂直对齐点是 Java 代码的首选约定，IDE 有支持此结构的设置。请务必配置 IDE 以遵循此结构，并使用 IDE 快捷方式轻松格式化代码。

### 将独立条件放在独立的 filter 中

开发人员常问我的一个问题是：“我应该编写多个各带一个条件的 filter，还是一个带多个条件的 filter？”简短而快速的答案是：使用多个 filter 调用，每个带一个条件。

请考虑以下代码：

```
drivers.stream()
.filter(driver -> driver.getAge() > 21 && driver.isDriversLicenseValid())
//Please don't code like the previous line
.map(driver -> driver.getPrimaryCar())
.map(car -> car.getRegistration())
.forEach(registration -> System.out.println(registration));
```

传递给 filter 方法的 Lambda 表达式执行两次独立检查：驾驶员是否超过 21 岁，以及驾驶员是否持有有效的驾驶执照。一个 filter 中有两个条件。

许多程序员倾向于这样编码，误以为将条件合并为一个能带来显著的性能提升；事实并非如此。在中间操作和终端操作中我们讨论过，filter 等方法是中间操作，它们不会立即执行。在内部，函数式管道中的中间阶段会在底层融合为一个操作，并且仅在调用终端操作时才会求值。因此，无论是将条件写入一个 filter 调用，还是写入多个各带一个条件的调用，真正的优化都发生在底层



hood，并且它不基于我们编写函数的方式。我们在一个 lambda 表达式中编写多个条件，不会获得任何性能收益。

让我们拿之前的代码，改用两个 filter 调用而不是一个：

```
drivers.stream()
.filter(driver -> driver.getAge() > 21)
.filter(Driver::isDriversLicenseValid)
.map(Driver::getPrimaryCar)
.map(Car::getRegistration)
.forEach(System.out::println);
```

这比之前的版本好多了。而且，我们在第二个 filter 中成功使用了方法引用。

采用多个 filter 调用，每个调用只包含一个条件的版本，有几个重要好处。首先，它没有任何性能问题，所以我们可以放下那个担忧。其次，与另一个版本相比，代码更简洁，也更易读。每行代码都非常内聚，只做一件事，并且专注于一个条件。添加新条件——添加一个 filter——要容易得多，而不需要去处理一个庞大的条件。如果我们想通过更改条件来尝试不同的行为，只需注释掉一行 filter 即可。删除一个条件也非常容易。最后，保持条件小巧增加了使用方法引用的机会，从而进一步提高可读性。

让我们总结一下保持条件分开的原因：

- 代码的性能与合并条件时一样好
- 代码更简洁
- 代码更易读
- 代码更易维护
- 使用方法引用来进一步提高可读性更容易
- 它提供了进一步简化的机会

采用多个 filter 调用，每个调用只包含一个条件的代码版本，内聚性好，易于编写、易于阅读、易于添加或删除条件，总体上远优于另一种选择，是首选方式。

### 提供良好的特定领域参数名

我们只编写一次代码，但会阅读和修改很多次，有时成千上万次。关于代码阅读的便利性和成本的考量，应当超越第一次编写代码时的考量。

你大概已经见过不少糟糕的 lambda 参数命名。出于某种原因，x 似乎是参数最喜欢的糟糕命名之一。其他糟糕的选择似乎包括 p、k 等等，而最糟糕的莫过于 l——读者可能会想：这是数字 1 还是字母 l？程序员很可能是从某个演示示例、某本书（比如这本书）或某篇博客文章中学到了这种做法。虽然这些简短、晦涩的名称对于快速示例可能很合适，但不幸的是，这样的名称无法帮助团队维护生产代码。

一支习惯于使用无意义变量名的团队可能会创建如下代码：

```
drivers.stream()
    .filter(x -> x.getAge() > 21) //Please avoid meaningless parameter names
    .filter(x -> x.isDriversLicenseValid())
    .map(x -> x.getPrimaryCar())
    .map(c -> c.getRegistration())
    .forEach(r -> System.out.println(r));
```

我有一个关于这些糟糕名称如何潜入代码的理论：也许输入它们的并不是程序员。当他们分心片刻的时候，他们的小猫会跳到键盘上。谁还有心去改变 Kitty 如此“呼噜完美”挑选的变量名呢？

糟糕的变量会使代码难以理解，这使得在修复错误的关键时刻，修复代码成为一种相当不愉快且令人沮丧的体验。

抵制使用单字母、无意义变量的冲动。相反，为 lambda 参数提供特定领域的名称。目标不是使用冗长的名称——它们和晦涩的名称一样糟糕。相反，选择一个简短的名称，清晰地表达该变量代表的含义。例如，不使用 `x`、`d`、`c` 等等，我们可以用描述性的名称重写之前的代码，如下所示：

```
drivers.stream()
    .filter(driver -> driver.getAge() > 21)
    .filter(driver -> driver.isDriversLicenseValid())
    .map(driver -> driver.getPrimaryCar())
    .map(car -> car.getRegistration())
    .forEach(registration -> System.out.println(registration));
```

养成起好名字的习惯。帮助你的团队重构 lambda 表达式中参数命名不好的代码。哄劝和指导他们，直到他们自然开始编写良好的参数名。在代码评审期间继续关注名称。

### 为参数使用类型推断

传统上，在 Java 中我们习惯于指定参数类型。从版本 8 开始，语言更倾向于类型推断。Java 编译器足够智能，在大多数情况下可以确定 lambda 表达式参数的类型。这意味着键盘输入更少，但不会牺牲代码的类型安全性。

许多长期使用 Java 编程的程序员，尤其是那些不编写其他语言的程序员，常常不愿使用类型推断。当指定了 lambda 表达式参数的类型时，他们感到很自在；而阅读未指定类型的代码时，他们会感到沮丧。

你可以利用 Java 的类型推断能力。编写代码的上下文通常提供了足够关于参数类型的细节。将其与参数的良好特定领域名称相结合，通常会使代码更易于理解。

假设一个程序习惯编写如下代码：

```
...
.filter((Driver x) -> x.getAge() > 21)
...
```

鼓励他们为参数起个更好的名字并去掉类型。作为额外的好处，如果 lambda 表达式只有一个参数，你还可以去掉参数周围的括号。

```
...
.filter(driver -> driver.getAge() > 21)
...
```

习惯为 lambda 表达式参数使用类型推断，并为参数名提供特定领域的名称。如果没有类型但配以精心选择的参数名，代码读起来同样好或更好，那就省略类型。

### 函数管道中的副作用

许多程序员常犯的一个错误是从函数管道中突变共享变量。这是大忌。

像 Haskell 这样的纯函数式编程语言不允许可变性。这类语言的编译器会禁止编写代码——更不用说会突变数据的 lambda 表达式。Java 是一种混合语言，函数式编程功能是在语言创建后近二十年才添加的。因此，编译器在大多数情况下不会因为发现不纯的 lambda 表达式而报错——但我们应该。

一位程序员曾给我发了一段代码片段，这段代码之前一直运行良好，但在他们最近做出一次更改后，行为变得相当不可预测。他们希望另一双眼睛来查看这个问题。快速浏览代码后发现了罪魁祸首。在函数管道的最后一步，在 forEach 中，他们将结果添加到了定义在函数管道外部的集合中。代码看起来没问题，直到最后一次更改——他们将对 stream 的调用改为对 parallelStream 的调用。在多线程场景下，代码遇到了竞态条件，结果中丢失了一些数据。

如果 lambda 表达式修改了外部可见变量，则它是不纯的。如果它依赖于可能发生变化的外部变量，它也是不纯的。换言之，纯 lambda 表达式不作恶——即不突变——也不睹恶。

并行执行不是唯一会因不纯 lambda 表达式而出问题的情况。即使是顺序执行，也会因惰性求值而引起困惑。让我们深入研究一下，看看这个问题是如何发生的。

假设我们有一个 lambda 表达式，它依赖于类中的一个字段。该字段未定义为 final，并且而且在 run 方法中被修改。让我们来看看代码：

```java
public class Impure {
  private int factor = 2;

  public void run() {
    var numbers = List.of(1, 2, 3);

    var stream = numbers.stream()
      .map(number -> number * factor);

    factor = 0;

    stream.forEach(System.out::println);
  }

  public static void main(String[] args) {
    new Impure().run();
  }
}
```

在 run 方法中，我们遍历一个数字列表，并使用 Stream 管道将数据转换为数字与 factor 字段值的乘积。然后，在流的最后一步执行之前，我们将 factor 变量的值设置为 0。





将代码展示给不同的同事，并询问他们输出会是什么。响应可能不一致的可能性很大。有人可能会说输出将是列表中值的两倍。有人可能会说结果将全是零。有人可能会抗议说他们毫无头绪。答案取决于语言以及该语言中实现的函数式管道的语义。因此，有些程序员的困惑是合理的，他们很可能是多语言程序员。

The result produced by the previous Java code is:

```
0
0
0
0
```

传递给 map 方法的 lambda 表达式中的转换，直到调用终端操作 forEach 时才会执行。到那时，字段 factor 的值已经被修改。因此，转换不是基于控制通过该阶段时的值，而是基于执行时的状态。最好的情况是这可能会令人困惑，最坏的情况是结果可能不可预测且难以调试。

函数式编程依赖于惰性求值来提高效率，并使并行化代码变得非常容易。惰性求值和并行执行都依赖于 lambda 表达式的纯净性，即没有副作用，以保证正确性。

彻底审查代码，确保 lambda 表达式是纯净的。纯净性有助于你思考代码的作用。

### Wrapping Up

尽管函数式风格优雅、简洁且流畅，但一些开发人员经常编写难以理解的代码。这与该范式的初衷背道而驰。

作为一名开发者，请花时间鼓励你的团队养成良好的编码习惯。本章我们讨论了团队需要关注的多个方面，以确保函数式风格的代码既不易出错又易于理解、阅读、分析和维护。请对开发者同伴表示同情，并遵循这些惯用法，以充分利用这个惊人的编程范式。
