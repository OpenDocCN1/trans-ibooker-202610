让我们拿之前的代码，改用两个 filter 调用而不是一个：

```
drivers.stream()
.filter(driver -> driver.getAge() > 21)
.filter(Driver::isDriversLicenseValid)
.map(Driver::getPrimaryCar)
.map(Car::getRegistration)
.forEach(System.out::println);
```

这比之前的版本好多了。而且，我们在第二个 filter 中成功使用了方法引用。

采用多个 filter 调用，每个调用只包含一个条件的版本，有几个重要好处。首先，它没有任何性能问题，所以我们可以放下那个担忧。其次，与另一个版本相比，代码更简洁，也更易读。每行代码都非常内聚，只做一件事，并且专注于一个条件。添加新条件——添加一个 filter——要容易得多，而不需要去处理一个庞大的条件。如果我们想通过更改条件来尝试不同的行为，只需注释掉一行 filter 即可。删除一个条件也非常容易。最后，保持条件小巧增加了使用方法引用的机会，从而进一步提高可读性。

让我们总结一下保持条件分开的原因：

- 代码的性能与合并条件时一样好
- 代码更简洁
- 代码更易读
- 代码更易维护
- 使用方法引用来进一步提高可读性更容易
- 它提供了进一步简化的机会

采用多个 filter 调用，每个调用只包含一个条件的代码版本，内聚性好，易于编写、易于阅读、易于添加或删除条件，总体上远优于另一种选择，是首选方式。

## 提供良好的特定领域参数名

我们只编写一次代码，但会阅读和修改很多次，有时成千上万次。关于代码阅读的便利性和成本的考量，应当超越第一次编写代码时的考量。

你大概已经见过不少糟糕的 lambda 参数命名。出于某种原因，x 似乎是参数最喜欢的糟糕命名之一。其他糟糕的选择似乎包括 p、k 等等，而最糟糕的莫过于 l——读者可能会想：这是数字 1 还是字母 l？程序员很可能是从某个演示示例、某本书（比如这本书）或某篇博客文章中学到了这种做法。虽然这些简短、晦涩的名称对于快速示例可能很合适，但不幸的是，这样的名称无法帮助团队维护生产代码。

一支习惯于使用无意义变量名的团队可能会创建如下代码：

```
drivers.stream()
    .filter(x -> x.getAge() > 21) //Please avoid meaningless parameter names
    .filter(x -> x.isDriversLicenseValid())
    .map(x -> x.getPrimaryCar())
    .map(c -> c.getRegistration())
    .forEach(r -> System.out.println(r));
```

我有一个关于这些糟糕名称如何潜入代码的理论：也许输入它们的并不是程序员。当他们分心片刻的时候，他们的小猫会跳到键盘上。谁还有心去改变 Kitty 如此“呼噜完美”挑选的变量名呢？

糟糕的变量会使代码难以理解，这使得在修复错误的关键时刻，修复代码成为一种相当不愉快且令人沮丧的体验。

抵制使用单字母、无意义变量的冲动。相反，为 lambda 参数提供特定领域的名称。目标不是使用冗长的名称——它们和晦涩的名称一样糟糕。相反，选择一个简短的名称，清晰地表达该变量代表的含义。例如，不使用 `x`、`d`、`c` 等等，我们可以用描述性的名称重写之前的代码，如下所示：

```
drivers.stream()
    .filter(driver -> driver.getAge() > 21)
    .filter(driver -> driver.isDriversLicenseValid())
    .map(driver -> driver.getPrimaryCar())
    .map(car -> car.getRegistration())
    .forEach(registration -> System.out.println(registration));
```

养成起好名字的习惯。帮助你的团队重构 lambda 表达式中参数命名不好的代码。哄劝和指导他们，直到他们自然开始编写良好的参数名。在代码评审期间继续关注名称。

## 为参数使用类型推断

传统上，在 Java 中我们习惯于指定参数类型。从版本 8 开始，语言更倾向于类型推断。Java 编译器足够智能，在大多数情况下可以确定 lambda 表达式参数的类型。这意味着键盘输入更少，但不会牺牲代码的类型安全性。

许多长期使用 Java 编程的程序员，尤其是那些不编写其他语言的程序员，常常不愿使用类型推断。当指定了 lambda 表达式参数的类型时，他们感到很自在；而阅读未指定类型的代码时，他们会感到沮丧。

你可以利用 Java 的类型推断能力。编写代码的上下文通常提供了足够关于参数类型的细节。将其与参数的良好特定领域名称相结合，通常会使代码更易于理解。

假设一个程序习惯编写如下代码：

```
...
.filter((Driver x) -> x.getAge() > 21)
...
```

鼓励他们为参数起个更好的名字并去掉类型。作为额外的好处，如果 lambda 表达式只有一个参数，你还可以去掉参数周围的括号。

```
...
.filter(driver -> driver.getAge() > 21)
...
```

习惯为 lambda 表达式参数使用类型推断，并为参数名提供特定领域的名称。如果没有类型但配以精心选择的参数名，代码读起来同样好或更好，那就省略类型。

## 函数管道中的副作用

许多程序员常犯的一个错误是从函数管道中突变共享变量。这是大忌。

像 Haskell 这样的纯函数式编程语言不允许可变性。这类语言的编译器会禁止编写代码——更不用说会突变数据的 lambda 表达式。Java 是一种混合语言，函数式编程功能是在语言创建后近二十年才添加的。因此，编译器在大多数情况下不会因为发现不纯的 lambda 表达式而报错——但我们应该。

一位程序员曾给我发了一段代码片段，这段代码之前一直运行良好，但在他们最近做出一次更改后，行为变得相当不可预测。他们希望另一双眼睛来查看这个问题。快速浏览代码后发现了罪魁祸首。在函数管道的最后一步，在 forEach 中，他们将结果添加到了定义在函数管道外部的集合中。代码看起来没问题，直到最后一次更改——他们将对 stream 的调用改为对 parallelStream 的调用。在多线程场景下，代码遇到了竞态条件，结果中丢失了一些数据。

如果 lambda 表达式修改了外部可见变量，则它是不纯的。如果它依赖于可能发生变化的外部变量，它也是不纯的。换言之，纯 lambda 表达式不作恶——即不突变——也不睹恶。

并行执行不是唯一会因不纯 lambda 表达式而出问题的情况。即使是顺序执行，也会因惰性求值而引起困惑。让我们深入研究一下，看看这个问题是如何发生的。

假设我们有一个 lambda 表达式，它依赖于类中的一个字段。该字段未定义为 final，并且而且在 run 方法中被修改。让我们来看看代码：

```java
public class Impure {
  private int factor = 2;

  public void run() {
    var numbers = List.of(1, 2, 3);

    var stream = numbers.stream()
      .map(number -> number * factor);

    factor = 0;

    stream.forEach(System.out::println);
  }

  public static void main(String[] args) {
    new Impure().run();
  }
}
```

在 run 方法中，我们遍历一个数字列表，并使用 Stream 管道将数据转换为数字与 factor 字段值的乘积。然后，在流的最后一步执行之前，我们将 factor 变量的值设置为 0。
