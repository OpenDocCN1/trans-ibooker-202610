# Chapter 7. Leadership as an Individual Contributor

你不需要经理头衔就能成为领导者。高级个人贡献者通常被期望提供技术领导力并在没有直接权威的情况下影响团队甚至整个组织的结果。本章是关于从个人贡献者职位进行领导：如何在不是“老板”的情况下指导他人，推动倡议，指导团队成员并塑造文化。

## 没有权威的领导

到了高级工程师的阶段，你经常会发现自己处于需要协调或影响不向你汇报的人的情况。也许你是一个项目的技术负责人，项目中有来自其他团队的工程师，或者你正在提出一项其他人必须采用的新工程标准。这就是影响力技能和非正式领导力发挥作用的地方（如我在 Chapter 4 中预览的那样）。

我们将讨论几种在没有直接权力时领导的关键技巧：

建立信誉。

正如整本书反复强调的那样，持续交付高质量的工作会赢得你的尊重。如果同事信任你的技术专长和判断力，他们在未来的决策中会更愿意跟随你的领导。这种信誉是领导力的货币。工程师通常会自然地追随那些有明智决策和乐于助人行为记录的人。

传达愿景和理由。

人们需要理解“为什么”才能加入进来。如果你正在领导一个项目，阐明目标以及你的计划如何实现它们。例如，“我们需要处理 10× 负载——我提出实施缓存并重构查询逻辑的方案，通过……来解决这个问题。”描绘成功的画面。当其他人看到清晰的目的地和合乎逻辑的路径时，他们更有可能跟随你。如果你只是下达指令（“我们必须重构 X 因为我说了算”），你会得到抵制或冷漠。

邀请输入并倾听。

领导力不仅仅是告诉人们该做什么。让团队参与决策。如果有人反对你计划的一部分，完全听取他们的意见。也许他们指出了你忽略的一点。通过纳入他人的想法并承认他们的担忧，你让他们对计划产生投入。他们会觉得这是“我们的计划”，而不是仅仅你的计划。此外，如果人们感到被倾听，即使他们的想法没有被采纳，他们也更愿意跟随，因为过程是尊重的。

协调和促进。

作为技术领导者，你通常充当组织者。这可能意味着安排会议以达成一致，写下计划和谁负责什么，跟踪进度并清除障碍。从本质上讲，你在做一些项目管理。许多工程师回避这一点，因为它“不是编码”，但它至关重要。优秀的技术负责人确保机器的所有部分同步运行。例如，你注意到两位开发人员在重复工作——停止并重新分配任务。或者后端正在等待前端的 API 规范——促进该讨论。良好的协调可以防止效率低下和挫败感，这是一项巨大的领导贡献。

指导和分享知识。

个人贡献者领导者提升团队水平。如果有人对技术的一部分不太熟悉，你可能会举办一次快速知识分享会或让他们与可以帮助的人配对。花时间指导团队中各个层级的工程师——从学习架构模式的初级工程师到寻求设计评审建议的同事——给予他们教育和赋能的指导。这建立了好感（人们看到你关心他们的成长，而不仅仅是项目）并提高了团队能力（下次你一个人需要处理的事情更少）。Chapter 5 强调分享知识而不是创建知识孤岛——这是领导层的一种体现。

客观解决冲突。

在技术讨论中，分歧会发生（架构选择、优先级等）。领导者通过关注事实和目标而不是自我来指导解决。你可能会提出一个实验来解决争论（例如，“让我们分别对选项 A 和 B 原型一天并进行测量”）。或引入数据（也许性能指标更倾向于某一方面）。有时只是清晰地以书面形式列出利弊有助于人们达成一致。如果真的陷入僵局，个人贡献者领导者可能会向工程经理或架构师升级以打破僵局，表述为，“我们有两个可行的选项；我们正在寻求新的视角来做出选择。”在冲突中被视为公平而不是独断会建立信任，并使人们更有可能在未来的决策中支持你的领导。

通过你所做的事情赢得权威，而不是你被称为什么。有一个领导原则：领导力是赢得的，而不是赋予的。作为个人贡献者，你不能依靠头衔来让人们倾听。但如果你始终展示技术知识、清晰的愿景、包容的决策制定和个人正直，人们会*想要*跟随你的领导。这有时甚至会导致正式的权威（例如，被要求担任团队技术负责人或工程经理），但即使在个人贡献者角色中，这也极其有价值。

考虑这个示例场景：你是一名在 Project Z 的高级工程师，没有正式的技术负责人角色，但项目有点停滞。不要等待，你挺身而出：组织一次设计会议以最终确定决策，自愿撰写设计文档，在征求意见后分配各部分（询问谁想要哪一块），并设置 Slack 频道或定期检查。你还注意到一名成员在组件上遇到困难；主动提出花一个小时配对编程来帮助他们。不久，事情重新回到正轨。团队现在视你为事实上的负责人。下次出现棘手的集成问题时，他们自然会请你帮忙仲裁。你不需要头衔就能做到这一点；你通过行动领导。

## 没有下属推动大型倡议

当你达到员工工程师级别时，你可能会领导跨多个团队或整个组织的倡议——仍然不是经理。Chapter 4 涵盖了在没有权威的情况下施加影响；在这里，我们将重点关注大规模个人贡献者领导的机制。





## 主导跨团队基础设施改造

让我们来看下面的场景：公司需要改造其基础设施（比如从本地部署迁移到云端）。这是一个多团队协作的项目。他们任命你，一名资深工程师，作为该项目的技术负责人架构师。你没有直接下属，但必须在六个月内让五个团队和 50 名工程师朝着共同目标对齐。

以下是你可以成功的办法：

## 成立工作组

从每个团队中挑选代表（可能是最资深或最有经验的个人贡献者）组成一个工作组。明确角色——也许一个人负责协调网络变更，另一个人负责数据库等，均在整体计划之下。现在你有了可以协作的对接人，而不是面对 50 个个人。这个小组将成为你传播信息和收集状态的首选联系人。这就是典型的“矩阵”式领导：你就该项工作领导这些人，尽管他们向别处汇报。

## 制定并传达计划

创建技术愿景（目标架构）和分阶段迁移计划。广泛传达： 在全员工程会上演示， 为 Confluence 编写架构文档等。人们需要看到整张地图，而不仅仅是自己的部分，这样他们才能理解自己的工作如何与更大项目相连。如有帮助，可使用可视化图表和时间线图表。作为负责人，你将随着事态发展维护并更新该计划。

## 项目管理（是的，你需要做一些 PM 工作）

识别团队间的依赖关系并明确化。例如，A 团队必须在二月交付新 API，以便 B 团队在三月切换。跟踪进度（使用电子表格或项目管理工具）。在同步会议中跟进。资深个人贡献者通常会与工程经理或技术项目经理（TPM）合作完成此项工作，但有时你必须做很多。关键是确保没有团队被阻塞，或者如果被阻塞，能及时暴露并解决。

## 技术监督

虽然你不能编写所有代码，但你应该审查每个团队的关键设计以确保一致性。也许设立每周迁移设计评审，让每个团队介绍他们接下来要做的事情以及任何挑战，而作为项目负责人，你确保一切相互契合，或在某个团队采用次优方法时提供建议。你不要微观管理（团队需要自主权），而是温和引导。更像是顾问而非老板。

## 统一标准和工具

对于大型项目，拥有共同方法可以加速进展。如果每个团队都以不同方式编写自己的迁移脚本，就会陷入混乱。你作为负责人可能会提议，“让我们都使用 X 工具进行基础设施即代码。” 提供模板或示例供他人复制。这减少了重复工作并促进共享专业知识（因为方法相似，每个人都可以互相帮助）。它也通过提供有用的资源来巩固你的领导角色。

## 跨团队沟通

确保成果和发现能在团队间共享。也许设立一个 Slack 频道（比如“#cloud-migration”）用于分享任何遇到的问题，以便其他人不会重复调试。频繁分享已完成的工作进展，并在公开场合庆祝里程碑。这不仅能激励大家（进展可见），还能让每个人保持知情。经常，你会成为项目在更广泛论坛中的发言人：向总监汇报状态，突出风险等。这就是领导力：代表一项工作并推动其成功。

## 外交地处理冲突或不一致

如果 X 团队落后或 Y 团队构建的东西不符合约定的规范，请以解决问题而非指责的方式处理。“我看到这里我们落后了——我们如何调整？你们需要帮助还是可以调整另一个里程碑？” 或 “这个组件最终与 API 规范所述不同；让我们协调一下——也许规范不完整？让我们想办法。” 大型项目总会有问题；领导者为修复问题设定协作基调，而不是互相指责。这保持了士气和信任，在长期工作中至关重要。

## 给予认可，承担责任

在汇报成功时，认可团队：“A 团队和 B 团队做得非常出色，达到了目标。” 在汇报问题时，作为集体或作为领导者承担责任：“我们低估了这里的工作量——这是我的责任；我们有计划重新回到正轨。” 这种保护性立场会让团队亲近你（他们知道你不会把他们推下水），也会给高层留下深刻印象（你展现了领导成熟度）。

作为个人贡献者主导大型项目具有挑战性，但可以成为个人贡献者职业生涯的巅峰。你指挥着努力的交响乐，确保最终成果和谐统一。许多资深/首席工程师发现这种跨组织推动大事的方面极具回报，与或超过单独编写代码的满足感。

成功推动大型跨团队项目通常是区分资深工程师和高级工程师在晋升校准中的关键因素。它表明你可以在组织层面运作。顺带一提，这也是一项可转移到管理岗位的技能，如果你将来选择那条道路。

这就是纯粹的个人贡献者形式的工程领导力。

## 导师制与赞助：攀登时托举他人

我多次提到导师制。到高级阶段，你不仅应该指导他人，还应有意赞助有潜力的新人。这是一种确保下一代成长的领导形式，在高级别个人贡献者中通常是期望的（许多职业晋升阶梯都有类似“积极指导他人”适用于高级，“培养其他技术领导者”适用于首席的标准）。作为提醒：

* *导师* 提供建议，回答问题，并提供反馈以帮助某人成长。
* *赞助人* 利用自己的影响力为某人倡导，推荐他们承担关键项目或晋升。

以下是作为资深个人贡献者有效指导的几个想法：

* 至少带一个固定的 mentee（通常是新员工或初级员工）。安排每周或每两周一次聊天。帮助他们解决问题，而不是直接给出答案。提出引导性问题，分享类似经历。
* 在代码评审中，不要只修复问题，要解释模式和推理。例如，“我重构了这部分，因为我们的约定是 X，这有助于 Y。下次请记住。”
* 鼓励他们承担一些 stretch 任务并成为他们的安全网。“为什么不由你来主导这个功能的实现？我会支持你并评审你的设计。” 他们通过实践学习，但知道你会支持他们。这对建立他们的信心和技能非常重要。
* 尽管很忙，也要为指导留出时间。很容易因为它“不紧急”而将其优先级降低。但请记住，团队成长是你高级阶段工作的一部分（通常反映在绩效评审中）。
* 你在指导中也能学习；你巩固自己的知识并获得他人如何处理事情的视角。

作为个人贡献者领导者，你可以更进一步进行赞助：

* 识别有潜力的初级/中级工程师。如果你看到有人默默做出出色工作，就引起关注。例如，告诉你的经理“嘿，我认为 Maria 在那个模块上做的是高级水平的工作——如果她保持下去，也许可以考虑她晋升。” 有时经理无法深入了解细节；你的声音可以突出应得的人。
* 提名他人获得机会。如果一个新项目需要负责人，你可以做，但你的同事也在成长，你可以支持他们担任负责人（你在旁边提供建议）。领导力不是囤积最好的任务；而是培养更多领导者。
* 邀请经验较少的同事与你一起在内部技术分享会上共同演讲，让他们获得曝光度。
* 如果你在校准会议上有席位（一些公司让资深工程师参与晋升委员会），为你认为达到标准的人发声。





*本质上，要成为你在职业生涯早期希望得到支持的那种高级工程师。这种文化会得到回报——你培养的人可能会成为你最强的合作者。*

你可能在想，为什么在讨论如何成为一名有效的工程师时，指导和赞助如此重要。以下是关于帮助同事带来的益处需要认识到的几点：

* 他们放大了团队的能力（因此能以质量完成更多工作）。
* 他们成为盟友——你帮助过的工程师会在项目上信任并支持你，给予你更多非正式的影响力。
* 这极具满足感——你能为他人的成功感到自豪，这是一流领导者的标志。
* 公司领导会注意到那些提携他人的人；这通常是晋升到首席级别的标准之一。它表明你是以组织的长期健康为出发点，而不仅仅是个体贡献。

这对公司文化也非常有益。如果每位高级工程师指导一到两位其他人，知识就会流动，文化也会健康传播。它避免了信息孤岛和英雄依赖。它也使入职更顺畅、留存更好（因为人们感到被重视）。因此，作为一名 IC 领导者的一部分就是培育这种文化。你可以组织一个导师计划，或简单地以身作则，表明指导是被重视的，而不是负担。

## 道德考量与承担责任

随着工程师影响力和领导能力增强，他们也需为工作的伦理影响承担更大责任。有效的工程师不仅仅是按要求构建——他们会批判性地思考对用户和社会的潜在负面影响。

## 预见并应对用户风险

在本书中，我们讨论了理解用户需求和交付价值。但有效性也意味着考虑潜在危害。在开展功能或系统工作时，请自问以下问题：

* 这是否会对某些用户群体造成不成比例的负面影响？
* 我们是否没有充分解决隐私问题？
* 该功能是否可能被误用而伤害用户？
* 我们收集或使用数据的方式是否尊重用户信任？

如果你预见到风险，你有责任提出它们。这可能很不舒服，尤其是在职业生涯早期或团队面临交付压力时。但伦理问题正是工程师需要发声的议题。请建设性地表达你的担忧：

提出具体场景。

: “如果我们按设计实现此功能，连接较慢的用户将有显著降级体验，可能排除发展中国家的用户。”

提出替代方案。

: “如果我们增加一个确认步骤，在用户继续前使其明确了解影响，会怎样？”

必要时升级处理。

: 如果你的担忧未得到充分考虑就被驳回，请向你的经理或适当渠道升级。大多数公司都有伦理委员会或提出担忧的流程。

## 处理错误和事故

在任何工程职业生涯中犯错都是不可避免的——从小错误到影响用户的重大事故。区分有效工程师的是他们如何处理这些情况。

当你犯错导致问题时，请遵循以下原则：

立即承担责任。

: 不要隐瞒、淡化或归咎他人。迅速通知团队和相关利益相关者。示例：“我部署的变更导致结账失败。我现在正在回滚并将调查根本原因。”

先关注解决，再关注根本原因。

: 你立即的首要任务是最小化用户影响。一旦情况稳定，再调查出了什么问题。

进行无责事后分析。

: 在重大事故后，写下发生了什么、为什么以及如何防止未来再次发生。重点应放在改进系统和流程上，而不是惩罚个人。优秀的组织认识到大多数失败源于系统性问题，而非个人无能。

广泛分享经验教训。

: 将你的错误转化为团队学习的机会。如果你发现某个测试缺口导致了问题，请提出改进测试实践的建议。

原谅自己并向前看。

: 每个人都会犯错。沉溺其中对任何人都没有帮助。学习你能学到的东西，在适当时弥补，并在知道下次会处理得更好的认知下继续前进。

在系统中建立韧性。

: 除了个别事故外，还要思考如何使系统对人为错误更宽容。你能否增加更好的监控、验证或回滚能力？让灾难性错误更难发生对每个人都有益。

对错误负责并考虑伦理影响不仅仅是为了避免负面结果——它们是与团队、用户和你自己建立信任的方式。它们是工程有效性的重要组成部分，超越了技术技能。

这些领导技能在应用于高影响工作时最有效。Chapter 8 将探讨工程师的战略思维，帮助你识别并将工作与业务真正重要的事情对齐。
