# 第 2 章. 理解基础知识（初级到中级重点）

在职业生涯早期（通常对应初级和中级角色，有时在大型科技公司中被指定为 `L3–L4`，或大约零到四年经验，具体取决于组织），有效性来自技术卓越和良好的工程习惯。通过掌握基础技能——编写干净的代码、有效调试、测试、使用版本控制和基础设计——你为可靠交付和更快学习奠定了基础。本章涵盖这些基础知识以及它们的重要性。

## 清晰、可维护且可读的代码

代码被阅读的次数远多于被编写的次数。你或他人将在未来几年维护这段代码。如果它粗糙或不清晰，维护将缓慢且容易出错。干净的代码——易于理解、修改和维护的代码——是一种力量倍增器，因为它加速了所有使用它的人。干净的代码创造了一个透明的环境，其中错误显而易见，整个团队的开发速度保持高位。“干净代码”一词由 Robert C. Martin（Uncle Bob）在其同名有影响力的书籍 (*Clean Code* \[Pearson\]) 中推广，指的是读起来几乎像写得很好的散文的代码。

干净代码的特征包括以下内容：

### 清晰度

使用有意义的名称 (`functions`, `variables`)。编写其他人（以及未来的你）在不需要深入领域知识或大量上下文的情况下就能理解的代码。当你添加注释时，重点解释 *为什么* 而不是 *什么*——代码本身应该展示它做了什么。如果你必须添加注释来解释一段代码的作用，请考虑重写该代码使其更清晰，或提取一个命名良好的函数。

### 简洁性

遵循 `KISS`——*keep it simple, silly*。如果一个简单的循环就足够，不要使用复杂的模式。避免过早泛化。解决手头的问题；抵制添加 `YAGNI` (*you aren’t gonna need it*) 功能。简单代码更容易理解、测试和调试。复杂性只有在解决真实的、当前的问题时才应引入。简洁性很重要，因为简单代码隐藏错误的地方更少，需要的文档更少，并能让新团队成员更快地变得高效。当面临一个巧妙的解决方案和一个同样有效的简单方案之间的选择时，每次都选择简单。

### 一致性

遵守团队风格指南和约定。一致性减少了认知负担，因为工程师知道会有什么样的预期。Google 的指南说：“在风格问题上，风格指南是绝对权威。” 与其在各处使用你个人的理想风格，不如保持一致更好。

### 可重构性

努力实现允许更改的代码结构。这包括 `single responsibility principle`（每个组件只有一个工作）和最小化紧密耦合。如果添加新功能需要修改 10 个不相关的文件，那就是代码不够干净的信号。干净的代码是模块化且逻辑组织的。

以下是一些现在就可以采用的好实践：

### 遵循核心设计原则

诸如 `single responsibility`（每个组件只有一个工作）、`high cohesion`（相关代码保持在一起）和 `loose coupling`（最小化组件间的依赖）等原则有助于创建可维护的代码。面向对象编程中的 `SOLID` 原则可以是有用的指导方针，尽管重点应放在更广泛的目标上：使你的代码易于理解和修改。`SOLID` 是五个面向对象设计原则的缩写：单一职责、开放/封闭、里氏替换、接口隔离和依赖倒置。这些原则旨在通过指导类和模块应如何构建来创建可维护、灵活和可扩展的软件。应用它们有助于减少耦合并增加内聚，使代码更容易理解和扩展。某些特定的 `SOLID` 原则在微服务或函数式编程等现代架构中可能感觉不太相关，但清晰和模块化的基本思想仍然有价值。

### 消除死代码并修复“待办事项”

在代码库中留下垃圾会累积“代码债务”，这可能会混淆或绊倒未来的工作。当你发现它时，解决它，或至少明确标记它。

### 学习你语言的惯用法

写 Pythonic 的 Python，而不是 Java 式的 Python 等。充分利用语言特性的代码通常更清晰、更简洁。

让我们看一个干净代码的例子：假设你有一些难以跟踪的复杂条件逻辑。这通常表明你的业务逻辑或状态模型存在潜在复杂性。初级开发者可能会把它全部写在一个巨大的 `if` 块中，带有复杂的条件。更干净的方法可能是将其拆分为多个命名良好的函数，使逻辑明确，或使用具有解释性条件名称的 `if/else` 部分。然而，如果你发现自己拥有真正复杂的条件逻辑，请考虑是否可以简化底层模型——有时最好的解决方案是解决根本原因，而不是仅仅重新组织代码。

干净代码导致更少的错误（因为它更容易推理和发现错误）、新团队成员更快上手（他们可以快速阅读和理解代码而无需大量解释），以及更大的灵活性（进行更改不需要解开复杂的依赖关系）。这些好处会随着时间的推移而累积——今天节省的 10 分钟，未来可能会为你的团队节省数小时甚至数天。作为初级开发者，培养留下比找到时更好的代码的习惯，将在你的整个职业生涯中为你服务，并让你成为团队中受重视的成员。

## 测试和质量思维





职业生涯早期的工程师有时会把测试看作是一种负担。但现在建立质量意识，将来会为你节省大量痛苦。优秀的工程师不仅仅是让东西运行起来；他们还要确保东西持续运行。有几件事你可以做来确保质量。

首先，为你的代码编写测试。如果你的团队没有强大的测试文化，就成为改变的推动者。从为关键逻辑编写基础的 `unit tests`（测试在隔离环境中验证单个函数或组件）开始。在你的代码库中可行时，使用 `integration tests`（测试验证多个组件协同工作）来确保关键流程端到端正常工作——尽管要认识到，在现有代码库中添加集成测试可能具有挑战性，并且可能需要架构支持。力求在覆盖率上取得良好平衡，不要过度（100% 测试覆盖率本身并不是目标，因为并非所有代码同等重要，而且某些代码，如简单的 getter/setter，测试时价值很小；重点测试重要的业务逻辑、边界情况和错误条件）。

你也可以使用 AI 助手来帮助生成初始测试脚手架或建议你可能忽略的边界情况。例如，在编写函数后，你可以要求 AI 工具提出测试场景——但将其视为起点，而非完成的测试。你仍然需要审查建议，确保它们符合你的需求，并验证测试确实能捕获 bug。AI 生成的测试是样板代码的省时工具，而不是深思熟虑的测试设计的替代品。

测试是有益的，因为它能做到以下几点：

Prevents regressions

: 

你知道自己所做的更改是否立即破坏了旧功能。

Facilitates refactoring

: 

如果你有测试的安全网，你就可以自信地改进代码结构。

Documents intent

: 

测试展示了代码预期如何工作的示例。未来的阅读者可以看到，“啊，给定输入 X，我们期望 Y，”而无需深入实现细节。

接下来，尽可能自动化。学习如何在本地和你的持续集成（`CI`）管道中运行测试。如果运行测试套件很麻烦，请与团队讨论如何加快速度或拆分测试以并行运行。工程师经常会跳过测试，如果它们很慢或不稳定。投入时间修复这个问题是高杠杆的。

质量不仅仅是关于测试；它还包括代码审查和静态分析：

Code reviews

: 

拥抱它们（第 4 章 涵盖协作，包括审查）。作为初级工程师，你会从反馈中学到很多。随着时间的推移，你也会提高发现他人代码中问题（从而也在自己代码中发现问题）的能力。

Linters/static analysis

: 

这些工具捕获常见错误（未使用变量、可能的空指针引用、风格问题）。示例包括 JavaScript 的 `ESLint`、Python 的 `Pylint` 和 Ruby 的 `RuboCop`。使用它们！它们将琐碎的 bug 捕获从你的大脑中卸载出来，让你专注于更复杂的问题。

最后，我们需要谈谈 bug 修复。当你遇到 bug 时（你一定会遇到），采用一种做法：每当你修复一个 bug 时，尽可能添加测试用例来覆盖它。这可以防止该 bug 再次潜入。这是一种根据真实场景持续改进测试套件的快速方法。

花费在测试上的时间，会通过在生产环境中 *不* 花费时间调试问题或在午夜救火而获得数倍回报。作为经验较少的工程师，你可能会担心编写测试会拖慢你。事实上，它会让 *整个团队* 在项目生命周期中更快。它还能建立你代码可靠的声誉。

考虑两位工程师，他们最初以相同的速度交付功能，但其中一位编写测试。三个月后，那位工程师的功能问题远少，扩展也更容易，因此他们现在交付更快（不会被维护拖累），而另一位工程师则被困在修复旧 bug 中。质量是长期提速。

## Tip

像对待生产代码一样对待你的测试代码——使用清晰的命名，避免复制粘贴，并保持测试的可维护性。写得不好的测试会成为维护负担，而不是资产。

## 版本控制和调试纪律

版本控制和调试纪律乍看像是独立的主题，但它们归结为系统化和自律，这是有效工程师的关键特质。

## 版本控制（例如 Git）

你可以用版本控制培养的最具变革性的习惯是把提交当作讲故事。每个提交都应讲述关于代码库一次更改的清晰、聚焦的故事。考虑采用常规提交格式（如 `feat:`、`fix:`、`docs:`），或使用团队的提交信息风格指南，使你的历史记录更易读。当你频繁提交早期且逻辑上自包含的更改时，你不仅仅是在保存工作；你是在创建一份历史叙事，未来开发者（包括你自己）可以跟随。“Add search API” 与一个同时重构三个无关函数的庞大提交之间的区别，就像一本书中清晰的一章与令人困惑的情节混乱之间的区别。

你的提交信息是你写给未来自己的情书。六个月后，当你使用 `git blame` 追踪神秘 bug 时，你要么会感谢自己写了“Fix off-by-one error in pagination logic (index should start at 0)” 要么会诅咒自己写了“Fix stuff”。花额外 30 秒写描述性信息，可以在以后节省数小时的考古工作。把它当作随代码旅行的文档。

对 git 功能如分支、变基和 `git revert` 的熟练掌握提供了编码无惧所需的安全网，将复杂的版本控制转变为可靠的基础。恢复的确定性给了你大胆重构和创新的自由。这种心理安全感是那些突破界限的工程师的决定性特征。

真正的魔力发生在事情出错且你需要使用版本控制的调试功能（如 `git bisect`）时（它在其他版本控制系统如 Mercurial、Fossil 和 Perforce 中工作方式类似）。此工具可以通过在历史记录中进行二分搜索，精确指出引入 bug 的提交。但它只有在你的提交小而聚焦时才有效。每个提交都成为潜在的调试检查点，这就是为什么自律的版本控制实践会在危机时刻产生回报，当你需要快速找到问题时。

## 调试

调试从根本上是侦探工作，但太多工程师把它当作考古学——随机挖掘，希望偶然发现文物。我认识的最有效的调试者将其视为科学学科。他们首先收集证据：确切的症状是什么？能否一致地重现问题？最近有什么变化？这种系统化的方法可以防止耗费整个下午的无头苍蝇追逐。

现代工程师甚至可以利用 AI 助手进行调试——将错误日志或堆栈跟踪输入 `ChatGPT` 等工具来假设潜在原因。明智使用时，这些工具可以加速证据收集阶段，尽管你仍必须通过测试验证所有建议。同样科学的方法适用：输入清晰的症状，输出有用的见解。

科学方法不仅仅适用于实验室；它是你的调试超能力。形成具体的假设，如“我认为身份验证令牌在 API 调用完成前就过期了”，而不是模糊的直觉如“登录有问题”。然后设计测试来证明或证伪该假设。策略性地使用日志，设置有针对性的断点，或编写快速单元测试来隔离可疑组件。这种有条不紊的方法起初感觉更慢，但实际上比许多开发者默认的散弹式调试高效得多。





你与调试工具——调试器、性能分析器、浏览器开发者工具——的关系决定了你花在挫败感中还是心流状态中的时间。每花一分钟学习键盘快捷键、理解调用栈，或掌握条件断点，都是会产生复利回报的投资。那些看起来对找 bug 有第六感的工程师其实并不具备特异功能；他们只是把调试中的机械部分自动化了，从而能把精神能量集中在逻辑的解谜上。

## 文档与笔记

最被低估的调试技能是通过笔记进行外部化思考。当你深入一个复杂 bug 时，你的工作记忆会迅速被假设、测试结果和死胡同填满。写下你观察到和测试过的内容不仅仅是一种良好实践；它是一种认知卸载，能让你的大脑自由地发现你可能 otherwise 会错过的模式和联系。我见过经验丰富的工程师仅仅通过回顾调试笔记并注意到自己忽略的东西就解决了问题。

当你发现那些奇特的环境怪癖或系统陷阱时，记录它们是对团队的一种工程体贴。那个让你花了两小时才搞明白的奇怪的 Secure Sockets Layer (`SSL`) 证书问题？下一个遇到它的开发者不应该被迫重走你整个调查过程。一段简单的代码注释或一篇 wiki 条目就能把你来之不易的知识转化为团队知识。这种在解决方案还新鲜时写下的文档——正是区分优秀工程师和伟大工程师的关键：伟大工程师优化的是团队的集体效率，而不仅仅是自己的即时生产力。

强大的版本控制意味着更少的丢失更改、更轻松的协作，以及快速识别引入 bug 的提交。严谨的调试方法意味着更少的时间被卡住，也更少“我的天，我完全不知道发生了什么”的时刻。两者结合确保这些基础能让你花更多时间编写功能代码，而不是处理自找的问题或与损坏的代码苦战。

## 文档与沟通（即使作为初级工程师）

你可能会认为文档是只有资深人士才需要操心的事，但这是一个误解——所有层级的工程师，包括初级工程师，都被期望能产出高质量的文档，尤其是在大型科技公司中。事实上，在学习的同时进行文档记录是巩固理解的最佳方式之一。现在养成良好的文档习惯会放大你的效能：

* 写下关于你代码的关键决策或假设（在代码注释或团队文档中）。这有助于未来的维护者（六个月后的你也可能是）。
* 如果你在上手过程中发现入职文档或操作手册不足，请在体验还新鲜时主动改进它们。这不仅帮助他人，还能迫使你巩固自己的理解。
* 如果你卡住了或需求似乎模糊，请尽早沟通。提出好问题是一种优势，而不是弱点。它能防止你在错误的事情上白费力气。

记住，与人愉快协作是有效性的组成部分。如果你写出很棒的代码但没人能理解它或不知道如何运行它，其价值就会大打折扣。清晰的代码、清晰的测试、清晰的文档、清晰的沟通——这些基础能让你在承担更大挑战时更有信心并得到团队的支持。

通过理解如何编写干净的代码、确保质量、有效使用工具以及清晰沟通，你将把自己定位为一名可靠的工程师。这些技能可能没有设计整个系统或发明算法那样光鲜，但它们能让你最终成功地完成那些更大的事情。此外，它们还能提升团队生产力和对你工作的信任，从而加速你的成长机会。现在投资良好的习惯；它们将在你的整个职业生涯中产生回报。

一旦你牢牢掌握了这些基础，你的职业成长将取决于新的战略考量，例如平衡技术知识的深度与广度，这正是我们在 Chapter 3 中要讨论的内容。
