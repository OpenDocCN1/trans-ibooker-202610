### 收集并比较

查看 AI 组和对照组的指标有何不同。AI 组的任务是否关闭得更快？他们的代码质量是否相似、更好或更差？这将让你对因果关系更有信心（是 AI 造成了差异还是其他因素）。在一项[企业研究](https://oreil.ly/gXe-L)中，这种方法发现 AI 组确实满意度更高，且代码质量相似或更好。

### 调查团队

指标是量化的，但不要忘记定性反馈。询问用户他们的感受：他们是否觉得自己更高效了？压力更小还是更大？他们是否信任这些建议？有时感知可以揭示原始指标不会显示的问题（例如，输出可能更快，但人们对代码的信心不足，这可能意味着存在隐藏问题）。

### 根据发现迭代

假设你发现开发速度提高了，但代码审查时间增加了（也许是因为审查者在 AI 编写的代码中发现了更多问题）。这就指向了调整流程：也许需要更多关于如何更好地提示的培训，或增加 AI 审查步骤，如在[“AI 代理：它们能做什么以及如何让它们保持受控”](#ch13.html#ch13_ai_agents_what_they_can_do_and_how_to_keep_them_t_1768431690629908)中讨论的那样。或者如果你发现某些类型的任务有了很大改进（如编写测试），而其他任务没有（如实现复杂算法），你可以专注于 AI 在最有帮助的地方使用，而不要在无用处强行使用。

目标是将 AI 的采用视为科学实验，而不是盲目冒险。为了有效跟踪采用情况，尽早建立明确的机制：设置遥测仪表板以监控每日/每周活跃用户，创建 AI 辅助提交的标记规范（例如在提交信息中添加 `AI-assisted`），并安排定期检查（每周或每两周）以审查采用率并收集团队的定性反馈。这不仅能产生价值证明（或缺乏价值）以指导决策，而且还能培养在工具使用上持续改进的文化。不是“我们买了这个东西，希望它有帮助”，而是“我们测试了这个工具，这里是它如何帮助以及我们需要调整的地方”。

衡量带来的另一个好处是，它可以指导辅导和最佳实践。如果你看到某位团队成员的接受率远低于其他人，也许他们需要提示方面的帮助，或有更难集成的环境。如果另一位成员的接受率非常高，也许他们可以与他人分享他们的做法（或者他们可能过度信任——参见[“AI 在哪里闪光（以及你仍然需要人工的地方）”](#ch13.html#ch13_where_ai_shines_and_where_you_still_need_a_human_1768431690628853)——你可以双重检查）。

此外，随着时间的推移，你可以关注趋势。也许最初 AI 帮助很大，但六个月后边际收益下降——可能是人们变得懒惰或停止学习工具的新功能。或者随着人们发现新的巧妙用途，改进会累积。持续的指标会讲述这个故事。

总之，不要盲目飞行。你不会在没有监控的情况下将新服务器或服务引入生产环境；同样，将 AI 引入你的开发流程时也要监控其自身有效性。衡量影响是将潮流与真正有效实践区分开来的关键。如果数据显示改进，你可以充满信心地加倍投入。如果显示出问题，你可以纠正方向。无论如何，你都会知道自己的立场——怀疑者也会知道，这很好地引出了下一节关于用数据说服他人的内容。

一旦你建立了证据基础，下一步就是实际的：将所学应用到日常中以获得更好的 AI 结果。

# Prompt Patterns That Actually Work (Templates to Reuse)

到目前为止，我们谈了很多关于如何使用 AI 以及如何集成它。让我们换个角度，变得非常具体：你可以使用的实际 *prompt patterns*。这些就像常见场景的小食谱。想法是节省你的时间，这样你就不必每次都从头制作提示（并与团队分享，让每个人都受益）。

你可以在仓库或知识库中保存这样一份提示模板文件。把它们看作是为每种用例定制的起点。以下是五种在日常工程工作中被证明有效的提示模式：

### Tests-first generator

当你想要为代码生成测试（尤其是在实现之前，如我们所讨论的）时，你的提示可以如下所示：

> You are a senior engineer familiar with our system. Write a set of unit tests (and property-based tests if applicable) for the following functionality: <describe functionality or user story>. Use our project’s typical testing frameworks. Where relevant, reference any functions or modules by name. The tests should be comprehensive for edge cases and clearly fail (with understandable messages) until the functionality is correctly implemented. Do not assume any implementation details beyond what’s described; focus on input-output behavior.

为助手提供你拥有的任何接口或规范信息（函数签名、验收标准）。此提示告诉它首先充当测试编写者，并确保测试会失败（这样你就知道它们正在工作）。它基本上是在指示 AI 像谨慎的高级开发人员一样思考：覆盖边界情况、清晰命名等。关于引用文件路径或 API 的部分，如果你的 AI 可以看到代码库，它可能会说，“使用模块 Y 中的函数 X 进行设置”，这很有用。

### Secure scaffolder

为了从一开始就内置安全性的生成样板代码，你的提示将如下所示：

> Create a scaffold implementation for <feature or service> using <framework/tech>. Important: incorporate security best practices: validate all inputs (e.g., check lengths, types, prevent SQL injection or script injection), perform output encoding for any user-facing text, avoid using any unsafe functions (like `eval` or raw SQL queries). Include structured logging (in our format) for key events, with sensitive data redacted. After writing the code, also produce a short security checklist explaining which OWASP-top-10 issues you mitigated and how (e.g., XSS—by encoding output).

此提示不仅要求代码，还要求一份清单，这有两个目的：它迫使 AI 反思安全问题（使其更可能生成安全的代码），并为你提供快速验证它是否遗漏了明显问题的途径。如果清单说“我通过使用参数化查询缓解了 SQL 注入”，而输出中看不到任何数据库代码，那就是一个危险信号（幻觉或错误）。但通常，这会产生具有额外保护的代码，外加一份漂亮的摘要，你可以将其包含在 PR 描述或设计文档中，以表明你考虑了安全问题。

### Reviewer assistant

要帮助生成代码审查评论并总结差异，使用此提示：

> You are a code review assistant. Analyze the following diff (or describe the change) and do three things:
>
> (a) Summarize the key changes in a few sentences.
>
> (b) List any risky or complex parts of the change, especially things that could affect security, performance, or maintainability.
>
> (c) Suggest two to five specific code review comments with line numbers (if applicable) that a human reviewer might raise. These comments should reference our coding standards or best practices when relevant. Be polite and constructive.
