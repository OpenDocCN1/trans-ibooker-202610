

职业生涯早期的工程师有时会把测试看作是一种负担。但现在建立质量意识，将来会为你节省大量痛苦。优秀的工程师不仅仅是让东西运行起来；他们还要确保东西持续运行。有几件事你可以做来确保质量。

首先，为你的代码编写测试。如果你的团队没有强大的测试文化，就成为改变的推动者。从为关键逻辑编写基础的 `unit tests`（测试在隔离环境中验证单个函数或组件）开始。在你的代码库中可行时，使用 `integration tests`（测试验证多个组件协同工作）来确保关键流程端到端正常工作——尽管要认识到，在现有代码库中添加集成测试可能具有挑战性，并且可能需要架构支持。力求在覆盖率上取得良好平衡，不要过度（100% 测试覆盖率本身并不是目标，因为并非所有代码同等重要，而且某些代码，如简单的 getter/setter，测试时价值很小；重点测试重要的业务逻辑、边界情况和错误条件）。

你也可以使用 AI 助手来帮助生成初始测试脚手架或建议你可能忽略的边界情况。例如，在编写函数后，你可以要求 AI 工具提出测试场景——但将其视为起点，而非完成的测试。你仍然需要审查建议，确保它们符合你的需求，并验证测试确实能捕获 bug。AI 生成的测试是样板代码的省时工具，而不是深思熟虑的测试设计的替代品。

测试是有益的，因为它能做到以下几点：

Prevents regressions

: 

你知道自己所做的更改是否立即破坏了旧功能。

Facilitates refactoring

: 

如果你有测试的安全网，你就可以自信地改进代码结构。

Documents intent

: 

测试展示了代码预期如何工作的示例。未来的阅读者可以看到，“啊，给定输入 X，我们期望 Y，”而无需深入实现细节。

接下来，尽可能自动化。学习如何在本地和你的持续集成（`CI`）管道中运行测试。如果运行测试套件很麻烦，请与团队讨论如何加快速度或拆分测试以并行运行。工程师经常会跳过测试，如果它们很慢或不稳定。投入时间修复这个问题是高杠杆的。

质量不仅仅是关于测试；它还包括代码审查和静态分析：

Code reviews

: 

拥抱它们（[第 4 章](#ch04.html#ch04_collaboration_and_cross_functional_influence_1768431688998639) 涵盖协作，包括审查）。作为初级工程师，你会从反馈中学到很多。随着时间的推移，你也会提高发现他人代码中问题（从而也在自己代码中发现问题）的能力。

Linters/static analysis

: 

这些工具捕获常见错误（未使用变量、可能的空指针引用、风格问题）。示例包括 JavaScript 的 `ESLint`、Python 的 `Pylint` 和 Ruby 的 `RuboCop`。使用它们！它们将琐碎的 bug 捕获从你的大脑中卸载出来，让你专注于更复杂的问题。

最后，我们需要谈谈 bug 修复。当你遇到 bug 时（你一定会遇到），采用一种做法：每当你修复一个 bug 时，尽可能添加测试用例来覆盖它。这可以防止该 bug 再次潜入。这是一种根据真实场景持续改进测试套件的快速方法。

花费在测试上的时间，会通过在生产环境中 *不* 花费时间调试问题或在午夜救火而获得数倍回报。作为经验较少的工程师，你可能会担心编写测试会拖慢你。事实上，它会让 *整个团队* 在项目生命周期中更快。它还能建立你代码可靠的声誉。

考虑两位工程师，他们最初以相同的速度交付功能，但其中一位编写测试。三个月后，那位工程师的功能问题远少，扩展也更容易，因此他们现在交付更快（不会被维护拖累），而另一位工程师则被困在修复旧 bug 中。质量是长期提速。

### Tip

像对待生产代码一样对待你的测试代码——使用清晰的命名，避免复制粘贴，并保持测试的可维护性。写得不好的测试会成为维护负担，而不是资产。

# 版本控制和调试纪律

版本控制和调试纪律乍看像是独立的主题，但它们归结为系统化和自律，这是有效工程师的关键特质。

## 版本控制（例如 Git）

你可以用版本控制培养的最具变革性的习惯是把提交当作讲故事。每个提交都应讲述关于代码库一次更改的清晰、聚焦的故事。考虑采用常规提交格式（如 `feat:`、`fix:`、`docs:`），或使用团队的提交信息风格指南，使你的历史记录更易读。当你频繁提交早期且逻辑上自包含的更改时，你不仅仅是在保存工作；你是在创建一份历史叙事，未来开发者（包括你自己）可以跟随。“Add search API” 与一个同时重构三个无关函数的庞大提交之间的区别，就像一本书中清晰的一章与令人困惑的情节混乱之间的区别。

你的提交信息是你写给未来自己的情书。六个月后，当你使用 `git blame` 追踪神秘 bug 时，你要么会感谢自己写了“Fix off-by-one error in pagination logic (index should start at 0)” 要么会诅咒自己写了“Fix stuff”。花额外 30 秒写描述性信息，可以在以后节省数小时的考古工作。把它当作随代码旅行的文档。

对 git 功能如分支、变基和 `git revert` 的熟练掌握提供了编码无惧所需的安全网，将复杂的版本控制转变为可靠的基础。恢复的确定性给了你大胆重构和创新的自由。这种心理安全感是那些突破界限的工程师的决定性特征。

真正的魔力发生在事情出错且你需要使用版本控制的调试功能（如 `git bisect`）时（它在其他版本控制系统如 Mercurial、Fossil 和 Perforce 中工作方式类似）。此工具可以通过在历史记录中进行二分搜索，精确指出引入 bug 的提交。但它只有在你的提交小而聚焦时才有效。每个提交都成为潜在的调试检查点，这就是为什么自律的版本控制实践会在危机时刻产生回报，当你需要快速找到问题时。

## 调试

调试从根本上是侦探工作，但太多工程师把它当作考古学——随机挖掘，希望偶然发现文物。我认识的最有效的调试者将其视为科学学科。他们首先收集证据：确切的症状是什么？能否一致地重现问题？最近有什么变化？这种系统化的方法可以防止耗费整个下午的无头苍蝇追逐。

现代工程师甚至可以利用 AI 助手进行调试——将错误日志或堆栈跟踪输入 `ChatGPT` 等工具来假设潜在原因。明智使用时，这些工具可以加速证据收集阶段，尽管你仍必须通过测试验证所有建议。同样科学的方法适用：输入清晰的症状，输出有用的见解。

科学方法不仅仅适用于实验室；它是你的调试超能力。形成具体的假设，如“我认为身份验证令牌在 API 调用完成前就过期了”，而不是模糊的直觉如“登录有问题”。然后设计测试来证明或证伪该假设。策略性地使用日志，设置有针对性的断点，或编写快速单元测试来隔离可疑组件。这种有条不紊的方法起初感觉更慢，但实际上比许多开发者默认的散弹式调试高效得多。
