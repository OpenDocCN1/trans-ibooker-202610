

# 防御性工程

代码评审、架构讨论和技术设计会议经常涉及冗长的讨论，你在其中为每一次实现决策进行辩护。你会立即用它们行不通的理由回应建议，而不是考虑其价值。同事似乎不愿提供反馈或批评你的工作。你很少在不经过大量讨论的情况下采纳他人的建议。绩效评估中提到了你之前听过但未解决的改进领域。

## 补救措施

以好奇心而非防御性来实践接收反馈。先通过提问来澄清建议，而不是立即解释你的理由。考虑反馈是否揭示了你未曾考虑到的假设或约束。即使最终决定不采纳他们的建议，也要感谢他人的意见。结对编程也有助于将反馈变成开发过程中的自然、持续的一部分，而非正式的评审事件。

将你的工作与你的身份分离。记住，对你工作的批评虽然会让人感觉个人化，但其焦点是改善结果。采用成长型思维，将反馈视为学习的机会，而非需要防御的攻击。考虑提供反馈的同事是在投入时间帮助改进工作和成果。

当你不同意反馈时，平静地解释你的理由并征求他人的观点，而不是驳斥他们的担忧。经常，当不同观点被公开探索时，会产生富有成效的讨论。有时你会发现之前未曾考虑到的有效观点；其他时候，你会帮助他人理解重要的约束或考量。

## 文化修复

团队可以建立围绕给予和接收反馈的规范，强调学习和改进而非评估或批评。关于有效反馈传递的培训有助于确保建议以建设性的方式提出。一些组织使用结构化反馈框架，例如 `radical candor`（由 Kim Malone Scott 提出，强调在直接挑战的同时关心他人）或领导力发展中心 `SBI`（情境-行为-影响）模型，它们将不同类型的输入分开并使期望明确。

## 收益

对反馈的开放性加速了你的职业发展，因为你可以从同事多样化的经验和观点中学习。通过协作评审流程，代码质量得到改善。团队关系得以加强，因为同事感到被倾听和被重视。你的声誉将发展为一个易于合作且致力于持续改进的人。

# 工具迷恋：追逐新奇事物

一名工程师经常在没有明确的业务理由或充分评估的情况下采用新工具、框架或技术。他们可能出于对新兴技术的兴趣、保持技能最新的愿望，或认为更新的工具本质上更好。然而，频繁的工具切换会产生巨大的开销，并可能分散交付实际业务价值的注意力。此外，第三方 (`3P`) 工具通常带有许可成本、供应商依赖和合规性考量，而第一方 (`1P`) 解决方案则没有。

这种模式给工程师及其团队带来了诸多问题。每个新工具都需要学习时间，而这些时间本可用于功能开发或解决问题。团队成员也必须学习新工具，使得每次切换的影响倍增。项目可能因大家适应新技术而延迟。工程师可能永远无法在任何特定工具上发展出深厚专长，因为他们不断转向下一个新选择。随着部分实现的解决方案被放弃以采用更新的方法，技术债务可能会累积。

## 反模式征兆

你的项目使用许多不同的工具和框架，而没有对这种多样性进行明确的理由说明。你经常建议用更新的替代品替换现有工具。同事对跟上工具变化表示沮丧。项目文档随着工具链的演变而迅速过时。你花费大量时间研究和试验工具，而不是解决业务问题。

## 补救措施

建立工具采用的明确标准，其中包括除新颖性或技术吸引力之外的因素。考虑维护负担、团队学习曲线、社区支持以及与现有基础设施的契合度。要求对工具变更提供明确的业务理由，而不是仅仅因为技术看起来有趣或现代就采用它们。

在较少的一组工具上实践深厚专长，而非对许多选项只有表面知识。精通较少的工具往往比熟悉众多替代方案更有价值。在评估新工具时，创建小型、限时的实验，而不是在没有验证的情况下就承诺进行重大更改。

考虑工具采用的总拥有成本，包括团队培训时间、迁移工作、持续维护以及潜在的未来变更。有时，老旧且成熟的工具尽管工作起来没那么令人兴奋，但仍能提供更好的整体价值。

## 文化修复

团队可以建立技术采用流程，要求在引入新工具前进行评估和批准。一些组织维护已批准的技术栈，以在创新与稳定性之间取得平衡。定期的架构评审可以评估工具选择是否符合当前需求和未来计划。

## 收益

专注的工具使用使你能够发展出深厚专长，从而实现更复杂的解决问题和更好的技术决策。随着每个人都熟练掌握稳定的工具集，团队生产力提高。随着工具因长期价值而非短期吸引力而被选择，技术债务减少。你可以将精力集中在业务问题上，而不是不断学习新技术。

# 冒名顶替综合征瘫痪：恐惧驱动的无所作为

一名工程师因自我怀疑和害怕犯错而变得瘫痪，导致他们回避具有挑战性的任务或成长机会。他们可能认为自己不具备胜任其角色的资格，或认为自己的成功归因于运气而非技能。这种模式阻止他们承担会推进职业发展并为团队成功做出贡献的责任。

这种反模式严重限制了个人成长和团队效能。工程师回避会发展其技能并展示其能力的拉伸任务。他们可能因害怕犯错而过度研究决策，而不是做出合理选择并从结果中学习。团队成员可能无法意识到工程师的全部潜力，因为他们持续回避具有挑战性的工作。随着恐惧主导技术决策，创新和承担风险减少。

## 反模式征兆

你持续自愿承担熟悉的任务，同时回避会拉伸你能力的任务。你花费过多的时间验证决策或在采取行动前寻求他人的批准。你将自己的成就视为运气，或主要归因于外部因素。当被要求展示你的工作或向他人解释技术决策时，你感到焦虑。同事似乎对你展示他们之前未曾观察到的能力感到惊讶。请注意，虽然冒名顶替综合征可以是一种内在挣扎，但外部因素如不可预测的管理者、不一致的领导或有毒的团队文化也可能触发或加剧这些感受。

## 补救措施

认识到冒名顶替综合征在各级别工程师中都很常见，并不反映实际能力。保留你成就、积极反馈和成功项目的记录，以便在自我怀疑出现时参考。练习承担稍具挑战性的任务，这些任务能推动你的边界但不会让人不堪重负。
