

## 向老板展示你在努力成长

向上管理不仅仅是为了达到自己的目的；它关乎建立良好的工作关系。如果他们建议你在某些方面改进（例如，“我希望你让新工程师更多地参与设计”），就去做。然后让他们知道积极的结果（“我和 Alex 一起完成了 API 设计；她很快就掌握了，并且提前交付了”）。现在你的经理会认为你是个低维护且“懂行”的人。这通常意味着他们会自然而然地给你更多的影响力（因为他们信任你的判断）。

## 让你的经理生活更轻松

在很多方面，这就概括了全部。资深 IC 通常会非正式地承担“技术负责人”的职责：在团队中协调任务、在不涉及经理的情况下解决 minor 分歧、指导初级员工。当你这样做时，你就是通过处理本应由经理介入的事情来向上管理。然后你可以带着解决方案或经过充分分析的选项，而不是问题，去找你的经理。例如，不要说，“团队对方案 X 有分歧”，而要说“团队对 X 有分歧，所以我们做了个快速的概念验证，发现方案 A 性能更好，所以我们将采用该方案，除非你有异议”。大多数经理都会说“太棒了！”并感谢你承担领导责任。

## 尊重边界和沟通链

向上管理的一部分是知道何时需要升级问题、何时自行处理，以及了解你的经理风格。有些经理喜欢详细的每日更新；其他人则更希望你放手去做，只在重大事件时通知他们。适应他们的风格。这再次有助于建立更顺畅的关系。

如果你的经理尊重并信任你，他们通常会更高层地为你的想法辩护，或让你负责实验性项目。建立这种信任意味着你可以在避免成为一个“唯唯诺诺的人”——简单地同意一切——的同时影响团队优先级——目标是建立一种建设性的合作伙伴关系，你提供数据和背景以帮助共同做出更好的决策。如果他们 constantly 担心你或需要为你纠偏，他们就会更犹豫是否支持你的创新建议（因为他们不确定这些建议能否成功）。本质上，与管理层保持一致会给你推动更大变革的杠杆，同时保持你的独立判断。

协作和影响力是 IC 角色的核心，尤其是在你变得更加资深时。技术技能可能让你达到中级水平，但在此之后，领导力和团队合作技能决定了你有效性的很大一部分。通过学习与 PM/设计师良好合作、在没有正式权力下领导同行、以及向上管理，你放大了技术才能的影响力。这些技能将一个优秀的工程师转变为组织中的 *伟大* 工程师。毕竟，最聪明的代码如果不能集成到人们使用的产品中就解决不了任何问题——而这需要与他人合作。有效的 IC 拥抱这一点并在其中出类拔萃。

通过磨练这些协作技能，你放大了你的有效性。然而，即使是技术娴熟的工程师也可能养成削弱其影响力的习惯。在 [Chapter 5](#ch05.html#ch05_anti_patterns_that_limit_individual_contributor_ef_1768431689179178) 中，我们将探讨限制 IC 有效性的常见反模式以及如何避免它们。

# Chapter 5. Anti-Patterns That Limit Individual Contributor Effectiveness

即使是聪明、努力工作的工程师也可能养成削弱其有效性的习惯。本章将揭示可能影响不同职业阶段工程师的常见 *反模式*，以及如何避免它们。虽然有些模式，如知识孤岛，可能在任何层级出现，但其他模式，如过度工程化和委派挑战，随着工程师获得资历（中级到高级）而更常见，而可见性问题在追求员工级角色时往往变得至关重要。

我们将探讨的反模式包括以下内容：

* 知识孤岛和代码囤积
* 英雄情结（“白骑士综合征”）
* 过度工程化 vs YAGNI（务实胜过完美）
* 无法委派（自我瓶颈）
* 沟通不畅和可见性差（隐形工作）
* 分析瘫痪（过度思考而不行动）
* 不是我发明的综合征（拒绝外部解决方案）
* 完美主义和镀金（从不发布）
* 上下文切换成瘾（缺乏深度专注）
* 范围蔓延助长（无法说不）
* 技术债务否认（忽视系统健康）
* 会议过载（时间管理不当）
* 反馈抗拒（对输入封闭）
* 工具痴迷（追逐新奇事物）
* 冒名顶替综合征瘫痪（恐惧驱动的无所作为）

像 [Code Climate](https://oreil.ly/9EjNS) 的研究表明，仅解决知识共享实践就能使开发生产力提高 50%。你在自己身上认出这些模式中的任何一种吗？没关系——我们都有盲点。但解决它们可以超速提升你的影响力和团队的成功。

# Knowledge Silos: Share What You Know

一名工程师成为某段代码或某个领域的唯一权威，例如构建系统、支付逻辑或遗留基础设施。他们可能会守护那片领地，无论是有意地出于工作安全心态，还是无意地因为缺乏时间来记录或教学。信息未被共享，围绕关键系统形成了一个 *知识孤岛*。

这种模式对团队有效性造成了重大问题。如果只有一个人真正知道某事物如何运作，该组件就会成为瓶颈。每当工作触及该区域时，团队就会放慢速度。*巴士系数* 是一种风险衡量技术，用于确定项目在失去关键团队成员时有多脆弱。该术语是对“如果有几个人被‘巴士撞到’（或因任何原因离开团队）项目就会停滞或失败”的幽默而黑暗的比喻。在这种情况下，巴士系数降至一，意味着如果专家生病或离职，团队就会陷入困境。它还让那个人承担该区域的所有 bug 和问题，通常导致压力或倦怠。

## Anti-Pattern Signs

你经常会听到诸如“哦，Alice 负责那个，你得问她”或“我们避免更改那部分；那是 Dave 的宝贝”之类的说法。在代码评审中，只有一个人能有意义地评审某些代码，因为没有其他人理解它。团队成员将关于特定系统的所有问题都路由到同一位个人。

对于发现自己成为知识持有者的工程师来说，放手可能感觉极度不舒服。当你不再成为某个领域的首选人物时，往往会出现身份危机。这种不适感是自然的，但也是成长的标志。虽然分享你的专业知识可能感觉不安，但值得庆祝这一转变，因为它代表了你从个人贡献者向团队赋能者的演变。

## Remedy

分享知识将你的影响力扩展到囤积永远无法达到的程度。有效的工程师通过传播知识而不是囤积知识来让自己更有价值。如果你发现自己处于孤岛中，从编写文档开始，或者至少为该组件编写高层级的 README 文件——说明它做什么、如何使用它以及常见故障排除步骤。

通过与队友配对完成该领域的几个任务来培养一名备份人员，以便他们学习诀窍。例如，下次出现 bug 时，不要自己花一个小时修复它，而是与另一位工程师配对编程两个小时，让他们学习系统。通过耐心解释代码来鼓励他人进行代码评审。起初需要更长时间，但它能训练团队并防止未来的中断。
