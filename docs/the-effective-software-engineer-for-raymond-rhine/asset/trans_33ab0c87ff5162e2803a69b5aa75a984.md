

由于你的专业知识，你可以有效地规划债务偿还（而不是盲目地删除东西）。你也知道哪些债务是可以容忍的，哪些是真正危险的。例如，你可能会说“是的，那个脚本里有一些全局变量 \[debt\]，但它只是一个只有两个人使用的构建工具——利息很低。但紧密耦合的 auth 和 user 模块导致了很多 bug——利息很高；让我们先解决这个问题。”

广度帮助你将债务工作与业务需求保持一致。它提醒你考虑更大的图景。以下是一些例子：

* 你权衡重写是否会延迟业务真正需要的功能（有时如果现在伤害不大，容忍一些债务是可以的）。
* 你用他们的术语与非工程师沟通。不要说“模块 X 是丑陋的代码”，而要说“模块 X 的代码债务导致每个新功能花费的时间是原来的两倍（影响我们推出改进的能力）”。
* 你关注跨团队的收益：也许清理一个核心服务将加速许多团队，使其比在孤立角落的清理更容易证明合理性。
* 你将债务工作与其他路线图项目协调：也许你说服 PM 让团队花一个冲刺在“工程健康”任务上。为此，你阐述了这次清理冲刺将使接下来一个季度的功能开发更顺畅。

让我们看一个例子：一位高级工程师发现处理支付的代码非常脆弱（在仓促发布期间做了很多快速补丁）。他们在之前的工作中有关于健壮支付系统的深入知识，所以他们确切知道如何重新设计它（深度）。但他们不会在真空中开始重构。利用广度，他们注意到即将计划添加新的订阅选项。先进行重新设计实际上将使这些功能更快地构建。他们提出一个计划：花两周时间重构支付模块（偿还债务），这将减少 bug（对财务很重要）并使新定价模型的实施更容易。他们还承认，正在进行的营销促销意味着一周内无法部署任何更改（广度：对业务日历的认知），因此他们谨慎地安排部署时间。债务在最小化干扰和明确价值的情况下得到解决。

总之，要在更高层级有效工作，培养 *T 形技能*：一两个你擅长的真正技术深度领域，加上跨技术栈和业务背景的广泛理解。深度让你成为强大的问题解决者和权威；广度让你成为明智的架构师和合作者。两者结合使你能够设计技术上健全且适合目的的系统，并就将你的（和你团队的）工程工作重点放在哪里以获得最大收益做出战略决策。

# 如何决定深度/广度投资

首先在与你的兴趣和团队需求一致的领域深入——这会给你信誉和基础。随着成长，逐渐通过在相邻系统上工作、参加你领域外的架构评审，并在跨团队讨论中提问来扩展你的广度。平衡会随时间推移而变化：初级工程师先深入以建立专业知识是有益的；中级工程师开始扩展广度同时保持深度；高级和员工工程师会持续刷新两者，让一些深度领域随着组织优先事项的变化而淡出并出现新的领域。你永远不会真正停止在任一维度学习——关键是根据职业目标和当前差距，有意地决定学习时间的投资。

发展 T 形 profile——平衡深度专业知识与广泛多才多艺——为你提供了解决复杂工程问题和设计健壮系统的原始能力。然而，在高级角色中，识别“正确”的技术解决方案往往只是战斗的一半；另一半是说服组织去构建它。你的技术杠杆最终会被你的沟通、协调和与他人协作的能力所放大或限制。随着我们从个人专业知识转向组织影响，重点从你如何与代码交互转变为你如何与人交互。

# 第 4 章。协作与跨职能影响

无论你的技术技能多么出色，如果你不能与他人很好地合作，你的有效性就会受到限制。软件是一项团队运动。作为一名 IC，尤其是在高级级别，你通常需要在没有正式权威的情况下影响决策。本章介绍如何与关键角色（PM、设计师、经理）协作以及如何在团队间获得影响力。

## 与产品和设计有效合作

优秀的产品源于工程、产品管理和设计之间的密切合作。与产品经理（拥有产品策略和路线图）和设计师（拥有用户体验和界面）进行跨职能协作对于有效工程师尤其关键。然而，有时工程师和 PM/设计师会感觉势不两立——工程想要简洁/技术纯粹性，PM/设计想要更多功能或像素完美的 UI。有效的工程师弥合了这一差距。为此并培养牢固的合作伙伴关系，有效的工程师采用以下几个关键实践：

### 理解需求背后的“为什么”

不要只是从你的任务跟踪器中拿一个任务并盲目执行。问你的产品经理一个功能解决什么用户问题，或旨在推动什么指标。这种上下文让你在开发期间做出明智的权衡。例如，如果你知道一个功能是实验性的，用来看看参与度是否会增加，你可能会以粗糙的方式构建它以快速测试（知道如果失败会被丢弃）。如果它对业务至关重要，你可能会在健壮性上投入更多。

### 将技术洞察带入产品讨论

PM 拥有 *什么* 和 *为什么*，但你拥有 *如何*。你的工作是提出技术约束或机会。例如，“我们可以两天内实现变体 A，但变体 B 由于后端复杂性需要两周”或“我们有一个现有的服务几乎可以做到这一点——如果我们调整它，我们可以用 10% 的工作量获得此功能。”这用现实塑造产品决策。好的 PM 欣赏这种输入，因为它帮助他们权衡投资回报率。这是没有权威的影响力的一部分——他们决定，但你的信息影响他们的决定。

### 具有解决方案导向

如果 PM 要求某事似乎在技术上不可行或非常困难，不要只说，“不行，做不了。”解释 *为什么* 并与他们一起研究替代方案。也许，“我们很难在我们的规模上交付实时搜索结果，但我们可以每五秒更新一次，我认为这能实现相同的用户收益。”或者，“做 X 会导致延迟问题；如果我们尝试 Y 方法呢，我可以更快完成，也许能满足需求？”这将潜在冲突转变为协作。你本质上是用工程视角进行产品头脑风暴。

### 尊重每个领域的约束并相互教育

有时 PM 或设计师可能不理解一件看起来很小的事（更改字段验证规则）实际上很复杂（因为它触及多个系统）。花时间向他们解释技术方面。相反，尝试理解基本的 UX 或业务原则，以便你能理解为什么一个看似微不足道的 UI 更改（“只要把那个按钮变成蓝色”）可能对转化或品牌很重要。当各方欣赏彼此的挑战时，合作会改善。

### 尽早参与
