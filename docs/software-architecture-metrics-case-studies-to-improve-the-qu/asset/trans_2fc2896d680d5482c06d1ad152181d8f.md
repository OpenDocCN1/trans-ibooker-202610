
### 单位
单位应包含属于一起的子单元，这意味着它们彼此之间的内聚性应高，而与外部的耦合应低。例如，如果某个模块的子模块与其他模块的耦合度高于与其“姐妹兄弟”的耦合度，那么它们彼此之间的内聚性就低，模块化做得也不好。与内聚性不同，耦合是可以度量的。

### 名称
如果系统的程序单元是模块化的，你应该能够针对每个单元回答以下问题：它的任务是什么？这里的关键点在于程序单元确实只有一个任务，而不是几个。判断职责不清的一个好线索是单元的名称，名称应描述其任务。如果名称含糊不清，就应该审视它。不幸的是，这无法度量。

### 良好平衡的比例
处于同一层级的模块化程序单元，如层、组件、包、类和方法，应具有良好的平衡比例。这里值得检查非常大的程序单元，以确定它们是否适合分解。一个极端的例子可以在[图 4-2](#ch04.html#extreme_proportions)中看到。在左侧图表中，你可以看到系统九个构建单元在饼图中的大小：团队告诉我们，构建单元反映了系统的计划模块。其中一个构建单元代表饼图的最大部分，为 950.860 行代码（`LOC`）。其他八个构建单元加起来只有 84.808 `LOC`，极不平衡。在[图 4-2](#ch04.html#extreme_proportions)的右侧，你可以看到系统的架构，其中九个构建单元以正方形表示，构建单元之间的关系以弧线表示。系统的一部分称为“`Monolith`”，它是饼图中的大块。它使用八个小的构建单元，我们在这里称之为“`Satellite X`”。与卫星的浅色阴影相比，`Monolith`正方形的深色阴影表明，就像饼图一样，这里集中了大部分源代码。该系统的模块化并不平衡。该指标是可以度量的。

![](assets/sarm_0402.png)

# 层次结构
层次结构在感知和理解复杂结构以及存储知识方面发挥着重要作用。如果知识以层次结构呈现，人们就能很好地吸收、再现并在其中找到方向。层次结构的形成在编程语言中通过 `contain-being relationships` 得到支持：类位于包中，包又位于包中，最终位于项目或构建产物中。这些层次结构符合我们的认知机制。

与 `contain-being relationship` 不同，`use and inherit relationships` 可以以不创建层次结构的方式使用：我们可以使用使用和/或继承关系将源代码库中的任何类和接口链接起来。这样，我们就创建了完全非层次化的交织结构。在我们的领域中，我们随后谈论类循环、包循环、模块之间的循环以及架构层之间的向上关系。在我的架构评审中，我看到了整个范围，从很少的循环结构到庞大的循环怪物。

[图 4-3](#ch04.html#a_cycle_with_twofourtwo_classes) 显示了一个包含 242 个类的类循环。每个矩形代表一个类，它们之间的线条代表它们的关系。该循环分布在 18 个目录中，它们都需要彼此来完成任务。

![](assets/sarm_0403.png)

产生[图 4-3](#ch04.html#a_cycle_with_twofourtwo_classes)中循环的系统总共有 479 个类。因此，这里超过一半的类（242 个）彼此直接或间接需要对方。此外，该循环在中心有很强的集中度，卫星很少。没有自然分解该循环的可能性，但重新设计这些类的工作量很大。最好从一开始就确保不会出现如此大的循环。幸运的是，大多数系统都有更小且集中度更低的循环，可以通过几次重构来分解。

[图 4-4](#ch04.html#cycles_at_the_architecture_level) 显示了架构层级上的非层次结构。一个小型应用系统（80,000 `LOC`）的四个技术层——`App`、`Services`、`Entities` 和 `Util`——层层叠加并相互使用，正如预期，主要从上到下（左侧的向下箭头）。一些回溯引用（右侧的向上箭头）已渗入层级之间，导致层级之间的循环，从而造成架构违规。

![](assets/sarm_0404.png)

这种分层架构中的违规仅由 16 个类引起，且很容易解决。同样，对于这类循环或分层违规，发现并重构得越早越好。

好消息是，循环在所有层级上都很容易度量，因此可以精确检查系统的层次结构。每个要点对 `MMI` 计算的影响请参考模式一致性的说明。

# 模式一致性
人类用来构建复杂关系的最有效机制是图式。图式将相似事物或连接的典型属性概括为抽象。例如，如果你被告知某人是一名教师，那么在抽象层面上，你的图式包含有关相关活动的不同假设和想法：教师受雇于学校，他们没有八小时的工作日，并且必须批改课堂测试。具体来说，你会记住自己的老师，你将他们存储为教师图式的原型。

如果你对生活中的某个情境有图式，那么你可以在没有图式的情况下更快地理解和处理问题和问题。例如，软件开发中广泛使用的设计模式利用了人类大脑处理图式的优势。如果开发人员已经使用过设计模式并从中创建了图式，他们就能更快地识别和理解使用该设计模式的程序文本和结构。

图式的应用为我们在日常生活中理解复杂结构提供了决定性的速度优势。这也是模式多年前进入软件开发的原因。对于开发人员和架构师来说，模式的存在、能在源代码中找到并且被一致使用是很重要的。因此，一致应用的模式帮助我们应对源代码的复杂性。

[图 4-5](#ch04.html#pattern_at_class_level_equals_pattern_l) 在左侧显示了一张图表，团队开发了该图表以在工具中记录他们的设计模式，该工具允许他们将一个模式的类收集到一层中。在右侧，源代码被划分为这些设计模式，你可以看到轴左侧有很多弧线，它们向下延伸以符合图表。轴左侧的弧线向下，轴右侧的弧线则违背分层向上。轴右侧有几条弧线违背分层从下到上。这很典型；设计模式形成层次结构。该系统的设计模式实现得很好，因为主要是左侧弧线（从上到下的关系），右侧弧线（从下到上、违背模式给出的方向的关系）很少。
