
现在我们已经明确了指标的来源，我们可以通过将通用心智模型映射到你的实际交付流程来使事情变得更复杂。我将在下一节中展示如何执行这种“心智重构”。

# 重构你的心智模型

定义每个指标*针对你的实际情况*至关重要。正如你很可能已经猜到的那样，前两个指标的基础是你在 CI 管道中发生的事情，而后一对指标则需要跟踪服务中断和恢复情况。

在进行这种心智重构时请仔细考虑范围。你是在查看组织中所有软件的所有更改吗？还是只考虑你工作项目中的那些？你是在包含基础设施更改还是只观察软件和服务的更改？所有这些可能性都是可以的，但请记住：*你考虑的范围必须对四个指标都相同。* 如果你在前置时间和部署频率中包含基础设施更改，也要包含由基础设施更改引起的中断。

## 将管道作为首要切入点

你应该考虑哪些管道？你需要的管道是那些监听目标范围内源代码库中的代码和配置更改、作为后果执行各种操作（例如编译、自动化测试和打包），并将结果部署到生产环境的管道。你不想包含用于诸如数据库备份之类的 CI 实现任务。

如果你只有一个代码仓库由一条端到端管道提供服务（例如，存储在单体仓库中的单体应用并直接部署，且在一组活动中部署到生产环境），那么你在这里的工作就很简单。这种模型的示例如 [图 1-2](#ch01.html#the_simplest_source_controlsoliduspipel) 所示。

![](assets/sarm_0102.png)

不幸的是，虽然这与我们的基本心智模型完全相同，但在现实中我很少见到这种情况。我们很可能需要对心智模型进行更广泛的重构，才能得到一个代表你实际情况的模型。

接下来最容易衡量且是我们第一次重要的心智重构的是这些端到端管道的集合，每个构件或仓库一条（例如，每个微服务一条），每个管道都完成自己的所有工作，并且再次以生产环境结束（[图 1-3](#ch01.html#the_quotation_markmultiple_end_to_end_p)）。例如，如果你使用 Azure DevOps，创建这些管道就很简单。^([3](#ch01.html#ch01fn3))

![](assets/sarm_0103.png)

这两种管道形状最可能*相似*于你所拥有的，但我猜你的这个图示版本会稍微复杂一些，需要再重构一次，拆分为一系列子管道（[图 1-4](#ch01.html#the_quotation_markpipeline_made_of_mult)）。让我们考虑一个示例，展示三个这样的子管道，它们端到端配合以将更改交付到生产环境。

也许第一个子管道监听对仓库的推送并进行编译、打包以及单元和组件测试，然后发布到二进制构件仓库。也许随后是一个第二个独立的子管道，将这个新发布的构件部署到一个或多个测试环境。可能第三个子管道由类似 CAB 流程^([4](#ch01.html#ch01fn4))触发，最终将更改部署到生产环境。

![](assets/sarm_0104.png)

希望你已经确定了自己的实际情况。但如果没有，还有第四种主要的管道类型，我们的最后一次心智重构步骤将带我们到达：多阶段扇入，如 [图 1-5](#ch01.html#the_quotation_markfan_in_pipelinequotat) 所示。这里我们通常会为第一阶段找到每个仓库一个单独的子管道，然后“扇入”到一个共享的子管道或一组子管道，将更改带到生产环境的其余部分。

![](assets/sarm_0105.png)

## 定位你的仪器化点

除了有四个指标外，我们还有四个仪器化点。现在让我们在心智模型中定位它们，无论你的模型是什么形式。我们到目前为止一直关注管道，因为它们通常提供其中两个点：提交时间戳和部署时间戳。第三和第四个仪器化点来自于服务降级被检测到时以及被标记为“已解决”时创建的时间戳。我们现在可以详细讨论每个点。

### 提交时间戳

在考虑团队的工作实践时，这里不可避免地会出现细微差别。他们是否按功能分支？他们是否进行拉取请求？他们是否混合使用不同的实践？理想情况下（正如 *Accelerate* 的作者所建议的），只要任何开发人员变更集被认为已完成并被提交，无论在哪里，你的计时器就开始计时。如果团队这样做，请注意：这种在分支上保留更改的做法不仅延长了反馈周期，还增加了你的工作负担和基础设施需求。（我将在下一节中介绍这些。）

由于这种复杂性，有些人选择使用从合并到 main 触发管道作为代理触发点或提交时间戳。我理解这听起来可能像是面对次优实践的认输，^([5](#ch01.html#ch01fn5)) 但如果你选择代理触发，我知道你会感到内疚（因为你知道自己没有遵循标准最佳实践）。无论我们是否包含额外的等待时间，指标都会为你带来许多其他好处，即使你给自己放个假，在代码到达 main 时才开始早期采样。如果这些代理最终被证明是显著交付次优化的来源，*Accelerate* 为你提供了建议（例如主干开发和结对编程），^([6](#ch01.html#ch01fn7)) 这些建议通过将更改到达 main 的时间作为你想要启动计时器的时间，影响了你的提交时间戳。到那时，你将开始看到指标的好处，并希望改进它们的捕获。

### 部署时间戳

在解决了提交时间后，你会很高兴听到时钟的“停止”要简单得多：就是执行最终部署到生产环境的管道完成时。这难道不给那些在*事后*进行手动冒烟测试的人一个喘息的机会吗？是的，但我再次把这留给你自己的良心，如果你真的想包含这个最终活动，你总可以在管道末尾放置一个手动检查点，由 QA（或检查部署的人）在他们确信部署成功后按下。

### 多阶段和扇入管道带来的复杂性

鉴于这两个数据源，你可以计算我们从管道中需要的信息，那就是*总运行时间*：时钟开始和时钟停止之间的经过时间。如果你有我们之前讨论的较简单管道场景之一，即不进行扇入的场景，那么这相对容易。拥有一个或多个端到端管道的人最容易。^([7](#ch01.html#ch01fn8))

如果你不幸拥有多个子管道（如我们在 [图 1-4](#ch01.html#the_quotation_markpipeline_made_of_mult) 中看到的），那么你需要对包含在“开始”时间戳和“部署”到生产环境中的变更集进行额外的数据收集。鉴于这些数据，你可以进行一些处理来计算每个单独更改的总运行时间。
