
## 实现债务
源代码中包含所谓的代码坏味道，例如过长的方法和空的 catch 块。实现债务现在可以利用各种工具以高度自动化的方式在源代码中发现。每个开发团队都应在日常工作中逐步解决这一债务，而无需额外预算。

## 设计与架构债务
类、包、子系统、层和模块的设计及其之间的依赖关系不一致且复杂，与计划的架构不符。这种债务无法通过简单的计数和测量来确定，需要进行广泛的架构评审，该内容在 [“确定 MMI 的架构评审”](#ch04.html#architecture_review_to_determine_the_mm) 中介绍。

其他也可视为软件项目债务的问题领域，例如缺少文档、测试覆盖率差、可用性差或硬件不足，在此被排除，因为它们不属于技术债务的范畴。

# 技术债务的起源
让我们来看技术债务的起源和影响。如果在软件开发项目的开始设计了高质量的架构，那么可以假设软件系统在开始时可以轻松维护。在此初始阶段，软件系统处于低技术债务的走廊中，维护工作量相同，如 [图 4-1](#ch04.html#origination_and_effect_of_technical_deb) 所示。
如果系统在维护过程中不断扩展以集成变更，技术债务不可避免地会产生（[图 4-1](#ch04.html#origination_and_effect_of_technical_deb) 中向上箭头所示）。软件开发是一个持续的学习过程，其中解决方案的第一次尝试很少是最终的。架构的修订（架构改进，以向下箭头表示）必须定期进行。这形成了一个持续的维护/变更与架构改进的序列。

![](assets/sarm_0401.png)

如果团队能够永久地遵循扩展和架构改进的恒定序列，系统将保持在低且稳定的维护成本走廊中。不幸的是，架构改进的这一方面直到近年才真正成为许多预算管理者的现实——对于大多数始于 2000 年代初的系统来说为时已晚。
如果开发团队不被允许持续减少技术债务，随着时间的推移，架构侵蚀不可避免地会发生，如 [图 4-1](#ch04.html#origination_and_effect_of_technical_deb) 中离开低且稳定维护成本走廊的上升箭头所示。此过程称为 *架构侵蚀*。一旦技术债务累积起来，维护和更改软件变得越来越昂贵，因果错误也越来越难以理解，以至于每次更改都成为一种痛苦的努力。[图 4-1](#ch04.html#origination_and_effect_of_technical_deb) 通过向上箭头不断变短的事实清楚地表明了这种缓慢的衰退。随着债务的增加，每单位时间内可实现的功能越来越少。

摆脱这种技术债务困境有两种方法：

### 重构
你可以从内部开始重构遗留系统，从而再次提高开发速度和稳定性。在这通常艰难的道路上，系统必须逐步重新进入低且稳定的维护成本走廊（参见 [图 4-1](#ch04.html#origination_and_effect_of_technical_deb) 中标记为“重构”的下降箭头）。

### 替换
或者可以用技术债务更少的软件替换遗留系统（参见 [图 4-1](#ch04.html#origination_and_effect_of_technical_deb) 中的圆圈）。

当然，也可能在开发开始时现场没有能力强的团队。在这种情况下，技术债务在开发开始时就被承担并持续增加。可以说这样的软件系统是在恶劣条件下成长起来的。无论是软件开发人员还是管理层，从长远来看都不会喜欢处于这种状态的系统。
这种对技术债务的看法对于大多数预算管理者来说是可理解的。没有人愿意累积技术债务并在开发中慢慢陷入困境，直到每次调整都成为无法估算的成本负担。需要持续工作以在软件整个生命周期内保持技术债务较低这一方面也可以很好地传达。大多数非 IT 人士现在都清楚地了解这个问题，但你如何实际评估软件系统中的债务呢？

# 使用 MMI 进行评估
我关于架构和认知科学的博士论文，以及超过三百次架构评估的结果，使我和我的团队能够创建一个统一的评估方案，名为 MMI，用于比较各种系统中架构中累积的技术债务。
认知科学告诉我们，在进化过程中，人类大脑获得了处理复杂结构的一些令人印象深刻的机制，例如政权组织、城镇和国家的布局、谱系关系等等。软件系统无疑也是复杂结构，因为它们的大小和所包含的元素数量。在我的博士论文中，我将认知心理学关于大脑处理复杂性的三个机制（分块、构建层级和构建图式）的发现与计算机科学中重要的架构和设计原则（模块化、层级和模式一致性）联系起来。在本章中，我只能提供这些关系的简要解释。完整的细节，特别是关于认知心理学的部分，可以在我的书中^([2](#ch04.html#ch01fn40))找到，该书源于我的博士论文。
这些原则具有突出的特性，即它们有利于大脑处理复杂结构的机制。遵循这些原则的架构和设计被人们视为统一且易于理解，从而更容易维护和扩展。因此，这些原则必须在软件系统中使用，以便维护和扩展可以快速且无太多错误地进行。目标是我们能够在很长一段时间内使用不断变化的开发团队继续开发我们的软件系统，同时保持相同的质量和开发速度。

# 模块化
在软件开发中，*模块化* 是 David Parnas 在 1970 年代引入的原则。Parnas 认为模块应只包含一个设计决策（封装），并且该设计决策的数据结构应封装在模块本地。^([3](#ch04.html#ch01fn41))
在现代编程语言中，模块是软件系统内的单元，例如类、组件或层。我们的脑喜欢在不同单元层面上对系统进行推理，以实现记忆容量的提升。这里的关键点是，我们的大脑只有在细节可以表示为形成有意义事物的连贯单元时才能从这些单元中受益。因此，结合任意无关元素的程序单元是没有意义的，也不会被我们的大脑接受。因此，具有连贯且有意义程序单元的模块化系统将具有低技术债务和低不必要的复杂性。
