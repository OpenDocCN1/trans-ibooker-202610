
* 在源文件/类级别限制循环依赖。任何包含超过五个元素的循环组都有很大可能变成代码癌症并进一步增长，直到变得非常难以理清混乱。如果可以，请避免即使是小的循环组。
* 避免代码重复（复制粘贴式编程）。我之前没有提到这一点，因为本章侧重于指标，但复制粘贴编程是一种典型的[代码坏味道](https://oreil.ly/xUtfn)。有时，复制代码可用于打破否则难以打破的循环，但我认为那是一种罕见的边缘情况。
* 将源文件的大小限制为 800 `LoC`（作为软阈值）。
* 将最大缩进限制为 4，`Modified Cyclomatic Complexity` 限制为 15（作为软阈值）。

所有这些规则都可以使用你在本章学到的内容来实现。实现它们的最佳方式是基于工具的方法，在 CI 构建中自动验证这些规则。跨组织实施这些规则也是一个好主意，这样所有开发人员都能熟悉它们。这样做几乎可以保证更好的可维护性、更好的代码质量，从而大幅提高开发人员生产力。我曾与多位客户合作实施这种基于规则的方法，可以确认它会随着时间的推移产生相当令人印象深刻的改进。

# 结论

你在本章学习了一些有用的指标，以及基于指标的反馈循环的概念。而且你现在知道结构性技术债务（或架构债务）会严重损害开发团队的生产力。

到现在为止，应该很清楚指标是一种强大的工具，可以帮助你及早发现有害趋势，确保你的软件项目永远不会变成一团乱麻。当然，为此你需要使用工具，其中一些甚至是免费的。如果你还不准备在更大范围内使用指标，我强烈建议专注于避免或至少限制代码库中的循环依赖。仅此一点就能阻止结构侵蚀的最坏副作用，并使你在今后更容易采用更严格的规则。

# 第 10 章. 使用目标-问题-度量方法衡量未知

Michael Keeling

在软件中，就像在生活中一样，最重要的事情往往是最具挑战性的衡量对象。系统中存在多少技术债务，应该在何处投资？已实现的架构在多大程度上满足了最重要的质量属性？团队的设计成熟度进展如何？对于这类大问题，很容易基于直觉做出猜测，而直觉可能存在偏见且不可靠。最好使用数据。当我需要为这类棘手、难以回答的问题定义指标时，我会转向目标-问题-度量（GQM）方法。

GQM 方法是一种分析技术，由 Victor Basili 和 David Weiss [提出](https://oreil.ly/SMvwj)，帮助团队弄清如何在软件开发中衡量和评估棘手问题。^([1](#ch10.html#ch01fn79)) 该技术易于学习且直接应用。它可以单独使用，也可以作为协作研讨会的一部分。发现用于评估困难问题的正确指标仍然需要创造力和分析思维，但 GQM 提供了足够的结构来推动团队取得更好的成果。

在本章中，你将学习如何使用 GQM 方法并主持以 GQM 为核心的协作研讨会。你还将看到一个案例研究，介绍一个软件开发团队如何使用 GQM 评估和改进其架构中的差距。读完本章后，你将知道将 GQM 应用于团队所需的一切。

## 目标-问题-度量方法

GQM 背后的核心假设很简单：要很好地衡量某件事，你必须了解为什么要衡量它。理解 *why*——你想要实现的目标以及评估进展所需回答的问题——使你能够识别和选择最适合工作的指标。理解指标背后 *why* 的团队更有可能使用并信任这些指标来指导未来的决策。GQM 帮助我们将目标从关于我们欲望的模糊陈述转变为可量化、可验证的模型。

GQM 模型是分层的。如果将其想象成一棵树，目标位于根部。从目标出发，树分支到问题，然后再次分支到用于回答这些问题的指标。叶子是用于计算指标的数据。通过这种方式，GQM 创造了可追溯性：你可以从任何单个叶子（正在收集的数据）追溯到根部（收集数据的最初目的）。

### 创建 GQM 树

在 GQM 中，*goal* 是一个简单的陈述，描述你想要理解和衡量的事物。理想的目标陈述描述了目的、要衡量的对象、感兴趣的问题或主题，以及你考虑目标的观点。

以下是一些关注软件架构问题的目标示例：

* 从用户角度提高系统可用性。
* 从产品经理的角度减少新微服务的开发时间。
* 从软件开发人员角度减少架构中的技术债务。
* 减少发布到生产环境中的错误数量。
* 在用户之前检测到生产环境中更多的问题。
* 从用户角度提高机器学习模型的准确性。
* 从开发团队角度在架构中做出更好的设计决策。

在流程开始时提供目标至关重要。目标通过将注意力集中在特定的一组度量上来确立概念方向。目标可以关注任何感兴趣的对象，包括架构元素、软件开发流程、技术实验、设计工件，甚至团队和组织。定义要评估的对象使要衡量的内容与你需要衡量的原因保持一致。

目标通常会在分析过程中被修订，因为你对所衡量内容的理解会不断提高。即使是不完美的目标陈述，只要能抓住需要衡量的本质，也是有用的。

一旦你定义了目标，你就可以提出 *questions* 来探索和描述它。问题应具有操作性，并帮助你评估相对于目标的进展：你是在靠近还是远离目标？

好的问题可以阐明问题以及解决这些问题的潜在下一步。提出好问题需要好奇心。你必须愿意暂时放下实际问题，提出需要被提出的问题，即使你现在不确定如何回答。
