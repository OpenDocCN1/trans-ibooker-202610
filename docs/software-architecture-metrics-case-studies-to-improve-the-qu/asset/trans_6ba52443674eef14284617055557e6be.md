
检查源代码中的模式通常是架构评审中最令人兴奋的部分。在这里，你必须把握开发团队实际工作的层面。实现各个模式的类通常分布在包或目录中。通过对右侧所示的 [图 4-5](#ch04.html#pattern_at_class_level_equals_pattern_l) 中的模式进行建模，可以使架构的这一层面变得可见且可分析。

模式一致性不像层次结构那样可以直接度量，但在下一节中，我们将汇总一些用于在 MMI 中评估模式一致性的度量。

# 计算 MMI

MMI 是根据各种标准和指标计算得出的，我们试图通过这些标准和指标映射模块化、层次结构和模式一致性这三个原则。在 MMI 的整体计算中，这三个原则以百分比形式包含在内，并针对它们使用 [表 4-1](#ch04.html#modularity_maturity_index) 中的说明计算出不同的标准。模块化对 MMI 具有最强的影响，占比 45%，因为模块化也是层次结构和模式一致性的基础。这也是 MMI 名称的由来。^([4](#ch04.html#ch01fn42))

[表 4-1](#ch04.html#modularity_maturity_index) 中的标准可以通过指标工具、架构分析工具或评审员的判断来确定（参见“确定方式”列）。有许多指标工具可以测量精确值，但为了 MMI 的可比性，必须考虑特定工具中使用的每个指标的实现方式。评审员的判断无法度量，但由评审员自行决定。架构分析工具是可以度量的，但很大程度上取决于评审员的见解。

为了评估我工作场所中这些不可度量的标准，评审员依赖于与开发人员和架构师的讨论。这在现场或远程研讨会中进行。我们还借助架构分析工具，从各种架构视角讨论系统。^([5](#ch04.html#ch01fn43)) 为了确保最大的兼容性，我们总是成对进行评审，然后在更大的架构评审员组中讨论结果。
