## 可持续变化的工具

什么样的架构选择能让你保持选择开放？有五种软件设计属性有助于实现可持续的、演进的方法。它们是：

Modularity: 将系统划分为可以更改而不强制其他部分更改的部分。
Cohesion: 将一起变化的代码部分在代码中保持靠近。
Separation of concerns: 确保代码和系统的每个部分都专注于解决一个问题。
Abstraction/information hiding: 在系统中创建“缝隙”允许在无需理解系统其他部分如何工作的情况下使用行为。
Coupling: 系统中不同部分需要一起变化的程度。

这些属性对信息普遍适用，而不仅仅是软件。它们没有说明系统如何工作或任何给定技术的性质。

无论系统做什么，无论它采用什么技术，如果它是模块化且内聚的，如果它有效地分离关注点，如果它使用良好的抽象来区分系统的各个部分，并且如果它适当地管理系统不同部分之间的耦合，那么它将比在这些属性上得分不高的类似系统更容易工作、更容易更改、更易于理解且更易于测试。

采用这种演进的方法进行设计和架构并以这种方式构建意味着，随着你学到更多，适应你所学到的新事物将变得更容易。

例如，如果你发现你的系统使用图数据库比关系型数据库更高效怎么办？如果你一开始就选择将领域逻辑的核心与持久化其结果的问题分离，那么更改起来会更容易。这样的系统表现出良好的关注点分离、更好的模块化、内聚性和不错的抽象。你可以想象相对轻松地拔掉你的基于 RDBMS 的存储库并替换为 GraphDB 存储库。然而，如果你的核心领域和持久化被混在一起，那么甚至考虑做出这样的改变都将非常困难。

## 可测试性：创建高质量系统

如何在你创建的系统中融入这五种质量属性？传统的答案是“视情况而定”。它取决于创建代码的团队或个人，特别是他们的技能、经验和承诺。

如果相关人员缺乏技能，那么无论他们多么努力，都不会产生高质量的结果。如果他们缺乏经验，即使在问题的某些方面很熟练，他们也会错过一些想法或更微妙的方面，比如抽象的泄漏或可能损害复杂系统开发的不同类型的耦合。如果他们没有足够的动力做好最好的工作，那么无论技能或经验如何，结果都可能很差。

但还有其他因素。你需要知道你的软件是否有效，这意味着要对其进行测试以验证系统是否按预期工作。更重要的是，你需要安全和自信地更改系统的自由。如果你编写代码或系统却不对其进行测试，那么你最好离开键盘重新思考。“Write-only development”永远不会为除琐碎的、一次性代码之外的任何东西产生高质量的结果。

如果你需要测试，那么唯一的争论就是：手动还是自动化？手动测试缓慢、低效、昂贵且不可靠；自动化测试无疑是更有效的方法，并且往往能带来更高的质量。那么如何尽可能轻松地测试你的代码？是什么使代码 *testable*？

要在系统中测试某物，你需要访问该系统的相关部分。这些组件应处于明确定义的状态，准备好进行评估。你将调用系统的某些行为，然后捕获系统的响应，以便你可以对其进行评估并确定它们是否与你的预期相匹配。
