```
    .layer("Service").definedBy("..service..")
    .layer("Persistence").definedBy("..persistence..")

    .whereLayer("Service").mayNotBeAccessedByAnyLayer("Controller")
    .whereLayer("Persistence").mayNotBeAccessedByAnyLayer("Service")
  
```

使用诸如 `ArchUnit` 之类的工具非常方便——但仅适用于 `Java` 平台上的团队，并且仅用于编译时验证。类似的工具 [NetArchTest](https://oreil.ly/CUako) 可用于 `.NET` 平台。那么不同平台怎么办？更重要的是，对于微服务等分布式架构的同类验证怎么办？

通常，架构解决方案需要手工打造。大多数架构并非通用，而是好/坏、旧/新以及自选/强加的工具、框架、包等的拼凑组合。然而，通过使用标准工具，架构师可以构建简单的适应性函数来实现相同的目的。

例如，请考虑 [图 8-7](#ch08.html#orchestrated_workflow_in_a_microservice) 中说明的微服务拓扑。

![](assets/sarm_0807.png)

在 [图 8-7](#ch08.html#orchestrated_workflow_in_a_microservice) 中，最左边的服务充当编排器，协调右侧三个领域服务的工作流。作为架构师，我希望确保领域服务之间不会相互交互——只有编排器。

虽然此问题与 [图 8-6](#ch08.html#package_structure_illustrating_a_layere) 中显示的层拓扑问题相似，但由于分布式架构之间可能存在差异，构建此类工具几乎不可能，因此没有单一工具可以管理它。这是一个很好的例子，说明架构师必须使用其技术组合可用的功能自行拼凑的必要工具。

架构师可以实现一个适应性函数来验证编排器通信，如 [示例 8-3](#ch08.html#example_eight_threedot_fitness_function) 中的伪代码所示。

### 示例 8-3. 用于验证允许的编排器通信的伪代码适应性函数

```
def ensure_domain_services_communicate_only_with_orchestrator
  list_of_services = List.new()
                        .add("orchestrator")
                        .add("order placement")
                        .add("payment")
                        .add("inventory")
  list_of_services.each { |service|
    service.import_logsFor(24.hours)
    calls_from(service).each { |call|
      unless call.destination.equals("orchestrator") 
          raise FitnessFunctionFailure.new()
    }
   }
end
```

在 [示例 8-3](#ch08.html#example_eight_threedot_fitness_function) 中，架构师定义了服务列表和期望的通信规则。然而，与 `ArchUnit` 的情况不同，没有框架可以为您的特定架构验证这些规则。因此，架构师必须编写代码来发现构建验证所需的必要信息。在此示例中，我们假设每个服务都为其在特定时间快照中进行的每个服务调用提供日志记录。适应性函数的主体为每个服务加载过去 24 小时的日志，然后解析每个日志以确定调用目标。如果目标与规则不同，代码会引发异常以指示失败。

架构师可以以多种方式实现 [示例 8-3](#ch08.html#example_eight_threedot_fitness_function) 中显示的适应性函数。例如，如果团队使用监视器而不是取证日志记录，适应性函数将连接到有关服务调用的实时信息，并且适应性函数将利用事件处理程序来调查并在出现错误调用时触发警报。

如果架构师无法立即找到可下载的现成工具来实现适应性函数，重要的是不要绝望。现代开发生态系统中存在的许多工具允许小型临时适应性函数将它们的输出粘合在一起。

# 案例研究：零日安全检查

架构师通常将指标视为代码的低级评估，基于众多的现有示例。然而，与适应性函数结合使用时，其范围可以像组织所需的那样广泛。

2017 年 9 月 7 日，美国一家主要的信用评分机构 Equifax 宣布发生数据泄露。问题追溯到对 `Java` 生态系统中流行的 `Struts` Web 框架的黑客利用（`Apache Struts` v`CVE-2017-5638`）。Apache 基金会已于 2017 年 3 月 7 日发布声明宣布该漏洞并发布了补丁。美国国土安全部随后在第二天联系了 Equifax 和类似公司警告他们此问题，并在 2017 年 3 月 15 日运行扫描，发现了大多数受影响系统……*most* of them。因此，关键补丁直到 2017 年 7 月 29 日才应用于许多旧系统，当时 Equifax 的安全专家发现了导致 2017 年 9 月发生数据泄露的黑客行为。

想象一个替代世界，其中每个项目（即使处于空闲状态）都有一个部署管道，并且安全团队在每个团队的部署管道中都有一个“插槽”，可以在其中部署适应性函数，如 [图 8-8](#ch08.html#a_deployment_pipeline_that_includes_a_s) 所示。

大多数情况下，[图 8-8](#ch08.html#a_deployment_pipeline_that_includes_a_s) 中显示的安全阶段将执行防止开发人员将密码存储在数据库中以及类似常规治理任务等保护措施的平凡检查。然而，当零日漏洞出现时，拥有相同的机制允许安全团队在每个项目中插入一个测试，检查特定框架和版本号，并启动项目的构建。如果发现危险版本，它将使构建失败并通知安全团队。如果 Equifax 的架构师让所有项目仍然使用部署管道，即使是未处于积极开发中的项目，也将实现自动化治理。团队配置部署管道以对生态系统的任何更改做出响应：代码、数据库模式、部署配置和适应性函数。这使企业能够普遍自动化重要的治理任务，其范围远比人们通常对指标的思考更广。

适应性函数为架构师提供了许多好处，其中最不重要的就是再次进行一些编码的机会！架构师的普遍抱怨之一是他们不再经常编码——但适应性函数通常就是代码。通过构建架构的可执行规范，任何人都可以随时通过运行项目的构建来验证它，架构师必须很好地理解系统及其持续演变，这与跟上项目代码增长的核心目标重叠。
