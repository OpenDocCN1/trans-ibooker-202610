
那么你的系统的哪些特性会促进这一点？如果能只关注系统的行为就太好了。模块化的系统比非模块化的系统更容易测试。

关注行为，关注我们面前的模块，那么我们希望它能很容易地为测试做好准备。如果被测试的模块缺乏内聚性并且与其它模块紧密耦合，这就会很困难。内聚且松耦合的软件也更容易测试。

为了将系统置于某种精确状态，你需要控制变量，从而在评估的上下文中限制其复杂性。良好的关注点分离让你能够专注于感兴趣的行为，而非一堆使画面复杂化的行为。

最后，如果你的测试与被测试的代码某种程度上是解耦的，那么代码可以更改而无需强制更改测试。这意味着最可测试的代码也被很好地抽象，并且隐藏了实现细节以免测试可见。这同样使测试更容易设置，因为我们设计中的抽象层形成了边界，我们可以在此基础上进行测试，从而限制测试的范围和复杂性。

因此，可测试代码的属性与我们看重在易于工作和更改的代码中的属性相同。这很有趣！

如果你想设计可测试的代码，最简单也最好的方法是使用测试来指导代码的设计。如果你将可测试性视为一种有价值的架构属性，并组织工作将测试融入开发和设计流程，使你的系统始终可测试，那么你将提升设计的品质。

为可测试性而设计放大了开发者的才华，并造就了系统，这些系统比仅依赖他们的技能、经验和承诺更能体现五大属性。

总而言之，为可测试性而构建，随着时间的推移赋予你根据需求修改系统的自由。

## 可部署性：扩展我们的系统开发

可测试性是我们可以用以推动更有效的工程流程从而实现更好架构系统的工具。它在多种不同的规模上发挥作用，但还有另一种在更系统层面运作的工具：*可部署性*。

我最密切相关的软件开发方法称为*持续交付*。在持续交付中，我们致力于确保我们的软件始终处于可发布状态。这由称为*部署流水线*的机制决定。部署流水线自动化了我们大部分发布流程，并代表了对系统可发布性的明确评估。如果部署流水线通过了所有评估，那么软件按定义是安全的可以发布，并且决定软件可发布性的所有内容都在部署流水线的范围内。

如果部署流水线定义了可发布性，那么其范围就是“从提交到可发布结果”。如果发布候选成功通过流水线，它就适合发布*无需再做任何工作*。如果在流水线结束时，你需要更广泛地与其他部分一起测试这些组件或子系统，那么你的流水线在任何有意义的方式上都不能决定“可发布性”。

为了实现高质量，你需要对系统进行明确的评估。这意味着要精确查看如果成功将被部署到生产环境中的更改。此外，为了提高这些评估的可靠性，你需要提高其*确定性*。因此你的目标是评估确切进入生产环境的代码，并确保该代码的行为尽可能确定。如果能做到这一点，你进行的任何测试在该版本代码上每次运行都会产生相同的结果。

这意味着部署流水线的范围存在一些合理的限制；*部署流水线的正确范围始终是一个独立可部署的软件单元*。这可能是一个单独的微服务或一个完整的企业系统，但可部署性是唯一的明确评估范围。

## 结论

当开发者思考软件架构时，我们经常会想到系统的其他重要属性，如安全性、可扩展性和弹性。最终，这些想法的重要性程度取决于系统及其开发者所处的业务以及整个系统的成熟度。

如果你过于关注可扩展性和弹性，而最终只有三个用户，那么所有这些工作都是浪费精力。如果为通用使用而关注安全性，但软件从未超出公司内网的围墙花园使用，那也是浪费精力。这相当于过度设计系统以满足未来可能出现也可能不出现的需要。

相反，如果你采用工程主导的问题解决方式以及架构和设计的演进方式，你可以更早开始开发，并更好地使系统适应眼前的需求。这是一个更好的策略。

将工作围绕可测试性和可部署性构建有助于你在系统演进时保持选择开放。如果你的系统是模块化、抽象化且总体上结构良好的，当你需要增强安全性时，将更容易添加。当你的代码需要更具弹性时，你可以实施混沌测试并了解如何实现。

在更技术层面，对更好可测试性和可部署性（特别是可测试性）的追求鼓励工程师设计系统，使其更有效地分离本质复杂性和偶然复杂性。这反过来为系统其他架构属性的变化——甚至相当激进的变化——保持更多选择。这种方法增强了你创建高质量、创新软件架构的能力。

Dr. Carola Lilienthal

在过去20年里，大量时间和金钱投入到了使用现代编程语言（如 Java、C#、PHP 等）实现的软件系统中。开发项目的重点往往在于功能的快速实现，而非软件架构的质量。这种做法导致技术债务——不必要的复杂性，会额外增加维护成本——随着时间的推移不断累积。今天，这些系统不得不被称为遗留系统，因为它们的维护和扩展成本高、繁琐且不稳定。
