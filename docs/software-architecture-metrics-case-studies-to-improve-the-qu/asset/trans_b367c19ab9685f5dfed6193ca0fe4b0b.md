
这里有多种商业力量在起作用，它们都影响着 YourFinFreedom 的软件架构。当然，这是一个简化的故事；每个情境都是独特的，并且总会有不同的力量在起作用（参见 [图 6-1](#ch06.html#examples_of_business_forces_that_affect)）。

![](assets/sarm_0601.png)

在我的职业生涯中，我观察到软件架构通常反映两个维度：公司的组织结构以及人们在该结构内的沟通方式。前者是显式的，通常可以在公司的组织架构图中找到。后者是隐式的，人们往往意识不到它对工作的影响，特别是对软件架构的影响。当软件架构不是有意设计的，也没有针对其应解决的挑战进行引导时，它会模仿人们（即团队和部门）的组织方式和沟通方式。这种现象被称为康威定律，以研究该现象的梅尔·康威命名。在一篇题为“How Do Committees Invent?”的1968年论文中，康威写道：“organizations which design systems (in the broad sense used here) are constrained to produce designs which are copies of the communication structures of these organizations.”^([1](#ch06.html#ch01fn52))

# YourFinFreedom 打破单体

*Keisha 产品工程部门负责人决定，最快的方式并提供更好质量的方法是采用微服务架构。现有的架构是一个单体，随着时间的推移不断增加各种功能和金融服务提供商的集成。随着部门向这种新的架构风格转型，它将从 3 个团队扩展到 10 个团队，每个团队负责自己的领域。Keisha 相信这种方法将使他们能够实现进入大型新欧洲市场的所需扩展。*

*在进行架构转型几个月后，Anna 觉得新的微服务架构不符合公司的业务需求，并且该项目可能会让公司失去一些市场机会。她向她的老板 Keisha 提出这个问题，但 Keisha 坚持要继续执行该计划并说服 Anna 配合。*

让我们聚焦于我在许多快速成长公司中观察到的两个常见场景（[图 6-2](#ch06.html#common_challenges_of_monoliths_and_micr)）：首先，我们来看拆分单体，然后我们来看如何理清微服务网络。

单体和微服务架构是不同的架构风格，团队需要在集中式架构（单体）和分布式架构（微服务）之间做出权衡。这种选择对软件架构有影响，因为它会影响团队聚合对产品或服务至关重要的业务逻辑的方式。

![](assets/sarm_0602.png)

这些架构在正确实现的情况下都可以是合理的。然而，基于从商业力量到技术炒作等不同因素，单体架构常常会演变成架构师所称的 *大泥球*，而微服务架构则常常会演变成 *分布式大泥球*（[图 6-3](#ch06.html#this_two_dimensional_chart_visualizes_t)）。

![](assets/sarm_0603.png)

“大泥球”这一术语由 Brian Foote 和 Joseph Yoder 于 1999 年提出；他们将其描述为“haphazardly structured, sprawling, sloppy, duct-tape and bailing wire, spaghetti code jungle。”^([2](#ch06.html#ch01fn53)) 在光谱的另一端，分布式大泥球具有相同的特征，外加一个新特征：它分布在网络上，给等式增加了更多复杂性。让我用两个例子及其后果来说明。

当一个组织采用单体架构并希望更快地将新功能推向市场时，它会招聘更多人员来组建产品工程团队。这些人员和团队开始在现有的集中式架构之上尝试不同的解决方案，向系统中引入 *偶然复杂性* 并形成大泥球。偶然复杂性可以理解为以依赖关系、某些文档不全或未经测试的代码，或无结构的软件设计形式引入系统的复杂性。这些通常发生在产品工程团队难以应对不同商业力量时。偶然复杂性会产生连锁反应，影响软件的可维护性、可运维性 和可变更性，最终使组织更难快速将新功能推向市场，正如 Frederick Brooks 所指出的那样。^([3](#ch06.html#ch01fn54))

在分布式大泥球光谱的这一侧，你有人员和团队试图理清微服务网络。这些系统通常对它们旨在解决的业务问题过度设计，以至于理解一次业务交易所需的 *认知负荷* 超出了人类大脑的承受能力。Matthew Skelton 和 Manuel Pais 将一个人的认知负荷定义为“limit on how much information they can hold in their brains at any given moment. The same happens for any one team by simply adding up all the team members’ cognitive capacities.”^([4](#ch06.html#ch01fn55))

# 实现分布式大泥球

*一年后，YourFinFreedom 拥有大量不同的微服务，包括单体的残余部分，均由 10 个产品工程团队管理。然而，新架构并未兑现更快行动并为客户提供更好质量的承诺。团队未能实现预期潜力，并且旗舰产品不断出现问题。*

*Anna 决定与 Keisha 以及产品工程管理团队的其他成员进行讨论，说明团队面临的日常障碍。这些包括以下内容：*

*   *团队必须在微服务之间进行发布编排，才能将特定区域的功能推向生产环境。*
*   *不同微服务之间存在功能重叠，使得团队难以承担所有权。*
*   *团队的生产力不如预期；Anna 指出部门的优先事项不断变化，导致大量工作被放弃。*
*   *产品不断出现问题，损害了士气并使员工失去动力。*
*   *团队成员不了解产品的方向以及他们如何为之做出贡献。*

*Anna 提出了一个潜在解决方案：在架构中实施指标和明确的边界可以为产品工程团队提供所需的方向，同时允许软件架构演进，以匹配公司扩张的雄心。*

*管理层对 Anna 坦诚的演示和提出的解决方案感到满意。他们一直怀疑转向微服务并未兑现其承诺，现在他们意识到在开始之前没有正确权衡取舍。Keisha 决定挑战 Anna：鉴于她在工程和领导方面的技能，她说，她正在考虑将 Anna 提升为部门内的新解决方案架构师职位。在这个新角色中，Anna 将推动产品工程团队的架构工作，并担任管家角色，促进公司技术生态系统的一致性。Keisha 邀请 Anna 考虑这次晋升。*

*几天后，Anna 在一个条件下接受了 Keisha 的提议：她希望获得完全的许可与公司各部门互动，以便了解他们的挑战。Keisha 同意了，Anna 感到受到支持。她职业生涯的新篇章开始了！*

Anna 的部门正在承受分布式大泥球的痛苦。她故事中描绘的障碍反映了架构的偶然复杂性。
