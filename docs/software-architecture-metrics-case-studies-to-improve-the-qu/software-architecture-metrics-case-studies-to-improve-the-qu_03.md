# 第 3 章. 进化式架构：以可测试性和可部署性指导架构

Dave Farley

软件架构既重要又短暂。它可以决定系统的一些重要特性，例如可扩展性、性能和弹性。它之所以短暂，是因为我们在评判这些品质时往往含糊且主观。

架构描述和文档最好像我们作为架构师所构建的系统的旅游地图。它们让我们能够在不对其细节过于精确或具体的条件下导航——而这些细节很可能发生变化。对用户和客户需求的进一步了解可能会改变我们对系统架构属性需要在尺度上处于何处的看法。

如果你从事软件架构工作，你可能会想：我如果从一个简单的系统开始，当需求快速增长时该如何应对？如果需求没有增长怎么办？如何应对对性能、安全性和长时间运行的需求增长？如何将我的系统维护为一个能够轻松演进以满足新需求或不可预见需求的可居住空间？如何在保持对不可预见变化开放的同时，避免用过于复杂的未来防范措施阻碍开发过程？

本章论证答案是一种防御性方法：软件架构师需要设计并学习管理他们所创建的系统复杂性的技术。

## 学习与发现的重要性

复杂系统永远不会完全从其创造者的脑海中凭空出现；它们是增量进展和学习过程的产物。软件开发始终是学习和发现的练习。这意味着如果你想做好工作，就需要停止试图想象你应该，甚至能够预见你的系统将如何被使用以及随时间如何演进。

在现实世界中，我们构建的系统是复杂自适应系统的一部分，其中包括开发者、用户和客户，以及他们的环境和组织背景。这一现实要求采用更动态、几乎是有机的架构和设计方法，使你能够在过程中学习并将软件适应对其功能和方式不断变化的认知。

## 可持续变化的工具

什么样的架构选择能让你保持选择开放？有五种软件设计属性有助于实现可持续的、演进的方法。它们是：

Modularity: 将系统划分为可以更改而不强制其他部分更改的部分。
Cohesion: 将一起变化的代码部分在代码中保持靠近。
Separation of concerns: 确保代码和系统的每个部分都专注于解决一个问题。
Abstraction/information hiding: 在系统中创建“缝隙”允许在无需理解系统其他部分如何工作的情况下使用行为。
Coupling: 系统中不同部分需要一起变化的程度。

这些属性对信息普遍适用，而不仅仅是软件。它们没有说明系统如何工作或任何给定技术的性质。

无论系统做什么，无论它采用什么技术，如果它是模块化且内聚的，如果它有效地分离关注点，如果它使用良好的抽象来区分系统的各个部分，并且如果它适当地管理系统不同部分之间的耦合，那么它将比在这些属性上得分不高的类似系统更容易工作、更容易更改、更易于理解且更易于测试。

采用这种演进的方法进行设计和架构并以这种方式构建意味着，随着你学到更多，适应你所学到的新事物将变得更容易。

例如，如果你发现你的系统使用图数据库比关系型数据库更高效怎么办？如果你一开始就选择将领域逻辑的核心与持久化其结果的问题分离，那么更改起来会更容易。这样的系统表现出良好的关注点分离、更好的模块化、内聚性和不错的抽象。你可以想象相对轻松地拔掉你的基于 RDBMS 的存储库并替换为 GraphDB 存储库。然而，如果你的核心领域和持久化被混在一起，那么甚至考虑做出这样的改变都将非常困难。

## 可测试性：创建高质量系统

如何在你创建的系统中融入这五种质量属性？传统的答案是“视情况而定”。它取决于创建代码的团队或个人，特别是他们的技能、经验和承诺。

如果相关人员缺乏技能，那么无论他们多么努力，都不会产生高质量的结果。如果他们缺乏经验，即使在问题的某些方面很熟练，他们也会错过一些想法或更微妙的方面，比如抽象的泄漏或可能损害复杂系统开发的不同类型的耦合。如果他们没有足够的动力做好最好的工作，那么无论技能或经验如何，结果都可能很差。

但还有其他因素。你需要知道你的软件是否有效，这意味着要对其进行测试以验证系统是否按预期工作。更重要的是，你需要安全和自信地更改系统的自由。如果你编写代码或系统却不对其进行测试，那么你最好离开键盘重新思考。“Write-only development”永远不会为除琐碎的、一次性代码之外的任何东西产生高质量的结果。

如果你需要测试，那么唯一的争论就是：手动还是自动化？手动测试缓慢、低效、昂贵且不可靠；自动化测试无疑是更有效的方法，并且往往能带来更高的质量。那么如何尽可能轻松地测试你的代码？是什么使代码 *testable*？

要在系统中测试某物，你需要访问该系统的相关部分。这些组件应处于明确定义的状态，准备好进行评估。你将调用系统的某些行为，然后捕获系统的响应，以便你可以对其进行评估并确定它们是否与你的预期相匹配。



那么你的系统的哪些特性会促进这一点？如果能只关注系统的行为就太好了。模块化的系统比非模块化的系统更容易测试。

关注行为，关注我们面前的模块，那么我们希望它能很容易地为测试做好准备。如果被测试的模块缺乏内聚性并且与其它模块紧密耦合，这就会很困难。内聚且松耦合的软件也更容易测试。

为了将系统置于某种精确状态，你需要控制变量，从而在评估的上下文中限制其复杂性。良好的关注点分离让你能够专注于感兴趣的行为，而非一堆使画面复杂化的行为。

最后，如果你的测试与被测试的代码某种程度上是解耦的，那么代码可以更改而无需强制更改测试。这意味着最可测试的代码也被很好地抽象，并且隐藏了实现细节以免测试可见。这同样使测试更容易设置，因为我们设计中的抽象层形成了边界，我们可以在此基础上进行测试，从而限制测试的范围和复杂性。

因此，可测试代码的属性与我们看重在易于工作和更改的代码中的属性相同。这很有趣！

如果你想设计可测试的代码，最简单也最好的方法是使用测试来指导代码的设计。如果你将可测试性视为一种有价值的架构属性，并组织工作将测试融入开发和设计流程，使你的系统始终可测试，那么你将提升设计的品质。

为可测试性而设计放大了开发者的才华，并造就了系统，这些系统比仅依赖他们的技能、经验和承诺更能体现五大属性。

总而言之，为可测试性而构建，随着时间的推移赋予你根据需求修改系统的自由。

## 可部署性：扩展我们的系统开发

可测试性是我们可以用以推动更有效的工程流程从而实现更好架构系统的工具。它在多种不同的规模上发挥作用，但还有另一种在更系统层面运作的工具：*可部署性*。

我最密切相关的软件开发方法称为*持续交付*。在持续交付中，我们致力于确保我们的软件始终处于可发布状态。这由称为*部署流水线*的机制决定。部署流水线自动化了我们大部分发布流程，并代表了对系统可发布性的明确评估。如果部署流水线通过了所有评估，那么软件按定义是安全的可以发布，并且决定软件可发布性的所有内容都在部署流水线的范围内。

如果部署流水线定义了可发布性，那么其范围就是“从提交到可发布结果”。如果发布候选成功通过流水线，它就适合发布*无需再做任何工作*。如果在流水线结束时，你需要更广泛地与其他部分一起测试这些组件或子系统，那么你的流水线在任何有意义的方式上都不能决定“可发布性”。

为了实现高质量，你需要对系统进行明确的评估。这意味着要精确查看如果成功将被部署到生产环境中的更改。此外，为了提高这些评估的可靠性，你需要提高其*确定性*。因此你的目标是评估确切进入生产环境的代码，并确保该代码的行为尽可能确定。如果能做到这一点，你进行的任何测试在该版本代码上每次运行都会产生相同的结果。

这意味着部署流水线的范围存在一些合理的限制；*部署流水线的正确范围始终是一个独立可部署的软件单元*。这可能是一个单独的微服务或一个完整的企业系统，但可部署性是唯一的明确评估范围。

## 结论

当开发者思考软件架构时，我们经常会想到系统的其他重要属性，如安全性、可扩展性和弹性。最终，这些想法的重要性程度取决于系统及其开发者所处的业务以及整个系统的成熟度。

如果你过于关注可扩展性和弹性，而最终只有三个用户，那么所有这些工作都是浪费精力。如果为通用使用而关注安全性，但软件从未超出公司内网的围墙花园使用，那也是浪费精力。这相当于过度设计系统以满足未来可能出现也可能不出现的需要。

相反，如果你采用工程主导的问题解决方式以及架构和设计的演进方式，你可以更早开始开发，并更好地使系统适应眼前的需求。这是一个更好的策略。

将工作围绕可测试性和可部署性构建有助于你在系统演进时保持选择开放。如果你的系统是模块化、抽象化且总体上结构良好的，当你需要增强安全性时，将更容易添加。当你的代码需要更具弹性时，你可以实施混沌测试并了解如何实现。

在更技术层面，对更好可测试性和可部署性（特别是可测试性）的追求鼓励工程师设计系统，使其更有效地分离本质复杂性和偶然复杂性。这反过来为系统其他架构属性的变化——甚至相当激进的变化——保持更多选择。这种方法增强了你创建高质量、创新软件架构的能力。
