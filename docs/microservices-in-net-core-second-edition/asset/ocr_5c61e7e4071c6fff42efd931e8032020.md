# 7.3.3 Implementing a slow-paced retry strategy

The loyalty program microservice subscribes to events from the special offers microservice. Based on the events, the loyalty program sends commands to the notifications microservice, asking it to notify users about new special offers. If sending a command to notifications fails, you want to retry. Because sending out notifications isn’t particularly time critical, you’ll choose not to retry immediately; instead, you’ll retry the next time the event subscriber would otherwise poll for new events. To do this, all you have to do is keep track of what the last successful event was.

Remember from chapter 5 that an event subscriber works by periodically waking up and polling the event feed for new events. On each such cycle, the next batch of events is read and handled. The next batch of events will begin one event after the last successfully handled event. This means all failed events are retried. It also means you may as well abort the rest of a batch as soon as one event fails—the rest will be retried later anyway.
