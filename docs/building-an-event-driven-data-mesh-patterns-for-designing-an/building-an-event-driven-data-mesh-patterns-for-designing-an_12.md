## 汇总

数据网格建立在四个原则之上，这些原则基于处理难以使用的数据时吸取的教训，此类数据通常不过是运营应用程序排放的一种废气。在数据原始来源之外获取和访问数据的机制通常是作为后续添加的，以临时方式附加到源系统上。

数据网格将数据提升为产品，采用与业务中任何其他产品相同的严谨性、所有权和功能管理。取而代之的是目的明确、受维护和支持的模式，而非“随便用，自己想办法”的数据访问方式。这既是社会转变，也是技术转变，需要自上而下和自下而上的支持。我们重新思考如何拥有、创建、发现和访问数据，然后构建使其运作所需的流程、治理和技术。

事件流是实现数据网格的首选方案。它们为历史数据和实时数据通信提供了一种单一机制，构成了数据网格的基本构建块，供消费者根据需要使用、混合和匹配。

数据网格基于四个主要原则：领域所有权、数据即产品、联邦治理和自助服务平台。这些原则共同帮助我们专注于安全、有效且大规模地在整个组织中传达重要业务数据：

- 领域所有权

最了解数据的人被赋予了责任，需要让同事和同行随意使用和访问这些数据。域所有者会与潜在消费者协商以获取数据需求，并确保满足业务需求。他们仍负责保护内部领域模型，防止外部方过度暴露和不可接受的耦合，以便内部模型和外部数据产品都能独立演变和变化。

### 数据即产品

重要业务数据需要作为构建块原语，随时可靠地为您的应用程序提供，无论应用程序的运行时、环境或代码库如何。我们可以通过专注于将数据创建为产品来实现这一目标，将数据视为一等公民，并配备专用所有权、最低质量保证、SLA 以及干净可靠访问的可扩展机制。

数据产品充当构建业务服务的基本构建块，使消费者能够为自己的用例访问和使用数据。

### 联邦治理

联邦治理关注的是维持稳定与秩序，平衡个人自主权与自上而下的集中控制。

由参与数据网格的人员组成的治理团队，负责满足域所有者、数据产品创建者、数据产品用户和基础设施提供者的需求。与任何有效治理形式一样，治理团队需要参与、代表、辩论和协作行动才能完成有意义的工作。治理团队指导自助服务平台的需求，重点是提高可发现性、易用性和与其他数据产品的互操作性。

成功的联邦治理将产生易于构建、管理和使用的数据产品。数据产品所有者在自助服务平台上构建和管理其数据产品时应拥有合理的选择。还应为他们提供护栏，以支持必要的非功能性业务要求，例如加密、访问控制和自动数据保留管理。

### 自助服务平台

正如每个数据网格实现都独一无二一样，其自助服务平台也是如此。创建自助服务平台的主要目标包括使以下操作变得容易：

- 浏览、发现和搜索可用的数据产品
- 授予、限制和管理访问控制
- 申请计算、存储和服务组件，包括事件流
- 管理数据产品生命周期，包括原型设计、发布、弃用和删除

构建自助服务平台需要与数据产品所有者和联邦治理团队密切合作。您成功的最佳机会是从一个最小可行产品开始，该产品由您已经使用的技术和控制系统组成。将您的自助服务数据平台视为任何其他产品，随着使用模式和要求变得更加清晰，迭代添加和测试新功能。

### 数据网格的事件流

事件是关于某事发生的不可变且自包含的记录。事件流是事件的不断更新的数据结构，每个流代表一组重要的业务事实。

事件流是服务数据产品的理想机制，因为它们提供了一种简单而强大的方式，可在整个组织中可靠地传达重要业务数据。事件流快速、可扩展且高效，可让消费者在新数据可用时立即得知，并能针对任何用例在整个业务中实现实时响应。

状态事件是构建数据产品的最佳选择，尽管您在选择上有一定余地。您可以包含诸如 _原因_ 状态发生变化的信息，将增量事件的某些方面与状态事件结合起来。但要谨慎，不要在数据产品中过度暴露源领域中的特定业务逻辑转换，因为它们会引入强耦合接缝。

Kappa 架构与状态事件协同工作。您可以仅从事件流中获取数据产品的完整历史，而不必像 Lambda 架构那样将历史和实时数据访问分开。历史状态可以通过从较早时间点消费事件流来访问。您可以使用压缩来消除较旧、不再相关的状态事件，使消费者访问数据变得快速、简单且廉价。

简单性是使数据网格运作的关键，事件流提供了一种简单而强大的解决方案，可让数据随时可用。

### 与现有系统集成

数据网格实现很少（如果有的话）是从零开始的开发。数据网格解决的痛点很大程度上是由组织的增长和多个不同用例对重要业务数据的需求造成的。因此，在构建数据网格时，您需要应对所有现有系统，并迭代努力改善数据在整个组织中的创建、共享和使用方式。




从现有数据库和系统中引导数据是开始使用数据网格的重要部分。您可以快速轻松地将数据发布到事件流中，以便消费者可以开始在自己的领域中试用它。它还能引发关于谁拥有连接器、进而谁拥有数据、领域以及管理功能请求以更改可用数据及其表示方式的讨论。

通常，引导式数据反映了源系统的内部领域模型。来自关系数据库的高度规范化数据往往难以使用，下游用户需要进行复杂且代价高昂的反规范化。事件频率、事件大小和紧密的内部耦合仍然是引导式数据产品需要关注的问题。

引导式数据产品仍然是通往一流数据产品（具有明确架构、反规范化数据结构以及与内部数据模型隔离）途中的垫脚石。但它们仍然是数据网格迭代增长的重要部分。

## 运营、分析与两者之间的一切

数据网格最初是为了解决分析领域固有的数据访问和可靠性问题而提出的。然而，它已被证明是为运营系统以及那些难以分类为其中一类的系统提供动力的一种强大非标签解决方案。可靠地访问干净、定义明确、低延迟的数据是战略灵活架构的基石。您可以自由创建、测试和试用新业务系统，而无需为数据访问而苦苦挣扎。您的系统将不再像弗兰肯斯坦的怪物那样，仅仅为了访问底层数据而被拼凑在一起。

事件流在为对时间敏感的应用程序提供动力方面发挥着关键作用。运营系统（尤其是有人参与循环的系统）从低延迟状态事件中获益匪浅。分析系统则通过从运营系统的相同来源获取数据而获益，缓解了历史上困扰数据领域的“类似却又不同”的数据来源问题。

## 摘要

事件驱动的数据网格是对未来的投资。要成功采用它，需要识别组织中的数据痛点，以便开始应用四项原则。通过帮助同事了解数据网格如何解决他们长期存在的数据问题，获得他们的支持。

进行迭代工作。您的数据网格不会一夜之间突然出现。试用新解决方案，从错误中吸取教训，并进行迭代改进。一路上发现价值对于保持人们投入并从数据产品中获益至关重要。

最后，在构建数据网格的过程中庆祝成功。道路将曲折曲折，有时您可能会感觉倒退。与同行分享您的磨难与考验，并共同努力寻找共同点和新的前进方向。祝您未来之旅顺利。
