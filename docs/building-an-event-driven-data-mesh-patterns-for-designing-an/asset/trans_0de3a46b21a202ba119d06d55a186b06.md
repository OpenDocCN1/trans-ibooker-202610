### 同一事件的多个消费者

一条记录可以被许多不同的用户消费，导致同一事件的多个副本，每个副本都有自己的血缘。

### 并非所有消费者都会发出事件

一些消费者不发出事件，而可能通过 REST API 提供对数据的访问。他们需要采取额外步骤来创建他们已摄取的哪些记录的日志，并确保数据可供查询。

### 聚合和连接事件

聚合可能由大量事件组成，使得跟踪与其组成相关的所有记录不切实际。连接也是如此，尽管在实践中，连接通常只涉及少量事件。

### 复杂转换

消费者可能有相当复杂的用例，其中输入事件无法轻松映射到输出。

将记录血缘存储在记录中的一种替代方案是改用外部数据库。每个服务必须向端点报告其已消费、处理和发出的事件。当多个服务已消费和使用了数据产品时，此选项确实更容易跟踪记录使用情况，包括使用后不再发出新事件的情况。

然而，它并未解决与连接、聚合和复杂转换相关的问题，在记录级血缘中留下了潜在的缺口。此外，您还需要投资于客户端工具，以自动将每条记录的状态报告给中央服务，包括考虑缩放、宕机和客户端语言支持。

重要的是，您要考虑想要血缘的原因以及它旨在帮助解决的问题。血缘没有放之四海而皆准的解决方案。银行的血缘需求将远大于出售袜子的商店，因此您需要确保治理团队了解其自身组织的真实需求。存在可以概念性地解决本节讨论的问题的血缘解决方案，但它们需要时间和精力来实现——时间和精力可能最好花在别处。

如果您不清楚自己血缘解决方案旨在解决什么问题，就有构建完全无关之物的风险。您必须确定需要哪些审计以及系统面临哪些风险，然后提出详细建议，说明血缘解决方案如何帮助您满足需求。

## 摘要

联邦治理涵盖广阔领域。

数据网格需要一个治理团队来帮助为组织的各种技术、领域、数据模型和用例带来秩序。治理是一种高度社会化的承诺，需要与同事合作，为实施数据网格的障碍提出有效解决方案。作为治理团队的一部分，您将专注于识别共同的标准、框架、语言和工具，以帮助支持数据网格用例。

治理团队与技术领域专家合作，识别自助平台的改进领域。如果您希望组织中的每个人都遵守数据加密政策，那么将其默认集成到数据产品平台中，而不是留给每个团队自己实施，会容易得多。同样，治理团队确保数据网格的使用者的声音被听到，他们的投诉得到处理，并且成功故事被分享和典范化。

联邦治理还涉及跟踪数据使用情况，确保其符合法律要求和良好的信息安全实践。您需要强大的访问控制，以确定哪些系统和人员可以访问哪些数据，但您需要在确保团队在需要时能够访问大部分数据之间取得平衡。数据可能还需要加密（部分或全部），并且可能还需要无限期归档，这再次取决于您的数据处理要求。

最后，治理还涉及为自助平台的实施提供方向。治理团队及其技术专家应将自助平台功能编码化和简化，使用户容易做*正确的事*，难以做*错误的事*。我们将在下一章中更详细地探讨这一点。

## 自助数据平台

自助数据平台使所有网格用户能够轻松发现、使用、发布、管理和保护数据及数据产品。我们已经介绍了构成该平台的一些组件：用于提供事件流的事件代理、用于跟踪基本元数据的元数据存储以及用于管理数据产品访问的访问控制。在本章中，我们将从极简主义到理想状态，介绍自助平台的功能。

还有几个重要的总体问题有待解决：潜在消费者如何发现可用的数据产品？发现后，如何将它们插入现有的应用程序和分析中？如何在数据产品之上构建新应用程序？同样，数据产品发布者的工作流程是什么样的？他们如何管理数据产品并与客户实际通信？自助平台必须为每个这些问题提供简化的解决方案。

自助数据平台部分由组织中已使用的组件组成，部分由需要构建或购买的组件组成。例如，您可能已经拥有一个元数据目录，用于跟踪重要数据集，也可以用于跟踪数据产品元数据。您可能正在使用 Docker 镜像部署应用程序，在 Kubernetes 上运行它们，并使用基于云的监控服务进行监控。但是，您可能缺乏流处理框架、连接器系统和工作流程标准化来启动和运行数据网格。您拥有什么和缺少什么将因组织而异，因此最好关注核心需求以确定着手处理什么。

从本质上讲，数据网格自助平台只是将组织使用的各个组件和子平台粘合在一起的胶水代码。它简化了团队、人员和服务用于使数据网格成为现实的流程。虽然我意识到此描述可能有些模糊，但现实是，每个组织的数据网格都受到现有系统、流程、治理、人员、团队和技术的强烈影响。您的自助平台将独特于您的组织，但将共享本章将介绍的一些共同主题：身份、发现、身份验证、授权、管理、通信和计算。

在本章中，我们将介绍数据网格自助平台应具备的所有重要功能——并且我们将非常务实地进行。构建数据网格最重要的是能够获得短期收益来测试、尝试并重复什么有效、什么无效。为此，我们将数据网格的方法划分为三级成熟度模型，专注于迭代构建和改进自助功能，同时仍能产生实际业务价值。

### 自助平台成熟度模型

自助平台有三个主要成熟度级别。

我的一位同事经常将构建自助平台称为“边飞边造飞机”，并且充分理由：与软件领域的大多数事物一样，我们希望将其作为最小项目启动并运行，以便开始从中获取价值：

- 级别 1：最小可行平台（MVP）
  定义了构建一个勉强可用平台所需的最小投资。此模型将帮助您从可用的数据产品中立即获取价值，同时提供获取反馈和规划迭代改进的机会。

- 级别 2：扩展平台（EP）
  定义了一个更强大且具备生产能力的自助平台，修复了 MVP 的许多缺陷。数据网格用户操作更加简化并集成到平台中，以至于手动出错的空间大大减少。

- 级别 3：成熟平台（MP）
  定义了完全开发并集成的平台。用户可以轻松发现、发布、管理、演进和删除数据产品。数据产品可以轻松为运营和分析应用程序提供动力。

这些成熟度级别并非金科玉律，您不需要在一个级别完成所有事情后再进入下一个级别。您自己的平台的构建和演化将类似于本章概述的内容，但将根据您的起始位置、业务需求和独特的治理要求而有所不同。
