
// int ChangeOrientation(int angle)
// changes the robot's orientation by some angle
// angle = 0 to 360 degrees
// returns success or an error code
// see enums for return values

enum return_code { Success, Illegal_angle, Rotation_Failure };
enum priority { Emergency, Alert, Critical, Error, Warning, Notice, Informational, Debug };

int ChangeOrientation( int angle )
{
    int rc;
    double wheelAmount;

    // debug log rotate() entry
#ifdef DEBUG
log(Debug, get_system_time(), id->sin_addr, "enter ChangeOrientation(), turn angle = %d", angle);
#endif /* DEBUG */

    // check that angle is legal, must be between 0 and 360
    // if the angle is 0 or 360, then do nothing
    if (angle > 0 && angle < 360) {
        // calculate how much to turn the wheels
        // if left turn (i.e. angle is > 180) then calculate negative turn value
        if ( angle <= 180)
            wheelAmount = (angle / 360) * ((trackWidth * PI) / wheelCircumference);
        else {
            angle -= 180;
            wheelAmount = (angle / 360) * ((trackWidth * PI) / wheelCircumference);
            wheelAmount *= -1;
        }

        // PointTurn() does a point turn where
        // the left wheel turns forward and the right wheel turns in reverse by wheelAmount
        rc = PointTurn(wheelAmount);

        // handle failure of PointTurn()
        if (rc > 0) {
            log(Error, get_system_time(), myIpAddr, "PointTurn() failed with error %d", rc);
            return Rotation_Failure;
        }
    } else if (angle < 0 || angle > 360) {      // if angle is illegal, log it and return a failure
        log(Error, get_system_time(), id->sin_addr, "illegal angle specified %d", angle);
        return Illegal_angle;
    }

#ifdef DEBUG
log(Debug, get_system_time(), id->sin_addr, "exiting rotate() successfully");
#endif /* DEBUG */
    return Success;
}

## 23 应用软件质量程序

一旦所有技术都得到理解，它们就会被整合到一个流程中，使软件组织能够生产高质量的软件。组织应采用两种通用类型的流程。第一种是软件开发流程。第二种是组织流程改进流程。软件开发流程是用于以足够质量交付特定软件项目的指标和技术集合。组织流程改进流程使团队能够从一次发布到下一次发布持续改进软件质量。

项目期间流程的概述包含七个要素：

- 1. 开发需求，包括质量目标。
- 2. 估算工作量。
- 3. 创建缺陷运行图，显示软件相对于质量目标的状况。
- 4. 使用失效模式和影响分析（FMEAs）、评审、检查和防御性编程技术来避免缺陷注入。
- 5. 采用各种测试技术来发现缺陷。
- 6. 测量项目期间发现的缺陷并保持缺陷运行图最新。
- 7. 使用缺陷运行图确定何时达到软件质量目标。

上面描述的通用流程可用于瀑布和敏捷软件生命周期。在瀑布生命周期中，这些活动相当清晰地映射到项目的各个阶段。在敏捷流程中，每个活动都可以在冲刺期间使用。然而，在敏捷中，其中一些活动可能在冲刺之间用于回顾，或应用于整个史诗。例如，每个冲刺都会有估算、需求、评审、代码检查和测试。每个冲刺都可以有一个缺陷运行图来跟踪该冲刺的质量。然而，缺陷运行图也可以应用于史诗而不是冲刺。如果每个冲刺都会发布给客户，则更合适为每个冲刺设置缺陷运行图。另一方面，如果史诗代表实际的客户发布，则缺陷运行图可能更适合应用于史诗。同样，流程改进方法，如根本原因分析（RCA）和 FMEAs，可能适合在冲刺之间进行的回顾。然而，这些机制通常需要几天才能很好地执行，因此完全可以将其应用于史诗，并在冲刺流程之外作为整体流程改进流程的一部分执行。敏捷中流程改进机制的另一种选择是创建涵盖它们的用户故事，并在各个冲刺期间实际执行 RCA 和 FMEAs 等任务作为交付成果。

长期质量改进流程通常执行以下操作：

- 1. 主要使用逃逸缺陷率设定软件质量目标。
- 2. 测量每次发布的逃逸缺陷率。
- 3. 在发布之间（或作为发布期间的正交活动），使用 RCA 和 FMEAs 等分析技术来识别技术、培训和流程方面的薄弱环节。
- 4. 解决上一步中确定的弱点。
- 5. 重复此程序。

### 23.1 使用缺陷模型创建缺陷运行图

从最简单的缺陷模型开始，其中仅估计注入的缺陷总数。要创建此简单模型，请通过将缺陷密度估计值乘以代码行数（LOC）大小估计值来计算项目中预计注入的缺陷总数。

对于此计算，最好使用开发组历史上测量的缺陷密度数据。如果您没有来自组织的历史数据，您可以使用第 9.3 节关于缺陷密度中讨论的行业数据；即低级语言每千行代码 10 个缺陷，高级语言每千行代码 20 个缺陷。

缺陷不会在项目过程中以稳定速率注入。缺陷也不会以稳定速率被发现。缺陷会在项目的每个活动中注入，即需求开发、设计、编码，甚至在修复其他缺陷时。缺陷会在评审、代码检查和各种测试活动中被发现。通常，大多数缺陷会在编码期间注入，大多数缺陷会在测试期间被发现并修复。更复杂的缺陷模型可能会估计项目过程中随时间推移注入、发现和修复的缺陷数量，甚至可能考虑到在任何给定时间开发、测试和修复代码的工程师数量。对于刚开始使用缺陷运行图的组织，足以仅创建一个简单的燃尽图，该图绘制预计的缺陷总数以及找到它们的进展，如第 9.5 节关于缺陷运行图中所示。
