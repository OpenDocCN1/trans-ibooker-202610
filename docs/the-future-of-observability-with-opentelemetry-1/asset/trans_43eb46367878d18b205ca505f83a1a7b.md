## 事件：一切的基础

OpenTelemetry 中最基本的对象是事件。事件只是一个时间戳和一组属性。使用一组属性而不是简单的消息/日志可以让分析工具正确地索引事件并使其可搜索。

某些属性将是事件独有的。时间戳、消息和异常详情都是特定于某个事件的属性的例子。

然而，大多数属性并不是某个单独事件独有的。相反，它们是共同属于一组事件的。例如，http.target 属性与作为 HTTP 请求一部分记录的每个事件都相关。一次又一次地在每个事件上记录这些属性效率低下。相反，我们将这些属性提取到围绕事件的信封中，在那里它们只需写入一次。我们称这些信封为上下文。

上下文有两种类型：静态和动态（见图 2-1）。静态上下文定义了事件发生的物理位置。在 OpenTelemetry 中，这些静态属性称为资源。一旦程序启动，这些资源属性的值通常不会改变。

![](img/4e6e799bc9cb3e86f203595f40542979_20_0.png)

图 2-1. 虽然事件有一些事件特定的属性，但大多数属性属于事件发生的上下文之一。

动态上下文定义了事件参与的活动操作。这种操作级上下文称为 span。每次操作执行时，这些属性的值都会改变。

并非所有事件都有这两种类型的上下文。仅具有资源的自由漂浮事件，例如程序启动时发出的事件，称为日志。作为分布式事务一部分发生的事件称为 span 事件。

## 资源：观察服务和机器

资源（静态上下文）描述了程序所消耗的物理和虚拟基础设施。服务、容器、部署和区域都是资源。图 2-2 显示了典型的购物车结账交易中涉及的资源。

![](img/4e6e799bc9cb3e86f203595f40542979_20_1.png)

图 2-2. 交易，被视为一组资源。

运行系统中大多数问题都源于资源竞争，许多并发交易试图同时使用相同的资源。通过将事件置于它们所使用的资源的上下文中，可以自动检测许多类型的资源竞争。

与事件一样，资源也可以定义为一组属性。表 2-2 显示了服务资源的示例。

## 表 2-2. 服务资源的示例

| Attribute | Type | Description | Example |
|---|---|---|---|
| service.name | string | Logical name of the service | shopping cart |
| service.instance.id | string | The string ID of the service instance | 627cc493-f310-47de-96bd-71410b7dec09 |
| service.version | string | The version string of the service API or implementation | 2.0.0 |

除了识别机器所需的基本信息外，配置设置也可以作为资源记录。必须访问正在运行的机器来了解其配置是一项可怕的负担。相反，配置文件中发现的任何重要信息也应表示为资源。

## Spans：观察交易

Spans（动态上下文）描述计算机操作。一个 span 有操作名称、开始时间、持续时间和一组属性。

标准操作使用语义约定描述，例如上面描述的 HTTP 规范。但也有应用程序特定的属性，例如 ProjectID 和 AccountID，可以由应用程序开发人员添加。

Spans 也是我们描述因果关系的方式。为了正确记录整个交易，我们需要知道哪些操作是由哪些其他操作触发的。为此，我们需要在 spans 中添加三个更多属性：TraceID、SpanID 和 ParentID，如表 2-3 所示。

## 表 2-3. spans 的三个附加属性

| Attribute | Type | Description | Example |
|---|---|---|---|
| traceid | 16-byte array | Identifies the entire transaction | 4bf92f3577b34da6a3ce929d0e0e4736 |
| spanid | 8-byte array | Identifies the current operation | 00f067aa0ba902b7 |
| parentid | 8-byte array | Identifies the parent operation | 53ce929d0e0e4736 |

这三个属性是 OpenTelemetry 的基础。通过添加这些属性，我们所有的事件现在都可以组织成一个图，表示它们的因果关系。这个图现在可以以多种方式索引，我们稍后会讲到。

## Tracing：像日志记录，只不过更好

我们现在已经从简单的事件发展到组织成与资源相关联的操作图的事件。这种类型的图称为 trace。图 2-3 显示了 traces 常用的可视化方式，重点是识别操作的延迟。

![](img/4e6e799bc9cb3e86f203595f40542979_22_0.png)

图 2-3. 当日志组织成图时，它们就变成了 traces。

本质上，tracing 只是具有更好索引的日志记录。当你为结构良好的日志添加适当的上下文时，你几乎可以定义 traces。

想想你花费了多少时间和精力通过搜索和过滤来收集那些日志；那是花费在收集数据上的时间，而不是分析数据的时间。而且你需要翻阅的日志越多——机器数量不断增长的堆积物执行着越来越多的并发交易——收集真正相关的那一小部分日志就越困难。

然而，如果你有 TraceID，收集这些日志只是一次查找。按 TraceID 索引允许你的存储工具自动为你完成这项工作；你找到一条日志，你就拥有了交易中的所有日志，而无需额外工作。

既然如此，为什么你会想要没有这些“trace” ID 的“日志”呢？我们已经习惯了传统日志记录强迫我们做的工作来连接点。但这项工作实际上是不必要的；它是我们数据缺乏结构的一个副产品。

因此，分布式追踪不仅仅是测量延迟的工具；它是一种定义上下文和因果关系的数据结构。它是粘合一切的胶水。正如我们将看到的，这种胶水包括最后一个支柱——指标。

## 指标：以聚合方式观察事件

现在我们已经确定了事件是什么，让我们谈谈聚合的事件。在活跃的系统中，相同的事件一次又一次地发生，我们以聚合方式查看其属性以寻找模式。属性的值可能出现得太频繁，或不够频繁，在这种情况下，我们想要计算这些值出现的频率。或者该值可能超过某个阈值，在这种情况下，我们想要衡量该值随时间的变化。或者我们可能想要以直方图的形式查看值的分布。

这些聚合事件称为指标。就像常规事件一样，指标有一组属性和一组语义约定来描述常见概念。表 2-4 显示了系统内存的一些示例属性。

## 表 2-4. 系统内存的属性

| Attribute | Value type | Attribute values |
|---|---|---|
| system.memory.usage | int64 | used, free, cached, etc. |
| system.memory.utilization | double | used, free, cached, etc. |
