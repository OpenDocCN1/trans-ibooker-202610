

## 稳定性与长期支持

OpenTelemetry 的设计允许长期稳定性和创新并行进行。在 OpenTelemetry 中，稳定性保证是按信号逐个提供的。不要查看版本号，请检查你想要使用的信号的稳定性评级。

## 信号生命周期

图 6-1 显示了新信号如何添加到 OpenTelemetry 中。实验性信号仍在开发中。它们可能随时更改——并且破坏兼容性。实验性信号以规范提案的形式开始开发，该提案与一组原型一起开发。一旦实验性信号准备好用于生产使用，就会对其规范进行功能冻结，并在多种语言中创建新信号的 Beta 版本。Beta 版本可能尚未功能完整，并且可能出现破坏性更改，但它们被认为已准备好供早期采用者提供生产反馈。一旦信号被认为准备好宣布为稳定，就会发布候选版本。如果候选版本能够在一段时间内保持稳定且无问题，则该信号的规范和 Beta 版本都将被宣布为稳定。

一旦信号变得稳定，它就受 OpenTelemetry 的长期支持保证的约束。OpenTelemetry 非常重视向后兼容性和无缝升级。有关详细信息，请参阅以下各节。

如果 OpenTelemetry 信号的某个组件需要退役，该组件将被标记为已弃用。已弃用组件不再接收新功能，但仍受 OpenTelemetry 的长期支持保证覆盖。如果可能，该组件将永远不会被移除并将继续运行。如果必须移除组件，将会提前很久宣布移除日期。

实验性功能始终与稳定功能分开打包，并且稳定功能永远不会引用实验性功能。这确保了新开发永远不会影响现有功能的稳定性。只要库仅依赖于稳定功能，它们就永远不会遇到破坏性的 API 更改。

## API 稳定性

预计 OpenTelemetry API 将被数千个库依赖，拥有数百万个调用点。因此，API 的稳定部分必须永远不会破坏向后兼容性。应用程序所有者和库开发人员在升级到新版本的 API 时不应重新为其应用程序进行检测。

如果 OpenTelemetry API 被弃用，尽管可能性不大，已弃用的 API 仍将保持稳定和可用。

## 原生检测即稳定检测

随原生 OpenTelemetry 检测一起发布的 OSS 库应仅使用稳定 API，因为对实验性功能的更改可能会导致依赖冲突。

话虽如此，我们绝对鼓励 Beta 测试。如果库希望提供对实验性 OpenTelemetry 功能的支持，这是一个很好的方式来为项目提供反馈并参与新功能的设计。然而，我们建议将与实验性 OpenTelemetry 功能的集成作为可选插件提供，最终用户必须单独安装以启用。

一旦功能变得稳定，就没有必要将其作为单独的插件保留。事实上，将 OpenTelemetry 原生集成更好，因为用户可能会忘记安装插件。这样，如果应用程序所有者安装了 OpenTelemetry SDK，他们将自动开始从每个库接收数据。如果未安装 SDK，API 调用将是无操作。原生检测是我们希望 OpenTelemetry 简化应用程序所有者可观测性的一种方式——它已存在于每个库中，并且在需要时即可使用。

## SDK 和 Collector 稳定性

SDK 稳定性关注两个方面：插件接口和资源使用。SDK 偶尔会弃用插件接口。为了确保应用程序所有者能够干净地升级，必须在移除已弃用接口之前添加替代接口，并且使用已弃用接口的流行插件必须迁移到新接口。通过以这种方式安全地迁移插件生态系统，我们避免了应用程序所有者想要升级但被不兼容的插件阻止的情况。在弃用和移除插件接口之间必须至少有六个月的时间窗口，并且只有在维护它们会造成性能问题时，才应计划移除已弃用接口。否则，我们将无限期保留已弃用接口。

说到性能，OpenTelemetry SDK 的稳定部分必须避免性能回归，以确保升级 SDK 新版本时不会引发资源争用。显然，在较新版本中启用新增功能可能需要额外的资源。但仅仅升级 SDK 不应导致性能回归。

与 SDK 类似，Collector 寻求避免性能回归并为 Collector 插件生态系统提供渐进式升级路径。

## 升级 OpenTelemetry 客户端

运行 OpenTelemetry 时，预计用户会保持与 SDK 最新版本同步。两个事件可能会迫使用户升级 SDK：库将其检测升级到新版本的 API，或 OpenTelemetry 发布关键安全补丁。

上面列出的稳定性保证确保了该升级路径始终可行。只要应用程序仅依赖于稳定信号，升级就只涉及依赖项的提升。无需重写检测，并且插件也不会突然变得不受支持。

OpenTelemetry 对向后兼容性的承诺的一个很好的例子可以在其对前身 OpenTracing 的支持中找到。OpenTelemetry 跟踪信号与 OpenTracing API 完全兼容，并且 OpenTelemetry 和 OpenTracing API 调用可以混合在同一个应用程序中。OpenTracing 用户可以在无需重写现有检测的情况下升级到 OpenTelemetry。

## 建议的设置和遥测管道

现在我们了解了构成 OpenTelemetry 的各个构建块，我们应该如何将它们组合成一个强大的生产管道？

答案取决于你的起点。OpenTelemetry 是模块化的，设计为可在各种不同的规模下工作。你只需要使用感觉相关的部分。也就是说，我们为你创建了一个建议的路线图。

## 安装 OpenTelemetry 客户端

可以在不部署 Collector 的情况下单独使用 OpenTelemetry 客户端。这种基本设置通常是绿地部署的足够起点，既用于测试，也用于初始生产。OpenTelemetry SDK 可以配置为直接将遥测传输到大多数可观测性服务。

## 选择导出器

默认情况下，OpenTelemetry 使用 OTLP 导出数据。SDK 随附了几种常见格式的导出器：Zipkin、Prometheus、StatsD 等。如果你使用的可观测性后端不支持 OTLP 原生支持，其中一种其他格式很可能得到支持。安装正确的导出器并直接将数据发送到你的后端系统。

## 安装库检测

除了 SDK 之外，还必须为应用程序中包含的所有 HTTP 客户端、Web 框架、数据库和消息队列安装 OpenTelemetry 检测。如果缺少其中一个库的检测，上下文传播将中断，导致跟踪不完整和数据混乱。

在某些语言中，例如 Java，检测可以自动安装，这使得操作更简单。确保学习 OpenTelemetry 如何在你使用的编程语言中管理检测，并仔细检查检测是否已正确安装在你的应用程序中。

## 选择传播器

同样重要的是要仔细检查你的系统需要哪些传播器。默认情况下，OpenTelemetry 使用 W3C trace-context 和 baggage 传播器。但是，如果你的应用程序需要与使用不同跟踪传播器的服务通信，例如 Zipkin 的 B3 或 AWS 的 X-Amzn，则更改 OTEL_PROPAGATORS 配置以包含此额外传播器。

如果 OpenTelemetry 最终将取代这些其他跟踪系统，我建议同时运行 trace-context 和额外的跟踪传播器。这将允许你在逐步替换部署中的旧系统时无缝过渡到 W3C 标准。

## 部署本地 Collector

虽然某些系统只需客户端即可应付，但通过在运行应用程序的机器上添加本地 Collector，可以改善你的运营体验。

运行本地 Collector 有许多好处，如图 7-1 所示。Collector 可以生成机器指标（CPU、RAM 等），这是遥测的关键部分。Collector 还可以执行任何所需的数据处理任务，例如从跟踪和日志数据中 scrub PII。
