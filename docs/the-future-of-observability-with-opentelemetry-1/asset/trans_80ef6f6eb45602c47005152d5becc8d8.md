## 问题分解

我们可以通过设计一个可观测性系统来明确解决所有相关人员的需求，从而解决上面列出所有问题。在本章剩余部分，我们将把现代可观测性系统的设计分解为基本需求。这些需求将为第 5 章中描述的 OpenTelemetry 架构提供动机。

## 需求：分离 Instrumentation、遥测和分析

归根结底，计算机系统实际上是人类系统。诸如可观测性之类的横切关注点会与几乎每个软件组件交互。同时，传输和处理遥测可能是一项高吞吐量的活动，以至于大规模的可观测性系统会产生自身的操作问题。这意味着许多不同的人，以不同的身份，需要与可观测性系统的不同方面进行交互。为了很好地服务于他们，该系统必须确保所有相关人员都有足够的自主权来快速、独立地执行任务。提供自主权是有效可观测性系统的一项基本设计需求。

让我们先确定与运行中的软件系统相关的每个角色的职责：库作者、应用所有者、运维人员和响应者。

库作者传达他们的软件在做什么。

对于封装关键功能（如网络和请求管理）的软件库，库作者还必须管理追踪系统的方面：注入、提取和上下文传播。

应用所有者组合软件并管理依赖项。

应用所有者选择构成其应用的组件，并确保它们编译成一个连贯、功能性的系统。应用所有者还编写应用级 instrumentation，该 instrumentation 必须与库作者提供的 instrumentation 和上下文传播干净地交互。

运维人员管理遥测的生产和传输。

运维人员管理从应用到响应者的可观测性数据的传输。他们必须能够选择数据的格式以及发送到何处。在数据传输过程中，他们必须操作传输系统：管理缓冲、处理和路由数据所需的所有资源。

响应者消费遥测并生成有用的洞察。

为此，响应者必须理解数据固有的结构和含义。结构和含义在第 3 章中有详细描述。响应者还需要在其工具箱中添加新的和改进的分析工具，当它们可用时。

这些角色代表不同的决策点：

- 库作者只能通过发布新版本代码来做出更改。
- 应用所有者只能通过部署可执行文件的新版本来做出更改。
- 运维人员只能通过管理可执行文件的拓扑和配置来做出更改。
- 响应者只能根据他们接收到的数据做出更改。

传统的三大支柱方法混淆了所有这些角色。垂直集成的副作用是，几乎任何数据更改都需要代码更改。几乎任何非平凡的可观测性系统更改都需要应用所有者进行代码更改。要求其他人做出你关心的更改会制造变更障碍，并可能导致压力、冲突和不作为。

很明显，一个设计良好的可观测性系统应专注于让每个人拥有尽可能多的自主权和直接控制权，并避免将开发者变成意外的守门人。

## 需求：零依赖

应用由依赖项、Web 框架、数据库客户端，加上其依赖项的依赖项、OpenTelemetry 或其他 instrumentation 库，加上其依赖项的依赖项的依赖项组成，无论这些 instrumentation 库依赖于什么。这些被称为传递依赖。

如果任意两个依赖项之间存在冲突，应用就无法运行。例如，两个库可能各自需要不同且不兼容的低级网络库版本，例如 gRPC。这可能导致许多糟糕的情况。例如，库的新版本可能包含所需的安全补丁，但也包含升级的依赖项，从而产生依赖冲突。糟糕！

此类传递依赖冲突为应用所有者造成了巨大的头痛，因为冲突无法独立解决。相反，应用所有者必须联系库作者并请求他们提供解决方案，这最终会花费时间，假设库作者甚至会回复请求。

为了使现代可观测性发挥作用，库必须能够嵌入 instrumentation，而不必担心它会在库被组合到应用中时导致问题。因此，可观测性系统必须提供不包含可能无意触发传递依赖冲突的依赖项的 instrumentation。

## 需求：严格的向后兼容性和长期支持

当 instrumentation API 破坏向后兼容性时，坏事就会发生。一个 instrumentation 良好的应用可能最终拥有数千个 instrumentation 调用点。由于 API 更改而必须更新数千个调用点是一项大量工作。

这造成了一种特别糟糕的依赖冲突形式，即一个库中的 instrumentation 不再与另一个库中的 instrumentation 兼容。

因此，instrumentation API 必须在非常长的时间尺度上严格向后兼容。理想情况下，一旦 instrumentation API 变得稳定，它永远不会破坏向后兼容性——永远——并且新的、实验性的 API 功能必须以这样的方式开发，即它们存在不会在包含稳定 instrumentation 的库之间产生冲突。

## 关注点分离是良好设计的基础

在下一章，我们将深入 OpenTelemetry 的架构，看看它如何满足上面列出的需求。但在我们这样做之前，我想强调一个重要观点。

如果你分析这些需求，你可能会注意到一些奇怪之处：它们几乎没有什么是特定于可观测性的。相反，重点是最小化依赖、维护向后兼容性，并确保不同用户可以在没有不必要干扰的情况下执行其角色。

每个需求都指向关注点分离作为关键设计特性。但这些特性并不独特于 OpenTelemetry。任何寻求广泛采用的软件库都应很好地包含它们。在这种意义上，OpenTelemetry 的设计也可以作为设计开源软件的一般指南。下次你启动一个新的 OSS 项目时，提前考虑这些需求并据此设计你的库——你的用户会感谢你的！
