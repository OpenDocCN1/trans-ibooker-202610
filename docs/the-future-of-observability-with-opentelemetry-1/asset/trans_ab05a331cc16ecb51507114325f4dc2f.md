

## OpenTelemetry：架构概述

第 2 章描述了实现自动化分析所需的数据模型，第 4 章描述了支持原生 OSS 仪器化并赋予各角色自主权（应用所有者、运维人员和响应人员）的额外需求。这是我们对现代可观测性的概念模型。

在本报告的剩余部分，我们将描述这种新模型的一种真实实现 OpenTelemetry。本章描述了构成 OpenTelemetry遥测管道的所有单个组件。后续章节将描述稳定性保证、建议的设置以及 OpenTelemetry 在现实世界中的采用部署策略。有关该项目的更多详细信息可在附录中找到。

## Signals

OpenTelemetry 规范分为不同类型的遥测，我们称之为信号。主要信号是追踪。日志和指标是其他示例。信号是 OpenTelemetry 中最基本的设计单元。

每个额外信号首先独立开发，然后与追踪和其他相关信号集成。这种分离允许新的实验性信号在不影响已稳定信号的兼容性保证的情况下开发。

OpenTelemetry 是一个横切关注点，遵循事务的执行路径，穿过每个库和服务。为实现此目的，所有信号都建立在更低层的上下文传播系统之上，该系统为信号提供了一个位置，用于存储它们需要与当前执行的代码关联的任何事务级数据。由于上下文传播系统与追踪清晰分离，其他横切关注点也可以使用它。图 5-1 说明了这种分层架构。

## Context

上下文对象是一个与执行上下文关联的键值存储，例如线程或协程。其实现方式取决于语言，但 OpenTelemetry 在每种语言中都提供上下文对象。

信号将其数据存储在上下文对象中。由于 OpenTelemetry API 调用始终可以访问整个上下文对象，因此信号可以在后台集成并共享数据，而无需 API 更改。例如，如果同时启用了追踪和指标信号，记录指标可能会自动创建追踪示例。日志也是如此：日志将自动绑定到当前追踪（如果存在）。

## Propagators

为了使分布式追踪工作，追踪上下文必须由参与事务的每个服务共享。传播器通过序列化和反序列化上下文对象来实现这一点，使信号能够跟随其事务跨越网络请求。

## Tracing

OpenTelemetry 追踪系统基于 OpenTracing 和 OpenCensus。这两个系统以及流行的 Zipkin 和 Jaeger 项目都基于 Google 开发的 Dapper 追踪系统。OpenTelemetry 寻求与所有这些基于 Dapper 的系统兼容。

OpenTelemetry 追踪包括一个称为链接的概念，允许将单独的追踪组合成更大的图。这用于将事务连接到后台处理，并观察 Kafka 和 AMQP 等大型异步系统。

## Metrics

指标是一个很大的领域，包含各种方法和实现。OpenTelemetry 指标信号旨在与 Prometheus 和 StatsD 完全兼容。

指标包括追踪示例，自动将指标与生成它们的追踪采样关联起来。手动关联指标和追踪通常是一项繁琐且容易出错的任务，自动执行此任务将为运维人员节省大量时间。

## Logs

OpenTelemetry 将高度结构化的日志 API 与高速日志处理系统结合。现有日志 API 可以连接到 OpenTelemetry，避免重新为应用程序进行仪器化。

只要存在，日志就会自动附加到当前追踪。这使得事务日志易于查找，并允许自动化分析在同一追踪中的日志之间找到准确的相关性。

## Baggage

OpenTelemetry baggage 是一个简单但多功能的键值系统。一旦数据作为 baggage 添加，它就可供所有下游服务访问。这允许有用的信息，例如账户和项目 ID，在事务的后面阶段可用，而无需从数据库重新获取。例如，使用项目 ID 作为索引的前端服务可以将它作为 baggage 添加，允许后端服务也按项目 ID 索引其 spans 和指标。

一种很好的思考 baggage 的方式是将其视为一种*分布式上下文*。直接放入上下文对象中的项目仅在当前服务内可访问。 much like trace context, items added as baggage are injected into network requests as headers, allowing them to be extracted by the downstream service.

与上下文对象一样，baggage 本身并不是可观测性工具。它更像是一个通用数据存储和传输系统。除了可观测性之外，其他横切工具——例如功能标记、A/B 测试和身份验证——也可以使用 baggage 存储跟踪当前事务所需的任何状态。

然而，baggage 也有成本。因为每个添加的项目都必须编码为头部，所以你添加的每个项目都会增加事务中每个后续网络请求的大小。这就是我们称之为 baggage 的原因。我建议谨慎使用 baggage，作为横切关注点的一部分。baggage 不应被用作“方便”的替代方案，用于通过明确定义的服务 API 将参数显式发送到下游应用程序。

在许多语言中，OpenTelemetry 提供了安装程序，有助于自动化 OpenTelemetry 客户端的安装和设置。然而，可用的自动化程度取决于语言。在 Java 中，OpenTelemetry 提供了一个 Java 代理，通过动态注入所有必要组件来完全自动化设置。在 Go 中，OpenTelemetry 包必须通过编写代码像任何其他 Go 包一样安装和初始化。Python、Ruby 和 NodeJS 介于两者之间，提供不同程度的自动化。

学习 OpenTelemetry 时，了解你所使用语言中的设置方式非常重要。特别是，请确保学习仪器化应如何安装，因为这在不同语言之间差异很大。

## Client Architecture: The Instrumentation API

OpenTelemetry API 指用于编写仪器化的组件集。API 设计为可直接嵌入到 OSS 库以及应用程序中。这是共享库和应用程序逻辑应直接依赖的 OpenTelemetry 的唯一部分。

## Providers

API 完全独立于任何实现。当应用程序启动时，可以通过为每个信号注册提供程序来加载实现。提供程序成为所有 API 调用的接收者。

当未加载提供程序时，API 默认使用 no-op 提供程序。这使得 OpenTelemetry 仪器化可以安全地包含在共享库中。如果应用程序不使用 OpenTelemetry，API 调用 simply become no-ops and do not incur any overhead.

对于生产使用，我们建议使用官方 OpenTelemetry 提供程序，我们将其称为 OpenTelemetry SDK。

## Why Have Multiple Implementations?

API 与实现的分离具有诸多好处。但如果用户被迫始终安装官方 OpenTelemetry SDK，这会有任何实际意义吗？是否真的有理由安装另一个实现？SDK 已经非常可扩展。

我们认为有。虽然我们希望 OpenTelemetry 仪器化是通用的，但我们不相信可以构建一个单一实现来满足所有用例。尽管我们认为 OpenTelemetry SDK 很好，但始终应有使用其他实现的选项。实现上的灵活性是提供通用仪器化 API 的关键特性。

一方面，这种分离确保 OpenTelemetry 永不会产生无法克服的依赖冲突。始终可以选择加载包含不同依赖链的实现。
