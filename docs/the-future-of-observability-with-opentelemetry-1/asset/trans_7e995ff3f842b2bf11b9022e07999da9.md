## eBPF

*Extended Berkeley Packet Filter (eBPF)* 是一种在 Windows、Linux 和其他类 Unix 操作系统上提供低级网络访问的机制。利用 eBPF 将为 OpenTelemetry 提供一种极其高效的网络监控形式，而无需任何开发人员埋点。

在 2021 年，Flowmill 项目被捐赠给了 OpenTelemetry。Flowmill 是一款基于 eBPF 的可观测性解决方案，专门用于观察分布式系统。Flowmill 的开发者以及 Pixie 项目的开发者正在努力为 OpenTelemetry Collector 增加 eBPF 支持。Pixie 是一款专门为 Kubernetes 设计的基于 eBPF 的可观测性工具，是 OpenTelemetry 在 CNCF 旗下的一姐妹项目。我们共同也在研究如何进一步将低级（第 2 层）eBPF 数据与高级（第 7 层）分布式追踪数据相关联，这将是行业内的首次。

## RUM

*Real user monitoring (RUM)* 是一种可观测性工具，用于描述用户如何在长时间的用户会话中与移动、Web 和桌面客户端进行交互。RUM 与分布式追踪的不同之处在于，图形用户界面（GUI）往往是基于反应器的系统，其根本架构与数据库和 Web 服务器等基于事务的系统存在根本差异。简单来说：你不能仅仅把一个用户会话建模为一个 Trace 就完事了。

客户端埋点 SIG 目前正在开发一种新的 RUM 设计，该设计将扩展并与 OpenTelemetry 现有的分布式追踪、指标和日志信号完全集成。

## OpenTelemetry Control Plane

目前，OpenTelemetry Collector 和 SDK 被作为独立单元进行管理，更改其配置时必须重启。控制平面可报告这些组件的当前状态并允许实时配置更改，目前正由 Agent Management SIG 开发。它将允许操作员或自动化服务动态控制整个遥测管道的<|message|> 处理。

动态配置将允许对采样、日志级别和其他形式的资源管理进行细粒度、响应式的控制，从而降低成本。最终，该控制平面可能能够实现更高级的尾部采样形式，采样技术需要在整个部署中进行协调。

## Columnar-Encoded OTLP

当前的 OpenTelemetry 协议是对 OpenTelemetry 数据模型的一种有效但直接的编码。Spans、metrics 和 logs 被编码为...spans、metrics 和 logs。这可以被视为一种基于行的模型，其中每个 span、metric 或 log 都被编码为元素列表中的一个离散元素。基于列的模型则会将每个元素编码到一个单一表中，所有元素共享时间戳和属性等重叠概念的相同列。

这种列式表示预计会优化数据批的创建、大小和处理。这种方法的优势主要有：

- 更好的数据压缩率（相似数据的分组）
- 更快的数据处理（更好的数据局部性意味着更好的 CPU 缓存行利用）
- 更快的序列化和反序列化（需要处理的对象更少）
- 更快的批创建（更少的内存分配）
- 更好的 I/O 效率（需要传输的数据更少）

这种方法的优势会随着批大小的增加而成比例增长。使用现有的“行式”表示非常适合小批场景。因此，列式编码将扩展当前协议。当前提出的实现基于 Apache Arrow，一种成熟的列式内存格式。

此优化旨在让高容量数据源，例如内容分发网络和大型多租户系统，能够像常规服务一样参与可观测性。列式编码还将降低跨网络边界导出遥测的成本。
