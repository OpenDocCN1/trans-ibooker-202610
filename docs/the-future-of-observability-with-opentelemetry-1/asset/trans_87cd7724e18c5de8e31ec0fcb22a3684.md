

为了尽可能高效，扩展性和性能始终是权衡取舍。例如，通过外部函数接口为 OpenTelemetry C++ SDK 创建绑定，对于 Ruby、Python 和 Node.js 等动态脚本语言来说，可能是一种非常高效的选择。

还有一些流式架构显示出有希望的性能提升。对于这些经过优化的解决方案，编写插件和生命周期钩子的能力将受到严重限制；支持这些类型功能的所需数据结构在这些优化解决方案中将不存在。最终，没有“完美的实现”；只有权衡。

API/SDK 分离是一个关键的设计选择，项目对此大量使用。例如，除了 SDK 之外，每个语言都有一个 no-op 实现，默认安装。还有一个 Fake/Mock 实现可供使用，我们将其用于测试。并且还有更多创造性实现的潜力——例如，为分布式系统构建开发者工具，如跨网络边界工作的实时调试器。

## 客户端架构：SDK

OpenTelemetry 项目为 OpenTelemetry API 提供了官方实现，我们称之为 OpenTelemetry SDK。SDK 通过提供插件框架来实现 OpenTelemetry API。下面的描述了追踪 SDK；指标和日志采用了类似的架构。

基本数据结构是一个无锁的 SpanData 对象。SpanData 对象在用户开始一个 span 时创建，并且会在用户添加属性和事件时自动构建。一旦 span 结束，SpanData 对象将不再更新，可以安全地传递给后台线程。

SDK 插件架构组织为一条管道。对于追踪而言，该管道由一系列 SpanProcessors 组成。每个处理器对 SpanData 对象有两次同步访问：一次在 span 开始时，再一次在 span 结束之后。采样器、日志附加器和数据清理器都是 SpanProcessors 的示例。链中最后一个处理器通常是 BatchSpanProcessor，它管理已完成 spans 的缓冲区。导出器可以连接到
BatchSpanProcessor，将一批 spans 通过网络刷新到遥测管道中的下一个服务，通常发送到 Collector 或直接发送到追踪后端。一旦 spans 被导出，管道就完成了，SpanData 对象将被释放。

## Samplers

OpenTelemetry 提供了几种常见的采样算法，包括预先采样和基于优先级的采样。采样可以帮助控制成本，但它是有代价的：你将丢失数据。在启用任何采样算法之前，重要的是要检查你计划使用的分析工具支持哪些类型的采样。意外的采样可能会破坏某些形式的分析。一些工具需要自己的采样插件。例如，AWS X-Ray 使用自己的采样算法，可作为 AWS 特定的采样插件使用。

## Exporters

OpenTelemetry 提供了 OTLP（OpenTelemetry Protocol）、Jaeger、Zipkin、Prometheus 和 StatsD 的导出器。第三方维护的额外导出器可以在每个语言的 OpenTelemetry-Contrib 仓库（repos）中找到。使用 OpenTelemetry 注册表来查找当前可用的插件。

## 客户端架构：库 Instrumentation

要正常工作，OpenTelemetry 需要端到端的 instrumentation。这不是可选的：如果关键库不包含 instrumentation，上下文传播将被破坏。

一般来说，必须进行 instrumentation 的库包括 HTTP 客户端、HTTP 服务器、应用程序框架、消息/队列系统和数据库客户端。这些库通常在上下文传播中发挥作用。

- HTTP 客户端必须创建客户端 span 来记录请求。客户端还必须使用传播器将当前上下文作为一组 HTTP 头注入到请求中。
- HTTP 服务器（应用程序框架）必须使用传播器从 HTTP 头中提取上下文。提取的上下文用于创建 *server span*，它被设置为当前活动 span，包装所有应用程序代码。
- 同样，消息/排队系统中的发送方必须使用传播器将上下文注入到消息中，以便通过在接收方提取上下文来继续追踪。
- 数据库客户端必须创建 *database span* 来记录数据库事务。一旦数据库服务器也使用 OpenTelemetry 进行 instrumentation，数据库客户端还必须将上下文注入到数据库请求中。

这一要求是我们希望看到 OSS 库随原生 instrumentation 一起发布的主要原因之一。在此期间，instrumentation 插件作为 *contrib packages* 提供，由 OpenTelemetry 项目或第三方维护。

## Collector

除了上面描述的客户端之外，OpenTelemetry 还提供了一个独立的服务，称为 Collector。Collector 是一个灵活、可配置的遥测处理系统。基本架构如图 5-3 所示。

Collector 管道可以构建以提供多种服务：

- 配置，例如路由和数据导出格式。几乎所有可用于 OpenTelemetry 客户端的配置选项都可以替代地在 Collector 中管理。
- 数据处理，例如 scrubbing、格式转换，以及 tee 到多个目的地。
- 缓冲以帮助管理背压和网络不稳定。
- 主机级环境的资源检测。主机、Kubernetes 和云提供商的详细信息可以被发现并附加到 collector 接收到的所有数据。
- 主机指标的收集，例如 RAM、CPU 和存储容量。

操作员可以使用 collector 来管理与可观测性系统相关的所有部署细节，而无需与应用程序本身交互。由于大多数配置选项是部署特定的——由操作员管理，而不是应用程序开发者——将遥测配置从应用程序移动到 Collector 可以清晰地分离关注点。

如果所有路由和数据处理任务都移至 Collector，OpenTelemetry SDK 可以使用更简单的配置运行。默认情况下，SDK 会将未处理的 OTLP 数据发送到预定的本地端口，在那里可以由本地 Collector 接收。

## Collector 架构：接收器

Collector 可以配置为从各种来源以各种格式接收遥测。目前 Collector 支持超过四十种不同类型的接收器！一旦接收，所有这些数据都将被转换为 OTLP。OpenTelemetry 支持基于推送和基于拉取的接收器。

## Collector 架构：处理器

一旦接收器将遥测转换为 OTLP，就会提供多种处理器。处理器可以配置为执行各种任务：

- 数据 scrubbing 以删除敏感数据，例如 PII（个人身份信息）。
- 数据规范化，例如将数据源的旧版本转换为与后端当前使用的仪表板和查询匹配的版本。
- 根据某些属性将数据路由到特定的后端。例如，将与欧盟用户相关的数据存储在托管在欧盟内的存储系统上。
- 基于尾部的采样，以帮助确保错误和异常值更有可能被捕获，同时限制嘈杂且不感兴趣的信息的速率。

## Collector 架构：导出器

一旦遥测被处理，它就可以导出到各种后端。未来，我们预计会有越来越多的后端原生支持 OTLP。在此期间，OTLP 可以转换为当前流行系统支持的许多格式。请查看 OpenTelemetry 厂商页面以查找当前支持 OpenTelemetry 的商业提供商列表。

除了将遥测转换为单一格式外，还可以安装多个导出器。遥测可以根据类型拆分并发送到单独的后端——例如，将追踪数据发送到 Jaeger，将指标数据发送到 Prometheus。

重复的遥测也可以同时发送到多个后端。这允许操作员在不丢失服务的情况下无缝地从一个后端切换到另一个后端。它还允许专业分析工具与通用可观测性平台并行接收数据。

## Collector 架构：管道

Collector 允许接收器、处理器和导出器组合成复杂的管道，可并发运行。管道通过 YAML 配置文件设计和管理。

这种配置语言非常强大。通过在每台机器上部署本地 Collector 并将它们连接到配置为执行专门处理任务的多个层级的 Collector 部署，Collector 可用于开发大规模、健壮的遥测系统。
