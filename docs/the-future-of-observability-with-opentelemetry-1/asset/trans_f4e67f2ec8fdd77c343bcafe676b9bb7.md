

## 我们在现实世界中如何实际观察系统

作为复习，让我们回顾一下操作员在调查问题时实际经历的、未经修饰的过程。

调查涉及两个步骤：注意到发生了某些事情，然后确定其发生的原因。

在执行这些任务时，我们使用可观测性工具。但重要的是，我们不会孤立地使用每种工具。我们会将它们一起使用。而在整个过程中，这些工具的孤岛化给操作员带来了巨大的认知负担。

通常，调查始于有人注意到某个重要指标变得“扭曲”。在这种情况下，“扭曲”是一个重要的行话术语，因为在此时操作员通常拥有的唯一信息是仪表板上的一条小线的形状，以及他们自己对该线的形状是否看起来“正确”的内部判断【图1-2】。

![](img/4e6e799bc9cb3e86f203595f40542979_14_0.png)

确定了线的形状开始看起来“不对劲”的时间点后，操作员随后会眯着眼，尝试找到仪表板上同时变得“扭曲”的其他线条。然而，由于这些指标彼此完全独立，操作员必须在脑中进行比较，而计算机没有任何帮助。

不用说，盯着图表希望找到有用的相关性需要时间和脑力，而且还会导致眼疲劳。

就我个人而言，我会用一把尺子或一张纸，看看什么对齐了。在“现代”仪表板中，尺子现在是作为 UI 的一部分绘制的一条线。但这仍然是一个非常粗糙的解决方案。识别相关性的真正工作仍然必须在操作员的头脑中进行，同样没有任何计算机的帮助。

在对问题有了初步的粗略猜测后，操作员通常开始调查他们认为可能与问题相关的事务【日志】和资源【机器、进程、配置文件】【图1-3】。

![](img/4e6e799bc9cb3e86f203595f40542979_15_0.png)

图1-3。查找与异常相关的日志也是一种糟糕的体验。

在这里，计算机同样没有真正的帮助。日志存储在完全独立的系统中，无法与任何指标仪表板自动关联。配置文件和其他特定于服务的<|message|>信息通常根本不在任何系统中，操作员必须通过 SSH 或其他方式访问正在运行的机器来查看它们。

因此，操作员再次被迫自行完成查找相关性的工作，这次是在指标和相关日志之间。识别这些日志可能很困难；通常必须查阅源代码才能对可能存在的日志有个概念。

当找到一个【可能、有希望的】相关日志时，下一步通常是确定导致该日志生成的事件链。这意味着找到同一事务中的其余日志。

同样，缺乏相关性给操作员带来了巨大负担。非结构化和半结构化日志系统没有自动按事务索引和过滤日志的机制。尽管这是操作员执行的迄今为止最常见的日志工作流程，但他们仍被迫执行一系列临时查询和过滤，以将可用日志缩小为一个子集，希望该子集能近似代表事务。为了有成功的机会，他们必须依赖应用程序开发人员添加各种请求 ID 和其他面包屑，以便日后找到并拼接起来。

在小型系统中，重建事务的过程很繁琐但可行。但一旦系统扩展到包含许多水平扩展的服务，重建单个事务所需的时间就开始严重限制任何调查的范围。图1-4显示了一个触及许多服务的复杂事务。你将如何收集所有日志？

![](img/4e6e799bc9cb3e86f203595f40542979_16_0.png)

图1-4。使用传统日志记录，找到构成特定事务的确切日志可能需要大量努力。一旦系统变得足够大，就几乎不可能了。

一个很好的答案是分布式追踪，它实际上拥有重建事务所需的所有 ID 和索引工具。不幸的是，追踪系统通常被视为延迟分析的利基工具。因此，它们接收到的日志数据相对较少。而且由于它们专注于延迟分析，追踪系统通常会被大量采样，使其对这类调查变得无关紧要。

## 不是三根支柱，而是一股单一的辫子

不用说，这很糟糕。上述工作流程确实代表了一种糟糕的状况。但由于我们长期生活在这种技术体制下，我们往往没有意识到它实际上有多低效，与它本可以达到的效果相比。

今天，为了了解系统如何变化，操作员必须首先收集大量数据。然后他们必须利用自己的大脑，根据仪表板显示和日志扫描等视觉刺激，在数据中识别相关性。这是一项强烈的脑力劳动。如果计算机程序能够自动扫描和关联这些数据，这也是不必要的。如果操作员能够专注于调查系统如何变化，而无需先识别发生了什么变化，他们将节省时间——通常是在时间至关重要的情况下。

在编写能够准确执行这种变更分析的计算机程序之前，所有这些数据点都需要连接起来。日志需要链接在一起，以便识别事务。指标需要链接到日志，以便将生成的统计数据与它们所测量的事务连接起来。并且每个数据点都需要链接到基础系统资源——软件、基础设施和配置细节——以便将所有事件连接到整个系统的拓扑结构。

最终结果——一个包含描述分布式系统状态所需的所有数据的单一、可遍历的图——是能够让分析工具获得系统完整视图的数据结构。不是“三个支柱”的孤立数据，我们将拥有一个相互连接数据的单一辫子。

这就是 OpenTelemetry 的用武之地。如图1-5所示，OpenTelemetry 是一种新的遥测系统，以集成的方式生成追踪、日志和指标。所有这些连接的数据点随后一起通过同一协议传输，然后可以输入到计算机程序中，以识别整个数据集中的相关性。

![](img/4e6e799bc9cb3e86f203595f40542979_17_0.png)

图1-5。OpenTelemetry 将所有这些孤立的信息连接为单一的、高度结构化的数据流。

这种统一的数据是什么样的？在下一章中，我们将把三根支柱放在一边，从零开始构建一个新的心智模型。

## 结构化数据的价值

眯眼看图并不是寻找相关性的最佳方式。操作员头脑中目前完成的大量工作实际上可以被自动化。这使操作员能够在识别问题、提出假设和验证根本原因之间快速切换。

要构建更好的工具，我们需要更好的数据。遥测必须具备两个质量才能支持高质量的自动化分析：

- 所有数据点必须在具有适当索引的图中连接起来。
- 所有代表常见操作的数据点必须具有明确定义的键和值。

在本章中，我们将逐步介绍现代遥测数据模型，从一个基本构建块开始：属性。

### 属性：定义键和值
