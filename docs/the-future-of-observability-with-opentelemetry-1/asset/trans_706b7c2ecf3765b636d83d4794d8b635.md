## 时间是我们最宝贵的资源

然而，我们不需要神奇的 AIOps 就能显著改善工作流程。识别相关性，同时获取相关信息以便你能有效地浏览它，这是计算机*绝对*可以为你做到的！而且这会为你节省时间。大量时间。如此多的时间，以至于它将从根本上改变你调查系统的方式。

体验到浪费时间的巨大减少，是实践现代可观测性的核心。即使在简单的系统中， crunching 数据以识别相关性也可能很困难——在规模化时几乎是不可能的。通过将认知负担转移到机器上，操作员能够有效地管理那些已经超出任何人类能够容纳的系统。

但这种对遥测分析方式的转变，并不是可观测性世界即将发生的唯一重大变化。我们需要的许多遥测数据都来自我们没有编写的软件：我们依赖的开源库、数据库和托管服务。这些系统传统上在仪表化和产生遥测方面存在困难。我们可以访问的数据以及其来源，也即将以根本性的方式发生变化。

## 支持开源和原生仪表化

到目前为止，我们已从数据的角度讨论了现代可观测性。但现代可观测性还有另一个方面，从长远来看，可能同样重要：我们如何处理创建数据的仪表化。

大多数软件系统都是由现成的组件构建的：Web 框架、数据库、HTTP 客户端、代理、编程语言。在大多数组织中，几乎没有这部分软件基础设施是在内部编写的。相反，这些组件在许多组织之间共享。最常见的是，这些共享组件以具有宽松许可的开源（OSS）库的形式出现。

由于这些 OSS 库封装了平均系统中几乎所有关键功能，因此对这些库的高质量仪表化的访问对于大多数可观测性系统至关重要。

传统上，仪表化是“单独销售”的。这意味着软件库不包含用于生成跟踪、日志或指标的仪表化。相反，特定于解决方案的仪表化是在部署可观测性系统时作为后续步骤添加的。

## 什么是特定于解决方案的仪表化？

在本章中，术语 *特定于解决方案的仪表化* 指的是任何为特定可观测性系统设计的仪表化，使用作为该特定系统数据存储系统衍生品开发的客户端。在这些系统中，客户端和存储系统通常变得深度交织。因此，应用程序要从一个可观测性系统切换到另一个系统时，通常需要完全重新进行仪表化。

特定于解决方案的仪表化是“三大支柱”固有的垂直整合的遗留问题。每个后端都摄取特定类型的专有数据；因此，这些后端的创建者还必须提供生成该数据的仪表化。

这种仪表化方法给软件开发的每个参与者都带来了麻烦：提供者、用户和 OSS 库作者。

## 可观测性正被特定于解决方案的仪表化淹没

从可观测性系统的角度来看，仪表化代表了巨大的开销。

过去，互联网应用程序相当同质化，可以围绕特定的 Web 框架构建可观测性系统：Java Spring、Ruby on Rails 或 .NET。但随着时间的推移，软件的多样性爆炸式增长。维护每个流行 Web 框架和数据库客户端的仪表化现在代表了巨大的投资。

由此产生的重复工作简直是巨大的。传统上，供应商将其在仪表化方面的投资既作为卖点，也作为一种守门机制。但软件开发速度的不断加快开始使这种做法不可持续。表面积对于一个规模合理的仪表化团队来说实在太大，无法跟上。

这种负担对于新的、新型的可观测性系统来说尤其严峻，尤其是 OSS 可观测性项目。如果一种新型系统在编写大量仪表化之前无法部署到生产环境中，而一个 OSS 项目在广泛部署之前无法吸引重大关注，那么科学进步就会陷入僵局。对于需要端到端仪表化才能提供最大价值的基于追踪的系统来说，这一点尤其正确。

## 应用程序被特定于解决方案的仪表化锁定

从应用程序开发者的角度来看，特定于解决方案的仪表化代表了一种有害的锁定形式。

可观测性是一个横切关注点。要彻底追踪、记录或度量一个大型应用程序，就意味着数千个仪表化 API 调用会散布在整个代码库中。更改可观测性系统需要剔除所有这些仪表化，并用新系统提供的不同仪表化替换它们。

替换仪表化代表了巨大的前期投资，即使只是尝试新系统也是如此。更糟糕的是，大多数系统都大到无法一次性在所有服务中同时交换所有仪表化。大多数系统需要逐步推出新仪表化，但执行此类推出可能难以设计，并且需要付出更多努力。

被特定于解决方案的仪表化“困住”是非常令人沮丧的。就在可观测性供应商开始难以提供自己的仪表化之际，用户开始拒绝采用它。知道重新仪表化需要多少工作，许多用户强烈希望他们考虑的任何新的可观测性系统都能与他们当前使用的仪表化一起工作。

为了支持这一请求，许多可观测性系统试图与多个其他系统提供的仪表化一起工作。但这种拼凑式方法降低了每个系统摄取的数据质量。从多个来源摄取数据意味着输入数据的定义不再清晰，而当预期数据不均匀且定义模糊时，分析工具很难完成其工作。

## 为 OSS 提供特定于解决方案的仪表化基本上是不可能的

从开源库作者的角度来看，特定于解决方案的仪表化代表了一种悲剧。

来自 OSS 库的遥测对于在其之上构建的软件应用程序的运行至关重要。对操作至关重要的数据是什么——以及操作员应如何利用这些数据来补救问题——最了解的人就是实际编写软件的 OSS 库开发者。

但库作者陷入了困境。正如我们将看到的，无论编写得多好，没有任何特定于解决方案的仪表化 API 是 OSS 库可以接受的选择。

## 你如何选择一个日志库？

假设你正在编写世界上最伟大的 OSS Web 框架。生产中可能出现许多问题，自然你希望将错误、调试和性能信息传达给你的用户。你使用哪个日志库？

有足够多的体面日志库。事实上，有这么多，以至于无论你选择哪个库，你都保证会有许多用户希望你选择另一个。如果你的 Web 框架选择一个日志库，而数据库客户端库选择另一个怎么办？如果两者都不是用户想要使用的那个怎么办？如果他们选择了同一库的不兼容版本怎么办？

没有干净的方法可以将多个特定于解决方案的日志库组合成一个连贯的系统。虽然日志足够简单，以至于一堆不同的解决方案可能可行，但对于特定于解决方案的指标和追踪来说并非如此。

因此，OSS 库通常不会内置日志、指标或追踪。相反，库选择提供“可观测性钩子”，这要求其用户编写和维护大量适配器，以将他们使用的库连接到他们的可观测性系统。
