

# 异步通信

用户将始终获得快速响应。为此，我们需要向用户返回某种状态信息。例如，当请求一个尚未验证的用户对象时，它可能会返回 `status: pending`。

你想要避免同步请求的原因很简单：

*   另一个服务（本例中为 `AddressService`）可能已宕机。
*   另一个服务可能进行了你不知情的更改。
*   另一个服务可能耗时较长，导致你或你的客户端超时。

如果你使用异步请求且服务宕机，你可以简单地重试，并通知开发人员潜在的问题。

你可能会想知道，即使你自己维护相关服务，这条规则是否仍然适用。是的，绝对适用。你会犯错，事物会变化，而你会忘记更新依赖服务。

## Swift 中的异步通信

### 接收请求时，请考虑以下事项：

这里没有什么是你为普通 Web API 所不做的。将任何 `internal` 调用视为公共调用一样对待。在大多数情况下，你只需增加一层额外的安全性。为非真正公开的调用定义一个内部子路由对你来说可能是合理的。这可能看起来像下面这样：

```
let root = routes.grouped(.anything, "internal")

try root.register(collection: InternalController())
```

现在，你可以在该控制器中完成所有可在内部工作的操作。

### 发送请求时，请考虑以下事项：

得益于 `SwiftNIO`（更多详情请参见[第 2 章](#0437cb27-3342-4d58-8253-7093af9626ac.xhtml) *理解服务端 Swift*），发送异步请求非常容易。以下代码展示了发送请求可能的样子：

```
return client.post(
    url,
    headers: [
        "Authorization": "Basic \(credentials.base64EncodedString())",
        "Content-Type": "application/json"
    ]
) { request in
    let body = try JSONEncoder().encode(json)
    request.http.body = HTTPBody(data: body)
}
```

这就是让请求在 `SwiftNIO` 的 `EventLoop` 上运行所需的全部操作。

既然我们已经探讨了异步通信，让我们看看应该避免什么。

# 应避免的事项

到目前为止，你已经了解了微服务之间*如何*通信。现在，让我们讨论要*避免*什么。避免事项的清单与最佳实践密不可分：

## 通信本身

少即是多；在通信方面这尤为真实。如果你想从根本上避免通信，请尝试创造性地思考如何规避通信需求。例如，不必通过认证服务验证用户会话，你可以使用 `JWT` 去中心化地验证请求，正如我们在[第 1 章](#992b21d0-d31a-4c8c-9f75-40c93fdd4526.xhtml) *微服务简介* 中讨论的那样。另一个例子是将某些信息存储在内部缓存中；例如，你只是偶尔请求一次更新，但保留一份内部缓存。

## 同步通信

我们已经谈过这个了，但让我再说一遍：不惜一切代价避免它。稍后修复它将花费你更多的时间和精力。唯一可接受的例外是如果你正在处理实时数据且通信至关重要；例如，支付确认。

## 多服务通信

你可能会发现自己处于需要与系统中多个微服务通信的境地。尽量避免这种情况，因为这会增加大量复杂性。通常，你可以绕过它。

## 链式请求

想象一下，服务 A 向服务 B 请求某些内容，但服务 B 需要先连接到服务 C。这不仅执行起来需要一段时间，还会招致各种麻烦。为了避免这种情况，你应该让 B 通过本地数据库缓存（缓存其从 C 所需的内容）异步地与 C 打交道。

在本节中，我们了解了微服务之间良好通信的样子。具体来说，我们研究了异步通信以及实现通信时应避免的事项。有了这些知识，我们可以开始研究消息和事件系统。

# 理解消息和事件系统

到目前为止，你可能想知道我们*实际上*是如何将微服务很好地连接在一起的。最直观简单的答案是我们提供 `REST` API。然而，还有系统间通信的方式并非公开，而是纯粹内部的。它们可分为两类：

*   消息系统
*   事件系统

我们将在本节探讨这两个主题。

让我们深入了解，从消息系统开始！

# 消息系统

消息系统是基础设施的一部分，允许消息跨系统发送。这意味着微服务可以通过该系统向另一个服务发送消息。问题是，这与直接使用服务提供的 API 有何不同？

消息系统通常提供以下优势：

*   可靠传输，因为消息需要由接收方确认
*   传输失败时自动重试
*   警告和崩溃检测
*   排队

随着系统的增长，这些优势中的每一个都非常有用。如果微服务宕机，API 也将不可用。你的依赖服务要么需要拥有自己的重试系统以进行通信，要么可以依赖消息系统。

现在，让我们看看事件系统是如何工作的。

# 事件系统

一般来说，事件系统类似于消息系统。主要区别在于，在消息系统中，你有一个*发送者*和一个*接收者*，而在事件系统中，你有一个*发送者*和一个*主题/事件*。服务可以订阅主题或事件，每当发送者向该主题或事件发送消息时，它们都会收到通知。

这里的重要区别是发送者无法控制已发送的消息。一旦消息发出，发送者将不知道谁在何时接收了消息，至少在大多数事件系统中是这样。

此类系统的用例显然不同于消息系统。一些流行的用例如下：

*   最终用户通知
*   大规模数据事件（如社交媒体）
*   统计和指标

到目前为止，你已经了解了什么是消息和事件系统，它们如何为你的应用程序带来益处，以及它们的区别和在何种情况下选择哪一种。现在，让我们来看看 `REST` 和 `WebSocket` API。

# REST 和 WebSocket API

许多 API 使用 `REST` 作为其暴露 API 的方式。`REST` 的主要优势是无状态。每个请求都是隔离的。对于微服务之间的通信来说，这不是一个坏主意。你永远不知道何时需要通信，当你确实需要通信时，通常是询问或发送信息的单次查询。

另一方面，你可能听说过 `WebSockets`。它们是在公共空间中使用*套接字*的简单想法。套接字是计算机相互通信的一种非常基础的方式。通常，它们不为你定义接口，但它们允许你发送原始字节数据。套接字连接和 `REST` 连接的主要区别在于套接字有状态。当你通过 (Web) 套接字连接到另一个服务时，你是在打开连接、通信，然后在之后关闭连接。

我们将在以下部分更详细地探讨这一点：

*   WebSocket 的优势：何时使用以及如何使用
*   定义接口：如何以结构化方式通信
*   REST 的优势：为什么 REST 是一个好的起点

让我们从 WebSocket 的优势开始。
