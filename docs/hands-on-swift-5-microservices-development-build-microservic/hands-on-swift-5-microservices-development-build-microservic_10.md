## 理解何时通信

面对现实吧——您的微服务迟早会相互通信。在本节中，我们将探讨它们何时应该通信以及应该通信什么内容。微服务之间进行通信的情况可限制为以下几种：

*   数据验证
*   数据处理
*   数据聚合
*   数据管理

注意到它们都以 *Data* 开头吗？这其实是一个重要的提示：微服务通常只为内部目的相互通信。这意味着从一个服务发送到另一个服务的请求几乎从不与用户请求同步发生，而是通过内部作业（如 `cron jobs`）进行。

例如，假设我们要验证一些用户输入，比如订单。订单包含产品，而这些产品有价格。当然，我们想用创建价格的服务来验证这些价格。

例如，以下是我们从用户那里得到的输入：

```json
{
"items":[
    {
        "id": 1,
        "name": "Product",
        "price": 1000,
        "quantity": 3
    },
    {
        "id": 1,
        "name": "Product",
        "price": 100,
        "quantity": 1
    }
],
"coupons": [
    {
        "code": "ABC",
        "percentage": 10,
        "amount": 310
    }
],
"total": 3100,
"coupon": 310,
"due": 2790,
"creditCardToken": "asdfasdfasdf"
}
```

自然地，我们要确保用户发送（和看到）的价格与我们使用的价格相同。为了将加载时间降至最低，我们不会在用户请求到来时立即发送此验证。相反，我们会将此作业排队，稍后再执行。

我们将在以下章节中探讨上述所有情况。

## 理解数据验证

验证是接收用户输入并针对保存在别处的数据进行核实的过程。一个例子是在线商店。当您下单时，即请求发送到 `Order Processing Service`，产品价格需要验证，优惠券和支付方式需要确认。所有这些*可以*在请求到来时同步发生，但如果这些服务中的任何一个出现问题且不可用，这可能会有问题。

让我们详细看看发生了什么。

首先，用户提交订单。然后，`Order Processing Service` 接收到请求，可能如下所示：

```json
{
"items":[
    {
        "id": 1,
        "name": "Product",
        "price": 1000,
        "quantity": 3
    },
    {
        "id": 1,
        "name": "Product",
        "price": 100,
        "quantity": 1
    }
],
"coupons": [
    {
        "code": "ABC",
        "percentage": 10,
        "amount": 310
    }
],
"total": 3100,
"coupon": 310,
"due": 2790,
"creditCardToken": "asdfasdfasdf"
}
```

此请求本质上是包含我们所需一切的完整订单：

*   用户想购买的所有产品，包括其价格
*   用户预期的总金额
*   用户拥有的优惠券总金额
*   应付金额
*   支付信息（如 `creditCardToken`），以便订单可立即支付

从技术上讲，我们可以按原样处理此请求，甚至不进行计算。您可能想知道为什么请求会是这样，所以让我们看看。

用户期望在一个页面上看到他们支付的所有内容。因此，最终结账页面将包含您在请求中看到的所有内容，包括所有总计。为什么我们现在要将其提交给我们的订单服务？因为我们可以验证用户*看到的*也是我们*知道的*。现在，我们可以可靠地判断用户屏幕上的内容是否真的是它应该的样子。

让我们非常清楚一点：我们永远不信任用户输入。当请求到来时，我们需要验证和核实每一个数字。然而，让非恶意用户知道何时存在差异是有帮助的。

让我们回到订单流程。现在，我们保存请求。此步骤仅意味着我们按原样接收订单并保存它。我们这样做的原因是想要一份用户请求了什么的记录，无论接下来发生什么。之后，我们向用户返回“订单已接收”消息。

用户请求已完成，此时用户不在主动等待我们。然而，我们需要在后台做一些工作。在这里，我们需要从 `Product Service` 请求每个产品的价格并验证其准确性。然后，我们需要计算每行的总计并将它们相加得到订单总金额。接下来，我们需要遍历优惠券并验证它们是否存在且适用。如果是，则我们必须将所有优惠券金额相加得到优惠券总金额。然后，我们从总金额中减去优惠券总金额。这是用户必须支付的数字。这也是请求中的数字，所以我们需要验证它是否正确。

如果我们发现问题（例如，优惠券不再有效），我们需要通知用户并让他们知情。最简单的解决方案可能是取消订单，但您也可以提供替代方案（例如支付更高金额）。

如果一切正常且应付总额与用户预期相符，则可以扣款他们的信用卡。




现在订单已验证完毕，可以进行处理并发送至发货环节。

在此整个过程中，我们至少要与其他服务通信两次：

*   获取商品价格时
*   向用户信用卡扣款时

取决于我们的架构，可能会有额外的服务（例如优惠券服务），但至少涉及两个其他服务。我们绝不希望这些请求在订单进来时同步发生，这意味着我们不想在请求到达时立即验证价格。这会导致用户等待，并可能引发问题。如果我们的商品服务宕机（无论何种原因），我们就无法接单，支付服务商也是如此。想象一下，如果这些服务之一出现故障，你就会错失订单。如果必须的话，最好能先接收订单，稍后再处理。

信用卡支付通常会进行预授权。这通常发生在*提交订单之前*，并直接与支付服务商进行。这将确认信用卡有足够的可用余额，并增加订单成功处理的可能性。我们将在下一章看到这一过程的实际操作。

既然我们了解了数据验证是如何进行的，接下来让我们看看数据是如何被处理的。

# 理解数据处理

既然我们已经介绍了数据验证，现在来谈谈数据处理。你存储的数据可能需要与更多数据交互。例如，继续沿用商店示例，你的订单详情需要提交给履约中心。这里的目标是以以下方式之一处理存储的数据：

*   将数据传输给另一个服务以进行进一步处理（沿链路向下传递）
*   使用另一个服务处理数据，然后接收结果（例如，将图像或视频处理为目标格式）
*   根据另一个服务更新“存档”信息（例如，更新存档的汇率）

这些服务的技术实现会因处理部分的用途不同而截然不同。不过，你确实需要遵循一些规则：

*   以异步方式处理数据。
*   预期其他服务会失败（实现重试机制）。

既然你已经掌握了数据处理的基础知识，让我们看看数据是如何聚合的。

# 理解数据聚合

在微服务架构中，你的信息通常分散在不同的服务中。商品在一个服务，订单在另一个服务，发货信息在又一个服务。但如果你想提供客户的全景视图怎么办？如果你想统计某些商品被购买的频率怎么办？

在这些情况下，你需要聚合数据，即从其他服务收集数据并汇总在一处。聚合后的数据通常应该是副本，以确保你不会从另一个服务获取数据然后在本地更新它。例如，一个微服务返回包含金额和日期的订单列表。你不应该维护自己的本地数据库，而应该在每次从其他服务获取数据时替换它。

这可能意味着你需要建立程序来更新聚合数据或持续追加数据。根据数据的性质，这可能会非常复杂。

让我们看一个例子。假设你的数据库中有订单，包含总价值和时间戳，你想按日期聚合它们。

以下是你的订单处理服务可能返回的响应：

```
[
    {
        "id": 1,
        "totalValue": 10,
        "date": "10-10-2019"
    },
    {
        "id": 2,
        "totalValue": 15,
        "date": "10-10-2019"
    },
    {
        "id": 3,
        "totalValue": 25,
        "date": "10-11-2019"
    },
    {
        "id": 4,
        "totalValue": 10,
        "date": "10-12-2019"
    }
]
```

这是一个简单的订单列表，未以任何方式聚合。在这里，你可以看到同一天有两笔订单，但它们没有被良好格式化，以便轻松查看每天有多少订单。因此，我们的聚合服务不会尝试按天聚合它们。期望的结果事后应如下所示：

```
[
    {
        "date": "10-10-2019",
        "totalValue": 25,
        "orders": 2
    },
    {
        "date": "10-11-2019",
        "totalValue": 25,
        "orders": 1
    },
    {
        "date": "10-12-2019",
        "totalValue": 10,
        "orders": 1
    }
]
```

你能看到现在变成了一个包含订单数量的日期列表吗？

这种聚合非常常见，应该通过你的微服务来完成。当然，你可能会争辩说客户端也可以执行此类任务。虽然对于较小的数据集这是真的，但一旦数据达到 GB 和 TB 级别，服务器将更有能力执行聚合。

既然我们已经了解了数据聚合，接下来将看看数据是如何管理的。

# 理解数据管理

从概念上讲，数据管理与数据聚合非常相似。我们希望根据一个服务来控制其他服务中的数据。一个例子是删除用户账户的请求。想象一个像 Facebook 那样复杂的数据系统。你可以轻松判断这不仅仅是一个更新数据库的简短调用。具体来说，删除条目本身就有其挑战（法律上和组织上），并需要与许多服务进行大量交互。

假设你收到用户请求，删除其在你在线商店中的所有内容。这里，用户的客户端（如 App 或网站）将删除请求发送给用户服务。用户服务会意识到其他服务也需要被通知，并向它们发送删除请求。可能有相当多的服务需要被通知，这就是为什么你应该在后台队列中异步处理此类任务（例如 cron 任务）。

在本节中，我们探讨了多数据管理在多微服务环境下的样子。我们了解了数据处理的四个组成部分：`数据验证`、`数据处理`、`数据聚合` 和 `数据管理`。现在，让我们看看良好的通信是什么样子的。

# 探索良好的通信

良好的微服务结构也享有微服务之间良好的通信。在第 1 章 *微服务简介* 中，我们讨论过微服务应尽可能独立运行，因此应尽可能限制彼此间的通信。在本节中，我们将探讨微服务之间通信实际上适用的情况。

我们将探讨以下主题：

*   异步通信：什么是异步通信，它有何用处？
*   避免事项：通信时不该做的事。

让我们从异步通信开始。

# 异步通信

这条规则总有例外，但请务必将其作为一条规则：不要在面向用户的 API 服务中发送同步请求——只要可行，请让一切变为异步。为了更好地解释这一点，让我们看一个例子。

你有一个名为 `UserService` 的面向用户服务。在该服务中，你需要从 `AddressService` 验证用户地址。因为 `UserService` 是面向用户的，意味着客户端（用户）从它请求信息，它应该尽快响应。为了尽快响应，我们应该异步实现地址检查，使其与用户请求分离。这意味着用户请求永远不会与对 `AddressService` 的内部调用结合在一起。





# 异步通信

用户将始终获得快速响应。为此，我们需要向用户返回某种状态信息。例如，当请求一个尚未验证的用户对象时，它可能会返回 `status: pending`。

你想要避免同步请求的原因很简单：

*   另一个服务（本例中为 `AddressService`）可能已宕机。
*   另一个服务可能进行了你不知情的更改。
*   另一个服务可能耗时较长，导致你或你的客户端超时。

如果你使用异步请求且服务宕机，你可以简单地重试，并通知开发人员潜在的问题。

你可能会想知道，即使你自己维护相关服务，这条规则是否仍然适用。是的，绝对适用。你会犯错，事物会变化，而你会忘记更新依赖服务。

## Swift 中的异步通信

### 接收请求时，请考虑以下事项：

这里没有什么是你为普通 Web API 所不做的。将任何 `internal` 调用视为公共调用一样对待。在大多数情况下，你只需增加一层额外的安全性。为非真正公开的调用定义一个内部子路由对你来说可能是合理的。这可能看起来像下面这样：

```
let root = routes.grouped(.anything, "internal")

try root.register(collection: InternalController())
```

现在，你可以在该控制器中完成所有可在内部工作的操作。

### 发送请求时，请考虑以下事项：

得益于 `SwiftNIO`（更多详情请参见第 2 章 *理解服务端 Swift*），发送异步请求非常容易。以下代码展示了发送请求可能的样子：

```
return client.post(
    url,
    headers: [
        "Authorization": "Basic \(credentials.base64EncodedString())",
        "Content-Type": "application/json"
    ]
) { request in
    let body = try JSONEncoder().encode(json)
    request.http.body = HTTPBody(data: body)
}
```

这就是让请求在 `SwiftNIO` 的 `EventLoop` 上运行所需的全部操作。

既然我们已经探讨了异步通信，让我们看看应该避免什么。

# 应避免的事项

到目前为止，你已经了解了微服务之间*如何*通信。现在，让我们讨论要*避免*什么。避免事项的清单与最佳实践密不可分：

## 通信本身

少即是多；在通信方面这尤为真实。如果你想从根本上避免通信，请尝试创造性地思考如何规避通信需求。例如，不必通过认证服务验证用户会话，你可以使用 `JWT` 去中心化地验证请求，正如我们在第 1 章 *微服务简介* 中讨论的那样。另一个例子是将某些信息存储在内部缓存中；例如，你只是偶尔请求一次更新，但保留一份内部缓存。

## 同步通信

我们已经谈过这个了，但让我再说一遍：不惜一切代价避免它。稍后修复它将花费你更多的时间和精力。唯一可接受的例外是如果你正在处理实时数据且通信至关重要；例如，支付确认。

## 多服务通信

你可能会发现自己处于需要与系统中多个微服务通信的境地。尽量避免这种情况，因为这会增加大量复杂性。通常，你可以绕过它。

## 链式请求

想象一下，服务 A 向服务 B 请求某些内容，但服务 B 需要先连接到服务 C。这不仅执行起来需要一段时间，还会招致各种麻烦。为了避免这种情况，你应该让 B 通过本地数据库缓存（缓存其从 C 所需的内容）异步地与 C 打交道。

在本节中，我们了解了微服务之间良好通信的样子。具体来说，我们研究了异步通信以及实现通信时应避免的事项。有了这些知识，我们可以开始研究消息和事件系统。

# 理解消息和事件系统

到目前为止，你可能想知道我们*实际上*是如何将微服务很好地连接在一起的。最直观简单的答案是我们提供 `REST` API。然而，还有系统间通信的方式并非公开，而是纯粹内部的。它们可分为两类：

*   消息系统
*   事件系统

我们将在本节探讨这两个主题。

让我们深入了解，从消息系统开始！

# 消息系统

消息系统是基础设施的一部分，允许消息跨系统发送。这意味着微服务可以通过该系统向另一个服务发送消息。问题是，这与直接使用服务提供的 API 有何不同？

消息系统通常提供以下优势：

*   可靠传输，因为消息需要由接收方确认
*   传输失败时自动重试
*   警告和崩溃检测
*   排队

随着系统的增长，这些优势中的每一个都非常有用。如果微服务宕机，API 也将不可用。你的依赖服务要么需要拥有自己的重试系统以进行通信，要么可以依赖消息系统。

现在，让我们看看事件系统是如何工作的。

# 事件系统

一般来说，事件系统类似于消息系统。主要区别在于，在消息系统中，你有一个*发送者*和一个*接收者*，而在事件系统中，你有一个*发送者*和一个*主题/事件*。服务可以订阅主题或事件，每当发送者向该主题或事件发送消息时，它们都会收到通知。

这里的重要区别是发送者无法控制已发送的消息。一旦消息发出，发送者将不知道谁在何时接收了消息，至少在大多数事件系统中是这样。

此类系统的用例显然不同于消息系统。一些流行的用例如下：

*   最终用户通知
*   大规模数据事件（如社交媒体）
*   统计和指标

到目前为止，你已经了解了什么是消息和事件系统，它们如何为你的应用程序带来益处，以及它们的区别和在何种情况下选择哪一种。现在，让我们来看看 `REST` 和 `WebSocket` API。

# REST 和 WebSocket API

许多 API 使用 `REST` 作为其暴露 API 的方式。`REST` 的主要优势是无状态。每个请求都是隔离的。对于微服务之间的通信来说，这不是一个坏主意。你永远不知道何时需要通信，当你确实需要通信时，通常是询问或发送信息的单次查询。

另一方面，你可能听说过 `WebSockets`。它们是在公共空间中使用*套接字*的简单想法。套接字是计算机相互通信的一种非常基础的方式。通常，它们不为你定义接口，但它们允许你发送原始字节数据。套接字连接和 `REST` 连接的主要区别在于套接字有状态。当你通过 (Web) 套接字连接到另一个服务时，你是在打开连接、通信，然后在之后关闭连接。

我们将在以下部分更详细地探讨这一点：

*   WebSocket 的优势：何时使用以及如何使用
*   定义接口：如何以结构化方式通信
*   REST 的优势：为什么 REST 是一个好的起点

让我们从 WebSocket 的优势开始。




# 定义接口

无论你使用 `WebSockets` 还是 `REST APIs`，你都希望清晰地定义接口或通信格式。你需要准确定义微服务期望什么以及返回什么。双方都需要知道期望的内容，包括并非总是存在的情况。让我们看一个例子：

登录请求可能如下所示：

```
{
    "email": "test@domain.com",
    "password": "test123"
}
```

正常的登录响应如下所示：

```
{
    "accessToken": "ABCDEFG",
    "refreshToken": "ABCDEFG"
}
```

然而，它也可能返回一个错误，指出用户提供了错误的密码。在这种情况下，响应将如下所示：

```
{
    "status": 400
    "errorCode": "invalidLogin",
    "errorMessage": "The submitted login was invalid."
}
```

以下是关于错误消息的几个重要注意事项：

*   在整体编码过程中依赖 `HTTP status codes`。除非你有特定理由，否则无需引入自己的状态码。不过，如果合理，你可以也可能想要在消息体中包含相同的 `HTTP` 代码。
*   使用你自己的 `error code`（如前面的示例所示）来明确标识问题。客户端将使用它来妥善处理错误。
*   你可以包含 `error message`，但不要依赖它被展示给用户。用户的界面语言可能与你代码中的语言不同。

# REST 的优势

为使用无状态数据的应用程序构建 `REST API` 非常合理。这通常适用于大多数应用程序和通用数据。你可能会遇到需要实时数据的情况（例如，Uber 的车辆追踪、Facebook Messenger 等），在这种情况下 `REST` 可能不是理想选择。然而，在许多情况下，`REST` 通常是一个可靠的选择。

让我们详细讨论一些优势：

**它使异步复杂性成为可能**：`WebSockets` 做不到这一点，因为 `WebSocket` 连接通常不会关闭，直到客户端断开连接，所以需要同步地来回通信。`REST` 允许你发送请求，而无需它们持续相互连接。

**轻松适配数据库结构**：通常，数据库由数据库表中的实体组成。每种实体类型可以在你的 `REST API` 中获得自己的端点，并使其易于寻址。在某些情况下，你也可以自动生成 API 端点。

**许多服务中的通用标准**：因为 `REST` 易于实现和交互，它常用于你可能遇到的许多服务中，例如支付处理器（`Stripe`）、税务相关服务（`Taxjar.com`）、会计（如 `Freshbooks`）等等。

# 利用 Swift

正如你已知，`Swift` 非常适合微服务。然而，有几个特性专门适用于 `Swift`，使其开发微服务非常方便。作为一门语言，`Swift` 还很年轻，所以其他语言中许多流行的特性在 `Swift` 起步时并不容易获得。在本节中，我们将探讨一些有助于编写微服务的 `Swift` 特有特性。

我们将探索 `Swift` 的以下两个特性：

*   **共享库**：编写可被多个服务使用的库的能力。
*   **泛型函数和类**：通过利用 `Swift` 的特性为自己节省时间。

让我们从共享库开始。

## 共享库

正如我们之前提到的，你会希望清晰地为你的微服务定义 `protocol` 和格式。如果你能通过定义一个包含所需 `structs`、`protocols` 和 `classes` 的通用库来做到这一点，那将非常方便。例如，让我们看看以下输出：

```
{
    "email": "test@domain.com",
    "password": "test123"
}
```

现在，让我们创建一个表示该输出的 `struct`：

```
struct LoginResponse {
    var email: String
    var password: String
}
```

正如你所见，输出可以被解析为 `struct`。`email` 和 `password` 是两个在两者中都存在的变量，因此 `struct` 可以读取或写入前面的输出。

现在，这个 `struct` 可以用于所有与此特定功能通信的微服务。同样，我们可以定义错误消息：

```
struct LoginErrorResponse {
    var status: Int
    var errorCode: String
    var errorMessage: String
}
```

你会注意到，我们刚刚定义的这些 `structs` 可以轻松地放置在一个共享库中，该库可被以下各方使用：

*   所有需要接收信息的微服务
*   发送此信息的微服务
*   与此信息交互的客户端

这样的库将确保你的服务能有效地相互通信并减少错误。

## 泛型函数和类

`Generic functions and classes` 允许你在不指定类型的情况下定义 `class` 或 `function`。你可能已经用过它们了。`generic functions and classes` 的一个示例如下：

```
func add<T>(_ a: T, _ b: T) -> T { 
    return a + b
}
```

这当然是一个非常简单的例子。然而，你可以使用相同的原则来创建一个函数，如下所示：

```
func loadModel<T: MyModelType>(_ id: Int, on container: Container) -> EventLoopFuture<T?> {
    return T.query(on: request.db).filter(\.$id == id).first()
}
```

在这里，你可以看到我们能够用一个函数加载*任意*模型。同样的原则可以应用于整个类：

```
final class ModelController<M: MyModelType> {
}
```

有了这个，我们现在可以为所有模型创建控制器，而无需重写相同的代码。我们可以让一个控制器服务于多个端点和不同的模型。这为你节省了时间和精力，并减少了错误。

`Generic functions` 也可以在其他语言中找到，例如 `Java` 和 `C#`。然而，很少有*原生*语言拥有如此强大的特性，同时仍然易于学习和使用。
