

-   更难保障安全。同样，这主要是因为不同的团队可能使用不同的技术、工具和框架，这些技术、工具和框架可能带有不同类型的漏洞。一个良好的 CI/CD 工厂有助于缓解其中一些问题，它会静态扫描你的代码以及你依赖的开源库。
-   与现有环境的集成变得更加困难，因为大多数企业都拥有大量遗留系统，这些系统不可能在眨眼间迁移到微服务。这可能迫使微服务设计者构建防腐层，以使他们的限界上下文免受遗留系统中发生的情况的影响。

正如你所看到的，微服务是复杂的，你当然不应该默认采用它们。对于复杂的领域和快速发展的业务，你应该求助于微服务。另一方面，如果你构建的是分布式单体而不是真正的微服务，结果复杂性仍然会更高，但你会自动获得敏捷性、可伸缩性和韧性。底线是，就非功能需求而言，分布式单体虽然更复杂，但仍然比单体更好。你将最大限度地增加获得一个*适合使用*的系统的机会。现在，让我们看看我们有哪些微服务托管选项。

## 托管微服务

微服务是云原生的*典范*。然而，你可以将微服务架构托管在本地，因为尽管这听起来矛盾，云原生并不需要云基础设施。我们将在*第 6 章，云对软件架构实践的影响*中再讨论这一点。大多数真正的微服务架构都托管在容器化平台上。这并不是绝对的要求，但它会让你的生活更轻松。以下是 **Kubernetes (K8s)** 非常适合微服务的一些原因：

-   **可伸缩性**：在 K8s 中，每个微服务对应一个部署。每个部署都可以开箱即用地指定自己的伸缩需求。
-   **韧性**：如前所述，使用微服务可以提高应用的韧性，因为单个服务的失败不应影响所有其他服务。借助 K8s，你可以利用自愈功能，这意味着 K8s 会尝试重启失败的容器。
-   **可部署性**：每个微服务都可以使用金丝雀发布、蓝绿部署、滚动更新等部署技术独立部署。
-   **可用性**：由于每个微服务彼此分离，我们可以轻松识别关键任务服务，并使用 **PodDisruptionBudget** 资源类型，它可以防止意外中断，包括计划维护期间的中断。
-   **对多语言架构的支持**：如前所述，微服务是多语言的，因为不同的团队可以使用不同的技术，只要底层托管平台支持即可。容器编排器就是这种情况。

为了补充 K8s，你还可以依赖 **Linkerd**、**Istio** 和 **Open Service Mesh** 等服务网格，因为它们可以改善全局监控，带有更智能的负载均衡器（这些负载均衡器是第 7 层协议感知的），并提供 **mTLS**，从而在不同微服务之间提供某种一致性。

### 理解设计模式及其目的

**设计模式**是一种公认的最佳实践，用于解决常见问题。许多应用程序都面临同样的挑战，如下所示：

-   它们必须高性能。
-   它们必须是可测试的。
-   它们必须是可维护的，并且应该能够随着时间增长。
-   它们必须具有一定程度的可移植性。
-   它们必须高效地管理内存和**中央处理器（CPU）**。
-   它们必须能够扩展。
-   它们必须支持并发（线程安全）。

上述列表只是典型的*横切关注点*的一个子集。设计模式的目的是找到处理常见问题的最佳方法，而不管使用什么编程语言。

设计模式具有启发性，并不特别规定详细实现应该如何完成。设计模式仍然是高层级的，它们旨在提高代码质量，并最终遵循 **SOLID** 原则，这是由 Robert C. Martin 创制的一套被广泛采用的原则。

SOLID 代表以下术语：

-   **单一职责原则（SRP）**：这一原则旨在掌控给定类的范围，并确保**关注点分离（SoC）**。
-   **开闭原则（OCP）**：这一原则背后的想法是促进代码扩展，同时防止对当前代码的修改。这可以通过接口和抽象类使用一定程度的抽象来实现。
-   **里氏替换原则（LSP）**：你可以找到许多关于这一原则的定义。掌握它的最佳方式之一是通过矩形和正方形示例。如你所知，在数学中，正方形也是矩形。假设我们有一个 `Rectangle` 基类，它有两个独立的 `SetWidth` 和 `SetHeight` 方法。现在，我们实现一个 `Square` 类，它是 `Rectangle` 的子类，这似乎是合适的，因为正方形是矩形。但因为我们知道正方形必须具有相等的高和宽，所以我们重写基类的方法，以便在设置宽度时调整高度，反之亦然。这样做时，以下构造将导致问题：

    ```csharp
    Rectangle rect = new Square();
    rect.setWidth(10);
    rect.setHeight(5);
    Assert.Equal(50, CalculateArea(rect));
    ```

    这是因为当传入正方形时，生成的面积在本例中将是 25 而不是 50。在这种情况下，我们不能再将矩形替换为正方形，因为正方形无法表现得像矩形。更一般地说，当基类和子类具有相互矛盾的约束时，破坏 LSP 原则的风险就会上升。在这种情况下，最好直接拆分 `Square` 和 `Rectangle`。破坏 LSP 最常见的（而且往往是无意的）可观察表现是著名的未实现异常，它实际上阻止了派生类对基类的任何替换。
-   **接口隔离原则（ISP）**：这一原则的目的是控制接口的范围，并确保接口客户端只实现其需求所必需的内容。因此，你应该尝试最大化接口的粒度。
-   **依赖倒置原则（DIP）**：DIP 的目的是确保类只依赖抽象，而不是具体类。我们将在本章后面重点探讨这一原则。

> **注意**
> 设计模式在 SOLID 创建之前很久就已经存在。因此，它们并非为遵循 SOLID 而创建，但由于最佳实践已融入这些模式，使用它们会增加按设计符合 SOLID 的机会。
