### ClusterRoleの作成

[例3-](#ch03.html#list-pods-clusterrole)2に示す`list-pods-clusterrole`という名前の`ClusterRole`をファイル`clusterrole.yaml`で定義することから始める。規則のセットは`Pod`リソースと動詞`list`を追加するだけである。

#### 例 3-2. PodをリストできるようにするClusterRoleのYAMLマニフェスト

```
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: list-pods-clusterrole
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["list"]
```

対応するYAMLマニフェストファイルをポイントしてオブジェクトを作成する：

```
$ kubectl apply -f clusterrole.yaml
clusterrole.rbac.authorization.k8s.io/list-pods-clusterrole created
```

### RoleBindingの作成

[例3-3は](#ch03.html#rolebinding-service-account)`RoleBinding`のYAMLマニフェストをファイル`rolebinding.yaml`で定義している。`RoleBinding`は`ClusterRole` `list-pods-clusterrole`を`sa-pod-api`という名前のサービスアカウントにマッピングし、名前空間`k97`にのみ適用される。

#### 例 3-3. サービスアカウントにアタッチされた RoleBinding の YAML マニフェスト

```
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: serviceaccount-pod-rolebinding
  namespace: k97
subjects:
- kind: ServiceAccount
  name: sa-api
roleRef:
  kind: ClusterRole
  name: list-pods-clusterrole
  apiGroup: rbac.authorization.k8s.io
```

`apply`、`RoleBinding`オブジェクトを作成する：

```
$ kubectl apply -f rolebinding.yaml
rolebinding.rbac.authorization.k8s.io/serviceaccount-pod-rolebinding created
```

付与された`list`パーミッションにより、サービス・アカウントは`k97`ネームスペース内のすべての`Pod`を適切に取得できるようになった。以下の出力に示すように、`pods`コンテナ内の`curl`コマンドは成功する：

### サービスアカウントトークンの自動マウントを無効にする

前のセクションで説明した`Pod`は、APIサーバーに対する認証手段としてサービス・アカウントのトークンを使用した。トークン・ファイルを`/var/run/secrets/kubernetes.io/serviceaccount/token`にマウントするのは、どのサービス・アカウントでも標準的な振る舞いだ。このファイルの内容が本当に必要になるのは、`Pod`が実際にKubernetes APIとやりとりする場合だけだ。それ以外の場合、この振る舞いは、`Pod`へのアクセスが攻撃者をトークンに直接導くことになるため、潜在的なセキュリティリスクをもたらす。

[例3-](#ch03.html#service-account-disable-automount)4に示すように、属性`automountServiceAccountToken`に値`false`を代入することで、サービスアカウントオブジェクトのオートマウントの振る舞いを無効にすることができる。

#### 例3-4. サービスアカウントのトークン自動マウントの振る舞いをオプトアウトする

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: sa-api
  namespace: k97
automountServiceAccountToken: false
```

個々の`Pod`に対して自動マウントの振る舞いを無効にしたい場合は、`Pod`定義で属性`spec.automountServiceAccountToken`を使用する。[例 3-5](#ch03.html#pod-serviceaccount-disable-automount)に、`Pod`のYAMLマニフェストを示す。

#### 例 3-5. Pod内のサービスアカウントのトークン自動マウントを無効にする

```
apiVersion: v1
kind: Pod
metadata:
  name: list-objects
  namespace: k97
spec:
  serviceAccountName: sa-api
  automountServiceAccountToken: false
  ...
```

### サービスアカウントトークンを生成する

トークンの自動マウントを*無効に*するサービスアカウントを作成したい理由には、様々なユースケースがある。例えば、外部ツールや継続的デリバリ・パイプラインからKubernetes APIにアクセスし、既存のオブジェクトに関する情報をクエリする必要があるかもしれない。このようなシナリオでAPIサーバに対して認証を行う場合にも、トークンが必要となる。リストにあるシナリオは、必ずしも代入されたサービスアカウントで`Pod`を実行するわけではなく、`curl`のようなツールからRESTful API呼び出しを実行するだけである。

トークンを手動で作成するには、`create token`コマンドを実行し、引数にサービスアカウント名を指定する。コマンドの出力がトークンを表示する：

```
$ kubectl create token sa-api
eyJhbGciOiJSUzI1NiIsImtpZCI6IjBtQkJzVWlsQjl...
```

トークンはパスワード・マネージャーなど安全な場所に保管する必要がある。トークンを紛失した場合、再度取り出すことはできない。同じコマンドでトークンを再作成することしかできないが、その場合、以前のトークンは自動的に無効になる。トークンを使用している参照はすべて変更しなければならない。

自動化されたプロセスでは、トークンの有効期限を設定しておくと便利である。`--duration`、「タイム・トゥ・ライフ」が過ぎるとトークンは自動的に無効になる：

```
$ kubectl create token sa-api --duration 10m
eyJhbGciOiJSUzI1NiIsImtpZCI6IjBtQkJzVWlsQjl...
```

### サービスアカウントのシークレットを作成する

Kubernetes 1.24では、`ServiceAccount`オブジェクトがトークンを含む対応する`Secret`オブジェクトを自動的に作成しなくなった。詳細は[リリースノートを](https://oreil.ly/MSPuX)参照のこと。`ServiceAccount`オブジェクトをリストすると、`Secrets`の数が0になる。また、オブジェクトのYAML表現に`secrets`属性が含まれなくなった：

```
$ kubectl get serviceaccount sa-api -n k97
NAME     SECRETS   AGE
sa-api   0         42m
```

[サービスアカウントトークンの作成](#ch03.html#generating-serviceaccount-token)」で説明されているように、`create token`コマンドを使ってトークンを生成するか、対応するシークレットを手動で作成することができる。[例 3-6](#ch03.html#serviceaccount-secret)はそのようなシークレットのYAMLマニフェストを示している。

#### 例3-6. サービスアカウントのシークレットを手動で作成する

```
apiVersion: v1
kind: Secret
metadata:
  name: sa-api-secret
  namespace: k97
  annotations:
    kubernetes.io/service-account.name: sa-api
type: kubernetes.io/service-account-token
```

シークレットにサービスアカウントを代入するには、`kubernetes.io/service-account.name`というキーでアノテーションを追加する。以下のコマンドで`Secret`オブジェクトを作成する：

```
$ kubectl create -f secret.yaml
secret/sa-api-secret created
```

トークンは、シークレットオブジェクトを説明する際の"データ"セクションで発見することができる：

```
$ kubectl describe secret sa-api-secret -n k97
...
Data
====
ca.crt:     1111 bytes
namespace:  3 bytes
token:      eyJhbGciOiJSUzI1NiIsImtpZCI6IjBtQkJzVWlsQjl...
```

# Kubernetesを頻繁にアップデートする

特定のバージョンでKubernetesクラスタをインストールすることは、1回限りのFire and Forget演算子ではない。インストール時に最新のLTS（Long-Term Support）リリースを使用したとしても、クラスタにセキュリティ脆弱性がないことを保証するものではない。

時間が経つにつれて、セキュリティ関連のバグや弱点が発見されるだろう。この文には、基盤となるオペレーティングシステムやクラスタノードが実行する依存関係が含まれる。攻撃者は、一般に公開されている[`CVE`](https://oreil.ly/FHhXD)（Common Vulnerabilities and Exposures）データベースでセキュリティ脆弱性を簡単に調べ、それを悪用することができる。

## バージョニング・スキーム

すべてのノードでKubernetesのバージョンを定期的に更新するのはクラスタ管理者次第だ。Kubernetesは[セマンティック・バージョニング・スキームに従って](https://semver.org)いる。セマンティックバージョンは、メジャーバージョン、マイナーバージョン、パッチバージョンで構成される。例えば、Kubernetesバージョン`1.24.3`の場合、メジャーバージョンは`1`、マイナーバージョンは`24`、パッチバージョンは`3`となる。

バージョンの各部分は特定の意味を持つ。メジャーバージョン部分の変更は破壊的変更を意味する。マイナーバージョン部分のインクリメントは、新しい関数が後方互換性をもって追加されたことを意味する。パッチバージョン部分は、単にバグを修正したものである。

# Kubernetesのマイナーバージョンアップに伴う破壊的変更

Kubernetesが常にセマンティック・バージョニングの厳密な解釈に固執するわけではないことに触れておくことは重要だ。例えば、`PodSecurityPolicy`（`PSP`）アドミッションコントローラーは、[バージョン`1.25.`](https://oreil.ly/JE-i8)0で`Pod Security Admission`概念に置き換えられた。従来であれば、これらの変更はメジャーバージョンの更新でのみ発生するはずだ。API、フラグ、または機能がどのように段階的に廃止されるかをよりよく理解するために、[Kubernetesの非推奨](https://oreil.ly/on9lu)ポリシーを参照すること。

## リリース・ケイデンス

Kubernetesの[新しいマイナーバージョンリリースは](https://oreil.ly/LGIn5)3カ月ごとに行われる。リリースには新機能や追加のバグ修正が含まれることがある。Kubernetesの最新リリースでは必要に応じてセキュリティ修正が実装される可能性があり、その前の2つのマイナーリリースにバックポートされる。自分のクラスタのために常に最新リリースへのアップデートを続けるには、かなりの人的パワーが必要だ。それに応じて、それらの活動のための時間を確保する必要がある。

## アップグレードプロセスを実行する

マイナーバージョンから次の上位バージョンへ（例えば`1.23`から`1.24`へ）、またはパッチバージョンからより新しいバージョンへ（例えば`1.24.1`から`1.24.3`へ）アップグレードすることが推奨される。予期せぬ副作用を避けるため、複数のマイナーバージョンをジャンプアップすることは控えること。

[アップグレード手順の](https://oreil.ly/RxC9j)詳細は、Kubernetesの公式ドキュメントで発見できる。[図3-4は](#ch03.html#cluster_version_upgrade_process)、アップグレードのプロセスを高いレベルで示している。
