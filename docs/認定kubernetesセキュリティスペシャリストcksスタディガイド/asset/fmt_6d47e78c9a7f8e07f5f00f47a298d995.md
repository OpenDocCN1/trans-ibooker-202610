# 既知の脆弱性について画像をスキャンする

セキュリティの脆弱性を記録・発見するためのトップソースのひとつに、[CVE Detailsが](https://oreil.ly/DDlVa)ある。このページでは、既知の脆弱性（CVE）をリストアップし、スコアでランク付けしている。自動化されたツールは、コンテナイメージに埋め込まれたソフトウェアコンポーネントを特定し、それらを中央の脆弱性データベースと比較し、重大度によって問題にフラグを立てることができる。

この機能を持つオープンソースツールの1つが、CKSカリキュラムで明示的に言及されている[Trivy](https://oreil.ly/hqPHH)である。`Trivy`は、コマンドラインツールとして、コンテナ内で、継続的インテグレーションワークフローで設定可能なGitHubアクションとして、IDE VSCodeのプラグインとして、`Kubernetes`演算子として、さまざまなモードで実行できる。利用可能なインストール・オプションと手順の概要については、[Trivyのドキュメントを](https://oreil.ly/qB_c8)参照のこと。試験中、ツールをインストールする必要はない。それはすでにあなたのために事前設定されている。あなたが理解する必要があるのは、ツールの実行方法と、発見された脆弱性のインタプリタと修正方法だけだ。

`Trivy`のコマンドライン実装をインストールしたとする。`Trivy`のバージョンは以下のコマンドで確認できる：

```
$ trivy -v
Version: 0.36.1
Vulnerability DB:
  Version: 2
  UpdatedAt: 2022-12-13 12:07:14.884952254 +0000 UTC
  NextUpdate: 2022-12-13 18:07:14.884951854 +0000 UTC
  DownloadedAt: 2022-12-13 17:09:28.866739 +0000 UTC
```

[図6-7で](#ch06.html#trivy-execution)わかるように、`Trivy`は、既知の脆弱性のコピーが中央データベースからダウンロードされたタイムスタンプを示す。`Trivy`はさまざまな形式でコンテナ・イメージをスキャンできる。サブコマンド`image` は、単純にイメージの名前とタグのスペルを期待するもので、この場合は`python:3.4-alpine` 。

![](assets/ckss_0607.png)

出力の中で最も重要な情報は、特定の脆弱性を含むライブラリ、その深刻度、問題を修正するために使用すべき最小バージョンである。発見された脆弱性のうち、深刻度が高いもの、あるいはクリティカルなものは、修正を検討すべきである。コンテナ・イメージを自分でコントロールできない場合は、新しいバージョンへのアップグレードを試みることができる。

# 概要

`Kubernetes`の主な目的は、スケーラブルかつセキュアな方法でコンテナ内のアプリケーションを実行することである。この章では、サイズが小さく、既知のセキュリティ脆弱性ができるだけ少ないコンテナイメージを確実に出荷するためのプロセス、ベストプラクティス、ツールについて見てきた。

コンテナ・イメージのフットプリントを最小限に抑えるための、最も効率的なテクニックをいくつかレビューした。まずは小さなベースイメージを選ぶことから始めよう。極端な話、シェルをまったく提供しないことで、サイズをさらに小さくすることもできる。`Docker`を使用している場合、目標達成に必要なコンパイラ、ランタイム、ビルドツールをバンドルすることなく、コンテナ内でアプリケーションをビルドできるマルチステージアプローチを活用できる。

`Pod`でコンテナイメージを消費するときは、信頼できるレジストリからのみコンテナイメージを引き出すようにする。社内でコンテナレジストリをセットアップし、コンテナイメージを提供することが望ましい。そうすれば、パブリックでインターネットからアクセス可能なレジストリにアクセスする必要がなくなり、潜在的なセキュリティリスクを排除できる。`OPA Gatekeeper` の助けを借りて、信頼できるコンテナレジストリのリストの使用を強制することができる。コンテナイメージの `SHA256` ハッシュを使用して期待される内容を検証することで、もう 1 つのセキュリティ対策を実施できる。

コンテナイメージのビルドとスキャンのプロセスは、CI/CDパイプラインに組み込むことができる。サードパーティのツールを使えば、デプロイ成果物をビルドする前でも、そのリソースファイルを解析・分析できる。我々は、`Dockerfile`用のHaskell Dockerfile Linterと`Kubernetes`マニフェスト用の`Kubesec`を調べた。セキュリティ面でカバーする必要があるもう1つのユースケースは、開発者であるあなたやあなたの会社の外部のエンティティによって構築された既存のコンテナイメージを消費することだ。`Kubernetes Pod`でコンテナイメージを実行する前に、その中身に脆弱性がないか必ずスキャンすること。`Trivy`は、コンテナ・イメージの脆弱性を特定し、レポートすることができるツールの1つで、コンテナでそのイメージを演算子する場合に、どのようなセキュリティ・リスクにさらされているかを知ることができる。

# 試験の要点

コンテナ・イメージのフットプリントを削減するテクニックに精通する。

: 

このセクションでは、コンテナ・イメージのビルド時にサイズを小さくするテクニックをいくつか紹介した。`Docker`のWebページに記載されているベストプラクティスを読み取り、サンプルのコンテナイメージに適用してみることをお勧めする。テクニックを適用する前と後で、プロデューサーのコンテナ・イメージのサイズを比較する。コンテナ・イメージを可能な限り小さなサイズに縮小し、同時に重要な機能の損失を回避することに挑戦してみるといい。

コンテナイメージがどこから解決できるかを管理するプロセスを歩く。

: 

`OPA Gatekeeper` は、ユーザがコンテナイメージを解決することを許可されるレジストリを定義する方法を提供する。制約テンプレートと制約のオブジェクトをセットアップし、メインアプリケーションコンテナ、init コンテナ、およびエフェメラルコンテナを定義する `Pod` に対して、規則が適切に適用されるかどうかを確認する。さらに、`Kubernetes`スペースで同様の機能を提供する他の製品にも目を向けてみよう。それらの製品の1つが[Kyverno](https://kyverno.io)だ。

コンテナイメージに署名し、ハッシュを使って検証する。

: 

コンテナイメージを作成したら、必ずダイジェストも作成する。コンテナイメージとダイジェストをレジストリに公開する。`Pod`定義でダイジェストを使用する方法を練習し、コンテナイメージをプルしたときの`Kubernetes`の振る舞いを検証する。

`ImagePolicyWebhook`アドミッションコントローラプラグインの設定方法を理解する。

: 

`ImagePolicyWebhook`のバックエンドを書くことは期待されていない。それは試験の範囲外であり、プログラミング言語の知識を必要とする。ただし、APIサーバの設定でプラグインを有効にする方法は理解しておく必要がある。実行中のバックエンドアプリケーションがなくても、ワークフローを練習することをお勧めする。

静的解析ツールが出す警告を修正する方法を知る。
