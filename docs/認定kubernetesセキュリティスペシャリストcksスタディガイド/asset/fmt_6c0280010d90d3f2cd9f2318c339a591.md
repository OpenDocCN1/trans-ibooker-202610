
次に、`plugins[].configuration.imagePolicy.kubeConfigFile`属性で参照されるファイルを作成する。このファイルの点は、外部サービスのHTTPS URLを指す。また、クライアント証明書と鍵ファイル、およびディスク上のCAファイルも定義する。[例6-10に](#ch06.html#image-policy-configuration-file)構成ファイルの内容を示す。

### 例6-10. イメージポリシー構成ファイル

```
apiVersion: v1
kind: Config
preferences: {}
clusters:
  - name: image-validation-webhook
    cluster:
      certificate-authority: /etc/kubernetes/admission-control/ca.crt
      server: https://image-validation-webhook:8080/validate 
contexts:
- context:
    cluster: image-validation-webhook
    user: api-server-client
  name: image-validation-webhook
current-context: image-validation-webhook
users:
  - name: api-server-client
    user:
      client-certificate: /etc/kubernetes/admission-control/api-server-client.crt
      client-key: /etc/kubernetes/admission-control/api-server-client.key
```

APIサーバーの`ImagePolicyWebhook`アドミッションコントローラプラグインを有効にし、アドミッションコントローラを構成ファイルに点す。これを実現するには、APIサーバの構成ファイル（通常は`/etc/kubernetes/manifests/kube-apiserver.yaml`に発見される）を編集する。

コマンドラインオプション`--enable-admission-plugins`を発見し、値`ImagePolicyWebhook`を既存のプラグインリストにカンマ区切りで追加する。コマンドラインオプション`--admission-control-config-file`がまだ存在しない場合はそれを指定し、値を`/etc/kubernetes/admission-control/image-policy-webhook-admission-configuration.yaml`に設定する。構成ファイルが新しいディレクトリに行くことを考えると、それをVolumeとして定義し、コンテナにマウントする必要がある。[例 6-11](#ch06.html#api-server-configuration-file)に、APIサーバーコンテナの関連オプションを示す。

  containers:

    - kube-apiserver

    volumeMounts:
    ...

      mountPath: /etc/kubernetes/admission-control

  ...
  - name: admission-control

      path: /etc/kubernetes/admission-control
      type: DirectoryOrCreate

# ワークロードの静的解析

本書を通して、DockerfileとKubernetesマニフェストのベストプラクティスについて話す。これらのファイルを手作業で検査し、望ましくない構成ファイルを発見し、手作業で修正することができる。このアプローチは多くの複雑な知識を必要とし、非常に面倒でエラーになりやすい。適切なツールを使って自動化された方法でワークロードファイルを分析する方が、はるかに便利で効率的だ。静的解析のための商用およびオープンソースのツールのリストは長い。このセクションでは、Haskell Dockerfile LinterとKubesecという2つの選択肢の機能を紹介する。

何百、何千ものワークロードファイルを処理しなければならない企業レベルでは、[図6-6に](#ch06.html#continuous-delivery-kubernetes-static-analysis)示すように、継続的デリバリパイプラインの助けを借りて処理することになる。

![](assets/ckss_0606.png)

関連する静的解析ツールは、コンテナイメージがビルドされ、レジストリにプッシュされ、Kubernetesクラスタにデプロイされる前であっても、パイプラインの初期段階で品質ゲートとして呼び出すことができる。継続的デリバリの原則、プラクティスについては、Jez Humble氏とDavid Farley氏による優れた書籍『[*Continuous Delivery*](https://oreil.ly/8CR5M)』（Addison-Wesley Professional）を参照されたい。

## Dockerファイルの分析にHadolintを使う

[`Haskell Dockerfile Linter`](https://oreil.ly/C9bvu)は、略して`hadolint`とも呼ばれ、Dockerfile用のリンターである。このツールはDockerドキュメント・ページにリストされている[ベスト・プラクティスに基づいて](https://oreil.ly/Fwksr)Dockerfileを検査する。[例6-12は](#ch06.html#unoptimized-dockerfile)、Goベースのアプリケーションを実行するコンテナイメージを構築するための、最適化されていないDockerfileを示している。

### 例6-12. 最適化されていないDockerファイル

```
FROM golang
COPY main.go .
RUN go build main.go
CMD ["./main"]
```

`Haskell Dockerfile Linter`は、`hadolint`の実行ファイルをディスク上のDockerfileに向けることができるモードをサポートしている。分析によって発見された警告メッセージを含む、この後のコマンド実行を見ることができる：

```
$ hadolint Dockerfile
Dockerfile:1 DL3006 warning: Always tag the version of an image explicitly
Dockerfile:2 DL3045 warning: `COPY` to a relative destination without \
`WORKDIR` set.
```

コマンドの出力は、ベース・イメージにタグを代入することを示唆している。既存のDockerfileは`latest`タグを引き、最新のGoコンテナ・イメージに解決する。このやり方は、Goランタイム・バージョンとアプリケーション・コードの間に非互換性をもたらす可能性がある。リソースをコピーする作業ディレクトリを定義することで、オペレーティングシステム固有のディレクトリやファイルと、アプリケーション固有のディレクトリやファイルを分けて管理することができる。[例6-13は](#ch06.html#optimized-dockerfile)、`Haskell Dockerfile Linter`が発見した警告メッセージを修正している。

### 例6-13. 最適化されたDockerファイル

```
FROM golang:1.19.4-alpine
WORKDIR /app
COPY main.go .
RUN go build main.go
CMD ["./main"]
```

変更されたDockerfileに対する別の実行は成功した終了コードにつながり、追加の警告メッセージは表示されない：

```
$ hadolint Dockerfile
```

Dockerfileは現在、`hadorint`が認識しているベストプラクティスに従っている。

## Kubernetesマニフェストの分析にKubesecを使う

[`Kubesec`](https://kubesec.io)はKubernetesマニフェストを分析するためのツールである。バイナリ、Dockerコンテナ、アドミッションコントローラプラグイン、さらには`kubectl`のプラグインとして実行できる。その使い方を実証するために、[例6-](#ch06.html#pod-yaml-manifest-initial-security-settings)14に示すYAMLマニフェストファイル`pod-initial-kubesec-test.yaml`を出発点としてセットアップする。

### 例 6-14. 初期セキュリティ設定を使用したPod YAMLマニフェスト

```
apiVersion: v1
kind: Pod
metadata:
  name: kubesec-demo
spec:
  containers:
  - name: kubesec-demo
    image: gcr.io/google-samples/node-hello:1.0
    securityContext:
      readOnlyRootFilesystem: true
```

Podのコンフィギュレーションを確認すると、前の章の内容に基づいて改善すべき点がすでにいくつか提案されているかもしれない。`Kubesec`が何を推奨しようとしているのか見てみよう。

`Kubesec`を起動する最も簡単な方法は、Dockerの助けを借りてコンテナ内でロジックを実行することだ。以下のコマンドは、YAMLマニフェストの内容を標準入力ストリームにフィードする。JSONで形式化された結果は、スコアをレンダリングし、結果の人間が読めるメッセージを提供し、変更すべき点をアドバイスする：
