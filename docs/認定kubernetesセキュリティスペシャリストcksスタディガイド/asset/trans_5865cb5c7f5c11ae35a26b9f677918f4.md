

接下来，让我们来看一下多阶段方法。多阶段 `Dockerfile` 中至少定义了两个阶段。[例6-](#ch06.html#dockerfile-multi-stage)2 中指定了别名为 ``build`` 的阶段，并执行了测试并构建了二进制文件。第二个阶段将阶段 ``build`` 中生成的二进制文件复制到专用的目录中。但是，使用 ``alpine`` 基础镜像进行运行。执行 ``docker build`` 命令时，阶段 ``build`` 不会包含在最终的容器镜像中。

### 例6-2. 作为多阶段 Dockerfile 的一部分构建并测试 Go 程序。

```
FROM golang:1.19.4-alpine AS build 
RUN apk add --no-cache git
WORKDIR /tmp/go-sample-app
COPY go.mod .
COPY go.sum .
RUN go mod download
COPY . .

RUN CGO_ENABLED=0 go test -v 
RUN go build -o ./out/go-sample-app . 

FROM alpine:3.17.0 
RUN apk add ca-certificates
COPY --from=build /tmp/go-sample-app/out/go-sample-app /app/go-sample-app 
CMD ["/app/go-sample-app"]
```

## 减少层数

所有 `Dockerfile` 都由按顺序排列的指令列表构成。只有部分指令会为创建的容器镜像创建只读层。这些指令是 ``FROM`` 、 ``COPY`` 、 ``RUN`` 、 ``CMD`` 。所有其他指令都不会创建层，因为它们会创建临时中间镜像。随着向容器镜像添加的层越多，构建执行时间越慢，或容器镜像大小越大。因此，为了最小化容器镜像的占用空间，需要谨慎使用 `Dockerfile` 中的指令。

连续执行多个命令是很常见的。如 [例6-](#ch06.html#dockerfile-multiple-run-instructions)3 所示，可以使用 ``RUN`` 指令列表在单独的行中定义这些命令。

### 例6-3. 指定多个 ``RUN`` 指令的 Dockerfile

```
FROM ubuntu:22.10
RUN apt-get update -y
RUN apt-get upgrade -y
RUN apt-get install -y curl
```

每个 ``RUN`` 指令都会创建层，可能增加容器镜像的大小。将它们用 ``&&`` 串联起来以确保仅生成单个层会更有效。[例6-4是](#ch06.html#dockerfile-combined-run-instructions)该优化技术的示例。

### 例6-4. 指定多个 ``RUN`` 指令的 Dockerfile

```
FROM ubuntu:22.10
RUN apt-get update -y && apt-get upgrade -y && apt-get install -y curl
```

# 确保供应链

供应链自动化了容器镜像的生产者以及在执行环境（本例中为 Kubernetes）中操作它的过程。我们已经提到了一些可以集成到供应链中以支持容器镜像优化的工具。本节将介绍针对安全方面的实践。详情请参阅 Liz Rice 所著的『*Container Security*』（O'Reilly）。

## 为容器镜像签名

在将容器镜像推送到容器注册表之前，可以对其进行签名。使用 ``docker trust sign`` 命令进行签名。命令会为容器镜像签名，即添加所谓的镜像摘要。镜像摘要是从容器镜像的内容派生出来的，通常以 SHA256 形式表示。在消费容器镜像时，Kubernetes 会将镜像摘要与镜像内容进行比较，以确认其未被篡改。

## 场景 攻击者向容器镜像注入恶意代码

验证镜像摘要的 Kubernetes 组件是 `kubelet`。如果将 [镜像拉取策略](https://oreil.ly/0wSjy) 设置为 ``Always`` ，``kubelet`` 会在每次从容器注册表查询镜像摘要，即使容器镜像之前已下载并验证过。

攻击者可以如 [图6-](#ch06.html#no-image-digest-validation-attacker)2 所示，修改现有容器镜像的内容，注入恶意代码，并上传到具有相同标签的容器注册表。在容器内运行的恶意方可能会将机密信息发送到攻击者可访问的第三方服务器。

# 镜像校验和验证不是自动的

镜像摘要的验证是 Kubernetes 的可选功能。在定义 Pod 时，应为所有容器镜像明确指定镜像摘要。

## 验证容器镜像

在 Kubernetes 中，可以在容器的规范中添加 SHA256 镜像摘要。例如，这可以通过 ``spec.containers[].image`` 属性实现。镜像摘要通常在容器注册表中可用。例如，[图6-3是](#ch06.html#dockerhub-alpine-image-digest) [Docker Hub 上](https://oreil.ly/ZAV_H) 的容器镜像 [``alpine:3.17.0``](https://oreil.ly/ZAV_H) 的镜像摘要。在此示例中，镜像摘要为 ``sha256:c0d488a800e4127c334ad20d61d7bc21b4097540327217dfab52262adc02380c`` 。

![](assets/ckss_0603.png)

让我们看看镜像摘要的运行方式。[例6-5中](#ch06.html#container-valid-image-digest)，而不是使用标签，通过附加镜像摘要来指定容器镜像。

### 例6-5. 使用有效容器镜像摘要的 Pod

```
apiVersion: v1
kind: Pod
metadata:
  name: alpine-valid
spec:
  containers:
  - name: alpine
    image: alpine@sha256:c0d488a800e4127c334ad20d61d7bc21b40 \
           97540327217dfab52262adc02380c
    command: ["/bin/sh"]
    args: ["-c", "while true; do echo hello; sleep 10; done"]
```

Pod 的创建按预期工作。镜像摘要得到验证，容器过渡到 “Running” 状态：

```
$ kubectl apply -f pod-valid-image-digest.yaml
pod/alpine-valid created
$ kubectl get pod alpine-valid
NAME           READY   STATUS    RESTARTS   AGE
alpine-valid   1/1     Running   0          6s
```

[例6-](#ch06.html#container-invalid-image-digest)6 显示了相同的 Pod 定义，但镜像摘要已更改为与容器镜像内容不匹配。

### 例 6-6. 使用无效容器镜像摘要的 Pod

```
apiVersion: v1
kind: Pod
metadata:
  name: alpine-invalid
spec:
```

## 使用公开镜像注册表

容器运行时引擎在每次创建 Pod 时，如果声明的容器镜像在本地不可用，就会从容器注册表下载。该运行时的行为可通过 [镜像拉取策略](https://oreil.ly/ZBMnH) 进一步微调。

镜像名称的前缀声明了注册表的域名。例如，``gcr.io/google-containers/debian-base:v1.0.1`` 指向 [Google Cloud 容器注册表](https://oreil.ly/QFxfY) 的容器镜像 ``google-containers/debian-base:v1.0.1`` ，表示为 ``gcr.io`` 。如果在容器镜像声明中省略域名，容器运行时会使用 [Docker Hub 容器注册表](https://hub.docker.com) 的 ``docker.io`` 。

## 场景 攻击者上传恶意容器镜像

从公开容器注册表解析容器镜像很方便，但并非没有风险。只要登录这些容器注册表，任何人都可以上传新镜像。消费容器镜像通常甚至不需要账户。

如 [图 6-4](#ch06.html#public-registries-attacker) 所示，攻击者可以使用被盗的凭证将包含恶意代码的容器镜像上传到公开注册表。引用该注册表的容器将自动执行恶意代码。
