# Chapter 1. Introduction to Model Performance Management and Explainability

在互联网兴起之前，由于分发和访问软件的性质，软件开发生命周期更长。还记得过去必须购买 CD 或 DVD 并插入电脑来安装软件的日子吗？生命周期是瀑布式的，以前推送补丁或更新给消费者需要数月（如果不是数年）的时间，而这些在今天的敏捷世界中是理所当然的。

互联网带来了更互联的软件系统后，监控系统之间以及人与系统之间的通信和交互变得越来越困难。这导致了两种框架的兴起，它们协同工作以实现快速迭代同时保持高性能系统：开发运营（DevOps）和应用性能管理（APM）。随着系统开始变得更智能，我们看到了机器学习（ML）和人工智能（AI）系统的兴起。但随着这项新技术而来的是许多风险和问题，如果我们让这些系统以无法解释或不可理解的方式行为会发生什么。

这些系统的快速出现也导致了针对机器学习和数据专门的新实践的发展。对于传统软件，很容易测试它是否正常工作：通常有一组离散的可能输入和输出。然而，对于复杂的 ML 模型和 AI 系统，很难完全监控和观察内部发生了什么。一些模型可能依赖数千甚至数百万个输入来做出决策。这就是为什么我们需要一个以数据为中心的新框架，旨在生产高质量的模型和系统，同时与 DevOps 和 MLOps 的快速迭代目标保持一致。

这样的框架将类似于 APM，但适用于 ML 模型并考虑这些模型与传统应用程序之间的细微差别和差异。该框架可以称为 *模型性能管理*（MPM）。模型性能不仅依赖于指标，还依赖于当某事最终出错时模型能够被解释得多好。这就是所谓的 *模型可解释性*。正如 APM 旨在为运维团队提供对整个应用程序开发过程的更多可见性，MPM 允许这些团队在模型被训练、验证和部署时对其进行监控。在本章中，我们将在深入探讨 ML 生命周期中涉及的细微差别和阶段以及 MPM 和模型可解释性如何融入其中之前，讨论建立这样一个框架的必要性。

## DevOps and Application Performance Management

让我们退一步谈谈 DevOps 和 APM 是为什么出现以及它们是什么。

## DevOps

DevOps，或开发运营，是一个用于描述用于实现快速迭代和高速度的文化实践、业务流程和工具链组合的术语。目标是快速创新并在问题出现时尽快发现问题。市面上有许多 DevOps 框架和工具，每个都有其优缺点，但核心是统一实践的整体哲学，在某种程度上在公司和领域之间统一。

DevOps 的一个原则是系统可观测性，进而是监控。监控是通过使用指标和日志实现的，使我们能够跟踪应用程序内部发生的情况。有工具可以做到



监控，并且有提供完整可观测性的工具，但没有统一的框架旨在实现对应用系统的完全可见性。因此，DevOps 通常会与 APM 结合使用。

## 应用性能管理

APM 提供了一个框架，用于通过衡量有关应用程序的指标来监控和管理软件应用程序性能，其目标是在问题出现时甚至之前就捕获问题。使用的确切指标可能有所不同，但随着应用程序越来越多地迁移到云，确保 API 保持高效并满足用户实时期望变得越来越复杂。我们需要确保我们的应用程序在需要时始终可用，并且能够在负载增加或减少时处理而不损失性能。

您的业务可能为客户提供 API，或为员工使用的应用程序提供内部 API。您也可能为自己的业务需求使用外部供应商的 API。无论细节如何，您都需要确保使用这些 API 的应用程序具有可接受的响应性和流畅性，以便用户不必等待数分钟页面加载。这归结为 API 对用户请求响应的速度。如果 API 突然变慢，APM 框架会自动提醒负责团队，以便他们可以调查、找到根本原因并解决它。完整的可见性使团队能够在问题导致业务收入损失之前快速识别和修复问题。

APM 的好处是：

### 广泛的可见性

在今天我们拥有的 DevOps 工具兴起之前，监控基础设施在功能上有限且难以使用。软件和硬件是分开监控的，造成了脱节的体验。APM 在整个部署周期中引入了广泛的可见性，并在一个统一的框架下统一。

### 增强的可观测性

当监控触发警报时，团队会通过修复来解决问题。然而，定位源可能很繁琐且重复，尤其是在警报实际上是预期而不是意外时。超越可见性，APM 提供了额外的根本原因调试支持，称为 *可观测性*。例如，通过可观测性，应用程序性能下降可能归因于集群中的节点无法处理请求，而不是代码本身的问题。

### 明确的责任归属

APM 使 DevOps 工程师能够通过可观测性和明确的责任归属来管理生产代码的端到端生命周期。责任归属的清晰度允许指定专门的人员，以便快速响应问题。

### 迭代速度

最终，流程的简化、明确的利益相关者和广泛可见性的监控工具的可用性使您的团队能够快速部署、识别和修复问题，从而减少迭代之间的时间并最大化每次迭代的影响。

## 应用性能指标

通常用于衡量应用性能的指标有：

### API 延迟

系统执行操作所需的时间，通常以毫秒（ms）为单位衡量

### 每秒查询数（QPS）

API 每秒被调用的次数

这些指标对于应用程序团队监控其应用程序能够处理的规模和负载至关重要。它们也是任何自动警报或基于触发的事件的基础，例如系统故障转移，并且可以馈入自动扩展管理解决方案，例如集群调整大小或节点池调整大小（一种管理 API 用于处理其请求所使用的计算机数量的方式）。随着云计算变得越来越普及，公司正在将许多应用程序和工作负载迁移到云中，使得监控这些指标变得越来越重要。

可能有一天——比如黑色星期五——您的系统会被请求淹没，导致应用程序崩溃。通过使用 APM 框架模拟此类流量并在事前衡量系统在任何给定 QPS 下的延迟，您的团队可以捕获任何问题并提前设计以防止任何故障或性能下降。这被称为负载测试，可以帮助扩展系统。

实时流数据、历史回放和出色的可视化工具是当今 APM 解决方案的标准部分。流行的 APM 产品不仅提供对简单统计数据的洞察，而且还具有可用于业务的 API 和组件集成。

## MLOps 的兴起

随着应用程序开始采用更先进的决策算法和模型，确保高性能所需的管理和工具变得更加复杂。对于以代码为中心的应用程序，测试它们是否按预期工作相对简单。但 ML 和 AI 模型是以数据为中心的，这增加了传统 DevOps 团队不习惯处理的许多挑战（例如确保数据完整性和有效性）。这就是 MLOps 发挥作用的地方。

机器学习运维，或简称 MLOps，是围绕数据及其使用、数据科学和工具的文化实践的融合，旨在快速迭代模型版本或快速运行实验以测试不同的假设。MLOps 不独立于 DevOps 存在，它们需要携手合作以确保所有方面都得到覆盖，并且任何问题都可以用最少的团队精力得到解决和解决。我们将在本报告的第 3 章介绍 ML 生命周期和一些 ML 方面，但现在让我们看看 MLOps 与 DevOps 的比较。

## MLOps 与 DevOps 的比较

MLOps 和 DevOps 都源于相同的根基，并专注于快速迭代和持续改进。没有基于这些哲学的框架，团队将很难建立高效的周期，并且会产生很少的有益成果。MLOps 和 DevOps 都建议在系统发布前进行验证和测试。然而，它们在可观测性和监控方面存在不足。这就是 APM 在 DevOps 中大放异彩的地方，因为它提供了对应用程序的完全可见性，使团队能够在问题变得明显时立即找到根本原因。

ML/AI 模型本质上是黑盒；数据科学家并不总是知道模型为何以及如何工作。但这种缺乏可见性无法通过一刀切的解决方案解决，因为每个模型都是独特的。因此，您需要执行大量规划和工作来正确监控模型所需的测试和验证。

## 模型性能指标

有许多不同类型的机器学习（ML）模型，每个模型都有其自己的细微差别和需要跟踪的指标。ML 模型高度依赖于数据，并且依赖于输入数据的质量和一致性。以下是当今 ML 模型复杂性的一些来源示例：

- *多功能性*

ML 服务于广泛的用例——反洗钱、职位匹配、临床诊断和行星监视，仅举几例。

### 架构

ML 算法可以采用多种形式，解释起来更容易或更难；它们范围从简单的逻辑回归和决策树到用于深度学习的先进神经网络。

### 多样性

ML 模型有许多种类（表格、时间序列、文本、图像、视频和音频），并且这些模态通常在某些领域中混合，进一步增加了跟踪模型性能复杂性。

### 数据量

云计算的兴起使团队能够并行使用更多数据训练多个模型，这使得更难跟踪训练数据。

团队必须能够监控数据分布的突然变化，这可能导致偏差。其他问题可能源于模型训练数据过少或过多，导致性能不佳。跟踪可能影响模型性能的所有参数比跟踪代码库中的代码更改要困难得多。

通常用于跟踪模型性能的指标有：

### 准确率

实际正确的预测占总预测的百分比

### 精确率

正确识别的阳性案例占阳性案例的百分比

### 负预测值

正确识别的阴性案例占阴性案例的百分比





### 灵敏度/召回率

正确识别的实际阳性病例的百分比

### 特异性

正确识别的实际阴性病例的比例

使用这些指标中的一些或全部，可以从离线跟踪模型到在线，并将其性能与模拟基线进行比较。由于不同的模型具有不同类型的数据和输出，因此每个模型都会使用这些指标的不同形式。一种常用的可视化工具是混淆矩阵。图 1-1 使用二元分类的矩阵说明了这一概念（模型仅预测真或假）。如果模型具有更多输出类别，则该矩阵可以扩展到任意数量的行和列，以分析所有表现不佳的类别。

使用该矩阵，我们可以看到：

- Accuracy = TP + TN / (TP + TN + FP + FN)
- Precision = TP / (TP + FP)
- Recall = TP / (TP + FN)

尽管这些指标可以很好地衡量模型的性能，但在模型部署后，通常无法确定预测的“真实”值。在生产环境中，模型通常根据其试图实现业务结果来衡量。例如，面向定向邮件的营销模型可能会通过有多少封邮件导致购买来衡量。在这种情况下，模型不是按准确率衡量，而是按其能够实现的业务结果衡量。我们将在后面的章节中更详细地介绍所有这些指标。

## 机器学习开发流程

开发机器学习模型通常涉及多个步骤，不同利益相关者共同工作，并在工作流程中不断迭代数据和模型。作为第一步，数据科学家定义业务问题并将其转化为机器学习模型，在收集必要数据后进行。

接下来，模型验证者评估模型以确保其按预期工作并符合公司标准和政府法规。模型验证后，由机器学习工程师将其部署到生产环境并开始在业务应用中进行预测。一旦投入生产，持续监控、测试和调试的过程就开始了，通常由 DevOps 工程师、数据工程师、ML 工程师和数据科学家团队管理。最后，团队实时或批量分析模型的输出以检查其性能、修复错误并收集见解以训练性能更好的模型。

利益相关者因公司而异，因为该领域仍新且在发展中，但迭代 ML 模型的核心循环保持不变。简单来说，MLOps 就是将机器学习模型操作化的这种持续反馈驱动循环。为了关闭此循环，MLOps 需要一个专用框架，可作为 ML 工作流程核心的集中控制系统。该框架在所有阶段跟踪和监控模型的性能，即模型性能管理。

## 模型性能管理

与应用性能相比，管理和监督模型性能需要处理更多数据，并对所涉及的领域有更深入的理解。如果没有统一的框架或工具集，数据科学和机器学习团队可能很难大规模部署模型并保持高性能。这就是
MPM 的用武之地。MPM 是一个管理模型在其生命周期内性能的框架，并确保团队对 ML 生命周期每个阶段都有清晰的可见性。图 1-2 显示了该生命周期的概述。MPM 提供的反馈循环允许持续改进模型。

MPM 反馈循环通过以下方式增强生命周期的每个步骤：

- 在 *training* 模型并选择用于训练模型的功能或数据时，您的团队可以通过数据中代表不足或过度代表的群体发现隐藏的偏差。偏差也可能由于输入数据的变化而发生，称为 *data drift*。
- 模型训练后，MPM 框架可以 *validate* 并将任何性能估计记录到数据库中以供跟踪和审计。此信息可用于为业务、合规和 AI 伦理利益相关者生成摘要报告。
- 当新模型准备好 *deploy* 时，可以使用相同的数据将其与以前的版本进行比较，以确保新模型优于旧模型。这通常称为 champion/challenger 测试和验证。
- 一旦模型发布到生产环境，MPM 框架可作为 *monitoring* 工具来观察模型性能、漂移、偏差，并在出现错误条件时发出警报。MPM 框架还可用于同时衡量两个模型的性能，称为 A/B 或 champion/challenger 测试。
- 由于 MPM 是一个反馈循环，任何从错误、性能问题或 *analyses* 中产生的见解都可用于提高未来模型的性能。

需要注意的是，MPM 框架不会取代现有的 ML 训练、部署和服务系统。相反，它位于 ML 工作流程的核心，捕获所有模型工件、训练和生产数据以及模型性能指标。

由于 ML 空间内的复杂性增加，即使他们已拥有 MLOps 框架，团队也经常面临以下挑战：

## 性能不一致

由于 ML 模型是在历史数据上训练的，因此模型在离线（在暂存环境中）的表现与在线（在生产环境中，使用以前未见过的数据）的表现之间可能存在很大差异。

## 缺乏控制

机器学习通常是黑盒。这使得很难理解模型如何以及为何从给定数据中得出输出以推动性能改进。

## 偏差放大

模型会放大其训练数据的偏差，这使得识别潜在的偏差来源非常重要。此外，由于缺乏可见性，很难确定模型在测试数据集或真实数据上的运行方式是否与训练数据上的运行方式相同。未能识别历史数据和真实数据集之间的差异或不平衡可能会放大隐藏的偏差，可能违反公司政策并导致客户不信任。

## 缺乏可调试性

无法调试复杂模型可能导致信任度低和模型性能下降。它还阻止这些模型在金融和医疗保健等受监管行业中使用。

## 反馈循环

模型退化经常推动构建更好的模型以代表当前的业务现实的需求——但形成反馈循环的操作见解今天却缺失了。

## 难以迭代改进性能

跟踪和比较生产版本中模型行为和性能的挑战使得很难理解性能如何随着时间的推移而改进。

## 用于全面覆盖的可解释性 MPM

准确率约为 80–90% 的高性能 ML 模型仍可能存在隐藏的偏差和数据中代表不足的群体。为了检测数据中的隐藏偏差，团队需要分析使用的特征以及这些特征中数据的分布。这应在特征选择和模型训练阶段进行，通常会导致这些问题在早期被发现。然而，随着时间的推移，模型被设置为自动重新训练，偏差可能会开始渗入，因为某些数据群体变得更普遍或不那么普遍。为了应对这种情况，MPM 框架需要监控数据分布与基线，以捕捉可能导致偏差的任何出现的漂移。

漂移可能由于用于进行预测的数据发生变化或用于训练模型的数据发生变化而发生。在任何一种情况下，MPM 都需要跟踪数据分布并考虑模型期望的内容与实际看到的内容之间的变化。任何超出正常范围的偏差都应被标记以进行调查和调试。第 2 章将更详细地介绍可解释性并讨论可解释人工智能的哲学。

## 使用 MPM 框架的好处

如前所述，MPM 框架旨在为机器学习生命周期带来可见性。它解决了 MLOps 中的几个运营挑战，例如性能不一致、控制力丧失和缺乏反馈循环。但这对企业意味着什么？让我们来看看 MPM 框架提供的一些关键业务优势。

## MPM 在模型上线前验证模型

在部署模型之前，验证模型至关重要，无论是否法律要求。这确保了在发布时，您拥有高性能、经过充分测试且稳健的模型。由于模型将围绕



业务假设或问题，验证过程涉及与业务利益相关者核实，一旦部署后它是否解决了预期的问题，并且不会损害业务的其他方面。这要求模型以人类可理解的术语进行解释。为了回答诸如“模型是如何做出预测的？”和“是否存在任何偏差？”这样的问题，模型必须经过验证。验证通常可以使用诸如交叉验证等技术来评估模型行为的变化。如果模型通过验证，它将被部署，业务就可以开始使用机器学习，并对机器学习模型的影响有清晰的理解。然而，这只是机器学习反馈循环的开始。

## MPM 持续监控生产环境中的模型性能

与传统程序相比，机器学习模型是独特的软件实体，因为它们是使用历史示例针对可重复任务的高性能进行训练的。因此，随着它们作为输入接收到的真实世界数据发生变化，其性能会随着时间推移而波动。没有公司能确切知道模型部署后会表现如何。因此，成功的机器学习部署需要持续监控，以持续重新评估模型对业务的价值和性能。

## MPM 主动解决模型偏差

偏差在世界上是普遍存在的。由于机器学习模型从有限的训练数据中捕捉关系，因此它们很可能传播或放大现有的数据偏差，甚至可能引入新的偏差。关于信贷借贷、招聘和医疗保健人工智能算法中 alleged 偏差的故事证明了这些风险。因此，公司一直在花费额外精力来衡量和防范偏差，通过摄取或推断受保护属性。但模型在发布后也可能变得有偏差。

由于偏差可能造成严重的业务损害，尤其是在高度受监管的环境中，实时识别偏差可以让公司避免昂贵的处罚，例如财务罚款或消费者愤怒。与性能指标一样，数据科学家通常需要离线计算偏差指标，这增加了出错的风险（因为他们没有使用生产数据）。此外，偏差问题可能与其他问题相关；例如，男性求职者数量的激增可能导致求职者匹配中的偏差。孤立地调查偏差原因可能会导致数据科学家忽视此类相关性，导致他们不必要地花费时间调试本可以轻松纠正的问题。

## MPM 检测训练/服务偏差

用于在在线和离线环境中训练和服务模型的特征可能不同。当这种情况发生时，模型的行为会不同，需要进行调试。通过将训练数据和预测日志保存在一个地方，MPM 使开发人员能够检测这些偏差。

## MPM 解释过去的预测

想象一家银行正在使用机器学习来批准贷款，而一位客户对某笔贷款被拒提出投诉。由于 MPM 从训练到服务跟踪模型的行为，风险运营官可以回溯时间重现预测以及解释（这被称为“预测时间旅行”）。
