## Chapter 1. Software Development Life Cycles





软件开发作为一种智力活动所存在的问题是，你不能像管理其他项目那样管理开发项目。对于建造房屋这样的项目，增加更多的人手（只要他们能操作施工工具）就可以缩短完成房屋所需的整体时间。在软件开发中，人与完成时间之间的关系要复杂得多。

在本章中，我们将快速回顾软件开发的起源。我们将考察该流程的好处以及任何方法论必须包含的基本阶段。然后我们将更深入地探讨几种最流行的方法论的优缺点。

### 流程的价值

为什么要费心使用方法论？自 1960 年代开始进行严肃的软件开发项目以来，开发人员和项目经理学到了很多。他们创建了各种方法论来帮助更快、更高效地完成大规模软件项目（甚至小型项目），并提高质量。有时新的方法论源于开发人员希望解决在使用另一种方法论时遇到的问题的愿望。

不同的方法论有不同的目标和不同的问题。一种对一个组织来说非常有效的方法论可能对另一个组织来说是不合适的。有一点是明确的：拥有方法论至关重要。

#### 可重复性和一致性

任何流程或方法论的一个目标都是可重复性：你知道如何再次做到这一点。当你建造的东西要出售时，你想要一致性。你希望知道你已经尽最大努力去做，并且以与所有其他事物相同的方式去做，没有变化。可变性会导致缺陷，这当然会使销售产品变得更加困难。在软件中，缺陷就是 bug，没有人想发布有 bug 的代码。一致性是帮助限制已发布软件中 bug 数量的一种方式。

#### 流程改进

有了流程，你就可以评估自己是如何做某事的，并从其效果如何中学习。你可以不断改进流程以消除缺陷。（有些方法论强调减少缺陷，例如 `Six Sigma`。）

关注流程改进是成熟组织的标志之一。在卡内基梅隆大学开发的成熟度模型 `Capability Maturity Model Integration` 中，组织可以达到的最高成熟度级别是 `Optimizing`。这就是组织已经制定了定期遵循的流程并努力学习经验教训并随着时间的推移改进该流程的地方。

对于单个项目或甚至非常小的项目，可能没有太多关注可重复性、一致性和流程改进，但商业组织应该关注这些。没有合适的方法论来帮助组织关注这些因素（或更糟，没有任何方法论），产品的质量很可能很差或不一致。

### DevOps

历史上，软件开发方法论存在很多问题。像 `waterfall` 这样长期存在的方法论会导致开发时间长且沟通有限。这可能导致成本高和质量低，这不是软件开发流程的良好结果。

沟通问题在软件开发中并非新鲜事。随着公司转向 Web 应用程序和基于 Web 的部署，运维团队已成为比过去更大的利益相关者。有很多很棒的漫画和图形突出了 `DevOps` 流行之前软件开发是如何进行的。这些插图通常涉及一侧的开发人员将软件项目扔过墙，扔到另一侧运维人员站立的地方。没有沟通，甚至可能没有多少文档。

`DevOps` 与其说是一种方法论，不如说是一种文化。`DevOps` 的文化旨在更紧密地整合运维人员与开发人员。运维人员应在需求收集过程中就参与其中，以确保他们能够在应用程序开发完成后部署和管理该应用程序。

`DevOps` 非常注重自动化和测试。`DevOps` 的目标是通过尽可能自动化软件开发、构建和部署的各个方面来提高软件开发流程的整体质量。许多 `DevOps` 组织使用一种称为 `development pipeline` 的东西，这意味着当软件被检入 `code repository` 时，表示开发人员已完成一项任务并且他们希望将文件返回到存储库以便其他人使用时，自动化流程会开始执行测试、构建软件，然后执行更多测试。这种方法意味着你可以在部署之前确保测试已完成，而不是在测试并行进行的同时匆忙部署。

这并不意味着所有测试都可以自动化。在某些情况下，测试团队仍需要在部署进行时执行测试，但由于开发周期短，任何发现的 bug 都可以快速解决并快速投入生产。

所有这些自动化意味着流程可以完全测试。当你转向自动化时，你有另一件可以测试的软件，因为自动化是一个程序或脚本。这消除了人为出错的可能性。自动化程序或脚本可以在使用之前完全测试，以确保它们完全按照预期执行。任何更改也可以在投入生产之前进行类似测试。

### Kubernetes 和软件开发生命周期

在开发软件时，无论是完整的应用程序还是可供基于 Web 或移动前端使用的应用程序编程接口，都需要有人考虑整个应用程序生命周期——不仅仅是开发人员构建软件的部分。`Kubernetes` 可以帮助支持这些工作。在需求收集阶段，团队可能会发现实现项目整体目标的最佳方式是实施 `Kubernetes`。这不仅可能解决一些需求，还会引入其他需求。应用程序通常不会一开始就完全成形，而是通过对需求的迭代视图形成应用程序应有的图景。一个需求产生另一个需求，依此类推，直到整个应用程序或项目的视图完成。

当开发项目开始时，会有一个需求阶段，在此期间会做出关于项目方向的许多决定。这就是 `Kubernetes` 发挥作用的地方，因为最好在前期决定选择 `Kubernetes` 作为编排平台。这将指导一些开发工作，因为 `Kubernetes` 是为容器设计的。开发人员和运维人员从一开始就知道他们将使用虚拟化应用程序环境。这也意味着需要额外的开发，或者至少需要大量的沟通，因为运维团队将负责部署项目，这意味着他们可能还负责开发将通过 `Kubernetes` 管理的编排脚本和配置。这就是 `DevOps` 和 `DevSecOps` 作为实践派上用场的地方，我们将在 Chapter 3 中更详细地介绍。





历史上，测试的一个问题是测试环境与开发环境看起来不同。开发人员在自己的系统上编写软件，这些系统的配置与测试系统完全不同。在 Kubernetes 环境中，测试容器化应用程序可以变得容易得多，因为 Kubernetes 会帮助确保每次应用程序空间的每个实例看起来都一样。这意味着测试团队可以在与开发团队完全相同的环境中工作。当你从单个系统抽象出来并将应用程序虚拟化时，你就能获得应用程序在隔离空间中运行的好处，该空间仅包含该应用程序正常运行所需的先决条件和依赖项。

运营团队花费了数年时间试图让自己的生活更轻松，首先是通过编写脚本并创建框架来支持大量物理系统，然后后来对虚拟机以及完整而复杂的基于 Web 的应用程序所需的所有网络和其他支持基础设施做同样的事情。在部署和部署后阶段，Kubernetes 通过提供一个管理框架来支持运营团队，该框架负责团队过去由于缺乏知识或资源而必须手动执行的所有编排工作，包括计算资源、存储和网络的配置，等等。

决定使用 Kubernetes 可以对从需求到部署和应用程序运行的整个应用程序开发产生重大积极影响。不过，确保所有团队成员都了解像 Kubernetes 这样的工具的使用带来的好处和要求是很重要的。

### Summary

软件开发是一项复杂的任务，除了软件开发人员本身之外，还有很多人参与其中。仅仅编写代码就是一项复杂的事业。拥有一种开发方法论有助于确保所开发的软件是企业、用户或客户所期望的。始终如一，确定问题后再确定解决方案。

多年来出现了许多不同的开发方法论。在某些情况下，开发方法论与其说是别的，不如说是一种哲学或文化。这在 DevOps 方面尤其如此。DevOps 与现代软件开发实践非常契合，尽管由于对沟通的强烈关注，实现起来可能具有挑战性。对于习惯于墙壁或孤岛限制不同团队的根深蒂固的开发团队来说，这可能是一个需要克服的挑战。将项目管理、开发、测试和运营围绕 Kubernetes 等单一平台进行聚焦可以帮助指导团队之间的必要沟通，因为每个人都在朝着同一个方向在同一技术上工作，而这在开发团队中并不总是如此。

此外，DevOps 与 Kubernetes 非常契合，而 Kubernetes 需要整个 SDLC 中所有团队成员的支持。在生命周期中的需求/设计阶段决定使用 Kubernetes 等工具可能会引入额外的需求，但也可以为开发人员和测试人员等其他团队成员提供很多答案，这可能会让生活更轻松并有助于提高应用程序的整体质量。

除了这个预告之外，我们将在本书的剩余部分研究 DevOps 中其他有助于高质量应用程序开发的实践。
