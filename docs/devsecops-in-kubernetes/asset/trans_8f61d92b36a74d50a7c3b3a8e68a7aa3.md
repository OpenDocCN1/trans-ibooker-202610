

历史上，测试的一个问题是测试环境与开发环境看起来不同。开发人员在自己的系统上编写软件，这些系统的配置与测试系统完全不同。在 Kubernetes 环境中，测试容器化应用程序可以变得容易得多，因为 Kubernetes 会帮助确保每次应用程序空间的每个实例看起来都一样。这意味着测试团队可以在与开发团队完全相同的环境中工作。当你从单个系统抽象出来并将应用程序虚拟化时，你就能获得应用程序在隔离空间中运行的好处，该空间仅包含该应用程序正常运行所需的先决条件和依赖项。

运营团队花费了数年时间试图让自己的生活更轻松，首先是通过编写脚本并创建框架来支持大量物理系统，然后后来对虚拟机以及完整而复杂的基于 Web 的应用程序所需的所有网络和其他支持基础设施做同样的事情。在部署和部署后阶段，Kubernetes 通过提供一个管理框架来支持运营团队，该框架负责团队过去由于缺乏知识或资源而必须手动执行的所有编排工作，包括计算资源、存储和网络的配置，等等。

决定使用 Kubernetes 可以对从需求到部署和应用程序运行的整个应用程序开发产生重大积极影响。不过，确保所有团队成员都了解像 Kubernetes 这样的工具的使用带来的好处和要求是很重要的。

# Summary

软件开发是一项复杂的任务，除了软件开发人员本身之外，还有很多人参与其中。仅仅编写代码就是一项复杂的事业。拥有一种开发方法论有助于确保所开发的软件是企业、用户或客户所期望的。始终如一，确定问题后再确定解决方案。

多年来出现了许多不同的开发方法论。在某些情况下，开发方法论与其说是别的，不如说是一种哲学或文化。这在 DevOps 方面尤其如此。DevOps 与现代软件开发实践非常契合，尽管由于对沟通的强烈关注，实现起来可能具有挑战性。对于习惯于墙壁或孤岛限制不同团队的根深蒂固的开发团队来说，这可能是一个需要克服的挑战。将项目管理、开发、测试和运营围绕 Kubernetes 等单一平台进行聚焦可以帮助指导团队之间的必要沟通，因为每个人都在朝着同一个方向在同一技术上工作，而这在开发团队中并不总是如此。

此外，DevOps 与 Kubernetes 非常契合，而 Kubernetes 需要整个 SDLC 中所有团队成员的支持。在生命周期中的需求/设计阶段决定使用 Kubernetes 等工具可能会引入额外的需求，但也可以为开发人员和测试人员等其他团队成员提供很多答案，这可能会让生活更轻松并有助于提高应用程序的整体质量。

除了这个预告之外，我们将在本书的剩余部分研究 DevOps 中其他有助于高质量应用程序开发的实践。

# Chapter 2. Architectural Designs

软件应用程序是复杂的存在。组件很多。谈到基于 Web 的应用程序时，除了基于软件的元素之外，可能还涉及很多系统。当公司开发基于 Web 的应用程序时，他们需要负责的远不止软件开发，因为他们还必须关心交付平台。这与开发原生应用程序相比是一个重大的变化，即在桌面上直接运行的应用程序，其中最终用户负责软件运行的平台。

传统上，基于 Web 的应用程序使用一种称为 n 层设计的东西，这是软件开发的常见方法。一般来说，即使在原生应用程序中，你也可以看到 n 层设计的使用。然而，在过去十年多里，应用程序开发中出现了向不同模型的推动。随着越来越多的公司使用云服务来交付应用程序，无论是专门通过 Web 浏览器交付还是通过具有基于 Web 的后端的移动应用程序交付，都出现了向面向服务架构的转变。这种转变改变了应用程序的交付方式以及它们的设计和开发方式。它还改变了 Web 应用程序的安全态势以及它们的管理和部署方式。

在本章中，我们将研究一些传统的应用程序设计以及一些更现代的开发大型系统和应用程序的方法。这些更现代的方法在 Web 应用程序中尤其常见，我们看到它们在许多领域取代了原生应用程序。每种设计都有一些安全考虑，我们也会看一下这些。

## Traditional Application Design

n 层应用程序设计具有多个组件，它们以你可以认为是层级或层的方式进行良好定义的通信。n 层应用程序设计的一种常见方法是模型-视图-控制器，MVC，设计模式。模型是数据在应用程序中存储和表示的地方。视图是同一数据向用户展示的方式。这可能与模型中使用的表示方式非常不同，因为模型必须从编程角度来看是有意义的，而视图需要是视觉的。也就是说，用户需要能够查看它并知道应用程序中发生了什么。最后，控制器是中间层，它将数据从模型中取出并进行转换，无论是从模型中出来还是进入模型。业务逻辑可能存在于这一层，它防止视图直接与模型通信。这使你能够创建与接口无关的程序。例如，你最终可能会为不同类型的应用程序使用相同的模型。视图可能会改变，但只要接口、函数、方法和属性的调用在视图之间保持相同，模型和控制器就可以保留在原位。

传统的 Web 应用程序使用与此设计模式类似的东西。然而，它可能不被称为 MVC，而是被称为三层或 n 层设计。这是因为可能存在多个层，但它们可能无法很好地与 MVC 的描述对齐。[Figure 2-1](#ch02.xhtml#fig2-1) 显示了一个为弹性而构建的传统 Web 应用程序设计。图表左侧是用户。你可以将其视为表示层，在这里显示应用程序的输出并接受用户的任何输入并将其发送回应用程序的其余部分。图表显示用户通过互联网与应用程序通信。实际上可能并非如此，因为应用程序可能托管在企业数据中心，用户通过企业网络进行通信。无论如何，用户都在向他们没有直接连接的网络发送流量，即他们的本地网络，无论谁拥有该网络。
