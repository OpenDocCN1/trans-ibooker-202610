## 前言

今天，构建软件和系统就像在自家前院组装宜家厨房——人们正在把原本 intended 用于受信任数据、由个人在自己的命令行上使用的解析器、实用工具和其他组件，暴露到互联网上。随着每一种新的查询语言和解释器/解析器组合的出现（GraphQL 是其中较新的一个），旧问题又重现了。

在我的职业生涯中，拒绝服务（DoS）、注入、信息披露以及身份验证/授权绕过等漏洞类别，在几乎每一种使用正则表达式解析的数据格式和语言中都一直存在。其中一部分原因是底层技术存在固有的弱点，而开发新语言的开发者并不十分了解。但这不仅仅是技术问题让这些漏洞类别难以解决。这是一个生态系统问题。

在大多数情况下，由于暴露到互联网的组件的固有设计，在不损失功能或效率的情况下在其之上分层安全控制是具有挑战性的。以正则表达式本身为例：自我引用和反向引用的能力使其如此强大，但同样的能力也造成了固有的 DoS 风险。为了解析一个语句，正则表达式可以按需进行反向引用或自我引用任意多次。然而对于攻击者来说，必要可能意味着直到你付钱让我停止。

开发者可以合理地假设，在自己的系统上工作的命令行用户会提交格式良好的请求，设计为在计算上合理的时间内结束。毕竟，谁会 DoS 自己，除非是意外？但这一基础假设在互联网上并不成立。即使对于那些极少数考虑并理解在线威胁如何使组件重用基本设计假设失效的人来说，补偿设计决策也是棘手的。更常见的是，人们甚至不知道存在需要考虑的问题。

然后你还有可用性的问题。我们面向互联网的大多数技术本应在使用错误时具有容错性，以便我们的最低公分母互联网用户可以处理它。它应该具有自动纠正功能，以便优雅地处理错误。同时，该技术需要对最技术娴熟、厌倦或决心最强的攻击者保持安全。没有有效的自我纠正和通信系统可以阻止一个人推断数据是正确或已被纠正。一个精明的用户，即使对系统没有任何先验知识，也常常可以通过做出一系列有根据的猜测并滥用技术的通信方面来推断其包含的数据。这种推断然后确认的能力是许多微妙信息披露风险的来源。

从更广泛的意义上说，这些数据格式和语言的许多规范由于设计过程而变得不安全。像 PDF 和图像之类的东西的标准通常包含由标准制定时最大厂商规定的拼凑要求。核心规范包含厂商能够达成一致的内容，而可选项目则适应每个厂商的特殊功能和设计决策。由有既得利益的委员会创建的拼凑物并不能真正激励该群体思考安全问题。随着数据成为新的货币，委员会几乎故意将隐私和安全风险添加到标准中，以便公司可以继续进行数据收集（并相应获利）。

最后，对这些问题的教育严重缺乏，这就引出了本书。如果你第一次学习如何攻击解释型查询语言和数据格式，本书应该为你提供超越仅仅黑客攻击 GraphQL 的基础方法。本书中描述的相同技术、思维过程和问题类别很可能会在未来十年及以后为你的职业生涯服务。

如果你阅读本书是为了更好地理解 GraphQL（或在为下一次任务做准备的疯狂冲刺中浏览它），你会发现它是由两个不得不自己做相当多黑客攻击的人创建的绝佳简报，他们知道你需要的信息。这包括一个有用的问题清单、大量小陷阱的见解，以及否则需要你花费大量时间和研究才能发现的 GraphQL 特定怪癖和细微差别。

Nick Aleks 和 Dolev Farhi 都使用这些信息来破坏和构建复杂系统，因此他们可以描述构建者的视角以及破坏者的视角，而这种角度在黑客书籍中经常缺失。他们对 GraphQL 生态系统的见解应该能快速提升你的工作水平，使你超越发现漏洞，并转向对抗性模拟或威胁狩猎方法。





如果您正在开发一个新框架，这本书将是帮助您改变生态系统中的一小部分的有用资源。通过研究常见的技术问题并了解 GraphQL 的生态系统挑战，希望您能学到应避免的内容以及能转化为更安全设计决策的概念。
