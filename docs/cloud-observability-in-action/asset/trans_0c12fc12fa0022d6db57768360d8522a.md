
## 4.2 Prometheus

你可以使用在 Prometheus scrape config 中定义的重新标记规则来实现此操作（[https://prometheus.io/blog/2015/06/01/advanced-service-discovery/#scrape-configurations-and-relabeling](https://prometheus.io/blog/2015/06/01/advanced-service-discovery/#scrape-configurations-and-relabeling)），如下所示：

```
- source_labels: [handler]   ❶
  action: replace
  target_label: path
- regex: "handler"           ❷
  action: labeldrop
```

❶ 匹配 `handler` 标签名称并使用相同的标签值添加 `path` 标签

❷ 完成后，它会删除 `handler` 标签名称，仅保留 `path` 作为捕获 URL 路径的标签。

提示

如果你想交互式地尝试重新标记，可以访问 [https://relabeler.promlabs.com/](https://relabeler.promlabs.com/) 并使用重新标记规则（在左侧的 Relabeling Rules 输入框中）以及以下内容作为右侧（Object Labels）的输入：

```
method: "GET"
handler: "/some/interesting/thing"
```

当你现在点击 Analyze Rules 按钮时，你应该能看到规则引擎运行并产生预期结果。

此外，为了提高查询性能，你可以在 Prometheus scrape config 中定义 recording rules（[http://mng.bz/V1vX](http://mng.bz/V1vX)）。此功能允许我们预先计算频繁使用或开销大的表达式，实质上是用空间换时间，将结果保存为新的时间序列。假设我们想要使用 recording rule 来捕获 API 调用示例的服务器端错误率（其中 `api_requests_total` 为 counter 指标类型）：

```
- name: api_invocation_server_error                              ❶
  interval: 5m                                                   ❷
  rules:
  - record: http_status_5xx:api_requests_total:ratio_rate_5m     ❸
    expr:                                                        ❹
      sum(rate(api_requests_total{code=~"5.."}[5m]))
        /
        sum(rate(api_requests_total[5m]))
```

❶ recording rule 名称

❷ 评估规则的频率（此处为每 5 分钟）

❸ 生成指标的名称（请注意 `:` 的使用，按惯例它保留用于 recording rule 指标）

❹ 在当前时间评估的 PromQL 表达式，会生成一个新时间序列，其指标名称由前面的 record 值定义——在我们的例子中为 `http_status_5xx:api_requests_total:ratio_rate_5m`

你可以用两种方式使用 Prometheus（即使用相同的二进制文件，但配置不同）：

* Prometheus server（默认模式）
* Prometheus agent mode（[https://prometheus.io/blog/2021/11/16/agent/](https://prometheus.io/blog/2021/11/16/agent/)），针对抓取和联邦的远程读写进行了优化

我们在第 2 章已经看到 Prometheus 的实际应用，但作为提醒，Prometheus 的核心是其 `scrape config`。在这里你定义 Prometheus 应该抓取什么（其 `targets`）以及它应该如何找到 `targets`（服务发现），以及可选的 recording 和 alerting 规则。例如，要抓取 Prometheus 本身公开的指标（即自抓取），你可以在 scrape config 中使用如下内容：

```
global:
  scrape_interval: 30s                 ❶
 
scrape_configs:
  - job_name: "prom"                   ❷
    static_configs:
      - targets: ["localhost:9090"]    ❸
```

❶ 默认情况下，Prometheus 每 15 秒抓取（调用）一次 `targets`，但此处我们放宽到 30 秒。

❷ Prometheus 会将 `job_name` 作为标签（此处为 `job=prom`）添加到抓取的任何指标时间序列中。这是良好的溯源实践，有助于关联。

❸ 我们使用静态服务发现方法（提供要抓取或调用的 URL）。在这种情况下，由于 Prometheus 在 `$host:9090/metrics` 下公开指标，我们将其用作 `targets` 键的值。

请注意，`scrape configs`  going forward 仍然很重要，因为 OpenTelemetry 旨在与 Prometheus 兼容，并允许你重用你的 `scrape configs`（只需做少量调整）。你将在本章的端到端示例中看到所有这些的实际应用。

如果你想了解更多关于如何使用 Prometheus 以及其内部工作原理，我强烈推荐终极参考书：*Prometheus: Up & Running*，作者 Julien Pivotto 和 Brian Brazil，*Second Edition*（O’Reilly；[http://mng.bz/x458](http://mng.bz/x458)）。

### 4.2.2 其他指标代理

虽然 Prometheus 是云原生生态系统，尤其是 Kubernetes 上下文中已确立的指标平台，但出于各种原因，包括遗留使用或你的组织决定全力投入某个厂商或项目，你可能会遇到其他代理。这包括但不限于以下代理（按字母顺序排列）：

* `Collectd`（[https://collectd.org/](https://collectd.org/)）—用 C 编写，使用此代理可以高效收集操作系统和应用程序性能指标。多个云提供商和 ISV 提供了与 `collectd` 的集成，例如 Amazon CloudWatch、Splunk 和 Sumo Logic。
* `Grafana Agent`（[https://grafana.com/docs/agent/latest/](https://grafana.com/docs/agent/latest/)）—由 Grafana Labs 创建，此代理针对 Prometheus 指标进行了优化。该代理的代码已捐赠给 Prometheus 项目，并构成了 Prometheus 中代理模式的基础。在代理模式下，Prometheus 会停用多个功能，包括 UI、告警和本地存储。
* `Graphite`（[https://grafana.com/oss/graphite/](https://grafana.com/oss/graphite/)）—现在也在 Grafana Labs 旗下，此代理代表了上一代机器中心化监控的遥测示例。
* `Nagios`（[https://www.nagios.org/](https://www.nagios.org/)）—这是一个久负盛名的开源系统（包括代理），用于监控机器和网络。
* `StatsD`（[https://github.com/statsd/statsd](https://github.com/statsd/statsd)）—由 Etsy 开发，此代理是一个 Node.js 工具，采用客户端-服务器模型，允许你收集和聚合应用程序指标并将指标发送到后端，例如 Graphite。
* `Telegraf`（[https://github.com/influxdata/telegraf](https://github.com/influxdata/telegraf)）—来自 InfluxData，这是一个功能丰富且强大的代理，拥有许多插件，最初为其 InfluxDB 时序开源数据存储编写，现在也支持 OpenTelemetry。

本节故意简短，因为我认为了解该领域的其他代理很重要；然而，实践中，你可以预期在大多数情况下，你将以一种或另一种形式处理 Prometheus。如果你遇到使用上述代理之一的遗留环境，你需要确保有清晰的迁移路径到 Prometheus 或 OpenTelemetry 取代它。

## 4.3 OpenTelemetry

OpenTelemetry 是一个孵化中的云原生计算基金会项目，最初由两个专注于分布式追踪的项目 `OpenCensus` 和 `OpenTracing` 合并而成。OpenTelemetry 从 2019 年开始将其范围扩展到指标和日志。该项目是 Kubernetes 之后第二大的 CNCF 项目，其核心是一组 API、SDK 和工具，你可以用它们来对遥测信号进行检测、收集、处理和摄取。
