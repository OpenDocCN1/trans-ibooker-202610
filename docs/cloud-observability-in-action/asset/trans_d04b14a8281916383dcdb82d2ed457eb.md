
# OpenTelemetry 收集器

## 概述

OpenTelemetry 的代理称为 `collector`。它由管道组成，这些管道组装收集器组件，例如接收器、处理器和导出器，如图 4.6 所示。将管道视为组件的组合，这些组件定义了如何以及从何处获取信号（接收器）、在边缘处处理它们（通过处理器和连接器进行转换、批处理等），以及将信号摄取到哪个后端（导出器）。

你可以在收集器中定义一个或多个管道。每个管道专用于一种信号类型（例如，metrics）。你也可以为同一信号类型拥有多个管道，例如不同的环境或强制执行不同的策略。每个管道都独立运行，从源收集信号并将其摄取到后端。

## OTLP 协议

与收集器通信的原生方式是通过 OpenTelemetry 协议（`OTLP`; [https://tinyurl.com/mngbz](https://tinyurl.com/mngbz)），一种通用遥测数据传输协议。`OTLP` 规范描述了在下游源、中间节点（如收集器）和后端目标之间信号的编码、传输和交付机制。

`OTLP` 本身由 OpenTelemetry 项目设计，是对 `OpenCensus` 协议的增量改进，专注于交付的高可靠性以及在数据无法交付时提供清晰的可视性。此外，`OTLP` 友好于 L7 负载均衡器，支持将不均衡的入站流量映射到均衡的出站流量。进一步，`OTLP` 允许从目标一直到源的反压信号，使你能够通过中间节点（例如 OpenTelemetry 收集器）构建可靠的多跳交付，每个节点可能具有不同的处理能力。

从协议角度来看，`OTLP` 使用请求-响应风格：下游客户端发送请求，上游服务器回复相应的响应。`OTLP` 相当灵活——你可以在 `gRPC`、`HTTP` 以及（今后）`WebSockets` 上运行它。

虽然未来我们可能生活在一个每个人和一切都原生支持 OpenTelemetry 的世界——即使用 `OTLP` 进行通信——但在撰写本文时，2023 年还不是这种情况。OpenTelemetry 社区找到了一种巧妙的方法来帮助启动这一进程：通过引入大量入口和出口组件（接收器和导出器），这些组件可以从源读取现有格式和协议，以及向目标写入现有格式和协议。

## 收集器组件

现在，我们将重点关注收集器中的管道。每个管道使用一个或多个组件：

* 在入口路径中，从下游源收集信号，一个或多个接收器可以来自两个地方。
  * 对于原生的 `OTLP`，来自 `opentelemetry-collector` ([http://mng.bz/mVM4](http://mng.bz/mVM4)) 仓库
  * 对于所有其他接收器（`Prometheus`、`Jaeger`、`Kafka` 等），来自 `opentelemetry-collector-contrib` ([http://mng.bz/5wVa](http://mng.bz/5wVa)) 仓库
* 核心操作组件——一个或多个处理器可以来自两个地方。
  * 对于少量通用处理器，例如 `Batch`，来自 `opentelemetry-collector` ([http://mng.bz/6DxA](http://mng.bz/6DxA)) 仓库
  * 对于所有其他处理器（`Filter`、`Transform`、`Tail Sampling` 等），来自 `opentelemetry-collector-contrib` ([http://mng.bz/o1gp](http://mng.bz/o1gp)) 仓库
* 在出口路径中，将信号摄取到上游目标，一个或多个导出器可以来自两个地方。
  * 对于原生的 `OTLP`（和日志导出器），来自 `opentelemetry-collector` ([http://mng.bz/nWa2](http://mng.bz/nWa2)) 仓库
  * 对于所有其他导出器（`Prometheus Remote Write`、`Elasticsearch`、`AWS X-Ray` 等），来自 `opentelemetry-collector-contrib` ([http://mng.bz/vn04](http://mng.bz/vn04)) 仓库

## 示例管道

让我们从高层次来看图 4.6 中的一些示例管道：

* `pipeline 1` 是一个 traces 管道，可以通过 `OTLP` 入站收集 traces，批量处理它们，并将它们摄取到 `Jaeger` 实例中。
* `pipeline 2` 是一个 metrics 管道，通过 `Prometheus` 接收器入站抓取指标，再次批量处理，并使用 `Prometheus remote write` API 将它们摄取到例如 `Thanos` 或 `Cortex` 中。
* `pipeline N` 是一个 logs 管道，通过 `Filelog` ([http://mng.bz/rjJE](http://mng.bz/rjJE)) 接收器入站收集日志行，然后再次批量处理并过滤它们，然后可以将日志行摄取到两个不同的后端目标 `Splunk` 和 `CloudWatch` 中，通过各自的导出器。

## 扩展和部署

此外，收集器还提供多个扩展（[https://opentelemetry.io/docs/collector/configuration/#extensions](https://opentelemetry.io/docs/collector/configuration/#extensions)）来运行代理，包括健康检查、服务发现以及丰富的遥测（例如，日志、Prometheus 格式的指标、`OTLP` 中的 traces 以及 `pprof` 格式的 profiles）。

Tip 有不同的部署方式（[https://opentelemetry.io/docs/collector/deployment/](https://opentelemetry.io/docs/collector/deployment/)）收集器，通常区分于靠近工作负载（`agent mode`）和在中心位置（`gateway mode`）。在 `gateway mode`（有效地，在负载均衡器后面的一组收集器）中运行收集器可以帮助集中执行策略并支持围绕访问控制和身份验证的关注点分离，包括 `API keys` 和 `IAM roles`。

    - otel-collector
