
我们已在第 2 章详细介绍了为日志、指标和追踪对代码进行仪器化（instrumenting）的成本和收益。取决于你使用的编程语言（即解释型与编译型），你需要付出不同的努力来发出多种信号。在可能的情况下，你应该使用自动仪器化，并且通常最好标准化为 `OpenTelemetry`，以避免在切换信号目标时重新进行仪器化工作。我们将在第 4 章更详细地介绍这一点。

### 3.5.2 代理源

在你不拥有代码但仍想获取一些信号的情况下，可以使用代理源。例如，在使用 Prometheus 抓取指标的上下文中，考虑以下情况：

*   你想将来自消息队列（如 Kafka 或物联网设备）的指标加入其中，那么你会运行 Prometheus 可以抓取的众多导出器之一（[http://mng.bz/lWDj](http://mng.bz/lWDj)）。
*   另一种可能的情况是你确实拥有代码（例如在批处理作业或 Lambda 函数的上下文中），这是一个短暂运行的进程。另一方面，Prometheus 假定是一个可以随时抓取的长期运行进程；在这种情况下，你会使用 Pushgateway（[https://github.com/prometheus/pushgateway](https://github.com/prometheus/pushgateway)）来弥补阻抗不匹配。你可以通过 Bartek Płotka 和 Saswata Mukherjee 在 KubeCon EU 2022 的演讲“Fleeting Metrics: Monitoring Short-lived or Serverless Jobs”了解更多信息，该演讲可通过 YouTube 获取（[https://www.youtube.com/watch?v=rt4JiK995s8](https://www.youtube.com/watch?v=rt4JiK995s8)）。

代理也可以是适配器（例如从日志文件到 `stdout`），以使某些信号类型（如日志）在云原生设置中兼容且可用。

至此，我们已完成了对云原生设置中源的讨论，从计算到存储到网络再到你自己的代码，现在我们转向信号如何到达各种目的地以供消费的问题。简而言之，我们转向代理。

## 摘要

*   源是被观察系统中的任何发出遥测信号的实体，例如日志、指标、追踪和概要文件。
*   如果你拥有一个源（例如你在容器中运行的应用程序代码），那么你可以对其进行仪器化；否则，你需要绕过它，处理源所有者发出的内容。
*   我们可以区分源类型：计算、存储和网络。
*   容器和函数由于其短暂的生命周期，可能具有挑战性的源类型。
*   从可观测性的角度来看，无服务器环境意味着工作量更少但控制也更少。
*   与存储相关的源附带广泛的日志；指标支持；以及在较小程度上追踪，但概要文件是可用的。
*   对于 RDBMS，查询规划（分析）至关重要。对于 NoSQL 数据存储，访问模式和存储布局是最重要的关注领域。
*   对于文件系统，最重要的是关注可用磁盘空间（对于操作员而言）。
*   与网络相关的源可能很嘈杂，因为事件量很高。按源、目标或应用程序进行过滤可能具有挑战性。
*   更高级别的网络源，例如负载均衡器，通常比更低级别的源，例如 NIC，更有价值且更易访问。
*   在对代码进行仪器化时，请注意供应链问题（依赖项）。
*   对于追踪和指标，始终将自动仪器化用作基线，然后根据投资回报率决定在哪里以及对什么进行手动仪器化。

# 4 代理和仪器化

本章涵盖

*   我们所说的代理和仪器化是什么意思
*   存在哪些类型的代理，适用于哪些信号类型
*   什么是 OpenTelemetry 以及你如何从中受益
*   选择代理的标准

在本章中，我们将重点介绍如何将我们在第 3 章中讨论的源的信号获取到我们将在第 5 章和第 6 章中重点介绍的目的地。由于可观测性完全是关于从被观察系统公开的信号中获取可操作的见解，如果没有代理和仪器化，就几乎没有什么可观察的。

简而言之，在本章中，我们将学习如何对代码进行仪器化（并自动化该任务）以及选择和部署收集、聚合、过滤、下采样、脱敏和路由日志、指标和追踪的代理。

遥测行业在撰写本文时正处于一场 tectonic 转变之中。这种从特定于供应商或特定于信号的仪器化和代理向名为 `OpenTelemetry` 的行业标准的转变始于 2019 年。在本书的上下文中，我们将特定于供应商以及特定于信号的代理视为传统代理，与 `OpenTelemetry` 形成对比。

从 AWS 到 Azure 再到 Google Cloud 的云提供商，以及从 Datadog 到 Splunk 到 New Relic 到 Lightstep 到 Dynatrace 到 Honeycomb 到 Grafana Labs 的可观测性供应商，都已决定在 `OpenTelemetry` 背后组建。这有效地意味着遥测行业已决定使遥测成为基本要求，将其商品化，而是在目的地（存储和查询以及前端）上竞争。

`OpenTelemetry` 涵盖，按成熟度排序且截至撰写本文时，追踪、指标和日志。今后，社区已决定也在 `OpenTelemetry` 中涵盖概要文件（进程中的资源使用和时间）。另见我们在第 2 章中的讨论。

由于日志在 2022 年仍在进行中，我将在本章中使用特定于供应商或特定于信号的设置来演示日志。对于指标和追踪，另一方面，我将向你展示如何从开放且与供应商无关的标准 `OpenTelemetry` 及其代理收集器中受益。

## 4.1 日志路由器

首先，我们将看一下日志路由器。这些代理允许你从各种源收集日志，无论是系统级别还是你的应用程序，并将其发送到中央位置以供查找。在此上下文中，你经常还会听到日志转发、日志收集和日志聚合。然而，为了保持简单，我们将忽略细节并将所有这些统称为 *log routers*。

截至撰写本文时（2023 年），特定于供应商的代理，例如 Splunk 的 Universal Forwarder 或 Datadog 代理，以及特定于信号的代理，包括 Fluentd/Fluent Bit 或广泛使用的 Logstash。预计今后会发生变化并转向 `OpenTelemetry`。

我们将区分系统日志和应用程序日志。系统日志来自，但不限于，以下源（有关详细信息，请参阅我们在第 2 章中的讨论）：

*   操作系统（例如，在 Linux 中，来自 `/var/log` 和 `journalctl`）
*   Kubernetes 控制平面（[http://mng.bz/BmWv](http://mng.bz/BmWv)）日志（包括来自 `API server`、`etcd` 和 `controller manager` 的日志）以及工作节点日志（[http://mng.bz/d10D](http://mng.bz/d10D)），例如来自 `kubelet` 或 `container runtime` 的日志
*   用户活动和 API 使用日志，如 AWS CloudTrail（[https://aws.amazon.com/cloudtrail/](https://aws.amazon.com/cloudtrail/)）提供的日志
*   基础设施自动化日志（例如来自 HashiCorp `Terraform` 或 AWS `CloudFormation`）

应用程序日志，另一方面，是你在代码中发出的内容。你最终可能会为系统日志和应用程序日志使用不同的代理；但是，如果可能，你应该尝试通过选择一个代理来标准化，例如以下各节中讨论的代理。这主要是出于运营原因，因为这意味着需要修补（例如，考虑 `Log4j` 挑战）的内容会更少，并且升级。
