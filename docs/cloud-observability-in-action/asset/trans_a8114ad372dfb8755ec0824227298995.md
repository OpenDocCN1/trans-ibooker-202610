
## 9.1 使用 Parca 生成配置文件
为了生成配置文件，我们将设置一个信号源（与往常一样，我们将使用 `ho11y` 配合负载生成器），它将 trace 发送到 OpenTelemetry collector，然后我们将使用 Parca 从 collector 接收并查询配置文件。所有源代码都在 `ch09/parca` 中，因此请切换到该目录。首先，要查看来自 OpenTelemetry collector 的配置文件，你需要在 collector 中配置 `pprof` 扩展（[http://mng.bz/6D6e](http://mng.bz/6D6e)）（有关详细信息，请参阅下面的 `otel-config.yaml` 文件）。因此，让我们以通常的方式启动 Docker Compose 栈：
```
docker-compose -f docker-compose.yaml up
```
以下列表显示了与我们讨论相关的 Compose 文件片段。

### Listing 9.1 Parca 设置的 Docker Compose 配置相关片段
```
otel-collector:
    image: otel/opentelemetry-collector-contrib:0.68.0
    command: [
      "--config=/conf/otel-collector-config.yaml"
    ]
    volumes:
    - ./otel-config.yaml:/conf/otel-collector-config.yaml
    ports:
    - "4317:4317"
    - "1777:1777"                              ❶
 
  parca:                                       ❷
    image: ghcr.io/parca-dev/parca:v0.15.0
    command: /parca --config-path=/opt/parca.yaml
    ports:
    - "7070:7070"
    volumes:
    - "./parca.yaml:/opt/parca.yaml"           ❸
```
❶ 我们在 OpenTelemetry collector 上在此端口公开 `pprof` 扩展。
❷ Parca 作为服务器，提供服务发现和 UI。
❸ Parca 配置文件

`otel-config.yaml` 中 OpenTelemetry collector 的配置在以下列表中显示，配置了一个简单的 trace 管道，通过 `logging` exporter 将 trace 发送到 collector 的 `stdout`。

### Listing 9.2 用于生成配置文件的 OpenTelemetry collector 配置
```
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
 
exporters:
  logging:
    loglevel: debug
 
extensions:                         ❶
  pprof:
    endpoint: "otel-collector:1777"
 
service:
  pipelines:
    traces:                         ❷
      receivers: [ otlp ]
      exporters: [ logging ]        ❸
```
❶ 用于 collector 自遥测配置文件生成的 `pprof` 扩展
❷ 一个简单的 traces 管道，以产生一定的负载
❸ 实际上意味着记录到 stdout 且不摄入后端

请注意，列表 9.2 中管道的细节对我们并不重要，因为我们关注的是 `pprof` 扩展，以及由此带来的整个 collector，而不是特定的管道。

接下来，我们需要确保 Parca 知道从哪里获取配置文件。与 Prometheus 类似，我们定义一个抓取配置（在 `parca.yaml` 中），如以下列表所示。

### Listing 9.3 Parca 用于从 OpenTelemetry collector 收集配置文件的配置
```
object_storage:                        ❶
  bucket:
    type: "FILESYSTEM"
    config:
      directory: "./tmp"
 
scrape_configs:
  - job_name: "default"
    scrape_interval: "2s"
    static_configs:
      - targets: ["127.0.0.1:7070"]    ❷
```
❶ 告诉 Parca 我们仅使用本地存储
❷ 我们配置文件的来源（collector 的 `pprof` 扩展）

## 9.2 开发者生产力
我们正在见证一套工具的兴起，这些工具旨在通过为开发者提供洞察来提高开发者生产力，遵循左移趋势。在本节中，我们将查看该领域的工具，并描述它们与持续分析的关系。

### 9.2.1 挑战
开发者寻求哪些可操作的洞察来提高生产力？也就是说，我们如何更快、更安全地添加新功能或修复错误？挑战大致可分为以下几类：
*   *Volume of data*—你作为开发者编写的源代码以及你构建服务所依赖的所有库、包和模块构成了数据的大部分。然后，还有上下文数据集，包括问题跟踪器（GitHub、GitLab 等）以及路线图和用户输入与反馈，如访谈或录音。然后是文档，既与源代码相关，也有独立的项目或产品文档，以及 API，其操作和基于模式的数据类型。所有这些数据都作为输入，而作为开发者，我们倾向于试图将这些各种工件之间的所有连接都保存在脑海中。随着我们使用抽象层的增多，这变得越来越具有挑战性。
*   *Testing*—随着云服务的引入，许多事情发生了变化，我不一定是指基于云的 IDE；而是指软件的测试位置和方式。现在，我们仍会进行单元测试（取决于编程语言，这是可靠且可维护代码的一个或多或少重要的方面），但集成和端到端测试应该在哪里进行？一个假设是在生产中进行测试，并通过金丝雀、A/B 测试和功能标志（由 LaunchDarkly \[[https://launchdarkly.com/](https://launchdarkly.com/)\] 提供）或 Amazon CloudWatch Evidently ([https://aws.amazon.com/blogs/aws/cloudwatch-evidently/](https://aws.amazon.com/blogs/aws/cloudwatch-evidently/)) 来减轻影响。
*   *Distributed systems*—微服务是分布式系统，因此依赖网络通信。无论你使用 HTTP、gRPC 还是 WebSockets，你都需要了解通信行为、负载（编码、格式等），以及当远程 API 承受负载时会发生什么。这意味着一方面要处理泄漏的抽象（实现细节透过抽象层显现），另一方面要检测和处理超时、重试和限流。请记住，你的网络很可能不可靠或不安全（[https://architecturenotes.co/fallacies-of-distributed-systems/](https://architecturenotes.co/fallacies-of-distributed-systems/)）。

### 9.2.2 工具
我们在以下小节中更详细地介绍的开发者生产力工具通常基于或使用 OpenTelemetry，并提供深入的 IDE 集成，通常集成到 VS Code。越来越多的公司开始开源其（通常基于 OpenTelemetry 的）与开发者生产力相关的工具，其中包括 eBay，它提供了一个有趣的框架 `flow telemetry` ([https://github.com/eBay/flow-telemetry](https://github.com/eBay/flow-telemetry))。请注意，本节讨论的工具正在迅速发展，你可以预期功能的变化或其他工具或平台的整合。
