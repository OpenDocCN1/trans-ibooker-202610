
接下来，我们将更详细地审视与存储相关的来源。这些来源从关系数据库到文件系统不等。总的来说，由于很少有人需要编写自己的存储系统，在这一类别中，主要在于识别有哪些信号可用，以何种形式存在，以及保留多长时间（保留期）。

### 3.3.1 关系数据库和 NoSQL 数据存储

任何有用的实际应用通常都具有某种状态。在云原生系统的上下文中，存在多种不同的关系数据库管理系统（RDBMS），例如 PostgreSQL 和 MySQL，以及在微服务中使用的 NoSQL 数据存储（如 DynamoDB、Redis 和 MongoDB），具体取决于需求，例如强一致性、可扩展性和访问模式。

不论数据库类型如何，从用户角度来看，最重要的问题是如何快速处理查询。数据库采用了多种技术来加速查询处理，从使用索引到缓存。总的来说，你希望将数据库视为黑盒，除非你的角色专门聚焦于此部分，例如数据库管理员。要在高层次上了解更多相关指标，请查阅 Omed Habib 的文章“企业应用中需要监控的 Top 6 数据库性能指标” ([http://mng.bz/vn24](http://mng.bz/vn24))。

#### 关系数据库管理系统

在 RDBMS 的上下文中，最常见的信号类型是日志和指标，跟踪数据也日益可用。捕获数据库查询指标，例如最频繁或最慢的查询以及数据库性能（如缓存和会话），为运维提供了基础。

Silvia Botros 和 Jeremy Tinley 所著的 *High Performance MySQL*、*Fourth Edition* ([http://mng.bz/4Dyj](http://mng.bz/4Dyj)) 是了解 MYSQL 提供哪些信号类型的绝佳资源。它也可以作为将相关信号推广到其他 RDBMS（如 Maria DB ([https://mariadb.com/kb/en/server-monitoring-logs/](https://mariadb.com/kb/en/server-monitoring-logs/))）的基础。让我们看一个具体示例：在图 3.5 中，你可以看到使用 Grafana 作为前端的 Amazon Redshift 性能监控。

你可以自行收集相关数据库指标（例如流行的 RDBMS PostgreSQL）：

* 使用 Prometheus 配合 PostgreSQL Server Exporter ([http://mng.bz/QP1v](http://mng.bz/QP1v))

处理 RDBMS 性能指标的另一种选择是将此任务外包给供应商，无论是专注于可观测性的供应商，如 Dynatrace ([http://mng.bz/XNQa](http://mng.bz/XNQa))、Datadog ([https://www.datadoghq.com/blog/postgresql-monitoring/](https://www.datadoghq.com/blog/postgresql-monitoring/)) 或 New Relic ([http://mng.bz/yQ6d](http://mng.bz/yQ6d))。或者，你也可以使用你选择的云提供商提供的服务，如 AWS（见图 3.5）、Azure SQL Database ([http://mng.bz/MBAB](http://mng.bz/MBAB)) 或 Cloud SQL Insights ([http://mng.bz/a1Ym](http://mng.bz/a1Ym))。

对于 SQL 这种声明式语言，你声明期望的操作是什么，而不是如何执行。执行你的 SQL 查询的 RDBMS 有一个专门的组件称为 *query planner* ([https://sqlite.org/queryplanner.html](https://sqlite.org/queryplanner.html))，它负责优化 SQL 查询，考虑索引和其他因素。你可以通过 PostgreSQL 中的 `EXPLAIN` 语句 ([https://explain.depesz.com/s/Q6sQ](https://explain.depesz.com/s/Q6sQ)) 等方式了解查询规划的细节。

#### NoSQL

NoSQL 数据存储出现的时间不如关系数据库长（相比 RDBMS 的 50 多年，NoSQL 不到 20 年）。对于日志而言，同样适用于 RDBMS 的考虑：对于性能指标，我们面临不同的特征。在 NoSQL 的上下文中，重点较少放在查询规划上，因为缺乏关系意味着查询规划的重要性降低。在 NoSQL 上下文中最重要的是访问模式以及存储层中发生的情况。

鉴于 NoSQL 数据存储的广泛性（从键值和文档存储，如 Redis、MongoDB 和 DynamoDB，到图存储，如 Neo4j 或 Amazon Neptune，再到包括 Elasticsearch/OpenSearch 在内的搜索引擎），我们在这里不会深入详细介绍，但几个示例可能会突出良好的实践：

* “使用 Prometheus 监控 Redis” 由 David de Torres Huerta ([https://sysdig.com/blog/redis-prometheus/](https://sysdig.com/blog/redis-prometheus/))
* “MongoDB 监控” ([http://mng.bz/pPrK](http://mng.bz/pPrK))
* “Top DynamoDB 性能指标” 由 Jean-Mathieu Saponaro ([https://www.datadoghq.com/blog/top-dynamodb-performance-metrics/](https://www.datadoghq.com/blog/top-dynamodb-performance-metrics/))
* “使用 Sematext 监控 Elasticsearch” ([http://mng.bz/e1KV](http://mng.bz/e1KV))

接下来，我们将介绍两种通用而简单的存储系统：文件系统和对象存储。

### 3.3.2 文件系统和对象存储

我们现在将转向两种在云原生系统中广泛使用的与存储相关的来源，通常用于二进制大对象（BLOB），例如图像、视频或文档（PDF、Word 文档等）。在云原生环境中，本地文件系统（例如 Linux `ext4` 或 Windows NTFS）的一个重要用例是作为临时空间，即管理临时文件。网络文件系统，如 NFS ([https://datatracker.ietf.org/doc/rfc3530/](https://datatracker.ietf.org/doc/rfc3530/))，以及对象存储通常用于长期存储，因为它们与本地附加的非临时存储形成对比（即生命周期超出实例、容器或函数存在的时间）。

在 Linux 中，`/var/log` 目录是各种日志的中心位置，从应用日志到系统日志，而管理本地日志的主流工具日益是 `journalctl`。我在此强调 *local*，因为 `journalctl`（按设计）不支持将日志从机器上发送出去，这留给操作员自行处理。我们将在第 4 章和第 5 章中重新审视这个问题，当我们从代理和后端目标的角度讨论日志传输时。

从基础设施操作员的角度来看（例如 Kubernetes 平台管理员），最重要的文件系统信号是根设备上剩余的可用空间，如果磁盘空间用完，会发生各种坏事 ([https://sre.google/workbook/eliminating-toil/](https://sre.google/workbook/eliminating-toil/))。检查 Linux 系统上可用磁盘空间的一种简单方法是 `df` ([https://man7.org/linux/man-pages/man1/df.1.html](https://man7.org/linux/man-pages/man1/df.1.html)) 命令。以下是一个示例：

```
$ df -h                                            ❶
Filesystem      Size  Used Avail Use% Mounted on
/dev/root       7.7G  3.7G  4.1G  47% /            ❷
tmpfs           3.8G     0  3.8G   0% /dev/shm
tmpfs           1.5G  904K  1.5G   1% /run
tmpfs           5.0M     0  5.0M   0% /run/lock
tmpfs           4.0M     0  4.0M   0% /sys/fs/cgroup
tmpfs           767M  4.0K  767M   1% /run/user/1000
```

❶ 使用 -h 选项以 1024 的幂打印大小——即更易于人类阅读的格式

❷ 我们在这里可以看到，这台机器上使用了略少于一半的磁盘空间（47%）。
