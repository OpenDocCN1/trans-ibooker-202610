## 4.4 Other agents
除了用于日志的 Fluent 家族、用于指标的 Prometheus，以及作为通用遥测代理的 OpenTelemetry 收集器之外，还有一些成熟且广泛使用的代理。大多数由云服务提供商编写和分发，另外一些可观测性厂商也推出了代理，让我们快速了解一下（同样的思路适用：随着时间的推移，它们很可能会被 OpenTelemetry 或其收集器取代）：
* Amazon CloudWatch Agent（[https://github.com/aws/amazon-cloudwatch-agent/](https://github.com/aws/amazon-cloudwatch-agent/)）可用于日志和指标，支持 AWS 专有的嵌入式指标格式（EMF；[http://mng.bz/nWa5](http://mng.bz/nWa5)）。CloudWatch 代理已通过嵌入式收集器支持 OpenTelemetry，并已在 OpenTelemetry 上重新平台化（[http://mng.bz/G91q](http://mng.bz/G91q)）。除 CloudWatch 代理外，AWS 已通过其 AWS Distro for OpenTelemetry 提供符合 OpenTelemetry 的收集器（[https://aws.amazon.com/otel/](https://aws.amazon.com/otel/)）。
* Azure 正在逐步淘汰其 Log Analytics 代理和 Telegraf 代理，转而采用新的 Azure Monitor 代理（AMA；[http://mng.bz/2DNd](http://mng.bz/2DNd)）。与其它云服务提供商一样，Azure 在长期内也在标准化 OpenTelemetry（[http://mng.bz/vn0p](http://mng.bz/vn0p)）。
* 与 Azure 类似，Google Cloud 正在放弃其基于 collectd 的传统监控代理，转而采用新的 Ops Agent（[https://cloud.google.com/monitoring/agent/ops-agent](https://cloud.google.com/monitoring/agent/ops-agent)），它使用 Fluent Bit 进行日志收集和路由，并使用 OpenTelemetry 收集器处理指标。
* Datadog 的 Vector（[https://vector.dev/docs/about/what-is-vector/](https://vector.dev/docs/about/what-is-vector/)）是一个有趣的开源项目，在通用信号类型支持方面在一定程度上与 OpenTelemetry 竞争；然而它也支持 OpenTelemetry。如果您完全使用 Datadog，它似乎是一个不错的代理选择。
现在我们对存在的代理、其覆盖范围和使用场景有了良好的理解，让我们继续讨论如何选择代理的话题。
## 4.5 Selecting an agent
如常一样，你有多种选择。确保选择一个适合你的工作负载、环境和组织能力的代理非常重要。
