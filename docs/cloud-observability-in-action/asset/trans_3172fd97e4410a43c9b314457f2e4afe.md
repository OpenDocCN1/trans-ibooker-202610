
## 查询语言、模式和格式

关于查询的表达方式以及线格式，一些常用的查询语言、模式和格式如下（注意我在此有意混淆传输模式和查询语言以保持简单）：

* 对于日志信号类型：
  * `Elastic Common Schema (ECS)` ([http://mng.bz/lWy6](http://mng.bz/lWy6)) 查询语法为 `Elastic-flavored Lucene`
  * Grafana Labs’ `LogQL` ([https://grafana.com/docs/loki/latest/logql/](https://grafana.com/docs/loki/latest/logql/))
  * `CloudWatch Logs Insights` 查询语法 ([http://mng.bz/BmJ0](http://mng.bz/BmJ0))
  * `syslog` 协议 ([https://datatracker.ietf.org/doc/rfc5424/](https://datatracker.ietf.org/doc/rfc5424/))，依据 RFC 5424
  * Apache 的 `Common Log Format` ([https://en.wikipedia.org/wiki/Common_Log_Format](https://en.wikipedia.org/wiki/Common_Log_Format))
  * `NGINX` 访问和错误日志 ([https://docs.nginx.com/nginx/admin-guide/monitoring/logging](https://docs.nginx.com/nginx/admin-guide/monitoring/logging))
  * `Graylog Extended Log Format (GELF)` ([https://go2docs.graylog.org/5-0/getting_in_log_data/gelf.html](https://go2docs.graylog.org/5-0/getting_in_log_data/gelf.html))
  * `Windows Event Log` 模式 ([http://mng.bz/d1AN](http://mng.bz/d1AN))，如果你使用 Windows Event Explorer 时作为查询格式
  * `Common Event Format (CEF)` ([https://docs.nxlog.co/userguide/integrate/cef-logging.html](https://docs.nxlog.co/userguide/integrate/cef-logging.html))

* 在时序数据库领域或对于指标信号类型：
  * `PromQL` ([http://mng.bz/qrGw](http://mng.bz/qrGw))，即 Prometheus 查询语言
  * `Prometheus` 导出格式 ([http://mng.bz/rW7B](http://mng.bz/rW7B)) 和 `OpenMetrics` ([https://openmetrics.io/](https://openmetrics.io/))
  * InfluxData 的 `Flux` ([https://www.influxdata.com/products/flux/](https://www.influxdata.com/products/flux/))，一种独立的数据脚本和查询语言

* 对于追踪信号类型，目前还没有广泛建立的查询标准，但 Grafana Labs 正在研究这一主题。此外，`OpenTelemetry OTLP` 作为默认的线格式，在此上下文中被广泛采用。

* 对于类型为 profiles 的信号，`pprof` ([https://github.com/google/pprof](https://github.com/google/pprof)) 被广泛使用；另请参阅第 9 章，我们将在其中深入探讨这一主题。

请注意，对于大多数上述信号类型（排除 profiles，预计 2023 年可用），`OpenTelemetry OTLP` ([http://mng.bz/V1KP](http://mng.bz/V1KP)) 已经是或即将成为执行数据交换的标准方式。在大多数情况下，你希望选择支持（开放）行业标准的后端，例如 `OpenTelemetry` 或 `OpenMetrics`，而不是专有（仅）方案，但请参阅有关开放标准的上一节，了解此上下文中预期的注意事项。

有了这个选型指南，我们已经到达了后端章节的结尾。接下来，我们将讨论前端（例如 `Grafana`）和一体式解决方案，例如 `Apache SkyWalking`。

## 摘要

* 后端是你可观测性问题的事实来源。
* 后端以持久且长期的方式存储信号，支持各种查询语言，通常是声明式的。
* 日志、指标和追踪后端各有多种选择。你可以在云提供商提供的方案、开源（自行运行）选项以及众多提供商的管理型方案之间进行选择。
* 一些后端（例如 OSS 领域的 `OpenSearch` 以及可观测性厂商的大多数商业方案）可以处理多个信号类型；然而，实践中可能会为每种信号类型使用不同的后端。
* 能够将后端中的一种信号类型移动到另一个——可能不同——后端中的另一种信号类型，对于回答任意问题至关重要。
* 基数爆炸是指指标维度可能取许多不同的值（想想用户 ID）这一挑战。
* `TSDBs`，例如 `Prometheus`，是指标信号类型（数值聚合）的绝佳选择，直到你遇到基数爆炸。
* 对于高基数信号和用例，使用列式数据存储和格式。
* 确保你对要存储的确切内容有清晰的认识（例如日志与指标）。
* 由于数据引力，仔细选择后端至关重要（以避免在传输数据时产生大量导出-导入成本）。
* 在选择后端时，要注意摄取、存储和查询阶段的直接和间接成本。
* 在后端中选择对查询语言和线格式的开放标准支持，而非专有方案，以最大限度地减少锁定并提高互操作性。

# 6 前端目的地

本章涵盖

* 前端目的地是什么以及有哪些选项
* 一体式目的地是什么以及有哪些可用选项
* 如何选择前端和一体式方案

在第 5 章中，我们查看了可观测性后端。本质上，这些是专门的时序数据库（`TSDBs`）、具有 `TSDB` 扩展的通用关系数据库，或能够存储日志、指标和追踪的列式数据存储。一旦你在后端中摄取了信号，你就可以使用后端来回答可观测性问题，通常称为 *查询*。这个过程可能是声明式的，例如使用 `SQL` 或 `PromQL` 的情况，也可能是命令式的，例如你指示追踪后端通过根 span ID 查找一个 span。

但信号的存储和能够查询它们只是手段。可观测性是关于理解系统并从收集和摄取的遥测信号中获得可操作的洞察。所以作为可观测性解决方案的用户，你真正想要的是提出临时问题并获得（及时的）答案。

理想情况下，这应该无论你询问的时间范围或涉及的遥测数据量如何都成立。例如，假设你每天摄取 10 GB 的日志数据和 10 亿条追踪，保留期为一年。当你在进行故障排除时，你不希望这一事实拖慢你（等待查询超时或花费数分钟返回），因为这会打断你的流程，可能导致你忽视问题，例如更慢地找到 bug——甚至找不到。

提出这些（可观测性）问题的环境是什么？这些环境可以是前端和一体式。前端按设计是纯图形用户界面（`GUIs`），允许你配置一个或多个数据源以创建仪表板或告警，例如 `Grafana`。一体式则将后端和前端组合成一个不可分割的逻辑单元。换句话说，你不能将一体式的 GUI 作为独立使用，只能与提供商为其设计的后端（们）结合使用。

那么你如何提出不同的问题，结果如何呈现给你？你猜对了：正是前端和一体式目的地让你实现这一点。可观测性社区中你可能会遇到的一个术语是 *一站式视图*。在本书的上下文中，我指的是一个单一位置或应用程序，你可以用它来消费所有信号、查询并关联不同信号类型。让我们深入了解可观测性前端的巡览。

**提示**

现实表明，将追求一站式视图作为最重要需求或优先事项（可能来自管理层）往往不是最有效的时间和金钱使用方式。能否在单一位置标准化消费许多、如果不是大多数信号？可以。是否会有例外？也会有。换句话说：通过考虑本章介绍的解决方案之一来追求它，但在不易实现的地方允许灵活性。
