
# 列式数据存储

列式或列存储数据存储（参见 Mike Stonebraker 等人，《`C-Store`: A Column-oriented DBMS.》第 31 届 `VLDB` 大会论文集，挪威特隆赫姆，2005 年；另见 [https://people.brandeis.edu/~nga/papers/VLDB05.pdf](https://people.brandeis.edu/~nga/papers/VLDB05.pdf)）将列的数据彼此相邻存储，通常是所谓的在线分析处理（`OLAP`）用例的良好选择。这些情况事务较少，但查询量很大。写入路径是例如时序数据的摄取，而读取路径例如是对时间范围的即席查询。因此，这些列式数据存储非常适合历史（时序）数据，在这些数据中，我们希望以通常交互的方式从大型数据集（数十亿行，甚至可能达到 PB 级数据）中提取可操作的洞察，或者换句话说，可观测性用例。让我们更仔细地看一下：图 5.5 显示了行式与列式存储策略。

## 存储布局

从逻辑布局开始，以列（垂直）和行（水平）的表格视图来看，某个值具有坐标 `CiRj`（例如，第三列第二行的值会被引用为 `C2R1`）。现在，当你以行式存储值（图 5.5 的左侧）时，你从第一行开始，然后进入第二行，依此类推，从而得到一个存储布局（在磁盘或内存上），它存储第一行、第二行，依此类推，直到最后一行。相比之下，当以列式存储值（图 5.5 的右侧）时，你从第一列开始，然后进入第二列，依此类推，从而得到一个存储布局（在磁盘或内存上），它存储第一列、第二列，依此类推，直到最后一列。

你可能会想，为什么要使用列式存储？事实证明，列式存储对于 `OLAP` 用例有许多优势，其中包括我们的可观测性用例。

## 优势

在可观测性用例中，你可能有许多感兴趣的维度，导致高基数和大量列。对于任何给定查询，可能只有少数列与查询相关。列式数据存储允许更快、更少的扫描，因为需要读取的不必要值更少（这些值随后会被立即丢弃，因为它们不贡献于答案）。

此外，列式设计允许你应用存储优化技术，例如差分存储，如 Facebook 在 `Gorilla TSDB` 上下文中开发的 `XOR` 压缩（参见 Tuomas Pelkonen 等人，《Gorilla: A Fast, Scalable, In-Memory Time Series Database.》`VLDB` Endowment 第 8 卷第 12 期，2015 年；另见 [http://www.vldb.org/pvldb/vol8/p1816-teller.pdf](http://www.vldb.org/pvldb/vol8/p1816-teller.pdf)）以及游程编码（`RLE`；参见 D. Abadi、S. Madden、M. Ferreira，《Integrating Compression and Execution in Column-Oriented Database Systems.》第 33 届数据管理国际会议论文集 [`SIGMOD`]；[https://doi.org/10.1145/1142473.1142548](https://doi.org/10.1145/1142473.1142548)），从而获得更小的占用空间和更少的资源使用。

除了压缩之外，列式设计还支持向量化执行（每个 CPU 周期处理多个数据项）以及在单机环境中的有效分区，并通过分片和复制实现扩展，从而让你在亚秒级时间内回答涉及数亿行的查询。

## 典型示例

以下列出了使用该策略的典型列式数据存储、列式格式或服务的示例：

* `Apache Cassandra` ([https://cassandra.apache.org/](https://cassandra.apache.org/)) — 用 Java 编写 — C++ 变体 `ScyllaDB` 也可获得 ([https://www.scylladb.com/](https://www.scylladb.com/))。
* `Apache Druid` ([https://druid.apache.org/](https://druid.apache.org/)) — 一个开源实时分析数据库，由 Airbnb、Alibaba、eBay、Lyft 等公司用于可观测性用例。你可以在 `Kubernetes` 中运行 `Druid` ([http://mng.bz/0KDp](http://mng.bz/0KDp))。
* `Apache Pinot` ([https://pinot.apache.org/](https://pinot.apache.org/)) — 一个开源实时分布式 `OLAP` 数据存储，被 LinkedIn ([http://mng.bz/KeOP](http://mng.bz/KeOP))、Uber、Slack、Stripe 等众多公司使用。
* `ClickHouse` ([https://clickhouse.com/](https://clickhouse.com/)) — 一个开源列式数据库，最初由 Yandex 于 2008 年开发。你可以使用 `ClickHouse` 处理所有信号类型，既可用于单机，也可用于各种分布式环境（使用 `Apache Zookeeper` 作为协调器的分片和复制数据）。在 `Kubernetes` 上运行它时，应考虑使用 `ClickHouse` 的 `Altinity Operator` ([https://github.com/Altinity/clickhouse-operator](https://github.com/Altinity/clickhouse-operator))。`ClickHouse` 的采用率相当不错，包括 Uber（日志）、Cloudflare 和 SigNoz，在这些地方它被用作 o11y 解决方案的构建块。
* `FrostDB` ([https://github.com/polarsignals/frostdb](https://github.com/polarsignals/frostdb)) — 一个允许半结构化模式的列式数据库，使用 `Apache Parquet` 进行存储以及 `Apache Arrow` 进行查询，由 Polar Signals 以开源形式开发。
* `Snowflake` ([https://www.snowflake.com/](https://www.snowflake.com/)) — 一个作为服务交付的集成平台。它具有存储、计算和全球服务层，这些层在物理上分离但在逻辑上集成。

如果你有兴趣了解上述数据存储的一些实现细节，我推荐阅读 Roman Leventov 的优秀文章，“Comparison of the Open Source `OLAP` Systems for Big Data: `ClickHouse`, `Druid`, and `Pinot`,” ([http://mng.bz/9DRx](http://mng.bz/9DRx))。

在此上下文中，有趣的是，列式存储不仅限于后端。例如，在 `OpenTelemetry` 中，正在进行工作以在采集器和协议中引入列式编码 ([https://github.com/open-telemetry/oteps/pull/171](https://github.com/open-telemetry/oteps/pull/171))，以加快处理速度并提高性能和可扩展性。

### 提示

列式数据存储和数据库、格式以及开源项目的空间在过去十年中爆炸式增长。事实上，我在研究领域工作约 12 年后的第一份行业工作，是在 `Hadoop` 初创公司中，参与现在已退役的 `Apache Drill` 项目（它类似于 Google 的 `Dremel` 的开源版本，而 `Dremel` 是 `BigQuery` 的基础）。

有许多有趣的数据存储你可能会感兴趣，包括 `MonetDB`、`Hypertable`、`Apache Kudu` 和 `Greenplum`。在本书范围内详细涵盖它们超出了范围。如果你想了解更多，我推荐阅读 Martin Kleppmann 的优秀书籍 *设计数据密集型应用*（O’Reilly，2017 年；[https://dataintensive.net/](https://dataintensive.net/)）和唯一一位 Andy Petrella 所著的 *数据可观测性基础*（O’Reilly，2023 年；[http://mng.bz/jPQz](http://mng.bz/jPQz)）。

在这么多理论之后，我们理应有些实际操作！所以让我们深入研究一个在过去几年中获得大量关注的开源列式数据存储的示例：`ClickHouse`。
