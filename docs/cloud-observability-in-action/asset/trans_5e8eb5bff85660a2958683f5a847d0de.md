### 4.3.1 仪器化

在你拥有的代码上下文中，首先要解决的就是使用 OpenTelemetry 发出信号。截至撰写时，OpenTelemetry 为 11 种编程语言提供仪器化支持。更具体地说，OpenTelemetry 支持 C++、.NET、Erlang/Elixir、Go、Java、JavaScript、PHP、Python、Ruby、Rust 和 Swift。

在 OpenTelemetry 中，仪器化是这样组织的：用户为每种编程语言获得一个库软件开发工具包，并且可能支持自动仪器化。某些语言通过单独的仓库提供此功能（例如 Java），而其他语言，如 Ruby，则维护一个同时支持手动和自动仪器化的单一仓库。请记住，仪器化并非免费。即使在最佳的自动仪器化情况下，你无需更改代码，应用程序的性能仍会受到轻微影响（[http://mng.bz/Rx5j](http://mng.bz/Rx5j)）。

让我们更详细地了解 OpenTelemetry 中的不同仪器化方法。我们将从自动仪器化开始，因为它是一个很好的起点，并且所需工作较少。

#### 自动仪器化

在 OpenTelemetry 中，使用自动仪器化，或简称为自动仪器化，所需步骤如下：

1. 首先，启用自动仪器化。你通常需要添加一个或多个依赖项。至少，这些依赖项将添加 OpenTelemetry `API` 和 `SDK` 功能。
2. 然后，配置自动仪器化，可以通过 `environment variables`（和/或语言特定的机制，例如 Java 中的 `system properties`）进行。你至少必须提供一个 `service name` 来标识你要仪器化的服务，并且可选地提供其他配置选项，包括诸如 `source configuration`、`exporter configuration` 和 `resource configuration` 之类的内容。

OpenTelemetry（截至撰写时）为某些编程语言生成追踪提供自动仪器化，包括

* Java 自动仪器化（[https://github.com/open-telemetry/opentelemetry-java-instrumentation](https://github.com/open-telemetry/opentelemetry-java-instrumentation)），它是 OpenTelemetry 的一部分，以你包含的 `JAR` 文件形式存在（使用 `-javaagent`）。你可以在精细程度上配置此代理（[http://mng.bz/2DQ8](http://mng.bz/2DQ8)），从清理数据库查询到捕获预定义的 `HTTP` 头部，它将动态注入 `JVM` 字节码以从流行的 Java 框架中捕获信号。
* JavaScript（[https://github.com/open-telemetry/opentelemetry-js](https://github.com/open-telemetry/opentelemetry-js)），也通过 OpenTelemetry 核心官方支持，允许你使用所有 JavaScript 应用。请注意，还有额外的框架特定 SDK，例如 OpenTelemetry `Node SDK`（[http://mng.bz/1q41](http://mng.bz/1q41)），可启用自动仪器化。
* Python（[http://mng.bz/Pz2Y](http://mng.bz/Pz2Y)）也在官方支持的自动仪器化语言之列。
* .NET（[https://opentelemetry.io/docs/instrumentation/net/automatic/](https://opentelemetry.io/docs/instrumentation/net/automatic/)）将自动仪器化作为 .NET 分析器支持，以在运行时使用猴子补丁注入额外的仪器化。
* Go（[https://github.com/keyval-dev/opentelemetry-go-instrumentation](https://github.com/keyval-dev/opentelemetry-go-instrumentation)）是基于 `eBPF` 的用户贡献。严格来说，`eBPF` 是一个 `Linux syscall` 和虚拟机（`VM`），对内核版本和符号支持有一定要求，允许你将用户空间功能下推到 Linux 内核中，基于事件触发。在此上下文中，这意味着为你自动捕获遥测信号。

 going forward，你可以期待为更多编程语言以及支持指标提供自动仪器化。自动仪器化是一个值得始终考虑的良好基线，因为你几乎可以免费获得一些洞察。然而，它也有局限性：自动仪器化将服务视为黑盒，这意味着你无法从中获得业务逻辑相关的信号。为此，你需要使用手动仪器化，让我们来看一下。

#### 手动仪器化

手动仪器化意味着你修改自己的代码以手动发出信号。语言无关地执行此操作所需的步骤是

1. 在你的代码中导入 OpenTelemetry——即对语言特定的 `API` 和 `SDK` 产生依赖。
2. 对于追踪和指标，首先创建一个 `provider`（通常已有默认实现），它进而允许你创建一个 `instance`（连同 `name` 和 `version`）。
3. 对于服务（与你可能仪器化的库相对），此外，还需配置 `SDK`，并提供导出信号的适当选项。
4. 在所有设置完成后，专注于主要工作：创建事件（追踪和指标）。

注意 `Logs`（[http://mng.bz/JgrK](http://mng.bz/JgrK)）不遵循之前所示的模式。相反，它们利用现有的设置；换句话说，虽然 OpenTelemetry 对指标和追踪采用了全新方法（通过指定新的 `API` 并在各编程语言中提供所述 `API` 的完整实现），但日志的方法不同，其重点在于支持现有日志和日志库。

手动和自动仪器化存在许多可能的用例和组合，如果你确实想在自己的设置上下文中获得实践指导，你将在网上找到大量优秀的文章和教程。例如，“OpenTelemetry and Python: A Complete Instrumentation Guide”（[http://mng.bz/wvK2](http://mng.bz/wvK2)）、“Auto-Instrumenting Node.js Apps With OpenTelemetry”（[http://mng.bz/qrpJ](http://mng.bz/qrpJ)）、“Trace Context Propagation With OpenTelemetry”（[http://mng.bz/7DAe](http://mng.bz/7DAe)）和“OpenTelemetry in Java: Tutorial & Agent Example”（[https://www.containiq.com/post/opentelemetry-in-java](https://www.containiq.com/post/opentelemetry-in-java)）都是优秀资源。接下来，我们来看 OpenTelemetry Collector——“通用信号类型”代理或“通用遥测”代理。
