### 4.1.2 其他日志路由器

我们已经见识了 Fluent Bit 的实际应用，但这并不是我们唯一的选项。事实上，有许多商业和开源日志路由器可供选择，例如以下这些：

*   Beats（[https://github.com/elastic/beats/tree/master](https://github.com/elastic/beats/tree/master)）家族以及 Logstash（[https://github.com/elastic/logstash](https://github.com/elastic/logstash)），均为 Elastic Stack 的一部分。
*   Data Prepper（[https://github.com/opensearch-project/data-prepper](https://github.com/opensearch-project/data-prepper)），一个允许状态化处理的 AWS 开源项目。
*   syslog-ng（[https://www.syslog-ng.com/products/open-source-log-management/](https://www.syslog-ng.com/products/open-source-log-management/)）是一个 syslog 实现，默认从 systemd journal 摄取消息，应用过滤器并将其发送到文件。
*   rsyslog（[https://www.rsyslog.com/](https://www.rsyslog.com/)）是一个用于在 TCP/IP 网络上路由和过滤日志消息的开源工具，作为 `syslogd` 的替代品引入。
*   Graylog（[https://www.graylog.org/](https://www.graylog.org/)）是一家日志管理软件公司，提供以安全用例为重点的日志解决方案。

请记住，随着 OpenTelemetry 的成熟和日志的持续稳定，请确保制定迁移策略，以便从你当前与 OpenTelemetry collector 一起使用的日志路由代理迁移。让我们现在转向指标。

## 4.2 指标收集

与日志相比，指标方面的生态系统碎片化程度较低。过去几年（实际上自 2016 年 Kubernetes 兴起以来），主导者是 Prometheus 项目，它提出了指标的收集方式以及指标在传输线上的表示方式——*exposition format*。让我们先来看看 Prometheus，然后快速浏览一下指标领域中的其他成熟代理。

注意 虽然 Prometheus 建立了基于拉取的收集——即代理通过默认为 `/metrics` 的 HTTP 端点查询指标源——但在 OpenTelemetry 的上下文中情况更为微妙。在那里，入口部分仍然是基于拉取的；然而，出口部分（面向后端目标）通常是基于推送的。我们将在下一节关于 OpenTelemetry 的内容中详细介绍。

### 4.2.1 Prometheus

Prometheus（[https://prometheus.io/](https://prometheus.io/)）是一个成熟的 CNCF 项目，与 Kubernetes 共同成长，在 Kubernetes 中也主要使用。它涵盖了指标的摄取、存储以及查询和联邦接口，包括一个简单的 UI。此外，Prometheus 项目的一部分是告警功能（一个独立的二进制文件但紧密集成）。

在第 2 章中，我们对指标进行了一般性讨论。现在，让我们更详细地仔细看看 Prometheus 是如何运作的。

Prometheus 中的一个时间序列由其指标名称和若干（可选的）键值对唯一标识，这些键值对称为 *labels*。指标名称捕获你想要测量的通用特征。例如，`api_requests_total` 可用于 API 调用的总数。另一方面，标签代表 Prometheus 的维度数据模型。假设你想用 API 调用指标捕获两个维度：使用的 HTTP 方法以及 URL 路径是什么。你可以使用两个标签 `method` 和 `path` 来实现，例如如下所示：

```
api_requests_total{method="GET", path="/some/interesting/thing"}
```

Prometheus 支持不同类型的指标，包括计数器、仪表和直方图，并且 Prometheus 对指标和标签有命名约定（[https://prometheus.io/docs/practices/naming/](https://prometheus.io/docs/practices/naming/)），但它并未为其定义或强制执行语义。实际上，Prometheus 缺乏定义的语义并不是一个大问题，因为 Prometheus 提供了一个名为 *relabeling* 的功能（[https://prometheus.io/docs/prometheus/latest/configuration/configuration/#relabel_config](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#relabel_config)），它允许你对命名进行标准化。

通过 relabeling，你可以按目标添加、删除或修改标签。一个具体的例子就是重命名标签以标准化标签名称。假设我们的源会在标签 `handler` 下公开 URL 路径，但我们希望在设置中使用 `path`。在这种情况下，我们想要执行以下 relabeling：

```
api_requests_total{method="GET", handler="/some/interesting/thing"}

=>

api_requests_total{method="GET", path="/some/interesting/thing"}
```
