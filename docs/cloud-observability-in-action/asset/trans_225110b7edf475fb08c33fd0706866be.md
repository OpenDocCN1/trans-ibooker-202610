
有多种日志标准和格式可用，包括行式格式，例如 syslog RFC 5424 ([https://tools.ietf.org/html/rfc5424](https://tools.ietf.org/html/rfc5424)) 和 Apache 通用日志格式（CLF； [http://mng.bz/lWg8](http://mng.bz/lWg8)）；JSON 日志格式（大多数现代库均支持）；以及二进制格式，例如在 `systemd` 上下文中找到的 journal 文件格式（[http://mng.bz/Bmw8](http://mng.bz/Bmw8)）。要了解更多信息，请查看 Graylog 的 Logs Format Guide（[http://mng.bz/d1nO](http://mng.bz/d1nO)）。在日志上下文中，一些良好的实践包括以下内容：
*   考虑记录什么内容，目标是提供可操作的洞察（上下文为王）。
*   记录到 `stdout` 而不是固定位置，例如文件。这使得日志代理能够收集和路由你的日志事件。另请参阅 `12-factor` 方法论中的条目（[https://12factor.net/logs](https://12factor.net/logs)）以了解背景。
*   使用标签来增强日志事件的价值。例如，你可以使用组件名称或类型、源的类型或操作的类型作为标签来帮助筛选事件。

提示 如果你想知道如何让你的日志策略“面向未来”，我建议阅读 Ben Sigelman（Lightstep 的联合创始人，以其在 OpenTelemetry、Google Dapper 和 Monarch 方面的工作而闻名）的 2001 年 Twitter 线程，“Why Tracing Might Replace (Almost) All Logging”（[http://mng.bz/rWzD](http://mng.bz/rWzD)），其中他认为在云原生系统中，追踪将通过关于事务本身的仪器化（而不是关于基础设施或其他资源的日志记录）取代大部分工作负载的日志记录。这是有道理的，至少对于事务性设置中日志的许多用例而言，我希望你能考虑这种思维方式并将其应用于你的环境，如果你有条件这样做的话。当然，许多环境更偏向棕地而非绿地，因此建立这种以追踪为中心（而非以日志为中心）的方法可能很困难或需要花费大量时间和精力。

### 2.3.1 仪器化

现在让我们看看日志的实际应用。为此，我们对 `echo` 服务进行仪器化，使其发出日志事件。以下列表展示了我们的 `echo` 服务经过仪器化以发出日志。

列表 2.3 用于发出结构化日志的示例 Go 程序，已进行仪器化
```
package main
 
import (
    "fmt"
    "math/rand"
    "net/http"
    "time"
 
    log "github.com/sirupsen/logrus"
)
 
func handleEcho(w http.ResponseWriter, r *http.Request) {
    message := r.URL.Query().Get("message")
    log.WithFields(log.Fields{
        "service": "echo",
    }).Info("Got input ", message)                    ❶
    if rand.Intn(100) > 90 {
        log.WithFields(log.Fields{
            "service": "echo",
        }).Error("Something really bad happened :(")  ❷
        w.WriteHeader(500)
        return
    }
    fmt.Fprintf(w, message)
}
 
func main() {
    rand.Seed(time.Now().UnixNano())
    log.SetFormatter(&log.JSONFormatter{})            ❸
    http.HandleFunc("/echo", handleEcho)
    log.Fatal(http.ListenAndServe(":4242", nil))
}
```
❶ 无论如何，始终在此处发出一条 INFO 日志行，确认我们通过查询参数 `message` 获得的输入值。请注意上文（以及下面的错误情况中再次出现）中的 "service": "echo"：这为事件提供了上下文，使你能够精确定位服务。
❷ 在错误情况下发出一条 ERROR 日志行。
❸ 配置记录器以发出 JSON 格式的日志行。另外，请注意我们在此使用的记录器 `logrus` (https://github.com/Sirupsen/logrus) 默认输出到 `stderr`，在我们稍后消费日志时需要考虑这一点。

要构建该服务，你还需通过名为 `go.mod` 的文件（如下列表所示）定义其依赖项。

列表 2.4 示例 Go 程序依赖文件 `go.mod`
```
module co11yia/ch2/logs
 
go 1.20
 
require github.com/sirupsen/logrus v1.8.1
```
现在，要引入 `echo` 服务的依赖项，运行以下命令：
```
$ go mod vendor
```
通过执行 `go build` 完成构建，如列表 2.2 中所述。

### 2.3.2 遥测

我们现在可以本地执行 `echo` 服务，并将执行期间发出的日志事件发送到某些目标，例如屏幕和文件：
```
$ ./echosvc 2>&1 | \
  tee echo.log
```
❶ 执行 `echosvc` 并将其 `stderr` 输出重定向到 `stdout`。
❷ 使用 `tee` 命令在终端上显示日志行，同时将日志行追加到名为 `echo.log` 的文件中。我们将在下一步中使用此文件作为输入将其发送到目标。

接下来，我们将使用 Grafana Labs 提供的一些开源工具来路由和收集日志。我们使用 `Promtail`（[http://mng.bz/V1J0](http://mng.bz/V1J0)）捕获 `echo` 服务的日志，并将其发送到 `Loki`（[https://grafana.com/docs/loki/latest/](https://grafana.com/docs/loki/latest/)）作为目标（作为 `Grafana` 中的数据源）。使用 `Grafana` 作为前端，你就可以按需查看和查询日志。

要设置我们的日志场景，请使用以下列表中所示的 Docker Compose 清单文件。它启动了所需的一切，从目标到前端。

列表 2.5 使用 `docker-compose.yaml` 启动 `Promtail`、`Loki` 和 `Grafana`
```
version: "3.5"
networks:
  loki:
services:
  loki:
    image: grafana/loki:2.4.0
    ports:
      - "3100:3100"
    command: -config.file=/etc/loki/local-config.yaml
    networks:
      - loki
  promtail:
    image: grafana/promtail:2.4.0
    volumes:
      - ./promtail-config.yaml:/etc/promtail/config.yml     ❶
      - ./echo.log:/var/log/echo.log                        ❷
    command: -config.file=/etc/promtail/config.yml
    networks:
      - loki
  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    networks:
      - loki
```
❶ 定义 `Promtail` 配置文件的位置。我们将主机本地文件 `promtail-config.yaml` 映射到容器中的 `/etc/promtail/config.yml`，`Promtail` 预计在该位置找到它。
❷ 将主机本地文件 `echo.log`（我们的 `echo` 服务记录到该文件）映射到容器中的 `/var/log/echo.log`。我们将在列表 2.6 中使用它来定义日志处理和路由管道。

提示 虽然使用 `Docker Compose` 在本地开发或测试应用非常方便，但对于生产环境设置，`Kubernetes` 更有用。例如，你可以通过 `Helm` 图表或使用 `Tanka`（[https://tanka.dev/](https://tanka.dev/)）安装 `Promtail`、`Loki` 和 `Grafana` 堆栈。

现在我们已通过 `Docker Compose` 文件（列表 2.5）设置了启动日志目标（`Loki`）、遥测代理（`Promtail`）和前端（`Grafana`）的框架，我们还需要做最后一件事：配置 `Promtail`，我们的日志路由器/摄取器。`Docker Compose` 清单在第 15 行引用了此 `Promtail` 配置文件，我们称其为 `promtail-config.yaml`，如下列表所示。

列表 2.6 `Promtail` 配置文件 `promtail-config.yaml`
```
server:
  http_listen_port: 9080
  grpc_listen_port: 0
 
positions:
  filename: /tmp/positions.yaml
 
clients:
  - url: http://loki:3100/loki/api/v1/push
 
scrape_configs:
- job_name: app
  static_configs:
  - targets:
      - localhost
    labels:
      job: echosvc
      __path__: /var/log/echo.log    ❶
 pipeline_stages:
  - json:                            ❷
     expressions:
        level: level
        payload: msg
        timestamp: time
        service: service
  - labels:                          ❸
     level:
      service:
```
❶ 这定义了 `Promtail` 的输入。在这里，我们告诉它从名为 `/var/log/echo.log` 的文件摄取日志（我们已通过 `Docker Compose` 清单第 16 行的卷从主机挂载）。
