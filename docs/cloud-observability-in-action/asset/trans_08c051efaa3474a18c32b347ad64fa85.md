
我们之前讨论过，解决事件的第一步是能够首先理解确实出现了问题。这听起来可能很简单，但在由众多组件组成的云原生系统中，这是一个非平凡的问题。换句话说，像在浏览器中访问你的网站并检查一切是否看起来正常这样的人工方法，是你不想考虑的。相反，力求尽可能自动化对你的服务以及“外部视角”——即客户体验（`CX`）的检查。在此上下文中，强调这一外部视角至关重要；想象一下这样一种情况：你的所有服务都报告健康且按预期工作，但你的终端用户却无法访问应用，例如由于 `DNS` 问题。

实际用于执行健康和性能监控的机制实际上是一个谱系，包括以下内容：

*   *可达性监控*—执行一次简单的调用（`ICMP`、`TCP`、`HTTP`）以检查可达性或确保端点返回预定义的状态码。

*   *合成监控*—执行脚本以模拟典型的终端用户操作。这些模拟的终端用户有时被称为 *canaries*（源自原始用例的引用，其中那些小鸟被用来检测矿井中的瓦斯泄漏）。多个开源和商业产品允许你执行合成监控——例如，Datadog（[https://docs.datadoghq.com/synthetics/](https://docs.datadoghq.com/synthetics/)）、Elastic（[http://mng.bz/5wDO](http://mng.bz/5wDO)）、New Relic（[http://mng.bz/6Dle](http://mng.bz/6Dle)）和 Amazon CloudWatch（[http://mng.bz/o17Z](http://mng.bz/o17Z)）。请参阅图 7.1 作为示例。

你通常希望自动化检查条件的过程并通知相关负责人，这也被称为 *alerting* 或 *alarming*。有一篇不错的高层次文章，“When to Alert on What?”（[https://ali.sattari.me/posts/2023/when-to-alert-on-what/](https://ali.sattari.me/posts/2023/when-to-alert-on-what/)），它是从手动到使用服务等级目标（我们在第 10 章详细讨论）等主题入门的有用文章。

顺带一提，你如何知道某事是否异常？你需要一个基线。你可以通过手动观察和记录事物来确定基线（即“当一切健康时，服务或系统是什么样子？”），也可以采用更复杂的技巧，通常称为 *anomaly detection*（[https://www.reddit.com/r/sre/comments/zxdd2y/anomaly_detection/](https://www.reddit.com/r/sre/comments/zxdd2y/anomaly_detection/)）。在解决了检测基础之后，我们现在关注在得知事件后如何处理事件。

### 7.1.2 处理事件

现在我们已经通过部署健康和性能监控，能够检测到云原生应用中出现问题，我们接下来讨论如何处理事件。让我们先讨论“谁”，然后再讨论“什么”和“如何”。通常需要有一个人在循环中，被指派处理事件。这通常通过值班机制完成。在一段时间内，从数小时到一周甚至更久，值班人员会由监控系统通知，需要尽快掌控情况。

Tip 有些产品，有时称为 `AIOps`，试图优化人在回路中的体验（例如，Shoreline，[https://www.shoreline.io/](https://www.shoreline.io/)）。

如今，此通知通常通过应用交付（同时通过电子邮件、Slack、MS Teams 提醒、电话等），并且可能在一天中的任何时间到达。你可以想象，如果这样的通知（或呼叫）在凌晨 2 点到达你，并且你有 15 分钟的时间签到，你希望确保自己有一个结构化的方法。

谈论值班角色和模式时，有几个需要考虑的问题：

*   *传统与值班*—在传统设置中，开发和运维严格分离，运维（ops）团队值班（技术响应者）。这会造成问题，因为值班设置本身就很苛刻，而且最熟悉某项服务的人肯定不是值班的运维人员。另一种选择是建立开发和值班相结合的模式。例如，这就是 AWS 服务团队的工作方式。这为开发人员提供了正确为代码添加监控的激励，使值班人员能够尽快解决问题。

*   *工程与沟通*—不言而喻，要修复技术问题，需要有工程师值班。然而，还有另一个可能被分离出来的角色：沟通（事件经理或指挥官）。一方面，这可以是内部沟通（让利益相关者保持最新），另一方面，它可以指向客户传达问题。有人需要确定客户是否确实受到影响（与 canaries 相比）；有多少客户受到影响；以及他们在何处受到影响（如果我们谈论的是全球系统）。根据结果，你可能会看到更个性化层面的更新，例如 AWS Personal Health Dashboard（[http://mng.bz/nW75](http://mng.bz/nW75)），或与 GitHub Status（[https://www.githubstatus.com/](https://www.githubstatus.com/)）页面类似的适用于所有用户的全局视图。

关于 *what* 和 *how*，最重要的是记住要止血——也就是说，尝试修复问题，理想情况下在过程中收集数据点。分析（为什么出错）稍后再进行；不要让分析减缓你止血的努力。

为了支持值班人员，组织通常会制定操作手册和运行手册（[http://mng.bz/vn7p](http://mng.bz/vn7p)），描述事件期间需要检查的内容并记录依赖关系，以了解下游影响或上游问题的可能来源。此外，一些团队会在通常称为 *game day*（[http://mng.bz/4DNR](http://mng.bz/4DNR)）的活动中练习流程或可用材料（包括运行手册的覆盖）。

### 7.1.3 事后从事件中学习

假设值班团队做得很好并修复了问题。这并不是故事的结束。你希望有一个流程来审视事件并实现两件事：了解根本问题是什么，并确保不再重复同样的错误。

我建议遵循无责事后分析的路径（[http://mng.bz/QPO6](http://mng.bz/QPO6)）；在 AWS，我们称之为 *corrections of error*（`COE`；[https://wa.aws.amazon.com/wat.concept.coe.en.html](https://wa.aws.amazon.com/wat.concept.coe.en.html)）。这些会议帮助你确定问题的原因以及如何避免未来再次发生，通常采用五问法技术（[https://www.lucidchart.com/blog/5-whys-analysis](https://www.lucidchart.com/blog/5-whys-analysis)）。你也可能会遇到 *root cause analysis*（`RCA`；[https://www.techtarget.com/searchitoperations/definition/root-cause-analysis](https://www.techtarget.com/searchitoperations/definition/root-cause-analysis)）这一术语，它指的是用实证数据测试关于问题最初原因的各种理论。

在这一理论性较强的部分之后，让我们继续讨论如何处理值班角色的通知——换句话说，*alerting*。
