
每家主要云服务提供商都提供一种警报解决方案，通常与其产品深度集成。这些产品是一个很好的基准，你应该始终考虑，因为它们涵盖了云服务提供商的 API。包括

*   Amazon CloudWatch 警报 ([http://mng.bz/0Kjp](http://mng.bz/0Kjp))，它使用 Amazon SNS 发送电子邮件或 SMS 通知
*   Azure Monitor 警报 ([http://mng.bz/KeyP](http://mng.bz/KeyP))，支持电子邮件、SMS 和推送通知
*   Google 云警报 ([https://cloud.google.com/monitoring/alerts/](https://cloud.google.com/monitoring/alerts/))，支持从电子邮件到 Pub/Sub 的多种通知类型

如前所述，你也可以从 Grafana 使用这些警报解决方案（如果想从该面板控制警报，它提供了一个 CloudWatch 数据源），提供单一操作视图。我们现在转换话题，快速了解一下终端用户跟踪以及资源使用跟踪。

## 7.3 使用跟踪

警报在很大程度上是一个反应性过程。这意味着某些事情正在发生，并基于此，有人收到通知，对事件做出反应。本节介绍一种不同的云运营技术，你可以将其用于各种情况，从故障排除到安全再到规划。我说的是跟踪用户及其访问的内容。让我们从你的云原生应用的终端用户开始。

### 7.3.1 用户

要了解你的终端用户如何使用你的应用，你需要有一种方式来跟踪他们在应用内的活动。这使你能够识别受欢迎的功能和潜在的 UX 问题。多年来，术语 *real user monitoring*（RUM；[https://github.com/open-telemetry/oteps/issues/169](https://github.com/open-telemetry/oteps/issues/169)）为此而流行。例如，对于 Web 应用，有广泛使用的 Google Analytics（[https://analytics.google.com/analytics/web/](https://analytics.google.com/analytics/web/)），并且你可以在 AWS 中使用 CloudWatch RUM（[http://mng.bz/9Drx](http://mng.bz/9Drx)）。所有这些产品都需要预先在你的网页中嵌入一些小的 JavaScript 代码片段，以便在专用位置查看使用信息（人口统计、区域、设备类型、使用路径等）。如果你想更深入地了解该主题，我推荐阅读 Chinmay Gaikwad 的优秀文章，“An Introduction to Real User Monitoring (RUM): Monitoring and Observability”（[http://mng.bz/jPJz](http://mng.bz/jPJz)）。

注意 RUM 需要注意的一件事是单页应用（SPA；[https://en.wikipedia.org/wiki/Single-page\_application](https://en.wikipedia.org/wiki/Single-page_application)）网站的兴起。在 SPA 的上下文中，传统的指标，例如页面加载时间，不再重要（或没有意义），因为页面只在会话开始时加载一次，而 UI 更新实际上是本地渲染。要了解更多关于这个主题，请查看 O11ycast 第 60 集，“Customer-Centric Observability With Todd Gardner and Winston Hearn”（[http://mng.bz/Wz94](http://mng.bz/Wz94)），以及 Jessica Kerr 的文章，“Observable Frontends: the State of OpenTelemetry in the Browser”（[http://mng.bz/8rdZ](http://mng.bz/8rdZ)）。

RUM 也是 CNCF OpenTelemetry 项目考虑的内容；OpenTelemetry 增强提案 OTEP 169（[http://mng.bz/EQoo](http://mng.bz/EQoo)）通过提出新的数据模型和语义来涵盖这一点，支持收集和导出 RUM遥测数据，一种新的信号类型，与 traces、metrics、logs 和 profiles 并列。虽然仍处于早期阶段，你可以期待该领域有更多发展，尤其是日志信号类型在 2023 年 6 月稳定下来（意味着你可以使用 OpenTelemetry 在生产环境中处理日志）。

虽然 RUM 专注于终端用户，但还有另一类用户跟踪：内部用户，包括开发人员和运营人员。例如，你可能希望出于合规或风险审计原因，记录用户或服务账户采取的操作。这类服务的示例是 AWS CloudTrail（[http://mng.bz/N2gN](http://mng.bz/N2gN)），支持长长的服务列表，包括 Amazon API Gateway、AWS CloudFormation、Amazon CloudWatch、Amazon EKS、AWS Lambda 和 AWS Systems Manager。

你也可以从上述内部用户审计日志设置警报。话虽如此，让我们现在转向成本。

### 7.3.2 成本

跟踪资源访问的另一个完全不同的类别是成本跟踪。无论你想教育内部用户了解成本和使用情况（showback）还是提供需要向某些租户收费的服务（chargeback），你都希望尽可能精细地了解实际成本。我们可以区分计量，即计数访问（例如，API 端点 XYZ 在过去 15 分钟内被调用了 3,478 次），以及实际费用，后者可能取决于许多因素，从预先承诺到你可能根据消耗量协商的特殊优惠。

云服务提供商通常提供服务，允许你（交互式地）探索你的使用情况（例如，AWS Cost and Usage Reports \[CUR\]，[http://mng.bz/D46n](http://mng.bz/D46n)）。除了这些原生产品之外，你可能希望选择使用提供成本分配和资源使用监控的解决方案，监控到单个执行单元，例如 OpenCost（[https://www.opencost.io/](https://www.opencost.io/)）为 Kubernetes 环境所做的那样。

通过对用户和用量跟踪与报告的高层次讨论，我们已经到达了云运营章节的末尾。虽然我们讨论的大多数主题主要重要且由运营角色的人员负责理解和拥有，但对于云原生系统来说，让每个参与角色的人员，从开发人员到测试人员再到发布经理，都牢固掌握这些概念至关重要。在完全无服务器的环境中，这可能意味着，开发人员本身确实需要值班（[http://mng.bz/lW76](http://mng.bz/lW76)）。

## Summary

*   要成功运营云原生应用，你需要有一种结构化的方法来检测、处理和从事件中学习。
*   健康和性能监控使你能够拥有系统外部的视图，并了解某些功能未按预期工作。
*   如果你为某项服务值班并且发生事件，重点是止血；分析出了什么问题稍后再进行，最好在无责事后分析中进行。
*   警报的目标是让人类自动被通知到影响系统的事件。
*   你希望避免警报疲劳，因此需要制定政策，允许你接收有意义数量的通知（但不要太多）。
*   Prometheus 允许你定义警报规则，而分组、过滤、抑制和通知则由单独的组件处理：Alertmanager。
*   如果你想跨各种后端集中管理警报，可以使用 Grafana。
*   使用跟踪意味着捕获应用中的终端用户交互，或捕获对系统资源的访问以及成本。
