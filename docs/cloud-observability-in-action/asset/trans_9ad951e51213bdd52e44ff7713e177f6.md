
## 考虑事项
效果因人而异，但在评估和选择该领域的方案时，这里有几点考虑事项：

* 你能否确定成本？前端在托管方案中通常按用户计费（查看者和编辑者），且相对可预测。一体化方案通常采用类似后端的计费计划（可能也有按席位计费）。对于自托管部署，请务必考虑补丁、扩展、值班时间、安全相关要求和工作以及跟上上游更新的运营成本。数据存储、摄取和查询也可能产生成本，正如我们在第 5 章中更详细讨论的那样。
* 一体化方案通常是实现单一视图面板的最接近选择，如果你确保支持 OpenTelemetry 等开放标准，从而最大限度地减少厂商锁定，它们是极佳的选择。
* 对于所有开源方案，请确保了解项目背后的主体（即单一厂商开源与通常由 CNCF 或 ASF 主持的社区）、许可（可能发生变化）以及开源项目的健康状况。关于最后一点，仅仅查看其 GitHub 星标数量是不够的（这纯粹是流行度指标）。你需要投入时间查看其发布节奏（你应能适应该节奏）、贡献者数量（理想情况下来自不同地方的多个贡献者）和用户数量（理想情况下来自不同行业领域）、可用的文档、存在的 issue 以及 pull 或 merge 请求的数量（以及处理速度），以及支持策略（即内部或社区支持），因为支持是企业使用的关键。
* 越来越相关且被要求的功能之一，有助于你更高效地使用所选工具的是关联（[https://www.youtube.com/watch?v=qVITI34ZFuk](https://www.youtube.com/watch?v=qVITI34ZFuk)）。请确保检查可用的关联类型（基于时间、示例等；另见第 11 章）以及从一种信号类型切换到另一种所需的手动工作量，前提是所评估的工具确实支持一种以上的信号类型，这是关联工作的基础。

Tip 鉴于前端和一体化方案的本质是最终用户交互的可见部分，请确保让所有利益相关者参与其中。仅基于价格标签或因其精致程度而选择工具可能会变得具有挑战性。

现在，这是一大堆新信息！我希望你能将其利用起来，在该领域选择工具时发挥优势。这是一个发展迅速且令人兴奋的领域，因此定期重新审视你的选择是有意义的。

## 摘要
* 前端允许你与后端存储的可观测性数据集进行交互。
* 你使用前端以各种图形和文本方式找到对你（临时）问题的答案。
* 有许多开源前端（Grafana、Kibana、Metabase 等）可用，当你构建自己的内部可观测性解决方案时，请考虑使用这些而不是从头构建。
* 如果你能避免过度的厂商锁定，一体化方案是极佳的选择；它们允许你将大部分运营负担外包，并通常以溢价提供一系列功能。
* 过去的 APM 现在基本上被重新命名为分布式追踪。
* 在该领域选择工具可能很棘手，但请确保你充分了解相关成本，并对想要交付的价值（以及交付给谁）有清晰的认识。
* 选择开源工具是实现互操作性和厂商无关性的好方法；然而，请确保你了解开源项目的动态，并有明确的支持获取策略。
* 工具支持的开放标准（如 OpenTelemetry）越多，你就越不可能被锁定，并在其不再符合需求时能够转向其他工具。
* 前端通常是关联发生的地方；也就是说，你期望 UI 支持操作和可视化，以便轻松地从一种遥测信号类型切换到另一种。

# 7 云运营
本章涵盖
* 如何管理事件
* 健康监控和告警
* 治理和用量跟踪

到目前为止，本书主要关注我们云原生设置的理想路径，涵盖信号源、遥测以及存储、查询、可视化并与信号交互的目的地，以理解和影响系统。在本章中，我们将讨论我称之为 *云运营* 的云原生解决方案的一个方面，它涵盖了你在运营角色中很可能会遇到的多个主题。

我们从事件开始：如何检测事物未按预期工作、应对异常行为并从过去的错误中学习。然后，我们关注告警或警报（我在此互换使用这两个术语，尽管告警可以是触发条件，而警报可能涵盖多个告警）——即检查条件并通知负责服务或基础设施的人员的自动化过程。本章的最后一部分，我们将讨论用量跟踪，无论是内部或外部用户访问的内容，还是提供云原生应用所使用的资源成本。

为什么云运营会很棘手？嗯，在云原生解决方案的背景下，无论是运行在 Kubernetes 上的工作负载还是一堆 lambda 函数，它们的共同点都是有很多 moving parts 且可能有许多不同的所有者。因此，当你的云原生应用的最终用户受到影响时——例如响应时间比平时慢或（部分）故障——谋杀之谜就开始了：请求路径上的哪些服务导致了问题？谁拥有它，因此应该被通知来修复它？

请记住，对于最终用户来说，你运行了数百个微服务这一事实是未知的，而且坦率地说，不应该重要。他们感知到的是某些东西无法正常工作，而你的组织有责任确保你能检测到此类问题——理想情况下，在用户向你反馈之前——并制定策略，不仅能尽快修复问题，还能从问题中学习以确保它不再发生。在此背景下，我们可以考虑客户体验跟踪（并不总是清楚谁拥有此项）与基础设施跟踪（通常所有权明确定义）。让我们从事件开始，了解如何以结构化方式检测和响应它们。

## 7.1 事件管理
在本书的背景下，我们将考虑两种事件：服务或平台的意外行为负面影响其功能或性能，以及尚未应用经验教训的意外行为重复。对于后一种重复的意外行为的情况，拥有先前事件如何解决的运行手册对于处理重复情况会很有帮助。

通常，最好建立事件响应流程。此事件响应流程通常是一套定义如何解决和从事件中学习的过程。你可以将其视为三个阶段：
1. 首先，你需要能够检测到某些事情出了问题（健康和性能监控）。
2. 然后，你需要能够以结构化方式对事件做出反应并处理它。
3. 最后但同样重要的是，你需要从事件中学习。你希望避免未来重复类似情况（应完成哪些行动项目以防止同一问题再次发生）。我们将从介绍如何检测问题开始。

### 7.1.1 健康和性能监控
