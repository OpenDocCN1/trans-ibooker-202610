## 谈论内存

并非所有内存都是平等的。在大多数编程环境中，你的程序可以访问栈、堆、寄存器、文本段、内存映射寄存器、内存映射文件，或许还有非易失性 RAM。在特定情况下选择使用哪一种，会影响你可以在其中存储什么、它保持可访问的时间有多长，以及你使用什么机制来访问它。这些内存区域的确切细节因平台而异，超出了本书的范围，但其中一些对于你如何推演 Rust 代码至关重要，值得在此介绍。

### 内存术语

在我们深入探讨内存区域之前，你首先需要了解值（value）、变量（variable）和指针（pointer）之间的区别。Rust 中的值是类型与该类型值域中一个元素的组合。值可以通过其类型的表示转换为字节序列，但就其本身而言，你可以将值更多地理解为“你作为程序员所表达的含义”。例如，`u8` 类型中的数字 6 是数学整数 6 的一个实例，它在内存中的表示是字节 `0x06`。类似地，`str` "Hello world" 是所有字符串值域中的一个值，其表示是其 UTF-8 编码。值的含义与这些字节存储的位置无关。

值存储在一个“场所”（place）中，这是 Rust 术语，指“可以保存值的位置”。这个位置可以在栈上、堆上，或许多其他位置。存储值最常见的场所是变量，即栈上命名的值槽。

指针是保存某个内存区域地址的值，因此指针指向一个场所。指针可以被解引用，以访问其所指向内存位置中存储的值。我们可以将同一个指针存储在多个变量中，从而让多个变量间接引用内存中的同一位置，进而引用同一个底层值。

考虑清单 2-1 中的代码，它说明了这三个元素。

```rust
let x = 42;
let y = 43;
let var1 = &x;
let mut var2 = &x;
var2 = &y;
```

*清单 2-1：值、变量和指针*

这里有四个不同的值：42（一个 `i32`）、43（一个 `i32`）、x 的地址（一个指针）和 y 的地址（一个指针）。还有四个变量：x、y、var1 和 var2。后两个变量都持有指针类型的值，因为引用就是指针。虽然 var1 和 var2 初始存储相同的值，但它们存储的是该值的独立副本；当我们改变 var2 中存储的值时，var1 中的值不会改变。特别要注意，`=` 运算符将右侧表达式的值存储到左侧命名的场所中。

一个体现变量、值和指针之间区别的有趣例子是如下语句：

```rust
let string = "Hello world";
```

尽管我们向变量 string 赋值了一个字符串值，但该变量的*实际*值是指向字符串值 "Hello world" 第一个字符的指针，而不是字符串值本身。此时你可能会说：“等等，那么字符串值存储在哪里？指针指向哪里？”如果你这样问，那你的眼光很敏锐——我们马上就会讲到。

## 深入变量

我之前给出的变量定义较为宽泛，本身可能不太有用。当你遇到更复杂的代码时，你需要一个更准确的心智模型来帮助你推理程序的真实行为。有很多这样的模型可供我们使用。详细描述它们会占用数章篇幅，超出本书范围，但大致可分为两类：高层模型和低层模型。高层模型适用于在生命周期和借用层面思考代码，低层模型则适用于推演不安全代码和裸指针。下面两节描述的变量模型足以应对本书大部分内容。

### 高层模型

在高层模型中，我们不把变量视为保存字节的场所。相反，我们只将它们视为值在程序中实例化、移动和使用时赋予这些值的名称。当你向一个变量赋值时，该值从此就由该变量命名。当后续访问该变量时，你可以想象从该变量的前一次访问画一条线到新访问，这就在两次访问之间建立了依赖关系。如果变量中的值被移动，则不能再从它画出任何线。

在这个模型中，变量只在持有合法值时才存在；你无法从值未初始化或已被移动的变量画出线，因此它实际上并不存在。使用这个模型，你的整个程序由许多这样的依赖线组成，通常称为*流*（flow），每条流都追踪某个特定值实例的生命周期。当存在分支时，流可以分叉和汇合，每个分支都追踪该值的一个不同生命周期。编译器可以检查在程序的任何给定点，所有可以并行存在的流之间是否兼容。例如，不能有两条对某个值进行可变访问的并行流。也不能存在一条借用某个值的流，而同时没有一条拥有该值的流。清单 2-2 展示了这两种情况的示例。

```rust
let mut x;
// 这种访问是非法的，因为无处可画流：
// assert_eq!(x, 42);
❶ x = 42;
    // 这没问题，可以从上面赋的值画一条流：
❷ let y = &x;
    // 这建立了来自 x 的第二条可变流：
❸ x = 43;
    // 这延续了来自 y 的流，而 y 又源自 x：
❹ assert_eq!(*y, 42);
```

*清单 2-2：借用检查器会捕获的非法流*

首先，我们不能在 x 初始化之前使用它，因为我们无处画流。只有当我们向 x 赋值后，才能从它画出流。这段代码有两条流：一条是独占（`&mut`）流，从 ❶ 到 ❸；一条是共享（`&`）流，从 ❶ 经过 ❷ 到 ❹。借用检查器检查每条流的每个顶点，并检查是否存在其他不兼容的流并发存在。在这种情况下，当借用检查器检查 ❸ 处的独占流时，它会看到终止于 ❹ 的共享流。由于你不能同时对某个值进行独占使用和共享使用，借用检查器（正确地）拒绝了这段代码。注意，如果 ❹ 不存在，这段代码可以正常编译！共享流会在 ❷ 处终止，当在 ❸ 处检查独占流时，不存在冲突的流。

如果声明了一个与之前同名的新变量，它们仍被视为不同的变量。这称为*遮蔽*（shadowing）——后面的变量通过相同的名称“遮蔽”了前面的变量。这两个变量共存，不过后续代码无法再命名先前的那个变量。这个模型大致对应于编译器（尤其是借用检查器）推演程序的方式，实际上也用于编译器内部以生成高效的代码。

### 低层模型

变量为内存位置命名，这些位置可能持有合法值，也可能不持有。你可以将变量视为一个“值槽”。当你向其赋值时，槽被填满，其旧值（如果有的话）被丢弃并替换。当你访问它时，编译器会检查槽是否为空，因为为空意味着变量未初始化或其值已被移动。指向变量的指针引用该变量的后备内存，可以通过解引用来获取其值。例如，在语句 `let x: usize;` 中，变量 x 是一个


栈上用于存放一个大小为 `usize` 的值的内存区域的名称，尽管它并没有一个定义明确的值（它的槽位是空的）。如果你为该变量赋值，例如使用 `x = 6`，那么这块内存区域随后就会存储表示值 6 的位。为 `x` 赋值时，`&x` 不会发生变化。如果你声明多个同名变量，它们最终仍会由不同的内存作为后备存储。这一模型与 C、C++ 以及许多其他底层语言所使用的内存模型相匹配，对于需要明确推理内存的场景很有用。

> 在本例中，我们忽略 CPU 寄存器，并将其视为一种优化。实际上，如果某个变量不需要内存地址，编译器可能会使用寄存器为其提供存储，而不是使用一块内存区域。

你可能会发现，其中一种模型与你之前的模型更加吻合，但我强烈建议你尝试理解这两种模型。它们都同样有效，而且都是简化模型——任何有用的心智模型都必须如此。如果你能够从这两种视角来审视一段代码，就会发现分析复杂的代码片段、理解它们为何能够或不能编译，以及为何运行结果符合或不符合预期，会容易得多。

## 内存区域

现在你已经掌握了我们如何引用内存，接下来需要讨论内存实际上是什么。内存有许多不同的区域，或许令人意外的是，并非所有区域都存储在计算机的 DRAM 中。你使用哪一部分内存，会对代码的编写方式产生重要影响。对于编写 Rust 代码而言，最重要的三个内存区域是栈、堆和静态内存。

### 栈

栈是程序用于函数调用临时存储空间的一段内存。每次调用函数时，栈顶都会分配一块称为栈帧的连续内存。栈的底部附近是主函数的栈帧；当函数调用其他函数时，更多栈帧会被压入栈中。函数的栈帧包含该函数中的所有变量，以及函数接收的所有参数。当函数返回时，它的栈帧会被回收。

组成函数局部变量值的字节不会立即被清除，但访问它们并不安全，因为后续函数调用的栈帧可能与已回收的栈帧重叠，从而覆盖这些字节。即使它们尚未被覆盖，也可能包含不允许使用的值，例如函数返回时已经被移动的值。

栈帧，以及它们最终会消失这一关键事实，与 Rust 中的生命周期概念密切相关。存储在栈帧中的任何变量，在该栈帧消失后都无法访问，因此对它的任何引用，其生命周期最多只能与该栈帧的生命周期一样长。

### 堆

*堆*是一块与程序当前调用栈无关的内存池。堆内存中的值会一直存在，直到被显式释放。当你希望某个值的存活时间超过当前函数栈帧的生命周期时，这一点非常有用。如果该值是函数的返回值，调用函数可以在自己的栈上留出一块空间，让被调用函数在返回前将该值写入其中。但如果你希望将该值发送给另一个线程，而当前线程与该线程可能完全没有共享的栈帧，就可以将它存储在堆上。

堆允许你显式分配连续的内存区域。这样做时，你会获得一个指向该内存区域起始位置的指针。在之后将其释放之前，这段内存都会为你保留；这个过程通常称为 *freeing*，名称源自 C 标准库中对应的函数。由于从堆中分配的内存在函数返回时不会消失，因此你可以在一个位置为某个值分配内存，将指向它的指针传递给另一个线程，然后让该线程安全地继续操作这个值。换句话说，当你在堆上分配内存时，所得指针的生命周期不受限制——它的生命周期有多长，取决于你的程序让它保持存活多久。

在 Rust 中，与堆交互的主要机制是 Box 类型。当你编写 `Box::new(value)` 时，`value` 会被放置在堆上，而你获得的返回值（`Box<T>`）是一个指向堆上该值的指针。当 Box 最终被丢弃时，这块内存就会被释放。

如果你忘记释放堆内存，它就会永远存在，最终你的应用程序会耗尽计算机上的所有内存。这称为 *内存泄漏*，通常是你希望避免的情况。不过，有些情况下你确实希望显式泄漏内存。例如，假设你有一份整个程序都应能够访问的只读配置。你可以将它分配到堆上，并使用 `Box::leak` 显式泄漏它，从而获得指向它的 `'static` 引用。

### 静态内存

*静态内存*实际上是一个统称，指代程序编译到的文件中几个密切相关的区域。程序执行时，这些区域会自动加载到程序的内存中。静态内存中的值会在程序的整个执行期间存活。程序的静态内存包含程序的二进制代码，这些代码通常会被映射为只读。程序执行时，会在文本段中逐条执行二进制代码中的指令，并在调用函数时跳转到相应位置。静态内存还存储使用 `static` 关键字声明的变量所占用的内存，以及代码中的某些常量值，例如字符串。

## 丢弃顺序

当值离开作用域时，Rust 会自动丢弃这些值，例如清单 2-3 中内层作用域里的 `x1` 和 `x2`。丢弃顺序的规则相当简单：变量（包括函数参数）按逆序丢弃，而嵌套值则按源代码中的顺序丢弃。

这乍听起来可能有些奇怪——为什么会存在这种差异？不过，仔细观察后就会发现，这非常合理。假设你编写了一个函数，先声明一个字符串，然后将对该字符串的引用插入一个新的哈希表中。当函数返回时，必须先丢弃哈希表；如果先丢弃字符串，哈希表就会持有一个无效引用！一般来说，后声明的变量可能包含对先前值的引用，而由于 Rust 的生命周期规则，反过来的情况不可能发生。因此，Rust 按逆序丢弃变量。

对于嵌套值，例如元组、数组或结构体中的值，我们本来也可以采用相同的行为，但这很可能会让用户感到意外。如果你构造了一个包含两个值的数组，那么最后一个元素先被丢弃似乎很奇怪。元组和结构体也是如此，最直观的行为是先丢弃元组的第一个元素或结构体的第一个字段，然后是第二个，依此类推。与变量不同，在这种情况下没有必要反转丢弃顺序，因为 Rust 目前不允许单个值中存在自引用。因此，Rust 选择了更符合直觉的方案。

## 借用与生命周期

Rust 允许值的所有者通过引用将该值借给其他人，而不放弃所有权。引用是指针，同时附带了关于其使用方式的额外契约，例如该引用是否对被引用的值提供独占访问，或者被引用的值是否还可以被其他引用指向。

### 共享引用

共享引用 `&T` 顾名思义，是一种可以被共享的指针。同一个值可以存在任意数量的其他引用，并且每个共享引用都实现了 `Copy`，因此你可以轻松地创建更多共享引用。共享引用背后的值不可变；你不能修改或重新赋值共享引用所指向的值，也不能将共享引用转换为可变引用。

Rust 编译器可以假设，共享引用所指向的值在该引用存活期间不会发生变化。例如，如果 Rust 编译器发现某个函数多次读取共享引用背后的值，那么它完全可以只读取一次，然后重复使用该值。更具体地说，清单 2-4 中的断言不应该失败。




```rust
fn cache(input: &i32, sum: &mut i32) {
    *sum = *input + *input;
    assert_eq!(*sum, 2 * *input);
}
```

*清单 2-4：Rust 假定共享引用是不可变的。*

编译器是否选择应用某个优化或多或少并不重要。编译器的启发式规则会随时间变化，因此你通常应该针对编译器被允许做什么来编写代码，而不是针对它在特定时刻的特定情况下实际做什么。

## 可变引用

共享引用的替代方案是可变引用：`&mut T`。对于可变引用，Rust 编译器同样可以充分利用引用自带的约定：编译器假定没有任何其他线程访问目标值，无论是通过共享引用还是可变引用。换句话说，它假定可变引用是*独占的*。这带来了一些在其他语言中不易实现的巧妙优化。例如，以清单 2-5 中的代码为例。

```rust
fn noalias(input: &i32, output: &mut i32) {
    if *input == 1 {
❶       *output = 2;
    }
❷   if *input != 1 {
        *output = 3;
    }
}
```

*清单 2-5：Rust 假定可变引用是独占的。*

在 Rust 中，编译器可以假定 `input` 和 `output` 不指向同一块内存。因此，在❶处对 `output` 的重新赋值不会影响❷处的检查，整个函数可以编译成一个单一的 `if-else` 块。如果编译器不能依赖独占可变性的约定，这种优化就是无效的，因为在类似 `noalias(&x, &mut x)` 的情况下，输入为 1 时可能会产生输出为 3 的结果。

可变引用只允许你修改引用所指向的内存位置。你能否修改超出直接引用范围的值，取决于位于中间的类型所提供的方法。通过一个例子可能更容易理解，请看清单 2-6。

```rust
let x = 42;
let mut y = &x; // y is of type &i32
let z = &mut y; // z is of type &mut &i32
```

*清单 2-6：可变性仅适用于直接引用的内存。*

在这个示例中，你可以通过让指针引用不同的变量，将指针的值改为另一个值（也就是另一个指针），但你不能改变被指向的值（也就是 x 的值）。类似地，你可以通过 z 改变 y 的指针值，但你不能改变 z 本身来持有另一个不同的引用。

拥有一个值和拥有对它的可变引用之间的主要区别在于，所有者负责在值不再需要时将其丢弃。除此之外，你可以通过可变引用做任何你拥有该值时可以做的事情，但有一个警告：如果你移动了可变引用后面的值，那么你必须留下另一个值来代替它。如果你不这么做，所有者仍然会认为它需要丢弃这个值，但那时已经没有值可供丢弃了！

清单 2-7 给出了你可以移动可变引用后面的值的几种方式的示例。

```rust
fn replace_with_84(s: &mut Box<i32>) {
    // this is not okay, as *s would be empty:
❶   // let was = *s;
    // but this is:
❷   let was = std::mem::take(s);
    // so is this:
❸   *s = was;
    // we can exchange values behind &mut:
    let mut r = Box::new(84);
❹   std::mem::swap(s, &mut r);
    assert_ne!(*r, 84);
❺ }
let mut s = Box::new(42);
replace_with_84(&mut s);
```

*清单 2-7：通过可变引用访问后必须留下一个值。*

我加入了一些注释行，它们表示非法操作。你不能直接移动出值❶，因为调用者仍然认为自己拥有该值，并会在❺处再次释放它，从而导致双重释放。如果你只是想在后面留下一个有效的值，`std::mem::take` ❷ 是一个不错的选择。它等价于 `std::mem::replace(&mut value, Default::default())`；它把 `value` 从可变引用后面移出，但会在原位置留下一个新的、该类型的默认值。这个默认值是一个独立的、被拥有的值，因此调用者在❺处作用域结束时丢弃它是安全的。

或者，如果你不需要引用后面的旧值，你可以用一个你已经拥有的值❸覆盖它，留给调用者稍后丢弃该值。当你这样做时，原本位于可变引用后面的值会立即被丢弃。

最后，如果你有两个可变引用，你可以在不拥有其中任何一个的情况下交换它们的值❹，因为两个引用最终都会得到一个合法的被拥有的值，供其所有者最终释放。

## 内部可变性

有些类型提供*内部可变性*，这意味着它们允许你通过共享引用修改一个值。这些类型通常依赖额外的机制（如原子 CPU 指令）或不变量来提供安全可变性，而不依赖独占引用的语义。它们通常分为两类：一类允许你通过共享引用获得可变引用，另一类只允许你通过共享引用直接修改值。

第一类包括 `Mutex` 和 `RefCell` 等类型，它们包含安全机制，确保对于它们给出可变引用的任何值，同一时间只能存在一个可变引用（且不能存在共享引用）。在底层，这些类型（以及类似类型）都依赖于一个叫做 `UnsafeCell` 的类型，这个名字应该立刻让你对使用它产生犹豫。我们将在第 10 章更详细地介绍 `UnsafeCell`，但现在你应该知道，它是通过共享引用进行修改的*唯一*正确方式。

提供内部可变性的其他类型类别是那些不给出内部值的可变引用，而只是提供给你就地操作该值的方法的类型。`std::sync::atomic` 中的原子整数类型和 `std::cell::Cell` 类型属于这一类。你无法直接获得这类类型背后的 `usize` 或 `i32` 的引用，但你可以在给定时间点读取和替换它的值。

> **注意**
> 标准库中的 `Cell` 类型是通过不变量实现安全内部可变性的一个有趣例子。它不能跨线程共享，也从不给出对 `Cell` 中所包含值的引用。相反，所有方法要么完全替换该值，要么返回所包含值的副本。由于对内部值不存在任何引用，因此移动它总是可以的。而且由于 `Cell` 不能跨线程共享，即使修改是通过共享引用进行的，内部值也永远不会被并发修改。

## 生命周期

如果你正在读这本书，你可能已经对生命周期的概念有所熟悉，很可能是通过编译器反复提示的违反生命周期规则的警告。这种程度的理解对于你将编写的大部分 Rust 代码来说已经够用，但随着我们深入 Rust 更复杂的部分，你需要一个更严谨的心智模型来工作。

较新的 Rust 开发者常常被教导将生命周期视为与作用域相对应：生命周期在你取得对某个变量的引用时开始，在该变量被移动或超出作用域时结束。这通常是正确的，也通常很有用，但实际情况要稍微复杂一些。*生命周期*实际上是某个引用必须在其中有效的代码区域的一个名称。虽然生命周期经常与作用域重合，但并非必须如此，我们将在本节后面看到这一点。

## 生命周期与借用检查器

Rust 生命周期的核心是借用检查器。每当使用一个带有某个生命周期 `'a` 的引用时，借用检查器都会检查 `'a` 是否仍然存活。它通过从使用点回溯到 `'a` 开始的地方（即引用被取得的地方）来做到这一点，并检查该路径上是否存在冲突的使用。这确保了引用仍然指向一个可以安全访问的值。这类似于我们本章前面讨论的高层“数据流”心智模型；编译器会检查我们正在访问的引用的流是否与任何其他并行流冲突。

清单 2-8 展示了一个简单的代码示例，其中包含对 `x` 引用的生命周期标注。

```rust
let mut x = Box::new(42);
① let r = &x;          // 'a
if rand() > 0.5 {
②   *x = 84;
} else {
③   println!("{}", r);  // 'a
④ }
```

*清单 2-8：生命周期不需要是连续的。*

生命周期在①处我们取得对 `x` 的引用时开始。在第一个分支②中，我们立即尝试通过将其值改为 84 来修改 `x`，这需要一个 `&mut x`。借用检查器取得对 `x` 的可变引用，并立即检查其使用情况。它在引用取得和使用之间没有发现冲突的使用，因此接受这段代码。如果你习惯于将生命周期视为作用域，这可能会让你感到惊讶，因为 `r` 在②处仍然在作用域内（它在③处才超出作用域）。但借用检查器足够聪明，能够意识到如果走这个分支，`r` 之后永远不会被使用，因此在这里对 `x` 进行可变访问是没问题的。或者换个说法，①处创建的生命周期并没有延伸到这个分支中：从 `r` 出发的流没有超过②，因此不存在冲突的流。借用检查器随后在③处的打印语句中发现了 `r` 的使用。它回溯到①，发现没有冲突的使用（②不在这条路径上），因此它也接受这次使用。

如果我们再在清单 2-8 的④处添加一次对 `r` 的使用，代码将无法编译。生命周期 `'a` 将会从①一直持续到④（`r` 的最后一次使用），当借用检查器检查我们对 `r` 的新使用时，它会在②处发现冲突的使用。

生命周期可能会变得相当复杂。在清单 2-9 中，你可以看到一个带有空洞的生命周期示例，它在开始和最终结束之间会间歇性地无效。

```rust
let mut x = Box::new(42);
① let mut z = &x;      // 'a
for i in 0..100 {
```





```
2   println!("{}", z);      // 'a
3   x = Box::new(i);
4   z = &x;                  // 'a
}
println!("{}", z);          // 'a
```

清单 2-9：生命周期可以存在空洞。

生命周期在①处开始，此时我们获取了对 `x` 的引用。接着，我们在③处将 `x` 移出，这会结束生命周期 `'a`，因为它已经不再有效。借用检查器通过将 `'a` 视为在②处结束来接受这次移动，因为这样在③处就不会存在从 `x` 流出的冲突。然后，我们通过在④处更新 `z` 中的引用来重新开始生命周期。无论代码此时是循环回到②，还是继续执行最后的打印语句，这两种使用方式现在都有一个有效值可供流出，并且不存在冲突流，因此借用检查器接受这段代码！

同样，这与我们之前讨论的内存数据流模型完全一致。当 `x` 被移动时，`z` 就停止存在。稍后我们重新赋值给 `z` 时，实际上创建了一个全新的变量，它只从那一刻起存在。基于这个模型，这个例子并不奇怪。

## 泛型生命周期

有时，你需要在自定义类型中存储引用。这些引用需要具有生命周期，这样借用检查器才能在它们被该类型的各种方法使用时检查其有效性。如果你希望类型中的某个方法返回一个生命周期长于对 `self` 的引用的引用，这一点尤其重要。

Rust 允许你让类型定义对一个或多个生命周期参数具有泛型性，就像允许你让类型定义对类型参数具有泛型性一样。Steve Klabnik 和 Carol Nichols 所著的《Rust 程序设计语言》（No Starch Press，2018 年）较为详细地介绍了这一主题，因此我不会在这里重复基础内容。不过，当你编写更复杂的此类类型时，需要注意这类类型与生命周期交互时的两个细节。

首先，如果你的类型还实现了 `Drop`，那么丢弃该类型会被视为使用了类型所泛型化的任何生命周期或类型。实际上，当你的类型的一个实例被丢弃时，借用检查器会在丢弃它之前检查：使用该类型的任意泛型生命周期是否仍然合法。如果你的丢弃代码确实使用了其中某些引用，这是必需的。如果你的类型没有实现 `Drop`，丢弃该类型就不算作一次使用；只要之后不再使用这些引用，用户就可以自由地使存储在类型中的引用失效，就像清单 2-7 中看到的那样。我们将在第 10 章进一步讨论与丢弃相关的这些规则。

其次，虽然一个类型可以对多个生命周期参数具有泛型性，但这样做往往只会给类型签名带来不必要的复杂性。通常，让一个类型对单个生命周期参数具有泛型性就足够了；对于插入该类型中的任何引用，编译器会将这个生命周期解析为这些引用生命周期中较短的那个。只有当一个类型包含多个引用，并且其方法返回的引用应当只与其中某一个引用的生命周期绑定时，你才真正需要使用多个泛型生命周期参数。

请考虑清单 2-10 中的类型，它为你提供了一个迭代器，用于遍历由某个特定字符串分隔的字符串片段。

```
struct StrSplit<'s, 'p> {
    delimiter: &'p str,
    document: &'s str,
}
impl<'s, 'p> Iterator for StrSplit<'s, 'p> {
    type Output = &'s str;
    fn next(&self) -> Option<Self::Output> {
        todo!()
    }
}
fn str_before(s: &str, c: char) -> Option<&str> {
    StrSplit { document: s, delimiter: &c.to_string() }.next()
}
```

清单 2-10：需要对多个生命周期参数具有泛型性的类型

构造这种类型时，你必须提供要搜索的分隔符和文档，这两者都是对字符串值的引用。当你请求下一个字符串时，会得到一个指向文档内部的引用。请考虑一下，如果在这个类型中使用单个生命周期，会发生什么。迭代器生成的值将同时与文档和分隔符的生命周期绑定。这会使 `str_before` 无法编写：返回类型将带有一个与函数内部局部变量相关联的生命周期——也就是 `to_string` 生成的 `String`——而借用检查器会拒绝这段代码。

## 生命周期方差

方差是程序员经常接触、却很少知道其名称的概念，因为它大多是不可见的。乍看之下，方差描述了哪些类型是其他类型的子类型，以及何时可以用子类型代替超类型（反之亦然）。一般来说，如果类型 A 至少和类型 B 一样有用，那么 A 就是 B 的子类型。方差解释了为什么在 Java 中，如果 `Turtle` 是 `Animal` 的子类型，就可以将 `Turtle` 传递给接受 `Animal` 的函数；也解释了为什么在 Rust 中，可以将 `&'static str` 传递给接受 `&'a str` 的函数。

虽然方差通常隐藏在幕后，但它出现得足够频繁，以至于我们需要掌握其基本知识。`Turtle` 是 `Animal` 的子类型，因为 `Turtle` 比某个未指定的 `Animal` 更“有用”——`Turtle` 能做 `Animal` 能做的一切，而且很可能还能做更多。同样，`'static` 是 `'a` 的子类型，因为 `'static` 的存活时间至少和任意 `'a` 一样长，因此更有用。或者更一般地说，如果 `'b: 'a`（`'b` 的生命周期长于 `'a`），那么 `'b` 就是 `'a` 的子类型。这显然不是形式化定义，但已经足够接近，具有实际应用价值。

所有类型都有方差，它定义了哪些其他相似类型可以替代该类型。方差有三种：协变、不变和逆变。如果可以直接用子类型替代某个类型，那么该类型就是协变的。例如，如果一个变量的类型是 `&'a T`，你可以向它提供类型为 `&'static T` 的值，因为 `&'a T` 关于 `'a` 是协变的。`&'a T` 关于 `T` 也是协变的，因此你可以将 `Vec<&'static str>` 传递给接受 `&Vec<&'a str>` 的函数。

有些类型是不变的，这意味着你必须提供完全相同的类型。`&mut T` 就是一个例子——如果某个函数接受 `&mut Vec<&'a str>`，你就不能向它传递 `&mut Vec<&'static str>`。也就是说，`&mut T` 关于 `T` 是不变的。如果允许这样做，该函数就可以将一个生命周期较短的字符串放入 `Vec`，而调用者会继续使用这个 `Vec`，并认为它的类型是 `Vec<&'static str>`，从而错误地认为其中的字符串是 `'static` 的！任何提供可变性的类型通常出于同样的原因而是不变的，例如，`Cell<T>` 关于 `T` 就是不变的。

最后一种类别是逆变，它会出现在函数参数中。如果函数参数可以是“不那么有用”的类型，函数类型就会更有用。当你对比参数类型本身的方差与它们作为函数参数时的方差，这一点会更清楚：

```
let x: &'static str; // 更有用，存活时间更长
let x: &'a str; // 不那么有用，存活时间更短

fn take_func1(&'static str) // 限制更严格，因此不那么有用
fn take_func2(&'a str) // 限制不那么严格，因此更有用
```

这种关系发生了反转，说明 `Fn(T)` 关于 `T` 是逆变的。

那么，为什么学习生命周期时还需要了解方差？当你考虑泛型生命周期参数如何与借用检查器交互时，方差就变得相关了。请考虑清单 2-11 所示的类型，它在单个字段中使用了多个生命周期。

```
struct MutStr<'a, 'b> {
    s: &'a mut &'b str
}
let mut s = "hello";
① *MutStr { s: &mut s }.s = "world";
println!("{}", s);
```

清单 2-11：需要对多个生命周期参数具有泛型性的类型

乍看之下，这里的两个生命周期似乎没有必要——我们没有任何方法需要像清单 2-10 中的 `StrSplit` 那样区分结构不同部分的借用。但如果你将这里的两个生命周期替换为单个 `'a`，代码就无法再编译！这一切都是由方差导致的。

在①处，编译器必须确定生命周期参数应当被设置为何值。如果有两个生命周期，`'a` 会被设置为对 `s` 的借用的待确定生命周期，而 `'b` 会被设置为 `'static`，因为所提供字符串 `"hello"` 的生命周期就是 `'static`。如果只有一个生命周期 `'a`，编译器就会推断出该生命周期必须是 `'static`。





当我们之后尝试通过共享引用来访问字符串引用 s 以打印它时，编译器会尝试缩短 MutStr 所使用的 s 的可变借用，以允许对 s 的共享借用。

在双生命周期的情况下，'a 恰好会在 println 之前结束，而 'b 保持不变。另一方面，在单生命周期的情况下，我们遇到了问题。编译器想要缩短对 s 的借用，但要做到这一点，它还必须缩短对 str 的借用。虽然 &'static str 通常可以缩短为任意 &'a str（&'a T 在 'a 上是协变的），但这里它位于 &mut T 之后，而 &mut T 在 T 上是不变的。不变性要求相关类型永远不会被子类型或超类型替换，因此编译器缩短借用的尝试失败了，并报告该列表仍被可变借用。哎！

由于不变性带来的灵活性降低，你希望确保你的类型在尽可能多的泛型参数上保持协变（或在适当情况下保持逆变）。如果这需要引入额外的生命周期参数，你需要仔细权衡增加另一个参数的认知成本与不变性的易用性成本。
