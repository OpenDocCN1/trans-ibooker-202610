# 5 错误处理

## 错误处理

![](img/bbeab1f2edc3d45a3e6f7f6efbbb1747_60_0.png)

对于除最简单程序之外的所有程序，你都会有一些可能失败的方法。在本章中，我们将探讨表示、处理和传播这些失败的不同方式，以及每种方式的优缺点。我们将首先探索表示错误的不同方法，包括枚举和类型擦除，然后研究一些需要不同表示技术的特殊错误情况。接下来，我们将了解处理错误的各种方式以及错误处理的未来。

值得注意的是，Rust 中错误处理的最佳实践仍然是一个活跃的讨论话题，而在撰写本文时，生态系统尚未形成统一的方法。因此，本章将侧重于基本原理和技术，而不是推荐特定的 crate 或模式。

`source` 的实现很直接：我们对 `self` 进行匹配，提取并返回内部的 `std::io::Error`。

其次，你的类型应该同时实现 `Display` 和 `Debug`，以便调用者可以有意义地打印你的错误。如果你实现了 `Error` trait，这是必需的。一般来说，`Display` 的实现应该提供一行关于出错原因的描述，并且可以很容易地嵌入到其他错误消息中。显示格式应该使用小写字母，且不带结尾标点，以便很好地融入其他更大的错误报告中。`Debug` 则应提供更具描述性的错误信息，包括可能有助于追踪错误原因的辅助信息，例如端口号、请求标识符、源代码位置等。

> **注意** 在较旧的 Rust 代码中，你可能会看到对 `Error::description` 方法的引用，但该方法已被弃用，取而代之的是 `Display`。

第三，你的类型如果可能的话，应该同时实现 `Send` 和 `Sync`，以便用户能够在线程之间共享错误。如果你的错误类型不是线程安全的，你会发现几乎不可能在多线程上下文中使用你的 crate。实现 `Send` 和 `Sync` 的错误类型也更容易与非常常见的 `std::io::Error` 类型一起使用，后者能够包装实现了 `Error`、`Send` 和 `Sync` 的错误。当然，并非所有错误类型都能合理地实现 `Send` 和 `Sync`，例如它们如果与特定的线程局部资源绑定，那也没关系。你可能也不会将这些错误跨线程发送。然而，在将 `Rc<String>` 和 `RefCell<bool>` 类型放入错误之前，你需要意识到这一点。

最后，在可能的情况下，你的错误类型应该是 `'static`。这样做最直接的好处是，它能让调用者更容易将你的错误向上传播到调用栈，而不会遇到生命周期问题。它还能让你的错误类型更容易与类型擦除的错误类型一起使用，我们稍后会看到。

## 不透明错误

现在让我们考虑另一个例子：一个图像解码库。你给这个库一堆要解码的字节，它向你提供各种图像操作方法。如果解码失败，用户需要能够弄清楚如何解决问题，因此必须理解原因。但是，原因是图像头中的大小字段无效，还是压缩算法无法解压缩某个块，这重要吗？可能并不重要——即使应用程序知道确切原因，它也无法从任何一种情况中有意义地恢复。在这种情况下，作为库作者，你可能更希望提供一个单一的、不透明的错误类型。这也会让你的库更好用一些，因为到处都是只有一种错误类型。这种错误类型应该实现 `Send`、`Debug` 和 `Display`，并且可能还应该实现 `Error`，但除此之外，调用者不需要知道更多。你可以在内部表示更细粒度的错误状态，但没有必要向库的用户暴露这些。这样做只会不必要地增加 API 的规模和复杂性。

你的不透明错误类型具体应该是什么，主要取决于你。它可以只是一个所有字段都私有的类型，只暴露有限的用于显示和检查错误的方法；也可以是一种严重类型擦除的错误类型，例如 `Box<dyn Error + Send + Sync + 'static>`，它除了表明自己是一个错误之外不透露任何信息，通常根本不让你的用户进行内省。决定在类型擦除的道路上走多远，主要取决于错误除了描述之外是否还有其他值得关注的信息。使用 `Box<dyn Error>` 时，你的用户几乎没有选择，只能向上冒泡你的错误。如果这个错误确实没有对用户有价值的信息，比如它只是一个动态错误消息，或者是程序深处大量不相关错误之一，那这可能没问题。但如果错误有一些有趣的方面，比如行号或状态码，你可能希望通过一个具体但不透明的类型来暴露这些。

> **注意**

> 一般来说，社区共识是错误应该是罕见的，因此不应给“快乐路径”增加太多成本。出于这个原因，错误通常放在指针类型后面，例如 `Box` 或 `Arc`。这样，它们不太可能给它们所在的整个 `Result` 类型增加太多体积。

使用类型擦除的错误的一个好处是，它允许你轻松地组合来自不同来源的错误，而无需引入额外的错误类型。也就是说，类型擦除的错误通常可以很好地组合。如果你编写一个返回类型为 `Box<dyn Error + ...>` 的函数，那么你几乎可以在该函数内不加区分地对各种不同的错误使用 `?`，它们都会被转换成这个共同的错误类型。

`Box<dyn Error + Send + Sync + 'static>` 上的 `'static` 约束值得在类型擦除的语境下多花一些时间讨论。我在上一节中提到，它有助于让调用者传播错误，而不必担心失败方法引用的生命周期，但它还有一个更大的用途：支持向下转型（downcasting）。向下转型是将一种类型的项转换为更具体的类型的过程。这是 Rust 在少数几个允许你在运行时访问类型信息的情况之一；它是动态语言通常提供的更通用的类型反射的一个有限案例。在错误的语境中，向下转型允许用户将一个 `dyn Error` 转换为具体的底层错误类型——前提是该 `dyn Error` 最初就是那个类型。例如，如果用户收到的错误是 `std::io::ErrorKind::WouldBlock` 类型的 `std::io::Error`，他们可能希望采取某种特定操作，但在其他任何情况下都不会采取同样的操作。如果用户得到一个 `dyn Error`，他们可以使用 `Error::downcast_ref` 尝试将错误向下转型为 `std::io::Error`。`downcast_ref` 方法返回一个 `Option`，告诉用户向下转型是否成功。这里有一个关键观察：只有当目标类型参数为 `'static` 时，`downcast_ref` 才有效。如果我们返回一个不是 `'static` 的不透明 `Error`，就会剥夺用户进行这种错误内省的能力（如果他们希望这样做的话）。

生态系统中对于库的类型擦除错误（或更一般地说，其类型擦除类型）是否属于其公开且稳定的 API 存在一些分歧。也就是说，如果你的库中的方法 `foo` 返回 `lib::MyError` 作为 `Box<dyn Error>`，那么将 `foo` 改为返回不同的错误类型算不算是破坏性变更？类型签名没有改变，但用户可能已经编写了假设他们可以使用向下转型将该错误转换回 `lib::MyError` 的代码。我对此事的看法是，你选择返回 `Box<dyn Error>`（而不是 `lib::MyError`）是有原因的，除非有明确文档说明，否则这并不能保证向下转型的任何具体内容。

你可能想知道 `Error::downcast_ref` 如何保证安全。也就是说，它如何知道提供的 `dyn Error` 参数确实是指定类型 `T`？标准库中甚至有一个名为 `Any` 的 trait，它针对任何类型实现，并为 `dyn Any` 实现了 `downcast_ref`——这怎么会没问题呢？答案在于编译器支持的类型 `std::any::TypeId`，它可以让你获得任何类型的唯一标识符。`Error` trait 有一个名为 `type_id` 的隐藏的提供方法，其默认实现是返回 `TypeId::of::<Self>()`。类似地，`Any` 有一个对 `T` 的 blanket 实现 `impl Any for T`，在该实现中，它的 `type_id` 返回同样的值。在这些 `impl` 块的语境中，`Self` 的具体类型是已知的，因此这个 `type_id` 就是真实类型的类型标识符。这提供了 `downcast_ref` 所需的全部信息。`downcast_ref` 调用 `self.type_id`，它会通过动态大小类型的虚表（vtable，见第 3 章）转发到底层类型的实现，并将该结果与所提供的向下转型类型的类型标识符进行比较。如果它们匹配，那么 `dyn Error` 或 `dyn Any` 背后的类型确实就是 `T`，从一个引用转换为另一个引用就是安全的。

## 特殊错误情况

有些函数可能会失败，但在失败时无法返回任何有意义的错误。从概念上讲，这些函数的返回类型是 `Result<T, ()>`。在某些代码库中，你可能会看到这种类型被表示为 `Option<T>`。虽然两者对于这类函数的返回类型都是合理的选择，但它们传达的语义含义不同，你通常应该避免将 `Result<T, ()>` “简化”为 `Option<T>`。`Err(())` 表示操作失败，应该重试、报告或以其他方式特殊处理。另一方面，`None` 仅表示函数没有可返回的内容；它通常不被视为特殊情况或需要处理的情况。你可以从 `Result` 类型上的 `#[must_use]` 注解中看出这一点——当你得到 `Result` 时，语言期望处理这两种情况都很重要，而对于 `Option`，实际上两种情况都不需要处理。

> **注意** 你还应该记住，`()` 没有实现 `Error` trait。这意味着它不能被类型擦除为 `Box<dyn Error>`，并且在使用 `?` 时会有点麻烦。因此，在这些情况下，通常最好定义你自己的单元结构体类型，为它实现 `Error`，并将其作为错误而不是 `()` 使用。




我们是否需要 Into，以及反过来呢？有几个原因，但让我们从历史原因开始：在 Rust 早期，由于第 3 章讨论的相干性规则，根本不可能只保留一个。或者更具体地说，是相干性规则曾经的样子。

假设你想在自己在 crate 中定义的一些本地类型和标准库中的某些类型之间实现双向转换。你可以明确地编写 `impl<T> From<Vec<T>> for MyType<T>` 和 `impl<T> Into<Vec<T>> for MyType<T>`。但如果你只有 From 或 Into，你就必须编写 `impl<T> From<MyType<T>> for Vec<T>` 或 `impl<T> Into<MyType<T>> for Vec<T>`。然而，编译器过去会拒绝这些实现！只有从 Rust 1.41.0 开始，在相干性规则中加入了被覆盖类型的例外后，它们才是合法的。在此更改之前，必须同时拥有两个 trait。由于大量 Rust 代码是在 Rust 1.41.0 之前编写的，因此现在这两个 trait 都不能被移除。

除此历史事实之外，即使我们今天可以从零开始，也有很好的人体工学原因需要同时保留这两个 trait。在不同情况下，使用其中一个往往会显著更容易。例如，如果你正在编写一个方法，该方法接受可以转换为 Foo 的类型，你更愿意写 `fn(impl Into<Foo>)` 还是 `fn<T>(T) where Foo: From<T>`？反过来，要将字符串转换为语法标识符，你更愿意写 `Ident::from("foo")` 还是 `<_ as Into<Ident>>::into("foo")`？这两个 trait 都有其用途，我们最好同时保留它们。

既然我们同时拥有两者，你可能会想知道在今天的代码中应该使用哪一个。答案其实很简单：实现 From，并在边界中使用 Into。原因在于 Into 对任何实现了 From 的 T 都有一个 blanket 实现，因此无论类型是否显式实现了 From 或 Into，它都实现了 Into！

当然，正如简单的事情经常会发生，故事并没有就此结束。由于编译器在使用 Into 作为边界时经常需要“经过” blanket 实现，判断一个类型是否实现了 Into 的推理比判断它是否实现了 From 要复杂得多。在某些情况下，编译器还不够聪明，无法弄清这个谜题。因此，截至撰写时，`?` 运算符使用的是 From，而不是 Into。大多数时候这并不会产生差异，因为大多数类型都实现了 From，但如果有差异，意味着来自旧库且仅实现 Into 而非 From 的错误类型可能无法与 `?` 一起使用。随着编译器变得更聪明，我可能会“升级”为使用 Into，到那时这个问题就会消失，但目前我们只能这样。

`?` 的第二个需要注意的方面是，这个运算符实际上只是对一个暂定名为 Try 的 trait 的语法糖。截至撰写时，Try trait 尚未稳定，但到你阅读本文时，很可能它或非常相似的东西已经被确定。由于细节尚未全部确定，我只会给你介绍 Try 的工作原理的大致轮廓，而不是完整的方法签名。其核心是，Try 定义了一个包装类型，其状态要么是进一步计算有用的状态（happy path），要么是无用的状态。你们中的一些人会正确地想到 monads，但我们在这里不会探讨这种联系。例如，在 `Result<T, E>` 的情况下，如果你有一个 `Ok(t)`，你可以通过解包 `t` 在 happy path 上继续下去。另一方面，如果你有一个 `Err(e)`，你希望立即停止执行并产生错误值，因为由于你没有 `t`，进一步的计算是不可能的。

Try 的有趣之处在于它适用于的不仅仅是 `Result`。例如，`Option<T>` 也遵循相同的模式——如果你有一个 `Some(t)`，你可以在 happy path 上继续，而如果你有一个 `None`，你希望产生 `None` 而不是继续。这种模式扩展到更复杂的类型，例如 `Poll<Result<T, E>>`，其 happy path 类型是 `Poll<T>`，这使得 `?` 应用于比你预期更多的情况下。当 Try 稳定时，我们可能会看到 `?` 开始与各种类型一起使用，以使我们的 happy path 代码更优雅。

`?` 运算符已经可以在易错函数、doctest 和 `fn main` 中使用。为了发挥其全部潜力，我们还需要一种方法来限定这种错误处理。例如，考虑清单 5-2 中的函数。

```rust

## 项目结构

![](img/bbeab1f2edc3d45a3e6f7f6efbbb1747_70_0.png)

本章为结构化你的 Rust 项目提供了一些思路。对于简单项目，cargo new 设置的结构很可能就是你几乎不会考虑的东西。你可能会添加一些模块来拆分代码，并为额外功能添加一些依赖，但就这样了。然而，随着项目规模和复杂度的增长，你会发现自己需要超越这一点。也许你的 crate 的编译时间变得难以控制，或者你需要条件依赖，或者你需要更好的持续集成策略。在本章中，我们将研究 Rust 语言，特别是 Cargo 提供的一些工具，使管理这些事情变得更容易。

## 特性

特性是 Rust 自定义项目的首要工具。核心来说，一个特性只是一个构建标志，crate 可以将其传递给其依赖项以添加可选功能。特性本身没有语义含义——相反，你选择特性对你的 crate 的含义。

通常，我们以三种方式使用特性：启用可选依赖、条件包含 crate 的额外组件，以及增强代码的行为。请注意，这三种用途都是增量的；特性可以增加 crate 的功能，但它们通常不应该做诸如移除模块或替换类型或函数签名之类的事情。这源于一个原则：如果开发者对其 Cargo.toml 做出简单更改，例如添加新依赖或启用特性，这不应该使他们的 crate 停止编译。如果一个 crate 具有互斥的特性，这一原则很快就会被破坏——如果 crate A 依赖于 crate C 的一个特性，而 crate B 依赖于 C 的另一个互斥特性，那么添加对 crate B 的依赖就会破坏 crate A！因此，我们通常遵循的原则是：如果 crate A 在某组特性下可以编译 crate C，那么它也应该在 crate C 的所有特性都启用时编译。

Cargo 非常重视这一原则。例如，如果两个 crate（A 和 B）都依赖于 crate C，但它们各自在 C 上启用了不同的特性，Cargo 只会编译一次 crate C，并使用 A 或 B 所需的所有特性。也就是说，它会取 A 和 B 对 C 请求的特性的并集。由于这个原因，很难为 Rust crate 添加互斥特性；很可能某些两个依赖项会以不同的特性依赖于该 crate，如果这些特性是互斥的，下游 crate 将无法构建。

> NOTE
> 我强烈建议你配置你的持续集成基础设施以检查你的 crate 在其特性的任何组合下都能编译。有助于做到这一点的工具是 cargo-hack，你可以在 https://github.com/taiki-e/cargo-hack 上找到它。

## 定义和包含特性

特性在 Cargo.toml 中定义。清单 6-1 显示了一个名为 foo 的 crate 的示例，其中有一个简单的特性可启用可选依赖 syn。

```
[package]
name = "foo"
...
[features]
derive = ["syn"]

[dependencies]
syn = { version = "1", optional = true }
```

清单 6-1：启用可选依赖的特性

```
[package]
name = "bar"
...
```



```toml
[dependencies]

```

Listing 6-2: Enabling a feature of a dependency

某些特性被使用得如此频繁，以至于让一个 crate 选择退出它们而不是选择进入它们更有意义。为了支持这一点，Cargo 允许你为一个 crate 定义一组默认特性。同样，它也允许你选择退出依赖项的默认特性。Listing 6-3 显示了 foo 如何使其 derive 特性默认启用，同时也选择退出 syn 的某些默认特性，而只启用其 derive 特性所需的特性。

```toml
[package]
name = "foo"
...
[features]
derive = ["syn"]
default = ["derive"]

[dependencies.syn]
version = "1"
default-features = false
features = ["derive", "parsing", "printing"]
optional = true
```

Listing 6-3: Adding and opting out of default features, and thus optional dependencies

这里，如果一个 crate 依赖于 foo 并且没有明确选择退出默认特性，它也将编译 foo 的 syn 依赖项。进而，syn 将仅使用列出的三个特性构建，而没有其他特性。以这种方式选择退出默认特性，并只选择你需要的特性，是减少编译时间的好方法！

## OPTIONAL DEPENDENCIES AS FEATURES

当你定义一个特性时，等号后面跟随的列表本身就是一个特性列表。这乍一听可能有点奇怪——在 Listing 6-3 中，syn 是一个依赖项，而不是一个特性。事实证明，Cargo 会将每个可选依赖项都作为一个与依赖项同名的特性。你会在尝试添加一个与可选依赖项同名的特性时看到这一点；Cargo 不允许这样做。Cargo 中为特性与依赖项提供不同命名空间的支持正在进行中，但在写作时尚未稳定。在此期间，如果你想拥有一个以依赖项命名的特性，你可以使用 package = "" 重命名依赖项以避免名称冲突。特性启用的特性列表也可以包括依赖项的特性。例如，你可以写 derive = ["syn/derive"] 来让你的 derive 特性启用 syn 依赖项的 derive 特性。

unit; Rust 编译器将一个 crate 基本上视为一个作为一个整体编译的大型源文件，最终转换为单个二进制输出（要么是二进制文件，要么是库）。

虽然这简化了编译器的许多方面，但也意味着大型 crate 在使用时会很痛苦。如果你更改了一个单元测试、一条注释或应用程序某一部分的类型，编译器必须重新评估整个 crate 以确定是否发生了变化。内部，编译器实现了许多机制来加快这一过程，例如增量重新编译和并行代码生成，但最终你的 crate 的大小是项目编译时间长短的一个重要因素。

因此，随着项目的增长，你可能希望将其拆分为多个相互依赖的 crate。Cargo 提供了你需要的功能来让这变得方便：工作区。*工作区* 是一组 crate（通常称为 *子 crate*），它们由一个顶层的 *Cargo.toml* 文件绑定在一起，如 Listing 6-4 所示。

```toml
[workspace]
members = [
    "foo",
    "bar/one",
    "bar/two",
]
```

*Listing 6-4: A workspace Cargo.toml*

members 数组是包含工作区中每个 crate 的目录列表。这些 crate 在各自的子目录中都有自己的 *Cargo.toml* 文件，但它们共享单个 *Cargo.lock* 文件和单个输出目录。crate 名称不需要与 members 中的条目匹配。工作区中的 crate 通常、但不是必须共享一个名称前缀，通常选择为“主”crate 的名称。例如，在 tokio crate 中，成员被称为 tokio、tokio-test、tokio-macros 等。

工作区最重要特性之一是，你可以通过在工作区根目录调用 cargo 来与工作区的所有成员交互。想检查它们是否都能编译？cargo check 会检查它们全部。想运行所有测试？cargo test 会测试它们全部。这并不像将所有内容放在一个 crate 中那样方便，所以不要把所有东西都拆分成微小的 crate，但它是一个相当好的近似。

> **NOTE**  
> *Cargo commands will generally do the “right thing” in a workspace. If you ever need to disambiguate, such as if two workspace crates both have a binary by the same name, use the -p flag (for package). If you are in the subdirectory for a particular workspace crate, you can pass --workspace to perform the command for the entire workspace instead.*

一旦你有了包含工作区成员数组的工作区级 *Cargo.toml*，你就可以使用路径依赖让你的 crate 互相依赖，如 Listing 6-5 所示。

```toml
[patch.crates-io]
# use a local (presumably modified) source
regex = { path = "/home/jon/regex" }
# use a modification on a git branch
serde = { git = "https://github.com/serde-rs/serde.git", branch = "faster" }
# patch a git dependency
[patch.'https://github.com/jonhoo/project.git']
project = { path = "/home/jon/project" }
```

Listing 6-6: Overriding dependency sources in Cargo.toml using [patch]

即使你修补了一个依赖项，Cargo 也会注意检查 crate 版本，以确保你不会意外地修补了 crate 的错误主版本。如果你由于某种原因在传递依赖中依赖于同一 crate 的多个主版本，你可以通过为它们提供不同的标识符来分别修补它们，如 Listing 6-7 所示。

```toml
[patch.crates-io]
nom4 = { path = "/home/jon/nom4", package = "nom" }
nom5 = { path = "/home/jon/nom5", package = "nom" }
```

Listing 6-7: Overriding multiple versions of the same crate in Cargo.toml using [patch]

Cargo 会查看每个路径中的 Cargo.toml，意识到 /nom4 包含主版本 4 而 /nom5 包含主版本 5，并相应地修补这两个版本。package 关键字告诉 Cargo 在两种情况下都按名称 nom 查找 crate，而不是像默认情况下那样使用依赖项标识符（左侧的部分）。你也可以在常规依赖项中使用 package 这种方式来重命名依赖项！

请记住，补丁在你发布 crate 时上传的包中不会被考虑。依赖于你的 crate 的 crate 只会使用它自己的 [patch] 部分（可能为空），而不是你的 crate 的！

## CRATES VS. PACKAGES

你可能会想知道 package 和 crate 有什么区别。这些术语在非正式场合经常互换使用，但在 Rust 编译器、Cargo、crates.io 或其他地方谈论时，它们也有特定的定义会有所不同。我个人认为 crate 是一个从根 .rs 文件开始的 Rust 模块层次结构（你可以在其中使用 crate 级属性如 #![feature]）——通常是像 lib.rs 或 main.rs 这样的文件。相比之下，package 是一组 crate 和元数据，本质上就是 Cargo.toml 文件所描述的所有内容。这可能包括一个库 crate、多个二进制 crate、一些集成测试 crate，甚至多个本身具有 Cargo.toml 文件的工作区成员。

## [profile]

[profile] 部分允许你向 Rust 编译器传递额外的选项，以改变它编译 crate 的方式。这些选项主要分为三类：性能选项、调试选项以及以用户定义方式改变代码行为的选项。它们在调试模式或发布模式下编译时都有不同的默认值（也存在其他模式）。

三个主要的性能选项是 opt-level、codegen-units 和 lto。opt-level 选项通过告诉编译器以多大的激进程度优化你的程序来调整运行时性能（0 表示“完全不优化”，3 表示“尽可能多地优化”）。设置越高，你的代码优化程度越高，这 *可能* 使其运行更快。额外的优化是以更高的编译时间为代价的，这就是为什么优化通常只在发布构建中启用。

> 你也可以将 opt-level 设置为 "s" 以优化二进制大小，这在嵌入式平台上可能很重要。

codegen-units 选项是关于编译时 *性能*。它告诉编译器允许将单个 crate 的编译拆分为多少个独立的编译任务（*代码生成单元*）。大型 crate 的编译拆分为越多部分，编译速度越快，因为更多线程可以帮助并行编译 crate。不幸的是，为了实现这种加速，线程需要在很大程度上独立工作，这意味着代码优化会受损。例如，想象一下在一个线程中编译的 crate 段可以从另一个段中的代码内联中受益——由于这两个段是独立的，这种内联就无法发生！因此，这个设置是在编译时性能和运行时性能之间权衡。默认情况下，Rust 在调试模式下使用基本上无限制数量的代码生成单元（基本上是“尽可能快地编译”），而在发布模式下使用较少数量（写作时为 16）。

lto 设置切换 *链接时优化 (LTO)*，它使编译器（如果你想在技术上说，是链接器）能够联合优化原本单独编译的程序的各个部分，即 *编译单元*。LTO 的确切细节超出了本书的范围，但基本思想是每个编译单元的输出都包含有关该单元中代码的信息。所有单元编译完成后，链接器会再次遍历所有单元，并使用这些额外信息来优化组合的编译代码。这一额外遍历会增加编译时间，但可以恢复大部分由于将编译拆分为更小部分而可能丢失的运行时性能。特别是，LTO 可以为可能从跨 crate 优化中受益的性能敏感程序提供显著的性能提升。但要注意，跨 crate 的 LTO 会大大增加你的编译时间。

Rust 默认在每个 crate 内的所有 codegen units 之间执行 LTO，以试图弥补使用


许多代码生成单元。由于 LTO 只在每个 crate 内部执行，而不是跨 crate 执行，因此这一额外遍并不会太繁重，增加的编译时间也应低于使用大量代码生成单元所节省的时间。Rust 还提供了一种称为 thin LTO 的技术，它可以让 LTO 遍在很大程度上并行化，代价是会错过一些“完整” LTO 遍本可以发现的优化。

> 注意：LTO 在许多情况下也可以跨外部函数接口边界进行优化。更多细节请参阅 `linker-plugin-lto` rustc 标志。

[profile] 部分还支持有助于调试的标志，例如 debug、debug-assertions 和 overflow-checks。debug 标志告诉编译器在编译后的二进制文件中包含调试符号。这会增大二进制文件的大小，但意味着在回溯和剖析中你得到的是函数名称等信息，而不仅仅是指令地址。debug-assertions 标志会启用 debug_assert! 宏以及其他相关的调试代码，这些代码在其他情况下不会编译（通过 cfg(debug_assertions)）。此类代码可能会让你的程序运行得更慢，但能让你更容易在运行时捕获可疑行为。overflow-checks 标志，顾名思义，会对整数运算启用溢出检查。这会让它们变慢（你注意到这里的规律了吗？）但能帮助你及早发现棘手的 bug。默认情况下，调试模式下这些全部启用，发布模式下全部禁用。

## [profile.*.panic]

[profile] 部分还有另一个值得拥有自己小节的标志：panic。该选项决定程序中的代码直接或间接（例如通过 unwrap）调用 panic! 时会发生什么。你可以将 panic 设置为 unwind（大多数平台上的默认值）或 abort。我们会在第 10 章更多地讨论 panic 和展开，但我这里先做一个简要总结。

通常，在 Rust 中，当你的程序 panic 时，发生 panic 的线程会开始展开其栈。你可以把展开想象为从当前函数递归地强制返回到该线程栈底部。也就是说，如果 main 调用了 foo，foo 调用了 bar，bar 调用了 baz，那么 baz 中的 panic 会强制从 baz 返回，然后 bar、foo，最后从 main 返回，导致程序退出。发生展开的线程会正常释放栈上的所有值，这使这些值有机会清理资源、报告错误等。这给了运行中的系统在 panic 时优雅退出的机会。

当线程 panic 并展开时，其他线程不受影响地继续运行。只有在运行 main 的线程退出时（如果它退出），程序才会终止。也就是说，panic 通常被隔离在发生 panic 的线程中。

这意味着展开是一把双刃剑；程序带着一些失败的组件勉强运行，这可能导致各种奇怪的行为。例如，想象一个线程在更新一个 Mutex 中的状态进行到一半时发生 panic。任何随后获取该 Mutex 的线程都必须准备好处理状态可能处于部分更新、不一致状态的情况。因此，一些同步原语

（如 Mutex）会记住上次被访问时是否发生过 panic，并将此信息传递给任何随后尝试访问该原语的线程。如果某个线程遇到这种状态，它通常也会 panic，从而导致级联，最终终止整个程序。但这可以说比带着已损坏的状态继续运行要好！

支持展开所需的簿记并非没有代价，而且它通常需要编译器和目标平台的特殊支持。例如，许多嵌入式平台根本无法高效地展开栈。因此 Rust 支持另一种 panic 模式：abort 确保在 panic 发生时整个程序立即退出。在这种模式下，任何线程都得不到清理的机会。这看起来可能很严厉，也确实如此，但它确保程序绝不会处于半运行状态，并且错误会立即显现。

> 警告
> panic 设置是全局的——如果你将其设置为 abort，所有依赖项也会以 abort 模式编译。

你可能已经注意到，当线程 panic 时，它往往会打印一个回溯：导致 panic 发生的一系列函数调用。这也是一种展开形式，虽然它与此处讨论的展开 panic 行为是分开的。即使使用 panic=abort，你也可以通过向 rustc 传递 -Cforce-unwind-tables 来获得回溯，这会让 rustc 包含向上遍历栈所需的信息，同时在 panic 时仍会终止程序。

## Profile 覆盖

你可以使用 profile 覆盖来仅为某个特定依赖项或特定 profile 设置 profile 选项。例如，清单 6-8 展示了如何使用 [profile.<profile-name>.package.<crate-name>] 语法，在调试模式下为 serde crate 启用激进优化，并为所有其他 crate 启用适度优化。

```toml
[profile.dev.package.serde]
opt-level = 3

[profile.dev.package."*"]
opt-level = 2
```

清单 6-8：覆盖特定依赖项或特定模式的 profile 选项

如果某个依赖项在调试模式下慢得令人望而却步（例如解压缩或视频编码），而你需要它被优化以加快测试套件的运行，这种优化覆盖就很有用。你还可以在 ~/.cargo/config 中的 Cargo 配置文件里使用 [profile.dev]（或类似）部分来指定全局 profile 默认值。

当你为特定依赖项设置优化参数时，请记住，这些参数只适用于作为该 crate 的一部分编译的代码；

> 如果此示例中的 serde 有一个你在自己的 crate 中使用的泛型方法或类型，那么该方法或类型的代码将在你的 crate 中被单态化并优化，此时应用的是你的 crate 的 profile 设置，而不是 serde 的 profile 覆盖设置。

## 条件编译

你编写的大多数 Rust 代码都是通用的——无论运行在什么 CPU 或操作系统上，行为都一样。但有时你必须做点特别的事情，才能让代码在 Windows、ARM 芯片上工作，或者当针对特定平台应用程序二进制接口（ABI）编译时。又或者，你可能想在某个给定的 CPU 指令可用时编写特定函数的优化版本，或者在持续集成（CI）环境中运行时禁用一些缓慢但无趣的初始化代码。为了满足这类情况，Rust 提供了条件编译机制，即只有在编译环境满足某些条件时，特定代码段才会被编译。

我们使用 cfg 关键字来表示条件编译，你在第 XX 页的“在你的 crate 中使用特性”中见过它。它通常以 #[cfg(condition)] 属性的形式出现，表示仅当 condition 为真时才编译下一个项目。Rust 还有 #[cfg_attr(condition, attribute)]，如果 condition 成立，它会被编译为 #[attribute]，否则就是空操作。你还可以使用 cfg!(condition) 宏将 cfg 条件作为布尔表达式求值。

每个 cfg 构造都接受一个由选项组成的单一条件，例如 feature = "some-feature"，以及组合器 all、any 和 not，它们的功能正如你所预期。选项要么是简单的名称，如 unix，要么是与特性条件中使用的键/值对。

有许多有趣的选项可以让编译依赖于它们。让我们从最常见到最不常见逐一介绍：

### 特性选项

你已经见过这些示例。特性选项采用 feature = "name-of-feature" 的形式，如果命名的特性已启用，则该选项为真。你可以使用组合器在单个条件中检查多个特性。例如，如果特性 f1 或特性 f2 已启用，则 any(feature = "f1", feature = "f2") 为真。

### 操作系统选项

这些选项使用键/值语法，键为 target_os，值为 windows、macos 和 linux 等。你还可以使用 target_family 来指定操作系统家族，其取值为 windows 或 unix。这些选项非常常见，因此它们拥有自己的命名简写，你可以直接使用 cfg(windows) 和 cfg(unix)。例如，如果你希望某个特定代码段只在 macOS 和 Windows 上编译，可以这样写：#[cfg(any(windows, target_os = "macos"))].




## 上下文选项

这些选项让你能够针对特定的编译上下文来定制代码。其中最常用的是 `test` 选项，它仅在 crate 以测试（test）配置文件编译时为 `true`。请注意，`test` 只对正在被测试的 crate 设置，而不会对其任何依赖项设置。这也意味着，在运行集成测试时，你的 crate 并不会设置 `test`；是集成测试本身以测试配置文件编译，而你的实际 crate 则正常编译（即不设置 `test`）。`doc` 和 `doctest` 选项也同理，它们分别只在构建文档或编译 doctest 时设置。此外还有 `debug_assertions` 选项，默认在调试模式下会被设置。

## 工具选项

某些工具（如 `clippy` 和 `Miri`）会设置自定义选项（后面会详述），让你在这些工具下运行时能够定制编译行为。通常，这些选项以相应工具的名称命名。例如，如果你希望某个计算密集型的测试不要在 Miri 下运行，可以给它加上 `#[cfg_attr(miri, ignore)]` 属性。

## 架构选项

这些选项让你能够基于编译器所针对的 CPU 指令集进行编译。你可以使用 `target_arch` 指定特定架构，其取值如 `x86`、`mips`、`aarch64`；也可以使用 `target_feature` 指定特定的平台特性，其取值如 `avx` 或 `sse2`。对于非常底层的代码，你还会发现 `target_endian` 和 `target_pointer_width` 选项也很有用。

## 编译器选项

这些选项让你能够使代码适应所编译所针对的平台 ABI，可通过 `target_env` 获得，其取值如 `gnu`、`msvc` 和 `musl`。由于历史原因，该值通常为空，尤其是在 GNU 平台上。通常你只在需要直接与生态环境的 ABI 交互时才需要此选项，例如通过 `#[link]` 链接到某个 ABI 特定的符号名时。

虽然 `cfg` 条件通常用于定制代码，但有些也可以用于定制依赖项。例如，`winrt` 依赖通常只在 Windows 上有意义，而 `nix` crate 可能只在基于 Unix 的平台上才有用。清单 6-9 给出了如何使用 `cfg` 条件来实现这一点的示例：

```
[target.'cfg(windows)'.dependencies]
winrt = "0.7"
[target.'cfg(unix)'.dependencies]
nix = "0.17"
```

清单 6-9：条件依赖

在这里，我们指定 `winrt` 0.7 版仅在 `cfg(windows)` 条件下（即在 Windows 上）被视为依赖项，而 `nix` 0.17 版仅在 `cfg(unix)` 条件下（即在 Linux、macOS 及其他基于 Unix 的平台上）被视为依赖项。需要记住的一点是，`[dependencies]` 部分在构建过程的很早阶段就会被求值，此时只有某些 `cfg` 选项可用。特别是，`feature` 和上下文选项此时还不可用，因此你不能使用这种语法来基于特性（features）和上下文引入依赖。不过，你可以使用任何仅依赖于目标规范或架构的 `cfg`，以及由调用 `rustc` 的工具（如 `cfg(miri)`）显式设置的任何选项。

> 注意
> *既然谈到了依赖规范，我强烈建议你设置 CI 基础设施，使用 `cargo-deny` 和 `cargo-audit` 等工具对依赖项进行基本审计。这些工具能够检测出：你是否在传递依赖中依赖了某个依赖项的多个主要版本、是否依赖于无人维护或存在已知安全漏洞的 crate、以及是否使用了你可能想要避免的许可证。使用这类工具是以自动化方式提升代码库质量的绝佳途径！*

添加自定义的条件编译选项也相当简单。你只需要确保在 `rustc` 编译你的 crate 时传入 `--cfg=myoption`。最简单的做法是将你的 `--cfg` 添加到 `RUSTFLAGS` 环境变量中。这在 CI 中非常有用，你可能希望根据测试是在 CI 上运行还是在开发机上运行来定制测试套件：在 CI 设置中向 `RUSTFLAGS` 添加 `--cfg=ci`，然后在代码中使用 `cfg(ci)` 和 `cfg(not(ci))`。以这种方式设置的选项在 `Cargo.toml` 的依赖项中也可用。

## 版本管理

所有 Rust crate 都有版本，并且预期遵循 Cargo 实现的语义化版本（semantic versioning）规则。语义化版本规定了什么样的变更需要什么样版本的提升、哪些版本被认为是兼容的、以及以何种方式兼容。RFC 1105 标准本身非常值得一读（其技术性并不强），但概括而言，它区分了三种变更：破坏性变更（breaking changes），需要主版本号的提升；新增功能（additions），需要次版本号的提升；以及缺陷修复（bug fixes），只需要补丁版本号的提升。RFC 1105 很好地概述了在 Rust 中什么构成破坏性变更，我们在本书的其他地方也已涉及其中一些方面。

在这里，我不打算详细讨论不同变更类型的确切语义。相反，我想强调版本号在 Rust 生态系统中出现的一些不太直观的方式，在决定如何为自己的 crate 进行版本管理时，你需要牢记这些。

## 最低支持 Rust 版本

第一个 Rust 特色是最低支持 Rust 版本（MSRV）。在 Rust 社区中，关于项目在 MSRV 和版本管理方面应遵循何种策略存在大量争论，而且没有真正完美的答案。问题的核心在于，一些 Rust 用户只能使用较旧版本的 Rust，这通常是在企业环境中，他们几乎没有选择余地。如果我们不断利用新稳定的 API，这些用户将无法编译我们 crate 的最新版本，从而被落下。

crate 作者可以采用两种技术来让处于这种境地的用户生活更轻松一些。第一种是建立 MSRV 策略，承诺 crate 的新版本始终能够与过去 X 个月的任何稳定版本编译。具体数字各不相同，但 6 或 12 个月较为常见。考虑到 Rust 每六周一个发布周期，这分别对应最近四个或八个稳定版本。项目中引入的任何新代码都必须能够使用 MSRV 编译器编译（通常通过 CI 检查），或者等到 MSRV 策略允许时再按原样合并。这有时会很痛苦，因为这意味着这些 crate 无法利用语言提供的最新、最强大的功能，但这会让你的用户生活更轻松。

第二种技术是确保每当 MSRV 发生变化时，都提升 crate 的次版本号。因此，如果你发布了 crate 的 2.7.0 版本，并且该版本将你的 MSRV 从 Rust 1.44 提升到 Rust 1.45，那么一个停留在 1.44 且依赖你 crate 的项目可以使用依赖版本限定符 `version = "2, <2.7"` 来保持项目正常工作，直到它能够升级到 Rust 1.45。重要的是，你应递增次版本号，而不仅仅是补丁版本号，这样如果必要，你仍然可以针对之前的 MSRV 版本发布关键安全修复（通过再进行一次补丁发布）。

有些项目非常重视 MSRV 支持，以至于他们将 MSRV 变更视为破坏性变更并递增主版本号。这意味着下游项目必须显式选择接受 MSRV 变更，而不是选择不接受——但这也意味着，那些没有如此严格 MSRV 要求的用户如果不更新依赖项，将看不到未来的缺陷修复，而这些依赖项更新可能也会要求他们发布破坏性变更。正如我所说，这些解决方案都不是没有缺点的。

如今在 Rust 生态系统中强制实施 MSRV 是很有挑战性的。只有一小部分 crate 提供 MSRV 保证，即使你的依赖项提供了，你也需要不断监控它们，以便了解它们何时提高了 MSRV。当它们提高时，你需要用前面提到的受限版本边界发布新版本的 crate，以确保你的 MSRV 不会随之改变。这可能反过来迫使你放弃对依赖项的安全和性能更新，因为你必须继续使用旧版本，直到你的 MSRV 政策允许更新。而这个决定也会传递给你的下游依赖方。已经有人提议将 MSRV 检查构建到 Cargo 本身中，但在撰写本文时，还没有任何可用的方案被稳定下来。





## 最低依赖版本

当你首次添加依赖时，往往并不清楚应该为该依赖指定什么样的版本说明符。程序员通常会选择最新版本，或者仅仅选择当前的主版本号，但这两种选择很可能都是错误的。这里所说的“错误”，并不是指你的 crate 无法编译，而是指这种选择可能会在日后给你的 crate 用户带来麻烦。让我们来看看为什么这两种情况都有问题。

首先，假设你添加了一个对 `uuid = "1.7.3"`（最新发布版本）的依赖。现在设想某个开发者的项目依赖你的 crate，同时也依赖另一个 crate `foo`，而 `foo` 本身又依赖 uuid。再设想 `foo` 的作者对其 MSRV 策略非常谨慎，因此他们依赖 `uuid = "1, <1.6"`。这时你就会遇到麻烦。当 Cargo 看到 `uuid = "1.7.3"` 时，它只考虑大于等于 1.7 的版本。但随后它发现 foo 对 uuid 的依赖要求小于 1.6，于是它放弃并报告说，没有与所有要求兼容的 uuid 版本。

> *在实践中，crate 显式地不想要某个依赖项的较新版本，原因可能有很多。最常见的原因有：强制 MSRV、满足企业审计要求（较新版本会包含未经审计的代码），以及确保可重现构建（只使用明确列出的确切版本）。*

这很不幸，因为你的 crate 很可能完全可以与，比如说，`uuid 1.5.6` 一起编译。甚至可能任何 1.x 版本都能编译！但是，通过使用最新版本号，你在告诉 Cargo 只考虑该次版本号及以上的版本。那么，改用 `uuid = "1"` 是不是解决方案呢？不，这也不完全正确。你的代码可能确实依赖于只在 uuid 1.6 中添加的某些东西，所以虽然 1.6.2 可以，1.5.6 却不行。如果你只在最终会使用较新版本的环境中编译你的 crate，你不会注意到这一点；但如果依赖图中的某个 crate 指定了 `uuid = "1, <1.5"`，你的 crate 将无法编译！

正确的策略是列出包含你的 crate 所依赖的全部功能的最早版本，并确保即使你在 crate 中添加新代码，这一情况也仍然成立。但除了翻遍更新日志或反复试错之外，你如何确定这一点呢？最好的办法是使用 Cargo 的不稳定标志 `-Z minimal-versions`，它会让你的 crate 对所有依赖使用最低可接受版本，而不是最高版本。然后，将所有依赖仅设置为最新主版本号，尝试编译，并对任何无法编译的依赖添加次版本号。反复进行，直到一切都能正常编译，这时你就有了最低版本要求！

值得注意的是，与 MSRV 一样，最低版本检查也面临着生态系统采用的问题。你可能已经正确设置了所有版本说明符，但你依赖的项目未必如此。这使得 Cargo 的最低版本标志在实践中难以使用（这也是它仍然不稳定的原因）。如果你依赖 foo，而 foo 依赖 bar 时使用了说明符 `bar = "1"`，但实际上它需要 `bar = "1.4"`，那么无论你如何列出 foo，Cargo 都会报告无法编译 foo，因为 `-Z` 标志告诉它始终优先选择最低版本。你可以通过直接在你的依赖中列出 bar 并给出合适的版本要求来绕过这个问题，但这些变通方法的设置和维护可能很麻烦。你最终可能会列出大量实际上只是通过传递依赖引入的依赖项，而且随着时间推移，你还得让这份列表保持最新。

> **注意**
>
> 目前有一个提案，提出一种标志：这种标志倾向于为当前 crate 选择最低版本，而为依赖项选择最高版本。这看起来相当有前景。

## 更新日志

对于除最简单的 crate 之外的所有 crate，我都强烈建议保留更新日志。没有什么比看到某个依赖项进行了主版本升级，然后不得不翻遍 Git 日志来找出变更内容以及如何更新代码更令人沮丧的了。我建议你不要简单地把 Git 日志倾倒进一个名为 changelog 的文件，而是保留一份人工维护的更新日志。这样它更有可能真正有用。

一种简单而优秀的更新日志格式是 Keep a Changelog 格式，其文档位于 https://keepachangelog.com/。

## 未发布的版本

即使依赖项的来源是目录或 Git 仓库，Rust 也会考虑版本号。这意味着，即使你还没有向 crates.io 发布版本，语义化版本控制依然很重要；在两次发布之间，你的 Cargo.toml 中列出的版本也很关键。语义化版本控制标准并未规定如何处理这种情况，但我会提供一种既相当有效又不会太繁琐的工作流程。

发布一个版本后，立即将 Cargo.toml 中的版本号更新为下一个补丁版本，并加上像 `-alpha.1` 这样的后缀。如果你刚刚发布了 2.0.3，那么把新版本设为 2.0.4-alpha.1。如果你刚刚发布了 alpha 版本，则改为递增 alpha 编号。

在两次发布之间修改代码时，要留意新增功能变更或破坏性变更。如果发生了这类变更，且自上次发布以来对应版本号尚未更改，就递增它。例如，如果上次发布的版本是 2.0.3，当前版本是 2.0.4-alpha.2，然后你做了一处新增功能的变更，那么把这次变更后的版本设为 2.1.0-alpha.1。如果你做的是破坏性变更，则改为 3.0.0-alpha.1。如果相应的版本号递增已经完成，只需递增 alpha 编号。

当你发布时，去掉后缀（除非你想发布预发布版本），然后发布，再从头开始。

这个过程之所以有效，是因为它让两种常见的工作流程都运行得更好。首先，设想一个开发者依赖你的 crate 的主版本 2，但他们需要一个目前只在 Git 中可用的功能。这时你提交了一个破坏性变更。如果你不同时提升主版本号，他们的代码就会突然以意想不到的方式失败——要么无法编译，要么出现奇怪的运行时问题。如果你遵循这里给出的流程，Cargo 反而会通知他们发生了破坏性变更，他们就必须解决这一问题，或者固定一个特定的提交。

接下来，设想一个开发者需要某个他们刚刚为你的 crate 贡献的功能，但这个功能尚未包含在你 crate 的任何已发布版本中。他们通过 Git 依赖使用你的 crate 已经有一段时间了，所以他们项目中的其他开发者已经拥有你的 crate 仓库的旧检出。如果你不在 Git 中递增次版本号，这位开发者就无法传达他们的项目现在依赖于刚刚合并的功能。如果他们推送自己的更改，他们的同伴开发者会发现项目不再编译，因为 Cargo 会复用旧的检出。另一方面，如果该开发者能为 Git 依赖递增次版本号，Cargo 就会意识到旧检出已经过时。

这个工作流程绝非完美。它没有提供一种好的方式来传达两次发布之间的多个次版本或主版本变更，而且你仍然需要做一些工作来跟踪版本。然而，它的确解决了 Rust 开发者在处理 Git 依赖时最常遇到的两个问题；即使你在两次发布之间进行了多个这样的变更，这个工作流程也仍然能发现许多问题。

如果你不太在意发布中版本号偏小或是否连续，你可以通过总是递增版本号中的适当部分来改进这个建议的工作流程。不过要注意，取决于你进行此类变更的频率，这可能会使你的版本号变得非常大！

## 总结

在本章中，我们探讨了多种配置、组织和发布 crate 的机制，既是为了你自己受益，也是为了他人。我们还回顾了在 Cargo 中处理依赖和特性时一些常见的陷阱，希望这些以后不会让你措手不及。在下一章中，我们将转向测试，深入探讨如何超越我们所熟知并喜爱的 Rust 简单的 #[test] 函数。





## Rust 测试机制

要理解 Rust 提供的各种测试机制，你必须首先了解 Rust 如何构建和运行测试。当你运行 `cargo test --lib` 时，Cargo 做的唯一特殊事情就是向 `rustc` 传递 `--test` 标志。该标志告诉 `rustc` 生成一个运行所有单元测试的测试二进制文件，而不是仅仅编译 crate 的库或二进制文件。在幕后，`--test` 有两个主要作用。首先，它启用 `cfg(test)`，以便你可以有条件地包含测试代码（稍后会详细介绍）。其次，它使编译器生成一个测试 harness：一个精心生成的 `main` 函数，在运行时调用程序中每个 `#[test]` 函数。

### 测试 Harness

编译器通过程序宏的混合生成测试 harness `main` 函数，我们将在第 8 章更深入地讨论这些宏，以及少量魔法。本质上，harness 将每个用 `#[test]` 注释的函数转换为测试描述符——这是程序宏的部分。然后它将每个描述符的路径暴露给生成的 `main` 函数——这是魔法部分。描述符包含诸如测试的名称、其设置的任何附加选项（如 `#[should_panic]`）等信息。其核心是，测试 harness 遍历 crate 中的测试，运行它们，捕获其结果并打印结果。因此，它还包括解析命令行参数（例如 `--test-threads=1`）、捕获测试输出、以并行方式运行列出的测试并收集测试结果的逻辑。

截至本文撰写时，Rust 开发者正在努力使测试 harness 生成的魔法部分成为一个公开可用的 API，以便开发者可以构建自己的测试 harness。这项工作仍处于实验阶段，但该提案与今天存在的模型相当接近。需要弄清楚的魔法的一部分是如何确保 `#[test]` 函数可供生成的 `main` 函数使用，即使它们位于私有子模块内部。

集成测试（`tests/` 中的测试）遵循与单元测试相同的流程，唯一例外是它们各自被编译为独立的 crate，这意味着它们只能访问主 crate 的公共接口，并且在针对未使用 `#[cfg(test)]` 编译的主 crate 运行。每个 `tests/` 中的文件都会生成一个测试 harness。`tests/` 下子目录中的文件不会生成测试 harness，以便你可以为测试拥有共享子模块。

NOTE 如果你明确希望为子目录中的文件生成测试 harness，可以通过调用该文件 `main.rs` 来选择加入。

Rust 不要求你使用默认的测试 harness。你可以改为选择退出它，并通过在 `Cargo.toml` 中为给定的集成测试设置 `harness = false` 来实现自己的 `main` 方法作为测试运行器，如清单 7-1 所示。然后你定义的 `main` 方法将被调用来运行测试。

```
[[test]]
name = "custom"
path = "tests/custom.rs"
harness = false
```

清单 7-1：选择退出标准测试 harness

没有测试 harness，`#[test]` 周围的魔法就不会发生。相反，你需要编写自己的 `main` 函数来运行你想要执行的测试代码。本质上，你正在编写一个普通的 Rust 二进制文件，只是恰好由 `cargo test` 运行。该二进制文件负责处理默认 harness 通常做的所有事情（如果你想支持它们），例如命令行标志。`harness` 属性是为每个集成测试单独设置的，因此你可以有一个使用标准 harness 的测试文件和一个不使用标准 harness 的测试文件。

### 默认测试 HARNESS 的参数

默认测试 harness 支持许多命令行参数来配置测试的运行方式。这些参数不是直接传递给 `cargo test`，而是传递给 Cargo 为你编译和运行的测试二进制文件，当你运行 `cargo test` 时。要访问该标志集，请在 `cargo test` 后传递 `--`，然后是测试二进制文件的参数。例如，要查看测试二进制文件的帮助文本，你需要运行 `cargo test -- --help`。

通过这些命令行参数可以获得许多方便的配置选项。`--nocapture` 标志禁用运行 Rust 测试时通常发生的输出捕获。这在你想实时观察测试输出而不是在测试失败后一次性全部看到时很有用。你可以使用 `--test-threads` 选项限制并发运行的测试数量，这在你有一个挂起或段错误的测试并且想要通过顺序运行测试来找出它时很有帮助。还有 `--skip` 选项用于跳过匹配特定模式的测试，`--ignored` 用于运行通常会被忽略的测试（例如需要外部程序运行的测试），以及 `--list` 用于仅列出所有可用测试。

请记住，这些参数都是由默认测试 harness 实现的，因此如果你禁用它（使用 `harness = false`），你需要在自己的 `main` 函数中自行实现你需要的参数！

没有 harness 的集成测试主要用于基准测试，如我们稍后会看到的，但它们在你想要运行不符合标准“一个函数，一个测试”模型的测试时也很方便。例如，你经常会看到无 harness 测试与模糊测试器、模型检查器以及需要自定义全局设置（例如在 WebAssembly 下或在处理自定义目标时）的测试一起使用。

### `#[cfg(test)]`

当 Rust 为测试构建代码时，它会设置编译器配置标志 `test`，你可以用它与条件编译一起使用，以便在代码未被专门测试时将其编译掉。乍一看，这似乎很奇怪：你难道不想测试进入生产环境的完全相同的代码吗？你确实想，但仅在测试时可用的代码允许你在几个方面编写更好、更彻底的测试。

### 模拟

在编写测试时，你通常希望对正在测试的代码以及你的代码可能交互的任何其他类型都有严格的控制。例如，如果你正在测试网络客户端，你可能不想通过真实网络运行单元测试，而是直接控制“网络”发出哪些字节以及何时发出。或者，如果你正在测试数据结构，你希望你的测试使用允许你在每次调用时控制每个方法返回值的类型。你可能还想收集指标，例如给定方法被调用的频率或是否发出给定字节序列。

这些“假”类型和实现被称为模拟，它们是任何广泛单元测试套件的关键特性。虽然你通常可以通过手动方式完成获得这种控制所需的工作，但让库为你处理大部分繁琐细节会更方便。这就是自动化模拟发挥作用的地方。模拟库将具有生成具有特定属性或签名的类型（包括函数）的设施，以及在测试执行期间控制和 introspect 这些生成项的机制。

Rust 中的模拟通常通过泛型实现——只要你的程序、数据结构、框架或工具对你可能想要模拟的任何内容都是泛型的（或接受 trait 对象），你就可以使用模拟库生成符合的类型来实例化这些泛型参数。然后你通过使用生成的模拟类型实例化你的泛型构造来编写单元测试，就开始了！

在泛型不方便或不合适的情况下，例如如果你想避免让类型的某个方面对用户泛型化，你可以改为将你想要模拟的状态和行为封装在专用结构体中。然后你将生成该结构体及其方法的模拟版本，并使用条件编译根据 `cfg(test)` 或仅测试的功能如 `cfg(feature = "test_mock_foo")` 使用真实或模拟实现。

目前，Rust 社区中还没有出现一个单一的模拟库，甚至一个单一的模拟方法成为“唯一真理”。我所知道的最广泛和最彻底的模拟库是 `mockall` crate，但它仍在积极开发中，还有许多其他竞争者。





## 仅用于测试的 API

首先，拥有仅用于测试的代码可以让你向你的（单元）测试公开额外的方法、字段和类型，这样测试不仅可以检查公共 API 是否按预期行为，还可以检查内部状态是否正确。例如，考虑来自 `hashbrown` 的 `HashMap` 类型，该 crate 实现了标准库的 `HashMap`。`HashMap` 类型实际上只是 `RawTable` 类型的包装器，而 `RawTable` 实现了大部分哈希表逻辑。假设在对空映射执行 `HashMap::insert` 之后，你想检查映射中的单个桶是否非空，如清单 7-2 所示。

```
#[test]
fn insert_just_one() {
    let mut m = HashMap::new();
    m.insert(42, ());
    let full = m.table.buckets.iter().filter(Bucket::is_full).count();
    assert_eq!(full, 1);
}
```

*清单 7-2：访问无法访问的内部状态的测试，因此无法编译*

这段代码按原样编写将无法编译，因为虽然测试代码可以访问 `HashMap` 的私有 `table` 字段，但它无法访问 `RawTable` 的同样私有的 `buckets` 字段，因为 `RawTable` 位于不同的模块中。我们可以通过将 `buckets` 字段的可见性设为 `pub(crate)` 来修复这个问题，但我们真的不希望 `HashMap` 通常可以触及桶，因为它可能会意外破坏 `RawTable` 的内部状态。即使将桶作为只读提供也可能有问题，因为 `HashMap` 中的新代码随后可能会开始依赖 `RawTable` 的内部状态，从而使未来的修改变得更加困难。

解决方案是使用 `#[cfg(test)]`。我们可以向 `RawTable` 添加一个方法，该方法仅在测试时允许访问桶，如清单 7-3 所示，从而避免为其余代码添加脚枪。清单 7-2 中的代码随后可以更新为调用 `buckets()` 而不是访问私有的 `buckets` 字段。

```
impl RawTable {
    #[cfg(test)]
    pub(crate) fn buckets(&self) -> &[Bucket] {
        &self.buckets
    }
}
```

*清单 7-3：使用 `#[cfg(test)]` 使内部状态在测试上下文中可访问*

拥有仅在测试期间存在的代码的第二个好处是，你可以增强程序以执行额外的运行时记账，然后由测试检查。例如，想象你正在编写自己的标准库中 `BufWriter` 类型的版本。在测试它时，你想确保 `BufWriter` 不会发出系统调用

使用类似 `#[tokio::main] async fn main` 的异步 main 函数，或者如果你想向文档测试添加额外的模块。

要在文档测试中使用 `?` 运算符，你通常不必使用自定义 main 函数，因为 `rustdoc` 包含一些启发式方法，如果你的代码看起来使用了 `?`（例如，如果它以 `Ok(())` 结尾），则将返回类型设置为 `Result<(), impl Debug>`。如果类型推断在函数错误类型方面给你带来困难，你可以通过将文档测试的最后一行显式键入来消除歧义，如下所示：`Ok::<(), T>(())`。

## 额外测试工具

测试不仅仅是运行测试函数并查看它们是否产生预期结果。测试技术、方法和工具的全面调查超出了本书的范围，但随着你扩展测试范围，你应该了解一些关键的 Rust 特定部分。

### 静态检查

你可能不认为 linter 的检查是测试，但在 Rust 中它们通常可以是。Rust linter `clippy` 将其许多 lint 分类为正确性 lint。这些 lint 捕获编译但几乎肯定是 bug 的代码模式。一些例子是 `a = b; b = a`，它未能交换 `a` 和 `b`；`std::mem::forget(t)`，其中 `t` 是引用；以及 `for x in y.next()`，它只会遍历 `y` 中的第一个元素。如果你尚未将 `clippy` 作为 CI 流程的一部分运行，你可能应该这样做。

Clippy 还附带许多其他 lint，虽然通常有帮助，但可能比你更喜欢的更具主观性。例如，默认启用的 `type_complexity` lint，如果你在程序中使用特别复杂的类型，如 `Rc<Vec<Vec<Box<(u32, u32, u32, u32)>>>>`，就会发出警告。虽然该警告鼓励你编写更易读的代码，但你可能会发现它过于挑剔而缺乏广泛的实用性。如果代码的某个部分错误地触发了特定 lint，或你只想允许其特定实例，你可以使用 `#[allow(clippy::name_of_lint)]` 仅对该段代码选择退出 lint。

Rust 编译器还附带了一套以警告形式存在的 lint，不过这些通常更侧重于编写惯用代码而不是检查正确性。相反，编译器中的正确性 lint 只是被视为错误（请查看 `rustc -W help` 获取列表）。

> **注意：** 并非所有编译器警告默认都启用。默认禁用的警告通常仍在完善中，或更多关于风格而非内容。一个很好的例子是“惯用 Rust 2018 版” lint，你可以用 `#![warn(rust_2018_idioms)]` 启用它。启用此 lint 后，编译器会告诉你是否未能利用 Rust 2018 版带来的更改。你可能还想养成在开始新项目时启用 `missing_docs` 和 `missing_debug_implementations` 等 lint 的习惯，这些 lint 会在你忘记为 crate 中的任何公共项编写文档或为任何公共类型添加 `Debug` 实现时警告你。

### 测试生成

编写良好的测试套件需要大量工作。即使你做了这项工作，你编写的测试也只测试你在编写时考虑的那组特定行为。幸运的是，你可以利用多种测试生成技术来开发更好、更全面的测试。这些技术为你生成输入以检查应用程序的正确性。存在许多此类工具，各有其优缺点，因此这里我只介绍这些工具使用的主要策略：模糊测试和属性测试。

### 模糊测试

模糊测试已经写了整本书，但从高层次来看，想法很简单：向程序生成随机输入，看看它是否崩溃。如果程序崩溃，那就是 bug。例如，如果你正在编写 URL 解析库，你可以通过系统地生成随机字符串并将其抛给解析函数，直到它 panic 来模糊测试你的程序。完成。





天真地讲，这需要花费很长时间才能产生结果：如果模糊测试器从 a 开始，然后是 b，然后是 c，依此类推，它需要很长时间才能生成一个棘手的 URL，比如 http://[:]。实际上，现代的模糊测试器使用代码覆盖率指标来探索代码中的不同路径，这使得它们能够比真正随机选择输入时更快地达到更高的覆盖率。

模糊测试器非常擅长找到代码未正确处理的奇怪边界情况。它们几乎不需要你进行设置：你只需将模糊测试器指向一个接受“可模糊”输入的函数，然后它就开始运行了。例如，清单 7-7 显示了你如何对 URL 解析器进行模糊测试的示例。

```
libfuzzer_sys::fuzz_target!(|data: &[u8]| {
    if let Ok(s) = std::str::from_utf8(data) {
        let _ = url::Url::parse(s);
    }
});
```

清单 7-7：使用 libfuzzer 对 URL 解析器进行模糊测试

模糊测试器会向闭包生成半随机的输入，任何形成有效 UTF-8 字符串的输入都会被传递给解析器。请注意，这里的代码并没有检查解析是否成功或失败——相反，它是在寻找解析器因违反内部不变量而 panic 或以其他方式崩溃的情况。

模糊测试器会一直运行直到你终止它，因此大多数模糊测试工具都内置了在探索一定数量的测试用例后停止的机制。如果你的输入不是一个简单可模糊的类型——比如哈希表——你通常可以使用像 arbitrary 这样的 crate 将模糊测试器生成的字节字符串转换为更复杂的 Rust 类型。看起来像魔法，但实际上在底层以非常直接的方式实现。该 crate 定义了一个 Arbitrary trait，其中有一个名为 arbitrary 的单一方法，用于从随机字节源构造实现该类型的实例。像 u32 或 bool 这样的原始类型会从该输入中读取必要数量的字节来构造自身的有效实例，而更复杂的类型如 HashMap 或 BTreeSet 则会从输入中产生一个数字来决定其长度，然后在内部类型上调用 Arbitrary 该次数。甚至还有一个属性 #[derive(Arbitrary)]，它通过对每个包含的类型调用 arbitrary 来实现 Arbitrary！要进一步探索模糊测试，我建议从 cargo-fuzz 开始。

## Property-Based Testing

有时你不仅想检查程序是否不会崩溃，还想检查它是否按预期工作。你的 add 函数没有 panic 很好，但如果它告诉你 add(1, 4) 的结果是 68，它可能仍然是错误的。这就是基于属性测试发挥作用的地方；你描述代码应遵守的若干属性，然后属性测试框架生成输入并检查这些属性是否确实成立。

使用基于属性测试的常见方法是首先编写一个简单但天真的代码版本，你确信它是正确的。然后，对于给定的输入，你将该输入同时提供给想要测试的代码和简化的天真版本。如果两个实现的結果或输出相同，你的代码就没问题——这就是你寻找的正确性属性——但如果不同，你很可能找到了一个 bug。你也可以使用基于属性测试来检查与正确性无关的属性，例如某个操作是否比另一个实现严格花费更少的时间。共同的原则是，你希望真实版本和测试版本之间的任何结果差异都是信息丰富且可操作的，以便每次失败都能让你做出改进。天真实现可能是你试图替换或增强的标准库实现（如 std::collections::VecDeque），也可能是你试图优化的算法的更简单版本（如天真与优化的矩阵乘法）。

如果这种生成输入直到满足某个条件的方法听起来很像模糊测试，那是因为它确实如此——比我更聪明的人认为模糊测试“只是”基于属性测试，其中你测试的属性是“它不会崩溃”。

基于属性测试的一个缺点是它更依赖于提供的输入描述。而模糊测试会不断尝试所有可能的输入，属性测试往往由开发者注释引导，例如“0 到 64 之间的数字”或“包含三个逗号的字符串”。这使得属性测试能够更快地达到模糊测试可能需要很长时间随机遇到情况，但它确实需要人工工作，并且可能遗漏重要但小众的有 bug 的输入。随着模糊测试器和属性测试器越来越接近，模糊测试器也开始获得这种基于约束的搜索能力。

如果你对基于属性的测试生成感兴趣，我建议从 proptest crate 开始。

## TESTING SEQUENCES OF OPERATIONS

由于模糊测试器和属性测试器允许你生成任意的 Rust 类型，你并不局限于在 crate 中测试单个函数调用。例如，假设你想测试某个类型 Foo 在对其执行特定操作序列时是否表现正确。你可以定义一个枚举 Operation 来列出操作，并让你的测试函数接受一个 Vec<Operation>。然后你可以实例化一个 Foo 并依次对该 Foo 执行每个操作。大多数测试器都支持输入最小化，因此如果发现违反属性的输入，它们甚至会搜索仍然违反属性的最短操作序列！

## Test Augmentation

假设你有一个宏伟的测试套件已经设置好，你的代码通过了所有测试。很辉煌。但有一天，其中一个通常可靠的测试莫名其妙地失败或因段错误而崩溃。这类非确定性测试失败的两个常见原因是：竞态条件，即测试可能仅在两个操作在不同线程中以特定顺序发生时才失败，以及 unsafe 代码中的未定义行为，例如如果某些 unsafe 代码从未初始化的内存中读取特定值。

用普通测试捕获这类 bug 很困难——通常你没有足够的底层控制来对线程调度、内存布局和内容或其他随机系统因素编写可靠的测试。你可以让每个测试在循环中多次运行，但即使这样也可能无法捕获错误，如果坏情况足够罕见或不太可能的话。幸运的是，有工具可以帮助增强你的测试，使捕获这类 bug 变得容易得多。

第一个就是令人惊叹的工具 Miri，它是 Rust 中间层中间表示（MIR）的解释器。MIR 是 Rust 的内部简化表示，有助于编译器在不必考虑 Rust 本身所有语法糖的情况下找到优化并检查属性。通过 Miri 运行你的测试与运行 cargo miri test 一样简单。Miri 解释你的代码而不是像普通二进制那样编译并运行它，这使得测试运行速度会慢不少。但作为回报，Miri 可以跟踪每行代码执行时整个程序的状态。这使得 Miri 能够检测并报告如果你的程序表现出某些类型的未定义行为，例如未初始化内存读取、使用已 drop 的值后，或越界指针访问。与其让这些操作产生可能只有有时导致可观察测试失败（如崩溃）的奇怪程序行为，Miri 会在它们发生时检测到并立即通知你。

例如，考虑清单 7-8 中非常不安全的代码，它创建了对一个值的两个独占引用。

```
let mut x = 42;
let x: *mut i32 = &mut x;
let (x1, x2) = unsafe { (&mut *x, &mut *x) };
println!("{}", x1, x2);
```

# 宏

![](img/bbeab1f2edc3d45a3e6f7f6efbbb1747_104_0.png)

宏本质上是一种让编译器替你编写代码的工具。你为编译器提供一个公式，让它根据给定的输入参数生成代码；每次调用宏时，编译器都会用执行该公式得到的结果来替换这次调用。你可以把宏看作自动化的代码替换，而替换规则由你来定义。

Rust 的宏有各种不同的形态和规模，以便轻松实现多种不同形式的代码生成。两种主要的类型是*声明式*（declarative）宏和*过程式*（procedural）宏，本章将探讨这两类宏。我们还会看看宏在日常编码中派上用场的几种方式，以及更高级使用中可能出现的一些陷阱。本章假定你对宏已有一定了解，因此在阅读本章之前，我建议你先阅读 Rust 语言参考中关于宏的章节（https://doc.rust-lang.org/reference/macros.html）。

来自 C 系语言的程序员可能已经习惯了 C 和 C++ 那片无法无天的土地，在那里你可以用 #define 把每个 true 改成 false，或者删除所有出现的 else 关键字。如果你正是如此，就需要把宏与“做坏事”的感觉分离开来。Rust 中的宏远非 C 宏那样的狂野西部。它们（大多）遵循定义良好的规则，并且相当难以误用。

# 声明式宏

声明式宏是使用 macro_rules! 语法定义的，这种语法让你可以方便地定义类函数宏，而无需为此专门编写一个 crate（过程式宏则需要这样做）。一旦定义了声明式宏，你就可以用宏名后跟感叹号的方式调用它。我喜欢把这种宏想象成一种编译器辅助的查找替换：它能胜任许多常规、结构良好的转换任务，也能消除重复的样板代码。就你到目前为止使用 Rust 的经验而言，你所识别为宏的大多数宏很可能都是声明式宏。不过请注意，并非所有类函数宏都是声明式宏；macro_rules! 本身就是一个例子，format_args! 是另一个。! 后缀仅仅向编译器表明：这个宏调用将在编译时被替换为不同的源代码。

> 注意  
> 由于 Rust 的解析器会专门识别并解析带有 ! 的宏调用，你只能在解析器允许的位置使用它们。它们在大多数你期望的位置都能工作，比如表达式位置或 impl 块中，但并非所有位置都可以。例如，（在撰写本文时）你不能在期望标识符或 match 分支的位置调用类函数宏。

为什么声明式宏被称为“声明式”可能并不那么显而易见。毕竟，你在程序中不就是在“声明”一切吗？在这个语境下，“声明式”指的是：你并不说明宏的输入应该如何转换为输出，而只是声明当输入是 B 时，你希望输出看起来像 A。你声明事情应当如此，编译器会弄清楚为使你的声明成为现实所需的所有解析重连。这使得声明式宏简洁而富有表现力，不过由于用于表达声明的语言很有限，它们也往往相当晦涩难懂。

# 何时使用它们

当你发现自己一遍又一遍地编写相同的代码，并且希望，嗯，别再这样时，声明式宏就主要派上用场了。它们最适合相当机械的替换——如果你的目标是做花哨的代码变换或大量代码生成，过程式宏可能更合适。

我最常使用声明式宏的场景，是发现自己正在编写重复且结构相似的代码，例如测试和 trait 实现。对于测试，我经常想用略有不同的配置多次运行同一个测试。我可能会有类似于清单 8-1 所示的代码。

```rust
fn test_inner<T>(init: T, frobnify: bool) { ... }
#[test]
fn test_1u8_frobnified() {
    test_inner(1u8, true);
}
// ...
#[test]
fn test_i128_not_frobnified() {
    test_inner(1i128, false);
}
```

*清单 8-1：重复的测试代码*

虽然这样可行，但过于冗长、过于重复，也太容易因手工操作而出错。借助宏，我们可以做得更好，如清单 8-2 所示。

```rust
macro_rules! test_battery {
    ($($t:ty as $name:ident),*) => {
        $(
            mod $name {
                #[test]
                fn frobnified() { test_inner::<$t>(1, true) }
                #[test]
                fn unfrobnified() { test_inner::<$t>(1, false) }
            }
        )*
    }
}
test_battery! {
    u8 as u8_tests,
    // ...
    i128 as i128_tests
}
```

*清单 8-2：让宏替你重复*

这个宏会把每个逗号分隔的指令展开成自己的模块，每个模块包含两个测试：一个用 true 调用 `test_inner`，另一个用 false 调用。虽然宏定义并不简单，但它让添加更多测试变得容易得多。每个类型在 `test_battery!` 调用中只占一行，宏会负责为 true 和 false 两种参数都生成测试。我们还可以让它为不同的 `init` 值生成测试。现在，我们忘记测试某个特定配置的可能性已大大降低！

trait 实现的情况与此类似。如果你定义了自己的 trait，你通常会想为标准库中的多个类型实现该 trait，即使这些实现微不足道。假设你发明了 Clone trait，并想为标准库中所有 Copy 类型实现它。与其手动为每个类型写出实现，不如使用类似清单 8-3 中的宏。

```rust
macro_rules! clone_from_copy {
    ($( $t:ty ),*) => {
        $(impl Clone for $t {
            fn clone(&self) -> Self { *self }
        })*
    }
}
clone_from_copy![bool, f32, f64, u8, i8, /* ... */];
```

*清单 8-3：使用宏一蹴而就地为一众相似类型实现 trait*

在这里，我们为每个提供的类型生成一个 Clone 实现，其函数体只是用 * 从 &self 中 Copy 出值。你可能会疑惑，为什么我们不添加一个对 T where T: Copy 的 blanket 实现呢？我们确实可以这样做，但不这样做的重大原因之一是：那会迫使其他 crate 中恰好是 Copy 的类型也使用相同的 Clone 实现。有一个名为 specialization（特化）的实验性编译器特性可以提供变通方案，但在撰写本文时，该特性的稳定化仍有一段距离。所以，就目前而言，我们最好还是具体地逐一列出这些类型。这种模式也不仅限于简单的转发实现：例如，你可以轻松调整清单 8-3 中的示例，为所有整数类型实现一个 AddOne trait！

> 注意  
> 如果你曾在“应该用泛型还是声明式宏”上犹豫不决，那就应该用泛型。泛型通常比宏更符合人体工程学，也更能与语言中的其他结构集成。如果你想要一条经验法则：如果你的代码因类型而变，使用泛型；否则，使用宏。

## 编写声明式宏

对声明式宏所支持的全部语法进行详尽解释超出了本书的范围。不过，我们将介绍基础知识，因为其中有一些值得指出的奇特之处。

声明式宏由两个主要部分组成：*匹配器*和*转录器*。一个给定的宏可以有多个匹配器，每个匹配器都有一个关联的转录器。当编译器发现一个宏调用时，它会从第一个匹配器到最后一个匹配器逐一检查；当它找到一个与调用中的令牌匹配的匹配器时，它就会遍历相应转录器的令牌来替换该调用。清单 8-4 展示了声明式宏规则的不同部分是如何组合在一起的。

```
macro_rules! /* macro name */ {
  (/* 1st matcher */) => { /* 1st transcriber */ };
  (/* 2nd matcher */) => { /* 2nd transcriber */ };
}
```

## 匹配器

你可以把宏匹配器想象成一个令牌树，编译器会试图以预定义的方式对其进行扭曲和弯曲，以匹配调用点提供给它的输入令牌树。举个例子，考虑一个匹配器为 `$a:ident + $b:expr` 的宏。该匹配器可以匹配任意标识符（`:ident`）后跟一个加号，再后跟任意 Rust 表达式（`:expr`）。如果宏以 `x + 3 * 5` 被调用，编译器会发现，如果设置 `$a = x` 和 `$b = 3 * 5`，匹配器就能匹配成功。即使 `*` 从未出现在匹配器中，编译器也意识到 `3 * 5` 是一个有效表达式，因此可以与 `$b:expr` 匹配，后者接受任何表达式（即 `:expr` 部分）。

匹配器可能会变得相当复杂，但它们拥有巨大的表达能力，很像正则表达式。举一个不那么复杂的例子，下面的匹配器接受一个序列（`$()`），该序列由逗号分隔（`,`）的一个或多个（`+`）键/值对组成，键/值对的格式为 `key => value`：

```
$(\$key:expr => $value:expr),+
```

而且，关键在于，使用此匹配器调用宏的代码可以为键或值提供任意复杂的表达式——匹配器的魔力将确保键和值表达式被恰当地划分。

宏规则支持多种多样的*片段类型*；你已经见过用于标识符的 `:ident` 和用于表达式的 `:expr`，此外还有用于类型的 `:ty`，甚至还有用于任何单个令牌树的 `:tt`！你可以在 [Rust 语言参考书的第 3 章](https://doc.rust-lang.org/reference/macros-by-example.html) 中找到片段类型的完整列表。这些，再加上重复匹配模式的机制（`$()`），使你能够匹配大多数简单的代码模式。然而，如果你发现用匹配器难以表达你想要的模式，那么你可以尝试使用过程宏，因为过程宏不需要遵循 `macro_rules!` 所要求的严格语法。我们稍后将在本章中更详细地介绍这些内容。

## 转录器

一旦编译器匹配了声明式宏的匹配器，它就会使用该匹配器关联的转录器生成代码。宏匹配器定义的变量称为元变量。编译器会将转录器中每个元变量的每次出现（如上一节示例中的 `$key`）替换为与匹配器该部分匹配的输入。如果匹配器中有重复（如那个示例中的 `$(),+`），你可以在转录器中使用相同的语法，它将对输入中的每个匹配重复一次，每次展开都会为该次迭代持有每个元变量的适当替换。例如，对于 `$key` 和 `$value` 匹配器，我们可以编写以下转录器，为每个匹配到的 `$key`/`$value` 对生成一次对某个 map 的 `insert` 调用：

```
$(map.insert($key, $value;)+
```

注意，这里我们希望对每次重复使用分号，而不只是分隔重复，因此我们将分号放在重复括号内。你必须在转录器的每个重复中使用一个元变量，以便编译器知道要使用匹配器中的哪个重复（以防有多个重复）。

## 卫生性

你可能听说过 Rust 宏是卫生的，也许认为卫生使它们更安全或更易于使用，但未必理解这意味着什么。当我们说 Rust 宏是卫生的，我们的意思是声明式宏（通常）不能影响未明确传递给它的变量。一个简单的例子是：如果你声明了一个名为 `foo` 的变量，然后调用一个也定义了名为 `foo` 的变量的宏，那么默认情况下，宏的 `foo` 在调用点（即宏被调用的地方）是不可见的。类似地，宏也不能访问在调用点定义的变量（甚至 `self` 也不行），除非它们被显式传入。

在大多数情况下，你可以将宏标识符视为存在于自己的命名空间中，与它们展开成的代码的命名空间是分开的。例如，看看清单 8-5 中的代码，其中有一个宏试图（但失败了）遮蔽调用点的一个变量。

```
macro_rules! let_foo {
    ($x:expr) => {
        let foo = $x;
    }
}
let foo = 1;
let_foo!(2);
// expands to let foo = 2;
assert_eq!(foo, 1);
```

*清单 8-5：宏存在于它们自己的小宇宙中。大多数情况下如此。*

```rust
let mut x = 1;
please_set!(x, x + 1);
assert_eq!(x, 2);
```

*清单 8-6：让宏访问调用点的标识符*

我们本可以在宏中使用 `$i + 1`，但不能使用 `x + 1`，因为名字 `x` 在宏的定义作用域中不可用。

关于声明式宏和作用域，还有最后一点要注意：与 Rust 中几乎所有其他内容不同，声明式宏只有在声明之后才存在于源代码中。如果你试图使用文件中靠后定义的宏，那将行不通！这适用于整个项目；如果你在一个模块中声明了一个宏，并想在另一个模块中使用它，那么声明宏的模块必须在 crate 中较早出现，而不是较晚。反过来，如果 `foo` 和 `bar` 是 crate 根部的模块，而 `foo` 声明了一个 `bar` 想要使用的宏，那么 `mod foo` 必须出现在 *lib.rs* 中的 `mod bar` 之前！

> **注意**  
> *对于这种奇特的宏作用域（正式名称为文本作用域），有一个例外：如果你用 `#[macro_export]` 标记宏。该注解实际上会将宏提升到 crate 的根，并将其标记为 pub，因此它可以在你的 crate 中的任何地方或由你的 crate 的依赖者使用。*

## 过程宏

你可以把过程宏看作是解析器和代码生成的组合，而你在其中编写胶水代码。在高层面上，使用过程宏时，编译器会收集输入宏的令牌序列，并运行你的程序来确定应该用哪些令牌来替换它们。

过程宏之所以被称为“过程”宏，是因为你定义的是给定一些输入令牌后*如何*生成代码，而不仅仅是写出生成什么代码。编译器这一侧涉及的智能很少——就编译器而言，过程宏或多或少是一个可以执行任意代码替换的源代码预处理器。你的输入必须能被解析为 Rust 令牌流这一要求仍然存在，但也仅此而已！

## 过程宏的类型

过程宏有三种不同的风格，每种都专门针对一个特定的常见用例：

-   函数式宏，类似于 `macro_rules!` 生成的宏
-   派生宏，如 `#[derive(Serialize)]`
-   属性宏，如 `#[test]`

这三种类型都使用相同的基本机制：编译器向你的宏提供一个令牌序列，并期望你产生

一个（可能）与输入树相关的令牌序列作为回报。然而，它们在宏的调用方式以及输出的处理方式上有所不同。接下来我们将逐一简要介绍。

## 函数式宏

函数式宏是过程宏中最简单的形式。与声明式宏类似，它只是用过程宏返回的代码替换调用点的宏代码。然而，与声明式宏不同，所有的护栏都已移除：这些宏（像所有过程宏一样）不要求是卫生的，也不会保护你不与调用点周围代码中的标识符产生交互。相反，你的宏需要明确说明哪些标识符应与周围代码重叠（使用 `Span::call_site`），哪些应被视为宏私有的（使用 `Span::mixed_site`，我们稍后讨论）。

## 属性宏

属性宏同样是整体替换属性所附加的项，但它接受两个输入：属性中出现的令牌树（减去属性名）和它附加到的整个项的令牌树，包括该项可能拥有的任何其他属性。属性宏允许你轻松编写一个过程宏来转换某个项，例如向函数定义添加序言或尾声（就像 `#[test]` 所做的那样），或者修改结构体的字段。

## 派生宏

派生宏与另外两种略有不同，因为它是对宏目标进行添加，而不是替换。尽管这一限制可能看起来有些严格，但派生宏正是过程宏创建初期的主要推动因素之一。具体来说，著名的 serde crate 需要派生宏来实现其如今广为人知的 `#[derive(Serialize, Deserialize)]` 魔法。

派生宏可以说是过程宏中最简单的，因为它们的形态非常固定：你只能在被注解的项后面追加项；不能替换被注解的项，也不能让派生过程接受参数。派生宏确实允许你定义辅助属性——放在被注解类型内部以给派生宏提供线索的属性（如 `#[serde(skip)]`）——但这些属性大多像标记一样起作用，并不是独立的宏。

## 过程宏的代价

在我们讨论每种过程宏类型何时适用之前，有必要讨论一下为什么在伸手拿起过程宏之前你可能要三思——也就是编译时间的增加。

过程宏可能因为两个主要原因而显著增加编译时间。首先，它们往往会带来一些相当


依赖很重。例如，`syn` crate 为 Rust 标记流提供了解析器，大大简化了编写过程宏的体验，但在启用所有特性时，它可能需要数十秒才能编译完成。这个问题可以通过禁用不需要的特性，以及以调试模式而非发布模式编译过程宏来缓解（也应该这样做）。代码在调试模式下通常编译速度快几倍，对于大多数过程宏来说，你甚至不会注意到执行时间上的差异。

第二个原因是，过程宏很容易在不知不觉中生成大量代码。虽然宏让你不必真正输入生成的代码，但它并不能让编译器免于解析、编译和优化这些代码。随着你使用更多的过程宏，那些生成的样板代码会不断累积，从而拖慢编译时间。

值得指出的是，过程宏的实际执行时间很少成为整体编译时间的因素。虽然编译器必须等待过程宏完成其工作才能继续，但实际上大多数过程宏不会进行任何繁重的计算。*话虽如此，* 如果你的过程宏特别复杂，你可能会发现编译过程会把大量执行时间花在你的过程宏代码上，这一点值得留意！

## 那么，你认为你需要一个宏

现在让我们看看每种过程宏的一些好的使用场景。我们先从简单的开始：派生宏。

## 何时使用派生宏

派生宏只为一件事，而且仅此一件：在可以自动化的情况下，自动生成某个 trait 的实现。并非所有 trait 都有显而易见的自动化实现，但很多都有。在实践中，只有当某个 trait 经常被实现，并且它对任何给定类型的实现都相当明显时，你才应该考虑为它添加派生宏。第一点可能看起来像常识；如果你的 trait 只会被实现一两次，那么为它编写和维护一个复杂的派生宏可能并不值得。

然而，第二点可能看起来更奇怪：实现“显而易见”是什么意思？考虑一个像 `Debug` 这样的 trait。如果你被告知 `Debug` 的作用，并看到一个类型，你很可能会期望 `Debug` 的实现输出每个字段的名称以及其值的调试表示。这正是 `derive(Debug)` 所做的。那 `Clone` 呢？你可能会期望它直接克隆每个字段——同样，这正是 `derive(Clone)` 所做的。对于 `derive(serde::Serialize)`，我们希望它序列化每个字段及其值，而它也的确如此。总的来说，你希望 trait 的派生实现能够匹配开发者直觉中它大概会做的事情。如果某个 trait 没有明显的派生方式，或者更糟的是，你的派生实现与显而易见的实现不一致，那么最好不要为它提供派生宏。

## 何时使用函数式宏

函数式过程宏更难给出一个通用的经验法则。你可能会说，当你想要一个函数式宏但无法用 `macro_rules!` 表达时，就应该使用函数式宏，但这是一个相当主观的指导原则。毕竟，如果你真的用心去做，声明式宏也能做很多事情。

有两个特别好的理由让人选择函数式过程宏：

-   如果你已经有一个声明式宏，但其定义变得非常杂乱，导致宏难以维护。
-   如果你有一个纯函数，需要在编译时执行，但无法用 `const fn` 表达。这方面的一个例子是 `phf` crate：当在编译时给出一组键时，它会使用完美哈希函数生成一个哈希映射或集合。另一个例子是 `hex-literal`，它接收一个十六进制字符串并将其替换为相应的字节。一般来说，任何在编译时不仅转换输入，而是实际对输入进行计算的宏，都可能是一个好的候选者。

我还要补充一点，我不建议仅仅为了破坏宏的卫生性而采用函数式过程宏。函数式宏的卫生性是一个能避免许多调试麻烦的特性，在你故意破坏它之前，应该非常仔细地思考。

## 何时使用属性宏

接下来就剩下属性宏了。尽管它们可以说是过程宏中最通用的一种，但也最难确定在何时使用它们才是合适的。多年来，我反复看到四个用例是属性过程宏带来巨大价值的典型例子：

### 测试生成

我们通常希望在不同的配置下运行同一个测试，或者使用相同的引导代码运行许多类似的测试。虽然声明式宏可以让你表达这一点，但如果你有一个像 `#[foo_test]` 这样的属性，在每个被标注的测试中引入设置前奏和收尾代码，或者一个像 `#[test_case(1)]`、`#[test_case(2)]` 这样的可重复属性，用来标记某个测试应使用每个输入重复多次，那么你的代码通常会更容易阅读和维护。

### 框架注解

像 `rocket` 这样的库使用属性宏为函数和类型增加额外信息，框架随后利用这些信息，而无需用户进行大量手动配置。能够直接编写 `#[get("/<name>")] fn hello(name: String)` 比设置一个带有函数指针等的配置结构体要方便得多。本质上，这些属性构成了一种微型的领域特定语言（DSL），隐藏了大量原本必需的样板代码。类似地，异步 I/O 框架 `tokio` 允许你使用 `#[tokio::main] async fn main()` 来自动设置一个运行时并运行你的异步代码，从而让你不必在每个异步应用的 `main` 函数中编写相同的运行时设置。

### 透明中间件

有些库希望以不引人注目的方式注入到你的应用程序中，以提供不改变应用功能的附加价值。例如，像 `tracing` 这样的追踪与日志库，以及像 `metered` 这样的指标收集库，允许你通过添加一个属性来透明地检测函数；之后每次调用该函数都会运行由该库决定的额外代码。

### 类型转换器

有时你希望不仅仅是为类型派生 trait，而是以某种根本方式实际改变类型的定义。在这种情况下，属性宏是正确的选择。`pin_project` crate 就是一个很好的例子：它的主要目的不是实现特定的 trait，而是确保对给定类型字段的所有固定访问都遵循 Rust 的 `Pin` 类型和 `Unpin` trait 所规定的严格规则（我们将在第 9 章详细讨论这些类型）。它通过生成额外的辅助类型、为被标注的类型添加方法，并引入静态安全检查，确保用户不会意外地搬起石头砸自己的脚。虽然 `pin_project` 本来可以用过程式派生宏实现，但这可能会违背派生 trait 实现应显而易见的预期。

## 它们是如何工作的？

所有过程宏的核心是 `TokenStream` 类型，你可以遍历它来获取构成该标记流的各个 `TokenTree` 项。一个 `TokenTree` 要么是一个单独的标记——比如标识符、标点符号或字面量——要么是由 `()` 或 `{}` 等分隔符包围的另一个 `TokenStream`。通过遍历 `TokenStream`，你可以解析出任意你希望的语法，只要这些单独的标记是有效的 Rust 标记。如果你特别想将输入解析为 Rust 代码，那么你可能会想使用 `syn` crate，它实现了完整的 Rust 解析器，可以将 `TokenStream` 转换为易于遍历的 Rust AST。

对于大多数过程宏，你不仅需要解析 `TokenStream`，还需要生成 Rust 代码，注入到调用该过程宏的程序中。有两种主要方法。第一种是手动构造 `TokenStream`，每次扩展一个 `TokenTree`。第二种

使用 TokenStream 的 FromStr 实现即可，你可以用 `"".parse::<TokenStream>()` 将包含 Rust 代码的字符串解析为 TokenStream。你也可以混合使用这些方法；如果想在宏的输入前加上一些代码，只需为前言构造一个 TokenStream，然后使用 Extend trait 将原始输入追加上去。

> NOTE TokenStream 还实现了 Display，它会以可读的方式打印流中的 token。这在调试时非常有用！

Token 比我迄今描述的要稍微神奇一点，因为每个 token，实际上每个 TokenTree，都有一个 span。Span 是编译器将生成的代码关联回生成该代码的源代码的方式。每个 token 的 span 标记了该 token 来自的原始源位置。例如，考虑 Listing 8-7 中的宏，它为提供的类型生成一个平凡的 Debug 实现。

```
macro_rules! name_as_debug {
    ($t:ty) => {
        impl ::core::fmt::Debug for $t {
            fn fmt(&self, f: &mut ::core::fmt::Formatter<'_>) -> ::core::fmt::Result
            {
                ::core::write!(f, ::core::stringify!($t))
            }
        }
    }
}
```

Listing 8-7: 一个实现 Debug 的非常简单的宏

现在假设有人用 name_as_debug!(u31) 调用此宏。技术上，编译器错误发生在宏内部，具体在我们写 for $t 的地方（$t 的另一处使用可以处理无效类型）。但我们希望编译器指向用户代码中的 u31——事实上，span 正是让我们做到这一点。

生成的代码中 $t 的 span 是映射到宏调用中 $t 的代码。该信息随后在编译器中传递并与最终的编译器错误关联。当该编译器错误最终被打印时，编译器会打印宏内部的错误，说明类型 u31 不存在，但会高亮宏调用中的 u31 参数，因为那是错误的关联 span！

Span 非常灵活，它们使你能够编写能通过 compile_error 宏产生复杂错误信息的过程宏。顾名思义，compile_error! 会导致编译器在放置它的位置发出错误，并以提供的字符串作为消息。这看起来可能没什么用，直到你把它与 span 结合起来。通过将你为 compile_error! 调用生成的 TokenTree 的 span 设置为与输入的某个子集的 span 相等，你实际上是在告诉编译器“发出此编译器错误，并指向用户源代码的这一部分。”这两种机制结合起来，让宏产生的错误看起来源自代码的相关部分，即使实际的编译器错误在用户从未见过的生成的代码中的某个位置！

> NOTE
>
> 如果你曾好奇 syn 的错误处理是如何工作的，其 Error 类型实现了 Error::to_compile_error 方法，它会将其转换为仅包含 compile_error! 指令的 TokenStream。syn 的 Error 类型特别巧妙的地方在于它内部保存了一组错误，每个错误都会产生一个具有自己 span 的不同的 compile_error! 指令，这样你就可以轻松地从过程宏中产生多个独立的错误。

span 的威力还不止于此；span 也是 Rust 宏卫生性实现的机制。当你构造一个 Ident token 时，你也会给出该标识符的 span，而该 span 决定了该标识符的作用域。如果你将标识符的 span 设置为 Span::call_site()，标识符将在宏被调用的位置解析，因此不会与周围的作用域隔离。反之，如果你将其设置为 Span::mixed_site()，则（变量）标识符将在宏定义位置解析，因此相对于调用位置同名变量将完全卫生。Span::mixed_site 之所以这样命名，是因为它与 macro_rules! 中标识符卫生性的规则相匹配，我们之前讨论过它是“混合”的，即在调用位置和宏定义位置之间解析标识符。
