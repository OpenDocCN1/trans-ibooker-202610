
许多代码生成单元。由于 LTO 只在每个 crate 内部执行，而不是跨 crate 执行，因此这一额外遍并不会太繁重，增加的编译时间也应低于使用大量代码生成单元所节省的时间。Rust 还提供了一种称为 thin LTO 的技术，它可以让 LTO 遍在很大程度上并行化，代价是会错过一些“完整” LTO 遍本可以发现的优化。

> 注意：LTO 在许多情况下也可以跨外部函数接口边界进行优化。更多细节请参阅 `linker-plugin-lto` rustc 标志。

[profile] 部分还支持有助于调试的标志，例如 debug、debug-assertions 和 overflow-checks。debug 标志告诉编译器在编译后的二进制文件中包含调试符号。这会增大二进制文件的大小，但意味着在回溯和剖析中你得到的是函数名称等信息，而不仅仅是指令地址。debug-assertions 标志会启用 debug_assert! 宏以及其他相关的调试代码，这些代码在其他情况下不会编译（通过 cfg(debug_assertions)）。此类代码可能会让你的程序运行得更慢，但能让你更容易在运行时捕获可疑行为。overflow-checks 标志，顾名思义，会对整数运算启用溢出检查。这会让它们变慢（你注意到这里的规律了吗？）但能帮助你及早发现棘手的 bug。默认情况下，调试模式下这些全部启用，发布模式下全部禁用。

## [profile.*.panic]

[profile] 部分还有另一个值得拥有自己小节的标志：panic。该选项决定程序中的代码直接或间接（例如通过 unwrap）调用 panic! 时会发生什么。你可以将 panic 设置为 unwind（大多数平台上的默认值）或 abort。我们会在第 10 章更多地讨论 panic 和展开，但我这里先做一个简要总结。

通常，在 Rust 中，当你的程序 panic 时，发生 panic 的线程会开始展开其栈。你可以把展开想象为从当前函数递归地强制返回到该线程栈底部。也就是说，如果 main 调用了 foo，foo 调用了 bar，bar 调用了 baz，那么 baz 中的 panic 会强制从 baz 返回，然后 bar、foo，最后从 main 返回，导致程序退出。发生展开的线程会正常释放栈上的所有值，这使这些值有机会清理资源、报告错误等。这给了运行中的系统在 panic 时优雅退出的机会。

当线程 panic 并展开时，其他线程不受影响地继续运行。只有在运行 main 的线程退出时（如果它退出），程序才会终止。也就是说，panic 通常被隔离在发生 panic 的线程中。

这意味着展开是一把双刃剑；程序带着一些失败的组件勉强运行，这可能导致各种奇怪的行为。例如，想象一个线程在更新一个 Mutex 中的状态进行到一半时发生 panic。任何随后获取该 Mutex 的线程都必须准备好处理状态可能处于部分更新、不一致状态的情况。因此，一些同步原语

（如 Mutex）会记住上次被访问时是否发生过 panic，并将此信息传递给任何随后尝试访问该原语的线程。如果某个线程遇到这种状态，它通常也会 panic，从而导致级联，最终终止整个程序。但这可以说比带着已损坏的状态继续运行要好！

支持展开所需的簿记并非没有代价，而且它通常需要编译器和目标平台的特殊支持。例如，许多嵌入式平台根本无法高效地展开栈。因此 Rust 支持另一种 panic 模式：abort 确保在 panic 发生时整个程序立即退出。在这种模式下，任何线程都得不到清理的机会。这看起来可能很严厉，也确实如此，但它确保程序绝不会处于半运行状态，并且错误会立即显现。

> 警告
> panic 设置是全局的——如果你将其设置为 abort，所有依赖项也会以 abort 模式编译。

你可能已经注意到，当线程 panic 时，它往往会打印一个回溯：导致 panic 发生的一系列函数调用。这也是一种展开形式，虽然它与此处讨论的展开 panic 行为是分开的。即使使用 panic=abort，你也可以通过向 rustc 传递 -Cforce-unwind-tables 来获得回溯，这会让 rustc 包含向上遍历栈所需的信息，同时在 panic 时仍会终止程序。

## Profile 覆盖

你可以使用 profile 覆盖来仅为某个特定依赖项或特定 profile 设置 profile 选项。例如，清单 6-8 展示了如何使用 [profile.<profile-name>.package.<crate-name>] 语法，在调试模式下为 serde crate 启用激进优化，并为所有其他 crate 启用适度优化。

```toml
[profile.dev.package.serde]
opt-level = 3

[profile.dev.package."*"]
opt-level = 2
```

清单 6-8：覆盖特定依赖项或特定模式的 profile 选项

如果某个依赖项在调试模式下慢得令人望而却步（例如解压缩或视频编码），而你需要它被优化以加快测试套件的运行，这种优化覆盖就很有用。你还可以在 ~/.cargo/config 中的 Cargo 配置文件里使用 [profile.dev]（或类似）部分来指定全局 profile 默认值。

当你为特定依赖项设置优化参数时，请记住，这些参数只适用于作为该 crate 的一部分编译的代码；

> 如果此示例中的 serde 有一个你在自己的 crate 中使用的泛型方法或类型，那么该方法或类型的代码将在你的 crate 中被单态化并优化，此时应用的是你的 crate 的 profile 设置，而不是 serde 的 profile 覆盖设置。

## 条件编译

你编写的大多数 Rust 代码都是通用的——无论运行在什么 CPU 或操作系统上，行为都一样。但有时你必须做点特别的事情，才能让代码在 Windows、ARM 芯片上工作，或者当针对特定平台应用程序二进制接口（ABI）编译时。又或者，你可能想在某个给定的 CPU 指令可用时编写特定函数的优化版本，或者在持续集成（CI）环境中运行时禁用一些缓慢但无趣的初始化代码。为了满足这类情况，Rust 提供了条件编译机制，即只有在编译环境满足某些条件时，特定代码段才会被编译。

我们使用 cfg 关键字来表示条件编译，你在第 XX 页的“在你的 crate 中使用特性”中见过它。它通常以 #[cfg(condition)] 属性的形式出现，表示仅当 condition 为真时才编译下一个项目。Rust 还有 #[cfg_attr(condition, attribute)]，如果 condition 成立，它会被编译为 #[attribute]，否则就是空操作。你还可以使用 cfg!(condition) 宏将 cfg 条件作为布尔表达式求值。

每个 cfg 构造都接受一个由选项组成的单一条件，例如 feature = "some-feature"，以及组合器 all、any 和 not，它们的功能正如你所预期。选项要么是简单的名称，如 unix，要么是与特性条件中使用的键/值对。

有许多有趣的选项可以让编译依赖于它们。让我们从最常见到最不常见逐一介绍：

### 特性选项

你已经见过这些示例。特性选项采用 feature = "name-of-feature" 的形式，如果命名的特性已启用，则该选项为真。你可以使用组合器在单个条件中检查多个特性。例如，如果特性 f1 或特性 f2 已启用，则 any(feature = "f1", feature = "f2") 为真。

### 操作系统选项

这些选项使用键/值语法，键为 target_os，值为 windows、macos 和 linux 等。你还可以使用 target_family 来指定操作系统家族，其取值为 windows 或 unix。这些选项非常常见，因此它们拥有自己的命名简写，你可以直接使用 cfg(windows) 和 cfg(unix)。例如，如果你希望某个特定代码段只在 macOS 和 Windows 上编译，可以这样写：#[cfg(any(windows, target_os = "macos"))].
