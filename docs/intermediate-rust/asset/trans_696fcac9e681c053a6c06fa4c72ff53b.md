模糊测试器非常擅长找到代码未正确处理的奇怪边界情况。它们几乎不需要你进行设置：你只需将模糊测试器指向一个接受“可模糊”输入的函数，然后它就开始运行了。例如，清单 7-7 显示了你如何对 URL 解析器进行模糊测试的示例。

```
libfuzzer_sys::fuzz_target!(|data: &[u8]| {
    if let Ok(s) = std::str::from_utf8(data) {
        let _ = url::Url::parse(s);
    }
});
```

清单 7-7：使用 libfuzzer 对 URL 解析器进行模糊测试

模糊测试器会向闭包生成半随机的输入，任何形成有效 UTF-8 字符串的输入都会被传递给解析器。请注意，这里的代码并没有检查解析是否成功或失败——相反，它是在寻找解析器因违反内部不变量而 panic 或以其他方式崩溃的情况。

模糊测试器会一直运行直到你终止它，因此大多数模糊测试工具都内置了在探索一定数量的测试用例后停止的机制。如果你的输入不是一个简单可模糊的类型——比如哈希表——你通常可以使用像 arbitrary 这样的 crate 将模糊测试器生成的字节字符串转换为更复杂的 Rust 类型。看起来像魔法，但实际上在底层以非常直接的方式实现。该 crate 定义了一个 Arbitrary trait，其中有一个名为 arbitrary 的单一方法，用于从随机字节源构造实现该类型的实例。像 u32 或 bool 这样的原始类型会从该输入中读取必要数量的字节来构造自身的有效实例，而更复杂的类型如 HashMap 或 BTreeSet 则会从输入中产生一个数字来决定其长度，然后在内部类型上调用 Arbitrary 该次数。甚至还有一个属性 #[derive(Arbitrary)]，它通过对每个包含的类型调用 arbitrary 来实现 Arbitrary！要进一步探索模糊测试，我建议从 cargo-fuzz 开始。

## Property-Based Testing

有时你不仅想检查程序是否不会崩溃，还想检查它是否按预期工作。你的 add 函数没有 panic 很好，但如果它告诉你 add(1, 4) 的结果是 68，它可能仍然是错误的。这就是基于属性测试发挥作用的地方；你描述代码应遵守的若干属性，然后属性测试框架生成输入并检查这些属性是否确实成立。

使用基于属性测试的常见方法是首先编写一个简单但天真的代码版本，你确信它是正确的。然后，对于给定的输入，你将该输入同时提供给想要测试的代码和简化的天真版本。如果两个实现的結果或输出相同，你的代码就没问题——这就是你寻找的正确性属性——但如果不同，你很可能找到了一个 bug。你也可以使用基于属性测试来检查与正确性无关的属性，例如某个操作是否比另一个实现严格花费更少的时间。共同的原则是，你希望真实版本和测试版本之间的任何结果差异都是信息丰富且可操作的，以便每次失败都能让你做出改进。天真实现可能是你试图替换或增强的标准库实现（如 std::collections::VecDeque），也可能是你试图优化的算法的更简单版本（如天真与优化的矩阵乘法）。

如果这种生成输入直到满足某个条件的方法听起来很像模糊测试，那是因为它确实如此——比我更聪明的人认为模糊测试“只是”基于属性测试，其中你测试的属性是“它不会崩溃”。

基于属性测试的一个缺点是它更依赖于提供的输入描述。而模糊测试会不断尝试所有可能的输入，属性测试往往由开发者注释引导，例如“0 到 64 之间的数字”或“包含三个逗号的字符串”。这使得属性测试能够更快地达到模糊测试可能需要很长时间随机遇到情况，但它确实需要人工工作，并且可能遗漏重要但小众的有 bug 的输入。随着模糊测试器和属性测试器越来越接近，模糊测试器也开始获得这种基于约束的搜索能力。

如果你对基于属性的测试生成感兴趣，我建议从 proptest crate 开始。

## TESTING SEQUENCES OF OPERATIONS

由于模糊测试器和属性测试器允许你生成任意的 Rust 类型，你并不局限于在 crate 中测试单个函数调用。例如，假设你想测试某个类型 Foo 在对其执行特定操作序列时是否表现正确。你可以定义一个枚举 Operation 来列出操作，并让你的测试函数接受一个 Vec<Operation>。然后你可以实例化一个 Foo 并依次对该 Foo 执行每个操作。大多数测试器都支持输入最小化，因此如果发现违反属性的输入，它们甚至会搜索仍然违反属性的最短操作序列！

## Test Augmentation

假设你有一个宏伟的测试套件已经设置好，你的代码通过了所有测试。很辉煌。但有一天，其中一个通常可靠的测试莫名其妙地失败或因段错误而崩溃。这类非确定性测试失败的两个常见原因是：竞态条件，即测试可能仅在两个操作在不同线程中以特定顺序发生时才失败，以及 unsafe 代码中的未定义行为，例如如果某些 unsafe 代码从未初始化的内存中读取特定值。

用普通测试捕获这类 bug 很困难——通常你没有足够的底层控制来对线程调度、内存布局和内容或其他随机系统因素编写可靠的测试。你可以让每个测试在循环中多次运行，但即使这样也可能无法捕获错误，如果坏情况足够罕见或不太可能的话。幸运的是，有工具可以帮助增强你的测试，使捕获这类 bug 变得容易得多。

第一个就是令人惊叹的工具 Miri，它是 Rust 中间层中间表示（MIR）的解释器。MIR 是 Rust 的内部简化表示，有助于编译器在不必考虑 Rust 本身所有语法糖的情况下找到优化并检查属性。通过 Miri 运行你的测试与运行 cargo miri test 一样简单。Miri 解释你的代码而不是像普通二进制那样编译并运行它，这使得测试运行速度会慢不少。但作为回报，Miri 可以跟踪每行代码执行时整个程序的状态。这使得 Miri 能够检测并报告如果你的程序表现出某些类型的未定义行为，例如未初始化内存读取、使用已 drop 的值后，或越界指针访问。与其让这些操作产生可能只有有时导致可观察测试失败（如崩溃）的奇怪程序行为，Miri 会在它们发生时检测到并立即通知你。

例如，考虑清单 7-8 中非常不安全的代码，它创建了对一个值的两个独占引用。

```
let mut x = 42;
let x: *mut i32 = &mut x;
let (x1, x2) = unsafe { (&mut *x, &mut *x) };
println!("{}", x1, x2);
```
