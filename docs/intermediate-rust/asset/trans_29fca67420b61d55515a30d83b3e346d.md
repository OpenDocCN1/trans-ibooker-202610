
使用 TokenStream 的 FromStr 实现即可，你可以用 `"".parse::<TokenStream>()` 将包含 Rust 代码的字符串解析为 TokenStream。你也可以混合使用这些方法；如果想在宏的输入前加上一些代码，只需为前言构造一个 TokenStream，然后使用 Extend trait 将原始输入追加上去。

> NOTE TokenStream 还实现了 Display，它会以可读的方式打印流中的 token。这在调试时非常有用！

Token 比我迄今描述的要稍微神奇一点，因为每个 token，实际上每个 TokenTree，都有一个 span。Span 是编译器将生成的代码关联回生成该代码的源代码的方式。每个 token 的 span 标记了该 token 来自的原始源位置。例如，考虑 Listing 8-7 中的宏，它为提供的类型生成一个平凡的 Debug 实现。

```
macro_rules! name_as_debug {
    ($t:ty) => {
        impl ::core::fmt::Debug for $t {
            fn fmt(&self, f: &mut ::core::fmt::Formatter<'_>) -> ::core::fmt::Result
            {
                ::core::write!(f, ::core::stringify!($t))
            }
        }
    }
}
```

Listing 8-7: 一个实现 Debug 的非常简单的宏

现在假设有人用 name_as_debug!(u31) 调用此宏。技术上，编译器错误发生在宏内部，具体在我们写 for $t 的地方（$t 的另一处使用可以处理无效类型）。但我们希望编译器指向用户代码中的 u31——事实上，span 正是让我们做到这一点。

生成的代码中 $t 的 span 是映射到宏调用中 $t 的代码。该信息随后在编译器中传递并与最终的编译器错误关联。当该编译器错误最终被打印时，编译器会打印宏内部的错误，说明类型 u31 不存在，但会高亮宏调用中的 u31 参数，因为那是错误的关联 span！

Span 非常灵活，它们使你能够编写能通过 compile_error 宏产生复杂错误信息的过程宏。顾名思义，compile_error! 会导致编译器在放置它的位置发出错误，并以提供的字符串作为消息。这看起来可能没什么用，直到你把它与 span 结合起来。通过将你为 compile_error! 调用生成的 TokenTree 的 span 设置为与输入的某个子集的 span 相等，你实际上是在告诉编译器“发出此编译器错误，并指向用户源代码的这一部分。”这两种机制结合起来，让宏产生的错误看起来源自代码的相关部分，即使实际的编译器错误在用户从未见过的生成的代码中的某个位置！

> NOTE
>
> 如果你曾好奇 syn 的错误处理是如何工作的，其 Error 类型实现了 Error::to_compile_error 方法，它会将其转换为仅包含 compile_error! 指令的 TokenStream。syn 的 Error 类型特别巧妙的地方在于它内部保存了一组错误，每个错误都会产生一个具有自己 span 的不同的 compile_error! 指令，这样你就可以轻松地从过程宏中产生多个独立的错误。

span 的威力还不止于此；span 也是 Rust 宏卫生性实现的机制。当你构造一个 Ident token 时，你也会给出该标识符的 span，而该 span 决定了该标识符的作用域。如果你将标识符的 span 设置为 Span::call_site()，标识符将在宏被调用的位置解析，因此不会与周围的作用域隔离。反之，如果你将其设置为 Span::mixed_site()，则（变量）标识符将在宏定义位置解析，因此相对于调用位置同名变量将完全卫生。Span::mixed_site 之所以这样命名，是因为它与 macro_rules! 中标识符卫生性的规则相匹配，我们之前讨论过它是“混合”的，即在调用位置和宏定义位置之间解析标识符。

### Summary

在本章中，我们介绍了声明式宏和过程宏，并探讨了在你自己的代码中何时可能觉得它们有用。我们还深入研究了支撑每种宏类型的机制，以及在编写自己的宏时需要注意的一些特性和陷阱。在下一章，我们将开始进入异步编程和 Future trait 的旅程。我保证——它就在下一页。

## 9 ASYNCHRONOUS PROGRAMMING

![](img/bbeab1f2edc3d45a3e6f7f6efbbb1747_120_0.png)

异步编程顾名思义，就是非同步的编程。在高层面上，异步操作在后台执行——程序不会等待异步操作完成，而是会立即继续执行下一行代码。如果你对异步编程还不熟悉，这个定义可能感觉不够，因为它并没有真正解释异步编程是什么。要真正理解 Rust 中的异步编程模型及其工作原理，我们必须先深入了解替代方案。也就是说，我们需要在理解异步模型之前先理解同步编程模型。这在澄清概念和展示使用异步编程的权衡方面都很重要：异步解决方案并不总是正确的！我们将从先快速了解异步编程作为概念的动机开始；然后深入探讨 Rust 中异步在底层实际如何工作。

### What’s the Deal with Asynchrony?

在我们进入同步和异步编程模型的细节之前，我们首先需要快速了解一下你的计算机在运行你的程序时实际在做什么。

计算机很快。非常快。事实上快到它们大部分时间都在等待事情发生。除非你在解压缩文件、编码音频或 crunch 数字，否则很可能你的 CPU 大部分时间都在空闲，等待操作完成。它在等待网络数据包到达，等待鼠标移动，等待磁盘完成写入字节，甚至可能只是等待主内存读取完成。从 CPU 的角度来看，在大多数此类事件之间，漫长的岁月过去了。当其中一个事件发生时，CPU 运行几条指令，然后又回到等待状态。看看你的 CPU 利用率——它可能在个位数徘徊，而且这很可能就是它大部分时间的状态。

### Synchronous Interfaces

同步接口只允许你的程序（或更确切地说，你程序中的单个线程）一次执行一个操作；每个操作必须等待前一个同步操作完成后才能运行。你在野外看到的大多数接口都是同步的：你调用它们，它们去做一些事情，最终在操作完成后返回，你的程序就可以继续了。其原因正如本章后面会看到的，是使操作异步需要相当多的额外机制。除非你需要异步的好处，否则坚持同步模型需要的繁文缛节要少得多。

同步接口隐藏了所有这些等待；应用程序调用一个函数说“把这些字节写入这个文件”，一段时间后，该函数完成，下一行代码执行。在幕后，真正发生的是操作系统将写操作排队到磁盘，然后让应用程序休眠，直到磁盘报告写操作已完成。应用程序将其体验为函数执行时间很长，但实际上它根本没有执行，只是在等待。

以这种方式顺序执行操作的接口也常被称为阻塞，因为接口中必须等待某些外部事件发生才能取得进展的操作会阻塞进一步的执行，直到该事件发生。无论你将接口称为同步还是阻塞，其基本思想都相同：应用程序不会继续，直到当前操作完成。在操作等待期间，应用程序也在等待。

同步接口通常被认为易于使用且易于推理，因为你的代码一次只执行一行。
