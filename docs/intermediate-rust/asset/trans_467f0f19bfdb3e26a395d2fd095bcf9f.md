

当我们之后尝试通过共享引用来访问字符串引用 s 以打印它时，编译器会尝试缩短 MutStr 所使用的 s 的可变借用，以允许对 s 的共享借用。

在双生命周期的情况下，'a 恰好会在 println 之前结束，而 'b 保持不变。另一方面，在单生命周期的情况下，我们遇到了问题。编译器想要缩短对 s 的借用，但要做到这一点，它还必须缩短对 str 的借用。虽然 &'static str 通常可以缩短为任意 &'a str（&'a T 在 'a 上是协变的），但这里它位于 &mut T 之后，而 &mut T 在 T 上是不变的。不变性要求相关类型永远不会被子类型或超类型替换，因此编译器缩短借用的尝试失败了，并报告该列表仍被可变借用。哎！

由于不变性带来的灵活性降低，你希望确保你的类型在尽可能多的泛型参数上保持协变（或在适当情况下保持逆变）。如果这需要引入额外的生命周期参数，你需要仔细权衡增加另一个参数的认知成本与不变性的易用性成本。

## 内存中的类型

每个 Rust 值都有一个类型。类型在 Rust 中有许多用途，我们将在本章中看到，但它们最基本的角色之一是告诉你如何解释内存中的位。例如，位序列 0b10111101（用十六进制表示法写成 0xBD）本身没有任何意义，直到你给它分配一个类型。当在 u8 类型下解释时，该位序列是数字 189。当在 i8 类型下解释时，它是 −67。当你定义自己的类型时，编译器的工作是确定所定义类型的每个部分在该类型的内存表示中的位置。你的 struct 的每个字段出现在位序列的哪个位置？你的 enum 的判别式存储在哪里？当你开始编写更高级的 Rust 代码时，理解这个过程是如何工作的很重要，因为这些细节既影响代码的正确性，也影响性能。

### 对齐

在我们讨论类型的内存表示如何确定之前，我们首先需要讨论对齐的概念，它决定了类型的字节可以存储在哪里。一旦类型的表示被确定，你可能会认为你可以取任意的内存位置，并将存储在那里的字节解释为该类型。虽然这在理论上是正确的，但在实践中，硬件也限制了给定类型的放置位置。最明显的例子是指针指向字节，而不是位。如果你将类型 T 的值放在计算机内存的第 4 位开始，你将无法引用它的位置；你只能创建指向字节 0 或字节 1（第 8 位）的指针。因此，所有值，无论其类型如何，都必须从字节边界开始。我们说所有值至少必须是字节对齐的——它们必须被放置在一个是 8 的倍数的地址上。

某些值比字节对齐有更严格的规则。在 CPU 和内存系统中，内存通常以大于单个字节的块进行访问。例如，在 64 位 CPU 上，大多数值以 8 字节（64 位）的块访问，每次操作从 8 字节对齐的地址开始。这被称为 CPU 的字长。然后 CPU 使用一些技巧来处理更小值的读写，或跨越这些块边界的值。

在可能的情况下，你希望确保硬件能够以其“原生”对齐方式运行。要了解原因，请考虑如果尝试读取一个从 8 字节块中间开始的 i64（也就是说，指向它的指针不是 8 字节对齐的）会发生什么。硬件将不得不进行两次读取——一次从第一个块的后半部分读取以到达 i64 的起始位置，另一次从第二个块的前半部分读取 i64 的其余部分——然后将结果拼接在一起。这不是很高效。由于该操作分散在对底层内存的多次访问中，如果你正在读取的内存被另一个线程并发写入，你最终可能会得到奇怪的结果。你可能会在另一个线程写入之前读取前 4 个字节，在写入之后读取后 4 个字节，从而导致值损坏。

对未对齐数据的操作被称为未对齐访问，可能导致性能不佳和严重的并发问题。因此，许多 CPU 操作要求或强烈倾向于其参数自然对齐。自然对齐的值是其对齐方式与其大小匹配的值。例如，对于 8 字节加载，提供的地址需要是 8 字节对齐的。

由于对齐访问通常更快，并提供更强的一致性语义，编译器会尽可能利用它们。它通过为每个类型赋予一个基于其包含的类型计算的对齐方式来实现这一点。内置值通常与其大小对齐，所以 u8 是字节对齐，u16 是 2 字节对齐，u32 是 4 字节对齐，u64 是 8 字节对齐。复杂类型——包含其他类型的类型——通常被分配为其包含的任何类型中最大的对齐方式。例如，包含 u8、u16 和 u32 的类型将是 4 字节对齐的，因为 u32 的存在。

### 布局

既然你已经了解了对齐，我们可以探讨编译器如何决定类型的内存表示，即布局。默认情况下，正如你很快会看到的，Rust 编译器对如何布局类型给出的保证很少，这使得它成为理解底层原理的一个不好的起点。幸运的是，Rust 提供了一个 repr 属性，你可以将其添加到类型定义中，以请求该类型的特定内存表示。如果你能看到的话，你将看到的最常见的 repr 是 repr(C)。顾名思义，它以与 C 或 C++ 编译器布局相同类型的方式兼容的方式来布局该类型。这在编写使用外部函数接口与其他语言交互的 Rust 代码时很有帮助，我们将在第 12 章中讨论，因为 Rust 将生成与其他语言编译器期望匹配的布局。由于 C 布局是可预测的且不会改变，repr(C) 在 unsafe 上下文中也很有用，如果你正在使用指向该类型的原始指针，或者如果你需要在你知道具有相同字段的两个不同类型之间进行转换。当然，它也是我们迈出布局算法第一步的完美选择。

> 另一种有用的表示是 repr(transparent)，它只能用于具有单个字段的类型，并保证外部类型的布局与内部类型的布局完全相同。这与“newtype”模式结合使用时很方便，在 newtype 模式中，你可能希望以相同的方式操作某个 struct A 和 struct NewA(A) 的内存表示。如果没有 repr(transparent)，Rust 编译器不保证它们具有相同的布局。

那么，让我们看看编译器如何使用 repr(C) 布局一个特定类型：清单 3-1 中的 Foo 类型。你认为编译器会如何在内存中布局它？

```
#[repr(C)]
struct Foo {
    tiny: bool,
    normal: u32,
    small: u8,
    long: u64,
    short: u16,
}
```
