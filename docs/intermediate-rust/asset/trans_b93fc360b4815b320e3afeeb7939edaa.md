

## Rust 测试机制

要理解 Rust 提供的各种测试机制，你必须首先了解 Rust 如何构建和运行测试。当你运行 `cargo test --lib` 时，Cargo 做的唯一特殊事情就是向 `rustc` 传递 `--test` 标志。该标志告诉 `rustc` 生成一个运行所有单元测试的测试二进制文件，而不是仅仅编译 crate 的库或二进制文件。在幕后，`--test` 有两个主要作用。首先，它启用 `cfg(test)`，以便你可以有条件地包含测试代码（稍后会详细介绍）。其次，它使编译器生成一个测试 harness：一个精心生成的 `main` 函数，在运行时调用程序中每个 `#[test]` 函数。

### 测试 Harness

编译器通过程序宏的混合生成测试 harness `main` 函数，我们将在第 8 章更深入地讨论这些宏，以及少量魔法。本质上，harness 将每个用 `#[test]` 注释的函数转换为测试描述符——这是程序宏的部分。然后它将每个描述符的路径暴露给生成的 `main` 函数——这是魔法部分。描述符包含诸如测试的名称、其设置的任何附加选项（如 `#[should_panic]`）等信息。其核心是，测试 harness 遍历 crate 中的测试，运行它们，捕获其结果并打印结果。因此，它还包括解析命令行参数（例如 `--test-threads=1`）、捕获测试输出、以并行方式运行列出的测试并收集测试结果的逻辑。

截至本文撰写时，Rust 开发者正在努力使测试 harness 生成的魔法部分成为一个公开可用的 API，以便开发者可以构建自己的测试 harness。这项工作仍处于实验阶段，但该提案与今天存在的模型相当接近。需要弄清楚的魔法的一部分是如何确保 `#[test]` 函数可供生成的 `main` 函数使用，即使它们位于私有子模块内部。

集成测试（`tests/` 中的测试）遵循与单元测试相同的流程，唯一例外是它们各自被编译为独立的 crate，这意味着它们只能访问主 crate 的公共接口，并且在针对未使用 `#[cfg(test)]` 编译的主 crate 运行。每个 `tests/` 中的文件都会生成一个测试 harness。`tests/` 下子目录中的文件不会生成测试 harness，以便你可以为测试拥有共享子模块。

NOTE 如果你明确希望为子目录中的文件生成测试 harness，可以通过调用该文件 `main.rs` 来选择加入。

Rust 不要求你使用默认的测试 harness。你可以改为选择退出它，并通过在 `Cargo.toml` 中为给定的集成测试设置 `harness = false` 来实现自己的 `main` 方法作为测试运行器，如清单 7-1 所示。然后你定义的 `main` 方法将被调用来运行测试。

```
[[test]]
name = "custom"
path = "tests/custom.rs"
harness = false
```

清单 7-1：选择退出标准测试 harness

没有测试 harness，`#[test]` 周围的魔法就不会发生。相反，你需要编写自己的 `main` 函数来运行你想要执行的测试代码。本质上，你正在编写一个普通的 Rust 二进制文件，只是恰好由 `cargo test` 运行。该二进制文件负责处理默认 harness 通常做的所有事情（如果你想支持它们），例如命令行标志。`harness` 属性是为每个集成测试单独设置的，因此你可以有一个使用标准 harness 的测试文件和一个不使用标准 harness 的测试文件。

### 默认测试 HARNESS 的参数

默认测试 harness 支持许多命令行参数来配置测试的运行方式。这些参数不是直接传递给 `cargo test`，而是传递给 Cargo 为你编译和运行的测试二进制文件，当你运行 `cargo test` 时。要访问该标志集，请在 `cargo test` 后传递 `--`，然后是测试二进制文件的参数。例如，要查看测试二进制文件的帮助文本，你需要运行 `cargo test -- --help`。

通过这些命令行参数可以获得许多方便的配置选项。`--nocapture` 标志禁用运行 Rust 测试时通常发生的输出捕获。这在你想实时观察测试输出而不是在测试失败后一次性全部看到时很有用。你可以使用 `--test-threads` 选项限制并发运行的测试数量，这在你有一个挂起或段错误的测试并且想要通过顺序运行测试来找出它时很有帮助。还有 `--skip` 选项用于跳过匹配特定模式的测试，`--ignored` 用于运行通常会被忽略的测试（例如需要外部程序运行的测试），以及 `--list` 用于仅列出所有可用测试。

请记住，这些参数都是由默认测试 harness 实现的，因此如果你禁用它（使用 `harness = false`），你需要在自己的 `main` 函数中自行实现你需要的参数！

没有 harness 的集成测试主要用于基准测试，如我们稍后会看到的，但它们在你想要运行不符合标准“一个函数，一个测试”模型的测试时也很方便。例如，你经常会看到无 harness 测试与模糊测试器、模型检查器以及需要自定义全局设置（例如在 WebAssembly 下或在处理自定义目标时）的测试一起使用。

### `#[cfg(test)]`

当 Rust 为测试构建代码时，它会设置编译器配置标志 `test`，你可以用它与条件编译一起使用，以便在代码未被专门测试时将其编译掉。乍一看，这似乎很奇怪：你难道不想测试进入生产环境的完全相同的代码吗？你确实想，但仅在测试时可用的代码允许你在几个方面编写更好、更彻底的测试。

### 模拟

在编写测试时，你通常希望对正在测试的代码以及你的代码可能交互的任何其他类型都有严格的控制。例如，如果你正在测试网络客户端，你可能不想通过真实网络运行单元测试，而是直接控制“网络”发出哪些字节以及何时发出。或者，如果你正在测试数据结构，你希望你的测试使用允许你在每次调用时控制每个方法返回值的类型。你可能还想收集指标，例如给定方法被调用的频率或是否发出给定字节序列。

这些“假”类型和实现被称为模拟，它们是任何广泛单元测试套件的关键特性。虽然你通常可以通过手动方式完成获得这种控制所需的工作，但让库为你处理大部分繁琐细节会更方便。这就是自动化模拟发挥作用的地方。模拟库将具有生成具有特定属性或签名的类型（包括函数）的设施，以及在测试执行期间控制和 introspect 这些生成项的机制。

Rust 中的模拟通常通过泛型实现——只要你的程序、数据结构、框架或工具对你可能想要模拟的任何内容都是泛型的（或接受 trait 对象），你就可以使用模拟库生成符合的类型来实例化这些泛型参数。然后你通过使用生成的模拟类型实例化你的泛型构造来编写单元测试，就开始了！

在泛型不方便或不合适的情况下，例如如果你想避免让类型的某个方面对用户泛型化，你可以改为将你想要模拟的状态和行为封装在专用结构体中。然后你将生成该结构体及其方法的模拟版本，并使用条件编译根据 `cfg(test)` 或仅测试的功能如 `cfg(feature = "test_mock_foo")` 使用真实或模拟实现。

目前，Rust 社区中还没有出现一个单一的模拟库，甚至一个单一的模拟方法成为“唯一真理”。我所知道的最广泛和最彻底的模拟库是 `mockall` crate，但它仍在积极开发中，还有许多其他竞争者。
