

## 仅用于测试的 API

首先，拥有仅用于测试的代码可以让你向你的（单元）测试公开额外的方法、字段和类型，这样测试不仅可以检查公共 API 是否按预期行为，还可以检查内部状态是否正确。例如，考虑来自 `hashbrown` 的 `HashMap` 类型，该 crate 实现了标准库的 `HashMap`。`HashMap` 类型实际上只是 `RawTable` 类型的包装器，而 `RawTable` 实现了大部分哈希表逻辑。假设在对空映射执行 `HashMap::insert` 之后，你想检查映射中的单个桶是否非空，如清单 7-2 所示。

```
#[test]
fn insert_just_one() {
    let mut m = HashMap::new();
    m.insert(42, ());
    let full = m.table.buckets.iter().filter(Bucket::is_full).count();
    assert_eq!(full, 1);
}
```

*清单 7-2：访问无法访问的内部状态的测试，因此无法编译*

这段代码按原样编写将无法编译，因为虽然测试代码可以访问 `HashMap` 的私有 `table` 字段，但它无法访问 `RawTable` 的同样私有的 `buckets` 字段，因为 `RawTable` 位于不同的模块中。我们可以通过将 `buckets` 字段的可见性设为 `pub(crate)` 来修复这个问题，但我们真的不希望 `HashMap` 通常可以触及桶，因为它可能会意外破坏 `RawTable` 的内部状态。即使将桶作为只读提供也可能有问题，因为 `HashMap` 中的新代码随后可能会开始依赖 `RawTable` 的内部状态，从而使未来的修改变得更加困难。

解决方案是使用 `#[cfg(test)]`。我们可以向 `RawTable` 添加一个方法，该方法仅在测试时允许访问桶，如清单 7-3 所示，从而避免为其余代码添加脚枪。清单 7-2 中的代码随后可以更新为调用 `buckets()` 而不是访问私有的 `buckets` 字段。

```
impl RawTable {
    #[cfg(test)]
    pub(crate) fn buckets(&self) -> &[Bucket] {
        &self.buckets
    }
}
```

*清单 7-3：使用 `#[cfg(test)]` 使内部状态在测试上下文中可访问*

## 测试断言的记账

拥有仅在测试期间存在的代码的第二个好处是，你可以增强程序以执行额外的运行时记账，然后由测试检查。例如，想象你正在编写自己的标准库中 `BufWriter` 类型的版本。在测试它时，你想确保 `BufWriter` 不会发出系统调用

使用类似 `#[tokio::main] async fn main` 的异步 main 函数，或者如果你想向文档测试添加额外的模块。

要在文档测试中使用 `?` 运算符，你通常不必使用自定义 main 函数，因为 `rustdoc` 包含一些启发式方法，如果你的代码看起来使用了 `?`（例如，如果它以 `Ok(())` 结尾），则将返回类型设置为 `Result<(), impl Debug>`。如果类型推断在函数错误类型方面给你带来困难，你可以通过将文档测试的最后一行显式键入来消除歧义，如下所示：`Ok::<(), T>(())`。

文档测试具有许多额外的功能，在你为更复杂的接口编写文档时非常有用。首先是隐藏单个行的能力。如果你用 `#` 为文档测试的一行加前缀，该行在编译和运行时会被包含，但不会包含在文档中生成的代码片段中。这让你可以轻松隐藏对当前示例不重要的细节，例如为虚拟类型实现特征或生成值。如果希望在不每次都显示相同的引导代码的情况下呈现一系列示例，这也很有用。清单 7-5 给出了文档测试中隐藏行的示例。

````
/// Completely frobnifies a number through I/O.
///
/// In this first example we hide the value generation.
/// ```
/// # let unfrobnified_number = 0;
/// # let already_frobnified = 1;
/// assert!(frobnify(unfrobnified_number).is_ok());
/// assert!(frobnify(already_frobnified).is_err());
/// ```
///
/// Here's an example that uses `?` on multiple types
/// and thus needs to declare the concrete error type,
/// but we don't want to distract the user with that.
/// We also hide the use that brings the function into scope.
/// ```
/// # use mylib::frobnify;
/// frobnify("0".parse()?)?;
/// # Ok::<(), anyhow::Error>(())
/// ```
///
/// You could even replace an entire block of code completely,
/// though use this _very_ sparingly:
/// ```
/// # /*
/// let i = ...;
/// # */
/// # let i = 42;
/// frobnify(i)?;
/// ```
fn frobnify(i: usize) -> std::io::Result<()> {
````

*清单 7-5：使用 # 在文档测试中隐藏行*

> **注意：** 慎用此功能；如果用户复制粘贴示例后因你隐藏了必需步骤而无法工作，这会让用户感到沮丧。

与 `#[test]` 函数一样，文档测试也支持修改文档测试运行方式的属性。这些属性紧跟在用于表示代码块的三重反引号之后，并且多个属性可以用逗号分隔。

与测试函数一样，你可以指定 `should_panic` 属性来指示特定文档测试中的代码在运行时应 panic，或 `ignore` 来仅在 `cargo test` 使用 `--ignored` 标志运行时检查代码段。你还可以使用 `no_run` 属性来指示给定的文档测试应编译但不应运行。

属性 `compile_fail` 告诉 `rustdoc` 文档示例中的代码不应编译。这向用户表明特定用法是不可能的，并且作为有用的测试提醒你在库的相关方面发生变化时更新文档。你也可以使用此属性来检查你的类型的某些静态属性是否成立。清单 7-6 显示了如何使用 `compile_fail` 检查给定类型是否未实现 `Send`，这可能对于在不安全代码中维护安全保证是必要的。

```compile_fail
# struct MyNonSendType(std::rc::Rc<()>);
fn is_send<T: Send>() {}
is_send::<MyNonSendType>();
```

*清单 7-6：使用 `compile_fail` 测试代码是否无法编译*

`compile_fail` 是一个相当粗糙的工具，因为它没有说明代码为何无法编译。例如，如果代码因缺少分号而无法编译，`compile_fail` 测试仍会显示成功。因此，你通常只应在确保测试确实以预期错误无法编译后才添加此属性。如果你需要更精细的编译错误测试，例如在开发宏时，请查看 `trybuild` crate。

## 额外测试工具

测试不仅仅是运行测试函数并查看它们是否产生预期结果。测试技术、方法和工具的全面调查超出了本书的范围，但随着你扩展测试范围，你应该了解一些关键的 Rust 特定部分。

### 静态检查

你可能不认为 linter 的检查是测试，但在 Rust 中它们通常可以是。Rust linter `clippy` 将其许多 lint 分类为正确性 lint。这些 lint 捕获编译但几乎肯定是 bug 的代码模式。一些例子是 `a = b; b = a`，它未能交换 `a` 和 `b`；`std::mem::forget(t)`，其中 `t` 是引用；以及 `for x in y.next()`，它只会遍历 `y` 中的第一个元素。如果你尚未将 `clippy` 作为 CI 流程的一部分运行，你可能应该这样做。

Clippy 还附带许多其他 lint，虽然通常有帮助，但可能比你更喜欢的更具主观性。例如，默认启用的 `type_complexity` lint，如果你在程序中使用特别复杂的类型，如 `Rc<Vec<Vec<Box<(u32, u32, u32, u32)>>>>`，就会发出警告。虽然该警告鼓励你编写更易读的代码，但你可能会发现它过于挑剔而缺乏广泛的实用性。如果代码的某个部分错误地触发了特定 lint，或你只想允许其特定实例，你可以使用 `#[allow(clippy::name_of_lint)]` 仅对该段代码选择退出 lint。

Rust 编译器还附带了一套以警告形式存在的 lint，不过这些通常更侧重于编写惯用代码而不是检查正确性。相反，编译器中的正确性 lint 只是被视为错误（请查看 `rustc -W help` 获取列表）。

> **注意：** 并非所有编译器警告默认都启用。默认禁用的警告通常仍在完善中，或更多关于风格而非内容。一个很好的例子是“惯用 Rust 2018 版” lint，你可以用 `#![warn(rust_2018_idioms)]` 启用它。启用此 lint 后，编译器会告诉你是否未能利用 Rust 2018 版带来的更改。你可能还想养成在开始新项目时启用 `missing_docs` 和 `missing_debug_implementations` 等 lint 的习惯，这些 lint 会在你忘记为 crate 中的任何公共项编写文档或为任何公共类型添加 `Debug` 实现时警告你。

### 测试生成

编写良好的测试套件需要大量工作。即使你做了这项工作，你编写的测试也只测试你在编写时考虑的那组特定行为。幸运的是，你可以利用多种测试生成技术来开发更好、更全面的测试。这些技术为你生成输入以检查应用程序的正确性。存在许多此类工具，各有其优缺点，因此这里我只介绍这些工具使用的主要策略：模糊测试和属性测试。

### 模糊测试

模糊测试已经写了整本书，但从高层次来看，想法很简单：向程序生成随机输入，看看它是否崩溃。如果程序崩溃，那就是 bug。例如，如果你正在编写 URL 解析库，你可以通过系统地生成随机字符串并将其抛给解析函数，直到它 panic 来模糊测试你的程序。完成。
