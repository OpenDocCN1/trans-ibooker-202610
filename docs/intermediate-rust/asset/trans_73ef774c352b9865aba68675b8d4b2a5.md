

## 最低依赖版本

当你首次添加依赖时，往往并不清楚应该为该依赖指定什么样的版本说明符。程序员通常会选择最新版本，或者仅仅选择当前的主版本号，但这两种选择很可能都是错误的。这里所说的“错误”，并不是指你的 crate 无法编译，而是指这种选择可能会在日后给你的 crate 用户带来麻烦。让我们来看看为什么这两种情况都有问题。

首先，假设你添加了一个对 `uuid = "1.7.3"`（最新发布版本）的依赖。现在设想某个开发者的项目依赖你的 crate，同时也依赖另一个 crate `foo`，而 `foo` 本身又依赖 uuid。再设想 `foo` 的作者对其 MSRV 策略非常谨慎，因此他们依赖 `uuid = "1, <1.6"`。这时你就会遇到麻烦。当 Cargo 看到 `uuid = "1.7.3"` 时，它只考虑大于等于 1.7 的版本。但随后它发现 foo 对 uuid 的依赖要求小于 1.6，于是它放弃并报告说，没有与所有要求兼容的 uuid 版本。

> *在实践中，crate 显式地不想要某个依赖项的较新版本，原因可能有很多。最常见的原因有：强制 MSRV、满足企业审计要求（较新版本会包含未经审计的代码），以及确保可重现构建（只使用明确列出的确切版本）。*

这很不幸，因为你的 crate 很可能完全可以与，比如说，`uuid 1.5.6` 一起编译。甚至可能任何 1.x 版本都能编译！但是，通过使用最新版本号，你在告诉 Cargo 只考虑该次版本号及以上的版本。那么，改用 `uuid = "1"` 是不是解决方案呢？不，这也不完全正确。你的代码可能确实依赖于只在 uuid 1.6 中添加的某些东西，所以虽然 1.6.2 可以，1.5.6 却不行。如果你只在最终会使用较新版本的环境中编译你的 crate，你不会注意到这一点；但如果依赖图中的某个 crate 指定了 `uuid = "1, <1.5"`，你的 crate 将无法编译！

正确的策略是列出包含你的 crate 所依赖的全部功能的最早版本，并确保即使你在 crate 中添加新代码，这一情况也仍然成立。但除了翻遍更新日志或反复试错之外，你如何确定这一点呢？最好的办法是使用 Cargo 的不稳定标志 `-Z minimal-versions`，它会让你的 crate 对所有依赖使用最低可接受版本，而不是最高版本。然后，将所有依赖仅设置为最新主版本号，尝试编译，并对任何无法编译的依赖添加次版本号。反复进行，直到一切都能正常编译，这时你就有了最低版本要求！

值得注意的是，与 MSRV 一样，最低版本检查也面临着生态系统采用的问题。你可能已经正确设置了所有版本说明符，但你依赖的项目未必如此。这使得 Cargo 的最低版本标志在实践中难以使用（这也是它仍然不稳定的原因）。如果你依赖 foo，而 foo 依赖 bar 时使用了说明符 `bar = "1"`，但实际上它需要 `bar = "1.4"`，那么无论你如何列出 foo，Cargo 都会报告无法编译 foo，因为 `-Z` 标志告诉它始终优先选择最低版本。你可以通过直接在你的依赖中列出 bar 并给出合适的版本要求来绕过这个问题，但这些变通方法的设置和维护可能很麻烦。你最终可能会列出大量实际上只是通过传递依赖引入的依赖项，而且随着时间推移，你还得让这份列表保持最新。

> **注意**
>
> 目前有一个提案，提出一种标志：这种标志倾向于为当前 crate 选择最低版本，而为依赖项选择最高版本。这看起来相当有前景。

## 更新日志

对于除最简单的 crate 之外的所有 crate，我都强烈建议保留更新日志。没有什么比看到某个依赖项进行了主版本升级，然后不得不翻遍 Git 日志来找出变更内容以及如何更新代码更令人沮丧的了。我建议你不要简单地把 Git 日志倾倒进一个名为 changelog 的文件，而是保留一份人工维护的更新日志。这样它更有可能真正有用。

一种简单而优秀的更新日志格式是 Keep a Changelog 格式，其文档位于 https://keepachangelog.com/。

## 未发布的版本

即使依赖项的来源是目录或 Git 仓库，Rust 也会考虑版本号。这意味着，即使你还没有向 crates.io 发布版本，语义化版本控制依然很重要；在两次发布之间，你的 Cargo.toml 中列出的版本也很关键。语义化版本控制标准并未规定如何处理这种情况，但我会提供一种既相当有效又不会太繁琐的工作流程。

发布一个版本后，立即将 Cargo.toml 中的版本号更新为下一个补丁版本，并加上像 `-alpha.1` 这样的后缀。如果你刚刚发布了 2.0.3，那么把新版本设为 2.0.4-alpha.1。如果你刚刚发布了 alpha 版本，则改为递增 alpha 编号。

在两次发布之间修改代码时，要留意新增功能变更或破坏性变更。如果发生了这类变更，且自上次发布以来对应版本号尚未更改，就递增它。例如，如果上次发布的版本是 2.0.3，当前版本是 2.0.4-alpha.2，然后你做了一处新增功能的变更，那么把这次变更后的版本设为 2.1.0-alpha.1。如果你做的是破坏性变更，则改为 3.0.0-alpha.1。如果相应的版本号递增已经完成，只需递增 alpha 编号。

当你发布时，去掉后缀（除非你想发布预发布版本），然后发布，再从头开始。

这个过程之所以有效，是因为它让两种常见的工作流程都运行得更好。首先，设想一个开发者依赖你的 crate 的主版本 2，但他们需要一个目前只在 Git 中可用的功能。这时你提交了一个破坏性变更。如果你不同时提升主版本号，他们的代码就会突然以意想不到的方式失败——要么无法编译，要么出现奇怪的运行时问题。如果你遵循这里给出的流程，Cargo 反而会通知他们发生了破坏性变更，他们就必须解决这一问题，或者固定一个特定的提交。

接下来，设想一个开发者需要某个他们刚刚为你的 crate 贡献的功能，但这个功能尚未包含在你 crate 的任何已发布版本中。他们通过 Git 依赖使用你的 crate 已经有一段时间了，所以他们项目中的其他开发者已经拥有你的 crate 仓库的旧检出。如果你不在 Git 中递增次版本号，这位开发者就无法传达他们的项目现在依赖于刚刚合并的功能。如果他们推送自己的更改，他们的同伴开发者会发现项目不再编译，因为 Cargo 会复用旧的检出。另一方面，如果该开发者能为 Git 依赖递增次版本号，Cargo 就会意识到旧检出已经过时。

这个工作流程绝非完美。它没有提供一种好的方式来传达两次发布之间的多个次版本或主版本变更，而且你仍然需要做一些工作来跟踪版本。然而，它的确解决了 Rust 开发者在处理 Git 依赖时最常遇到的两个问题；即使你在两次发布之间进行了多个这样的变更，这个工作流程也仍然能发现许多问题。

如果你不太在意发布中版本号偏小或是否连续，你可以通过总是递增版本号中的适当部分来改进这个建议的工作流程。不过要注意，取决于你进行此类变更的频率，这可能会使你的版本号变得非常大！
