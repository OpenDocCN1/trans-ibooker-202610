## DERIVE TRAIT

虽然 `#[derive(Trait)]` 非常方便，但在 trait 边界的上下文中，你应该意识到它实现方式上一个细微之处。许多 `#[derive(Trait)]` 展开会被解糖为 `impl Trait for Foo<T> where T: Trait`。这通常是你想要的，但并非总是如此。例如，考虑如果我们以这种方式为 `Foo<T>` 推导 `Clone` 会发生什么，而 `Foo` 包含一个 `Arc<T>`。`Arc` 无论 `T` 是否实现 `Clone` 都实现了 `Clone`，但由于推导出的边界，`Foo` 只有在 `T` 实现时才会实现 `Clone`！这通常不是太大的问题，但它确实添加了一个并不需要的边界。如果我们将类型重命名为 `Shared`，问题可能会变得更清晰一些。想象一下，一个拥有 `Shared<NotClone>` 的用户在编译器告诉他无法克隆它时会多么困惑！在撰写本文时，这就是标准库提供的 `#[derive(Clone)]` 的工作方式，尽管未来可能会改变。

有时，你希望对你泛型的类型的关联类型设置边界。作为一个例子，考虑迭代器方法 `flatten`，它接受一个产生项的迭代器，而这些项本身又实现了 `Iterator`，并产生这些内部迭代器的项的迭代器。它产生的类型 `Flatten` 是关于 `I` 的泛型，`I` 是外部迭代器的类型。`Flatten` 在 `I` 实现 `Iterator` 且 `I` 产生的项本身实现 `IntoIterator` 时实现 `Iterator`。为了让你能够写出这样的边界，Rust 允许你使用语法 `Type::AssocType` 来引用一个类型的关联类型。例如，我们可以使用 `I::Item` 来引用 `I` 的 `Item` 类型。如果一个类型有多个同名的关联类型，例如如果提供关联类型的 trait 本身是泛型的（因此存在多个实现），你可以使用语法 `<Type as Trait>::AssocType` 来消除歧义。使用这种方式，你不仅可以为外部迭代器类型写边界，还可以为该外部迭代器的项类型写边界。

在大量使用泛型的代码中，你可能会发现需要写一个关于类型引用 的边界。这通常没问题，因为你往往也会有一个泛型的生命周期参数，可以用作这些引用的生命周期。然而，在某些情况下，你希望边界表示“这个引用对任何生命周期都实现这个 trait”。这种情况极为罕见——在撰写本文时，标准库仅在三个地方使用了它——但确实会发生。这种类型的边界被称为高阶 trait 边界，它与 `Fn` trait 结合使用时特别有用。例如，想象你希望对一个接受 `T` 的引用并返回 `T` 内部引用的函数进行泛型化。如果你写 `F: Fn(&T) -> &U`，你需要为这些引用提供一个生命周期，但你真正想说的是“任何生命周期，只要输出与输入相同”。使用高阶生命周期，你可以写 `F: for<'a> Fn(&'a T) -> &'a U` 来表示对于任何生命周期 `'a`，边界必须成立。Rust 编译器足够智能，可以在你以这种方式写带引用的 `Fn` 边界时自动添加 `for`，这也是你很少需要显式形式的部分原因，但了解它是有价值的。

为了将所有这些内容整合起来，请考虑第 3-6 节中的代码，可用于为任何可迭代且其元素为 `Debug` 的类型实现 `Debug`。

```
impl Debug for AnyIterable
    where for<'a> &'a Self: IntoIterator,
        for<'a> <&'a Self as IntoIterator>::Item: Debug {
    fn fmt(&self, f: &mut Formatter) -> Result<(), Error> {
        f.debug_list().entries(self).finish()
    }
}
```

你几乎可以为任何集合类型复制粘贴此实现，它就会“正常工作”。当然，你可能想要一个更智能的 debug 实现，但这很好地说明了 trait 边界的强大功能。

## Marker Traits

通常，我们使用 trait 来表示多个类型可以支持的功能；一个 `Hash` 类型可以通过调用 `hash` 来哈希，一个 `Clone` 类型可以通过调用 `clone` 来克隆，一个 `Debug` 类型可以通过调用 `fmt` 来格式化用于调试。但并非所有 trait 都是以这种方式功能的。一些 trait，称为标记 trait，反而表示实现类型的属性。标记 trait 没有方法和关联类型，仅用于告诉你特定类型可以或不可以以某种方式使用。例如，如果一个类型实现了 `Send` 标记 trait，它是安全的跨线程边界发送。如果它没有实现此标记 trait，则不安全发送。与此行为没有关联的方法；它只是关于类型的事实。标准库在 `std::marker` 模块中有许多这些，包括 `Send`、`Sync`、`Copy`、`Sized` 和 `Unpin`。其中大多数（除了 `Copy`）也是自动 trait；编译器会自动为类型实现它们，除非该类型包含不实现标记 trait 的内容。

标记 trait 在 Rust 中发挥着重要作用：它们允许你编写捕获代码中未直接表达的语义要求的边界。要求类型为 `Send` 的代码中没有对 `send` 的调用。相反，代码假设给定类型在单独的线程中使用是安全的，而如果没有标记 trait，编译器将无法检查该假设。这将取决于程序员记住假设并非常仔细地阅读代码，而我们都知道这不是我们希望依赖的东西。那条道路布满了数据竞争、段错误和其他运行时问题。

与标记 trait 类似的是 *标记类型*。这些是单元类型（像 `struct MyMarker;`）不持有数据也没有方法。标记类型用于，嗯，标记一个类型处于特定状态。当你希望使用户无法误用 API 时，它们非常有用。例如，考虑一个像 `SshConnection` 这样的类型，它可能尚未经过身份验证。你可以向 `SshConnection` 添加一个泛型类型参数，然后创建两个标记类型：`Unauthenticated` 和 `Authenticated`。当用户首次连接时，他们会得到 `SshConnection<Unauthenticated>`。在其 `impl` 块中，你只提供一个方法：`connect`。`connect` 返回一个 `SshConnection<Authenticated>`，并且只有在该 `impl` 块中你才提供运行命令等剩余方法。我们将在第 4 章进一步研究这种模式。

## Existential Types

在 Rust 中，你很少需要在函数体中声明的变量的类型或你调用的方法的泛型参数的类型进行指定。这是因为 *类型推断*，编译器根据类型在代码中出现的上下文决定使用什么类型。编译器通常只为变量以及闭包的参数（和返回类型）推断类型；顶层定义如函数、类型、trait 和 trait 实现块都需要你显式命名所有类型。这有几个原因，但主要原因是当你至少有一些已知的起点时，类型推断会容易得多。然而，并非总是容易，甚至可能完全不可能完全命名一个类型！例如，如果你从函数返回一个闭包，或从 trait 方法返回一个 async 块，其类型没有一个你可以输入到代码中的名称。

为了处理这种情况，Rust 支持 *存在类型*。很可能，你已经见过存在类型在行动。所有标记为 `async fn` 或返回类型为 `impl Trait` 的函数都有一个存在返回类型：签名没有给出返回值的真实类型，只是提示函数返回 *某个* 实现调用者可以依赖的一组 trait 的类型。并且至关重要的是，调用者只能依赖返回类型实现这些 trait，而不能依赖其他任何东西。

> NOTE
> 技术上来说，并不严格正确地说调用者只依赖返回类型而没有其他依赖。编译器还会将 `Send` 和 `Sync` 等自动 trait 通过返回位置的 `impl Trait` 传播。我们将在下一章更详细地研究这个问题。

这种行为就是存在类型名称的由来：我们断言存在某个与签名匹配的具体类型，并将找到该类型的工作留给编译器。编译器通常会通过对函数体应用类型推断来弄清楚这一点。
