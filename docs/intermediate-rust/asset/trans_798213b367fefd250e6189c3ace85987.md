

首先编译器看到字段 `tiny`，其逻辑大小为 1 位（true 或 false）。但由于 CPU 和内存以字节为单位操作，`tiny` 在内存表示中被分配了 1 个字节。接下来，`normal` 是一个 4 字节类型，因此我们希望它 4 字节对齐。但即使 `Foo` 是对齐的，分配给 `tiny` 的 1 个字节也会使 `normal` 错过其对齐。为了纠正这一点，编译器在内存表示中在 `tiny` 和 `normal` 之间插入 3 个字节的 *填充*——填充字节的值是不确定的，在用户代码中会被忽略。填充中没有值，但它确实占用空间。

对于下一个字段 `small`，对齐很简单：它是一个 1 字节值，结构体中当前字节偏移量为 1 + 3 + 4 = 8。这已经是字节对齐的，因此 `small` 可以紧跟在 `normal` 之后。对于 `long` 我们又遇到问题了。我们现在已经在 `Foo` 中使用了 1 + 3 + 4 + 1 = 9 个字节。如果 `Foo` 是对齐的，那么 `long` 就不会像我们希望的那样 8 字节对齐，因此我们必须再插入 7 个字节的填充以使 `long` 再次对齐。这也恰好确保了最后一个字段 `short` 所需的 2 字节对齐，总计达到 26 字节。现在我们已经遍历了所有字段，还需要确定 `Foo` 本身的对齐方式。这里的规则是使用 `Foo` 的所有字段中最大的对齐方式，由于 `long` 的存在，这将是 8 字节。因此，为了确保 `Foo` 在放置在例如数组中时仍然对齐，编译器随后添加最后 6 个字节的填充，使 `Foo` 的大小为其对齐方式的倍数，达到 32 字节。

现在我们准备抛弃 C 的遗留问题，考虑如果我们在列表 3-1 中不使用 `repr(C)`，布局会发生什么。C 表示的主要限制之一是要求我们按原始结构体定义中出现的相同顺序放置所有字段。默认的 Rust 表示 `repr(Rust)` 去除了这一限制，同时去除了一些较小的限制，例如对于恰好具有相同字段的类型，字段顺序是确定的。也就是说，即使两个不同的类型共享完全相同的字段、类型相同、顺序相同，使用默认的 Rust 布局时也不能保证它们的布局相同！

由于我们现在可以重新排序字段，我们可以将它们按大小递减的顺序放置。这意味着我们不再需要在 `Foo` 的字段之间使用填充；字段本身用于实现必要的对齐！`Foo` 现在只是其字段的大小之和：只有 16 字节。这就是 Rust 默认情况下对类型在内存中的布局没有给出太多保证的原因之一：通过给编译器更大的重新排列的自由度，我们可以生成更高效的代码。

事实证明，还有第三种布局类型的方法，那就是告诉编译器我们不希望字段之间有任何填充。在这样做时，我们表示愿意承受使用未对齐访问带来的性能损失。这种行为最常见的用例是当每增加一个字节的内存影响都能感受到时，例如如果你有大量该类型的实例，如果内存非常有限，或者如果你将内存表示通过网络连接等低带宽介质发送。要选择此行为，你可以为类型添加注释 `#[repr(packed)]`。请记住，这可能导致代码运行速度大幅变慢，在极端情况下，如果你尝试执行 CPU 仅在对齐参数上支持的操作，这可能会导致程序崩溃。

有时，你希望给某个特定字段或类型提供比其技术上所需更大的对齐方式。你可以使用属性 `#[repr(align(n))]` 来做到这一点。这种行为的一个常见用例是确保在内存中连续存储的不同值（如数组中）最终位于 CPU 上的不同缓存行中。这样，你就可以避免 *伪共享*，伪共享可能导致并发程序中巨大的性能下降。伪共享发生在两个不同的 CPU 访问不同的值时，这些值恰好共享一个缓存行；虽然它们理论上可以并行操作，但它们最终都会争夺更新缓存中的同一个条目。我们将在第 11 章更详细地讨论并发。

## 复杂类型

你可能好奇编译器如何在内存中表示其他 Rust 类型。这里有一个快速参考：

- **元组** 表示为与元组值类型相同且顺序相同的字段的结构体。
- **数组** 表示为包含类型的连续序列，元素之间没有填充。
- **联合** 每个变体的布局独立选择。对齐是所有变体中的最大值。
- **枚举** 与联合相同，但带有一个额外的隐藏共享字段来存储枚举变体判别式。判别式是代码用来确定给定值持有哪个枚举变体的值。判别式字段的大小取决于变体的数量。

## 动态大小类型和胖指针

你可能在 Rust 文档的各种角落以及错误信息中遇到过标记 trait Sized。通常，它出现是因为编译器希望你提供一个 Sized 类型，但你（显然）没有提供。Rust 中大多数类型会自动实现 Sized——也就是说，它们在编译时大小已知——但有两个常见类型没有实现：trait 对象和切片。如果你有例如 `dyn Iterator` 或 `[u8]`，它们没有明确定义的大小。它们的大小取决于只有程序运行时才知道的信息，而不是编译时，这就是为什么它们被称为 *动态大小类型 (DSTs)*。没有人能提前知道你的函数收到的 `dyn Iterator` 是这个 200 字节的结构体还是那个 8 字节的结构体。这带来了一个问题：编译器经常必须知道某个事物的大小才能生成有效代码，例如为类型为 `(i32, dyn Iterator, [u8], i32)` 的元组分配多少空间，或如果你的代码尝试访问第四个字段时使用什么偏移量。但如果类型不是 Sized，则该信息不可用。

编译器几乎在所有地方都要求类型为 Sized。结构体字段、函数参数、返回值、变量类型和数组类型都必须为 Sized。这一限制如此常见，以至于你编写的每个类型边界都包含 T: Sized，除非你明确使用 T: ?Sized 退出（? 表示“可能不是”）。但如果你有一个 DST 并且想对它做一些事情，例如真的希望你的函数接受 trait 对象或切片作为参数，这就没什么帮助了。

解决办法是将其放在胖指针后面。胖指针就像普通指针一样，但它包含一个额外的字长字段，提供编译器生成处理该指针的合理代码所需的那部分关于该指针的额外信息。当你对 DST 取引用时，编译器会自动为你构造一个胖指针。对于切片，额外信息只是切片的长度。对于 trait 对象——嗯，我们稍后再说。并且至关重要的是，该胖指针是 Sized。具体来说，它是 usize 两倍大小（目标平台上字长）：一个 usize 用于保存指针，一个 usize 用于保存“完成”该类型所需的信息。

> NOTE Box 和 Arc 也支持存储胖指针，这就是为什么它们都支持 T: ?Sized。

## Traits 和 Trait Bounds

Traits 是 Rust 类型系统的关键部分——它们是使类型能够相互协作的胶水，即使它们在定义时彼此不知道。Rust 编程语言很好地介绍了如何定义和使用 traits，所以我在这里不会重复。相反，我们将看看 traits 的一些更技术性的方面：它们是如何实现的，你必须遵守的限制，以及 traits 的一些更晦涩的使用。

## 编译和分发

到现在为止，你可能已经在 Rust 中编写了相当多的通用代码。你在类型和方法上使用了泛型类型参数，也许还使用了几个 trait bounds。但你有没有想过当你编译泛型代码时会发生什么，或者当你在 dyn Trait 上调用 trait 方法时会发生什么？

当你编写一个关于 T 的泛型类型或函数时，你实际上是在告诉编译器为你提供的每种类型 T 制作该类型或函数的副本。当你构造一个 Vec<i32> 或一个 HashMap<String, bool> 时，编译器本质上会复制粘贴泛型类型及其所有实现块，并用你提供的具体类型替换每个泛型参数的每个实例。它会制作一个完整的 Vec 类型副本，其中所有 T 都被替换为 i32，并制作一个完整的 HashMap 类型副本，其中所有 K 都被替换为 String，所有 V 都被替换为 bool。

> NOTE 实际上，编译器并没有真正进行完整的复制粘贴。它只复制你使用的代码部分，因此如果你从未在 Vec<i32> 上调用 find，则 find 的代码不会被复制和编译。
