请记住，对象安全是你的公共接口的一部分！如果你以向后兼容的方式修改 trait，例如添加一个具有默认实现的方法，但这使得 trait 不再对象安全，你需要提升你的主版本号。

## 借用 vs. 所有权

对于你在 Rust 中定义的几乎每个函数、trait 和类型，你都必须决定它是否应该拥有其数据，或仅持有对数据的引用。你所做的决定将对接口的易用性和性能产生深远的影响。幸运的是，这些决定通常会自行做出。

如果你的代码需要数据的所有权，例如调用接收 self 的方法或将数据移动到另一个线程，它必须存储所有权数据。当你的代码必须拥有数据时，它通常也应让调用者提供所有权数据，而不是通过引用接收值然后克隆它们。这让调用者控制分配，并且它明确说明了使用该接口的成本。

另一方面，如果你的代码不需要拥有数据，它应改为操作引用。其中一个常见的例外是像 i32、bool 或 f64 这样的小类型，它们直接存储和复制的成本与通过引用存储一样低廉。不过要小心不要假设这对所有 Copy 类型都成立；[u8; 8192] 是 Copy，但到处存储和复制它会很昂贵。

当然，在现实世界中，事情往往没有那么清晰。有时，你事先并不知道你的代码是否需要拥有数据。例如，String::from_utf8_lossy 只有在传入的字节序列包含无效的 UTF-8 序列时才需要接管所有权。在这种情况下，Cow 类型就是你的朋友：它允许你在数据允许时操作引用，并在必要时生成一个拥有值。

其他时候，引用生命周期使接口变得如此复杂以至于使用起来很痛苦。如果你的用户在你的接口之上编写代码时难以让代码编译通过，这就是一个信号，表明你可能想要（即使是不必要地）接管某些数据的所有权。如果你这样做，先从那些便宜克隆或不属于性能敏感部分的数据开始，然后再决定是否要堆分配可能是一个巨大的字节块。

## 可能失败且阻塞的析构函数

以 I/O 为中心的类型的析构时通常需要执行清理工作。这可能包括将写入刷新到磁盘、关闭文件，或优雅地终止与远程主机的连接。执行此清理的自然位置是在类型的 Drop 实现中。不幸的是，一旦值被丢弃，我们除了 panic 之外就再也没有办法向用户传达错误。类似的问题出现在异步代码中，在那里我们希望在有待处理工作时完成收尾。drop 被调用时，executor 可能正在关闭，我们没有办法做更多工作。我们可以尝试启动另一个 executor，但这会带来自己的问题，例如在异步代码中阻塞，正如我们在第 9 章中将看到的那样。

这些问题没有完美的解决方案，无论我们做什么，一些应用程序不可避免地会回退到我们的 Drop 实现。因此，我们需要通过 Drop 提供尽力而为的清理。如果清理出错，至少我们尝试过了——我们吞掉错误并继续。如果 executor 仍然可用，我们可能会 spawn 一个 future 来执行清理，但如果它永远无法运行，我们也尽力了。

然而，我们应该为希望不留下任何松散线程的用户提供更好的替代方案。我们可以通过提供显式的析构函数来做到这一点。这通常采用接收 self 所有权并暴露固有错误（使用 -> Result<_, _>）或异步性（使用 async fn）的形式。谨慎的用户随后可以使用该方法优雅地拆除任何相关资源。

> NOTE 确保你在文档中突出显示显式的析构函数！

一如既往，存在权衡。一旦你添加了显式的析构函数，你会遇到两个问题。首先，由于你的类型实现了 Drop，你就不能在析构函数中从该类型的任何字段中移出。这是因为 Drop::drop 在你的显式析构函数运行后仍会被调用，而它接收 &mut self，这要求 self 的任何部分都未被移动。其次，drop 接收 &mut self，而不是 self，所以你的 Drop 实现不能简单地调用你的显式析构函数并忽略其结果（因为它不拥有 self）。解决这些问题的办法有几种，没有一种是完美的。

第一种方法是让你的顶层类型成为一个 newtype 包装器，包装一个 Option，而 Option 又持有某个内部类型，该内部类型持有类型的所有字段。你可以在两个析构函数中都使用 Option::take，并在内部类型尚未被取出时调用内部类型的显式析构函数。由于内部类型未实现 Drop，你可以在那里接管所有字段的所有权。这种方法的缺点是，你希望在顶层类型上提供的所有方法现在都必须包含代码来穿过 Option（你知道它在 drop 尚未被调用时始终是 Some）以访问内部类型的字段。

第二个变通方法是让你的每个字段都 *可取出*。你可以通过将其替换为 None 来“取出”一个 Option（这就是 Option::take 所做的），但你也可以对许多其他类型这样做。例如，你可以通过简单地将它们替换为其廉价构造的默认值来取出 Vec 或 HashMap——std::mem::take 就是你的朋友。这里的方法在你的类型具有合理的“空”值时效果很好，但在你必须将几乎每个字段都包装在 Option 中，然后用匹配的 unwrap 修改这些字段的每个访问时就会变得繁琐。

第三个选项是将数据放在 ManuallyDrop 类型内部，该类型解引用为内部类型，因此无需 unwrap。你也可以在 drop 中使用 ManuallyDrop::take 在销毁时接管所有权。这种方法的主要缺点是 ManuallyDrop::take 是不安全的。没有任何安全机制来确保你不会在调用 take 之后尝试使用 ManuallyDrop 内部的值，或多次调用 take。如果你这样做，你的程序将静默地表现出未定义行为，坏事就会发生。

最终，你应该选择最适合你的应用程序的方法。我会倾向于采用第二个选项，只有当你发现自己陷入 Option 的海洋时才切换到其他方法。ManuallyDrop 解决方案在代码足够简单以便你能轻松检查代码的安全性，并且你对自己的能力有信心时是优秀的。

## 显而易见

虽然一些用户可能熟悉支撑你的接口的实现方面的内容，但他们不太可能理解其所有规则和限制。他们不会知道在调用 bar 之后调用 foo 永远是不允许的，或只有在月亮处于 47 度角且过去 18 秒内没有人打喷嚏时调用 unsafe 方法 baz 才是安全的。只有当接口明确表明有些奇怪的事情正在发生时，他们才会去查阅文档或仔细阅读类型签名。因此，对你来说，让用户尽可能容易理解你的接口并尽可能难以错误使用它至关重要。你为此拥有的两个主要技术是你的文档和类型系统，让我们依次来看一下。

> NOTE 你也可以利用命名来提示用户接口中还有超出表面之外的东西。如果用户看到一个名为 dangerous 的方法，他们很可能会阅读其文档。

## 文档

使你的接口透明的第一步是编写良好的文档。我可以写一整本书专门讲如何写文档，但让我们在这里专注于 Rust 特定的建议。

首先，清楚地记录任何你的代码可能做一些意外的操作的情况，或依赖用户做超出类型签名所规定的事情。panic 就是两者兼有的一个好例子。
