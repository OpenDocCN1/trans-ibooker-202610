
需求是对代码使用方式的限制，而承诺则是关于代码使用方式的保证。在设计新接口时，你需要仔细思考这份契约。一个好的经验法则是：避免施加不必要的限制，并且只做出你能够兑现的承诺。增加限制或移除承诺通常需要一次主版本号的语义化版本变更，并且很可能会破坏其他地方的代码。反之，放宽限制或增加新的承诺通常可以向后兼容。

在 Rust 中，限制通常以 trait 约束和参数类型的形式出现，承诺则以 trait 实现和返回类型的形式出现。例如，比较清单 4-1 中的三个函数签名。

```
fn frobnicate1(s: String) -> String
fn frobnicate2(s: &str) -> Cow<'_, str>
fn frobnicate3(s: impl AsRef<str>) -> impl AsRef<str>
```

清单 4-1：契约不同的相似函数签名

这三个函数签名都接收一个字符串并返回一个字符串，但它们是在截然不同的契约下完成这一点的。

第一个函数要求调用者以 `String` 类型的形式拥有该字符串，并承诺返回一个拥有的 `String`。由于该契约要求调用者进行分配，并要求我们返回一个拥有的 `String`，我们日后无法以向后兼容的方式让这个函数变成零分配。

第二个函数放宽了契约：调用者可以提供任何字符串引用，因此用户不再需要分配内存或放弃对 `String` 的所有权。它还承诺返回一个 `std::borrow::Cow`，这意味着它既可以返回字符串引用，也可以返回拥有的 `String`，具体取决于它是否需要拥有该字符串。这里的承诺是函数将始终返回一个 `Cow`，这意味着我们日后不能将其改为使用其他优化的字符串表示形式。调用者还必须专门提供一个 `&str`，因此如果他们拥有一个预先存在的 `String`，就必须先将其解引用为 `&str` 才能调用我们的函数。

第三个函数解除了这些限制。它只要求用户传入一个能产生字符串引用的类型，并且只承诺返回值能产生字符串引用。

这些函数签名中没有哪一个比其他的更好。如果你在函数中需要拥有一个字符串，可以使用第一种参数类型来避免额外的字符串拷贝。如果你希望允许调用者利用已分配并返回拥有字符串的情况，那么第二个返回类型为 `Cow` 的函数可能是一个不错的选择。不过，我希望你从中明白的是：你应该仔细思考你的接口会把你绑定到怎样的契约上，因为事后更改它可能会造成破坏。

在本节的剩余部分，我会给出一些经常出现的接口设计决策示例，以及它们对你的接口契约的影响。

## 泛型参数

你的接口必须对用户施加的一个明显需求是：他们必须为你的代码提供哪些类型。如果你的函数明确接受一个 `Foo`，用户就必须拥有并交给你一个 `Foo`。这没有其他办法。在大多数情况下，使用泛型而不是具体类型是值得的，这样可以允许调用者传入任何符合函数实际需求的类型，而不仅仅是某个特定类型。将清单 4-1 中的 `&str` 改为 `impl AsRef<str>` 就是这类放宽操作的一个例子。以这种方式放宽需求的一种做法是：先让参数完全不带约束地使用泛型，然后跟随编译器的错误提示，找出需要添加的约束。

然而，如果走到极端，这种方法会让每个函数的每个参数都变成各自的泛型类型，这既难以阅读又难以理解。对于究竟何时应该或不应该将某个参数设为泛型，并没有硬性规定，所以请运用你的最佳判断。一个好的经验法则是：如果你能想到用户可能合理地、频繁地想要使用其他类型来代替你最初使用的具体类型，那就将该参数设为泛型。

你可能还记得第 3 章中提到的：泛型代码会通过单态化，为每一种使用过的类型组合进行复制。想到这一点，让大量参数变成泛型的想法可能会让你担心二进制文件过大。在第 3 章中我们还讨论了如何通过动态分发来缓解这一问题，而代价（通常是可忽略不计的）是性能损失，这一点在这里同样适用。

对于你本来就通过引用接收的参数（回想一下，`dyn Trait` 不是 `Sized`，你需要一个胖指针才能使用它们），你可以轻松地把泛型参数替换为使用动态分发的参数。例如，你可以使用 `&dyn AsRef<str>` 而不是 `impl AsRef<str>`。

不过，在你急着这么做之前，有几点需要考虑。首先，你是在代表你的用户做这个选择，他们无法选择不使用动态分发。如果你知道你应用动态分发的代码永远不会对性能敏感，那也许没问题。但如果某个用户想在高性能应用中使用你的库，那么在一个热循环中调用的函数里使用动态分发可能会成为交易破坏者。其次，在撰写本文时，只有当你有一个像 `T: AsRef<str>` 或 `impl AsRef<str>` 这样的简单 trait 约束时，动态分发才有效。对于更复杂的约束，Rust 不知道如何构造动态分发的 vtable，因此你不能使用例如 `&dyn Hash + Eq`。最后，请记住，使用泛型时，调用者总是可以通过传入一个 trait 对象来自己选择动态分发。反过来则不成立：如果你接收一个 trait 对象，调用者就必须提供 trait 对象。

你可能会想先用具体类型来设计接口，然后再逐步泛型化。这可以行得通，但请记住，这类更改不一定向后兼容。为了理解原因，想象一下你把一个函数从 `fn foo(v: &Vec<usize>)` 改为 `fn foo(v: impl AsRef<[usize]>)`。虽然每个 `&Vec<usize>` 都实现了 `AsRef<[usize]>`，但类型推断仍然可能给用户带来问题。考虑一下如果调用者调用 `foo(&iter.collect())` 会发生什么。在原始版本中，编译器可以确定应该收集到一个 `Vec` 中，而现在它只知道需要收集到某个实现了 `AsRef<[usize]>` 的类型中。而这样的类型可能不止一种，因此经过这一更改，调用者的代码将无法再编译！

## 对象安全

当你定义一个 trait 时，该 trait 是否对象安全（参见第 3 章“编译与分发”一节的末尾，第 XX 页）是该 trait 契约中一个不成文的部分。如果 trait 是对象安全的，用户就可以使用 `dyn Trait` 将实现了该 trait 的不同类型当作一个共同的类型来处理。如果不是，编译器将不允许为该 trait 使用 `dyn Trait`。你应该更倾向于让你的 trait 保持对象安全，即使这会稍微牺牲一些使用上的便利性（例如用 `impl AsRef<str>` 而不是 `&str`），因为对象安全可以为使用你的 trait 开辟新的方式。如果你的 trait 必须有一个泛型方法，请考虑它的泛型参数是否可以放在 trait 本身上，或者它的泛型参数是否也可以使用动态分发来保持 trait 的对象安全性。另外，你还可以在该方法上添加 `where Self: Sized` 的 trait 约束，这样该方法就只能通过 trait 的具体实例（而不能通过 `dyn Trait`）来调用。你可以在 `Iterator` 和 `Read` trait 中看到这种模式的例子，它们都是对象安全的，但在具体实例上提供了一些额外的便捷方法。

对于为了保护对象安全你愿意做出多少牺牲，并没有一个统一的答案。我的建议是：考虑你的 trait 将如何被使用，以及用户想要将其作为 trait 对象来使用是否有意义。如果你认为用户很可能想要将你的 trait 的许多不同实例放在一起使用，那么你就应该比在认为这种用例不太合理的情况下更加努力地提供对象安全。例如，动态分发对 `FromIterator` trait 没什么用，因为它的唯一方法不接收 `self`，所以你一开始就无法构造一个 trait 对象。同样地，`std::io::Seek` 单独作为 trait 对象也没什么用处，因为你用这种 trait 对象唯一能做的就是 seek，而无法读或写。
