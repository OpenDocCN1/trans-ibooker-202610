
栈上用于存放一个大小为 `usize` 的值的内存区域的名称，尽管它并没有一个定义明确的值（它的槽位是空的）。如果你为该变量赋值，例如使用 `x = 6`，那么这块内存区域随后就会存储表示值 6 的位。为 `x` 赋值时，`&x` 不会发生变化。如果你声明多个同名变量，它们最终仍会由不同的内存作为后备存储。这一模型与 C、C++ 以及许多其他底层语言所使用的内存模型相匹配，对于需要明确推理内存的场景很有用。

> 在本例中，我们忽略 CPU 寄存器，并将其视为一种优化。实际上，如果某个变量不需要内存地址，编译器可能会使用寄存器为其提供存储，而不是使用一块内存区域。

你可能会发现，其中一种模型与你之前的模型更加吻合，但我强烈建议你尝试理解这两种模型。它们都同样有效，而且都是简化模型——任何有用的心智模型都必须如此。如果你能够从这两种视角来审视一段代码，就会发现分析复杂的代码片段、理解它们为何能够或不能编译，以及为何运行结果符合或不符合预期，会容易得多。

## 内存区域

现在你已经掌握了我们如何引用内存，接下来需要讨论内存实际上是什么。内存有许多不同的区域，或许令人意外的是，并非所有区域都存储在计算机的 DRAM 中。你使用哪一部分内存，会对代码的编写方式产生重要影响。对于编写 Rust 代码而言，最重要的三个内存区域是栈、堆和静态内存。

### 栈

栈是程序用于函数调用临时存储空间的一段内存。每次调用函数时，栈顶都会分配一块称为栈帧的连续内存。栈的底部附近是主函数的栈帧；当函数调用其他函数时，更多栈帧会被压入栈中。函数的栈帧包含该函数中的所有变量，以及函数接收的所有参数。当函数返回时，它的栈帧会被回收。

组成函数局部变量值的字节不会立即被清除，但访问它们并不安全，因为后续函数调用的栈帧可能与已回收的栈帧重叠，从而覆盖这些字节。即使它们尚未被覆盖，也可能包含不允许使用的值，例如函数返回时已经被移动的值。

栈帧，以及它们最终会消失这一关键事实，与 Rust 中的生命周期概念密切相关。存储在栈帧中的任何变量，在该栈帧消失后都无法访问，因此对它的任何引用，其生命周期最多只能与该栈帧的生命周期一样长。

### 堆

*堆*是一块与程序当前调用栈无关的内存池。堆内存中的值会一直存在，直到被显式释放。当你希望某个值的存活时间超过当前函数栈帧的生命周期时，这一点非常有用。如果该值是函数的返回值，调用函数可以在自己的栈上留出一块空间，让被调用函数在返回前将该值写入其中。但如果你希望将该值发送给另一个线程，而当前线程与该线程可能完全没有共享的栈帧，就可以将它存储在堆上。

堆允许你显式分配连续的内存区域。这样做时，你会获得一个指向该内存区域起始位置的指针。在之后将其释放之前，这段内存都会为你保留；这个过程通常称为 *freeing*，名称源自 C 标准库中对应的函数。由于从堆中分配的内存在函数返回时不会消失，因此你可以在一个位置为某个值分配内存，将指向它的指针传递给另一个线程，然后让该线程安全地继续操作这个值。换句话说，当你在堆上分配内存时，所得指针的生命周期不受限制——它的生命周期有多长，取决于你的程序让它保持存活多久。

在 Rust 中，与堆交互的主要机制是 Box 类型。当你编写 `Box::new(value)` 时，`value` 会被放置在堆上，而你获得的返回值（`Box<T>`）是一个指向堆上该值的指针。当 Box 最终被丢弃时，这块内存就会被释放。

如果你忘记释放堆内存，它就会永远存在，最终你的应用程序会耗尽计算机上的所有内存。这称为 *内存泄漏*，通常是你希望避免的情况。不过，有些情况下你确实希望显式泄漏内存。例如，假设你有一份整个程序都应能够访问的只读配置。你可以将它分配到堆上，并使用 `Box::leak` 显式泄漏它，从而获得指向它的 `'static` 引用。

### 静态内存

*静态内存*实际上是一个统称，指代程序编译到的文件中几个密切相关的区域。程序执行时，这些区域会自动加载到程序的内存中。静态内存中的值会在程序的整个执行期间存活。程序的静态内存包含程序的二进制代码，这些代码通常会被映射为只读。程序执行时，会在文本段中逐条执行二进制代码中的指令，并在调用函数时跳转到相应位置。静态内存还存储使用 `static` 关键字声明的变量所占用的内存，以及代码中的某些常量值，例如字符串。

## 丢弃顺序

当值离开作用域时，Rust 会自动丢弃这些值，例如清单 2-3 中内层作用域里的 `x1` 和 `x2`。丢弃顺序的规则相当简单：变量（包括函数参数）按逆序丢弃，而嵌套值则按源代码中的顺序丢弃。

这乍听起来可能有些奇怪——为什么会存在这种差异？不过，仔细观察后就会发现，这非常合理。假设你编写了一个函数，先声明一个字符串，然后将对该字符串的引用插入一个新的哈希表中。当函数返回时，必须先丢弃哈希表；如果先丢弃字符串，哈希表就会持有一个无效引用！一般来说，后声明的变量可能包含对先前值的引用，而由于 Rust 的生命周期规则，反过来的情况不可能发生。因此，Rust 按逆序丢弃变量。

对于嵌套值，例如元组、数组或结构体中的值，我们本来也可以采用相同的行为，但这很可能会让用户感到意外。如果你构造了一个包含两个值的数组，那么最后一个元素先被丢弃似乎很奇怪。元组和结构体也是如此，最直观的行为是先丢弃元组的第一个元素或结构体的第一个字段，然后是第二个，依此类推。与变量不同，在这种情况下没有必要反转丢弃顺序，因为 Rust 目前不允许单个值中存在自引用。因此，Rust 选择了更符合直觉的方案。

## 借用与生命周期

Rust 允许值的所有者通过引用将该值借给其他人，而不放弃所有权。引用是指针，同时附带了关于其使用方式的额外契约，例如该引用是否对被引用的值提供独占访问，或者被引用的值是否还可以被其他引用指向。

### 共享引用

共享引用 `&T` 顾名思义，是一种可以被共享的指针。同一个值可以存在任意数量的其他引用，并且每个共享引用都实现了 `Copy`，因此你可以轻松地创建更多共享引用。共享引用背后的值不可变；你不能修改或重新赋值共享引用所指向的值，也不能将共享引用转换为可变引用。

Rust 编译器可以假设，共享引用所指向的值在该引用存活期间不会发生变化。例如，如果 Rust 编译器发现某个函数多次读取共享引用背后的值，那么它完全可以只读取一次，然后重复使用该值。更具体地说，清单 2-4 中的断言不应该失败。
