```rust
fn cache(input: &i32, sum: &mut i32) {
    *sum = *input + *input;
    assert_eq!(*sum, 2 * *input);
}
```

*清单 2-4：Rust 假定共享引用是不可变的。*

编译器是否选择应用某个优化或多或少并不重要。编译器的启发式规则会随时间变化，因此你通常应该针对编译器被允许做什么来编写代码，而不是针对它在特定时刻的特定情况下实际做什么。

## 可变引用

共享引用的替代方案是可变引用：`&mut T`。对于可变引用，Rust 编译器同样可以充分利用引用自带的约定：编译器假定没有任何其他线程访问目标值，无论是通过共享引用还是可变引用。换句话说，它假定可变引用是*独占的*。这带来了一些在其他语言中不易实现的巧妙优化。例如，以清单 2-5 中的代码为例。

```rust
fn noalias(input: &i32, output: &mut i32) {
    if *input == 1 {
❶       *output = 2;
    }
❷   if *input != 1 {
        *output = 3;
    }
}
```

*清单 2-5：Rust 假定可变引用是独占的。*

在 Rust 中，编译器可以假定 `input` 和 `output` 不指向同一块内存。因此，在❶处对 `output` 的重新赋值不会影响❷处的检查，整个函数可以编译成一个单一的 `if-else` 块。如果编译器不能依赖独占可变性的约定，这种优化就是无效的，因为在类似 `noalias(&x, &mut x)` 的情况下，输入为 1 时可能会产生输出为 3 的结果。

可变引用只允许你修改引用所指向的内存位置。你能否修改超出直接引用范围的值，取决于位于中间的类型所提供的方法。通过一个例子可能更容易理解，请看清单 2-6。

```rust
let x = 42;
let mut y = &x; // y is of type &i32
let z = &mut y; // z is of type &mut &i32
```

*清单 2-6：可变性仅适用于直接引用的内存。*

在这个示例中，你可以通过让指针引用不同的变量，将指针的值改为另一个值（也就是另一个指针），但你不能改变被指向的值（也就是 x 的值）。类似地，你可以通过 z 改变 y 的指针值，但你不能改变 z 本身来持有另一个不同的引用。

拥有一个值和拥有对它的可变引用之间的主要区别在于，所有者负责在值不再需要时将其丢弃。除此之外，你可以通过可变引用做任何你拥有该值时可以做的事情，但有一个警告：如果你移动了可变引用后面的值，那么你必须留下另一个值来代替它。如果你不这么做，所有者仍然会认为它需要丢弃这个值，但那时已经没有值可供丢弃了！

清单 2-7 给出了你可以移动可变引用后面的值的几种方式的示例。

```rust
fn replace_with_84(s: &mut Box<i32>) {
    // this is not okay, as *s would be empty:
❶   // let was = *s;
    // but this is:
❷   let was = std::mem::take(s);
    // so is this:
❸   *s = was;
    // we can exchange values behind &mut:
    let mut r = Box::new(84);
❹   std::mem::swap(s, &mut r);
    assert_ne!(*r, 84);
❺ }
let mut s = Box::new(42);
replace_with_84(&mut s);
```

*清单 2-7：通过可变引用访问后必须留下一个值。*

我加入了一些注释行，它们表示非法操作。你不能直接移动出值❶，因为调用者仍然认为自己拥有该值，并会在❺处再次释放它，从而导致双重释放。如果你只是想在后面留下一个有效的值，`std::mem::take` ❷ 是一个不错的选择。它等价于 `std::mem::replace(&mut value, Default::default())`；它把 `value` 从可变引用后面移出，但会在原位置留下一个新的、该类型的默认值。这个默认值是一个独立的、被拥有的值，因此调用者在❺处作用域结束时丢弃它是安全的。

或者，如果你不需要引用后面的旧值，你可以用一个你已经拥有的值❸覆盖它，留给调用者稍后丢弃该值。当你这样做时，原本位于可变引用后面的值会立即被丢弃。

最后，如果你有两个可变引用，你可以在不拥有其中任何一个的情况下交换它们的值❹，因为两个引用最终都会得到一个合法的被拥有的值，供其所有者最终释放。

## 内部可变性

有些类型提供*内部可变性*，这意味着它们允许你通过共享引用修改一个值。这些类型通常依赖额外的机制（如原子 CPU 指令）或不变量来提供安全可变性，而不依赖独占引用的语义。它们通常分为两类：一类允许你通过共享引用获得可变引用，另一类只允许你通过共享引用直接修改值。

第一类包括 `Mutex` 和 `RefCell` 等类型，它们包含安全机制，确保对于它们给出可变引用的任何值，同一时间只能存在一个可变引用（且不能存在共享引用）。在底层，这些类型（以及类似类型）都依赖于一个叫做 `UnsafeCell` 的类型，这个名字应该立刻让你对使用它产生犹豫。我们将在第 10 章更详细地介绍 `UnsafeCell`，但现在你应该知道，它是通过共享引用进行修改的*唯一*正确方式。

提供内部可变性的其他类型类别是那些不给出内部值的可变引用，而只是提供给你就地操作该值的方法的类型。`std::sync::atomic` 中的原子整数类型和 `std::cell::Cell` 类型属于这一类。你无法直接获得这类类型背后的 `usize` 或 `i32` 的引用，但你可以在给定时间点读取和替换它的值。

> **注意**
> 标准库中的 `Cell` 类型是通过不变量实现安全内部可变性的一个有趣例子。它不能跨线程共享，也从不给出对 `Cell` 中所包含值的引用。相反，所有方法要么完全替换该值，要么返回所包含值的副本。由于对内部值不存在任何引用，因此移动它总是可以的。而且由于 `Cell` 不能跨线程共享，即使修改是通过共享引用进行的，内部值也永远不会被并发修改。

## 生命周期

如果你正在读这本书，你可能已经对生命周期的概念有所熟悉，很可能是通过编译器反复提示的违反生命周期规则的警告。这种程度的理解对于你将编写的大部分 Rust 代码来说已经够用，但随着我们深入 Rust 更复杂的部分，你需要一个更严谨的心智模型来工作。

较新的 Rust 开发者常常被教导将生命周期视为与作用域相对应：生命周期在你取得对某个变量的引用时开始，在该变量被移动或超出作用域时结束。这通常是正确的，也通常很有用，但实际情况要稍微复杂一些。*生命周期*实际上是某个引用必须在其中有效的代码区域的一个名称。虽然生命周期经常与作用域重合，但并非必须如此，我们将在本节后面看到这一点。

## 生命周期与借用检查器

Rust 生命周期的核心是借用检查器。每当使用一个带有某个生命周期 `'a` 的引用时，借用检查器都会检查 `'a` 是否仍然存活。它通过从使用点回溯到 `'a` 开始的地方（即引用被取得的地方）来做到这一点，并检查该路径上是否存在冲突的使用。这确保了引用仍然指向一个可以安全访问的值。这类似于我们本章前面讨论的高层“数据流”心智模型；编译器会检查我们正在访问的引用的流是否与任何其他并行流冲突。

清单 2-8 展示了一个简单的代码示例，其中包含对 `x` 引用的生命周期标注。

```rust
let mut x = Box::new(42);
① let r = &x;          // 'a
if rand() > 0.5 {
②   *x = 84;
} else {
③   println!("{}", r);  // 'a
④ }
```

*清单 2-8：生命周期不需要是连续的。*

生命周期在①处我们取得对 `x` 的引用时开始。在第一个分支②中，我们立即尝试通过将其值改为 84 来修改 `x`，这需要一个 `&mut x`。借用检查器取得对 `x` 的可变引用，并立即检查其使用情况。它在引用取得和使用之间没有发现冲突的使用，因此接受这段代码。如果你习惯于将生命周期视为作用域，这可能会让你感到惊讶，因为 `r` 在②处仍然在作用域内（它在③处才超出作用域）。但借用检查器足够聪明，能够意识到如果走这个分支，`r` 之后永远不会被使用，因此在这里对 `x` 进行可变访问是没问题的。或者换个说法，①处创建的生命周期并没有延伸到这个分支中：从 `r` 出发的流没有超过②，因此不存在冲突的流。借用检查器随后在③处的打印语句中发现了 `r` 的使用。它回溯到①，发现没有冲突的使用（②不在这条路径上），因此它也接受这次使用。

如果我们再在清单 2-8 的④处添加一次对 `r` 的使用，代码将无法编译。生命周期 `'a` 将会从①一直持续到④（`r` 的最后一次使用），当借用检查器检查我们对 `r` 的新使用时，它会在②处发现冲突的使用。

```rust
let mut x = Box::new(42);
① let mut z = &x;      // 'a
for i in 0..100 {
```
