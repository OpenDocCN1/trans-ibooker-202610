

*coherence* 属性：对于任何给定的类型和方法，只能有一种正确的选择来决定为该类型使用该方法的哪个实现。要了解其重要性，请考虑如果我可以为标准库中的 `bool` 类型编写自己的 `Display` trait 实现会发生什么。现在，对于任何尝试打印 bool 值并包含我的 crate 的代码，编译器都不会知道是选择我编写的实现还是标准库中的实现。两种选择都不是正确或更好，编译器显然不能随机选择。如果标准库根本不涉及，情况也一样，但我们有两个相互依赖的 crate，它们都为某个共享类型实现了 trait。coherence 属性确保编译器永远不会陷入这些情况，也永远不需要做出这些选择：总会有一个显而易见的选择。

一种简单的方式来维护 coherence 就是确保只有定义 trait 的 crate 才能为该 trait 编写实现；如果没有人可以实现该 trait，那么在其他地方就不会有冲突的实现。然而，这在实践中过于严格，本质上会使 trait 变得无用，因为除非你将自己的类型纳入定义 crate，否则就无法为自己的类型实现诸如 `std::fmt::Debug` 和 `serde::Serialize` 之类的 trait。相反的极端情况，即说你只能为自己的类型实现 trait，解决了这个问题但引入了另一个问题：定义 trait 的 crate 现在无法为标准库或其它流行 crate 中的类型提供该 trait 的实现！理想情况下，我们希望找到一套规则，在下游 crate 为其自己的类型实现上游 trait 的需求与上游 crate 能够在不破坏下游代码的情况下添加其自身 trait 的实现的需求之间取得平衡。

> **NOTE**
> 
> *Upstream 指的是你的代码所依赖的东西，而 downstream 指的是依赖你代码的东西。这些术语通常以 crate 依赖关系的直接意义使用，但也可以用来指代码库的权威分支——如果你对 Rust 编译器进行分支，那么官方 Rust 编译器就是你的“上游”。*

在 Rust 中，建立这种平衡的规则是 *orphan rule* 孤儿规则。简单来说，孤儿规则规定，你只能在 trait *或* 类型是本地于你的 crate 时为类型实现 trait。因此，你可以为自己的类型实现 `Debug`，也可以为 `bool` 实现 `MyNeatTrait`，但你不能为 `bool` 实现 `Debug`。如果你尝试这样做，你的代码将无法编译，编译器会告诉你存在冲突的实现。

这已经让你走得很远；它允许你为第三方类型实现自己的 trait，并为自己的类型实现第三方的 trait。然而，孤儿规则并不是故事的全部。还有许多额外的含义、注意事项和例外情况，你应该了解。

## Blanket Implementations  blanket 实现

孤儿规则允许你使用类似 `impl<T> MyTrait for T where T: ...` 的代码为一系列类型实现 trait，等等。这是一种 *blanket implementation*——它不限于某一种特定类型，而是适用于广泛的类型。只有定义 trait 的 crate 才允许编写 blanket 实现，并且向现有 trait 添加 blanket 实现被视为破坏性变更。如果不是这样，下游 crate 中包含 `impl MyTrait for Foo` 的代码可能仅仅因为你更新了定义 `MyTrait` 的 crate 而突然停止编译，并出现冲突实现的错误。

## Fundamental Types 基础类型

有些类型如此重要，以至于有必要允许任何人在其上实现 trait，即使这似乎违反了孤儿规则。这些类型被标记为 `#[fundamental]` 属性，目前包括 `&`、`&mut` 和 `Box`。就孤儿规则而言，基础类型几乎可以认为不存在——它们在检查孤儿规则之前被有效地擦除，以便允许你例如为 `&MyType` 实现 `IntoIterator`。仅凭孤儿规则，这种实现是不被允许的，因为它为外来的类型实现了外来的 trait——`IntoIterator` 和 `&` 都来自标准库。对基础类型添加 blanket 实现也被视为破坏性变更。

## Covered Implementations 覆盖实现

有一些有限的情况，我们希望允许为外来的类型实现外来的 trait，而孤儿规则通常不允许这样做。最简单的例子是当你想写类似 `impl From<MyType> for Vec<i32>` 时。这里 `From` trait 是外来的，`Vec` 类型也是外来的，但不会有违反 coherence 的危险。这是因为冲突的实现只能通过标准库中的 blanket 实现添加（标准库否则无法命名 `MyType`），而这本身就是破坏性变更。

为了允许这类实现，孤儿规则包含了一个狭窄的豁免，允许在非常特定的情况下为外来的类型实现外来的 trait。具体来说，给定的 `impl<P1...=Pn> ForeignTrait<T1...=Tn> for T0` 仅在至少一个 `Ti` 是本地类型并且在第一个这样的 `Ti` 之前没有 `T` 是泛型类型 `P1...=Pn` 之一时才被允许。泛型类型参数（`Ps`）*可以*出现在 `T0...Ti` 中，只要它们被某个中间类型 *covered* 覆盖即可。`T` 被视为 covered 如果它作为某个其它类型的类型参数出现（如 `Vec<T>`），但如果它单独存在（仅 `T`）或仅出现在基础类型后面（如 `&T`）则不算。因此，列表 3-4 中的所有实现都是有效的。

```
impl<T> From<T> for MyType
impl<T> From<T> for MyType<T>
impl<T> From<MyType> for Vec<T>
impl<T> ForeignTrait<MyType, T> for Vec<T>
```

然而，列表 3-5 中的实现是无效的。

```
impl<T> ForeignTrait for T
impl<T> From<T> for T
impl<T> From<Vec<T>> for T
impl<T> From<MyType<T>> for T
impl<T> From<T> for Vec<T>
impl<T> ForeignTrait<T, MyType> for Vec<T>
```

孤儿规则的这种放宽使在为现有 trait 添加新实现时，判断何种变更构成破坏性变更的规则变得复杂。特别是，向现有 trait 添加新实现只有在它包含至少一个新的本地类型，并且该新本地类型满足前面所述豁免规则时才是非破坏性的。添加任何其它新实现都是破坏性变更。

> NOTE 注意 `impl<T> ForeignTrait<LocalType, T> for ForeignType` 是有效的，但 `impl<T> ForeignTrait<T, LocalType> for ForeignType` 是无效的！这可能看起来很随意，但如果没有此规则，你可以编写 `impl<T> ForeignTrait<T, LocalType> for ForeignType`，而另一个 crate 可以编写 `impl<T> ForeignTrait<TheirType, T> for ForeignType`，冲突只会在两个 crate 被组合时出现。与其完全禁止这种模式，孤儿规则要求你的本地类型出现在类型参数之前，这打破了平局并确保如果两个 crate 在各自独立时都保持 coherence，那么在组合时也保持 coherence。

## Trait Bounds

标准库充斥着 trait bounds，无论是 HashMap 中的键必须实现 Hash + Eq，还是传给 thread::spawn 的函数必须为 FnOnce + Send + 'static。当你自己编写泛型代码时，它几乎肯定会包含 trait bounds，否则你的代码无法对它泛型的类型做太多事情。随着你编写更复杂的泛型实现，你会发现你也需要更精确的 trait bounds，因此让我们看看实现这一点的方法。

首先，trait bounds 不必是形式为 T: Trait 的形式，其中 T 是你的实现或类型所泛型的某个类型。bounds 可以是任意的类型限制，甚至不需要包含泛型参数、参数类型或本地类型。你可以写一个像 where String: Clone 的 trait bound，即使 String: Clone 始终为真且不包含本地类型。你也可以写 where io::Error: From<MyError<T>>；你的泛型类型参数不需要只出现在左侧。这不仅允许你表达更复杂的 bounds，还可以避免不必要地重复 bounds。例如，如果你的方法想要构造一个键为某个泛型类型 T、值为 usize 的 HashMap<K, V, S>，而不是像 where T: Hash + Eq, S: BuildHasher + Default 这样写出 bounds，你可以写 where HashMap<T, usize, S>: FromIterator。这可以节省你查找确切 bounds 要求的麻烦
