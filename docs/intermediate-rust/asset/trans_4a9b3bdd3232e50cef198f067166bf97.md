

并非所有 impl Trait 的实例都使用 existential types。如果你将 impl Trait 用在函数的参数位置，它实际上只是该函数的一个未命名泛型参数的简写。例如，fn foo(s: impl ToString) 基本上只是 fn foo<S: ToString>(s: S) 的语法糖。

Existential types 在实现带有关联类型的 trait 时特别有用。例如，想象你在实现 IntoIterator trait。它有一个关联类型 IntoIter，用于保存该类型可以被转换为的迭代器的类型。有了 existential types，你就不需要为 IntoIter 定义一个单独的迭代器类型。相反，你可以将关联类型写成 impl Iterator<Item = Self::Item>，然后在 fn into_iter(self) 内部写一个求值为 Iterator 的表达式，例如通过对某个现有迭代器类型使用 map 和 filter。

Existential types 还提供了一个超越单纯便利性的特性：它们允许你执行零成本的类型擦除。不是仅仅因为它们出现在某个公共签名中就导出辅助类型——迭代器和 future 就是常见的例子——你可以使用 existential types 来隐藏底层具体类型。你的接口的使用者只能看到相关类型实现的相关 trait，而具体类型则作为实现细节保留下来。这不仅简化了接口，而且还使你能够在未来随意更改该实现，而不会破坏下游代码。

## Summary

本章对 Rust 类型系统进行了全面回顾。我们既研究了编译器如何在内存中体现类型，也研究了它如何对类型本身进行推理。这对于编写 unsafe 代码、复杂的应用接口以及后续章节中的异步代码而言是非常重要的背景知识。你还会发现，本章中的许多类型推理也影响着你如何设计 Rust 代码接口，我们将在下一章中介绍这一点。

## Common Traits for Types

Rust 中的用户还会做出一个主要假设，即接口中的一切都“只需工作”。他们期望能够使用 {:?} 打印任何类型，并将任何东西发送到另一个线程，并且他们期望每个类型都是 Clone。在可能的情况下，我们应再次避免让用户感到惊讶，并在不需要立即使用时也积极实现大多数标准 trait。

由于第 3 章中讨论的 coherence 规则，编译器不会允许用户在需要时为这些 trait 实现。用户不被允许为外来的类型（如你接口中的类型）实现外来的 trait（如 Clone）。他们反而需要将你的接口类型包装在自己的类型中，即使这样，在没有访问该类型内部结构的情况下，编写合理的实现也可能相当困难。

这些标准 trait 中首要的是 Debug trait。几乎每种类型都可以，也应该实现 Debug，即使它只打印类型的名称。使用 #[derive(Debug)] 通常是实现接口中 Debug trait 的最佳方式，但请记住，所有派生的 trait 都会自动为任何泛型参数添加相同的 bound。你也可以通过利用 fmt::Formatter 上的各种 debug_helpers 来自行编写实现。

紧随其后的是 Rust 的 auto-traits Send 和 Sync（以及在较小程度上 Unpin）。如果一个类型未实现这些 trait 中的一个，那应该有非常充分的理由。未实现 Send 的类型不能放入 Mutex 中，也不能在包含线程池的应用程序中甚至间接使用。未实现 Sync 的类型不能通过 Arc 共享，也不能放在静态变量中。用户已经习惯于类型在这些上下文中“只需工作”，尤其是在异步世界中几乎所有内容都在线程池上运行，如果你不确保你的类型实现了这些 trait，他们会感到沮丧。如果你的类型无法实现它们，请确保这一事实及其原因得到充分记录！

接下来的一组几乎通用的 trait 你应该实现的是 Clone 和 Default。这些 trait 可以轻松派生或实现，并且对大多数类型来说都有意义。如果你的类型无法实现这些 trait，请务必在文档中指出，因为用户通常期望能够轻松创建更多（和新的）类型的实例。如果他们不能，他们会感到惊讶。

在预期 trait 层级中更进一步的是比较 trait：PartialEq、PartialOrd、Hash、Eq 和 Ord。PartialEq trait 尤其可取，因为用户在某个时候不可避免地会有两个你的类型的实例，他们希望使用 == 或 assert_eq! 进行比较。即使你的类型仅在同一实例时才相等，实现 PartialEq 也值得去做，以便你的用户可以使用 assert_eq!。

PartialOrd 和 Hash 更为专门，可能适用范围不那么广，但只要有可能，你也希望实现它们。这对于用户可能用作 map 中的键的类型，或他们可能使用 std::collection 中的任何集合类型去去重的类型尤其正确，因为它们往往需要这些 bound。Eq 和 Ord 在实现类型的比较操作上比 PartialEq 和 PartialOrd 有额外的语义要求。这些在这些 trait 的文档中都有很好的记录，只有当你确定这些语义确实适用于你的类型时才应实现它们。

最后，对于大多数类型，实现 serde crate 的 Serialize 和 Deserialize trait 是有意义的。这些可以轻松派生，并且 serde_derive crate 甚至提供了仅重写一个字段或枚举变体的序列化的机制。由于 serde 是一个第三方 crate，你可能不希望在上面添加必需的依赖。大多数库因此选择提供一个 serde feature，仅在用户选择加入时才添加对 serde 的支持。

你可能会想知道为什么我没有在本节中包含可派生的 trait Copy。Copy 与提到的其他 trait 有两点不同。首先，用户通常并不期望类型是 Copy；恰恰相反，他们倾向于期望如果想要某物的两个副本，就必须调用 clone。Copy 改变了移动给定类型值的语义，这可能会让用户感到惊讶。这与第二个观察相关：类型很容易不再是 Copy，因为 Copy 类型受到严格限制。一个起初简单的类型很容易最终需要持有 String 或其他非 Copy 类型。如果发生这种情况，并且你必须移除 Copy 实现，那是一个向后不兼容的更改。移除 Clone 实现的情况要少得多，因此这是一个负担更小的承诺。

## Ergonomic Trait Implementations

Rust 不会自动为实现了 trait 的类型的引用实现 trait。换句话说，你通常不能用 &Bar 调用 fn foo<T: Trait>(t: T)，即使 Bar: Trait。这是因为 Trait 可能包含接收 &mut self 或 self 的方法，而这些方法显然不能在 &Bar 上调用。尽管如此，这种行为对于看到 Trait 只有 &self 方法的用户来说可能非常令人惊讶！

因此，当你定义一个新的 trait 时，你通常希望为 &T where T: Trait、&mut T where T: Trait 以及 Box<T> where T: Trait 提供适当的 blanket 实现，具体取决于 Trait 的方法接收者是什么。你可能只能实现其中一些，具体取决于 Trait 方法的接收者。标准库中的许多 trait 都有类似的实现，正是因为这会让用户感到更少惊讶。

迭代器是另一个你通常希望在类型的引用上专门添加 trait 实现的案例。对于任何可以迭代的类型，请考虑为 &MyType 和 &mut MyType 在适用时实现 IntoIterator。这使得 for 循环开箱即用地与你类型的借用实例一起工作，就像用户期望的那样。

## Wrapper Types

Rust 在经典意义上没有对象继承。然而，Deref trait 及其表亲 AsRef 都提供了一种有点像继承的东西。这些 trait 允许你拥有类型 T 的值，并通过在 T 类型的值上直接调用它们来调用类型 U 的方法，如果 T: Deref<Target = U>。这对用户来说感觉像魔法，通常非常棒。
