## 内存中的类型

每个 Rust 值都有一个类型。类型在 Rust 中有许多用途，我们将在本章中看到，但它们最基本的角色之一是告诉你如何解释内存中的位。例如，位序列 0b10111101（用十六进制表示法写成 0xBD）本身没有任何意义，直到你给它分配一个类型。当在 u8 类型下解释时，该位序列是数字 189。当在 i8 类型下解释时，它是 −67。当你定义自己的类型时，编译器的工作是确定所定义类型的每个部分在该类型的内存表示中的位置。你的 struct 的每个字段出现在位序列的哪个位置？你的 enum 的判别式存储在哪里？当你开始编写更高级的 Rust 代码时，理解这个过程是如何工作的很重要，因为这些细节既影响代码的正确性，也影响性能。

### 对齐

在我们讨论类型的内存表示如何确定之前，我们首先需要讨论对齐的概念，它决定了类型的字节可以存储在哪里。一旦类型的表示被确定，你可能会认为你可以取任意的内存位置，并将存储在那里的字节解释为该类型。虽然这在理论上是正确的，但在实践中，硬件也限制了给定类型的放置位置。最明显的例子是指针指向字节，而不是位。如果你将类型 T 的值放在计算机内存的第 4 位开始，你将无法引用它的位置；你只能创建指向字节 0 或字节 1（第 8 位）的指针。因此，所有值，无论其类型如何，都必须从字节边界开始。我们说所有值至少必须是字节对齐的——它们必须被放置在一个是 8 的倍数的地址上。

某些值比字节对齐有更严格的规则。在 CPU 和内存系统中，内存通常以大于单个字节的块进行访问。例如，在 64 位 CPU 上，大多数值以 8 字节（64 位）的块访问，每次操作从 8 字节对齐的地址开始。这被称为 CPU 的字长。然后 CPU 使用一些技巧来处理更小值的读写，或跨越这些块边界的值。

在可能的情况下，你希望确保硬件能够以其“原生”对齐方式运行。要了解原因，请考虑如果尝试读取一个从 8 字节块中间开始的 i64（也就是说，指向它的指针不是 8 字节对齐的）会发生什么。硬件将不得不进行两次读取——一次从第一个块的后半部分读取以到达 i64 的起始位置，另一次从第二个块的前半部分读取 i64 的其余部分——然后将结果拼接在一起。这不是很高效。由于该操作分散在对底层内存的多次访问中，如果你正在读取的内存被另一个线程并发写入，你最终可能会得到奇怪的结果。你可能会在另一个线程写入之前读取前 4 个字节，在写入之后读取后 4 个字节，从而导致值损坏。

对未对齐数据的操作被称为未对齐访问，可能导致性能不佳和严重的并发问题。因此，许多 CPU 操作要求或强烈倾向于其参数自然对齐。自然对齐的值是其对齐方式与其大小匹配的值。例如，对于 8 字节加载，提供的地址需要是 8 字节对齐的。

由于对齐访问通常更快，并提供更强的一致性语义，编译器会尽可能利用它们。它通过为每个类型赋予一个基于其包含的类型计算的对齐方式来实现这一点。内置值通常与其大小对齐，所以 u8 是字节对齐，u16 是 2 字节对齐，u32 是 4 字节对齐，u64 是 8 字节对齐。复杂类型——包含其他类型的类型——通常被分配为其包含的任何类型中最大的对齐方式。例如，包含 u8、u16 和 u32 的类型将是 4 字节对齐的，因为 u32 的存在。

### 布局

既然你已经了解了对齐，我们可以探讨编译器如何决定类型的内存表示，即布局。默认情况下，正如你很快会看到的，Rust 编译器对如何布局类型给出的保证很少，这使得它成为理解底层原理的一个不好的起点。幸运的是，Rust 提供了一个 repr 属性，你可以将其添加到类型定义中，以请求该类型的特定内存表示。如果你能看到的话，你将看到的最常见的 repr 是 repr(C)。顾名思义，它以与 C 或 C++ 编译器布局相同类型的方式兼容的方式来布局该类型。这在编写使用外部函数接口与其他语言交互的 Rust 代码时很有帮助，我们将在第 12 章中讨论，因为 Rust 将生成与其他语言编译器期望匹配的布局。由于 C 布局是可预测的且不会改变，repr(C) 在 unsafe 上下文中也很有用，如果你正在使用指向该类型的原始指针，或者如果你需要在你知道具有相同字段的两个不同类型之间进行转换。当然，它也是我们迈出布局算法第一步的完美选择。

> 另一种有用的表示是 repr(transparent)，它只能用于具有单个字段的类型，并保证外部类型的布局与内部类型的布局完全相同。这与“newtype”模式结合使用时很方便，在 newtype 模式中，你可能希望以相同的方式操作某个 struct A 和 struct NewA(A) 的内存表示。如果没有 repr(transparent)，Rust 编译器不保证它们具有相同的布局。

那么，让我们看看编译器如何使用 repr(C) 布局一个特定类型：清单 3-1 中的 Foo 类型。你认为编译器会如何在内存中布局它？

```
#[repr(C)]
struct Foo {
    tiny: bool,
    normal: u32,
    small: u8,
    long: u64,
    short: u16,
}
```

首先编译器看到字段 `tiny`，其逻辑大小为 1 位（true 或 false）。但由于 CPU 和内存以字节为单位操作，`tiny` 在内存表示中被分配了 1 个字节。接下来，`normal` 是一个 4 字节类型，因此我们希望它 4 字节对齐。但即使 `Foo` 是对齐的，分配给 `tiny` 的 1 个字节也会使 `normal` 错过其对齐。为了纠正这一点，编译器在内存表示中在 `tiny` 和 `normal` 之间插入 3 个字节的 *填充*——填充字节的值是不确定的，在用户代码中会被忽略。填充中没有值，但它确实占用空间。

对于下一个字段 `small`，对齐很简单：它是一个 1 字节值，结构体中当前字节偏移量为 1 + 3 + 4 = 8。这已经是字节对齐的，因此 `small` 可以紧跟在 `normal` 之后。对于 `long` 我们又遇到问题了。我们现在已经在 `Foo` 中使用了 1 + 3 + 4 + 1 = 9 个字节。如果 `Foo` 是对齐的，那么 `long` 就不会像我们希望的那样 8 字节对齐，因此我们必须再插入 7 个字节的填充以使 `long` 再次对齐。这也恰好确保了最后一个字段 `short` 所需的 2 字节对齐，总计达到 26 字节。现在我们已经遍历了所有字段，还需要确定 `Foo` 本身的对齐方式。这里的规则是使用 `Foo` 的所有字段中最大的对齐方式，由于 `long` 的存在，这将是 8 字节。因此，为了确保 `Foo` 在放置在例如数组中时仍然对齐，编译器随后添加最后 6 个字节的填充，使 `Foo` 的大小为其对齐方式的倍数，达到 32 字节。

现在我们准备抛弃 C 的遗留问题，考虑如果我们在列表 3-1 中不使用 `repr(C)`，布局会发生什么。C 表示的主要限制之一是要求我们按原始结构体定义中出现的相同顺序放置所有字段。默认的 Rust 表示 `repr(Rust)` 去除了这一限制，同时去除了一些较小的限制，例如对于恰好具有相同字段的类型，字段顺序是确定的。也就是说，即使两个不同的类型共享完全相同的字段、类型相同、顺序相同，使用默认的 Rust 布局时也不能保证它们的布局相同！

由于我们现在可以重新排序字段，我们可以将它们按大小递减的顺序放置。这意味着我们不再需要在 `Foo` 的字段之间使用填充；字段本身用于实现必要的对齐！`Foo` 现在只是其字段的大小之和：只有 16 字节。这就是 Rust 默认情况下对类型在内存中的布局没有给出太多保证的原因之一：通过给编译器更大的重新排列的自由度，我们可以生成更高效的代码。

事实证明，还有第三种布局类型的方法，那就是告诉编译器我们不希望字段之间有任何填充。在这样做时，我们表示愿意承受使用未对齐访问带来的性能损失。这种行为最常见的用例是当每增加一个字节的内存影响都能感受到时，例如如果你有大量该类型的实例，如果内存非常有限，或者如果你将内存表示通过网络连接等低带宽介质发送。要选择此行为，你可以为类型添加注释 `#[repr(packed)]`。请记住，这可能导致代码运行速度大幅变慢，在极端情况下，如果你尝试执行 CPU 仅在对齐参数上支持的操作，这可能会导致程序崩溃。

有时，你希望给某个特定字段或类型提供比其技术上所需更大的对齐方式。你可以使用属性 `#[repr(align(n))]` 来做到这一点。这种行为的一个常见用例是确保在内存中连续存储的不同值（如数组中）最终位于 CPU 上的不同缓存行中。这样，你就可以避免 *伪共享*，伪共享可能导致并发程序中巨大的性能下降。伪共享发生在两个不同的 CPU 访问不同的值时，这些值恰好共享一个缓存行；虽然它们理论上可以并行操作，但它们最终都会争夺更新缓存中的同一个条目。我们将在第 11 章更详细地讨论并发。

## 复杂类型

你可能好奇编译器如何在内存中表示其他 Rust 类型。这里有一个快速参考：

- **元组** 表示为与元组值类型相同且顺序相同的字段的结构体。
- **数组** 表示为包含类型的连续序列，元素之间没有填充。
- **联合** 每个变体的布局独立选择。对齐是所有变体中的最大值。
- **枚举** 与联合相同，但带有一个额外的隐藏共享字段来存储枚举变体判别式。判别式是代码用来确定给定值持有哪个枚举变体的值。判别式字段的大小取决于变体的数量。

## 动态大小类型和胖指针

你可能在 Rust 文档的各种角落以及错误信息中遇到过标记 trait Sized。通常，它出现是因为编译器希望你提供一个 Sized 类型，但你（显然）没有提供。Rust 中大多数类型会自动实现 Sized——也就是说，它们在编译时大小已知——但有两个常见类型没有实现：trait 对象和切片。如果你有例如 `dyn Iterator` 或 `[u8]`，它们没有明确定义的大小。它们的大小取决于只有程序运行时才知道的信息，而不是编译时，这就是为什么它们被称为 *动态大小类型 (DSTs)*。没有人能提前知道你的函数收到的 `dyn Iterator` 是这个 200 字节的结构体还是那个 8 字节的结构体。这带来了一个问题：编译器经常必须知道某个事物的大小才能生成有效代码，例如为类型为 `(i32, dyn Iterator, [u8], i32)` 的元组分配多少空间，或如果你的代码尝试访问第四个字段时使用什么偏移量。但如果类型不是 Sized，则该信息不可用。

编译器几乎在所有地方都要求类型为 Sized。结构体字段、函数参数、返回值、变量类型和数组类型都必须为 Sized。这一限制如此常见，以至于你编写的每个类型边界都包含 T: Sized，除非你明确使用 T: ?Sized 退出（? 表示“可能不是”）。但如果你有一个 DST 并且想对它做一些事情，例如真的希望你的函数接受 trait 对象或切片作为参数，这就没什么帮助了。

解决办法是将其放在胖指针后面。胖指针就像普通指针一样，但它包含一个额外的字长字段，提供编译器生成处理该指针的合理代码所需的那部分关于该指针的额外信息。当你对 DST 取引用时，编译器会自动为你构造一个胖指针。对于切片，额外信息只是切片的长度。对于 trait 对象——嗯，我们稍后再说。并且至关重要的是，该胖指针是 Sized。具体来说，它是 usize 两倍大小（目标平台上字长）：一个 usize 用于保存指针，一个 usize 用于保存“完成”该类型所需的信息。

> NOTE Box 和 Arc 也支持存储胖指针，这就是为什么它们都支持 T: ?Sized。

## Traits 和 Trait Bounds

Traits 是 Rust 类型系统的关键部分——它们是使类型能够相互协作的胶水，即使它们在定义时彼此不知道。Rust 编程语言很好地介绍了如何定义和使用 traits，所以我在这里不会重复。相反，我们将看看 traits 的一些更技术性的方面：它们是如何实现的，你必须遵守的限制，以及 traits 的一些更晦涩的使用。

## 编译和分发

到现在为止，你可能已经在 Rust 中编写了相当多的通用代码。你在类型和方法上使用了泛型类型参数，也许还使用了几个 trait bounds。但你有没有想过当你编译泛型代码时会发生什么，或者当你在 dyn Trait 上调用 trait 方法时会发生什么？

当你编写一个关于 T 的泛型类型或函数时，你实际上是在告诉编译器为你提供的每种类型 T 制作该类型或函数的副本。当你构造一个 Vec<i32> 或一个 HashMap<String, bool> 时，编译器本质上会复制粘贴泛型类型及其所有实现块，并用你提供的具体类型替换每个泛型参数的每个实例。它会制作一个完整的 Vec 类型副本，其中所有 T 都被替换为 i32，并制作一个完整的 HashMap 类型副本，其中所有 K 都被替换为 String，所有 V 都被替换为 bool。

> NOTE 实际上，编译器并没有真正进行完整的复制粘贴。它只复制你使用的代码部分，因此如果你从未在 Vec<i32> 上调用 find，则 find 的代码不会被复制和编译。





## 非泛型内部函数

通常，泛型方法中的大量代码并不依赖于类型。例如，考虑 `HashMap::insert` 的实现。计算所提供键的哈希值的代码取决于映射的键类型，但遍历映射的桶以找到插入点的代码可能并不依赖。 在这种情况下，更高效的做法是跨单态化共享非泛型部分的方法生成的机器代码，而仅在确实需要时生成不同的副本。

对于这种情况，你可以使用的一种模式是在泛型方法内部声明一个非泛型辅助函数来执行共享操作。这样就只剩下类型相关的代码需要编译器为你复制粘贴，同时允许辅助函数被共享。

将函数设为内部函数还有一个额外的好处，那就是不会用单一用途的函数污染你的模块。你也可以在方法外部声明这样的辅助函数；只是要小心不要将其设为泛型 `impl` 块下的一个方法，因为那样它仍然会被单态化。

静态分派的替代方案是 *动态分派*，它使代码能够在不知道该类型的情况下调用泛型类型上的 trait 方法。我之前说过，我们在清单 3-2 中需要方法的多个实例的原因是，否则你的程序就不知道要跳转到哪个地址去调用给定模式上的 trait 方法 `is_contained_in`。好吧，使用动态分派，调用者只需告诉你即可。如果你用 `&dyn Pattern` 替换 `impl Pattern`，你就告诉调用者他们必须为此参数提供两条信息：模式的地址和 `is_contained_in` 方法的地址。实际上，调用者给我们一个指向称为虚方法表，或 vtable 的内存块的指针，该表保存了所讨论类型的 trait 所有方法的实现地址，其中之一就是 `is_contained_in`。当方法内部的代码想要在提供的模式上调用 trait 方法时，它会在 vtable 中查找该模式的 `is_contained_in` 实现的地址，然后调用该地址处的函数。这使我们能够无论调用者想要使用什么类型，都使用相同的函数体。

NOTE 每个 vtable 还包含有关具体类型布局和对齐的信息，因为这些信息在使用类型时始终是必需的。如果你想看一个显式 vtable 的例子，可以看看 `std::task::RawWakerVTable` 类型。

你会注意到，当我们使用 `dyn` 关键字选择动态分派时，我们必须在它前面加上一个 `&`。原因是我们不再能在编译时知道调用者传入的 pattern 类型的大小，因此我们不知道要为其预留多少空间。换句话说，`dyn Trait` 是

!Sized，其中 `!` 表示不是。为了使其成为 Sized 以便我们可以将其作为参数传递，我们将其放在指针后面（我们知道其大小）。由于我们还需要传递方法地址表，这个指针就变成了一个胖指针，其中额外的字保存指向 vtable 的指针。你可以使用任何能够容纳胖指针的类型来进行动态分派，例如 `&mut`、`Box` 和 `Arc`。清单 3-3 显示了清单 3-2 的动态分派等价物。

```
impl String {
    pub fn contains(&self, p: &dyn Pattern) -> bool {
        p.is_contained_in(&*self)
    }
}
```

清单 3-3：使用动态分派的泛型方法

实现 trait 的类型与其 vtable 的组合被称为 trait 对象。大多数 trait 都可以转换为 trait 对象，但并非全部。例如，`Clone` trait，其 `clone` 方法返回 `Self`，就不能转换为 trait 对象。如果我们接受一个 `dyn Clone` trait 对象然后在其上调用 `clone`，编译器就不知道要返回什么类型。或者，考虑标准库中的 `Extend` trait，它有一个 `extend` 方法，该方法对提供的迭代器的类型是泛型的（因此可能存在多个实例）。如果你要调用一个接受 `dyn Extend` 的方法，就没有单一的地址可以放在 trait 对象的 vtable 中的 `extend`；对于 `extend` 可能被调用的每种类型都必须有一个条目。这些就是不是对象安全的 trait，因此不能转换为 trait 对象的例子。为了成为对象安全，trait 的任何方法都不能是泛型的或使用 `Self` 类型。此外，trait 不能有任何静态方法（即第一个参数不解引用为 `Self` 的方法），因为不可能知道要调用该方法的哪个实例。例如，`FromIterator::from_iter(&[0])` 应该执行什么代码就不清楚了。

当阅读有关 trait 对象的资料时，你可能会看到提到 trait bound `Self: Sized`。这样的 bound 意味着 `Self` 并不是通过 trait 对象使用（因为它将是 `!Sized`）。你可以在 trait 上放置该 bound 以要求该 trait 永不使用动态分派，或者可以在特定方法上放置它以使该方法在通过 trait 对象访问 trait 时不可用。带有 `where Self: Sized` bound 的方法在检查 trait 是否对象安全时会被豁免。

动态分派可以缩短编译时间，因为不再需要编译类型和方法的多个副本，并且可以提高 CPU 指令缓存的效率。然而，它也阻止编译器针对使用的特定类型进行优化。使用动态分派时，编译器对清单 3-2 中的 `find` 所能做的只是通过 vtable 插入对函数的调用——它无法再进行任何额外的优化，因为它不知道函数调用另一侧的代码是什么。此外，对 trait 对象的每次方法调用都需要 vtable 中的查找，这比直接调用方法会带来少量开销。

当你需要在静态分派和动态分派之间做出选择时，很少有明确的正确答案。总体而言，你通常希望在库中使用静态分派，在二进制中使用动态分派。在库中，你希望允许用户决定哪种分派最适合他们，因为你不知道他们的需求是什么。如果你使用动态分派，他们就被迫同样使用，而如果你使用静态分派，他们可以选择是否使用动态分派。另一方面，在二进制中，你编写的是最终代码，所以除了你所编写的代码的需求外没有其他需求需要考虑。动态分派通常允许你编写更简洁的代码，省去泛型参数，并且编译速度更快，只是以（通常）边际的性能成本为代价，因此通常是二进制的更好选择。

## 泛型 Trait

Rust trait 可以以两种方式泛型化：使用泛型类型参数如 `trait Foo<T>` 或使用关联类型如 `trait Foo { type Bar; }`。两者之间的区别并不立即明显，但幸运的是经验法则非常简单：如果期望对给定类型只有一种 trait 实现，就使用关联类型；否则使用泛型类型参数。

其原理是关联类型通常更容易使用，但不允许多次实现。因此，更简单地说，建议是只要能用就使用关联类型。

对于泛型 trait，用户必须始终指定所有泛型参数并重复这些参数上的任何 bound。这很快就会变得混乱且难以维护。如果你向 trait 添加一个泛型参数，所有该 trait 的用户也必须更新以反映这一变化。而且由于对给定类型可能存在多个 trait 实现，编译器可能很难判断你打算使用哪个实例的 trait，导致像 `FromIterator::<u32>::from_iter` 这样糟糕的消除歧义函数调用。但好处是你可以在同一类型上多次实现 trait——例如，你可以针对多个右手边类型为你的类型实现 `PartialEq`，或者你可以同时实现 `FromIterator<T>` 和 `FromIterator<&T>` 其中 `T: Clone`，正是因为泛型 trait 提供的灵活性。

另一方面，使用关联类型时，编译器只需要知道实现 trait 的类型，而所有关联类型都会随之确定（因为只有一个实现）。这意味着所有 bound 都可以存在于 trait 本身中，而无需在使用时重复。反过来，这允许 trait 在不影响其用户的情况下添加进一步的关联类型。而且由于类型决定了 trait 的所有关联类型，你永远不需要使用上一段中显示的统一函数调用语法来消除歧义。然而，你不能针对多个 `Target` 类型实现 `Deref`，也不能使用多个不同的 `Item` 类型实现 `Iterator`。

## 一致性与孤儿规则

Rust 对你可以在哪里实现 trait 以及可以在什么类型上实现它们有一些相当严格的规则。这些规则的存在是为了保持



*coherence* 属性：对于任何给定的类型和方法，只能有一种正确的选择来决定为该类型使用该方法的哪个实现。要了解其重要性，请考虑如果我可以为标准库中的 `bool` 类型编写自己的 `Display` trait 实现会发生什么。现在，对于任何尝试打印 bool 值并包含我的 crate 的代码，编译器都不会知道是选择我编写的实现还是标准库中的实现。两种选择都不是正确或更好，编译器显然不能随机选择。如果标准库根本不涉及，情况也一样，但我们有两个相互依赖的 crate，它们都为某个共享类型实现了 trait。coherence 属性确保编译器永远不会陷入这些情况，也永远不需要做出这些选择：总会有一个显而易见的选择。

一种简单的方式来维护 coherence 就是确保只有定义 trait 的 crate 才能为该 trait 编写实现；如果没有人可以实现该 trait，那么在其他地方就不会有冲突的实现。然而，这在实践中过于严格，本质上会使 trait 变得无用，因为除非你将自己的类型纳入定义 crate，否则就无法为自己的类型实现诸如 `std::fmt::Debug` 和 `serde::Serialize` 之类的 trait。相反的极端情况，即说你只能为自己的类型实现 trait，解决了这个问题但引入了另一个问题：定义 trait 的 crate 现在无法为标准库或其它流行 crate 中的类型提供该 trait 的实现！理想情况下，我们希望找到一套规则，在下游 crate 为其自己的类型实现上游 trait 的需求与上游 crate 能够在不破坏下游代码的情况下添加其自身 trait 的实现的需求之间取得平衡。

> **NOTE**
> 
> *Upstream 指的是你的代码所依赖的东西，而 downstream 指的是依赖你代码的东西。这些术语通常以 crate 依赖关系的直接意义使用，但也可以用来指代码库的权威分支——如果你对 Rust 编译器进行分支，那么官方 Rust 编译器就是你的“上游”。*

在 Rust 中，建立这种平衡的规则是 *orphan rule* 孤儿规则。简单来说，孤儿规则规定，你只能在 trait *或* 类型是本地于你的 crate 时为类型实现 trait。因此，你可以为自己的类型实现 `Debug`，也可以为 `bool` 实现 `MyNeatTrait`，但你不能为 `bool` 实现 `Debug`。如果你尝试这样做，你的代码将无法编译，编译器会告诉你存在冲突的实现。

这已经让你走得很远；它允许你为第三方类型实现自己的 trait，并为自己的类型实现第三方的 trait。然而，孤儿规则并不是故事的全部。还有许多额外的含义、注意事项和例外情况，你应该了解。

## Blanket Implementations  blanket 实现

孤儿规则允许你使用类似 `impl<T> MyTrait for T where T: ...` 的代码为一系列类型实现 trait，等等。这是一种 *blanket implementation*——它不限于某一种特定类型，而是适用于广泛的类型。只有定义 trait 的 crate 才允许编写 blanket 实现，并且向现有 trait 添加 blanket 实现被视为破坏性变更。如果不是这样，下游 crate 中包含 `impl MyTrait for Foo` 的代码可能仅仅因为你更新了定义 `MyTrait` 的 crate 而突然停止编译，并出现冲突实现的错误。

## Fundamental Types 基础类型

有些类型如此重要，以至于有必要允许任何人在其上实现 trait，即使这似乎违反了孤儿规则。这些类型被标记为 `#[fundamental]` 属性，目前包括 `&`、`&mut` 和 `Box`。就孤儿规则而言，基础类型几乎可以认为不存在——它们在检查孤儿规则之前被有效地擦除，以便允许你例如为 `&MyType` 实现 `IntoIterator`。仅凭孤儿规则，这种实现是不被允许的，因为它为外来的类型实现了外来的 trait——`IntoIterator` 和 `&` 都来自标准库。对基础类型添加 blanket 实现也被视为破坏性变更。

## Covered Implementations 覆盖实现

有一些有限的情况，我们希望允许为外来的类型实现外来的 trait，而孤儿规则通常不允许这样做。最简单的例子是当你想写类似 `impl From<MyType> for Vec<i32>` 时。这里 `From` trait 是外来的，`Vec` 类型也是外来的，但不会有违反 coherence 的危险。这是因为冲突的实现只能通过标准库中的 blanket 实现添加（标准库否则无法命名 `MyType`），而这本身就是破坏性变更。

为了允许这类实现，孤儿规则包含了一个狭窄的豁免，允许在非常特定的情况下为外来的类型实现外来的 trait。具体来说，给定的 `impl<P1...=Pn> ForeignTrait<T1...=Tn> for T0` 仅在至少一个 `Ti` 是本地类型并且在第一个这样的 `Ti` 之前没有 `T` 是泛型类型 `P1...=Pn` 之一时才被允许。泛型类型参数（`Ps`）*可以*出现在 `T0...Ti` 中，只要它们被某个中间类型 *covered* 覆盖即可。`T` 被视为 covered 如果它作为某个其它类型的类型参数出现（如 `Vec<T>`），但如果它单独存在（仅 `T`）或仅出现在基础类型后面（如 `&T`）则不算。因此，列表 3-4 中的所有实现都是有效的。

```
impl<T> From<T> for MyType
impl<T> From<T> for MyType<T>
impl<T> From<MyType> for Vec<T>
impl<T> ForeignTrait<MyType, T> for Vec<T>
```

impl<T> From<T> for T

孤儿规则的这种放宽使在为现有 trait 添加新实现时，判断何种变更构成破坏性变更的规则变得复杂。特别是，向现有 trait 添加新实现只有在它包含至少一个新的本地类型，并且该新本地类型满足前面所述豁免规则时才是非破坏性的。添加任何其它新实现都是破坏性变更。

> NOTE 注意 `impl<T> ForeignTrait<LocalType, T> for ForeignType` 是有效的，但 `impl<T> ForeignTrait<T, LocalType> for ForeignType` 是无效的！这可能看起来很随意，但如果没有此规则，你可以编写 `impl<T> ForeignTrait<T, LocalType> for ForeignType`，而另一个 crate 可以编写 `impl<T> ForeignTrait<TheirType, T> for ForeignType`，冲突只会在两个 crate 被组合时出现。与其完全禁止这种模式，孤儿规则要求你的本地类型出现在类型参数之前，这打破了平局并确保如果两个 crate 在各自独立时都保持 coherence，那么在组合时也保持 coherence。

## Trait Bounds

标准库充斥着 trait bounds，无论是 HashMap 中的键必须实现 Hash + Eq，还是传给 thread::spawn 的函数必须为 FnOnce + Send + 'static。当你自己编写泛型代码时，它几乎肯定会包含 trait bounds，否则你的代码无法对它泛型的类型做太多事情。随着你编写更复杂的泛型实现，你会发现你也需要更精确的 trait bounds，因此让我们看看实现这一点的方法。

首先，trait bounds 不必是形式为 T: Trait 的形式，其中 T 是你的实现或类型所泛型的某个类型。bounds 可以是任意的类型限制，甚至不需要包含泛型参数、参数类型或本地类型。你可以写一个像 where String: Clone 的 trait bound，即使 String: Clone 始终为真且不包含本地类型。你也可以写 where io::Error: From<MyError<T>>；你的泛型类型参数不需要只出现在左侧。这不仅允许你表达更复杂的 bounds，还可以避免不必要地重复 bounds。例如，如果你的方法想要构造一个键为某个泛型类型 T、值为 usize 的 HashMap<K, V, S>，而不是像 where T: Hash + Eq, S: BuildHasher + Default 这样写出 bounds，你可以写 where HashMap<T, usize, S>: FromIterator。这可以节省你查找确切 bounds 要求的麻烦



对于你最终使用的这些方法，它能更清晰地传达代码的“真实”需求。正如你所见，如果你想要调用的底层 trait 方法的边界很复杂，它还能显著降低你的边界复杂度。

## DERIVE TRAIT

虽然 `#[derive(Trait)]` 非常方便，但在 trait 边界的上下文中，你应该意识到它实现方式上一个细微之处。许多 `#[derive(Trait)]` 展开会被解糖为 `impl Trait for Foo<T> where T: Trait`。这通常是你想要的，但并非总是如此。例如，考虑如果我们以这种方式为 `Foo<T>` 推导 `Clone` 会发生什么，而 `Foo` 包含一个 `Arc<T>`。`Arc` 无论 `T` 是否实现 `Clone` 都实现了 `Clone`，但由于推导出的边界，`Foo` 只有在 `T` 实现时才会实现 `Clone`！这通常不是太大的问题，但它确实添加了一个并不需要的边界。如果我们将类型重命名为 `Shared`，问题可能会变得更清晰一些。想象一下，一个拥有 `Shared<NotClone>` 的用户在编译器告诉他无法克隆它时会多么困惑！在撰写本文时，这就是标准库提供的 `#[derive(Clone)]` 的工作方式，尽管未来可能会改变。

有时，你希望对你泛型的类型的关联类型设置边界。作为一个例子，考虑迭代器方法 `flatten`，它接受一个产生项的迭代器，而这些项本身又实现了 `Iterator`，并产生这些内部迭代器的项的迭代器。它产生的类型 `Flatten` 是关于 `I` 的泛型，`I` 是外部迭代器的类型。`Flatten` 在 `I` 实现 `Iterator` 且 `I` 产生的项本身实现 `IntoIterator` 时实现 `Iterator`。为了让你能够写出这样的边界，Rust 允许你使用语法 `Type::AssocType` 来引用一个类型的关联类型。例如，我们可以使用 `I::Item` 来引用 `I` 的 `Item` 类型。如果一个类型有多个同名的关联类型，例如如果提供关联类型的 trait 本身是泛型的（因此存在多个实现），你可以使用语法 `<Type as Trait>::AssocType` 来消除歧义。使用这种方式，你不仅可以为外部迭代器类型写边界，还可以为该外部迭代器的项类型写边界。

在大量使用泛型的代码中，你可能会发现需要写一个关于类型引用 的边界。这通常没问题，因为你往往也会有一个泛型的生命周期参数，可以用作这些引用的生命周期。然而，在某些情况下，你希望边界表示“这个引用对任何生命周期都实现这个 trait”。这种情况极为罕见——在撰写本文时，标准库仅在三个地方使用了它——但确实会发生。这种类型的边界被称为高阶 trait 边界，它与 `Fn` trait 结合使用时特别有用。例如，想象你希望对一个接受 `T` 的引用并返回 `T` 内部引用的函数进行泛型化。如果你写 `F: Fn(&T) -> &U`，你需要为这些引用提供一个生命周期，但你真正想说的是“任何生命周期，只要输出与输入相同”。使用高阶生命周期，你可以写 `F: for<'a> Fn(&'a T) -> &'a U` 来表示对于任何生命周期 `'a`，边界必须成立。Rust 编译器足够智能，可以在你以这种方式写带引用的 `Fn` 边界时自动添加 `for`，这也是你很少需要显式形式的部分原因，但了解它是有价值的。

为了将所有这些内容整合起来，请考虑第 3-6 节中的代码，可用于为任何可迭代且其元素为 `Debug` 的类型实现 `Debug`。

```

    where for<'a> &'a Self: IntoIterator,
        for<'a> <&'a Self as IntoIterator>::Item: Debug {
    fn fmt(&self, f: &mut Formatter) -> Result<(), Error> {

## Marker Traits

通常，我们使用 trait 来表示多个类型可以支持的功能；一个 `Hash` 类型可以通过调用 `hash` 来哈希，一个 `Clone` 类型可以通过调用 `clone` 来克隆，一个 `Debug` 类型可以通过调用 `fmt` 来格式化用于调试。但并非所有 trait 都是以这种方式功能的。一些 trait，称为标记 trait，反而表示实现类型的属性。标记 trait 没有方法和关联类型，仅用于告诉你特定类型可以或不可以以某种方式使用。例如，如果一个类型实现了 `Send` 标记 trait，它是安全的跨线程边界发送。如果它没有实现此标记 trait，则不安全发送。与此行为没有关联的方法；它只是关于类型的事实。标准库在 `std::marker` 模块中有许多这些，包括 `Send`、`Sync`、`Copy`、`Sized` 和 `Unpin`。其中大多数（除了 `Copy`）也是自动 trait；编译器会自动为类型实现它们，除非该类型包含不实现标记 trait 的内容。

标记 trait 在 Rust 中发挥着重要作用：它们允许你编写捕获代码中未直接表达的语义要求的边界。要求类型为 `Send` 的代码中没有对 `send` 的调用。相反，代码假设给定类型在单独的线程中使用是安全的，而如果没有标记 trait，编译器将无法检查该假设。这将取决于程序员记住假设并非常仔细地阅读代码，而我们都知道这不是我们希望依赖的东西。那条道路布满了数据竞争、段错误和其他运行时问题。

与标记 trait 类似的是 *标记类型*。这些是单元类型（像 `struct MyMarker;`）不持有数据也没有方法。标记类型用于，嗯，标记一个类型处于特定状态。当你希望使用户无法误用 API 时，它们非常有用。例如，考虑一个像 `SshConnection` 这样的类型，它可能尚未经过身份验证。你可以向 `SshConnection` 添加一个泛型类型参数，然后创建两个标记类型：`Unauthenticated` 和 `Authenticated`。当用户首次连接时，他们会得到 `SshConnection<Unauthenticated>`。在其 `impl` 块中，你只提供一个方法：`connect`。`connect` 返回一个 `SshConnection<Authenticated>`，并且只有在该 `impl` 块中你才提供运行命令等剩余方法。我们将在第 4 章进一步研究这种模式。

## Existential Types

在 Rust 中，你很少需要在函数体中声明的变量的类型或你调用的方法的泛型参数的类型进行指定。这是因为 *类型推断*，编译器根据类型在代码中出现的上下文决定使用什么类型。编译器通常只为变量以及闭包的参数（和返回类型）推断类型；顶层定义如函数、类型、trait 和 trait 实现块都需要你显式命名所有类型。这有几个原因，但主要原因是当你至少有一些已知的起点时，类型推断会容易得多。然而，并非总是容易，甚至可能完全不可能完全命名一个类型！例如，如果你从函数返回一个闭包，或从 trait 方法返回一个 async 块，其类型没有一个你可以输入到代码中的名称。

为了处理这种情况，Rust 支持 *存在类型*。很可能，你已经见过存在类型在行动。所有标记为 `async fn` 或返回类型为 `impl Trait` 的函数都有一个存在返回类型：签名没有给出返回值的真实类型，只是提示函数返回 *某个* 实现调用者可以依赖的一组 trait 的类型。并且至关重要的是，调用者只能依赖返回类型实现这些 trait，而不能依赖其他任何东西。

> NOTE
> 技术上来说，并不严格正确地说调用者只依赖返回类型而没有其他依赖。编译器还会将 `Send` 和 `Sync` 等自动 trait 通过返回位置的 `impl Trait` 传播。我们将在下一章更详细地研究这个问题。

这种行为就是存在类型名称的由来：我们断言存在某个与签名匹配的具体类型，并将找到该类型的工作留给编译器。编译器通常会通过对函数体应用类型推断来弄清楚这一点。





并非所有 impl Trait 的实例都使用 existential types。如果你将 impl Trait 用在函数的参数位置，它实际上只是该函数的一个未命名泛型参数的简写。例如，fn foo(s: impl ToString) 基本上只是 fn foo<S: ToString>(s: S) 的语法糖。

Existential types 在实现带有关联类型的 trait 时特别有用。例如，想象你在实现 IntoIterator trait。它有一个关联类型 IntoIter，用于保存该类型可以被转换为的迭代器的类型。有了 existential types，你就不需要为 IntoIter 定义一个单独的迭代器类型。相反，你可以将关联类型写成 impl Iterator<Item = Self::Item>，然后在 fn into_iter(self) 内部写一个求值为 Iterator 的表达式，例如通过对某个现有迭代器类型使用 map 和 filter。

Existential types 还提供了一个超越单纯便利性的特性：它们允许你执行零成本的类型擦除。不是仅仅因为它们出现在某个公共签名中就导出辅助类型——迭代器和 future 就是常见的例子——你可以使用 existential types 来隐藏底层具体类型。你的接口的使用者只能看到相关类型实现的相关 trait，而具体类型则作为实现细节保留下来。这不仅简化了接口，而且还使你能够在未来随意更改该实现，而不会破坏下游代码。

## Summary

本章对 Rust 类型系统进行了全面回顾。我们既研究了编译器如何在内存中体现类型，也研究了它如何对类型本身进行推理。这对于编写 unsafe 代码、复杂的应用接口以及后续章节中的异步代码而言是非常重要的背景知识。你还会发现，本章中的许多类型推理也影响着你如何设计 Rust 代码接口，我们将在下一章中介绍这一点。

## Common Traits for Types

Rust 中的用户还会做出一个主要假设，即接口中的一切都“只需工作”。他们期望能够使用 {:?} 打印任何类型，并将任何东西发送到另一个线程，并且他们期望每个类型都是 Clone。在可能的情况下，我们应再次避免让用户感到惊讶，并在不需要立即使用时也积极实现大多数标准 trait。

由于第 3 章中讨论的 coherence 规则，编译器不会允许用户在需要时为这些 trait 实现。用户不被允许为外来的类型（如你接口中的类型）实现外来的 trait（如 Clone）。他们反而需要将你的接口类型包装在自己的类型中，即使这样，在没有访问该类型内部结构的情况下，编写合理的实现也可能相当困难。

这些标准 trait 中首要的是 Debug trait。几乎每种类型都可以，也应该实现 Debug，即使它只打印类型的名称。使用 #[derive(Debug)] 通常是实现接口中 Debug trait 的最佳方式，但请记住，所有派生的 trait 都会自动为任何泛型参数添加相同的 bound。你也可以通过利用 fmt::Formatter 上的各种 debug_helpers 来自行编写实现。

紧随其后的是 Rust 的 auto-traits Send 和 Sync（以及在较小程度上 Unpin）。如果一个类型未实现这些 trait 中的一个，那应该有非常充分的理由。未实现 Send 的类型不能放入 Mutex 中，也不能在包含线程池的应用程序中甚至间接使用。未实现 Sync 的类型不能通过 Arc 共享，也不能放在静态变量中。用户已经习惯于类型在这些上下文中“只需工作”，尤其是在异步世界中几乎所有内容都在线程池上运行，如果你不确保你的类型实现了这些 trait，他们会感到沮丧。如果你的类型无法实现它们，请确保这一事实及其原因得到充分记录！

接下来的一组几乎通用的 trait 你应该实现的是 Clone 和 Default。这些 trait 可以轻松派生或实现，并且对大多数类型来说都有意义。如果你的类型无法实现这些 trait，请务必在文档中指出，因为用户通常期望能够轻松创建更多（和新的）类型的实例。如果他们不能，他们会感到惊讶。

在预期 trait 层级中更进一步的是比较 trait：PartialEq、PartialOrd、Hash、Eq 和 Ord。PartialEq trait 尤其可取，因为用户在某个时候不可避免地会有两个你的类型的实例，他们希望使用 == 或 assert_eq! 进行比较。即使你的类型仅在同一实例时才相等，实现 PartialEq 也值得去做，以便你的用户可以使用 assert_eq!。

PartialOrd 和 Hash 更为专门，可能适用范围不那么广，但只要有可能，你也希望实现它们。这对于用户可能用作 map 中的键的类型，或他们可能使用 std::collection 中的任何集合类型去去重的类型尤其正确，因为它们往往需要这些 bound。Eq 和 Ord 在实现类型的比较操作上比 PartialEq 和 PartialOrd 有额外的语义要求。这些在这些 trait 的文档中都有很好的记录，只有当你确定这些语义确实适用于你的类型时才应实现它们。

最后，对于大多数类型，实现 serde crate 的 Serialize 和 Deserialize trait 是有意义的。这些可以轻松派生，并且 serde_derive crate 甚至提供了仅重写一个字段或枚举变体的序列化的机制。由于 serde 是一个第三方 crate，你可能不希望在上面添加必需的依赖。大多数库因此选择提供一个 serde feature，仅在用户选择加入时才添加对 serde 的支持。

你可能会想知道为什么我没有在本节中包含可派生的 trait Copy。Copy 与提到的其他 trait 有两点不同。首先，用户通常并不期望类型是 Copy；恰恰相反，他们倾向于期望如果想要某物的两个副本，就必须调用 clone。Copy 改变了移动给定类型值的语义，这可能会让用户感到惊讶。这与第二个观察相关：类型很容易不再是 Copy，因为 Copy 类型受到严格限制。一个起初简单的类型很容易最终需要持有 String 或其他非 Copy 类型。如果发生这种情况，并且你必须移除 Copy 实现，那是一个向后不兼容的更改。移除 Clone 实现的情况要少得多，因此这是一个负担更小的承诺。

## Ergonomic Trait Implementations

Rust 不会自动为实现了 trait 的类型的引用实现 trait。换句话说，你通常不能用 &Bar 调用 fn foo<T: Trait>(t: T)，即使 Bar: Trait。这是因为 Trait 可能包含接收 &mut self 或 self 的方法，而这些方法显然不能在 &Bar 上调用。尽管如此，这种行为对于看到 Trait 只有 &self 方法的用户来说可能非常令人惊讶！

因此，当你定义一个新的 trait 时，你通常希望为 &T where T: Trait、&mut T where T: Trait 以及 Box<T> where T: Trait 提供适当的 blanket 实现，具体取决于 Trait 的方法接收者是什么。你可能只能实现其中一些，具体取决于 Trait 方法的接收者。标准库中的许多 trait 都有类似的实现，正是因为这会让用户感到更少惊讶。

迭代器是另一个你通常希望在类型的引用上专门添加 trait 实现的案例。对于任何可以迭代的类型，请考虑为 &MyType 和 &mut MyType 在适用时实现 IntoIterator。这使得 for 循环开箱即用地与你类型的借用实例一起工作，就像用户期望的那样。

## Wrapper Types

Rust 在经典意义上没有对象继承。然而，Deref trait 及其表亲 AsRef 都提供了一种有点像继承的东西。这些 trait 允许你拥有类型 T 的值，并通过在 T 类型的值上直接调用它们来调用类型 U 的方法，如果 T: Deref<Target = U>。这对用户来说感觉像魔法，通常非常棒。




需求是对代码使用方式的限制，而承诺则是关于代码使用方式的保证。在设计新接口时，你需要仔细思考这份契约。一个好的经验法则是：避免施加不必要的限制，并且只做出你能够兑现的承诺。增加限制或移除承诺通常需要一次主版本号的语义化版本变更，并且很可能会破坏其他地方的代码。反之，放宽限制或增加新的承诺通常可以向后兼容。

在 Rust 中，限制通常以 trait 约束和参数类型的形式出现，承诺则以 trait 实现和返回类型的形式出现。例如，比较清单 4-1 中的三个函数签名。

```
fn frobnicate1(s: String) -> String
fn frobnicate2(s: &str) -> Cow<'_, str>
fn frobnicate3(s: impl AsRef<str>) -> impl AsRef<str>
```

清单 4-1：契约不同的相似函数签名

这三个函数签名都接收一个字符串并返回一个字符串，但它们是在截然不同的契约下完成这一点的。

第一个函数要求调用者以 `String` 类型的形式拥有该字符串，并承诺返回一个拥有的 `String`。由于该契约要求调用者进行分配，并要求我们返回一个拥有的 `String`，我们日后无法以向后兼容的方式让这个函数变成零分配。

第二个函数放宽了契约：调用者可以提供任何字符串引用，因此用户不再需要分配内存或放弃对 `String` 的所有权。它还承诺返回一个 `std::borrow::Cow`，这意味着它既可以返回字符串引用，也可以返回拥有的 `String`，具体取决于它是否需要拥有该字符串。这里的承诺是函数将始终返回一个 `Cow`，这意味着我们日后不能将其改为使用其他优化的字符串表示形式。调用者还必须专门提供一个 `&str`，因此如果他们拥有一个预先存在的 `String`，就必须先将其解引用为 `&str` 才能调用我们的函数。

第三个函数解除了这些限制。它只要求用户传入一个能产生字符串引用的类型，并且只承诺返回值能产生字符串引用。

这些函数签名中没有哪一个比其他的更好。如果你在函数中需要拥有一个字符串，可以使用第一种参数类型来避免额外的字符串拷贝。如果你希望允许调用者利用已分配并返回拥有字符串的情况，那么第二个返回类型为 `Cow` 的函数可能是一个不错的选择。不过，我希望你从中明白的是：你应该仔细思考你的接口会把你绑定到怎样的契约上，因为事后更改它可能会造成破坏。

在本节的剩余部分，我会给出一些经常出现的接口设计决策示例，以及它们对你的接口契约的影响。

## 泛型参数

你的接口必须对用户施加的一个明显需求是：他们必须为你的代码提供哪些类型。如果你的函数明确接受一个 `Foo`，用户就必须拥有并交给你一个 `Foo`。这没有其他办法。在大多数情况下，使用泛型而不是具体类型是值得的，这样可以允许调用者传入任何符合函数实际需求的类型，而不仅仅是某个特定类型。将清单 4-1 中的 `&str` 改为 `impl AsRef<str>` 就是这类放宽操作的一个例子。以这种方式放宽需求的一种做法是：先让参数完全不带约束地使用泛型，然后跟随编译器的错误提示，找出需要添加的约束。

然而，如果走到极端，这种方法会让每个函数的每个参数都变成各自的泛型类型，这既难以阅读又难以理解。对于究竟何时应该或不应该将某个参数设为泛型，并没有硬性规定，所以请运用你的最佳判断。一个好的经验法则是：如果你能想到用户可能合理地、频繁地想要使用其他类型来代替你最初使用的具体类型，那就将该参数设为泛型。

你可能还记得第 3 章中提到的：泛型代码会通过单态化，为每一种使用过的类型组合进行复制。想到这一点，让大量参数变成泛型的想法可能会让你担心二进制文件过大。在第 3 章中我们还讨论了如何通过动态分发来缓解这一问题，而代价（通常是可忽略不计的）是性能损失，这一点在这里同样适用。

对于你本来就通过引用接收的参数（回想一下，`dyn Trait` 不是 `Sized`，你需要一个胖指针才能使用它们），你可以轻松地把泛型参数替换为使用动态分发的参数。例如，你可以使用 `&dyn AsRef<str>` 而不是 `impl AsRef<str>`。

不过，在你急着这么做之前，有几点需要考虑。首先，你是在代表你的用户做这个选择，他们无法选择不使用动态分发。如果你知道你应用动态分发的代码永远不会对性能敏感，那也许没问题。但如果某个用户想在高性能应用中使用你的库，那么在一个热循环中调用的函数里使用动态分发可能会成为交易破坏者。其次，在撰写本文时，只有当你有一个像 `T: AsRef<str>` 或 `impl AsRef<str>` 这样的简单 trait 约束时，动态分发才有效。对于更复杂的约束，Rust 不知道如何构造动态分发的 vtable，因此你不能使用例如 `&dyn Hash + Eq`。最后，请记住，使用泛型时，调用者总是可以通过传入一个 trait 对象来自己选择动态分发。反过来则不成立：如果你接收一个 trait 对象，调用者就必须提供 trait 对象。

你可能会想先用具体类型来设计接口，然后再逐步泛型化。这可以行得通，但请记住，这类更改不一定向后兼容。为了理解原因，想象一下你把一个函数从 `fn foo(v: &Vec<usize>)` 改为 `fn foo(v: impl AsRef<[usize]>)`。虽然每个 `&Vec<usize>` 都实现了 `AsRef<[usize]>`，但类型推断仍然可能给用户带来问题。考虑一下如果调用者调用 `foo(&iter.collect())` 会发生什么。在原始版本中，编译器可以确定应该收集到一个 `Vec` 中，而现在它只知道需要收集到某个实现了 `AsRef<[usize]>` 的类型中。而这样的类型可能不止一种，因此经过这一更改，调用者的代码将无法再编译！

## 对象安全

当你定义一个 trait 时，该 trait 是否对象安全（参见第 3 章“编译与分发”一节的末尾，第 XX 页）是该 trait 契约中一个不成文的部分。如果 trait 是对象安全的，用户就可以使用 `dyn Trait` 将实现了该 trait 的不同类型当作一个共同的类型来处理。如果不是，编译器将不允许为该 trait 使用 `dyn Trait`。你应该更倾向于让你的 trait 保持对象安全，即使这会稍微牺牲一些使用上的便利性（例如用 `impl AsRef<str>` 而不是 `&str`），因为对象安全可以为使用你的 trait 开辟新的方式。如果你的 trait 必须有一个泛型方法，请考虑它的泛型参数是否可以放在 trait 本身上，或者它的泛型参数是否也可以使用动态分发来保持 trait 的对象安全性。另外，你还可以在该方法上添加 `where Self: Sized` 的 trait 约束，这样该方法就只能通过 trait 的具体实例（而不能通过 `dyn Trait`）来调用。你可以在 `Iterator` 和 `Read` trait 中看到这种模式的例子，它们都是对象安全的，但在具体实例上提供了一些额外的便捷方法。

对于为了保护对象安全你愿意做出多少牺牲，并没有一个统一的答案。我的建议是：考虑你的 trait 将如何被使用，以及用户想要将其作为 trait 对象来使用是否有意义。如果你认为用户很可能想要将你的 trait 的许多不同实例放在一起使用，那么你就应该比在认为这种用例不太合理的情况下更加努力地提供对象安全。例如，动态分发对 `FromIterator` trait 没什么用，因为它的唯一方法不接收 `self`，所以你一开始就无法构造一个 trait 对象。同样地，`std::io::Seek` 单独作为 trait 对象也没什么用处，因为你用这种 trait 对象唯一能做的就是 seek，而无法读或写。

> **DROP TRAIT 对象**
>
> 你可能会认为 `Drop` trait 作为 trait 对象也没什么用，因为你用 `Drop` 作为 trait 对象唯一能做的就是丢弃它。但事实证明，有些库专门就是想要能够丢弃任意类型。例如，一个提供延迟丢弃值的库，比如用于并发垃圾回收或仅仅是延迟清理，它只关心这些值能否被



被丢弃，且没有其他操作。有趣的是，Drop 的故事并不止于此；由于 Rust 需要能够丢弃 trait 对象，因此每个 vtable 都包含 drop 方法。有效地，每个 dyn Trait 也都是一个 dyn Drop。

请记住，对象安全是你的公共接口的一部分！如果你以向后兼容的方式修改 trait，例如添加一个具有默认实现的方法，但这使得 trait 不再对象安全，你需要提升你的主版本号。

## 借用 vs. 所有权

对于你在 Rust 中定义的几乎每个函数、trait 和类型，你都必须决定它是否应该拥有其数据，或仅持有对数据的引用。你所做的决定将对接口的易用性和性能产生深远的影响。幸运的是，这些决定通常会自行做出。

如果你的代码需要数据的所有权，例如调用接收 self 的方法或将数据移动到另一个线程，它必须存储所有权数据。当你的代码必须拥有数据时，它通常也应让调用者提供所有权数据，而不是通过引用接收值然后克隆它们。这让调用者控制分配，并且它明确说明了使用该接口的成本。

另一方面，如果你的代码不需要拥有数据，它应改为操作引用。其中一个常见的例外是像 i32、bool 或 f64 这样的小类型，它们直接存储和复制的成本与通过引用存储一样低廉。不过要小心不要假设这对所有 Copy 类型都成立；[u8; 8192] 是 Copy，但到处存储和复制它会很昂贵。

当然，在现实世界中，事情往往没有那么清晰。有时，你事先并不知道你的代码是否需要拥有数据。例如，String::from_utf8_lossy 只有在传入的字节序列包含无效的 UTF-8 序列时才需要接管所有权。在这种情况下，Cow 类型就是你的朋友：它允许你在数据允许时操作引用，并在必要时生成一个拥有值。

其他时候，引用生命周期使接口变得如此复杂以至于使用起来很痛苦。如果你的用户在你的接口之上编写代码时难以让代码编译通过，这就是一个信号，表明你可能想要（即使是不必要地）接管某些数据的所有权。如果你这样做，先从那些便宜克隆或不属于性能敏感部分的数据开始，然后再决定是否要堆分配可能是一个巨大的字节块。

## 可能失败且阻塞的析构函数

以 I/O 为中心的类型的析构时通常需要执行清理工作。这可能包括将写入刷新到磁盘、关闭文件，或优雅地终止与远程主机的连接。执行此清理的自然位置是在类型的 Drop 实现中。不幸的是，一旦值被丢弃，我们除了 panic 之外就再也没有办法向用户传达错误。类似的问题出现在异步代码中，在那里我们希望在有待处理工作时完成收尾。drop 被调用时，executor 可能正在关闭，我们没有办法做更多工作。我们可以尝试启动另一个 executor，但这会带来自己的问题，例如在异步代码中阻塞，正如我们在第 9 章中将看到的那样。

这些问题没有完美的解决方案，无论我们做什么，一些应用程序不可避免地会回退到我们的 Drop 实现。因此，我们需要通过 Drop 提供尽力而为的清理。如果清理出错，至少我们尝试过了——我们吞掉错误并继续。如果 executor 仍然可用，我们可能会 spawn 一个 future 来执行清理，但如果它永远无法运行，我们也尽力了。

然而，我们应该为希望不留下任何松散线程的用户提供更好的替代方案。我们可以通过提供显式的析构函数来做到这一点。这通常采用接收 self 所有权并暴露固有错误（使用 -> Result<_, _>）或异步性（使用 async fn）的形式。谨慎的用户随后可以使用该方法优雅地拆除任何相关资源。

> NOTE 确保你在文档中突出显示显式的析构函数！

一如既往，存在权衡。一旦你添加了显式的析构函数，你会遇到两个问题。首先，由于你的类型实现了 Drop，你就不能在析构函数中从该类型的任何字段中移出。这是因为 Drop::drop 在你的显式析构函数运行后仍会被调用，而它接收 &mut self，这要求 self 的任何部分都未被移动。其次，drop 接收 &mut self，而不是 self，所以你的 Drop 实现不能简单地调用你的显式析构函数并忽略其结果（因为它不拥有 self）。解决这些问题的办法有几种，没有一种是完美的。

第一种方法是让你的顶层类型成为一个 newtype 包装器，包装一个 Option，而 Option 又持有某个内部类型，该内部类型持有类型的所有字段。你可以在两个析构函数中都使用 Option::take，并在内部类型尚未被取出时调用内部类型的显式析构函数。由于内部类型未实现 Drop，你可以在那里接管所有字段的所有权。这种方法的缺点是，你希望在顶层类型上提供的所有方法现在都必须包含代码来穿过 Option（你知道它在 drop 尚未被调用时始终是 Some）以访问内部类型的字段。

第二个变通方法是让你的每个字段都 *可取出*。你可以通过将其替换为 None 来“取出”一个 Option（这就是 Option::take 所做的），但你也可以对许多其他类型这样做。例如，你可以通过简单地将它们替换为其廉价构造的默认值来取出 Vec 或 HashMap——std::mem::take 就是你的朋友。这里的方法在你的类型具有合理的“空”值时效果很好，但在你必须将几乎每个字段都包装在 Option 中，然后用匹配的 unwrap 修改这些字段的每个访问时就会变得繁琐。

第三个选项是将数据放在 ManuallyDrop 类型内部，该类型解引用为内部类型，因此无需 unwrap。你也可以在 drop 中使用 ManuallyDrop::take 在销毁时接管所有权。这种方法的主要缺点是 ManuallyDrop::take 是不安全的。没有任何安全机制来确保你不会在调用 take 之后尝试使用 ManuallyDrop 内部的值，或多次调用 take。如果你这样做，你的程序将静默地表现出未定义行为，坏事就会发生。

最终，你应该选择最适合你的应用程序的方法。我会倾向于采用第二个选项，只有当你发现自己陷入 Option 的海洋时才切换到其他方法。ManuallyDrop 解决方案在代码足够简单以便你能轻松检查代码的安全性，并且你对自己的能力有信心时是优秀的。

## 显而易见

虽然一些用户可能熟悉支撑你的接口的实现方面的内容，但他们不太可能理解其所有规则和限制。他们不会知道在调用 bar 之后调用 foo 永远是不允许的，或只有在月亮处于 47 度角且过去 18 秒内没有人打喷嚏时调用 unsafe 方法 baz 才是安全的。只有当接口明确表明有些奇怪的事情正在发生时，他们才会去查阅文档或仔细阅读类型签名。因此，对你来说，让用户尽可能容易理解你的接口并尽可能难以错误使用它至关重要。你为此拥有的两个主要技术是你的文档和类型系统，让我们依次来看一下。

> NOTE 你也可以利用命名来提示用户接口中还有超出表面之外的东西。如果用户看到一个名为 dangerous 的方法，他们很可能会阅读其文档。

## 文档

使你的接口透明的第一步是编写良好的文档。我可以写一整本书专门讲如何写文档，但让我们在这里专注于 Rust 特定的建议。

首先，清楚地记录任何你的代码可能做一些意外的操作的情况，或依赖用户做超出类型签名所规定的事情。panic 就是两者兼有的一个好例子。




这些情况下：如果你的代码可能 panic，请记录这一事实，以及它可能 panic 的具体情形。同样，如果你的代码可能返回错误，请记录返回错误的情形。对于 unsafe 函数，请记录调用者必须保证什么，调用才是安全的。

其次，在 crate 和模块级别为你的代码提供端到端的使用示例。这些比特定类型或方法的示例更重要，因为它们能让用户体会到所有内容是如何组合在一起的。当开发人员对接口结构有了较好的高层理解后，他们可能很快就会意识到特定的方法和类型是做什么的，以及应该在何处使用它们。端到端示例还为用户提供了定制用法的起点；他们可以——而且通常会——复制粘贴示例，然后根据自己的需求进行修改。这种“在做中学”的方式往往比让他们尝试从零散组件中拼凑出内容更有效。

**注意** 那些高度针对某个方法的示例，比如展示 len 方法确实返回长度的示例，不太可能向用户传达任何有关你代码的新信息。

第三，组织好你的文档。如果你所有的类型、trait 和函数都放在一个顶层模块中，用户将很难知道从哪里开始。要利用模块将语义相关的项目组合在一起。然后，使用文档内链接将这些项目互相关联起来。如果关于类型 A 的文档提到了 trait B，那么就应该在那里直接链接到该 trait。如果你让用户能够轻松探索你的接口，他们就不太可能错过重要的关联或依赖。同时，考虑使用 `#[doc(hidden)]` 标记那些并非有意公开、但由于历史原因而需要保留的接口部分，以免它们使你的文档变得杂乱。

最后，尽可能丰富你的文档。链接到能够解释概念、数据结构、算法或接口其他方面的外部资源，这些内容可能在其他地方已有很好的说明。如果有相关的话，RFC、博客文章和白皮书都是很好的选择。使用 `#[doc(cfg(...))]` 来突出显示仅在特定配置下可用的项目，以便用户很快意识到为什么文档中列出的某个方法不可用。使用 `#[doc(alias = "...")]` 让类型和方法能够通过用户可能搜索的其他名称被发现。在顶层文档中，向用户指出常用的模块、功能、类型、trait 和方法。

## 类型系统指导

类型系统是一个极好的工具，可以确保你的接口清晰明了、自我文档化且不易被误用。你可以使用多种技术，让你的接口很难被误用，从而更有可能被正确使用。

其中第一种是语义类型化（semantic typing），即添加类型来表示值的含义，而不仅仅是其原始类型。这里经典的例子是布尔值：如果你的函数接受三个 bool 参数，很可能某个用户会弄错值的顺序，直到出了大问题才意识到。另一方面，如果它接受三个参数，而这三个参数是三种不同的两变体枚举类型，那么用户不可能在不被编译器警告的情况下弄错顺序：如果他们试图将 `DryRun::Yes` 传递给 overwrite 参数，那根本行不通，将 `Overwrite::No` 作为 dry_run 参数也同样行不通。你也可以在布尔值之外应用语义类型化。例如，在数值类型上创建一个 newtype，可以为其中包含的值提供单位，或者将原始指针参数限制为仅接受由另一个方法返回的那些指针。

一种密切相关的技术是使用零大小类型（zero-sized type）来表明某个类型的实例具有某个特定的事实。例如，考虑一个名为 Rocket 的类型，它表示真实火箭的状态。无论火箭处于什么状态，Rocket 的某些操作（方法）都应该可用，但有些操作只在特定情况下才有意义。例如，如果火箭已经发射过，就不可能再次发射。同样，如果火箭尚未发射，可能也不应该能够分离燃料箱。我们可以将这些状态建模为枚举变体，但那样所有方法在每个阶段都可用，而且我们需要引入可能的 panic。

相反，如清单 4-2 所示，我们可以在 Rocket 上引入一个泛型参数 Stage，并用它来限制哪些方法在何时可用。

```
① struct Grounded;
struct Launched;
// and so on
struct Rocket<Stage = Grounded> {
② stage: std::marker::PhantomData<Stage>,
}

③ impl Default for Rocket<Grounded> {}
impl Rocket<Grounded> {
    pub fn launch(self) -> Rocket<Launched> { }
}
④ impl Rocket<Launched> {
    pub fn accelerate(&mut self) { }
    pub fn decelerate(&mut self) { }
}

⑤ impl<Stage> Rocket<Stage> {
    pub fn color(&self) -> Color { }
    pub fn weight(&self) -> Kilograms { }
}
```

清单 4-2：使用标记类型来限制实现

我们引入单元类型来表示火箭可能处于的每个阶段 ①。我们实际上并不需要存储阶段本身——只需要它提供的元信息——因此我们将其存储在 PhantomData ② 后面，以确保它在编译时被消除。然后，我们仅为持有特定类型参数的 Rocket 编写实现块。你目前只能在地面上构建火箭，并且只能从地面发射它 ③。只有火箭发射后，你才能控制它的速度 ④。无论火箭处于什么状态，有些事情你总是可以做的，我们将这些操作放在一个泛型实现块 ⑤ 中。你会注意到，通过这种方式设计的接口，用户根本不可能在错误的时间调用某个方法——我们已经将使用规则编码到了类型本身，并使得非法状态无法被表示。

这个概念也适用于许多其他领域；如果你的函数只有在给定的布尔参数为 true 时才使用某个指针参数，那么最好将这两个参数合并起来。使用一个枚举类型，其中一个变体表示 false（且不包含指针），另一个变体表示 true 并持有指针，这样调用者和实现者都不会误解这两者之间的关系。这是一个强大的思路，我非常鼓励你加以利用。

另一个让接口清晰明了的小而实用的工具是 `#[must_use]` 注解。将它添加到任何类型、trait 或函数上后，如果用户的代码接收了该类型或 trait 的元素，或者调用了该函数，却没有显式地处理它，编译器就会发出警告。你可能已经在 Result 的上下文中见过这种情况：如果一个函数返回 Result，而你没有在某个地方赋值其返回值，就会收到编译器警告。不过，要注意不要过度使用这个注解——只有当用户不使用返回值时非常可能出错的情况下，才添加它。

## 约束

随着时间推移，总会有用户依赖于你接口的每一个属性，无论是 bug 还是特性。对于公开可用的库来说尤其如此，因为你无法控制你的用户。因此，在做出对用户可见的更改之前，你应该仔细考虑。无论你是添加新的类型、字段、方法或 trait 实现，还是修改现有的这些，你都需要确保该更改不会破坏现有用户的代码，并且你计划长期保留这一更改。频繁的不向后兼容更改（语义化版本中的主版本号增加）必然会招致用户的愤怒。

许多不向后兼容的更改是显而易见的，比如重命名公共类型或删除公共方法，但有些则更为微妙，并且与 Rust 的工作方式紧密相关。在这里，我们将介绍一些更棘手的细微更改，以及如何为它们做好规划。你会看到，需要在某些更改与你希望接口具备的灵活性之间进行权衡——有时候，必须有所舍弃。

### 类型修改

删除或重命名公共类型几乎肯定会破坏某些用户的代码。为了应对这种情况，你应该尽可能利用 Rust 的可见性修饰符，比如 `pub(crate)` 和 `pub(in path)`。你拥有的公共类型越少，在不破坏现有代码的情况下，将来进行更改的自由度就越大。



不过，用户代码对你的类型的依赖方式不仅仅是名称。请看代码清单 4-3 中的公开类型以及该代码的给定用法。

```
```rust
// in your interface
pub struct Unit;
// in user code
let u = lib::Unit;
```
```

*代码清单 4-3：一个看起来无害的公开类型*

现在，考虑如果给 Unit 添加一个私有字段会发生什么。即使你添加的字段是私有的，这一更改仍会破坏用户代码，因为用户依赖的构造函数消失了。类似地，请考虑代码清单 4-4 中的代码及其用法。

```
```rust

pub struct Unit { pub field: bool };
// in user code
fn is_true(u: lib::Unit) -> bool {
    matches!(u, Unit { field: true })
}
```
```

*代码清单 4-4：访问单个公共字段的用户代码*

在这里，给 Unit 添加私有字段同样会破坏用户代码，这次是因为 Rust 的穷尽模式匹配检查逻辑能够看到用户看不到的部分接口。它能够识别出还有更多字段，即使这些字段用户代码无法访问，也会将用户的模式视为不完整而拒绝。如果我们将元组结构体转换为具有命名字段的普通结构体，也会出现类似的问题：即使字段本身完全相同，任何旧模式都将不再适用于新的类型定义。

Rust 提供了 `#[non_exhaustive]` 属性来帮助缓解这些问题。你可以将它添加到任何类型定义上，编译器将禁止在该类型上使用隐式构造函数（如 `lib::Unit { field1: true }`）和非穷尽模式匹配（即没有尾部 `, ..` 的模式）。如果你怀疑某个特定类型将来可能会被修改，添加这个属性是很好的做法。不过，它确实会限制用户代码，例如剥夺用户依赖穷尽模式匹配的能力，因此如果你认为某个类型可能会保持稳定，应避免添加它。

## trait 实现

回顾第 3 章，Rust 的一致性规则禁止同一类型对同一 trait 有多个实现。由于我们不知道下游代码可能已经添加了哪些实现，为现有 trait 添加覆盖实现通常是一个破坏性变更。同样，为现有类型实现外部 trait，或为外部类型实现现有 trait，也是如此——在这两种情况下，外部 trait 或类型的所有者可能会同时添加一个冲突的实现，因此这必然是一个破坏性变更。

移除一个 trait 实现是破坏性变更，但为新类型实现 trait 从来都不是问题，因为没有任何 crate 会包含与该类型冲突的实现。

也许与直觉相反，你也需要小心为现有类型实现任何 trait。为了解原因，请考虑代码清单 4-5 中的代码。

```
// crate1 1.0
pub struct Unit;
pub trait Foo1 { fn foo(&self) }
// note that Foo1 is not implemented for Unit

// crate2; depends on crate1 1.0
use crate1::{Unit, Foo1};
trait Foo2 { fn foo(&self) }
impl Foo2 for Unit { ... }
fn main() {
    Unit.foo();
}
```

*代码清单 4-5：为现有类型实现 trait 可能会导致问题。*

如果你在 crate1 中为 Unit 添加 impl Foo1 for Unit，但不将其标记为破坏性变更，下游代码将突然无法编译，因为对 foo 的调用现在变得不明确了。如果下游 crate 使用了通配符导入（use crate1::*），这种情况甚至可能适用于新公共 trait 的实现。如果你提供了一个 prelude 模块，并指示用户使用通配符导入，那么你尤其需要牢记这一点。

对现有 trait 的大多数更改也都是破坏性变更，例如更改方法签名或添加新方法。更改方法签名会破坏该 trait 的所有实现，还可能破坏许多使用；而添加新方法“只是”破坏所有实现。不过，添加带有默认实现的新方法是可以的，因为现有实现将继续适用。

我在这里说“一般而言”和“大多数”，是因为作为接口作者，我们有一个工具可以用来规避其中一些规则：密封 trait。密封 trait 是一种其他 crate 只能使用而不能实现的 trait。这立即使许多破坏性变更变为非破坏性。例如，你可以向密封 trait 添加新方法，因为你已知当前 crate 之外没有需要考虑的实现。类似地，你可以为新的外部类型实现密封 trait，因为你已知定义该类型的外部 crate 不可能添加冲突的实现。

密封 trait 最常见的用途是用于派生 trait——即为实现了特定其他 trait 的类型提供覆盖实现的 trait。只有在密封某个 trait 对外部 crate 没有意义时，才应该将其密封。

如果你的 crate 从 itercrate 1.0 升级到 itercrate 2.0，但除此之外没有其他变化，本清单中的代码将不再编译。即使没有类型发生变化，编译器也会（正确地）认为 itercrate1.0::Empty 和 itercrate2.0::Empty 是不同的类型。因此，你不能将后者赋值给前者，这会使你的接口发生破坏性变更。

为了缓解此类问题，通常最好使用 newtype 模式包装外部类型，然后只暴露你认为有用的外部类型部分。在许多情况下，你可以完全避免 newtype 包装，使用 impl Trait 只向调用者提供最小的契约。承诺得越少，破坏性变更就越少。

## SemVer 技巧

itercrate 这个例子可能会让你感到不快。如果 Empty 类型没有改变，那么为什么编译器不允许任何使用它的代码继续工作，无论代码使用的是 1.0 还是 2.0 版本？答案是……很复杂。归根结底，Rust 编译器并不会仅仅因为两个类型具有相同的字段就认为它们是同一类型。举个简单的例子，假设 itercrate 2.0 为 Empty 添加了 #[derive(Copy)]。现在，根据你使用的是 1.0 还是 2.0，该类型会突然具有不同的移动语义！而针对其中一种版本编写的代码，将与另一种版本不兼容。

这个问题往往出现在大型、广泛使用的库中，在这些库中，随着时间的推移，破坏性变更很可能不得不发生在 crate 的某个地方。不幸的是，语义化版本控制发生在 crate 级别，而不是类型级别，因此任何一处的破坏性变更都是全局性的破坏性变更。

但并非全无希望。几年前，David Tolnay（serde 的作者，同时也是 Rust 生态众多其他贡献的作者）想出了一个巧妙的方法来应对这种情况。他称之为“semver 技巧”。其想法很简单：如果某个类型 T 在一次破坏性变更中保持不变（例如从 1.0 到 2.0），那么在发布 2.0 之后，你可以发布一个新的 1.0 次要版本，该版本依赖 2.0，并将 T 替换为从 2.0 重新导出的 T。

通过这样做，你确保了在两个主版本中实际上只有一个类型 T。这反过来意味着，任何依赖 1.0 的 crate 都将能够使用来自 2.0 的 T，反之亦然。而且由于这只发生在你使用此技巧显式选择的类型上，那些实际上属于破坏性的变更仍将继续保持破坏性。
