## 示例 8-2. 在 Python 中使用 SQLAlchemy 运行 SQL 查询

```
from sqlalchemy import create_engine, text

engine = create_engine('sqlite:///thunderbird_manufacturing.db')
conn = engine.connect()

stmt = text("SELECT * FROM CUSTOMER")
results = conn.execute(stmt)

for customer in results:
    print(customer)
```

## Pandas 和 NoSQL 呢？

我经常收到关于 SQL "替代品"（如 NoSQL 或 Pandas）的问题。这些实际上并非替代品，而是数据科学工具链中其他位置的不同工具。以 Pandas 为例。在示例 8-3 中，我可以创建一个 SQL 查询来从表 CUSTOMER 中提取所有记录，并将其放入 Pandas DataFrame 中。

## 示例 8-3. 将 SQL 查询导入 Pandas DataFrame

```
from sqlalchemy import create_engine, text
import pandas as pd

engine = create_engine('sqlite:///thunderbird_manufacturing.db')
conn = engine.connect()

df = pd.read_sql("SELECT * FROM CUSTOMER", conn)
print(df) # prints SQL results as DataFrame
```

在那里，SQL 被用来弥合关系型数据库与我的 Python 环境之间的差距，并将数据加载到 Pandas DataFrame 中。如果我有 SQL 能够处理的高要求计算，那么在数据库服务器上使用 SQL 进行处理，比在本地计算机上使用 Pandas 更高效。简单来说，Pandas 和 SQL 可以协同工作，并非竞争技术。

NoSQL 也是如此，它包括 Couchbase 和 MongoDB 等平台。虽然有些读者可能不同意并提出合理的论点，但我认为将 NoSQL 与 SQL 相比，就像是在比较苹果和橘子。是的，它们都存储数据并提供查询功能，但我不认为这使它们成为竞争对手。它们具有针对不同用例的不同特性。NoSQL 代表 "不仅仅是 SQL"，更适合存储非结构化数据，如图片或自由形式文本文章。SQL 更适合存储结构化数据。SQL 维护数据完整性的积极性高于 NoSQL，尽管这要以计算开销和较低的可扩展性为代价。

## SQL，数据世界的通用语言

2015 年，许多人曾猜测 NoSQL 和 Apache Spark 等分布式数据处理技术将取代 SQL 和关系型数据库。具有讽刺意味的是，SQL 对数据用户来说如此重要，以至于这些平台出于需求添加了 SQL 层。这些分层技术包括 Presto、BigQuery 和 Apache Spark SQL 等。大多数数据问题并非大数据问题，在查询数据方面，没有什么能像 SQL 那样有效。因此，SQL 继续蓬勃发展，并保持其作为数据世界通用语言的地位。

## 编程熟练度

通常，许多数据科学家并不擅长编码，至少没有达到软件工程师的水平。然而，他们具备编码能力变得越来越重要。这提供了一个获得竞争优势的机会。学习面向对象编程、函数式编程、单元测试、版本控制（例如 GIT 和 GitHub）、大 O 算法分析、密码学，以及你遇到的其他相关计算机科学概念和语言特性。

理由如下。假设你基于给定的一些示例数据创建了一个有前途的回归模型，比如逻辑回归或神经网络。你请求 IT 部门内部的程序员将其 "插入" 到现有软件中。

他们怀疑地审视你的提案。"我们需要用 Java 重写这个，而不是 Python，" 他们不情愿地说。"你的单元测试在哪里？" 另一个人问道。"你没有定义任何类或类型吗？我们必须将这段代码重构为面向对象的。" 此外，他们不理解你模型的数学原理，并且有理由担心它在未见过的数据上会表现异常。由于你没有定义单元测试（在机器学习中这并不容易），他们不确定如何验证模型的质量。他们还询问如何管理两个版本的代码（Python 和 Java）。

你开始感到手足无措，并说 "我不明白为什么 Python 脚本不能直接插入。" 其中一人若有所思地停顿了一下，回答说 "我们可以用 Flask 创建一个 Web 服务，从而避免用 Java 重写。然而，其他担忧并不会消失。然后我们还要担心可扩展性和高流量对 Web 服务的冲击。等等……也许我们可以将其部署到 Microsoft Azure 云作为虚拟机规模集，但我们仍然需要设计后端。听着，无论你采取什么方法，这都必须重新设计。"

这正是为什么许多数据科学家的工作从未离开他们的笔记本电脑。事实上，将机器学习投入生产变得如此难以捉摸，以至于近年来它成了独角兽和热门话题。数据科学家和软件工程师之间存在巨大的差距，因此数据科学专业人士自然面临着必须成为软件工程师的压力。

这听起来可能令人难以承受，因为数据科学的范围已经负荷过重，包含许多学科和要求。然而，这并非为了表明你需要学习 Java。你可以用 Python（或你偏好的任何实用语言）成为一名高效的软件工程师，但你必须精通它。学习面向对象编程、数据结构、函数式编程、并发以及其他设计模式。两本针对这些 Python 主题的好书包括 Luciano Ramalho 撰写的 *精通 Python，第 2 版* 和 Al Sweigart 撰写的 *超越 Python 基础*。

## Jupyter Notebooks 呢？

数据科学家经常因为编写糟糕的代码而名声不佳。这有很多原因，但一个可能的罪魁祸首可能是 Jupyter Notebooks 鼓励的工作流程。

你可能会想知道为什么我在这本书的整个过程中都没有使用（或鼓励使用）Jupyter Notebooks。Jupyter Notebooks 是一个流行的平台，用于编写数据科学代码，但它允许你将笔记、可运行的代码片段以及控制台/图表输出放在一个地方。它们可以是一个有用的工具，并提供了一种方便的方式来用数据讲述故事。

话虽如此，除非你的雇主要求，否则 Notebooks 并不是进行数据科学工作的必要条件。本书涵盖的所有内容都是在没有 Notebooks 的情况下使用纯 Python 完成的。我这样做是有意为之，因为我不想让读者承担设置额外工具的负担。这可能违背常规，但你可以在不接触 Notebooks 的情况下拥有健康的职业生涯。

理由如下：Notebooks 鼓励不良的编程习惯。Notebooks 鼓励强调线性而非模块化的工作流程，这意味着它们不利于编写可重用的代码。可重用性可以说是软件编程最基本的目标。此外，包含代码片段的 Notebook 单元可以按任意顺序运行，或多次重新运行。如果不小心，你可能会创建混乱的状态和错误，最好的情况是产生明显的错误，最坏的情况是产生不易被察觉的微妙计算错误。特别是如果你是初学者，这是一种令人沮丧的学习 Python 的方式，因为这些技术陷阱对新手来说并不明显。这也是一种提出并呈现发现的方式，却只能发现这是 bug 的结果，因此好得难以置信。

我并不主张避免使用 Notebooks。当然，如果它们能让你和你的工作场所开心，请大胆使用！然而，我主张不要过度依赖它们。Joel Grus（**从零开始学数据科学** 的作者
