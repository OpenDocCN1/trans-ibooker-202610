## Preface

当 O’Reilly 第一次找我写一本关于 Java 性能调优的书时，我心里没底。Java 性能，我想——这事不早就结束了？是的，我每天仍在努力提升 Java（和其他）应用程序的性能，但我喜欢认为我大部分时间都在处理算法低效和外部系统瓶颈，而不是直接与 Java 调优相关的事情。

稍作反思就让我意识到我（像往常一样）在自欺欺人。确实，端到端系统性能占据了我大量时间，我有时也会遇到代码使用 $O(n^2)$ 算法，而本可以用 $O(\log N)$ 性能的算法。尽管如此，事实证明我每天都在思考垃圾回收（GC）性能，或 JVM 编译器的性能，或如何从 Java API 中获得最佳性能。

这并不是要淡化过去二十多年里 Java 和 JVM 性能取得的巨大进步。当我在 1990 年代末在 Sun 做 Java 布道师时，唯一真正可用的“基准”就是 Pendragon 软件的 CaffeineMark 2.0。出于各种原因，该基准的设计很快限制了其价值；但在当时，我们喜欢告诉大家，根据该基准，Java 1.1.8 的性能是 Java 1.0 的八倍。事实确实如此——Java 1.1.8 有一个真正的即时编译器，而 Java 1.0 基本上是完全解释执行的。

随后，标准委员会开始开发更严格的基准，Java 性能开始围绕它们展开。结果是 JVM 的各个领域——垃圾回收、编译以及 API 内部——持续改进。当然，这一过程至今仍在继续，但性能工作的一个有趣事实是，它变得越来越困难。通过引入即时编译器实现八倍性能提升是直接的工程问题，即使编译器仍在改进，我们也不会再看到类似的提升。并行化垃圾回收器是一次巨大的性能提升，但最近的变化则更具增量性。

这对于应用程序来说是典型过程（JVM 本身也只是一个应用程序）：在项目初期，很容易找到架构变更（或代码错误），一旦解决，就会带来巨大的性能提升。在成熟的应用程序中，找到此类性能提升的情况很少。

这一原则是我最初担心工程界在很大程度上已经完成 Java 性能工作的原因。有几件事让我确信我错了。首先是我每天看到的关于 JVM 在某些情况下如何表现的众多问题。新工程师不断涌入 Java，而 JVM 的行为在某些领域仍然复杂到足以让操作指南仍然有益。其次是计算环境的变化似乎改变了工程师今天面临的性能关注点。

在过去几年里，性能关注点变得两极分化。一方面，能够运行具有非常大堆的 JVM 的非常大的机器现在很常见。JVM 已通过新的垃圾回收器（G1）来应对这些问题——作为一项新技术，它需要比传统回收器更多的手动调优。与此同时，云计算重新强调了小型单 CPU 机器的重要性：你可以去 Oracle 或 Amazon 或其他许多公司廉价租用一台单 CPU 机器来运行小型应用服务器。（你实际上并没有得到一台单 CPU 机器：你得到的是在一台非常大的机器上运行的虚拟操作系统映像，但该虚拟操作系统仅限于使用单个 CPU。从 Java 的角度来看，这与单 CPU 机器是一样的。）在这些环境中，正确管理少量内存变得非常重要。

Java 平台也在不断发展。Java 的每个新版本都提供新的语言特性和新的 API，以提高开发人员的工作效率——如果不总是提高其应用程序的性能。最佳实践使用这些语言特性可以帮助区分一个飞速运行的应用程序和一个缓慢运行的应用程序。而平台的演进也引发了有趣的性能问题：毫无疑问，使用 JSON 在两个程序之间交换信息比设计一个高度优化的专有协议要简单得多。为开发人员节省时间是一大胜利——但确保这一生产力提升带来性能提升（或至少持平）才是真正的目标。

### 谁应该（和不应该）阅读本书

本书面向希望了解 JVM 的各个方面以及 Java API 如何影响性能的性能工程师和开发人员。

如果你在星期天晚上很晚，网站将在星期一早上上线，而你正在寻找性能问题的快速修复方案，这本书不适合你。

如果你是性能分析的新手，并且正在 Java 中开始该分析，本书可以帮助你。当然，我的目标是提供足够的信息和背景，让新手工程师能够理解如何将基本的调优和性能原则应用于 Java 应用程序。然而，系统分析是一个广泛的领域。存在许多关于系统分析的优秀资源（这些原则当然也适用于 Java），从这个意义上说，本书理想情况下可以作为那些书籍的有用补充。

从根本上讲，让 Java 真正快速运行需要深入了解 JVM（和 Java API）实际的工作方式。存在数百个 Java 调优标志，调优 JVM 不能仅仅是盲目尝试它们并看看什么有效的方法。相反，我的目标是提供有关 JVM 和 API 正在做什么的详细知识，希望如果你了解这些东西的工作原理，你就能观察应用程序的特定行为并理解其性能不佳的原因。理解这一点，消除不良（性能差）行为就变得简单（或至少更简单）了。

Java 性能工作的一个有趣方面是，开发人员通常与性能或 QA 组的工程师有非常不同的背景。我认识一些开发人员，他们能记住成千上万个鲜为人知的 Java API 上的晦涩方法签名，但却不知道 -Xmn 标志是什么意思。而我认识一些测试工程师，他们可以通过设置垃圾回收器的各种标志获得每一分性能，但却几乎写不出合适的 Java “Hello, World” 程序。

Java 性能涵盖了这两个领域：编译器和垃圾回收器等的调优标志，以及 API 的最佳实践使用。因此我假设你对如何用 Java 编写程序有很好的理解。即使你的主要兴趣不在 Java 的编程方面，我也花了相当多的时间讨论程序，包括用于提供示例中大量数据点的示例程序。

尽管如此，如果你主要对 JVM 本身的性能感兴趣——也就是说，如何在不进行任何编码的情况下改变 JVM 的行为——那么本书的大部分内容仍然对你有益。请随意跳过编码部分，专注于你感兴趣的领域。也许在这一过程中，你会获得一些关于 Java 应用程序如何影响 JVM 性能的见解，并开始向开发人员建议更改，以便他们让你的性能测试生活更轻松。





## 第二版新内容

自第一版以来，Java 采用了六个月的发布周期，并伴随周期性的长期支持版本；这意味着与出版时间相吻合的当前受支持版本是 Java 8 和 Java 11。尽管第一版涵盖了 Java 8，当时它还相当新。本版聚焦于更加成熟的 Java 8 和 Java 11，并对 G1 垃圾回收器和 Java Flight Recorder 进行了重大更新。还特别关注了 Java 在容器化环境中的行为变化。

本版涵盖了 Java 平台的新特性，包括新的微基准测试框架（JMH）、新的即时编译器、应用程序类数据共享以及新的性能工具——以及对 Java 11 新特性的覆盖，如紧凑字符串和字符串连接。
