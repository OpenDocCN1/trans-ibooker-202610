
一些管理员忽视的一个问题是，有些用户拥有便携式电脑，只在旅行时使用。这台机器可能数周或数月没有更新，当用户最终收到更新提示时，他们可能会因为身处酒店或飞机上而取消更新。应始终鼓励便携式电脑用户提前做好旅行准备，在出行前至少一天将笔记本电脑连接到网络，并让所有更新得以进行。

## SQL 注入

也许最常见（也最可预防）的软件漏洞利用被称为*SQL 注入*。如图24.1所示，黑客可能会尝试将 SQL 命令注入面向公众的表单（如登录表单），希望借此获得对底层数据库中存储数据的访问权限。

现代网络的许多强大功能都与在线数据库的使用有关，许多网页设计师使用 SQL（或类似 SQL）的数据库引擎来驱动它们。网站通常是功能强大的 Web 应用程序，可能存储海量信息。使用 SQL，你常常可以像添加分号（;）然后跟上一条 SQL 命令一样轻松地串联查询和命令。分号的作用是从输入数据的需要“转义”出来，变成指示应用程序执行你随后添加内容的机会。即使你不完全理解 SQL 编程，也能看出 SQL 注入所呈现的问题。

想象一个基于邮政编码查找资源的 Web 表单。它会使用如下单个查询：

```
SELECT * FROM Locations WHERE Zip='$zipcode';
```

其中 $zipcode 实际上来自用户提供的输入字段。如果黑客输入的是：99336; DROP TABLE Locations 而不是仅输入 99336，那么数据库可能会串联这些命令并完全删除（drop）Locations 表。

黑客判断应用程序是否容易受到 SQL 注入攻击的常见方法是在登录表单上寻找单引号漏洞。身份验证查询可能如下所示：

```
SELECT ID FROM Users WHERE Username = '$username'
AND Password = '$password';
```

如果黑客知道或能猜到你有名为 Steve 的用户，他可以尝试输入以下密码的简单把戏：

```
something' OR 'a'='a
```

## 图 24.1 SQL 注入

注意，由于应用程序查询会提供单引号，这里没有开头或结尾的单引号。现在可能执行的查询看起来像这样：

```
SELECT ID FROM Users WHERE Username = 'Steve'
AND Password = 'something OR 'a'='a';
```

即使密码不是 something，'a' 也始终等于 'a'，通过使用逻辑 OR，只需其中一个比较条件为真即可。黑客甚至可能不需要猜测用户名，只需在用户名字段中尝试同样的把戏：

```
SELECT ID FROM Users where Username = 'Steve' OR 'x'='x'
AND Password = 'something OR 'a'='a';
```

这里黑客既猜测了用户名也猜测了密码，但这些并不重要，因为 'x'='x' 和 'a'='a' 始终为真。此外，OR 子句确保每一项都匹配，黑客将获得访问权限。你可能已经在想，我们不应该允许输入单引号。对于用户名和密码字段，这种选项可能有效。然而，如果你像下面这样请求数值数据：

```
SELECT ID FROM Users where UserID=$inputValue;
```

而数值字段不需要引号，只需输入：

```
8686 OR 5=5
```

查询应该匹配，因为即使数据库中没有等于 8686 的 UserID，5 也确实等于 5。

这可能相当吓人，但好消息是这也相当容易预防。Web 应用程序程序员只需在将每个输入字段包含到查询中之前对其进行过滤或净化。这可以通过多种方式完成，但请考虑以下方法：

- 只允许输入白名单中的字符。显然，单引号不会在该白名单中。
- 对输入字段数据进行转义。
- 解析输入字段数据，并禁止 OR 和 ||（当然还有 DROP）。
- 始终对数值输入字段加引号。

这些方法会产生一定效果，并且对于许多表单来说可能已经足够。然而，似乎总有某种注入字符串可以绕过输入验证。转义存在一些问题，并且可能在某些字段上造成麻烦（例如，名字字段中用户可能输入撇号作为其名字的一部分）。如果黑客输入反斜杠（\）字符来转义其输入，或使用 Unicode 或其他编码，他们最终可能击败你的净化例程。

防止 SQL 注入的最佳方法是使用 SQL 参数。现代 SQL 系统支持参数化查询，其中参数被严格作为数据求值，不允许任何命令执行。例如：

```
SELECT ID From Users where Username='@user' AND
Password='@pass';
```

在代码的某处，服务器会有处理这些参数的存储过程，并强制执行严格的数据类型和验证，以确保只有你自己的代码被执行。你在构造查询时仍然需要小心，并且要理解表和列不能作为参数。然而，这被认为是使用 SQL 系统时的最佳实践。

还有另外两种类似于 SQL 注入的漏洞：跨站脚本（XSS）和 LDAP 注入攻击。在*跨站脚本攻击*中，攻击者将 JavaScript 安装在输入字段中。如果该输入被回显，用户的浏览器可能会执行该代码。这类事情可以通过不回显该输入或在输入净化中转换所有 HTML 实体来避免，这将把 `<script>` 转换为 `&lt;script&gt;` 并使其无害。要防止 LDAP 注入攻击，重要的是执行 LDAP 查询的面向公众的表单使用某种类型的输入验证。

虽然现代浏览器可以防范跨站脚本攻击，但它们无法完全防御它。与许多其他攻击一样，这种攻击需要一个被黑客入侵或以其他方式恶意构造的网页，如图24.2所示。教育用户了解此风险，并手动登录社交媒体而不是通过网页链接登录，会有所帮助。托管网页应定期使用前面描述的工具（如 BeEF 或 Metasploit）扫描此类漏洞利用。

## Java

从统计上看，Java 可能比其他任何软件包都更容易成为漏洞利用的目标。许多人认为 Oracle 对 Java 的加固不够，并已采取立场认为应该避免使用 Java。Java 在其自己的虚拟环境中运行，标准操作系统保护方案无法针对 Java 漏洞利用提供保护。

大多数现代操作系统提供数据执行保护（DEP）和地址空间布局随机化（ASLR），以及其他应用程序沙箱方案，这使得漏洞利用变得困难得多。这些方案无法保护用户免受 Java 漏洞利用的影响。加上 Java 的普遍存在，这使它成为黑客的绝佳目标。

对于那些并不是真正需要 Java 的用户，直接禁用 Java 是一个很好的解决方案。对于那些必须运行 Java 的用户，可以在一定程度上限制可使用的文件。这使得用户必须保持 Java 修补变得更为重要。Oracle 的更新在公开漏洞利用发布后的滞后程度往往比网络安全行业所期望的稍大，但在这些补丁可用时及时更新至关重要。

## 其他软件漏洞利用

尽管相关各方都做出了努力，但似乎几乎任何软件只要得到合适的黑客足够的关注，都可能被利用。同样的概念适用于所有软件：用户必须警惕其软件和数据文件的获取来源，并且必须及时执行所有软件更新。

Microsoft Office 应用程序支持宏，这些宏存在许多可能的漏洞利用。由于大多数用户不使用这些宏，关闭宏支持在这些情况下是一个很好的解决方案。

Web 浏览器似乎擅长自我更新，越来越多的软件包正转向自动更新机制，因此总体上正在取得良好进展。浏览器扩展日益受到关注，因为它们越来越流行，必须像其他类型的软件一样被认真对待。

用户必须充分了解软件威胁，并对更新请求积极响应。

简单的防病毒和反恶意软件无法完全保护用户或服务器免受软件漏洞利用的影响。一些漏洞利用可能来自高风险的网络冒险行为或社会工程学（或用户的轻信）；但归根结底，重要的是要认识到，任何人能做的防止每种漏洞利用的事情都是有限的。

当你将这一现实与 CryptoLocker 和其他勒索软件等漏洞利用的恶劣性结合起来时，最好的防御可能是强大的备份解决方案。频繁的增量备份是最大程度减少这些漏洞利用影响的最佳方法。简单备份并不是完美的解决方案，因为你可能没有意识到漏洞利用，并可能将已被利用的软件或数据备份到好副本之上。

使用提供基于时间的数据检索的增量备份解决方案是最好的解决方案。Apple 的 Time Machine 和 Microsoft 的 File History 是优秀的备份解决方案，允许恢复到漏洞利用发生前的某个时间点。
