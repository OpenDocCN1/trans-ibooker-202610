# Levels of Testing

Depending on the size of the SUT, we can define different levels of testing. These levels define several categories in which software teams divide up their testing efforts. In this book, I propose a stacked layout to represent the different levels (see Figure 1-5). The lower levels of this structure represent the tests aimed to verify small pieces of software (called units). As long as we ascend in the stack, we find other tiers (e.g., integration, system, etc.) in which the SUT integrates more and more components.

![](bbox=[0.35, 0.25, 0.68, 0.38])

Figure 1-5. Stack representation of the different levels of testing

The lowest level of this stack is unit testing. At this level, we assess individual units of software. A unit is a particular observable element of behavior. For instance, units are typically methods or classes in object-oriented programing and functions in functional programming. The objective of unit testing is to verify that each unit behaves as expected. Automated unit tests typically run very fast since each test executes a small amount of code in isolation. To achieve this isolation, we can use test doubles, which are pieces of software that replace the dependant components of a given unit. For example, a popular type of test doubles in object-oriented programming is the mock objects. A mock object mimics an actual object using some programmed behavior.

The next level in Figure 1-5 is integration testing. At this level, different units are composed to create composite components. Integration testing aims to assess the interaction between the involved units and expose defects in their interfaces.

Then, at the system testing and end-to-end (E2E) levels, we test the software system as a whole. To carry out these levels, we need to deploy the SUT and verify its high-level features. The difference between system/end-to-end and integration testing is that the former involves all the system components and the final user (typically impersonated). In other words, system and end-to-end testing assess the SUT through the User Interface (UI). This UI can be graphical (GUI) or non-graphical (e.g., text-based or other types).
