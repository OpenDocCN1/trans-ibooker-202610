| iii. 实体管理在设计实体系统时假定由供应商实施且与实体的控制相结合对于实现实体的主要系统目标提供合理保证所必需的控制类型；此类控制通常被称为 *互补供应商控制* 或 CSC<br><br>*b.* 实体采用包容方法时，以下内容：<br>i. 供应商生产、制造或分销的产品性质或提供的服务<br>ii. 可归因于供应商的系统部分<br>iii. 供应商的基础设施、软件、人员、程序和数据的相关方面<br>iv. 供应商处的控制，与实体处的控制相结合，对于提供合理保证以实现实体的主要系统目标所必需 | - 实体对从供应商处收到货物后系统所接收的所有输入都有健全的质量检验流程。该流程包括检查运输容器和箱子是否受损；对样本输入进行统计抽样并对照输入规范和要求进行测量；以及由生产人员对输入进行目视检查。在这种情况下，实体的控制足以降低输入不符合规范的风险。<br><br>- 实体对其供应商用于生产新软件的系统拥有健全的控制，包括变更管理控制；然后实体在其生产流程中使用该新软件。在这种情况下，实体对供应商系统和控制的监控足以使实体实现其系统目标。<br><br>- 供应商负责每季度对实体的备用电源系统进行维护，以解决可用性问题。如果实体对其自身的监控控制覆盖供应商的控制，则供应商的控制对于实体实现其系统目标而言并非必要。<br><br>- 实体将其应用开发测试外包给供应商，并在供应商合同中规定供应商负责执行实体认为为应对与供应商开展业务相关的风险所必需的某些控制。实体指定一名员工监督外包服务；该员工将供应商的测试计划、测试脚本和测试数据与实体的应用变更请求和详细设计文档进行比较。该实体员工还在供应商批准对应用的变更并提交给实体进行用户验收测试之前审查供应商执行的测试结果。供应商的控制可能对于实体断言其控制能够提供合理保证以实现实体的可用性承诺而言并非必要，这是基于适用的受托服务标准。<br><br>然而在其他情况下，实体可能不具备此类控制。例如，采购包含嵌入式软件的子组件的实体可能无法直接评估该软件的质量和安全性。在这种情况下，实体将某些责任委托给供应商，并期望供应商对用于生产或交付子组件的流程执行特定控制。因此，有效的供应商控制对于实体实现其主要系统目标可能是必要的。 |
| *剔除法* | 当供应商执行的控制与实体的控制相结合对于实现主要系统目标所必需时，此类控制被称为 *互补供应商控制*（CSCs）。由于 CSC 对报告使用者很重要，因此在描述中予以披露。呈现 CSC 的最常见方法是仅包括执行责任属于实体的流程和控制，并识别实体期望供应商实施的 CSC。该方法称为 *剔除法*。<br><br>使用剔除法时，描述会识别供应商预期实施的 CSC 类型以及 CSC 影响的受托服务标准。还可考虑在信息对客户或业务合作伙伴有用时披露供应商的身份。<br><br>CSC 通常以表格形式呈现在描述的末尾，并附带每个 CSC 相关的受托服务标准。实体管理可能在确定如何在描述中呈现 CSC 时请求实务人员的协助。实务人员可以提供其他实体所做的 CSC 披露示例，并建议改进实体在描述中对 CSC 的呈现方式。 |
| *包容方法* | 在某些情况下，实体管理可能希望在其描述中呈现供应商的相关流程和控制，以满足使用者的共同信息需求，或因供应商在流程中的作用重要而如此。这种呈现方法称为 *包容方法*。在包容方法下，供应商的基础设施、软件、人员、程序和数据的相关方面被视为实体系统的一部分；因此，它们在描述中予以披露并受实务人员检查程序的约束。描述单独识别实体控制和供应商控制。然而，并没有区分两者的规定格式。<br><br>使用 *包容方法* 时，供应商管理也是检查中的责任方。由于使用 *包容方法* 涉及额外的复杂性，实体和供应商管理通常在业务承接期间就使用 *包容方法* 达成一致。 |
| *其他事项* | 使用多个供应商的实体可能对其描述采用对一个或多个供应商使用剔除法，对其他供应商使用包容方法。<br><br>无论实体管理选择何种方法，描述都需要披露旨在提供合理保证以实现实体主要系统目标的控制；这些控制包括实体用于监控供应商提供的服务的控制。此类监控控制可能包括以下组合：<br>- 对收到的输入进行质量控制测试<br>- 由实体内部审计职能部门成员对供应商控制进行测试<br>- 审查和核对输出报告<br>- 与供应商人员定期讨论并根据既定的服务水平目标和协议评估供应商绩效<br>- 拜访供应商现场<br>- 检查供应商系统的鉴证报告<br>- 监控外部沟通，例如与供应商提供的产品或服务相关的客户投诉 |
| DC9：与系统相关的任何特定适用受托服务标准不相关的原因及原因 | 如果一个或多个适用受托服务标准与所描述的系统无关，实体管理应在描述中说明此类标准为何不相关。适用受托服务标准可能不相关，如果它不适用于实体提供的生产、制造或分销服务。例如，一家植入式医疗器械的销售商使用一家实体为每位患者实施电子医疗器械的特定软件配置。在这种情况下，是客户 — 而非实体 — 从客户的患者处收集个人信息。每位患者的医疗信息由患者的医生提供给销售商，销售商随后将信息转发给实体以创建并在设备上实施配置数据。当描述涉及隐私控制时，实体管理不会在其描述中披露客户对收集的控制；然而，该遗漏的原因将被披露。<br><br>存在禁止某些活动的政策不足以使标准不适用。例如，当描述涉及隐私控制时，仅基于实体的政策禁止此类披露，就将个人信息的披露给第三方从描述中省略是不合适的。相反，描述应说明防止或检测此类披露的政策及相关控制。 |
| DC10：描述所涵盖期间内与实现实体主要系统目标相关的实体系统和控制的重大变更¹² | 需要披露的重大变更是那些可能与广泛使用者相关的内容。此类变更的披露应包括适当程度的细节，例如变更发生的日期以及变更前后系统的差异。<br><br>系统重大变更包括以下示例：<br><br>- 生产流程的变更，包括因产品性能规范变更而导致的变更<br>- IT 和安全人员的变更<br>- IT 流程、IT 架构和应用的变更，以及供应商使用的流程和系统<br>- 可能影响系统要求的法律和监管要求的变更<br>- 导致系统内部控制变更的组织结构变更（例如，从集中控制变为分散控制，或从内部控制变为外包控制）<br>- 因旨在实现产品性能规范、承诺和要求的控制失效而导致的风险评估和控制监控流程变更<br><br>对系统重大变更的披露仅限于与描述所涉及的受托服务类别或类别相关的程度。 |
