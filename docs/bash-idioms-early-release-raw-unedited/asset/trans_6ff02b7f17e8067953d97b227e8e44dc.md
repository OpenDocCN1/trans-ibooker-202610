## Other

其他指南：

- 对于“system”脚本，将日志记录到 syslog，让操作系统处理最终目的地、日志轮转等。
- 错误信息应输出到 STDOUT，如 echo 'A Bad Thing happened' >&2
- 检查外部工具是否可用
- 失败时提供有用的信息
- 设置退出码，尤其是在失败时

## Readability

代码的可读性很重要！或者正如 Python 所说，*可读性很重要*。你只写一次，但你（和其他人）可能会阅读很多次。花额外的几秒钟或几分钟思考明年试图阅读代码的可怜的糊涂的人……很可能就是你。抽象（不要重复自己）和可读性之间存在平衡和张力。

- KISS (Keep it Simple, Stupid!)
- 可读性：不要“聪明”，要清晰
- 好的名字至关重要！
- 一定要使用头部
- 如果可能的话，为 `-h`、`--help` 和错误参数发出有用的内容！
  - 优先使用“here”文档（带前导 TAB）而不是一堆 echo 行
- 使用 `source`（而不是 `.`）来包含配置文件，后者应以 `.cfg`（或 `.conf` 或你标准的任何名称）结尾
- 如果可能的话，对所有内容都使用 ISO-8601 ¹ 日期
- 如果可能，保持事物列表（例如，ip 地址、主机名、要安装的包等）的字母顺序；这可以防止重复并使添加或删除项目更容易
  - 这适用于 `case` 语句、变量或数组/列表的内容，以及任何有意义的地方
- 如果可能，使用命令的长参数以提高可读性，例如，使用 `diff --quiet` 而不是 `diff -q`，不过要注意对非 GNU/Linux 系统的可移植性

- 如果任何选项简短或晦涩，请添加注释。
- 还应强烈考虑记录你选择或需要选项的原因，甚至记录你考虑过但出于某种原因未使用的选项。
- 一定要记录任何看起来像个好主意但实际上可能导致问题的选项，尤其是你在其他地方常用到的选项。

## Comments

- 一定要使用头部
- 为一年后团队中的新人写你的注释
- 对你的函数进行注释
- 不要对你做了什么进行注释。对你为什么做或不做某事进行注释
  - 例外：当 bash 本身晦涩时，对你做了什么进行注释
- 考虑添加关于外部程序选项的注释，尤其是当它们简短或晦涩时

## Names

- 好的名字至关重要！
- 全局变量和常量使用大写
  - 尽量不要更改全局变量，但有时这样做要简单得多
