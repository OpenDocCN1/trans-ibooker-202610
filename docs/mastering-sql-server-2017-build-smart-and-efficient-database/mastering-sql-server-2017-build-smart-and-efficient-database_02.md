## SQL Server 2017 简介

SQL Server 是微软的主要关系数据库管理系统产品。它自 80 年代末以来以一种或另一种形式存在（与 Sybase 合作开发），但作为独立的微软产品，它自 90 年代初就已存在。在过去的 20 年里，SQL Server 发生了变化和演进，沿途获得了新特性和功能。

我们今天所知的 SQL Server 基于其历史上 arguably 最重要的（r）演进性一步：SQL Server 2005 的发布。所引入的变更使得 2005 发布之后的版本能够利用更新的硬件和软件改进，例如：64 位内存架构、更好的多 CPU 和多核支持、与 .NET 框架更好的对齐，以及总体系统架构的许多现代化。

在每个后续版本的 SQL Server 中引入的增量变更继续在此坚实的新基础上改进。幸运的是，微软已更改了多个产品的发布周期，包括 SQL Server，从而导致发布之间的时间间隔缩短。这在一定程度上是由于微软对其广受报道的移动优先、云优先战略的关注。该战略以及 SQL Server Azure SQL Database 云版本的开发，使得微软被迫进入大幅缩短的发布周期。此战略的优势在于，我们不再需要等待 3 到 5 年才能获得新版本（和新功能）。自 SQL Server 2012 引入以来，每两年就有一次发布，而在真正的版本之间还有 Azure SQL Database 的多次发布。

虽然我们可以高兴不再需要等待新版本，但我们也处于明显的劣势。新的版本和功能的快速发布，使得我们开发人员用于掌握这些闪亮新功能的时间越来越少。之前的版本发布间隔多年，让我们能够在必须吸收新信息之前，更深入地了解和掌握可用功能。

在 SQL Server 2016 发布后不久，SQL Server 2017 随之发布，距离 2016 发布仅一年多。许多功能只是 2016 发布版本的更精炼/更新版本，而 2017 发布中也有一些值得注意的增添。

在本章（和本书中），我们将介绍 SQL Server 2017 中的新内容。由于发布周期短，我们将概述产品此版本中的全新功能，并查看自 SQL Server 2016 以来已扩展或改进的功能。

我们将在以下领域概述新功能：

- Security
- Engine features
- Programming
- Business intelligence

## Security

过去几年使 IT 安全的重要性变得极其明显，特别是当我们考虑到爱德华·斯诺登数据泄露事件的后果或通过黑客进行数据盗窃的多个案例时。虽然没有任何系统是完全不可渗透的，但我们应始终考虑如何改进我们构建的系统的安全性。这些考虑范围广泛，有时甚至由规则、法规和法律规定。微软通过提供新功能来应对对安全的关注增加，以帮助开发人员和 DBA 寻找更安全的系统。

## 行级安全

在 SQL Server 2016 中引入的第一个用于解决对增加/改进安全需求的技术是行级安全（RLS）。RLS 提供了根据执行查询的用户控制对表中行的访问的能力。有了 RLS，就可以在数据库中的任何表上实现过滤机制，对任何外部应用程序或直接 T-SQL 访问完全透明。

无需重新设计数据访问层即可实现此类过滤的能力，使得系统管理员能够比以前更精细地控制对数据的访问。能够在无需任何应用程序逻辑重新设计的情况下实现此控制，使得该功能对某些用例更具吸引力。RLS 还使得结合必要的审计功能，能够锁定 SQL Server 数据库，以至于即使传统的 *god-mode* sysadmin 也无法访问底层数据。

## 动态数据屏蔽

我们将要介绍的第二个安全功能是 **动态数据屏蔽（DDM）**。DDM 允许系统管理员定义列级数据屏蔽算法，防止用户读取列的内容，同时仍能查询行本身。此功能最初旨在允许开发人员使用生产数据的副本进行工作，而无需实际 *查看* 底层数据。这在执行数据保护法律的环境中特别有用（例如，信用卡处理系统和医疗记录存储）。数据屏蔽仅在查询运行时发生，并且不影响表的存储数据。这意味着可以通过简单的 DDL 语句屏蔽多 TB 的数据库，而无需诉诸于先前通过物理屏蔽表中要屏蔽的底层数据的解决方案。DDM 的当前实现提供了将固定的一组函数定义到表的列的能力，这些函数将在查询屏蔽表时屏蔽数据。如果用户有权查看屏蔽数据，则不会运行屏蔽函数，而可能无法查看屏蔽数据的用户将通过定义的屏蔽函数看到的数据提供。

## Always Encrypted

在 SQL Server 2016 中引入的第三个主要安全功能是 Always Encrypted。SQL Server 的加密 previously 主要是基于服务器的解决方案。数据库要么在数据库级别受加密保护（整个数据库被加密），要么在列级别（单个列定义了加密算法）。虽然这种加密完全功能且安全，但加密过程的关键部分（例如，加密证书）存储在 SQL Server 内部。这有效地赋予了 SQL Server 实例的所有者潜在访问此加密数据的能力——如果不是直接访问，至少为潜在的恶意访问尝试提供了更大的攻击面。随着越来越多的公司转向托管服务和云解决方案（例如 Microsoft Azure），之前的加密解决方案不再提供所需级别的控制/安全。




始终加密（Always Encrypted）旨在弥补这一安全漏洞，它移除了实例所有者访问加密组件的能力。整个加密过程被移出 SQL Server，驻留在客户端。虽然使用自制解决方案也能达到类似效果，但始终加密提供了完全集成到 .NET Framework 和 SQL Server 中的加密套件。当数据被定义为需要加密时，数据会在 .NET 框架内进行加密，并且只有在加密完成后才发送到 SQL Server。这意味着，恶意用户（甚至系统管理员）若试图查询通过始终加密存储的数据，也只能访问到加密后的信息。

微软在产品这一领域取得了一些积极进展。虽然没有任何系统是绝对安全的，也没有任何单一功能能够提供包罗万象的解决方案，但这三项功能都为构建或改进任何系统当前的安全级别提供了额外的选择。

## 引擎特性

对于大多数 DBA 或系统管理员来说，每当新版本 SQL Server 发布时，引擎特性部分传统上是最重要或最有趣的。不过，许多引擎特性的改进对开发人员也有间接意义。所以，如果你是开发人员，不要跳过这一部分——否则你可能会错过一些以后能为你省去麻烦的改进！

## 查询存储（Query Store）

查询存储可能是随 SQL Server 2016 发布而来的最大新引擎特性。DBA 和开发人员一定非常熟悉这样的一种情况：一个查询在很长一段时间内运行稳定，却突然变成了一个运行缓慢、消耗资源的“怪兽”。有些读者可能会将问题原因归结为*参数嗅探*现象，或者类似地归因于*过时统计信息*。无论如何，在排查一个一成不变的查询为何突然变慢时，了解 SQL Server 创建并使用过的查询执行计划会非常有帮助。调查这类问题时的一个主要障碍是查询计划及其执行统计信息的短暂性。这正是查询存储发挥作用的地方；SQL Server 会按数据库收集并永久存储有关查询编译和执行的信息。这些信息随后被持久化到由查询存储功能**监控**的每个数据库中，从而允许 DBA 或开发人员在事后调查性能问题。

实现这一方法的一大步是 SQL Server 2016 中新增的 Stretch Database 功能。Stretch Database 允许 DBA 对数据库内的数据进行分类，定义哪些数据是*热*数据，哪些是*冷*数据。这种分类使 Stretch Database 能够将*冷*数据从本地数据库移动到 Azure 云存储中。

数据的分割对于任何查询数据的用户/应用程序来说都是透明的，这些数据现在驻留在两个不同的位置。这项技术背后的理念是通过将大量归档数据卸载到云中更便宜、更慢的存储上，来减少本地系统的存储需求。

这种减少应能让较小的*热*数据被放置在容量较小、性能更高的存储上。Stretch Database 的*神奇之处*在于，这种数据分离不需要在应用程序或数据库查询层面进行任何更改。这纯粹是存储层面的变更，这意味着对数据库进行分段的潜在投资回报率相当大。

## 数据库作用域配置

许多支持 SQL Server 上运行多个第三方应用程序的 DBA 可能会遇到这样的困难：需要按照应用程序要求或最佳实践来设置其 SQL Server 实例。许多第三方应用程序都有先决条件，规定实际 SQL Server 实例必须如何配置。一个常见情况是要求配置*最大并行度*，以强制仅使用一个 CPU 来执行查询。由于这是实例范围的设置，它可能会影响多租户 SQL Server 实例中的所有其他数据库/应用程序（通常情况正是如此）。借助 SQL Server 2016 中的数据库作用域配置，若干以前属于实例级别的设置已被移至数据库级别的配置选项。这极大地改善了多租户 SQL Server 实例，因为例如“多少个 CPU 可用于查询执行”这样的决策可以在数据库级别做出，而不是针对整个实例。这将允许 DBA 在同一实例上托管具有不同 CPU 使用需求的数据库，而不必要么用一项设置影响整个实例，要么被迫运行多个 SQL Server 实例并可能承担更高的许可成本。

最初，只有非聚集列存储索引可用。随着 SQL Server 2014 的发布，引入了聚集列存储索引，极大地扩展了该功能的可用性。最后，在 SQL Server 2016 中，引入了可更新列存储索引和对内存中列存储索引的支持。通过这些改进带来的潜在性能提升是巨大的。

## 容器和 Linux 上的 SQL Server

很长一段时间以来，SQL Server 只在 Windows 操作系统上运行。这是其在传统基于 Unix/Linux 的公司中采用的重大障碍，这些公司转而使用其他关系数据库管理系统。容器在 IT 领域已经存在了十多年，并在应用程序开发领域产生了重大影响。现在能够在容器中托管 SQL Server，这使得开发人员能够将与容器相关的开发和部署方法应用到数据库开发中。围绕 SQL Server 2017 的第二个重大突破（也是惊喜）是宣布 SQL Server 被移植到 Linux。IT 界对这一消息及其对市场上其他关系数据库管理系统的影响感到震惊。实际上，没有其他系统能够在相同的价格点上提供相同的功能集和支持网络。因此，Linux 上的 SQL Server 将开辟一个新市场，并允许 IT 领域以前无法触及的领域实现增长。

至此，概述引擎特性的部分结束。由于微软大力进军云计算及其 Azure 产品，他们自身对改进内部系统的需求也在增加。微软以其“吃自己狗粮”的做法而闻名，即使用自己的软件来运营自己的业务，而 Azure 可以说是他们在这方面最大的一次尝试。数据库引擎的主要改进受到了以下需求的推动：提高自身能力以持续大规模提供 Azure 数据库解决方案，并提供各项功能以允许不同大小和负载的数据库托管在一起。

## 编程

没有编程，SQL Server 就不会有多大用处。多年来，SQL Server 的编程领域持续改进，以采用更新的技术。SQL Server 2017 在这方面也不例外。该产品有一些期待已久的常规改进，也有一些相当革命性的新增功能，这些功能改变了 SQL Server 在未来项目中可被使用的方式。本节将概述 SQL Server 2017 中包含了哪些编程改进。

## Transact-SQL 增强

T-SQL 语言上一次的重大改进使得运行总计和其他类似窗口函数的处理更加高效。这已经是一大福音，使开发人员能够用高性能 T-SQL 取代神秘的游标。然而，对于我们中那些最注重性能的开发人员来说，这些改进永远不够，因此仍然有人要求将 ANSI SQL 标准进一步纳入 T-SQL 实现中。

T-SQL 语法中值得注意的新增功能包括最终能够使用单个函数调用 `STRING_SPLIT()` 来拆分逗号分隔的字符串，取代了以前使用循环或公共语言运行时（CLR）的黑客式实现。

与拆分字符串相对应的合理语法是一个将值聚合在一起的函数 `STRING_AGG()`，它返回以逗号分隔的字符串形式呈现的一组值。这取代了同样使用 XML 数据类型或众多循环解决方案之一的临时拼凑式解决方案。

T-SQL 语言的每一项改进都进一步扩展了我们作为开发人员操作 SQL Server 内部数据所拥有的工具箱。ANSI SQL 标准为开展工作提供了坚实的基础，这些标准的进一步补充总是受欢迎的。

## JSON

在微软技术栈之外，遇到一些看不起来自雷德蒙德（Redmond）产品的开发人员是很常见的。尤其是 Web 开发人员，一直对现代数据交换结构的可获取性（或者说缺乏可获取性）持批评态度。JSON 已成为应用程序开发领域事实上的数据交换方法。它在结构上类似于之前备受追捧的 XML，但出于本书范围之外的原因，JSON 已经超越了 XML，并成为应用程序和数据库通信所期望的数据载荷。



Microsoft已在SQL Server 2016中将JSON作为原生数据类型引入，并提供了一组配套函数。

## 内存OLTP

内存OLTP（代号Hekaton）在SQL Server 2014中引入。在SQL Server 2014发布时，SQL Server内部实现超高性能数据处理这一承诺是一个重要特性。正如意料之中的第一版特性，初始版本存在诸多限制，这使得许多客户无法采用该技术。到SQL Server 2017，其中大量限制要么提升到更高阈值，要么已完全移除。内存OLTP在功能集上已达到所需的成熟度和扩展性，使其能够胜任重要的生产环境部署。

## SQL Server工具

访问或管理SQL Server中的数据与开发数据解决方案是两个不同的领域，各自对SQL Server有特定的关注点。因此，Microsoft创建了两种不同的工具，分别针对这些领域的流程和方面量身定制。

SQL Server Management Studio（SSMS），顾名思义，是DBA/开发人员与SQL Server之间的主要管理界面。该工具最初随SQL Server 2005发布，用以替代并整合旧的查询分析器和企业管理器工具。与任何不产生收入的软件一样，SSMS多年来只获得极少的关注，对于SQL Server中的许多新功能存在局限性并缺乏配套工具。自SQL Server 2016起，Microsoft的重心发生了转变，SSMS已从SQL Server自身的发布周期中解耦。这种解耦使得SSMS和SQL Server都能独立开发，无需等待彼此或受发布窗口限制。SSMS的新版本基于更新版本的Visual Studio构建，自SQL Server 2016推向市场以来，几乎每月都有更新发布。

**SQL Server数据工具（SSDT）**也是一款基于Visual Studio框架的应用程序。SSDT专注于应用程序/数据开发领域。SSDT在结构和提供的功能上与Visual Studio的契合度更高。这一专注点包括创建完整数据库项目和解决方案文件的能力、更轻松地集成到源代码管理系统、将项目连接到自动化构建流程的能力，以及总体上提供一个熟悉Visual Studio的开发人员为中心的开发环境。在SSDT中，可以使用关系引擎、Analysis Services、Integration Services、Reporting Services以及当然还有Azure SQL数据库来设计和创建面向SQL Server的解决方案。

有关SQL Server工具的更多详细信息，请参阅第2章《SQL Server工具》。

## 商业智能

商业智能是IT领域的一大板块，至少自SQL Server 2005以来便一直是SQL Server产品的基石。随着商业智能领域市场和技术的发展，SQL Server也必须与时俱进。基于云的数据分析系统的出现以及近期围绕*大数据*的热议，成为所有数据平台提供商的驱动力，Microsoft也不例外。虽然SQL Server 2016的商业智能部分有多项增强，但我们将重点关注一个受众比数据分析师更广泛的功能：SQL Server中的R语言。

## SQL Server中的R

过去几年，数据分析一直是IT领域最热门的话题，新的细分领域几乎与技术发展速度同步被加冕为信息科学的巅峰。然而，IT领域确实有一些经受住时间考验且仍被广泛使用的坚定*经典*。SQL（及其多种形式）是我们在SQL Server世界中非常熟悉的语言。另一个这样的语言是简洁命名的 **R**。R语言是一种数据挖掘、机器学习和统计分析语言，自1993年以来就存在。

许多专业人士，如数据科学家、数据分析师或统计学家，使用R语言及该领域的工具已有同样悠久的历史。Microsoft认识到，尽管他们可能希望全世界的数据库都置于SQL Server之内，但这既不可行也不合理。像R这样的外部数据源和语言是客观存在的，需要以集成的方式使其可被访问。

为了实现这一点，Microsoft于2015年决定收购Revolution Analytics（一家生产分叉版*Revolution R*的商业实体），随后能够将该语言和服务器进程集成到SQL Server 2016中。这种集成允许*普通*T-SQL开发人员以原生方式与极其强大的R服务交互，并允许对其数据执行更高级的数据分析。

## 发布周期

过去5年中，Microsoft进行了几项重大的面向公众的变革。这些变革包括告别其主打产品的较长发布周期，并转向基于订阅的服务（例如Office 365和Azure服务）。围绕持续交付和敏捷软件开发的理念也塑造了Microsoft交付其旗舰集成开发环境Visual Studio的方式，大约每六个月发布一次。这种理念上的转变正逐步流入SQL Server的开发周期。由于云版SQL Server（Azure SQL数据库）类似的持续发布周期，人们希望尽可能保持该产品的云版本和本地版本接近。因此，看到之前的每三到五年发布周期正被更短的间隔所取代也就不足为奇了。一个明确的例子是：SQL Server 2016于2016年6月发布，SQL Server 2017的**社区技术预览版（CTP）**于2016年11月发布，而SQL Server 2017的**向市场发布（RTM）**则在2017年10月完成。技术进步的浪潮不会为任何人停留。这在SQL Server身上体现得尤为明显！
