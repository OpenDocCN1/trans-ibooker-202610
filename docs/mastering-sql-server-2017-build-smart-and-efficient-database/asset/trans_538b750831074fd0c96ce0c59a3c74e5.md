
始终加密（Always Encrypted）旨在弥补这一安全漏洞，它移除了实例所有者访问加密组件的能力。整个加密过程被移出 SQL Server，驻留在客户端。虽然使用自制解决方案也能达到类似效果，但始终加密提供了完全集成到 .NET Framework 和 SQL Server 中的加密套件。当数据被定义为需要加密时，数据会在 .NET 框架内进行加密，并且只有在加密完成后才发送到 SQL Server。这意味着，恶意用户（甚至系统管理员）若试图查询通过始终加密存储的数据，也只能访问到加密后的信息。

微软在产品这一领域取得了一些积极进展。虽然没有任何系统是绝对安全的，也没有任何单一功能能够提供包罗万象的解决方案，但这三项功能都为构建或改进任何系统当前的安全级别提供了额外的选择。

## 引擎特性

对于大多数 DBA 或系统管理员来说，每当新版本 SQL Server 发布时，引擎特性部分传统上是最重要或最有趣的。不过，许多引擎特性的改进对开发人员也有间接意义。所以，如果你是开发人员，不要跳过这一部分——否则你可能会错过一些以后能为你省去麻烦的改进！

## 查询存储（Query Store）

查询存储可能是随 SQL Server 2016 发布而来的最大新引擎特性。DBA 和开发人员一定非常熟悉这样的一种情况：一个查询在很长一段时间内运行稳定，却突然变成了一个运行缓慢、消耗资源的“怪兽”。有些读者可能会将问题原因归结为*参数嗅探*现象，或者类似地归因于*过时统计信息*。无论如何，在排查一个一成不变的查询为何突然变慢时，了解 SQL Server 创建并使用过的查询执行计划会非常有帮助。调查这类问题时的一个主要障碍是查询计划及其执行统计信息的短暂性。这正是查询存储发挥作用的地方；SQL Server 会按数据库收集并永久存储有关查询编译和执行的信息。这些信息随后被持久化到由查询存储功能**监控**的每个数据库中，从而允许 DBA 或开发人员在事后调查性能问题。

实现这一方法的一大步是 SQL Server 2016 中新增的 Stretch Database 功能。Stretch Database 允许 DBA 对数据库内的数据进行分类，定义哪些数据是*热*数据，哪些是*冷*数据。这种分类使 Stretch Database 能够将*冷*数据从本地数据库移动到 Azure 云存储中。

数据的分割对于任何查询数据的用户/应用程序来说都是透明的，这些数据现在驻留在两个不同的位置。这项技术背后的理念是通过将大量归档数据卸载到云中更便宜、更慢的存储上，来减少本地系统的存储需求。

这种减少应能让较小的*热*数据被放置在容量较小、性能更高的存储上。Stretch Database 的*神奇之处*在于，这种数据分离不需要在应用程序或数据库查询层面进行任何更改。这纯粹是存储层面的变更，这意味着对数据库进行分段的潜在投资回报率相当大。

## 数据库作用域配置

许多支持 SQL Server 上运行多个第三方应用程序的 DBA 可能会遇到这样的困难：需要按照应用程序要求或最佳实践来设置其 SQL Server 实例。许多第三方应用程序都有先决条件，规定实际 SQL Server 实例必须如何配置。一个常见情况是要求配置*最大并行度*，以强制仅使用一个 CPU 来执行查询。由于这是实例范围的设置，它可能会影响多租户 SQL Server 实例中的所有其他数据库/应用程序（通常情况正是如此）。借助 SQL Server 2016 中的数据库作用域配置，若干以前属于实例级别的设置已被移至数据库级别的配置选项。这极大地改善了多租户 SQL Server 实例，因为例如“多少个 CPU 可用于查询执行”这样的决策可以在数据库级别做出，而不是针对整个实例。这将允许 DBA 在同一实例上托管具有不同 CPU 使用需求的数据库，而不必要么用一项设置影响整个实例，要么被迫运行多个 SQL Server 实例并可能承担更高的许可成本。

最初，只有非聚集列存储索引可用。随着 SQL Server 2014 的发布，引入了聚集列存储索引，极大地扩展了该功能的可用性。最后，在 SQL Server 2016 中，引入了可更新列存储索引和对内存中列存储索引的支持。通过这些改进带来的潜在性能提升是巨大的。

## 容器和 Linux 上的 SQL Server

很长一段时间以来，SQL Server 只在 Windows 操作系统上运行。这是其在传统基于 Unix/Linux 的公司中采用的重大障碍，这些公司转而使用其他关系数据库管理系统。容器在 IT 领域已经存在了十多年，并在应用程序开发领域产生了重大影响。现在能够在容器中托管 SQL Server，这使得开发人员能够将与容器相关的开发和部署方法应用到数据库开发中。围绕 SQL Server 2017 的第二个重大突破（也是惊喜）是宣布 SQL Server 被移植到 Linux。IT 界对这一消息及其对市场上其他关系数据库管理系统的影响感到震惊。实际上，没有其他系统能够在相同的价格点上提供相同的功能集和支持网络。因此，Linux 上的 SQL Server 将开辟一个新市场，并允许 IT 领域以前无法触及的领域实现增长。

至此，概述引擎特性的部分结束。由于微软大力进军云计算及其 Azure 产品，他们自身对改进内部系统的需求也在增加。微软以其“吃自己狗粮”的做法而闻名，即使用自己的软件来运营自己的业务，而 Azure 可以说是他们在这方面最大的一次尝试。数据库引擎的主要改进受到了以下需求的推动：提高自身能力以持续大规模提供 Azure 数据库解决方案，并提供各项功能以允许不同大小和负载的数据库托管在一起。

## 编程

没有编程，SQL Server 就不会有多大用处。多年来，SQL Server 的编程领域持续改进，以采用更新的技术。SQL Server 2017 在这方面也不例外。该产品有一些期待已久的常规改进，也有一些相当革命性的新增功能，这些功能改变了 SQL Server 在未来项目中可被使用的方式。本节将概述 SQL Server 2017 中包含了哪些编程改进。

## Transact-SQL 增强

T-SQL 语言上一次的重大改进使得运行总计和其他类似窗口函数的处理更加高效。这已经是一大福音，使开发人员能够用高性能 T-SQL 取代神秘的游标。然而，对于我们中那些最注重性能的开发人员来说，这些改进永远不够，因此仍然有人要求将 ANSI SQL 标准进一步纳入 T-SQL 实现中。

T-SQL 语法中值得注意的新增功能包括最终能够使用单个函数调用 `STRING_SPLIT()` 来拆分逗号分隔的字符串，取代了以前使用循环或公共语言运行时（CLR）的黑客式实现。

与拆分字符串相对应的合理语法是一个将值聚合在一起的函数 `STRING_AGG()`，它返回以逗号分隔的字符串形式呈现的一组值。这取代了同样使用 XML 数据类型或众多循环解决方案之一的临时拼凑式解决方案。

T-SQL 语言的每一项改进都进一步扩展了我们作为开发人员操作 SQL Server 内部数据所拥有的工具箱。ANSI SQL 标准为开展工作提供了坚实的基础，这些标准的进一步补充总是受欢迎的。

## JSON

在微软技术栈之外，遇到一些看不起来自雷德蒙德（Redmond）产品的开发人员是很常见的。尤其是 Web 开发人员，一直对现代数据交换结构的可获取性（或者说缺乏可获取性）持批评态度。JSON 已成为应用程序开发领域事实上的数据交换方法。它在结构上类似于之前备受追捧的 XML，但出于本书范围之外的原因，JSON 已经超越了 XML，并成为应用程序和数据库通信所期望的数据载荷。
