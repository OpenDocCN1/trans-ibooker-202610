# 第 11 章 数据工程的未来

本书源于作者们的认识：该领域以变形般的速度变化，为现有数据工程师、有意转行从事数据工程的人员、技术管理者以及希望更好地了解数据工程如何融入其公司的高管，造成了显著的知识鸿沟。当我们开始思考如何组织本书时，朋友们曾强烈反对，问道：“你们怎么敢写一个变化如此之快的领域？！”在很多方面，他们是对的。数据工程领域——实际上，所有与数据相关的事物——确实感觉在每天都在变化。在撰写和组织本书时，从噪音中筛选出*不太可能改变*的信号，是最具挑战性的部分之一。

在本书中，我们关注未来几年内我们认为有用的宏大理念——因此有了数据工程生命周期及其暗流的连续体。最佳实践和技术的操作顺序和名称可能会改变，但生命周期的主要阶段在未来许多年内很可能保持完整。我们敏锐地意识到技术仍在以令人筋疲力竭的速度持续变化；在当今时代从事技术行业，感觉就像坐过山车，或者可能像在镜子迷宫中穿行。

几年前，数据工程甚至不存在作为一个领域或职位名称。现在您正在阅读一本名为《数据工程基础》的书！您已经了解了数据工程的基础知识——其生命周期、暗流、技术和最佳实践。您可能会问自己，数据工程的下一步是什么？虽然没人能预测未来，但我们对过去、现在和当前趋势有很好的视角。我们有幸从前排座位上见证了数据工程的起源和演变。最后一章呈现了我们对未来的思考，包括对正在进行的发展的观察和大胆的未来推测。

## 数据工程生命周期不会消失

虽然近年来数据科学获得了大部分关注，但数据工程正迅速成熟为一个独特且可见的领域。它是技术领域增长最快的职业之一，没有失去势头的迹象。随着公司意识到在转向“更性感”的 AI 和 ML 之前，首先需要建立数据基础，数据工程将继续增长其受欢迎度和重要性。这一进程以数据工程生命周期为中心。

有人质疑日益简化的工具和实践是否会导致数据工程师的消失。这种想法是肤浅、懒惰和短视的。随着组织以新方式利用数据，将需要新的基础、系统和工作流来满足这些需求。数据工程师处于设计、架构、构建和维护这些系统的核心位置。如果工具变得更易用，数据工程师将向价值链上游移动，专注于更高层次的工作。数据工程生命周期在可预见的未来不会消失。

## 复杂性的衰退与易用数据工具的兴起

简化、易用的工具持续降低数据工程的入门门槛。考虑到我们讨论过的数据工程师短缺，这是一件好事。简化的趋势将持续。数据工程不依赖于特定技术或数据规模。它也不只是大公司的专利。在 2000 年代，部署“大数据”技术需要庞大的团队和雄厚的资金。SaaS 托管服务的兴起在很大程度上消除了理解各种“大数据”系统内部结构的复杂性。数据工程现在是*所有*公司都能做的事情。





# 云规模数据操作系统与互操作性的提升

大数据是其非凡成功的受害者。例如，Google BigQuery 是 GFS 和 MapReduce 的后裔，能够查询 PB 级数据。这项极其强大的技术曾仅供 Google 内部使用，如今只要拥有 GCP 账号即可使用。用户只需为存储和查询的数据付费，而无需构建庞大的基础设施栈。Snowflake、Amazon EMR 以及许多其他超大规模云数据解决方案在该领域竞争，并提供类似的能力。

云计算导致开源工具使用方式发生重大转变。即使在 2010 年代初，使用开源通常意味着下载代码并自行配置。如今，许多开源数据工具以托管云服务的形式提供，直接与专有服务竞争。所有主流云平台上的服务器实例均预装并预配置了 Linux。AWS Lambda 和 Google Cloud Functions 等无服务器平台允许你在几分钟内部署事件驱动应用，使用 Python、Java 和 Go 等主流语言，底层运行在 Linux 之上。希望使用 Apache Airflow 的工程师可以采用 Google 的 Cloud Composer 或 AWS 的托管 Airflow 服务。托管 Kubernetes 使我们能够构建高度可扩展的微服务架构。诸如此类。

这从根本上改变了关于开源代码的讨论。在许多情况下，托管开源与其专有服务竞争对手一样易于使用。具有高度专业化需求的公司也可以部署托管开源，如果后续需要定制底层代码，再迁移到自托管开源。

另一个显著趋势是开箱即用的数据连接器日益流行（撰写本文时，流行的包括 Fivetran 和 Airbyte）。数据工程师传统上花费大量时间和资源构建和维护连接外部数据源的“管道”。新一代托管连接器极具吸引力，即使对于技术极强的工程师也是如此，因为他们开始意识到夺回时间和精力用于其他项目的价值。API 连接器将成为外包问题，以便数据工程师专注于驱动其业务的独特问题。

数据工具领域的白热化竞争与日益增长的数据工程师数量相互交织，意味着数据工具将继续降低复杂性，同时增加更多功能和特性。这种简化将进一步推动数据工程实践的发展，因为越来越多的公司发现了从数据中挖掘价值的机会。

让我们简要回顾一下（单设备）操作系统的一些内部工作原理，然后将其与数据和云联系起来。无论你使用的是智能手机、笔记本电脑、应用服务器还是智能恒温器，这些设备都依赖操作系统来提供基本服务、编排任务和进程。例如，在我正在敲字的这台 MacBook Pro 上，大约能看到 300 个正在运行的进程。除其他外，我看到诸如 WindowServer（负责在图形界面中提供窗口）和 CoreAudio（负责提供低级音频功能）等服务。

当我在这台机器上运行应用程序时，它不会直接访问声音和图形硬件。相反，它向操作系统服务发送命令以绘制窗口和播放声音。这些命令通过标准 API 发送；规范告诉软件开发者如何与操作系统服务通信。操作系统*编排*启动流程以提供这些服务，根据服务间的依赖关系按正确顺序启动每个服务；它还通过监控服务并在发生故障时按正确顺序重启它们来维护服务。

现在让我们回到云端的数据。我们在本书中提到的那些简化的数据服务（例如 Google Cloud BigQuery、Azure Blob Storage、Snowflake 和 AWS Lambda）类似于操作系统服务，但规模大得多，运行在许多机器上，而非单台服务器。

现在这些简化服务已可用，这种云数据操作系统概念的下一个演进前沿将发生在更高的抽象层级。Benn Stancil 呼吁建立标准化的数据 API，用于构建数据管道和数据应用。我们预测数据工程将逐渐围绕少数几个数据互操作性标准融合。云对象存储将作为各种数据服务之间的批处理接口层，其重要性与日俱增。新一代文件格式（如 Parquet 和 Avro）已接管云数据交换的任务，在可怕的 CSV 互操作性和原始 JSON 的低性能上有了显著改进。

数据 API 生态系统的另一个关键要素是描述模式和数据层级的元数据目录。目前，这一角色主要由传统的 Hive Metastore 承担。我们预计将有新进入者出现取而代之。元数据将在数据互操作性中发挥关键作用，无论是在应用和系统之间，还是在云和网络之间，推动自动化和简化。

我们还将看到管理云数据服务的脚手架方面的显著改进。Apache Airflow 已成为首个真正面向云的数据编排平台，但我们正处于重大增强的前夜。Airflow 将凭借其庞大的心智份额不断增强能力。Dagster 和 Prefect 等新进入者将通过从头重建编排架构来竞争。

这下一代数据编排平台将具备增强的数据集成和数据感知能力。编排平台将与数据编目和血缘集成，在此过程中变得更加数据感知。此外，编排平台将构建 IaC 能力（类似 Terraform）和代码部署功能（如 GitHub Actions 和 Jenkins）。这将允许工程师编写管道代码，然后将其传递给编排平台以自动构建、测试、部署和监控。工程师将能够直接在管道中编写基础设施规范；缺失的基础设施和服务（例如 Snowflake 数据库、Databricks 集群和 Amazon Kinesis 流）将在管道首次运行时自动部署。

我们还将在*实时数据*领域看到显著增强——例如，能够摄取和查询流数据的流式管道和数据库。过去，构建流式 DAG 是一个极其复杂的过程，且具有高昂的持续运维负担（见第 8 章）。Apache Pulsar 等工具指明了未来的方向：流式 DAG 可以使用相对简单的代码部署复杂的转换。我们已经看到了托管流处理器的出现（如 Amazon Kinesis Data Analytics 和 Google Cloud Dataflow），但我们将看到新一代编排工具来管理这些服务、将它们拼接在一起并进行监控。我们将在“实时数据栈”中讨论实时数据。





这种增强的抽象对数据工程师意味着什么？正如我们在本章中已经论述的，数据工程师的角色不会消失，但将发生重大演变。打个比方，更复杂的移动操作系统和框架并没有淘汰移动应用开发人员。相反，移动应用开发人员现在可以专注于构建质量更高、更复杂的应用程序。随着云规模数据操作系统范式提高了各种应用程序和系统之间的互操作性和简易性，我们预期数据工程领域也将出现类似的发展。

# “企业级”数据工程

数据工具日益简化，最佳实践不断涌现并被记录下来，这意味着数据工程将变得更加“企业级”。^(2) 这会让许多读者感到极度不适。对某些人来说，*企业* 一词唤起的是卡夫卡式的噩梦：面目模糊的委员会成员穿着过度挺括的蓝衬衫和卡其裤，无休止的繁文缛节，以及瀑布式管理的开发项目，进度不断拖延，预算不断膨胀。简而言之，你们中的一些人一看到“企业”，就会联想到一个创新扼杀殆尽的无灵魂之地。

幸运的是，这并非我们所指；我们指的是大公司利用数据做好的一些事情——管理、运维、治理，以及其他那些“枯燥”的工作。我们正处于“企业级”数据管理工具的黄金时代。曾经为大型组织保留的技术和实践正在向下游流淌。大数据和流数据曾经困难的部分现在已在很大程度上被抽象掉了，重点转移到了易用性、互操作性和其他改进上。

这使得从事新工具开发的数据工程师能够在数据管理、DataOps 以及数据工程所有其他暗流的抽象中找到机会。数据工程师将变得“企业级”。顺便说一句……

# 职称与职责将发生变形……

虽然数据工程生命周期在可预见的未来不会消失，但软件工程、数据工程、数据科学和 ML 工程之间的界限正变得越来越模糊。事实上，像作者一样，许多数据科学家通过一个自然的过程转型为数据工程师；他们被赋予“数据科学”的任务，却缺乏完成工作的工具，于是承担起设计和构建系统的工作，以服务于数据工程生命周期。

随着简化性上移到技术栈的上层，数据科学家花在收集和清洗数据上的时间比例将变小。但这一趋势将超越数据科学家。简化也意味着数据工程师将在数据工程生命周期中花费更少的时间在低级任务上（管理服务器、配置等），而“企业级”数据工程将变得更加普遍。

随着数据更紧密地嵌入到每个企业的流程中，数据和算法领域将涌现新角色。一种可能性是介于 ML 工程和数据工程之间的角色。随着 ML 工具集变得更易用，托管云 ML 服务能力增强，ML 正从临时探索和模型开发转变为一门运维学科。

这种横跨鸿沟的新型 ML 导向工程师将了解算法、ML 技术、模型优化、模型监控和数据监控。然而，他们的主要角色将是创建或利用系统，自动训练模型、监控性能，并为已被充分理解的模型类型将完整的 ML 流程运维化。他们还将监控数据管道和质量，与当前数据工程的领域产生重叠。ML 工程师将变得更加专业化，专注于更接近研究、理解程度较低的模型类型。

职称可能发生变形的另一个领域是软件工程与数据工程的交集。融合了传统软件应用与分析的数据应用将推动这一趋势。软件工程师将需要对数据工程有深得多的理解。他们将在流处理、数据管道、数据建模和数据质量等方面建立专长。我们将超越当前普遍存在的“甩过墙头”式做法。数据工程师将融入应用开发团队，软件开发人员将获得数据工程技能。应用后端系统与数据工程工具之间的界限也将降低，通过流处理和事件驱动架构实现深度集成。

# 超越现代数据栈，迈向实时数据栈

我们直说吧：现代数据栈（MDS）并不那么现代。我们为 MDS 向大众提供一系列强大的数据工具、降低价格、赋能数据分析师掌控其数据栈而喝彩。ELT 的兴起、云数据仓库的出现，以及 SaaS 数据管道的抽象，确实改变了许多公司的游戏规则，为 BI、分析和数据科学开启了新的能力。

话虽如此，MDS 本质上是利用现代云和 SaaS 技术对旧数据仓库实践的重新包装；因为 MDS 构建在云数据仓库范式之上，与下一代实时数据应用的潜力相比，它存在一些严重局限。从我们的角度来看，世界正在超越基于数据仓库的面向内部分析和数据科学，转向利用下一代实时数据库实时驱动整个业务和应用。

是什么在推动这种演变？在许多情况下，分析（BI 和运营分析）将被自动化取代。目前，大多数仪表盘和报表回答的是 *是什么* 和 *何时* 的问题。问问自己，“如果我在问一个 *是什么* 或 *何时* 的问题，我接下来采取什么行动？”如果该行动是重复性的，它就是自动化的候选者。为什么要看报表来决定是否采取行动，而不是根据事件发生时自动执行行动呢？

这远不止于此。为什么使用 TikTok、Uber、Google 或 DoorDash 等产品会让人感觉像魔法一样？虽然在你看来只是点击一下按钮观看短视频、叫车或订餐、或找到搜索结果，但引擎盖下发生了很多事情。这些产品是真正的实时数据应用的例子，它们在点击按钮的瞬间为你提供所需的操作，同时在幕后以微小的延迟执行极其复杂的数据处理和 ML。目前，这种复杂性被锁在大型科技公司的定制技术背后，但这种复杂性和力量正变得民主化，就像 MDS 将云规模数据仓库和管道带给大众一样。数据世界即将变得“实时”。

## 流管道与实时分析数据库




MDS 将自身局限于将数据视为有界的批处理技术。相比之下，实时数据应用将数据视为无界的连续流。流式管道和实时分析数据库是将推动从 MDS 向实时数据栈演进的两大核心技术。虽然这些技术已存在一段时间，但快速成熟的托管云服务将使它们得到更广泛的部署。

在可预见的未来，流式技术将继续保持极速增长。这将伴随对流式数据业务效用的更清晰关注。直到目前，流式系统常被视为昂贵的新鲜玩意，或仅作为从 A 点到 B 点传输数据的“哑管道”。未来，流式处理将从根本上改变组织的技术和业务流程；数据架构师和工程师将引领这些根本性变革。

实时分析数据库支持对该数据的快速摄取和亚秒级查询。这些数据可以通过历史数据集进行丰富或关联。当结合流式管道和自动化，或具备实时分析能力的仪表盘时，全新层面的可能性将随之开启。你不再受限于缓慢运行的 ELT 流程、15 分钟一次的更新，或其他迟缓的环节。数据以连续流的形式移动。随着流式摄取变得更加普遍，批量摄取将变得越来越少见。为什么要在数据管道的源头制造批处理瓶颈？我们最终看待批量摄取的方式，将如同我们现在看待拨号调制解调器一样。

随着流式处理的兴起，我们预计数据转换将迎来一个“回归未来”的时刻。我们将从 ELT（数据库内转换）转向更像 ETL 的模式。我们暂时称之为*流式处理、转换和加载*（STL）。在流式上下文中，提取是一个持续的、连续的过程。当然，批量转换不会完全消失。批处理对于模型训练、季度报告等仍非常有用。但流式转换将成为常态。

虽然数据仓库和数据湖非常适合存储大量数据和执行临时查询，但它们并未针对低延迟数据摄取或快速移动数据上的查询进行良好优化。实时数据栈将由专为流式处理构建的 OLAP 数据库提供支持。如今，`Druid`、`ClickHouse`、`Rockset` 和 `Firebolt` 等数据库正引领潮流，为下一代数据应用的后端提供动力。我们预计流式技术将继续快速演进，新技术将层出不穷。

我们认为另一个适合颠覆的领域是数据建模，自 2000 年代初以来，该领域鲜有重大创新。你在第 8 章中了解到的传统面向批处理的数据建模技术，不适用于流式数据。新的数据建模技术将不在数据仓库中发生，而是发生在生成数据的系统中。我们预计数据建模将涉及某种上游定义层的概念——包括语义、指标、血缘和数据定义（参见第 9 章）——始于应用程序中数据生成之处。建模也将在数据流经完整生命周期的每个阶段发生，随着数据的流动和演变而进行。

## 数据与应用的融合

我们预计下一场革命将是应用层与数据层的融合。目前，应用位于一侧，而 MDS 位于另一侧。更糟糕的是，数据的创建未考虑其如何用于分析。因此，需要大量“胶带代码”来让系统相互通信。这种拼凑的、孤岛式的设置既笨拙又难看。

很快，应用栈将成为数据栈，反之亦然。应用将集成实时自动化和决策，由流式管道和 ML 提供支持。数据工程生命周期不一定会改变，但生命周期各阶段之间的时间将大幅缩短。大量创新将发生在改进实时数据栈工程体验的新技术和实践中。请关注旨在解决 OLTP 和 OLAP 混合用例的新兴数据库技术；特征存储也可能为 ML 用例扮演类似角色。

## 应用与 ML 之间的紧密反馈

另一个令我们兴奋的领域是应用与 ML 的融合。如今，应用和 ML 是分离的系统，就像应用和分析一样。软件工程师在这边做他们的事，数据科学家和 ML 工程师在那边做他们的事。

ML 非常适合数据以如此高速率和大量生成、以至于人类无法手动处理的场景。随着数据规模和速度的增长，这适用于所有场景。大量高速移动的数据，加上复杂的工作流和操作，都是 ML 的候选对象。随着数据反馈循环变短，我们预计大多数应用将集成 ML。随着数据移动得更快，应用与 ML 之间的反馈循环将更加紧密。实时数据栈中的应用是智能的，能够实时适应数据变化。这创造了一个不断变得更智能的应用和不断增加的业务价值的循环。

## 暗物质数据与……电子表格的崛起？！

我们讨论了快速移动的数据，以及随着应用、数据和 ML 更紧密地协作，反馈循环将如何缩短。本节可能看起来很奇怪，但我们需要解决当今数据世界中被广泛忽视的问题，尤其是工程师们。

使用最广泛的数据平台是什么？它是不起眼的电子表格。根据你读到的估算，电子表格的用户群在 7 亿到 20 亿人之间。电子表格是数据世界的暗物质。相当一部分数据分析在电子表格中运行，从未进入本书描述的那些复杂数据系统。在许多组织中，电子表格处理财务报告、供应链分析，甚至 CRM。

从本质上讲，什么是电子表格？*电子表格*是一种支持复杂分析的交互式数据应用。与纯代码工具（如 `pandas` [Python 数据分析库]）不同，电子表格面向整个用户谱系，从只会打开文件查看报告的人，到能编写复杂程序化数据处理脚本的高级用户。到目前为止，BI 工具未能为数据库带来可比拟的交互性。与 UI 交互的用户通常局限于在特定护栏内切片和切块数据，而非通用的可编程分析。

我们预测，一类新工具将会出现，它将电子表格的交互式分析能力与云 OLAP 系统的后端强大功能相结合。确实，已有一些候选者进入竞争行列。该产品类别的最终赢家可能继续沿用电子表格范式，也可能为与数据交互定义全新的界面习语。
