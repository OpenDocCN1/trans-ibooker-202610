
原则上，网络安全应由贵公司的安全专家负责。（实际上，在小公司中，您可能需要承担网络安全的主要责任。）作为数据工程师，您将频繁接触数据库、对象存储和服务器，因此您至少应了解可以采取的简单措施，以确保您符合良好的网络访问实践。了解哪些 IP 和端口是开放的、对谁开放以及为什么开放。仅允许将访问这些端口的系统和用户的传入 IP 地址（即 IP 白名单），并避免因任何原因广泛开放连接。访问云或 SaaS 工具时，请使用加密连接。例如，不要在咖啡厅使用未加密的网站。

此外，虽然本书几乎完全专注于在云中运行工作负载，但我们在此简要提及本地托管服务器。回顾一下，在[第 3 章](#ch03.html#designing_good_data_architecture)中，我们讨论了强化边界与零信任安全的区别。云通常更接近零信任安全——每个操作都需要身份验证。我们认为，对于大多数组织而言，云是一个更安全的选择，因为它强制实施零信任实践，并允许公司利用公有云雇佣的庞大安全工程师团队。

然而，有时强化边界安全仍然讲得通；我们知道核导弹发射井是气隙隔离的（未连接到任何网络），这让我们多少感到些许安慰。气隙隔离服务器是强化安全边界的终极示例。请记住，即使在本地部署，气隙隔离服务器也容易受到人为安全失误的影响。

## 面向底层数据工程的安全

对于在数据存储和处理系统核心工作的工程师来说，考虑每个元素的安全影响至关重要。任何软件库、存储系统或计算节点都是潜在的安全漏洞。一个不起眼的日志库中的缺陷可能允许攻击者绕过访问控制或加密。即使是 CPU 架构和微代码也代表潜在漏洞；当敏感数据静止在内存或 CPU 缓存中时，它可能[处于脆弱状态](https://meltdownattack.com)。链条上的任何一环都不能掉以轻心。

当然，本书主要关注高层数据工程——将工具拼接在一起以处理整个生命周期。因此，我们将那些血腥的技术细节留给您自行深入挖掘。

### 内部安全研究

我们在[“流程”](#ch10.html#processes)中讨论了*主动安全*的理念。我们还强烈建议采用*主动安全*方法对待技术。具体来说，这意味着每一位技术员工都应思考安全问题。

为什么这很重要？每一位技术贡献者都会形成自己的技术专长领域。即使您的公司雇佣了一支庞大的安全研究团队，数据工程师也会对其职责范围内的特定数据系统和云服务变得极其熟悉。特定技术的专家处于有利位置，能够识别该技术中的安全漏洞。

鼓励每一位数据工程师积极参与安全工作。当他们在其系统中识别出潜在安全风险时，应思考缓解措施，并在部署这些措施中发挥积极作用。

# 结语

安全需要成为一种思维和行动的习惯；像对待钱包或智能手机一样对待数据。虽然您不太可能负责公司的安全，但了解基本安全实践并时刻牢记安全，将有助于降低贵组织发生数据安全漏洞的风险。

# 第 11 章 数据工程的未来

本书源于作者们的认识：该领域以变形般的速度变化，为现有数据工程师、有意转行从事数据工程的人员、技术管理者以及希望更好地了解数据工程如何融入其公司的高管，造成了显著的知识鸿沟。当我们开始思考如何组织本书时，朋友们曾强烈反对，问道：“你们怎么敢写一个变化如此之快的领域？！”在很多方面，他们是对的。数据工程领域——实际上，所有与数据相关的事物——确实感觉在每天都在变化。在撰写和组织本书时，从噪音中筛选出*不太可能改变*的信号，是最具挑战性的部分之一。

在本书中，我们关注未来几年内我们认为有用的宏大理念——因此有了数据工程生命周期及其暗流的连续体。最佳实践和技术的操作顺序和名称可能会改变，但生命周期的主要阶段在未来许多年内很可能保持完整。我们敏锐地意识到技术仍在以令人筋疲力竭的速度持续变化；在当今时代从事技术行业，感觉就像坐过山车，或者可能像在镜子迷宫中穿行。

几年前，数据工程甚至不存在作为一个领域或职位名称。现在您正在阅读一本名为《数据工程基础》的书！您已经了解了数据工程的基础知识——其生命周期、暗流、技术和最佳实践。您可能会问自己，数据工程的下一步是什么？虽然没人能预测未来，但我们对过去、现在和当前趋势有很好的视角。我们有幸从前排座位上见证了数据工程的起源和演变。最后一章呈现了我们对未来的思考，包括对正在进行的发展的观察和大胆的未来推测。

## 数据工程生命周期不会消失

虽然近年来数据科学获得了大部分关注，但数据工程正迅速成熟为一个独特且可见的领域。它是技术领域增长最快的职业之一，没有失去势头的迹象。随着公司意识到在转向“更性感”的 AI 和 ML 之前，首先需要建立数据基础，数据工程将继续增长其受欢迎度和重要性。这一进程以数据工程生命周期为中心。

有人质疑日益简化的工具和实践是否会导致数据工程师的消失。这种想法是肤浅、懒惰和短视的。随着组织以新方式利用数据，将需要新的基础、系统和工作流来满足这些需求。数据工程师处于设计、架构、构建和维护这些系统的核心位置。如果工具变得更易用，数据工程师将向价值链上游移动，专注于更高层次的工作。数据工程生命周期在可预见的未来不会消失。

## 复杂性的衰退与易用数据工具的兴起

简化、易用的工具持续降低数据工程的入门门槛。考虑到我们讨论过的数据工程师短缺，这是一件好事。简化的趋势将持续。数据工程不依赖于特定技术或数据规模。它也不只是大公司的专利。在 2000 年代，部署“大数据”技术需要庞大的团队和雄厚的资金。SaaS 托管服务的兴起在很大程度上消除了理解各种“大数据”系统内部结构的复杂性。数据工程现在是*所有*公司都能做的事情。
