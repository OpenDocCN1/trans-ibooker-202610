
在[“数据存储的原始要素”](#ch06.html#raw_ingredients_of_data_storage)中，我们讨论了列式序列化。*列式序列化*允许数据库仅扫描特定查询所需的列，有时能大幅减少从磁盘读取的数据量。此外，按列排列数据将相似的值紧密地放在一起，以最小的压缩开销产生高压缩比。这使得数据能更快地从磁盘和网络上扫描。

列式数据库在事务性用例中表现不佳——即当我们尝试异步查找大量单个行时。然而，当必须扫描大量数据时——例如复杂的数据转换、聚合、统计计算或对大型数据集进行复杂条件评估时——它们表现极佳。

过去，列式数据库在连接操作上表现不佳，因此给数据工程师的建议是反规范化数据，尽可能使用宽模式、数组和嵌套数据。近年来，列式数据库的连接性能有了显著提升，因此虽然反规范化仍可能带来性能优势，但这不再是必需。您将在[第 8 章](#ch08.html#queriescomma_modelingcomma_and_transfor)中了解更多关于规范化和反规范化的内容。

### 从索引到分区和聚类

虽然列式数据库允许快速扫描速度，但尽可能减少扫描的数据量仍然很有帮助。除了仅扫描与查询相关的列中的数据外，我们还可以通过按字段拆分将一个表分区为多个子表。在分析和数据科学用例中，按时间范围扫描非常常见，因此基于日期和时间的分区极为常见。列式数据库通常也支持多种其他分区方案。

*聚类*允许在分区内对数据进行更细粒度的组织。应用于列式数据库中的聚类方案按一个或几个字段对数据进行排序，将相似的值放在一起。这提高了过滤、排序和连接这些值的性能。

### 示例：Snowflake 微分区

我们提到 Snowflake [微分区](https://oreil.ly/nQTaP)，因为它是列式存储方法近期发展和演变的一个很好的例子。*微分区*是未压缩大小在 50 到 500 兆字节之间的行集合。Snowflake 采用算法方法尝试将相似的行聚类在一起。这与基于单个指定字段（如日期）进行分区的传统简单方法形成对比。Snowflake 专门寻找在许多行中某字段重复的值。这允许基于谓词对查询进行激进的*剪枝*。例如，`WHERE` 子句可能规定如下：

```
WHERE created_date='2022-01-02'
```

在这样的查询中，Snowflake 会排除任何不包含该日期的微分区，从而有效地剪枝这些数据。Snowflake 还允许重叠的微分区，可能基于多个显示显著重复的字段进行分区。

高效的剪枝得益于 Snowflake 的元数据库，它存储了每个微分区的描述，包括行数和字段的值范围。在每个查询阶段，Snowflake 分析微分区以确定哪些需要扫描。Snowflake 使用*混合列式存储*一词，^([2](#ch06.html#ch01fn56)) 部分指的是其表被分解成小行组，尽管存储从根本上说是列式的。元数据库扮演的角色类似于传统关系数据库中的索引。

# 数据工程存储抽象

*数据工程存储抽象*是位于数据工程生命周期核心的数据组织和查询模式，构建在先前讨论的数据存储系统之上（参见[图 6-3](#ch06.html#magnetic_disk_head_movement_and_rotatio)）。我们在[第 3 章](#ch03.html#designing_good_data_architecture)中介绍了许多此类抽象，并将在此重新审视它们。

我们将关注的主要抽象类型是那些支持数据科学、分析和报告用例的类型。这些包括数据仓库、数据湖、数据湖屋、数据平台和数据目录。我们不会涵盖源系统，因为它们在[第 5 章](#ch05.html#data_generation_in_source_systems)中讨论。

作为数据工程师，您所需的存储抽象归结为几个关键考量：

目的和用例

： 

您必须首先确定存储数据的目的。它用于什么？

更新模式

： 

该抽象是针对批量更新、流式插入还是更新插入进行优化的？

成本

： 

直接和间接的财务成本是什么？价值实现时间？机会成本？

分离存储和计算

： 

趋势是分离存储和计算，但大多数系统混合了分离和共置。我们在[“计算与存储的分离”](#ch06.html#separation_of_compute_from_storage)中介绍这一点，因为它影响目的、速度和成本。

您应该知道，分离存储和计算的流行意味着 OLAP 数据库和数据湖之间的界限日益模糊。主要的云数据仓库和数据湖正处于碰撞轨道上。未来，这两者的区别可能仅在于名称，因为它们在功能和技术上可能在底层非常相似。

## 数据仓库

数据仓库是标准的 OLAP 数据架构。正如[第 3 章](#ch03.html#designing_good_data_architecture)所讨论的，*数据仓库*一词指的是技术平台（如 Google BigQuery 和 Teradata）、数据集中化的架构以及公司内部的组织模式。就存储趋势而言，我们已从在传统事务数据库、基于行的 MPP 系统（如 Teradata 和 IBM Netezza）以及列式 MPP 系统（如 Vertica 和 Teradata Columnar）之上构建数据仓库，演变为云数据仓库和数据平台。（有关 MPP 系统的更多详细信息，请参阅我们在[第 3 章](#ch03.html#designing_good_data_architecture)中的数据仓库讨论。）

在实践中，云数据仓库常被用来将数据组织到数据湖中，数据湖是海量未处理原始数据的存储区域，最初由 James Dixon 构想。^([3](#ch06.html#ch01fn57)) 云数据仓库可以处理海量原始文本和复杂的 JSON 文档。局限在于云数据仓库无法处理真正的非结构化数据，如图像、视频或音频，这与真正的数据湖不同。云数据仓库可以与对象存储结合，提供完整的数据湖解决方案。

## 数据湖

*数据湖*最初被构想为一个海量存储，其中数据以原始、未处理的形式保留。最初，数据湖主要构建在 Hadoop 系统上，廉价存储允许保留海量数据，而无需专有 MPP 系统的成本开销。

过去五年见证了数据湖存储演变中的两大主要发展。首先，发生了向*计算与存储分离*的大规模迁移。在实践中，这意味着从 Hadoop 迁移到云对象存储以实现数据的长期保留。其次，数据工程师发现，MPP 系统提供的许多功能（模式管理；更新、合并和删除能力）在冲向数据湖的浪潮中最初被忽视，但实际上极其有用。这导致了数据湖屋的概念。
