

# 云规模数据操作系统与互操作性的提升

大数据是其非凡成功的受害者。例如，Google BigQuery 是 GFS 和 MapReduce 的后裔，能够查询 PB 级数据。这项极其强大的技术曾仅供 Google 内部使用，如今只要拥有 GCP 账号即可使用。用户只需为存储和查询的数据付费，而无需构建庞大的基础设施栈。Snowflake、Amazon EMR 以及许多其他超大规模云数据解决方案在该领域竞争，并提供类似的能力。

云计算导致开源工具使用方式发生重大转变。即使在 2010 年代初，使用开源通常意味着下载代码并自行配置。如今，许多开源数据工具以托管云服务的形式提供，直接与专有服务竞争。所有主流云平台上的服务器实例均预装并预配置了 Linux。AWS Lambda 和 Google Cloud Functions 等无服务器平台允许你在几分钟内部署事件驱动应用，使用 Python、Java 和 Go 等主流语言，底层运行在 Linux 之上。希望使用 Apache Airflow 的工程师可以采用 Google 的 Cloud Composer 或 AWS 的托管 Airflow 服务。托管 Kubernetes 使我们能够构建高度可扩展的微服务架构。诸如此类。

这从根本上改变了关于开源代码的讨论。在许多情况下，托管开源与其专有服务竞争对手一样易于使用。具有高度专业化需求的公司也可以部署托管开源，如果后续需要定制底层代码，再迁移到自托管开源。

另一个显著趋势是开箱即用的数据连接器日益流行（撰写本文时，流行的包括 Fivetran 和 Airbyte）。数据工程师传统上花费大量时间和资源构建和维护连接外部数据源的“管道”。新一代托管连接器极具吸引力，即使对于技术极强的工程师也是如此，因为他们开始意识到夺回时间和精力用于其他项目的价值。API 连接器将成为外包问题，以便数据工程师专注于驱动其业务的独特问题。

数据工具领域的白热化竞争与日益增长的数据工程师数量相互交织，意味着数据工具将继续降低复杂性，同时增加更多功能和特性。这种简化将进一步推动数据工程实践的发展，因为越来越多的公司发现了从数据中挖掘价值的机会。

让我们简要回顾一下（单设备）操作系统的一些内部工作原理，然后将其与数据和云联系起来。无论你使用的是智能手机、笔记本电脑、应用服务器还是智能恒温器，这些设备都依赖操作系统来提供基本服务、编排任务和进程。例如，在我正在敲字的这台 MacBook Pro 上，大约能看到 300 个正在运行的进程。除其他外，我看到诸如 WindowServer（负责在图形界面中提供窗口）和 CoreAudio（负责提供低级音频功能）等服务。

当我在这台机器上运行应用程序时，它不会直接访问声音和图形硬件。相反，它向操作系统服务发送命令以绘制窗口和播放声音。这些命令通过标准 API 发送；规范告诉软件开发者如何与操作系统服务通信。操作系统*编排*启动流程以提供这些服务，根据服务间的依赖关系按正确顺序启动每个服务；它还通过监控服务并在发生故障时按正确顺序重启它们来维护服务。

现在让我们回到云端的数据。我们在本书中提到的那些简化的数据服务（例如 Google Cloud BigQuery、Azure Blob Storage、Snowflake 和 AWS Lambda）类似于操作系统服务，但规模大得多，运行在许多机器上，而非单台服务器。

现在这些简化服务已可用，这种云数据操作系统概念的下一个演进前沿将发生在更高的抽象层级。Benn Stancil 呼吁建立标准化的数据 API，用于构建数据管道和数据应用。我们预测数据工程将逐渐围绕少数几个数据互操作性标准融合。云对象存储将作为各种数据服务之间的批处理接口层，其重要性与日俱增。新一代文件格式（如 Parquet 和 Avro）已接管云数据交换的任务，在可怕的 CSV 互操作性和原始 JSON 的低性能上有了显著改进。

数据 API 生态系统的另一个关键要素是描述模式和数据层级的元数据目录。目前，这一角色主要由传统的 Hive Metastore 承担。我们预计将有新进入者出现取而代之。元数据将在数据互操作性中发挥关键作用，无论是在应用和系统之间，还是在云和网络之间，推动自动化和简化。

我们还将看到管理云数据服务的脚手架方面的显著改进。Apache Airflow 已成为首个真正面向云的数据编排平台，但我们正处于重大增强的前夜。Airflow 将凭借其庞大的心智份额不断增强能力。Dagster 和 Prefect 等新进入者将通过从头重建编排架构来竞争。

这下一代数据编排平台将具备增强的数据集成和数据感知能力。编排平台将与数据编目和血缘集成，在此过程中变得更加数据感知。此外，编排平台将构建 IaC 能力（类似 Terraform）和代码部署功能（如 GitHub Actions 和 Jenkins）。这将允许工程师编写管道代码，然后将其传递给编排平台以自动构建、测试、部署和监控。工程师将能够直接在管道中编写基础设施规范；缺失的基础设施和服务（例如 Snowflake 数据库、Databricks 集群和 Amazon Kinesis 流）将在管道首次运行时自动部署。

我们还将在*实时数据*领域看到显著增强——例如，能够摄取和查询流数据的流式管道和数据库。过去，构建流式 DAG 是一个极其复杂的过程，且具有高昂的持续运维负担（见第 8 章）。Apache Pulsar 等工具指明了未来的方向：流式 DAG 可以使用相对简单的代码部署复杂的转换。我们已经看到了托管流处理器的出现（如 Amazon Kinesis Data Analytics 和 Google Cloud Dataflow），但我们将看到新一代编排工具来管理这些服务、将它们拼接在一起并进行监控。我们将在“实时数据栈”中讨论实时数据。
