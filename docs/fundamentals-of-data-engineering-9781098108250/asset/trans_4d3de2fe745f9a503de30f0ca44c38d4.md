

# 存储引擎

存储引擎在 2000 年代和 2010 年代经历了重大创新。过去的存储引擎针对旋转磁盘的直接访问进行了优化，而现代存储引擎则针对 SSD 的性能特征进行了更好的优化。存储引擎还为现代类型和数据结构提供了改进的支持，例如变长字符串、数组和嵌套数据。

存储引擎的另一个重大变化是转向面向分析和数据仓库应用的列式存储。`SQL Server`、`PostgreSQL` 和 `MySQL` 都提供了强大的列式存储支持。

# 压缩：gzip、bzip2、Snappy 等

压缩算法背后的数学原理很复杂，但基本思想很容易理解：压缩算法在数据中寻找冗余和重复，然后重新编码数据以减少冗余。当我们想要读取原始数据时，通过反转算法并将冗余加回去来对其进行*解压*。

例如，你可能注意到阅读本书时某些单词反复出现。对文本运行一些快速分析，你可以识别出最高频的单词并为这些单词创建缩短的标记。要压缩，你将用它们的标记替换常用单词；要解压，你将用各自的单词替换标记。

也许我们可以用这种朴素的技术实现 2:1 或更高的压缩比。压缩算法利用更复杂的数学技术来识别和消除冗余；它们通常能在文本数据上实现 10:1 的压缩比。

请注意，我们讨论的是*无损压缩算法*。使用无损算法编码的数据解压后，能恢复出与原始数据逐位完全相同的副本。*有损压缩算法*用于音频、图像和视频，旨在保真感官体验；解压恢复的内容听起来或看起来像原始内容，但并非逐位完全相同的副本。数据工程师可能会在媒体处理管道中处理有损压缩算法，但不会在用于分析的序列化中使用，因为后者要求精确的数据保真度。

传统压缩引擎如 `gzip` 和 `bzip2` 对文本数据压缩效果极好；它们经常被应用于 `JSON`、`JSONL`、`XML`、`CSV` 和其他基于文本的数据格式。近年来，工程师们创造了一代新的压缩算法，优先考虑速度和 CPU 效率，而非压缩比。主要例子包括 `Snappy`、`Zstandard`、`LZFSE` 和 `LZ4`。这些算法常用于压缩数据湖或列式数据库中的数据，以优化快速查询性能。

# 附录 B：云网络

本附录讨论了数据工程师应考虑的云网络因素。数据工程师在其职业生涯中经常遇到网络问题，但尽管网络很重要，却往往忽视它。

## 云网络拓扑

*云网络拓扑*描述了云中各种组件的排列和连接方式，例如云服务、网络、位置（可用区、区域）等。数据工程师应始终了解云网络拓扑将如何影响他们构建的数据系统之间的连接性。`Microsoft Azure`、`Google Cloud Platform (GCP)` 和 `Amazon Web Services (AWS)` 都使用非常相似的可用区和区域资源层级结构。在撰写本文时，`GCP` 增加了一个额外的层级，详见 [GCP 特定的网络和多区域冗余](#gcp-specific-networking-and-multiregional-redundancy)。

## 数据流出费用

[第 4 章](#ch04.html#choosing_technologies_across_the_data_e)讨论了云经济学，以及实际提供商成本不一定驱动云定价。关于网络，云允许免费入站流量，但对出站流量到互联网收费。出站流量本身并不更便宜，但云利用这种方法在其服务周围建立护城河，增加存储数据的粘性，这种做法受到广泛批评。^([1](#app02.html#ch01fn86)) 请注意，数据流出费用也可能适用于云内可用区和区域之间传输的数据。

## 可用区

*可用区*是公有云向客户可见的最小网络拓扑单元（图 B-1）。虽然一个可用区可能由多个数据中心组成，但云客户无法在此层级控制资源放置。

![](assets/fode_B001.png)

通常，云支持同一可用区内系统和服务之间的最高网络带宽和最低延迟。出于性能和成本原因，高吞吐量数据工作负载应运行在位于单个可用区内的集群上。例如，临时的 `Amazon EMR` 集群通常应位于单个可用区内。

此外，发送给可用区内虚拟机的网络流量是免费的，但有一个重要警告：流量必须发送到私有 IP 地址。主要云利用称为*虚拟私有云 (VPC)* 的虚拟网络。虚拟机在 VPC 内拥有私有 IP 地址。它们也可能被分配公有 IP 地址，以便与外部世界通信并接收来自互联网的流量，但使用外部 IP 地址进行通信可能会产生数据流出费用。

## 区域

*区域*是两个或多个可用区的集合。数据中心运行需要许多资源（电力、水等）。独立可用区的资源是相互独立的，因此局部停电不会导致多个可用区宕机。工程师可以通过在多个可用区运行服务器或创建自动化的跨可用区故障转移流程，即使在单个区域内也能构建高弹性的独立基础设施。

提供多个区域允许工程师将资源放置在靠近其任何用户的地方。*靠近*意味着用户连接服务时能获得良好的网络性能，最小化网络路径上的物理距离，并减少通过路由器的跳数。物理距离和网络跳数都会增加延迟并降低性能。主要云提供商持续增加新区域。

通常，区域支持区域间快速、低延迟的网络；区域间的网络性能将差于单个可用区内，且虚拟机之间会产生名义上的数据流出费用。区域间的网络数据移动甚至更慢，并可能产生更高的流出费用。

通常，对象存储是区域级资源。某些数据可能在可用区之间传输以到达虚拟机，但这主要对云客户不可见，且对此没有直接的网络费用。（当然，客户仍需承担对象访问成本。）

尽管区域具有异地冗余设计，但许多重大云服务故障已影响整个区域，这是*关联故障*的一个例子。工程师通常将代码和配置部署到整个区域；我们观察到的区域故障通常源于发生在区域层面的代码或配置问题。

## GCP 特定的网络和多区域冗余

`GCP` 提供了一些独特的抽象，如果工程师在此云中工作，应该了解这些抽象。第一个是*多区域*，资源层级中的一个层；一个多区域包含多个区域。当前的多区域有 `US`（美国的数据中心）、`EU`（欧盟成员国的数据中心）和 `ASIA`。
