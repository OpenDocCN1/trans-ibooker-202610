
在实践中，无论采用哪种高级工具，数据工程师都会在数据工程生命周期中遇到各种棘手问题，这些问题要求他们在所选工具的边界之外解决问题并编写自定义代码。在使用 Fivetran、Airbyte 或 Matillion 等框架时，数据工程师会遇到没有现有连接器的数据源，需要编写自定义代码。他们应精通软件工程，以理解 API、拉取和转换数据、处理异常等。

# 结论

我们过去看到的关于数据工程的大多数讨论都涉及技术，但忽略了数据生命周期管理的大局。随着技术变得更加抽象并承担更多繁重工作，数据工程师有机会在更高层面上思考和行动。数据工程生命周期及其暗流是组织数据工程工作的极其有用的思维模型。

我们将数据工程生命周期分为以下阶段：

*   生成
*   存储
*   摄入
*   转换
*   数据服务

有几个主题贯穿数据工程生命周期。这些是数据工程生命周期的暗流。在高层面上，暗流包括：

*   安全
*   数据管理
*   DataOps
*   数据架构
*   编排
*   软件工程

数据工程师在数据生命周期中有几个顶层目标：产生最佳 ROI 并降低成本（财务和机会成本）、降低风险（安全、数据质量），以及最大化数据价值和效用。

接下来两章将讨论这些要素如何影响良好的架构设计，以及如何选择合适的技术。如果您对这两个主题已经很熟悉，可以直接跳到 [第 2 部分](#part02.html#part2)，我们将介绍数据工程生命周期的每个阶段。

# 第 3 章 设计良好的数据架构

良好的数据架构为数据生命周期和暗流的每一步提供无缝能力。我们将首先定义*数据架构*，然后讨论组件和考量因素。接着我们将涉及特定的批处理模式（数据仓库、数据湖）、流处理模式，以及统一批处理和流处理的模式。贯穿始终，我们将强调利用云能力来提供可扩展性、可用性和可靠性。

# 什么是数据架构？

成功的数据工程建立在坚实的数据架构之上。本章旨在回顾几种流行的架构方法和框架，然后给出我们对什么是“良好”数据架构的观点定义。确实，我们无法让所有人满意。不过，我们将提出一个务实的、特定领域的、可操作的*数据架构*定义，我们认为这适用于规模、业务流程和需求截然不同的公司。

什么是数据架构？当你停下来拆解它时，这个话题变得有点模糊；研究数据架构会产生许多不一致且往往过时的定义。这很像我们在[第 1 章](#ch01.html#data_engineering_described)中定义*数据工程*时的情况——没有共识。在一个不断变化的领域中，这是意料之中的。那么，就本书而言，*数据架构*意味着什么？在定义该术语之前，理解其所处的上下文至关重要。让我们简要介绍企业架构，这将为我们的数据架构定义提供框架。

## 企业架构定义

企业架构有许多子集，包括业务、技术、应用和数据（[图 3-1](#ch03.html#data_architecture_is_a_subset_of_enterp)）。因此，有许多框架和资源专门用于企业架构。事实上，架构是一个令人惊讶的有争议的话题。

![](assets/fode_0301.png)

*企业*一词引起的反应不一。它让人联想到无菌的公司办公室、命令控制/瀑布式规划、停滞的商业文化和空洞的流行语。即便如此，我们仍能从中学到一些东西。

在定义和描述*企业架构*之前，让我们先拆解这个术语。让我们看看一些重要思想领袖是如何定义企业架构的：TOGAF、Gartner 和 EABOK。
