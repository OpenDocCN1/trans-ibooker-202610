

# 列式存储与压缩

将数据作为列存储也会将相似的值放在一起，从而使我们能够高效地对列式数据进行编码。一种常见技术是查找重复值并对这些值进行标记化，这是一种简单但对于包含大量重复值的列而言高效的压缩方法。

即使列不包含大量重复值，它们也可能表现出高冗余。假设我们将客户支持消息组织成单个数据列。我们很可能会在这些消息中反复看到相同的主题和措辞，从而使数据压缩算法能够实现高压缩比。因此，列式存储通常与压缩相结合，使我们能够最大化磁盘和网络带宽资源。

列式存储和压缩也带来了一些缺点。我们无法轻松访问单个数据记录；必须通过从多个列文件读取数据来重建记录。记录更新也颇具挑战性。要更改一条记录中的一个字段，我们必须解压列文件、修改它、重新压缩它，并将其写回存储。为了避免每次更新都重写整个列，列会被拆分成许多文件，通常使用分区和聚类策略，根据表的查询和更新模式来组织数据。即便如此，更新单行的开销也是巨大的。列式数据库极不适合事务型工作负载，因此事务型数据库通常采用某种形式的行式或记录导向存储。

## Parquet

`Parquet` 以列式格式存储数据，旨在在数据湖环境中实现卓越的读写性能。`Parquet` 解决了经常困扰数据工程师的几个问题。与 `CSV` 不同，`Parquet` 编码的数据内置了模式信息，并原生支持嵌套数据。此外，`Parquet` 具有可移植性；虽然 `BigQuery` 和 `Snowflake` 等数据库以专有列式格式序列化数据，并在内部存储的数据上提供卓越的查询性能，但与外部工具互操作时会发生巨大的性能损失。数据必须被反序列化、重新序列化为可交换格式并导出，才能使用 `Spark` 和 `Presto` 等数据湖工具。在多语言工具环境中，数据湖中的 `Parquet` 文件可能比专有云数据仓库是更优的选择。

`Parquet` 格式可与多种压缩算法配合使用；针对速度优化的压缩算法（如 `Snappy`，稍后在本附录中讨论）尤其流行。

## ORC

`优化行列式 (ORC)` 是一种类似于 `Parquet` 的列式存储格式。`ORC` 曾广泛用于 `Apache Hive`；虽然仍被广泛使用，但我们通常看到它的频率远低于 `Apache Parquet`，且在现代云生态系统工具中享受的支持稍少。例如，`Snowflake` 和 `BigQuery` 支持 `Parquet` 文件的导入和导出；虽然它们可以从 `ORC` 文件读取数据，但这两个工具都无法导出到 `ORC`。

## Apache Arrow 或内存序列化

当我们在本章开头将序列化作为存储原料引入时，我们提到软件可以将数据存储在通过指针连接的分散在内存中的复杂对象里，或者存储在更有序、紧密打包的结构中，如 `Fortran` 和 `C` 数组。通常，紧密打包的内存数据结构仅限于简单类型（如 `INT64`）或固定宽度数据结构（如固定宽度字符串）。更复杂的结构（如 `JSON` 文档）无法紧密存储在内存中，且需要序列化才能在系统间进行存储和传输。

[`Apache Arrow`](https://arrow.apache.org) 的理念是通过利用一种适合内存处理和导出的二进制数据格式，来重新思考序列化。^([1](#app01.html#ch01fn85)) 这使我们能够避免序列化和反序列化的开销；我们只需对内存处理、网络导出和长期存储使用相同的格式。`Arrow` 依赖列式存储，其中每个列本质上获得自己的内存块。对于嵌套数据，我们使用一种称为 `shredding`（碎片化/拆分）的技术，将 `JSON` 文档模式中的每个位置映射到一个单独的列。

这项技术意味着我们可以将数据文件存储在磁盘上，通过虚拟内存直接将其换入程序地址空间，并在没有反序列化开销的情况下开始针对数据运行查询。事实上，当我们扫描文件时，可以将文件块换入内存，然后再换出，以避免大型数据集耗尽内存。

这种方法一个显而易见的麻烦是不同编程语言以不同方式序列化数据。为了解决这个问题，`Arrow` 项目为多种编程语言（包括 `C`、`Go`、`Java`、`JavaScript`、`MATLAB`、`Python`、`R` 和 `Rust`）创建了软件库，允许这些语言在内存中与 `Arrow` 数据互操作。在某些情况下，这些库使用所选语言与另一种语言（如 `C`）中的底层代码之间的接口来读写 `Arrow`。这使得语言之间无需额外的序列化开销即可实现高互操作性。例如，`Scala` 程序可以使用 `Java` 库写入 Arrow 数据，然后将其作为消息传递给 `Python` 程序。

`Arrow` 正在各种流行框架（如 `Apache Spark`）中得到快速采用。`Arrow` 还催生了一款新的数据仓库产品；[`Dremio`](https://www.dremio.com) 是一个围绕 `Arrow` 序列化构建的查询引擎和数据仓库，旨在支持快速查询。

# 混合序列化

我们使用术语 `混合序列化` 来指代结合多种序列化技术或将序列化与额外抽象层（如模式管理）集成的技术。我们以 `Apache Hudi` 和 `Apache Iceberg` 为例。

## Hudi

`Hudi` 代表 `Hadoop Update Delete Incremental`（Hadoop 更新删除增量）。这种表管理技术结合了多种序列化技术，既能为分析查询提供列式数据库性能，又支持原子性、事务性更新。典型的 `Hudi` 应用是一个从事务型应用数据库的 `CDC` 流中更新的表。该流被捕获到行式序列化格式中，而表的主体部分保留在列式格式中。查询同时在列式和行式文件上运行，以返回表当前状态的结果。定期运行一个重新打包进程，将行式和列式文件合并为更新后的列式文件，以最大化查询效率。

## Iceberg

与 `Hudi` 一样，`Iceberg` 也是一种表管理技术。`Iceberg` 可以跟踪构成表的所有文件。它还可以跟踪随时间推移每个表快照中的文件，从而在数据湖环境中实现表时间旅行。`Iceberg` 支持模式演进，并能轻松管理 PB 级规模的表。

# 数据库存储引擎

为了完善关于序列化的讨论，我们简要讨论数据库存储引擎。所有数据库都有底层存储引擎；许多数据库不将其存储引擎作为单独的抽象暴露出来（例如 `BigQuery`、`Snowflake`）。一些数据库（特别是 `MySQL`）支持完全可插拔的存储引擎。其他数据库（如 `SQL Server`）提供主要的存储引擎配置选项（列式存储与行式存储），这些选项会极大地影响数据库行为。

通常，存储引擎是独立于查询引擎的一个单独软件层。存储引擎管理数据在磁盘上存储的所有方面，包括序列化、数据的物理排列和索引。
