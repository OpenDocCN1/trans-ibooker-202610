# 第 10 章. 安全与隐私

既然你已经了解了数据工程生命周期，我们想重申安全的重要性，并分享一些你可以融入日常工作流的简单实践。安全是数据工程实践的关键。这显而易见，但我们不断惊讶于数据工程师将安全视为事后诸葛亮的频率。我们认为，安全是数据工程师在工作的各个方面和数据工程生命周期的每个阶段首先需要考虑的事情。你每天都在处理敏感数据、信息和访问权限。你的组织、客户和业务合作伙伴期望这些宝贵资产得到最周全的照料和关注。一次安全漏洞或数据泄露就可能让你的业务陷入瘫痪；如果是你的过错，你的职业生涯和声誉将毁于一旦。

安全是隐私的关键要素。隐私长期以来一直是企业信息技术领域信任的关键；工程师直接或间接处理与人们私人生活相关的数据。这包括财务信息、私人通信数据（电子邮件、短信、电话通话）、病历、教育记录和工作履历。泄露或滥用这些信息的公司，一旦曝光，可能会成为众矢之的。



越来越多地，隐私已成为具有重大法律意义的问题。例如，《家庭教育权利和隐私法案》（FERPA）于 20 世纪 70 年代在美国生效；《健康保险流通与责任法案》（HIPAA）于 20 世纪 90 年代随之出台；《通用数据保护条例》（GDPR）于 2010 年代中期在欧洲通过。数项美国隐私法案已通过或即将通过。这只是隐私相关法规的极小一部分（我们认为这仅仅是开始）。尽管如此，违反这些法律中的任何一项的处罚对企业来说都可能是重大的，甚至是毁灭性的。由于数据系统已融入教育、医疗保健和业务的方方面面，数据工程师处理与这些法律相关的敏感数据。

数据工程师确切的安全和隐私职责在不同组织间会有显著差异。在小型初创公司，数据工程师可能身兼数据安全工程师的职责。大型科技公司会拥有庞大的安全工程师和安全研究人员团队。即使在这种情况下，数据工程师通常也能发现其所在团队和系统内的安全实践和技术漏洞，并能与专职安全人员协作上报和缓解这些问题。

因为安全和隐私对数据工程至关重要（安全是暗流），我们想花更多时间来探讨安全和隐私。在本章中，我们列出了一些数据工程师应在安全方面考虑的事项，特别是关于人、流程和技术（按此顺序）。这不是一个完整的清单，但它基于我们的经验列出了我们希望得到改进的主要事项。

# 人

安全和隐私中最薄弱的环节是*你*。安全往往在人为层面被攻破，所以请时刻表现得仿佛你一直是攻击目标。在任何给定时间，机器人或人类攻击者都在试图渗透你的敏感凭证和信息。这是我们的现实，且不会消失。对你在线上和线下所做的一切采取防御姿态。运用消极思维的力量，时刻保持警惕。

## 消极思维的力量

在一个痴迷于积极思维的世界里，消极思维令人反感。然而，美国外科医生阿图·葛文德曾于 2007 年在《[纽约时报》](https://oreil.ly/UtwPM)上发表专栏文章，专门探讨这一主题。他的核心论点是：积极思维会使我们对恐怖袭击或医疗急救的可能性视而不见，并阻碍准备工作。消极思维让我们能够考虑灾难性场景并采取行动加以预防。

数据工程师应主动思考数据利用的场景，仅在下游有实际需求时才收集敏感数据。保护私人和敏感数据的最佳方式是首先避免摄入这些数据。

数据工程师应考虑其使用的任何数据管道或存储系统的攻击和泄露场景。在决定安全策略时，确保你的方法提供真正的安全，而不仅仅是安全的*假象*。

## 时刻保持警惕

当有人向你索要凭证时，务必保持谨慎。心存疑虑时——当被索要凭证时，你应始终保持极度怀疑——暂缓行动，向同事和朋友寻求第二意见。与他人确认该请求确实合法。一次快速的聊天或电话沟通，成本远低于因点击邮件引发的勒索软件攻击。当被索要凭证、敏感数据或机密信息时，不要轻信任何人，包括你的同事。

你也是尊重隐私和道德的第一道防线。你是否对被指派收集的敏感数据感到不安？你是否对项目中处理数据的方式有道德方面的疑虑？向同事和领导提出你的担忧。确保你的工作既合法合规又符合道德。

# 流程

当人们遵循常规安全流程时，安全就成为工作的一部分。将安全养成习惯，定期进行真正的安全演练，实行最小权限原则，并理解云中的共享责任模型。

## 安全表演 与 安全习惯

在我们的企业客户中，我们看到了普遍存在的对合规性的关注（内部规则、法律、标准机构的建议），但对潜在不良场景的关注却不够。不幸的是，这制造了一种安全的假象，但往往留下巨大的漏洞，稍加反思几分钟就会显而易见。

安全需要足够简单有效，才能在整个组织中成为习惯。我们惊讶地发现，许多公司拥有长达数百页没人阅读的安全政策，每年的安全政策审查人们转头就忘，一切只是为了在安全审计中打个勾。这是安全表演，即在合规性的字面上（SOC-2、ISO 27001 等）做安全，而缺乏真正的*承诺*。

相反，应追求真正且习惯性安全的精神；将安全思维烘焙进你的文化中。安全不需要复杂。例如，在我们公司，我们至少每月进行一次安全培训和政策审查，将其植入团队的 DNA，并互相更新可改进的安全实践。安全绝不能成为数据团队的事后诸葛亮。每个人都有责任，都有角色可演。这必须是你和你共事的每个人的首要任务。

## 主动安全

回到消极思维的概念，*主动安全*意味着在一个动态变化的世界中思考和研究安全威胁。与其仅仅部署定时的模拟钓鱼攻击，不如通过研究成功的钓鱼攻击案例并思考组织的安全漏洞，采取主动安全态势。与其仅仅采用标准的合规清单，不如思考组织特有的内部漏洞，以及员工可能泄露或滥用私人信息的动机。

我们将在“技术”中进一步阐述主动安全。

## 最小权限原则

*最小权限原则*意味着个人或系统应仅获得完成手头任务所需的特权和数据，别无其他。我们在云端常见到一种反模式：普通用户被授予了所有资源的管理员访问权限，而该用户可能只需少量 IAM 角色即可完成工作。给予某人全权管理访问权限是一个巨大的错误，在最小权限原则下绝不应发生。

相反，在用户（或其所属组）需要时提供他们所需的 IAM 角色。当这些角色不再需要时，立即收回。同一规则适用于服务账户。以相同方式对待人和机器：仅授予他们完成工作所需的特权和数据，且仅在需要的时间段内授予。

当然，最小权限原则对隐私也至关重要。你的用户和客户期望人们仅在必要时查看他们的敏感数据。确保确实如此。在敏感数据周围实施列级、行级和单元格级访问控制；考虑对 PII 和其他敏感数据进行脱敏，并创建仅包含查看者所需访问信息的视图。某些数据必须保留，但只应在紧急情况下访问。将这些数据置于*破玻璃流程*之后：用户只有在经过紧急审批流程以修复问题、查询关键历史信息等后才能访问。工作完成后立即撤销访问权限。

## 云中的共享责任




安全在云端是共同的责任。云供应商负责确保其数据中心和硬件的物理安全。同时，您需要对在云端构建和维护的应用程序及系统的安全负责。大多数云安全漏洞依然是由最终用户造成的，而非云平台本身。漏洞的产生源于非预期的错误配置、失误、疏忽和马虎。

## 始终备份您的数据

数据会消失。有时是硬盘或服务器损坏；在其他情况下，有人可能会意外删除数据库或对象存储桶。恶意行为者也可能锁走数据。勒索软件攻击如今盛行。一些保险公司在遭遇攻击时减少赔付，让您既要负责恢复数据，又要支付挟持数据的恶意行为者赎金。您需要定期备份数据，既为了灾难恢复，也为了业务运营的连续性，以防数据版本在勒索软件攻击中受损。此外，要定期测试数据备份的恢复情况。

数据备份严格来说不属于安全和隐私实践范畴；它归属于更广泛的*灾难预防*标题下，但它与安全息息相关，尤其是在勒索软件攻击盛行的时代。

# 技术

在通过人员和流程解决了安全问题后，接下来要审视如何利用技术来保护您的系统和数据资产。以下是您应优先考虑的几个重要领域。

## 修补和更新系统

软件会过时，安全漏洞不断被发现。为避免因使用旧版工具而暴露安全缺陷，请始终在新更新可用时及时修补和更新操作系统和软件。值得庆幸的是，许多 SaaS 和云托管服务会自动执行升级和其他维护，无需您干预。要更新您自己的代码和依赖项，可以实现构建自动化，或在发布和漏洞上设置警报，以便提示您手动执行更新。

## 加密

加密不是万能药。如果发生*人为*安全漏洞导致凭证泄露，加密几乎无法保护您。加密是任何重视安全和隐私的组织的基线要求。它可以保护您免受基础攻击，例如网络流量拦截。

让我们分别看看静态加密和传输加密。

### 静态加密

确保数据在静止时（存储在存储设备上）经过加密。公司笔记本电脑应启用全盘加密，以防设备被盗时数据泄露。为云中存储在服务器、文件系统、数据库和对象存储中的所有数据实施服务端加密。用于归档的所有数据备份也应加密。最后，在适用的地方引入应用层加密。

### 传输加密

传输加密现在是当前协议的默认配置。例如，现代云 API 通常要求使用 HTTPS。数据工程师应始终关注密钥的处理方式；不当的密钥处理是数据泄露的重要来源。此外，如果存储桶权限对公众开放，HTTPS 也无法保护数据，这也是过去十年多起数据丑闻的成因。

工程师还应了解旧协议的安全局限性。例如，FTP 在公共网络上根本不安全。虽然当数据已公开时这似乎不是问题，但 FTP 易受中间人攻击，攻击者会拦截下载的数据并在其到达客户端前篡改它。最好直接避免使用 FTP。

确保所有传输过程均已加密，即使是遗留协议。拿不准时，请使用内置加密的成熟技术。

## 日志记录、监控和告警

黑客和恶意行为者通常不会宣称正在渗透您的系统。大多数公司在事后很久才发现安全事件。DataOps 的一部分职责是观察、检测并针对事件发出告警。作为数据工程师，您应设置自动化的监控、日志记录和告警，以便在系统发生异常事件时知情。如果可能，请设置自动异常检测。

以下是您应监控的一些领域：

访问
: 谁在何时、从何地访问了什么？授予了哪些新访问权限？现有用户是否存在异常模式，表明其账户可能已被盗用，例如尝试访问平时不访问或不应有权访问的系统？是否发现新的未识别用户访问您的系统？请务必定期梳理访问日志、用户及其角色，确保一切正常。

资源
: 监控磁盘、CPU、内存和 I/O，寻找看似异常的模式。资源是否突然发生变化？如果是，这可能预示着安全漏洞。

账单
: 尤其是使用 SaaS 和云托管服务时，您需要监管成本。设置预算告警，确保支出在预期范围内。如果账单出现意外激增，这可能表明有人或某物正在利用您的资源进行恶意活动。

过度权限
: 越来越多的供应商提供工具，监控用户或服务账户在一段时间内*未使用*的权限。这些工具通常可配置为在经过指定时间后自动通知管理员或移除权限。

例如，假设某分析师六个月未访问 Redshift。这些权限可以被移除，从而堵住一个潜在的安全漏洞。如果该分析师未来需要访问 Redshift，可以提交工单恢复权限。

最好将这些领域结合在监控中，以获得资源、访问和账单概况的横截面视图。我们建议为数据团队的每个人设置一个仪表板，以查看监控并接收告警，当某事看似异常时及时知情。将其与有效的事件响应计划相结合，以在安全漏洞发生时进行管理，并定期演练该计划，以便做好准备。

## 网络访问

我们经常看到数据工程师在网络访问方面做出相当疯狂的举动。在多个案例中，我们见过公开可用的 Amazon S3 存储桶存放着大量敏感数据。我们也见过 Amazon EC2 实例的入站 `SSH` 访问向全世界开放 `0.0.0.0/0`（所有 IP），或数据库对公共互联网上的所有入站请求开放访问。这些只是糟糕网络安全实践的几个例子。




原则上，网络安全应由贵公司的安全专家负责。（实际上，在小公司中，您可能需要承担网络安全的主要责任。）作为数据工程师，您将频繁接触数据库、对象存储和服务器，因此您至少应了解可以采取的简单措施，以确保您符合良好的网络访问实践。了解哪些 IP 和端口是开放的、对谁开放以及为什么开放。仅允许将访问这些端口的系统和用户的传入 IP 地址（即 IP 白名单），并避免因任何原因广泛开放连接。访问云或 SaaS 工具时，请使用加密连接。例如，不要在咖啡厅使用未加密的网站。

此外，虽然本书几乎完全专注于在云中运行工作负载，但我们在此简要提及本地托管服务器。回顾一下，在第 3 章中，我们讨论了强化边界与零信任安全的区别。云通常更接近零信任安全——每个操作都需要身份验证。我们认为，对于大多数组织而言，云是一个更安全的选择，因为它强制实施零信任实践，并允许公司利用公有云雇佣的庞大安全工程师团队。

然而，有时强化边界安全仍然讲得通；我们知道核导弹发射井是气隙隔离的（未连接到任何网络），这让我们多少感到些许安慰。气隙隔离服务器是强化安全边界的终极示例。请记住，即使在本地部署，气隙隔离服务器也容易受到人为安全失误的影响。

## 面向底层数据工程的安全

对于在数据存储和处理系统核心工作的工程师来说，考虑每个元素的安全影响至关重要。任何软件库、存储系统或计算节点都是潜在的安全漏洞。一个不起眼的日志库中的缺陷可能允许攻击者绕过访问控制或加密。即使是 CPU 架构和微代码也代表潜在漏洞；当敏感数据静止在内存或 CPU 缓存中时，它可能[处于脆弱状态](https://meltdownattack.com)。链条上的任何一环都不能掉以轻心。

当然，本书主要关注高层数据工程——将工具拼接在一起以处理整个生命周期。因此，我们将那些血腥的技术细节留给您自行深入挖掘。

### 内部安全研究

我们在“流程”中讨论了*主动安全*的理念。我们还强烈建议采用*主动安全*方法对待技术。具体来说，这意味着每一位技术员工都应思考安全问题。

为什么这很重要？每一位技术贡献者都会形成自己的技术专长领域。即使您的公司雇佣了一支庞大的安全研究团队，数据工程师也会对其职责范围内的特定数据系统和云服务变得极其熟悉。特定技术的专家处于有利位置，能够识别该技术中的安全漏洞。

鼓励每一位数据工程师积极参与安全工作。当他们在其系统中识别出潜在安全风险时，应思考缓解措施，并在部署这些措施中发挥积极作用。

# 结语

安全需要成为一种思维和行动的习惯；像对待钱包或智能手机一样对待数据。虽然您不太可能负责公司的安全，但了解基本安全实践并时刻牢记安全，将有助于降低贵组织发生数据安全漏洞的风险。
