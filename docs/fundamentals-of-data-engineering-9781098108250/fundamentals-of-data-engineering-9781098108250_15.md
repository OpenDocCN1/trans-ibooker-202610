# 附录 A. 序列化与压缩技术细节

在云端工作的数据工程师通常从管理对象存储系统的复杂性中解脱出来。尽管如此，他们仍需了解序列化和反序列化格式的细节。正如我们在第 6 章关于存储原材料中提到的，序列化和压缩算法是相辅相成的。

## 序列化格式

数据工程师可用的序列化算法和格式有很多。虽然选项的丰富是数据工程中一个重要的痛点来源，但它们也是性能提升的巨大机遇。我们有时看到，仅通过将序列化格式从 `CSV` 切换到 `Parquet`，作业性能就提升了 100 倍。随着数据在管道中流动，工程师还将管理重新序列化——即从一种格式转换为另一种格式。有时数据工程师别无选择，只能接受古老、糟糕格式的数据；他们必须设计流程来反序列化这种格式并处理异常，然后清理和转换数据，以便进行一致、快速的下游处理和消费。

### 基于行的序列化

顾名思义，`row-based serialization`（基于行的序列化）按行组织数据。`CSV` 格式是典型的基于行的格式。对于半结构化数据（支持嵌套和模式变化的数据对象），面向行的序列化意味着将每个对象作为一个单元存储。

#### CSV：非标准的标准

我们在第 7 章中讨论过 `CSV`。`CSV` 是数据工程师又爱又恨的序列化格式。术语 `CSV` 本质上是分隔文本的统称，但在转义约定、引号字符、分隔符等方面存在灵活性。

数据工程师应避免在管道中使用 `CSV` 文件，因为它们极易出错且性能低下。工程师往往被迫使用 `CSV` 格式与其无法控制的外部系统和业务流程交换数据。`CSV` 是数据归档的常用格式。如果你将 `CSV` 用于归档，请包含文件序列化配置的完整技术描述，以便未来的消费者能够摄取数据。

#### XML

可扩展标记语言（`XML`）在 `HTML` 和互联网初期很流行，但现在被视为遗留技术；对于数据工程应用，它通常反序列化和序列化速度较慢。`XML` 是另一个数据工程师在与遗留系统和软件交换数据时常被迫交互的标准。`JSON` 已在很大程度上取代 `XML` 用于纯文本对象序列化。

#### JSON 和 JSONL

JavaScript 对象表示法（`JSON`）已成为 `API` 数据交换的新标准，也成为数据存储极其流行的格式。在数据库领域，`JSON` 的流行与 `MongoDB` 等文档存储的兴起同步增长。`Snowflake`、`BigQuery` 和 `SQL Server` 等数据库也提供广泛的原生支持，促进了应用程序、`API` 和数据库系统之间的轻松数据交换。

`JSON Lines`（`JSONL`）是用于在文件中存储批量半结构化数据的 `JSON` 专用版本。`JSONL` 存储一系列 `JSON` 对象，对象之间用换行符分隔。从我们的角度来看，`JSONL` 是在从 `API` 或应用程序摄取数据后立即存储数据的极其有用的格式。然而，许多列式格式提供了显著更好的性能。请考虑在中间管道阶段和服务环节迁移到其他格式。

#### Avro

`Avro` 是一种面向行的数据格式，专为 `RPC` 和数据序列化设计。`Avro` 将数据编码为二进制格式，模式元数据以 `JSON` 指定。`Avro` 在 `Hadoop` 生态系统中很流行，也受到各种云数据工具的支持。

### 列式序列化

我们迄今讨论的序列化格式都是面向行的。数据被编码为完整的关系（`CSV`）或文档（`XML` 和 `JSON`），并按顺序写入文件。

采用 `columnar serialization`（列式序列化）时，数据组织本质上是透视的，将每一列存储在其自己的文件集中。列式存储的一个显著优势是，它允许我们仅读取字段的一个子集，而不必一次性读取完整的行。这是分析应用中的常见场景，能显著减少执行查询所必须扫描的数据量。





# 列式存储与压缩

将数据作为列存储也会将相似的值放在一起，从而使我们能够高效地对列式数据进行编码。一种常见技术是查找重复值并对这些值进行标记化，这是一种简单但对于包含大量重复值的列而言高效的压缩方法。

即使列不包含大量重复值，它们也可能表现出高冗余。假设我们将客户支持消息组织成单个数据列。我们很可能会在这些消息中反复看到相同的主题和措辞，从而使数据压缩算法能够实现高压缩比。因此，列式存储通常与压缩相结合，使我们能够最大化磁盘和网络带宽资源。

列式存储和压缩也带来了一些缺点。我们无法轻松访问单个数据记录；必须通过从多个列文件读取数据来重建记录。记录更新也颇具挑战性。要更改一条记录中的一个字段，我们必须解压列文件、修改它、重新压缩它，并将其写回存储。为了避免每次更新都重写整个列，列会被拆分成许多文件，通常使用分区和聚类策略，根据表的查询和更新模式来组织数据。即便如此，更新单行的开销也是巨大的。列式数据库极不适合事务型工作负载，因此事务型数据库通常采用某种形式的行式或记录导向存储。

## Parquet

`Parquet` 以列式格式存储数据，旨在在数据湖环境中实现卓越的读写性能。`Parquet` 解决了经常困扰数据工程师的几个问题。与 `CSV` 不同，`Parquet` 编码的数据内置了模式信息，并原生支持嵌套数据。此外，`Parquet` 具有可移植性；虽然 `BigQuery` 和 `Snowflake` 等数据库以专有列式格式序列化数据，并在内部存储的数据上提供卓越的查询性能，但与外部工具互操作时会发生巨大的性能损失。数据必须被反序列化、重新序列化为可交换格式并导出，才能使用 `Spark` 和 `Presto` 等数据湖工具。在多语言工具环境中，数据湖中的 `Parquet` 文件可能比专有云数据仓库是更优的选择。

`Parquet` 格式可与多种压缩算法配合使用；针对速度优化的压缩算法（如 `Snappy`，稍后在本附录中讨论）尤其流行。

## ORC

`优化行列式 (ORC)` 是一种类似于 `Parquet` 的列式存储格式。`ORC` 曾广泛用于 `Apache Hive`；虽然仍被广泛使用，但我们通常看到它的频率远低于 `Apache Parquet`，且在现代云生态系统工具中享受的支持稍少。例如，`Snowflake` 和 `BigQuery` 支持 `Parquet` 文件的导入和导出；虽然它们可以从 `ORC` 文件读取数据，但这两个工具都无法导出到 `ORC`。

## Apache Arrow 或内存序列化

当我们在本章开头将序列化作为存储原料引入时，我们提到软件可以将数据存储在通过指针连接的分散在内存中的复杂对象里，或者存储在更有序、紧密打包的结构中，如 `Fortran` 和 `C` 数组。通常，紧密打包的内存数据结构仅限于简单类型（如 `INT64`）或固定宽度数据结构（如固定宽度字符串）。更复杂的结构（如 `JSON` 文档）无法紧密存储在内存中，且需要序列化才能在系统间进行存储和传输。

[`Apache Arrow`](https://arrow.apache.org) 的理念是通过利用一种适合内存处理和导出的二进制数据格式，来重新思考序列化。^(1) 这使我们能够避免序列化和反序列化的开销；我们只需对内存处理、网络导出和长期存储使用相同的格式。`Arrow` 依赖列式存储，其中每个列本质上获得自己的内存块。对于嵌套数据，我们使用一种称为 `shredding`（碎片化/拆分）的技术，将 `JSON` 文档模式中的每个位置映射到一个单独的列。

这项技术意味着我们可以将数据文件存储在磁盘上，通过虚拟内存直接将其换入程序地址空间，并在没有反序列化开销的情况下开始针对数据运行查询。事实上，当我们扫描文件时，可以将文件块换入内存，然后再换出，以避免大型数据集耗尽内存。

这种方法一个显而易见的麻烦是不同编程语言以不同方式序列化数据。为了解决这个问题，`Arrow` 项目为多种编程语言（包括 `C`、`Go`、`Java`、`JavaScript`、`MATLAB`、`Python`、`R` 和 `Rust`）创建了软件库，允许这些语言在内存中与 `Arrow` 数据互操作。在某些情况下，这些库使用所选语言与另一种语言（如 `C`）中的底层代码之间的接口来读写 `Arrow`。这使得语言之间无需额外的序列化开销即可实现高互操作性。例如，`Scala` 程序可以使用 `Java` 库写入 Arrow 数据，然后将其作为消息传递给 `Python` 程序。

`Arrow` 正在各种流行框架（如 `Apache Spark`）中得到快速采用。`Arrow` 还催生了一款新的数据仓库产品；[`Dremio`](https://www.dremio.com) 是一个围绕 `Arrow` 序列化构建的查询引擎和数据仓库，旨在支持快速查询。

# 混合序列化

我们使用术语 `混合序列化` 来指代结合多种序列化技术或将序列化与额外抽象层（如模式管理）集成的技术。我们以 `Apache Hudi` 和 `Apache Iceberg` 为例。

## Hudi

`Hudi` 代表 `Hadoop Update Delete Incremental`（Hadoop 更新删除增量）。这种表管理技术结合了多种序列化技术，既能为分析查询提供列式数据库性能，又支持原子性、事务性更新。典型的 `Hudi` 应用是一个从事务型应用数据库的 `CDC` 流中更新的表。该流被捕获到行式序列化格式中，而表的主体部分保留在列式格式中。查询同时在列式和行式文件上运行，以返回表当前状态的结果。定期运行一个重新打包进程，将行式和列式文件合并为更新后的列式文件，以最大化查询效率。

## Iceberg

与 `Hudi` 一样，`Iceberg` 也是一种表管理技术。`Iceberg` 可以跟踪构成表的所有文件。它还可以跟踪随时间推移每个表快照中的文件，从而在数据湖环境中实现表时间旅行。`Iceberg` 支持模式演进，并能轻松管理 PB 级规模的表。

# 数据库存储引擎

为了完善关于序列化的讨论，我们简要讨论数据库存储引擎。所有数据库都有底层存储引擎；许多数据库不将其存储引擎作为单独的抽象暴露出来（例如 `BigQuery`、`Snowflake`）。一些数据库（特别是 `MySQL`）支持完全可插拔的存储引擎。其他数据库（如 `SQL Server`）提供主要的存储引擎配置选项（列式存储与行式存储），这些选项会极大地影响数据库行为。

通常，存储引擎是独立于查询引擎的一个单独软件层。存储引擎管理数据在磁盘上存储的所有方面，包括序列化、数据的物理排列和索引。





# 存储引擎

存储引擎在 2000 年代和 2010 年代经历了重大创新。过去的存储引擎针对旋转磁盘的直接访问进行了优化，而现代存储引擎则针对 SSD 的性能特征进行了更好的优化。存储引擎还为现代类型和数据结构提供了改进的支持，例如变长字符串、数组和嵌套数据。

存储引擎的另一个重大变化是转向面向分析和数据仓库应用的列式存储。`SQL Server`、`PostgreSQL` 和 `MySQL` 都提供了强大的列式存储支持。

# 压缩：gzip、bzip2、Snappy 等

压缩算法背后的数学原理很复杂，但基本思想很容易理解：压缩算法在数据中寻找冗余和重复，然后重新编码数据以减少冗余。当我们想要读取原始数据时，通过反转算法并将冗余加回去来对其进行*解压*。

例如，你可能注意到阅读本书时某些单词反复出现。对文本运行一些快速分析，你可以识别出最高频的单词并为这些单词创建缩短的标记。要压缩，你将用它们的标记替换常用单词；要解压，你将用各自的单词替换标记。

也许我们可以用这种朴素的技术实现 2:1 或更高的压缩比。压缩算法利用更复杂的数学技术来识别和消除冗余；它们通常能在文本数据上实现 10:1 的压缩比。

请注意，我们讨论的是*无损压缩算法*。使用无损算法编码的数据解压后，能恢复出与原始数据逐位完全相同的副本。*有损压缩算法*用于音频、图像和视频，旨在保真感官体验；解压恢复的内容听起来或看起来像原始内容，但并非逐位完全相同的副本。数据工程师可能会在媒体处理管道中处理有损压缩算法，但不会在用于分析的序列化中使用，因为后者要求精确的数据保真度。

传统压缩引擎如 `gzip` 和 `bzip2` 对文本数据压缩效果极好；它们经常被应用于 `JSON`、`JSONL`、`XML`、`CSV` 和其他基于文本的数据格式。近年来，工程师们创造了一代新的压缩算法，优先考虑速度和 CPU 效率，而非压缩比。主要例子包括 `Snappy`、`Zstandard`、`LZFSE` 和 `LZ4`。这些算法常用于压缩数据湖或列式数据库中的数据，以优化快速查询性能。

^(1) Dejan Simic, "Apache Arrow: Read DataFrame with Zero Memory," *Towards Data Science*, June 25, 2020, [*https://oreil.ly/TDAdY*](https://oreil.ly/TDAdY)。
