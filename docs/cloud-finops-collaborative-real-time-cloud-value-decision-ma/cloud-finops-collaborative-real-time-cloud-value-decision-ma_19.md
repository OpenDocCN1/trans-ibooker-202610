## 与其他框架的连接

除非你的公司诞生于云端并且大部分技术预算都在那里，否则 FinOps 很可能不会孤立存在，并且可能不是组织实践的唯一 IT 管理学科。

大多数大型组织使用多种不同的 IT 管理学科来定义它们将如何交付技术服务、了解相关支出的价值、加速采用或交付曲线，并使组织免受各种风险的侵害。

本章概述了如何与组织中使用其他 IT 和技术支出相关框架的团队合作的起点。重点将更少放在方法论之间的技术交叉点上，而更多放在与执行这些方法的人/团队合作的方式上。目标是成功地与这些其他框架和学科合作，以补充它们而不是重叠或与其竞争。太多时候我们看到学科或部门之间产生摩擦，因为每个部门都试图在组织内建立权力或创造影响力。FinOps 并不是解决所有 IT 支出问题的万灵药，而是帮助组织内所有学科——包括其他 IT 管理职能和团队——更有效地管理云使用和成本。

IT 相关框架的详尽列表很长——对我们中的许多人来说令人困惑。它们涵盖了广泛的 IT 管理领域，例如资产、许可、财务管理、安全、开发实践、架构流程等。

以下是我们看到与 FinOps 并存的一些常见框架。它们通常以以下方式与 FinOps 交互：


## IT 管理学科

FinOps 可以共享有关云环境中运行的内容、云资源配置方式以及其运行位置/区域等详细信息。第 12 章中涵盖的内容，包括成本分摊、账户层级和标签，在此非常重要。

- IT 服务管理 (ITSM)
- IT 基础设施库 (ITIL)
- 配置管理 (CM)

## IT 财务学科

FinOps 可以帮助对云账单中看到的各种云使用类型和类别进行分类。所需的分类也可能驱动你的标签策略。跟踪跨云环境的许可证使用情况以及资产的生命周期是重要概念。它们侧重于将云计费的深度数据与其它财务框架提供的现有 IT 成本类别相匹配。

- IT 财务管理 (ITFM)
- 技术商业管理 (TBM)
- 软件资产管理 (SAM)
- IT 资产管理 (ITAM)

## 信息安全 / 网络安全

FinOps 通常会共享异常检测数据，这可能有助于提醒安全团队关注问题领域。标签标准可以帮助安全团队在安全流程标记审查时，快速识别云资源的拥有者和预期用途。

## GreenOps

此内容在第 19 章有详细说明。

这些方法论、学科和实践可能在你使用公有云之前就已在组织内运行多年，以帮助管理 IT 交付的特定方面。一个常见的顿悟时刻是认识到这些其他学科实际上无法应对云的自助服务、按需和高度可变特性，也无法应对其产生的海量账单数据。FinOps 并非要取代这些，而是帮助实现同样的总体目标：为每笔技术支出获得最大价值，但对云有深入的领域关注。

你的组织可能正在采用或使用众多敏捷或 DevOps 框架的实现，以帮助加速和协调你的 IT 价值交付。你的组织可能有企业架构团队利用众多架构框架中的一种来驱动你开发和实施 IT 解决方案的方式。你可能已经拥有一个云卓越中心 (CCoE) 或云平台团队，使用你所使用的云服务提供商提供的云采用框架或 Well-Architected 框架中的一种。而且你肯定有一个信息安全团队，专注于确保每个产品和工程团队都高度关注网络安全要求和风险。

![](img/4d4736bc293fd892d1da81802d0f9520_415_0.png)

> 安全是与 FinOps 团队的惊人平行：安全团队并非唯一负责确保组织内安全实践，而是提供指导、集中最佳实践，并加速业务线团队。

并非每家公司都拥有所有这些其他团队。在成熟的组织中，FinOps 团队很可能是众多团队中最新的（除第 19 章中讨论的 GreenOps 外），以帮助改变组织的文化并提升 IT 为整个组织带来的价值。

## 总拥有成本

由于 FinOps 特别关注云，你需要与组织内的其他团队协作，以获得部分在云中、部分在本地部署的应用程序或投资组合的总拥有成本 (TCO)。所有那些你不通过云账单购买的其他成本——租金、人工、合同和部分许可证——因此通常不会出现在你的 FinOps 报告中，都是 TCO 的一部分。了解 TCO 对于确定技术采购的价值并实现我们在第 26 章讨论的数据驱动决策制定这一理想状态至关重要。

云的特殊性使得 FinOps 成为必要——你处理的数据量巨大、数据到达速度快、无限可用性创造了超支的机会——而 FinOps 恰好能够应对这些特殊性。如果你的财务团队已经在管理那些每月或固定的 IT 成本，FinOps 团队可以将云成本以可用的格式融合进来，为组织提供按应用程序、按业务部门、按产品等的支出全景。FinOps 团队可以更深入地提供不仅是该支出的分配，还有其为何如此的故事，并释放需要比许多传统 IT 管理学科更精细可见性的潜在优化机会，而这些学科需要继续使整体 IT 支出更有效。

## 与其他方法论和框架协作

在开发 FinOps 时，你应采取一系列步骤，以避免与已建立的其他方法论或框架发生冲突。

![](img/4d4736bc293fd892d1da81802d0f9520_416_0.png)

随着云成为大多数公司 IT 支出的主体，这些现有框架中的一些可能会整合为一个运作。及早认识到这一点并留意结合努力的机会，以便你的组织从长远来看获得最大利益。关注每个框架旨在实现的结果。

## 了解谁在那里

FinOps 团队开始工作后一段时间才发现有其他团队运营其他 IT 框架的情况并不少见。这可能导致团队之间产生相互冲突或重复工作的认知。理想情况下，你应在实施 FinOps 过程中尽早确定谁在运行哪些框架和职能。首先寻求了解每个团队做什么以及他们为业务提供的价值。去与他们交谈，了解他们试图完成什么以及他们的执行赞助人是谁，最重要的是，开始建立工作关系。

## 云端故事——Ashley Hromatko

在她担任 Pearson 的 FinOps 领导期间，Ashley Hromatko 分享了以下故事，讲述她的团队如何与现有的 SAM 实践进行接触并建立合作实践：

在我们数字化转型高峰期并将数百个工作负载迁移到云时，我们开始将第三方软件和服务的采购转移并简化到 AWS Marketplace。我们的组织有集中的采购和 SAM 团队，但业务部门希望通过云中更快的采购来释放创新。这种敏捷性带来了风险，即业务部门可能在未经批准或谈判的情况下获取资金，在不知公司整体协议的情况下购买许可证，以及对供应商合同适当审查的担忧。

我们的团队——体现了 FinOps 原则“团队需要协作”——着手了解现有的采购和 SAM 流程，并开始代表工程业务部门倡导效率、承诺优势和可获取的精细化跟踪的好处。

这些团队共同能够建立一些规则，并联合建立了新的云第三方治理。这包括将 AWS Marketplace 访问权限锁定给授权负责人、创建在购买前需要 SAM 和财务参与的阈值入职指南、记录合格供应商名单、设置在购买前收集详细信息的流程、定期审计采购，以及新的摊销成本分摊输出。我们继续每年共同合作进行预测，并在下一年的第三方软件采购类型和预算阈值方面做出业务决策。

## 建立友谊并共享目标

建立共同的理解，即不存在谁做得最好的竞争。拥有我们对他们 的态度（在第 24 章关于工程团队的讨论中提到）只会导致双方都不愿意协作，就像 FinOps 和工程或财务等其他团队将自己视为目标对立时一样。人们认为一方的成功往往以另一方的牺牲为代价。然而，共享的目标应该是组织使命的成功。

团队之间存在重叠目标是预期的，因此明确定义这些目标将使共享路线图得以实现，避免重复或更糟的冲突。

可以探索重叠目标的领域包括以下内容：

- 谁提供做出及时决策所需的数据，以及该数据如何使企业能够衡量旨在最大化业务价值的权衡
- 哪个团队负责 IT 支出和用量管理的每个部分
- IT 支出应如何控制/治理以及谁来定义它
- 各方法论提供的数据、报告和仪表板将如何生成和分发

![](img/4d4736bc293fd892d1da81802d0f9520_417_0.png)

FinOps 并非包揽一切——也不是其本意——其他框架也一样。识别每个框架的优势和劣势将使你能够确定在更大的组织目标上如何互相帮助，一个框架的输出可以解决另一个框架的弱点。制定责任矩阵可以帮助整个组织了解各团队如何协同工作。

以下是 FinOps 通常与其他框架不同的一些领域：

## 范围

其他框架通常针对所有 IT 相关支出，例如员工成本、咨询合同、许可证管理和数据中心运营，而 FinOps 则专门针对具有可变支出成本的公有云和 SaaS 提供商。

## 输入规模

其他框架通常使用大量来源输入，每个输入规模较小但复杂性和一致性各不相同。FinOps 依赖于有限数量的来源输入，其中包含极其庞大和复杂的数据集。



## 速度

其他框架最适合在较长业务周期（月度、季度）上运行的传统成本要素。FinOps 设计为以尽可能快的行动周期（每小时、每天）执行，以应对云使用量的变化。

稳固的框架组合可以形成 T 型技术价值交付方法。换句话说，它们共同提供广阔的可见性，通过像 ITFM 这样范围较宽（但颗粒度较低）的框架，以及通过像 FinOps 这样范围较深（但较窄）的框架提供颗粒化的领域能力。

## Share Influence, Terminology, and Processes

现有框架团队很可能已经对你引入 FinOps 时需要影响的相同角色拥有影响力，或者组织内对引入 FinOps 的日益增长的兴趣可能为现有框架团队提供放大其影响的机会，就像 Ashley 关于与 SAM 团队互动的故事一样。拥有组织内现有关系的团队可以帮助引入 FinOps，并缩短 FinOps 在组织内成为已知实践的过程。在框架之间统一共同信息意味着你最终会拥有统一的声音。

你们都在做以下事情：

- *不是*组织的核心业务，即实施这些框架所花费的时间和精力是本应用于构建组织销售的产品的时间和精力
- *需要工作*和公司各方人员的协作
- *至关重要*于组织的成功，即如果没有这些框架，组织将面临会对其成功产生负面影响的挑战

力求在公司内建立共同的影响力，既表达每个相关框架的重要性，又有助于说明为什么两者对组织的成功都是必需的。

要实施这些框架中的任何一个，都需要数据集、报告以及领域特定术语的教育。在向组织实施新政策或标准之前，应确定可以重复使用或重新利用的现有政策和标准。需要一个标签计划？像 ITFM、TBM、ITAM、DevOps 或你的 CCoE 这样的现有框架团队可能已经定义了一些分配规则。依靠组织内的现有流程和知识将使事情更简单，并加快建立成熟实践的过程。也许更重要的是，采用公司内部已知的术语和定义，比尝试为相似术语创建新的——并且可能冲突的——用法要容易得多。

## Share Infrastructure

记住第 8 章中介绍的 *将数据置于每个角色路径中* 的概念。现有框架很可能已有工程师、财务和领导层正在使用的现有报告和仪表板。与其制作新的报告和仪表板，你应与拥有这些现有报告的团队保持一致，并添加 FinOps 信息。如果 ITFM 报告已是你的高管报告流程的一部分，请努力通过你的 FinOps 实践向这些报告添加更深入的云数据。不要试图重新发明轮子。共享现有报告和仪表板既减少了建立 FinOps 报告的工作量，也避免了组织内相关角色需要额外付出努力。

## Share Knowledge

FinOps 是一个整合性学科，将组织内许多其他学科的工作联系起来，因此有几个关键学科与 FinOps 有关键相似之处。这些学科的从业者经常将 FinOps 描述为“我的学科，但针对云”。但云中存在重要差异，这就是为什么在大多数组织中 FinOps 需要自己的重点。

![](img/4d4736bc293fd892d1da81802d0f9520_419_0.png)

如果不了解我们在共享目标中讨论的现有框架的优势和劣势，很容易将每个框架及其能为组织带来的价值 trivialize。对 FinOps 来说，认为现有框架一无是处是一个错误。它们已在执行的许多活动将提供可被 FinOps 利用的价值。共享教育计划、外联和布道活动建立了对彼此框架的共同理解；这将使所有团队都能对彼此的框架产生共同的欣赏。

## Conclusion

FinOps 是关于建立桥梁，而非筑墙。所有 IT 管理方法论都有一个共同目标，即帮助企业从 IT 支出中获得最大价值，但它们从不同角度进行方法，并且有些专门针对特定类型的 IT 支出。

总结如下：

- 努力识别组织内部运营其他框架的团队。
- 努力与组织内管理其他框架的团队保持一致并互补。你们彼此都有可学习之处，并会找到可以相互支持的领域。
- 共同工作以避免重复并增强彼此的目标。
- 决定哪个团队负责重叠责任的每个组成部分。
- 在组织内部围绕云支出和业务价值决策建立一致的信息传递。

现在你已经了解如何建立关系并真正与工程师、财务以及 FinOps 团队将合作的许多其他团队协作。现在是让这些关系产生回报的时候了。

这就引出了我们喜欢称之为 *FinOps 涅槃* 的阶段。倒数第二章将概括我们迄今为止讨论的所有内容，这些内容使你能够实现最终目标：实现数据驱动的决策。
