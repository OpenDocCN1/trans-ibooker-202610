
> 我们仍然会在某些请求上遇到阻力，例如在感知到的时间价值不足时要求清理闲置资源。但这些会引发对话，而不是争论，因为我们建立了信任，并且得到了领导层的支持。

## 工程师路径上的数据

工程师——尤其是开发人员——经常处于深度专注的循环中，通常被称为 *flow*。打断其中一个循环会极大地影响工程师的表现。正因如此，你只有在响应或行动的时机需要立即进行时才应打断工程师；使用实时沟通方式，如聊天、视频通话或当面走过去，会让工程师脱离思路并破坏其专注度。如果你需要他们采取的行动可以等待，那么请考虑如何以不会造成干扰的方式告知他们任务。

回到第8章中引入的 *data in the path of the engineer* 概念，让 FinOps 数据存在于工程团队已在工作的场所，是减少工程师参与 FinOps 所需努力的关键因素。与工程师现有流程集成，避免了他们打开新报告并围绕 FinOps 运行额外仪式所需的努力。然而，未经通知就将 FinOps 注入工程团队的报告和流程中应避免，因为这会真正打断工程团队仪式的流程。理想情况下，工程师应帮助指导在现有工作流程中何处插入 FinOps 数据最能帮助他们。

如果领导层要求工程师必须立即清理云浪费并削减10%的成本，他们很可能会看到快速成果。强制要求是让工程师采取行动的快速方式。但它们通常不可持续，并可能造成鞭打式的负面文化。一旦强制要求过时且不再得到领导层强化，它就会从工程团队的脑海中消失，他们会重新专注于交付和其他关键指标的优化。而对 FinOps 的负面感受则是持久的。

成本强制要求是点对点的影响，短期内可能有效，但随着时间的推移，你会再次遇到同样的不断增长的浪费。成本指标对业务很重要这一更广泛的信息应作为工程运作方式的一部分持续重申。

当你在文化层面开始建立成本效率是核心价值时，它就成为服务工作流程的一部分。力求熟练练习并建立肌肉记忆。FinOps 成为整体故事的一部分。文化不会消失——它只是成为日常的一部分。

与工程团队合作，了解其现有流程和报告，从他们那里获得反馈，了解 FinOps 数据在何处以及如何能带来最大益处。当工程师能够参与 FinOps 的实施方式时，他们更有可能帮助做出必要的改变。

## 与工程团队合作的模式

每个 FinOps 团队都会以不同的方式与公司工程师合作，这取决于 FinOps 团队成员的知识和技能组合。

### 直接贡献

具备工程技能的 FinOps 团队通常会采取更主动的方法，直接帮助工程师设计更高效的云服务并开发工具以避免前期产生浪费。这是建立工程师与 FinOps 团队之间协作环境的有力方法，可以更有效地将使用优化量保持在最低限度。对于非常大的公司，这种类型的合作可能会存在局限性，因为积极从事云工作的工程团队数量可能会超出 FinOps 团队的承载能力。

### 间接协作

并非所有 FinOps 团队都配备了工程师，但这并不意味着他们无法与周边的工程团队有效合作。这种类型的合作通常会看到 FinOps 团队与组织内的云卓越中心 CCoE 或技术架构组 TAG 之间进行强有力的协作。依靠 TAG 和/或 CCoE 团队来推动所有工程团队更高效地设计，并利用他们深厚的云知识帮助 FinOps 了解当前云支出、预测未来成本，并明确识别优化机会。

### 具有针对性贡献的间接协作

作为与工程团队合作的混合方法，采用间接协作模式，但利用 FinOps 团队成员的工程技能来针对业务的特定领域。FinOps 成员可以直接与支出最大的工程团队合作，或专注于组织内云成熟度最低的工程团队以提升其能力。执行这种直接协作的 FinOps 团队成员可能会随着需求变化在组织中流动，或专属于某个工程领域。在 Atlassian，设有成本工程师嵌入其他团队执行此职能。

选择建立合作的模式应首先评估 FinOps 团队中的技能、工程领域内 CCoE/TAG 团队的建立程度，以及组织内所有工程团队的云采用成熟度。选择一种模式并不意味着永远锁定这种合作方式，随着云足迹的扩展，混合模式变得越来越可能成为最终结果。

## 结论

我们希望你对工程角色及其在 FinOps 中的核心作用有了更好的理解。来自各方的合作伙伴都需要倾听并分解不一定是工程特定性的挑战。我们不能把挑战抛过篱笆就期望它被推进完成。工程师 juggling 着大量相互竞争的优先事项。当成本意识被引入时，会带来额外的认知负担。与工程师沟通的方法和时机可以极大地影响 FinOps 被视为合作伙伴关系还是强制要求。

围绕成本效率改进所产生的摩擦通常来自以下几个方面：

- 领导层设定的其他优先事项
- 交付功能或服务的紧迫截止日期
- 担心更改可能会对性能产生负面后果
- 对工程师的期望不明确，或工作价值没有得到很好的传达

总结如下：

- 与工程师建立合作伙伴关系比完成一份 FinOps 任务清单更重要。
- 成本节约不是合作伙伴关系的目标，而是花钱获得高效价值。
- 在开发过程早期与工程团队就财务约束达成一致，以减少后期浪费的工作。
- 领导层应避免强制要求，即短期成本关注期，而应鼓励团队将持续监控和管理 FinOps 的需求作为组织工作流程和文化的一部分。
- 如果你的 FinOps 团队没有审查/推荐工程设计/更改的技能，请与组织内的架构团队协作。

## 与其他框架的连接

除非你的公司诞生于云端并且大部分技术预算都在那里，否则 FinOps 很可能不会孤立存在，并且可能不是组织实践的唯一 IT 管理学科。

大多数大型组织使用多种不同的 IT 管理学科来定义它们将如何交付技术服务、了解相关支出的价值、加速采用或交付曲线，并使组织免受各种风险的侵害。

本章概述了如何与组织中使用其他 IT 和技术支出相关框架的团队合作的起点。重点将更少放在方法论之间的技术交叉点上，而更多放在与执行这些方法的人/团队合作的方式上。目标是成功地与这些其他框架和学科合作，以补充它们而不是重叠或与其竞争。太多时候我们看到学科或部门之间产生摩擦，因为每个部门都试图在组织内建立权力或创造影响力。FinOps 并不是解决所有 IT 支出问题的万灵药，而是帮助组织内所有学科——包括其他 IT 管理职能和团队——更有效地管理云使用和成本。
