## 其他考虑因素

成本不是，也不应是买与建之间权衡的全部内容。存在安全影响。此外，你可能会发现某个工具提供的功能与你的环境不兼容，或无法与你已在使用的系统集成，例如用于警报和通知的聊天和工单应用程序。某些行业甚至有特定的合规要求，如 FedRAMP、HIPAA、SOC 2 或 PCI，而第三方工具提供商可能尚未持有相应的认证。找到具备正确认证组合的供应商，可以从合规角度让你的自动化流程更顺畅。

能够审计自动化操作至关重要，尤其是在自动化与生产环境交互时。这种认知建立了透明度。

第三方自动化工具通常文档完善，并提供员工学习的培训材料，因此在招聘新员工时，他们更有可能已熟悉这些工具。如果你自行构建自动化工具，你需要愿意并能够为现有和新团队成员提供持续培训，并且存在负责构建和维护工具的人员可能离开组织的风险。除非有超过少数几名员工熟悉工具及其实现方式，否则你会遇到“关键人员风险”。

当你决定自行构建自动化工具而不是购买现成产品时，应以知情的方式进行。你必须始终将构建所有所需功能所需的投入——包括衡量工具有效性的方法、持续维护以及你需要实施的更新——与购买的解决方案进行比较。而且你应谨慎识别任何第三方供应商工具缺失的功能或合规要求。

## 工具部署选项

与大多数软件一样，自动化工具的部署方式有几个需要考虑的因素，这会影响选型过程。

### 云原生

在云账户内运行的自动化，脚本可以由云服务提供商或更广泛的社区提供。这些脚本在你的云账户内的 Function-as-a-Service 平台（如 AWS Lambda）中执行。

### 自建

这是由你自己的员工构建和运行的软件。功能开发由内部团队负责。如果你组织内有多个不同的 DevOps 团队，你可能会发现他们各自使用自己的自动化版本解决相同问题。但最好由一个中央团队运行一个为整个云环境服务的自动化工具。集中管理工具将减少组织内的重复工作，但这也意味着你需要一个一刀切的解决方案。

### 第三方自托管

就预建自动化解决方案而言，有免费和开源工具可用，也有付费软件许可选项。在这种部署模式下，团队使用第三方软件，但在自己的环境中运行并自行维护和管理服务。在开源领域，一个常被推荐的工具是由 Capital One 团队创建的 Cloud Custodian 应用程序。你需要考虑运营和可能定制第三方自托管解决方案的成本。

### 第三方 SaaS

此选项消除了运行和管理软件的需求。第三方托管软件解决方案可提供最简单的设置和可能最快的自动化时间。供应商通常会提供简单的工具来处理在你的云账户中所需的设置，以便供应商平台与你的环境集成。复杂的指标和配置已经开发完成，通常附带易于使用的仪表板和设置屏幕。你通常需要支付月费，这很容易与工具本身的收益进行衡量。这种模式确实会带来安全影响，我们稍后会介绍。

![](img/4d4736bc293fd892d1da81802d0f9520_364_0.png)

并非总是简单的构建与购买；一些公司采用买入并增强的混合方法，即将现成工具的 API 数据或建议与其自己的内部自动化相结合，这样可以避免构建 FinOps 的数据摄取/管理能力，但可以拥有实际触及其基础设施的代码。

HERE Technologies 的 Jason Fuller 分享说，虽然他使用供应商 FinOps 平台来驱动其报告和建议，但他依赖于基于开源工具 Cloud Custodian 的内部分支进行大量定制的内部自动化代码来实际在其环境中实施更改。这种构建与购买的混合实施是一种三管齐下（供应商 + 开源 + 自定义代码）的方法，他在四个大型云支出者处从事 10 年 FinOps 后已将其打磨成熟。

## 自动化协同工作

自动化工具很少孤立运行。随着时间的推移，尤其是在你的云足迹增长时，很可能有多个工具同时运行。

### 集成

工具之间的集成非常强大，这是你应该寻找并利用的。避免使用许多各自做相同事情的独立工具。例如，如果你的组织已有现成的工单系统，你理想情况下应实施能够在该现有系统中为行动项目生成工单的 FinOps 工具，而不是构建单独的任务跟踪系统。

如果你选择的自动化工具没有与你的其他软件工具直接集成，自动化工具仍可能支持可扩展的事件处理。然后你可以接收自动化工具内部生成的事件通知，并构建一个扩展来将事件连接到你的其他软件包之一。这是一种扩展功能的好方法——例如，向你的聊天应用程序发送特定任务已完成的通知、在你的工单系统中为必要的后续任务生成工单，或根据检测结果实施你自己的自动化修复任务。

### 自动化冲突

部署多个自动化工具时，你需要确保它们不会相互冲突。如果一个工具试图启动服务器而另一个试图关闭它，你可能会导致自动化相互对抗其操作。如果你为特定功能部署自动化工具，而该工具还有你不打算使用的其他功能，请考虑是否可以删除该服务对该停用功能执行云账户更改的权限。

我们见过公司为其提供的不同功能部署不同的自动化工具，却发现两个工具都在尝试控制相同的资源。或者一个团队会实施与其现有自动化冲突的自己的自动化。

这是一个更难解决的问题。为防止这种情况，你需要让整个组织了解已部署的自动化情况，并让团队共同工作以确保他们了解其云账户中任何计划自动化可能产生的影响。

理想情况下，自动化应在与外部事物冲突时通知你。例如，如果自动化在短时间内停止服务器实例超过设定次数，它应发送警报并阻止任何进一步更改。

有时自动化服务冲突的不是其他工具，而是人员。你可能有自动化会停止服务器实例，而你的团队成员需要访问该服务器。这可能导致团队成员启动实例，却看到自动化将其停止。同样，你应确保团队已得到充分教育，包括如何将资源从自动化中排除。

![](img/4d4736bc293fd892d1da81802d0f9520_366_0.png)

曾任 Cardinal Health 和 Nationwide 云优化总监的 Joe Daly 讲述了他通过手动删除一个通过自动化与生产环境关联的非生产资源而意外导致生产环境宕机的故事。如前所述，组织内了解正在使用的自动化至关重要。如需听完整故事，请查看 FinOpsPod 播客第 13 集，标题为“FinOops——惨痛的教训”。

## 安全与保障

安全性是任何 FinOps 自动化工具的首要关注点。通常，FinOps 自动化需要对你的云环境拥有非常高的访问级别，无论只是描述账户中所有配置的方式，还是更改（启动/停止/删除）资源本身的能力。这种访问可能直接导致拒绝服务攻击、数据丢失、损坏或保密泄露。

安全性经常被引用为组织内部不使用第三方工具的主要原因。让安全团队批准需要广泛访问云账户的第三方工具的使用确实很难。然而，仅因为你的团队编写了软件并不意味着它将绝对安全。你必须确保部署的所有自动化工具都具有执行所需任务的最小权限，同时保护软件免受外部威胁。

很可能成功的第三方供应商已在安全方面投入了大量时间和精力。查看他们的文档和之前的任何安全公告将帮助你衡量该供应商对安全作为其产品一部分的重视程度。

如果你参考 FinOps 成熟度模型，你可能会选择最初以只读模式集成第三方 SaaS 工具。你可以随后将该工具的通知作为输入，并使用自己的工具自动化修复操作。当你对供应商更有信心时，你可以开始允许他们代表你执行更多操作，直到启用所有所需功能。
