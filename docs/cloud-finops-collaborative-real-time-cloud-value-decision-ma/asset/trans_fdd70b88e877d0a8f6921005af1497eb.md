
## 无服务器容器

由云服务提供商提供的无服务器容器，例如 AWS 的 Fargate，为您围绕容器的 FinOps 策略增添了有趣的变化。对于自管理的集群，您需要考虑运行更多集群的成本影响。每个集群的管理计算节点都存在额外的成本和维护要求，这可能导致工程团队选择在集中式账户中使用更少的集群。

由于集群管理层由云服务提供商管理，并且计算节点对您来说是抽象的，因此集中化工作负载的需求减少了。在无服务器世界中，跟踪调度程序的效率以及衡量容器在集群实例上的打包程度并不是问题。这一责任已转移给云服务提供商。然而，监控过度配置的容器仍然是必需的，因为当今的无服务器容器产品仅允许某些 vCPU 和内存组合。

成本分配由云服务提供商为您完成，因为每个容器任务都由云服务提供商直接计费。这是因为他们现在可以看到服务器上运行的容器。因此，按比例分配成本和划分共享资源的问题被消除了。当容器在您账户内的服务器实例上运行时，删除容器会在集群上腾出空间，但除非完全从集群中删除计算节点，否则成本不会降低。对于无服务器容器，当它们被删除时，您就停止被收费。

这听起来像是好消息，但正如 FinOps 中的一切一样，存在多重考虑因素。例如，让云服务提供商管理集群意味着您的团队可以调整的配置项更少，这可能会使您无法为工作负载优化集群。

## 结论

容器的问题与您最初迁移到云时面临的问题相似，因此您可以使用现有的 FinOps 实践来解决这些问题。

总结如下：

- 容器化并不会让您避免 FinOps，因为 FinOps 原则仍然适用，并且管理成本的需求对于容器化应用同样重要。
- 除非您使用的是云服务管理的容器化平台，否则您需要收集有关运行容器如何使用服务器的补充数据。
- 跟踪容器消耗的服务器实例比例并将该信息与您的云账单配对，可实现真正的成本分配。
- 容器化并不一定意味着高效：需要监控服务器使用情况并执行 rightsizing 和调度优化。
- 无服务器编排降低了成本分配的 FinOps 开销，但带来了成本大幅增加的高风险。

下一章将深入探讨与工程团队建立合作伙伴关系的过程。

## 与工程师合作以实现 FinOps

FinOps 是一项团队运动，如果没有工程师，很少能取得进展。在本章中，我们将讨论如何通过培养工程师的成本效率动机，而不是下达强制性指令，来灌输 FinOps 文化。强制性指令仅在领导层关注时提供短期行动。最终，强制性指令的压力会减弱，一切恢复正常，成本低效会重新出现。

在本章中，我们将探讨软件工程师日常工作为何使成本优化考虑变得困难，并介绍工程师在开始将成本考虑整合到日常工作流程中时通常会经历的转变。

许多工程师来自成本考虑 historically 从未成为他们工作一部分的世界。现在，在云中，他们被要求将成本视为新的约束。传达可变基础设施成本为何现在成为他们工作的重要组成部分以及对业务的影响的背景至关重要；否则，它可能会被降优先级。

在成熟的实践中，工程师和开发人员处于 FinOps 长矛的最前线，他们的早期参与、一致性和认可对成功至关重要。

## 融合我们与他们

重新审视本书的第一版时，我们注意到它在 FinOps 团队和工程团队之间使用了多少“我们与他们”的语气。一些措辞暗示工程师在某种程度上游离于 FinOps 工作之外，并且通常不关心成本。在云和 FinOps 转型成熟的公司中，这与事实相去甚远。仅进行被动成本优化、参与度低的工程师反映了不成熟的 FinOps 实践和成熟度，其中低效率经常被嵌入到开发过程中，而 FinOps 流程仅限于事后被动地清理浪费。相反，成熟的实践会在服务和架构设计早期就与工程师合作，以主动避免服务在云中部署方式上的低效率。

推动 FinOps 的角色在过去几年发生了变化。在《2022 年 FinOps 状况》中，负责推动 FinOps 的团队 overwhelmingly 向 CTO 或 CIO 汇报，并且由工程师 staffing——并且越来越多地由工程师领导。一旦成本意识文化得以建立，FinOps 本身的工作就由组织各地的工程师执行，从而让中央 FinOps 团队更专注于其他职能。正如我们在第 15 章提到的，FinOps 的许多关键职能——如使用量减少和优化——通常不是由 FinOps 团队集中完成的；而是将这些责任直接分配给各个业务部门或组的工程团队。部署服务的工程师比任何人都更了解自己的基础设施，最适合对其进行优化。

## 工程师心中的想法？

工程动机与财务团队动机形成鲜明对比。后者倾向于通过与预算和预测相比的支出金额的视角，关注业务可行性、毛利率以及业务的未来财务稳定。工程师的动机是创新，通过软件改进提供价值，并通常在包括安全、性能、正常运行时间和可靠性在内的多个领域提高效率。

在第 3 章中，我们谈到了如何提高团队的动机并减少信任的丧失。回忆一下所引入的行动量表，其中动机与所需努力之间存在平衡。有时存在一种误解，即工程师没有动力关注成本效率；实际上，他们的 FinOps 工作只是与其他关键约束和考虑因素竞争。

为了平衡行动量表，FinOps 从业者需要与工程师（以及设定其目标和激励的工程领导层）合作，使成本效率成为与安全、性能、可靠性或可持续性（第 19 章讨论）同样重要的考虑因素。只关注单一成功衡量标准不是一个选项。

工程师参与度不足的感知通常不是缺乏动机。由于他们负责的领域清单很长，因此必须定期做出权衡决策。如果 FinOps 需要大量或不明确的时间，则除非由领导层优先考虑，否则可能无法纳入工程日程。

## 云中的故事——Abuna Demoz

Abuna Demoz 是一名软件工程师，曾领导 Google Cloud 和 Amazon Web Services 的大型工程团队，他分享了以下见解：

您可以假设大多数工程师起初希望完成软件生命周期中尽可能多的任务，涵盖开发、文档、监控、告警、重构、扩展等。但随后他们会遇到在工作日或新功能目标发布日期内实际能完成的工作的限制。对于高级工程师来说尤其如此，他们的需求最高。他们被迫不断地优先排序，并在通常不允许任何超出关键要求之外的任务的时间范围内做出艰难选择。

这就是组织奖励结构发挥作用的地方。大多数工程师会根据会得到奖励（薪水、奖金等）或认可（赞扬、领导层可见度、晋升等）的标准来优先排序。使用奖励和认可来驱动行为非常有效，但我们也必须理解其中产生的隐含权衡。

例如，在大多数组织中，工程师因推出客户使用且理想情况下付费的新功能而获得奖励。这意味着当时间紧张时，很容易在可靠性、可维护性、可扩展性，尤其是成本方面投资不足。

随着组织向 FinOps 转型，将成本指标和目标与工程师奖励挂钩是让每个人关注相同问题的绝佳方式。奖励可以与提高标签覆盖率、减少浪费和未使用情况、以及/或提高预测准确性挂钩。领导者对团队为实现这些目标所做工作的认可有助于强化其重要性。

FinOps 必须寻找方法来减轻工程师的负担，尤其是在自动化方面。正如第 8 章所讨论的，将 FinOps 数据置于工程师的工作路径中将实现更快的决策，并减少因上下文切换而损失的认知负荷。我们不希望工程师花费大量时间（或脑力）来弄清他们的行动如何影响支出预测，这不仅会使他们远离其他优先事项，还会降低他们关注 FinOps 责任的可能性。FinOps 报告应为工程师提供清晰的行动考虑大纲以及支持这些行动的确切数据，减少工程师考虑成本所需的工作量和时间投入。
