# 第 21 章：中断和异常

![](img/chapterart.png)

到目前为止，我们将每个应用程序视为独占使用计算机。但像大多数操作系统一样，Linux 允许多个应用程序并发执行。操作系统以交织的方式管理硬件，在任何给定时间为每个应用程序以及操作系统本身提供所需的硬件组件的使用。

这里有两个问题。首先，为了执行其管理任务，操作系统需要保持对应用程序与硬件之间交互的控制。它通过使用 CPU 中的*权限级别*系统来实现这一点，该系统允许操作系统控制应用程序与操作系统之间的网关。其次，我们在上一章末尾看到，大多数 I/O 设备在准备好输入或准备好接受输出时，可以中断 CPU 的正在进行的活动。CPU 有一种机制，通过这个网关引导 I/O 中断，并调用受操作系统控制的函数，从而允许操作系统保持对 I/O 设备的控制。

我们将首先看看 CPU 如何使用权限级别来强制执行其控制。然后我们将看看 CPU 如何对中断或异常做出反应，包括通知 CPU 其服务被 I/O 设备或应用程序需要的三种方式：*外部中断*、*异常* 或 *软件中断*。我们将通过讨论应用程序如何通过使用软件中断直接调用操作系统服务来结束本章。

## 权限级别

为了执行其管理任务，操作系统需要保持对应用程序与硬件之间交互的控制。它通过使用 CPU 中的*权限级别*系统来实现这一点，操作系统使用该系统在应用程序和硬件之间维护一个网关。在任何给定时间，CPU 都在四个可能的权限级别之一中运行。表 21-1 显示了从最高权限到最低权限的级别。

表 21-1：CPU 权限级别

| 级别 | 用途 |
| --- | --- |
| 0 | 提供对所有硬件资源的直接访问。仅限于最底层的操作系统功能，如 I/O 设备和内存管理。 |
| 1 | 对硬件资源的访问受到一定限制。可能被某些库例程和控制不需要完全硬件访问权限的 I/O 设备的软件使用。 |
| 2 | 对硬件资源的访问受到更多限制。可能被某些库例程和控制不需要比级别 1 更少访问权限的 I/O 设备的软件使用。 |
| 3 | 无法直接访问硬件资源。应用程序在此级别运行。 |



大多数操作系统仅使用级别 0 和 3，通常分别称为*管理程序模式*和*用户模式*。操作系统（包括硬件设备驱动程序）运行在管理程序模式下，而应用程序（包括它们调用的库例程）运行在用户模式下。级别 1 和 2 很少使用。请小心，不要将 CPU 特权级别（一种硬件特性）与操作系统的*文件权限*（一种软件特性）混淆。

每当 CPU 访问内存时，都会通过*门描述符*进行。这个 16 字节的记录包含了正在被访问的内存页的特权级别。CPU 被允许访问特权级别等于或低于 CPU 当前特权级别的内存。

当操作系统首次启动时，分配给它的内存处于最高特权级别 0，且 CPU 运行在特权级别 0。为 I/O 设备分配的内存也处于特权级别 0。

当操作系统加载应用程序时，它首先在最低特权级别 3 为程序分配内存。应用程序加载后，操作系统将 CPU 的使用权移交给应用程序，同时将 CPU 切换到特权级别 3。随着 CPU 运行在最低特权级别，应用程序无法直接访问属于操作系统或 I/O 设备的任何内存。允许直接更改特权级别的指令只能在级别 0 执行。应用程序只能通过门描述符访问操作系统服务。

接下来，我们将了解当发生中断或异常时 CPU 会做什么，包括门描述符是如何被使用的。

## CPU 对中断或异常的响应

*中断*或*异常*是导致 CPU 暂停当前指令流执行并调用一个函数的事件，该函数称为*中断处理程序*、*异常处理程序*，或简称为*处理程序*。处理程序是操作系统的一部分。在 Linux 中，它们可以内建于内核，也可以根据需要作为单独的模块加载。

这种控制转移类似于函数调用，但会有一些额外的动作。除了在响应中断或异常时将 `rip` 寄存器的内容（返回地址）压入栈中外，CPU 还会将 `rflags` 寄存器的内容压入栈中。处理程序几乎总是需要在高特权级别下执行——在表 21-1 中最常见的是级别 0——因此还有一种机制用于将 CPU 置于适当的特权级别。

处理程序的调用地址和特权级别，以及其他信息，由操作系统存储在门描述符（也称为*向量*）中。中断和异常的门描述符存储在一个数组中，即*中断描述符表*（*IDT*），或*向量表*，位置对应于它们的中断号。x86-64 架构支持 256 个可能的中断或异常，编号为 0–255。前 32 个（0–31）在 CPU 硬件中预先分配给特定用途。例如，中断描述符表中的第一个门描述符，位置 0，用于除零异常。剩下的 224 个可供操作系统用于外部中断和软件中断。

除了将控制权转移到处理程序调用地址外，CPU 还会切换到中断或异常的门描述符中指定的特权级别。门描述符可以指示操作系统使用不同于应用程序的栈。在特定条件下，CPU 还会将应用程序的栈指针压入操作系统的栈中。然后 CPU 将中断处理程序的地址从门描述符移至 `rip`，并从那里继续执行。

以下是 CPU 响应中断或异常所采取动作的总结：

1.  将 `rflags` 寄存器的内容压入栈。

2.  将 `rip` 寄存器的内容压入栈。根据异常的性质，处理程序处理完异常后可能会返回当前程序，也可能不会。

3.  将 CPU 的特权级别设置为相应门描述符中指定的级别。

4.  从相应的门描述符中将处理程序的地址加载到 `rip` 寄存器中。

在处理程序末尾使用简单的 `ret` 指令将无法正确工作。还有一条指令 `iret`，它首先恢复被中断代码所使用的 `rflags` 寄存器、特权级别和栈指针（如果已保存），然后恢复 `rip`。

在某些情况下，无法继续执行被中断的代码。在这种情况下，处理程序可能能够显示错误消息并将控制权移交给操作系统。在其他情况下，操作系统本身会停止运行。

对于 *interrupt*（中断）和 *exception*（异常）这两个术语的用法，并没有统一的标准。我将遵循 Intel 和 AMD 手册中的用法，描述通知 CPU 需要操作系统服务的三种方式（由 I/O 设备或应用程序发起）：外部中断、异常或软件中断。

### 外部中断

*外部中断*由 CPU 外部的硬件引起。中断信号通过控制总线发送给 CPU。外部中断与 CPU 时序是*异步*的——它可能发生在 CPU 正在执行指令的中间。

键盘输入就是外部中断的一个例子。无法确切知道某人何时会按下键盘上的键，也无法知道下一个键会在多久之后被按下。例如，假设在执行以下两条指令中的第一条指令时按下了一个键：

```
        cmp     byte ptr [ebx], 0
        je      allDone
```

操作系统需要尽快使用 CPU 从键盘读取字符，以防止该字符被下一次按键覆盖，但首先，CPU 需要完成当前正在执行的指令。

CPU 只会在指令执行之间确认中断。在我们的例子中，CPU 将在执行完 `cmp` 指令后确认外部中断。在“指令执行周期”（第 180 页）中，你了解到当 CPU 执行 `cmp` 指令时，`rip` 寄存器会被更新为包含 `je` 指令的地址。这个地址会被压入栈中，以便 CPU 在处理完中断后能返回到我们程序中的 `je` 指令。

然后 CPU 调用键盘处理程序从键盘读取字符。处理程序几乎肯定会改变 `rflags` 寄存器。`je` 指令的动作需要基于 `cmp` 指令的结果，而不是基于处理程序中 `rflags` 寄存器可能发生的任何变化。现在我们明白了为什么 CPU 在响应外部中断时需要保存一份 `rflags` 寄存器的副本。

### 异常

我们要考虑的中断 CPU 的下一种方式是*异常*。异常通常是 CPU 无法处理的数字导致的。示例包括除以 0、访问无效地址或尝试执行无效指令。在一个完美的世界里，应用软件将包含所有防止这些错误发生的检查。现实是没有程序是完美的，因此这些错误中的一些必然会发生。

当这些错误中的一个确实发生时，采取适当行动是操作系统的责任。通常，操作系统能做的最好的就是退出应用程序并打印错误消息。例如，当我在一个汇编语言程序中处理调用栈的方式出错时，我得到了以下消息：



`Segmentation fault (core dumped)`

就像外部中断一样，需要调用操作系统中的处理程序来处理异常。处理程序在异常发生时对 CPU 状态了解得越多，就能更好地确定原因。因此，将 `rip` 和 `rflags` 寄存器中的值传递给异常处理程序是有帮助的。而且，当然 CPU 需要被置于最高特权级，因为处理程序是操作系统的一部分。

并非所有异常都是由实际的程序错误引起的。例如，当程序引用程序中尚未加载到内存的另一部分地址时，会导致*缺页异常*。操作系统提供一个处理程序，将程序的适当部分从磁盘加载到内存中，然后继续正常的程序执行，用户甚至不会察觉到这一事件。在这种情况下，处理程序需要缺页发生时 `rip` 和 `rflags` 寄存器中的值，以便在控制权返回程序时恢复它们。

## 软件中断

当我们使用一条指令让 CPU 表现得好像发生了外部中断或异常时，就会发生*软件中断*。程序员为什么要故意中断程序？答案是为了请求操作系统的服务。

应用程序运行在最低特权级，因此它们不能直接调用操作系统中的函数。CPU 中的中断/异常机制包含在调用函数时切换 CPU 特权级的手段。因此，软件中断允许运行在最低特权级 3 的应用程序调用操作系统内核中的函数，同时将 CPU 切换到操作系统的较高特权级。这种机制使操作系统能够保持控制。

编程中断和异常处理程序超出了本书的范围，但我们可以研究如何在应用程序（运行在最低特权级）中使用软件中断来调用操作系统中的函数（只能在较高特权级运行）。

## 系统调用

*系统调用*，通常称为 *syscall*，允许应用程序直接调用 Linux 内核系统任务，例如执行 I/O 功能。到目前为止，在本书中我们使用 C 标准库中的 C 封装函数（例如 `write` 和 `read`）来进行系统调用。这些 C 封装函数负责处理从应用程序到操作系统再返回的特权级转换。在本节中，我们将了解如何使用汇编语言指令直接进行系统调用，而不使用 C 运行时环境。

我们将介绍两种机制：`int 0x80` 和 `syscall`。`int 0x80` 指令引发一个软件中断，它使用中断描述符表。`syscall` 指令作为 64 位指令集的一部分被添加，仅在 64 位模式下可用。它会在 CPU 中引发一组略有不同的动作，我们稍后将看到。

### `int 0x80` 软件中断

我们可以使用 `int` 指令调用安装在中断描述符表中的任何中断处理程序：

**`int` — 调用中断过程**

1. 调用中断处理程序。
2. `int n` 调用中断处理程序 `n`。

`n` 可以是 0 到 255 范围内的任何数字。`int` 如何调用指定的中断处理程序的细节取决于 CPU 的状态，超出了本书的范围，但总体结果与外部设备发起中断相同。

虽然我们这里不会编写任何中断处理程序，但你可能意识到处理程序需要执行多项操作来在返回前恢复 CPU 状态。所有这些都是通过 `iret` 指令完成的。

**`iret` — 中断返回**

1. 从中断处理程序返回。
2. `iret` 从中断处理程序返回。

`iret` 指令从堆栈中恢复 `rflags` 寄存器、`rip` 寄存器和 CPU 特权级。

Linux 在中断描述符表中使用中断描述符编号 128[10] (= `80`[16]) 来指定一个处理程序，该处理程序将指示操作系统执行 300 多个函数中的一个。具体的操作系统功能由 `eax` 寄存器中的数字指定。

大多数操作系统函数都需要参数。我们使用寄存器向 `int 0x80` 系统调用传递参数，如表 21-2 所示。请注意，`int 0x80` 的寄存器用法与函数调用不同。

**表 21-2：`int 0x80` 系统调用的寄存器用法**

| **系统调用号** | **参数 1** | **参数 2** | **参数 3** | **参数 4** | **参数 5** | **参数 6** |
| --- | --- | --- | --- | --- | --- | --- |
| `eax` | `ebx` | `ecx` | `edx` | `esi` | `edi` | `ebp` |

系统调用号列在 Linux 文件 `unistd_32.h` 中。在我使用的 Ubuntu 版本 (20.04 LTS) 中，该文件位于 `/usr/include/x86_64-linux-gnu/asm/unistd_32.h`。表 21-3 显示了三个常用的系统调用号及其所需参数。

**表 21-3：`int 0x80` 指令的一些 Linux 操作**

| **操作** | **`eax`** | **`ebx`** | **`ecx`** | **`edx`** |
| --- | --- | --- | --- | --- |
| `read` | 3 | 文件描述符 | 存放输入的地址 | 要读取的字节数 |
| `write` | 4 | 文件描述符 | 要输出的第一个字节的地址 | 要写入的字节数 |
| `exit` | 1 | | | |

许多系统调用都有 C 封装函数，这允许你从函数的 `man` 页面确定参数。如果你回顾第 13 章的清单 13-2，你会看到使用 `int 0x80` 的 `write` 系统调用的参数与 `write` C 封装函数的参数相同。

清单 21-1 提供了一个使用 `int 0x80` 软件中断直接访问操作系统服务的示例。

```asm
# helloWorld-int80.s
# Hello World program
# ld -e myStart -o helloWorld3-int80 helloWorld3-int80.o

        .intel_syntax noprefix
# Useful constants
        .equ    STDOUT, 1           # screen
        .equ    WRITE, 4            # write system call
        .equ    EXIT, 1             # exit system call
        
        .text
        .section  .rodata           # read-only data
message:
        .string "Hello, World!\n"
        .equ    msgLength, .-message-1

# Code
        .text                       # code
        .globl  myStart

myStart:
      mov     edx, msgLength      # message length       
      lea     ecx, message[rip]   # message address
      mov     ebx, STDOUT         # the screen
      mov     eax, WRITE          # write the message
      int     0x80                # tell OS to do it

      mov     eax, EXIT           # exit program
      int     0x80
```

我们将 `write` 系统调用的编号传递给 `eax` 寄存器中的 `int 0x80` 处理程序 3。`write` 系统调用的参数与我们在第 13 章调用 `write` C 语言封装函数时使用的参数相同（参见清单 13-2），但我们需要将它们传递到表 21-2 2 中指定的寄存器中。

你可能会注意到，在调用 `int 0x80` 处理程序时，我们只使用了寄存器的 32 位部分。该机制是为 32 位环境设计的。尽管它在我们的 64 位环境中也能工作，但 x86 架构的 64 位增强增加了一条用于进行快速系统调用的指令，我们将在下一节讨论。

### `syscall` 指令

除了增加更多寄存器外，x86 架构的 64 位增强还增加了一些指令，其中之一是*快速系统调用* `syscall`。`syscall` 指令绕过了中断描述符表。它是在 64 位模式下进行系统调用的首选方法：

#### `syscall`——快速系统调用

`syscall` 将 `rip` 的内容移至 `rcx`，然后将 `LSTAR` 寄存器的内容移至 `rip`。将 `rflags` 移至 `r11`。切换到特权级 0。

`LSTAR` 寄存器是一个特殊的 CPU 寄存器，操作系统在其中存储 `syscall` 处理程序的地址。

与 `int 0x80` 指令不同，`syscall` 不使用中断描述符表，也不在栈上保存信息，从而节省了多次内存访问。它的所有操作都在 CPU 的寄存器中进行。这就是为什么它被称为*快速系统调用*。当然，这意味着如果 `syscall` 处理程序使用 `rcx` 和 `r11` 寄存器，它必须保存它们的内容，并在返回前将它们恢复为原始值。

从 `syscall` 处理程序返回是通过 `sysret` 指令完成的，该指令将 `r11` 移至 `rflags`，将 `rcx` 移至 `rip`，并将 CPU 特权级设置为 3。

你必须按照表 21-4 所示，通过寄存器传递 Linux 中 `syscall` 系统调用的参数。请务必注意，参数传递的寄存器与 `int 0x80` 系统调用不同。

**表 21-4：`syscall` 系统调用指令的寄存器用法**

| 系统调用号 | 参数 1 | 参数 2 | 参数 3 | 参数 4 | 参数 5 | 参数 6 |
| --- | --- | --- | --- | --- | --- | --- |
| `rax` | `rdi` | `rsi` | `rdx` | `r10` | `r8` | `r9` |

`syscall` 的系统调用编号列在 Linux 文件 `unistd_64.h` 中。在我使用的 Ubuntu 版本（20.04 LTS）中，该文件位于 `/usr/include/x86_64-linux-gnu/asm/unistd_64.h`。表 21-5 列出了几个常用的系统调用编号。

**表 21-5：`syscall` 指令的一些 Linux 操作**

| 操作 | `rax` | `rdi` | `rsi` | `rdx` |
| --- | --- | --- | --- | --- |
| `read` | 0 | 文件描述符 | 存放输入的地址 | 读取的字节数 |
| `write` | 1 | 文件描述符 | 待输出首字节的地址 | 写入的字节数 |
| `exit` | 60 | | | |

## 你学到了什么

1.  **特权级**：操作系统通过在较低的 CPU 特权级运行应用程序来维持对硬件的控制。
2.  **门描述符**：一条包含中断处理程序地址和运行中断处理程序的 CPU 特权设置的记录。
3.  **中断描述符表**：门描述符的数组。中断或异常编号是数组的索引。
4.  **外部中断**：其他硬件设备可以中断 CPU 的常规执行周期。
5.  **异常**：CPU 中的特定条件可能导致 CPU 中断其常规执行周期。
6.  **软件中断**：导致 CPU 中断其常规执行周期的特定指令。
7.  **中断处理程序**：当发生中断或异常时，由 CPU 调用的操作系统中的一个函数。
8.  `int 0x80`：Linux 中用于执行系统调用的软件中断。
9.  `syscall`：用于在 64 位 Linux 中执行快速系统调用的指令。

这只是对中断和异常的简要概述。细节复杂，需要对你正在使用的特定 CPU 型号有透彻的了解。
