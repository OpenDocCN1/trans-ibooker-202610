这证实了函数已成功执行，并且 Lambda 函数代码的原始版本正在 `$LATEST` 版本中运行。

### Note

此时，任何 AWS 账户用户导航到 Lambda 函数的 Code 选项卡时，都会看到返回 `Learning Serverless Security` 的原始代码。

6. 现在是时候验证恶意的 Lambda 函数版本（版本 `2`）是否可以直接调用，如 [Figure 5-8](#ch05.html#attacker-invokes-version-2) 所示。

![](assets/lsse_0508.png)

运行以下命令来调用 Lambda 函数版本 `2`：

```
aws lambda invoke \
  --function-name lambda-0000 \
  --payload '{}' \
  --region us-east-1 \
  --qualifier '2' \
  --profile admin-001 \
  output_response.json

cat output_response.json
```

响应如下：

```
{"AccessKeyId": "...", "SecretAccessKey": "...", "SessionToken": "..."}
```

这里，你提供的 qualifier 直接对应 Lambda 函数的已发布版本号。例如，指定 `--qualifier '2'` 将调用该函数的版本 `2`。

### Caution

版本号会在发布新版本时按升序自动分配，并且一旦创建就不能重复使用。因此，你需要确保指定的 qualifier 直接对应恶意函数代码的版本号。

选择 `lambda-0000` 函数，然后导航到 Code 选项卡以检查部署的最新代码。你应该在代码编辑器中看到原始的 Lambda 函数代码（[Figure 5-9](#ch05.html#how-it-looks-like-00)）。

这里，你有三个版本——其中版本 `2` 保留了恶意代码，在被调用时会返回与角色权限绑定的新临时凭证。

### Note

虽然 Versions 选项卡显示了已发布 Lambda 版本的历史记录，但查看每个版本的部署代码需要再点击几次——大多数开发者不会费心去做。

要无需凭证即可调用后门版本，攻击者需要创建一个指向特定 Lambda 版本的别名，然后配置与该别名关联的函数 URL，如 [Figure 5-11](#ch05.html#complete-backdoor-setup) 所示。

![](assets/lsse_0511.png)

通过此设置，攻击者可以直接从浏览器或脚本触发后门函数版本，并检索与 Lambda 函数执行角色关联的临时凭证。这些临时凭证随后可用于通过各种技术生成长期访问凭证，类似于你在 [“Establishing Persistence with New IAM User Credentials”](#ch05.html#ch05-establishing-persistence-with-new-iam-user-credentials) 中早期的探索。我们在这里不会详细介绍这些步骤，以避免通过公开可访问的 Lambda 函数 URL 泄露你账户的凭证。

从防御安全角度来看，除了审计和解决 IAM 误配置外，你还需要跟踪 Lambda 函数版本历史，监控对旧函数版本意外的调用，并审计函数配置和权限的更改。你可以利用自动化合规服务和功能，例如 AWS Config 自定义规则，以自动检测未经授权的 Lambda 版本和别名创建。此外，根据你的 AWS Organizations 和账户的结构和管理方式，你可以考虑应用服务控制策略来设置预防性护栏和限制，针对开发和安全团队之间明确商定的风险操作。

现在你已完成本章的动手示例，请务必清理你在 Serverless Lab 账户中创建的 IAM 和 Lambda 资源，以避免留下后门和配置错误的云资源。

# Chapter 6. Hacking Publicly Accessible AWS Lambda Functions

想象一下，你花费数周时间构建一个无服务器应用程序并将其发布给数千名用户。仅仅几天后，你发现应用程序停止工作，AWS 因为可疑活动而暂时暂停了你的账户。深入调查根本原因后，你意识到攻击者利用了公开可访问的 Lambda 函数中的代码注入漏洞，并使用其过于宽松的 IAM 角色访问并从 Secrets Manager 中窃取机密，以及从其他云资源中窃取敏感数据。此场景向你展示了单个易受攻击的 Lambda 函数足以触发整个 AWS 账户的全面数据泄露。
