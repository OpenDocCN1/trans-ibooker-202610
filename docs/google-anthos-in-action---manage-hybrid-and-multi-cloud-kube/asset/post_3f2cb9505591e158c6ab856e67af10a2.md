
- Kustomize file `kustomization.yaml` and
- patch file `patch.yaml` that defines which attributes should be changed in the Deployment.

## Kustomize Feature List

Kustomize comes with all the features that are needed to customize your Kubernetes deployment. These include:

- Generating Resources (ConfigMaps and Secrets)
- Setting cross-cutting fields
- Composing and Customizing Resources

**Figure 14.33** Kustomize features

![](img/fb3bebce7b5f593bca1a7f8a1371be06_524_0.png)

Let's have a look at each of them in detail:

### Composing

You can use the `resources` attribute to define which resource definitions you want to customize.

If you don't include any other customization feature in the file, the resources will be simply composed into one definition. In the example below we compose `deployment.yaml` and `service.yaml` definitions.

```yaml
# kustomization.yaml
resources:
- deployment.yaml
- service.yaml
```

To run the customization execute the below command.

```bash
kubectl kustomize ./
```

### Customizing

Customization allows you to patch your resources with specific values. This uses two methods:

- `patchesStrategicMerge` [28]
- `patchesJson6902` [29]

As an example, you can patch the `my-deployment` Deployment defined in the `deployment.yaml` file with the number of replicas by creating the below files.

```yaml
# increase_replicas.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 3
```

```yaml
# kustomization.yaml

resources:
- deployment.yaml
patchesStrategicMerge:
- increase_replicas.yaml
```

and run

```bash
kubectl kustomize ./
```

On top of this customize feature, you can also change container images in your Deployment by defining the `image` attribute.

### Setting cross-cutting fields

Using **Setting cross-cutting fields**, you can set the following attributes on your Kubernetes resources:

- `namespace`
- `namePrefix`
- `nameSuffix`
- `commonLabels`
- `commonAnnotation`

In the example below, we set the namespace to `my-namespace` for the `deployment.yaml` definition. Note: you can use the `resources` attribute to define the resources you want to be affected.

```yaml
# kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: my-namespace
resources:
- deployment.yaml
```

### Generating Resources

With Kustomize you can generate ConfigMaps and Secrets resources. As we have already learned, they are used for feeding in configuration and credentials to your application. Objects can be generated either from a literal or a file. The following generators are supported:

- `configmapGenerator`
- `secretGenerator`

As an example, to generate a ConfigMap with the key-value pair you can use the following file

```yaml
# kustomization.yaml

configMapGenerator:
- name: example-configmap
  literals:
  - Foo=Bar
```

and run:

```bash
kubectl kustomize ./
```

### Using variables

The variables feature is very useful when you want to capture an attribute of one resource and pass it to other resources. As an example, you might want to use the service name to pass it to a container command to be executed. Note that this currently supports string types. Please check the following link to see example usage:

https://kubectl.docs.kubernetes.io/references/kustomize/kustomization/vars/

### Bases and Overlays

Now that we have a good understanding of what features Kustomize brings, we can have a look at how we can use it to prepare Kubernetes for different environments in your CI/CD pipeline.

Kustomize comes with the concepts of **Bases** and **Overlays**. The base is a root directory with Kubernetes resource definitions and the main `kustomization.yaml` file. This performs a first layer of customization. Note that you can also set your base in a git repository. An overlay is a directory that stores a `kustomization.yaml` that customizes resources already customized in the base layer. You can create multiple overlays to represent each of your environments.

**Figure 14.34** Kustomize base and overlays

![](img/fb3bebce7b5f593bca1a7f8a1371be06_528_0.png)

Below we can see an example of file structure for a single base with three overlays for dev, test and prod environments:

```
├── base
│   ├── deployment.yaml
│   ├── kustomization.yaml
│   └── service.yaml
└── overlays
    ├── dev
    │   ├── kustomization.yaml
    │   └── patch.yaml
    ├── test
    │   ├── kustomization.yaml
    │   └── patch.yaml
    └── prod
        ├── kustomization.yaml
        └── patch.yaml
```

Now you could use this file structure to set the number of replicas to be different between each environment. Maybe for development you don't need to consume so many resources as for tests, where you might want to run performance testing.

### Summary of Kustomize

As we have seen, Kustomize can be a very powerful tool in your CI/CD pipeline to generate and patch Kubernetes resources for each of your environments. If you feel like you want to learn more about how to use Kustomize, check out the Kustomize examples: https://kubectl.docs.kubernetes.io/guides/example/, the API reference: https://kubernetes-sigs.github.io/kustomize/api-reference/, and the reference: https://kubectl.docs.kubernetes.io/references/

## 14.4 Continuous Deployment with Cloud Deploy

Cloud Deploy is a fully managed Continuous Deployment service that allows you to deliver your applications to a defined series of *target* environments according to a promotion sequence.

The *lifecycle* of your applications is managed using *releases* and is controlled by *delivery pipelines*.

### 14.4.1 Cloud Deploy in the Anthos CI/CD

Google Cloud Deploy integrates with the Google Cloud Platform ecosystem of services that we have already learned about, to complete the end-to-end CI/CD solution for GKE and Anthos clusters.

**Figure 14.35** Cloud Deploy CI/CD ecosystem

![](img/fb3bebce7b5f593bca1a7f8a1371be06_530_0.png)

The figure shows how Google Cloud Deploy interfaces with the following services:

- **CI tooling** can call the Google Cloud Deploy API or CLI to create a release. Hence, most of the CI tools are supported, including Cloud Build.
- **Cloud Build** is used to render the manifests and to deploy to the target runtime.
- **Skaffold** is used by Cloud Build to render and deploy the manifests. As a result, the application is deployed.
- **Cloud Storage** stores rendering source and rendered manifests.
- **Google Cloud's operations suite** collects and stores Audit Logs of the Cloud Deploy service.
- **Pub/Sub** allows publishing Cloud Deploy's messages to Pub/Sub topics. This can be used to integrate with external systems.
- **GKE and Anthos Clusters** are the target runtimes to which Google Cloud Deploy deploys the applications. This is done with the use of `skaffold apply`, through Cloud Build, to your target runtime.

Now that we know how Cloud Deploy interacts with the other Anthos CI/CD tools, let's see how we can configure it for Continuous Delivery of the Anthos applications.
