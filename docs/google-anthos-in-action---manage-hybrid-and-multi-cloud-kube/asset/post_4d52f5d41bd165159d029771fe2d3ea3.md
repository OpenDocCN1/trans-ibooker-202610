
+   - **enableApplication:** Set to true if you want to collect application metrics and logs from application workloads.

By default Cloud Operations collect only logs and metrics from workloads in the admin cluster, and for user clusters, workloads in system namespaces as: *kube-system*, *gke-system*, *gke-connect*, *istio-system*, and *config-management-system*. System components logs and metrics are used also from Google support to troubleshoot issues in case of support cases. In addition to the metrics for system namespaces, it also collects metrics on resource usage on nodes from all the pods.

Setting the *enableApplicationspec* to true enables collection for stdout logs for any pod in the cluster and for custom metrics exposed from the application through a prometheus endpoint.

In order to scrape custom application metrics you need to create a Service with the annotation `prometheus.io/scrape: "true"` that selects the application pods and points to the prometheus endpoint port exposed by the application. Below you will find an example for an application named “monitoring-example" that exposes prometheus metrics on port 9090.

### Note

This is not part of the Anthos on bare metal config file, but it’s a Service object created for the specific application in order to scrape metrics

```
kind: Service
apiVersion: v1
metadata:
  name: "monitoring-example"
  namespace: "default"
  annotations:
    prometheus.io/scrape: "true"
spec:
  selector:
    app: "monitoring-example"
  ports:
  - name: http
    port: 9090
```

The Anthos bare metal setup tool automatically creates a few dashboards in the Cloud Monitoring workspace to monitor system components:

+   - **Control plane status**: Showing availability for the clusters core control plane components as API server, scheduler, controller manager, etcd.
+   - **Pod status**: Showing metrics values as CPUusage, memory usage, network traffic, restarts etc...for pods
+   - **Node status**: Showing node metrics as CPU usage, memory usage, allocatable resources, node condition, filesystem size.

## Storage Configuration

The storage: section includes the configuration for the local volume provisioner (LVP) that can be used to provide persistent volumes using mount points on local nodes.

Using local persistent volumes binds the Pod to a specific disk and node. If that disk or node becomes unavailable, then the Pod also becomes unavailable. Due to this, workloads using local PVs need to be resilient to this kind of failure, this is why using local persistent volumes generally fits proof of concepts or advanced use cases where data persistence is not critical or data are replicated to other volumes so are recoverable in case of node/disk unavailability.

There are three types of storage classes for local PVs in an Anthos on bare metal cluster:

+   - LVP node mounts: This storage class creates a local PV for each mounted disk in a specified directory. Each PV maps to a disk with capacity equal to the underlying disk capacity. The total number of local PVs created in the cluster is the number of disks mounted under the path across all nodes.
+   - **LVP share**: This storage class creates a local PV backed by subdirectories in a local, shared file system on every node in the cluster. These subdirectories are automatically created during cluster creation. Workloads using this storage class will share capacity and IOPS because the PVs are backed by the same shared file system.
+   - **Anthos system**: This storage class creates preconfigured local PVs

during cluster creation that is used by Anthos system pods. Do not change or delete this storage class and do not use this storage class for stateful apps.

The `lvpNodeMounts:` section contains the parameters to configure the LVP node mounts:

+   - **path:** Local node directory path under which disk to be used as local persistent volumes are mounted
+   - **storageClassName:** The StorageClass that PVs will be created with. The StorageClass is created during cluster creation.

The `lvpShare:` section contains the parameters to the parameter to configure the LVP share:

+   - **path:** Local node directory path under which subdirectories will be created on each host. A local PV will be created for each subdirectory.
+   - **storageClassName:** The StorageClass that PVs will be created with. The StorageClass is created during cluster creation.
+   - **numPVUnderSharedPath:** Number of subdirectories to create under path, the total number of LVP share persistent volumes in the cluster would be this number multiplied for the number of nodes

The example configuration below uses the default parameters for a hybrid cluster:

```
storage:
  lvpNodeMounts:
    path: /mnt/localpv-disk
    storageClassName: local-disks
  lvpShare:
    path: /mnt/localpv-share
    storageClassName: local-shared
    numPVUnderSharedPath: 5
```

## Authentication

As mentioned in the chapter, Anthos on bare metal leverages the Anthos Identity Service authentication proxy to integrate with existing identity providers through OpenID Connect (OIDC).

Anthos Identity Service allows users to authenticate using existing corporate credentials both through GCP Console and kubectl (in that case gcloud CLI is used to authenticate and create a kubeconfig file containing the id token to be used by kubectl).

The `authentication:` section in the cluster configuration file contains the following parameters to configure authentication to the cluster using OIDC:

+   - **name**: The name you want to use to identify this configuration, typically the identity provider name.
+   - **issuerURI**: The url of the OpenID provider, it’s where gcloud CLI and GCP Console send authentication requests and it’s used by Kubernetes API server to discover public keys for verifying tokens. For example, for Active Directory Federation Server this is usually [https://SERVERFQDN/adfs](https://SERVERFQDN/adfs), while for Google Cloud Identity it’s [https://accounts.google.com](https://accounts.google.com)
+   - **clientID**: Client ID assigned to the application on the OIDC provider configuration. This is usually created automatically when you create the application on the OIDC provider.
+   - **clientSecret**: Client secret assigned to the client application on the OIDC provider configuration. This is usually created automatically when you create the application on the OIDC provider.
+   - **kubectlRedirectURI**: Callback/redirect url for gcloud CLI, this is `http://localhost:PORT_NUMBER/callback` where `PORT_NUMBER` is any port number greater than 1024 you can choose. This needs to be also added to the OIDC provider configuration
+   - **userClaim**: JWT claim to use as the username, this is optional, "sub" is used if not set.
+   - **userPrefix**: Optional. Prefix prepended to user claims to prevent clashes with existing names.
+   - **groupPrefix**: Optional. Prefix prepended to group claims to prevent clashes with existing names.
+   - **scopes**: Additional scopes to send to the OpenID provider as a comma-delimited list.
+   - **extraParams**: Optional. Additional key-value parameters to send to the

OpenID provider as a comma-delimited list.

+   - **proxy**: Optional. A proxy server to use for the cluster to connect to OIDC provider issuer URL
+   - **deployCloudConsoleProxy**: Optional. Specifies whether to deploy a reverse proxy in the cluster to allow Google Cloud Console access to the on-premises OIDC provider for authenticating users.
+   - **certificateAuthorityData**: Optional. A base64-encoded PEM-encoded certificate authority certificate of your OIDC provider. Needed if identity provider certificate is not issued by a well-known public CA or, in any case, if `deployCloudConsoleProxy:` is set to `true`.

The authentication configuration can be set at cluster creation or after cluster creation on an existing cluster.

## Node pools for worker nodes

If the first cluster in an installation is a hybrid or standalone cluster, intended to host user workloads too, you will need to configure the worker nodes Node Pool resource in the cluster config file, providing the IP addresses of the target worker nodes. Below is an example using three worker nodes in a node pool:

```
```yaml
# Node pools for worker nodes
apiVersion: baremetal.cluster.gke.io/v1
kind: NodePool
metadata:
  name: node-pool-1
  namespace: cluster-hybrid-cluster

  clusterName: hybrid-cluster
