In the example shown in figure 10, a policy was found that denies the request, resulting in the admissions controller sending the denial to the API server. Since the admission controller returned a denial, the API server will not create the object and will update the status of the object with the error provided by the policy engine.

A policy engine is a simple evaluation system that checks a request and decides if the request will be allowed. They have a fairly easy flow to them, but the real power in a policy engine are the policies themselves, which provide the logic for the decision process. In ACM we use constraint templates and constraints to implement security policies in our clusters. In the next sections, we will explain what a constraint template is and how they are implemented in a cluster by creating constraints.

# Introducing Gatekeeper Constraint Templates

Think of constraint templates as the logic that is used by the policy engine to make decisions about requests. When Gatekeeper is enabled on a cluster, it will create a set of default policies that contain rules for common use cases. At the time of this writing, ACM’s policy controller includes 32 templates, including:

+   - Allowed container registries
+   - Istio-specific policies
+   - Resource constraints
+   - Alternative security that provide similar security to Pod Security Policies (PSPs)
