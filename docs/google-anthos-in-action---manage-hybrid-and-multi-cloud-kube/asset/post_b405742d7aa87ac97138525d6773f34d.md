## 16.4.1 Understanding the Policy Controller

ACM’s Policy Controller provides an admission controller to a cluster. An admission controller is an engine that evaluates object requests based on a set of policies, which will allow or deny the creation of the object.

When you enable the policy engine, a ValidatingWebhookConfiguration is created, which registers the engine as an admission controller with the API server. Once registered, the API server will send object requests to the admission controller to be evaluated, as shown below.

**Figure 16.1 Admission Controller Policy Validation Flow**

![](img/fb3bebce7b5f593bca1a7f8a1371be06_591_0.png)

In the above workflow, the API server has received a request to create a new pod. Since the cluster has ACM installed with the Policy Controller enabled, the request is sent to the Gatekeeper service, which forwards the request to the Gatekeeper pod which checks the configured policies for any violations.

At this point, you may be wondering what kind of latency or performance issues a cluster may experience once Gatekeeper has been deployed. On average, policy evaluation takes about 1 millisecond, even when larger policies are evaluated. Like any system that allows you to create your own objects, it is possible to create a policy that will impact the performance of the policy engine - resulting in overall system latency. Creating policies is beyond the scope of this chapter, if you want to learn more about policies and performance, you can find additional details on the Open Policy Agent website at [https://www.openpolicyagent.org/docs/latest/policy-performance/](https://www.openpolicyagent.org/docs/latest/policy-performance/)

In the example shown in figure 16.1, a policy was found that denies the request, resulting in the admission controller sending the denial to the API server. Since the admission controller returned a denial, the API server will not create the object and will update the status of the object with the error provided by the policy engine.

A policy engine is a simple evaluation system that checks a request and decides if the request will be allowed. They have a fairly easy flow to them, but the real power in a policy engine are the policies themselves, which provide the logic for the decision process. In ACM we use constraint templates and constraints to implement security policies in our clusters. In the next sections, we will explain what a constraint template is and how they are implemented in a cluster by creating constraints.

## Enabling a Policy

To enable the enforcement of a policy, you need to create a YAML file that defines a constraint, which will be evaluated when a new object is **created**. *This is a key behavior to keep in mind* - since the policy engine is an admission controller, it only evaluates objects when they are created, or admitted to the cluster. It **will not** enforce the policy against any existing objects, until they are recreated. This is often overlooked by users who are newer to Gatekeeper, and is a key point to remember when you implement a new policy in your cluster.

Earlier we explained how a container that is started as a privileged container could be used to compromise the host, and ultimately the cluster. ## Auditing a Constraint

Before enforcing a new constraint, you should test it against the cluster to avoid any unexpected results. As mentioned in the previous section, when you create a new constraint, it will be enforced by default. This default behaviour can be changed, from enforcement to auditing, by adding the enforcementAction: dryrun option to the constraint manifest. Using the psp-privileged-container example, we can add the dryrun option to change the default enforcement behavior from enforcement to auditing.

```
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sPSPPrivilegedContainer
metadata:
  name: psp-privileged-container
spec:
  enforcementAction: dryrun
  match:
    kinds:
      - apiGroups: [""]
        kinds: ["Pod"]
```

Now that the enforcement has been changed to auditing, any pod that violates the constraint will only be logged as a violation, but it will still be allowed to start up. Also, unlike the default enforcement behavior, setting the constraint to dryrun will evaluate not only new requests but all running pods as well. This allows you to verify the effects of a constraint on every pod, rather than just new requests, so you will know how it would impact any pods that are restarted.

Once set to dryrun, you can view the results of the audit using `kubectl get <constraint kind> <constraint name> -o yaml`. For our example, we can view the affected pods by executing `kubectl get K8sPSPPrivilegedContainer psp-privileged-container -o yaml`. Depending on how many violations there are, you may receive a lengthy list of affected containers. The below output is an abbreviated list from a default cluster running Anthos on bare metal.
