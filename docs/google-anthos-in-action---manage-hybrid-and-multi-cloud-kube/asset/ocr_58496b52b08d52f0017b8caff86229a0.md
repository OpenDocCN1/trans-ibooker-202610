like containers versus virtual machines. Until recently, it was common for people to say that containers are not as secure as a virtual machine, with many pointing out that containers sharing the host's kernel as the primary security concern.

This shared kernel opens an avenue of attack for malicious actors, possibly allowing them to hack into a less-than-secure container, and from there, break out into the host itself. If an attacker breaks out of a container, they could, potentially, gain complete control of the host operating system. This is commonly contrasted with a virtual machine running on a hypervisor, where there’s no way a breakout could happen. Or could it?

Over the years, different hypervisors have had Common Vulnerabilities and Exposures (CVE’s) (More information about CVE’s can be found at https://cve.mitre.org/) that have led to varying levels of security issues, including privileged escalations, allowing an attacker to access the hypervisor with administrative permissions. Once compromised, an attacker would have access to every virtual machine on the host including the virtual disks used to run the virtual machine.

This section is not intended to spark a debate about container security versus virtual machine security. Our intention is to call out that no system is completely secure, and when a system, like Kubernetes, is deployed without understanding basic security, you put yourself and your organization at risk.

Let's take a look at some common Kubernetes security concerns that need to be examined before a cluster should be considered “production ready”.

# 16.3 Kubernetes Security Overview

A basic Kubernetes cluster usually enables very limited security settings, if any at all. This leaves organizations to address security on their own, which includes:

+   - Configuring any base Kubernetes security features
+   - Finding add-on products to address any missing security not included with a base cluster
