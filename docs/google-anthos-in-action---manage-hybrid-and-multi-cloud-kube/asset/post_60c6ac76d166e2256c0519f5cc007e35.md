
As the prerequisites we should already have 3 GKE/Anthos clusters deployed for each of your environments.

1. The first step is to define the delivery pipeline with the progression (the promotion sequence) and optionally the runtime targets. In this example we will create separate target files. For this example, we can define the following pipeline:

### 14.4.3 delivery-pipeline.yaml

```
apiVersion: deploy.cloud.google.com/v1beta1
kind: DeliveryPipeline
metadata:
    name: web-app
description: web-app delivery pipeline
serialPipeline:
  stages:
  - targetId: test
  - targetId: staging
  - targetId: prod
```

2. The targets can be defined as separate files. You can define a separate file per target. You will end up having 3 files:
   - target_test.yaml
   - target_staging.yaml
   - target_prod.yaml

   In each of the files you define the name of the target and the target cluster. Below you can see an example for the test target.

Now Cloud Deploy knows your application, and it will manage the deployment to targets according to your defined promotion sequence.

5. Now you can initiate the delivery pipeline by creating a **release** either from command line or from your CI tooling. Google Cloud Deploy creates a **rollout** resource, which associates the release with the first target environment. Based on that rollout, your application is deployed to the first target.

Run the following command from the directory containing your Skaffold config:

```
gcloud deploy releases create RELEASE_NAME --delivery-pipeline=PIPELINE_NAME
```

6. If you want to use Cloud Build as your CI tool, the following YAML file shows an example Cloud Build build configuration. This includes a call to Google Cloud Deploy to create a release, with a release name based on the date and Skaffold used for the build.

```
- name: gcr.io/k8s-skaffold/skaffold
  args:
    - skaffold
    - build
    - '--interactive=false'
    - '--file-output=/workspace/artifacts.json'
- name: gcr.io/google.com/cloudsdktool/cloud-sdk
  entrypoint: gcloud
  args:
    [
      "deploy", "releases", "create", "rel-${SHORT_SHA}",
      "--delivery-pipeline", "PIPELINE_NAME",
      "--region", "us-central1",
      "--annotations", "commitId=${REVISION_ID}",
      "--build-artifacts", "/workspace/artifacts.json"
    ]
```

7. Once you are ready to deploy the application to the next target of the sequence, you can promote it. Make a call to Google Cloud Deploy and create a new rollout.

```
gcloud deploy releases promote --release=RELEASE_NAME --delivery-pipeline=PIPELINE_NAME
```

8. You can continue the promotion to the last environment. In the example sequence it is the production.

Figure 14.38 promotion sequence

![](img/fb3bebce7b5f593bca1a7f8a1371be06_535_0.png)

9. If you want to introduce approvals into the promotion process, you can do it in the Target definitions. As an example, we might want to approve all promotions to staging and production as per Figure 14.39.

Figure 14.39 manual approvals

![](img/fb3bebce7b5f593bca1a7f8a1371be06_535_1.png)

You can define approvals in each of the target definitions.

```
apiVersion: deploy.cloud.google.com/v1
kind: Target
metadata:
  name:
  annotations:
  labels:
description:
requireApproval: true
gke:
  cluster: projects/[project_name]/locations/[location]/clusters/[cluster_name]
```

The parameter **requireApproval: true** indicates whether promotion to this target requires manual approval. Can be true or false. This property is optional. The default is false.

10. Now you can either approve or reject the rollout. To approve the rollout run the command:

```
gcloud deploy rollouts approve rollout-name --delivery-pipeline=PIPELINE_NAME
```

or reject the approval by running:

```
gcloud deploy rollouts reject rollout-name --delivery-pipeline=PIPELINE_NAME
```

As you can see this gives you full control over your application rollouts.

## 14.5 Modern CI/CD Platform

Modern CI/CD platforms must allow sustainable software development and operation of the entire application delivery pipeline. There is no single way to achieve that goal and it is always dependent on application and organization specifics.

![](img/fb3bebce7b5f593bca1a7f8a1371be06_538_0.png)

Anthos introduced capabilities to centralize management and unify tool sets that can be used while keeping at the same time the flexibility to integrate external tools into the pipeline. The goal for modern CI/CD platforms is to support enterprise-ready and secure GitOps implementations. That means every component must be described as a set of configuration files and definitions stored in the version control system. Each set is managed and maintained by a separate team. It was already mentioned that the modern CI/CD platform relies on shared responsibility. In such models there are always touch points for all parties via common interfaces like code repository, image build and Kubernetes manifest definition stage.

Modern application delivery relies on Kubernetes orchestration and microservices-based architecture. In such, there must be separation between developers and operator playground. Implementation depends on defined requirements. We can use a single cluster with multiple namespaces for a single site or non-production setups. If services we are delivering must be highly available, deliver low latency across the globe, or we must limit infrastructure lifecycle activities' impact, consider multiple Anthos clusters. Multi-cluster setup allows us also to roll out applications in small steps to individual clusters before it is fully released.

Let’s define an example application as a simple microservices-based voting system with capabilities to visualize voting results as presented below.

Figure 14.42 Application schema

![](img/fb3bebce7b5f593bca1a7f8a1371be06_539_0.png)

For the underlay infrastructure, it consumes an Anthos GKE cluster on GCP. There are three namespaces created there, one for each service:

- voting
- transfer
- results

It also uses three Google Managed services:

- Cloud Memorystore as managed Redis
- Cloud SQL as a central database for all votes, delivered as managed PostgreSQL
- Secret Manager as a secure secrets management system to store credentials for Memorystore and Cloud SQL

Developers consume infrastructure and do not care how it is delivered. It must meet their requirements related to namespaces and managed services. The responsible team must create a CI/CD pipeline that can be used for application hosting purposes and have full flexibility to test any changes.

To achieve the goal, we can use multiple different tools. If our teams are familiar with Terraform, we can utilize already available knowledge and integrate it into our CI/CD pipeline. Such an approach is fully in line with DORA's State of DevOps research program [30]. It defines that one of the key success factors for implementation of DevOps in an organization is freedom in the choice of tools that developers and operations people are using.

There is one more question: can I deliver such infrastructure even simpler? As we are using GCP managed resources instead of using external tools, we can leverage Anthos Config Connector capability described in detail in Chapter “Anthos Configuration Management” to deliver Secret Manager, Cloud Memorystore and Cloud SQL as declared objects in our code repository.

In case of a requirement to deliver services for other sources like Anthos on-prem, it is important to introduce infrastructure changes starting from day 1 in an automated way. Every Anthos on VMware or Anthos on bare metal must rely on predefined practices and security policies that can be constantly reused if needed.

Going deeper into our modern platform infrastructure, it must deliver the following elements to enable successful application delivery.
