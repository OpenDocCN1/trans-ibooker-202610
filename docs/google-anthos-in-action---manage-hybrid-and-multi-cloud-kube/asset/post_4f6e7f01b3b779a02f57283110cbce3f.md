## 6.2 Logging and Monitoring

Within Kubernetes, there are different kinds of logs and monitoring that can be used for managing the cluster. There are many metrics that Kubernetes system services provide, such as open-source, self-managed, and cluster-managed logging and monitoring solutions. Clusters have many control plane components, which provide detailed metrics for the workloads running on the Kubernetes cluster. You can also access them through the Cloud Console, which communicates with the Kubernetes API and essentially issues a kubectl logs command.

Whenever you use the Cloud Console, the output is delivered from the cluster via the Kubernetes API, which provides a real-time interface to the cluster’s logs and events. Especially for the systems like the one shown in Figure 6.10, you can inspect the logs directly in the console.

**Figure 6.10. Container logs**

![](img/fb3bebce7b5f593bca1a7f8a1371be06_182_0.png)

Pay attention to errors, warnings, and output from the standard output stream during the execution of the Kubernetes job. If you want to use the logs with Google Cloud’s operations suite (formerly Stackdriver), it must be enabled on the GKE cluster; you also need to configure and forward the logs to the Cloud Logging API and write them into the cloud.

There are different observability dimensions about a service, based on its metrics, requests, and codes. Observability can be used as a historical trend, which can be used to trace issues and to identify possible issues in implementation. When a service is unable to handle a request, the error appears in the logs as a 5xx response, and every request is recorded in the monitoring system as a metric. You can then monitor the system performance and user metrics in a unified way, and set alerts based on the defined thresholds.

External tools such as Splunk, Elastic, and others can be used to forward your logs to the services (e.g., [https://cloud.google.com/architecture/logging-anthos-with-splunk-connect](https://cloud.google.com/architecture/logging-anthos-with-splunk-connect) and [https://cloud.google.com/architecture/partners/monitoring-gke-on-prem-with-the-elastic-stack](https://cloud.google.com/architecture/partners/monitoring-gke-on-prem-with-the-elastic-stack)).

### 6.2.1 Logging and Monitoring GKE on-prem

There are different options to choose between when installing GKE on-prem clusters.

The first option is to use Google’s managed Cloud Logging and Cloud Monitoring solution. Cloud Logging and Monitoring features provide interfaces to use as a unified view, such as Google Kubernetes Engine Logging and Monitoring. All logs are collected and displayed in a graphical UI level according to the Kubernetes object type. In most cases, GKE logging includes the logging facet and generates metrics for high-availability, high-throughput, cluster-level, node-level, and container-level metrics as a set of metrics, which are easy to track cluster health and set alarms for Cloud Logging and Monitoring in Google Cloud. This is a fully managed service and includes managed dashboards and integration capabilities to help you build a useful monitoring control plane. Cloud Logging and Monitoring are often used to monitor Google Cloud services and provide alerts and notifications related to container events; this makes them the single point for all monitoring service health.

This is the recommended option in the current architecture to gain a comprehensive understanding of the system using a single point for managing the logging and monitoring stack, and it also has a few cost-effective and fully managed options. There are some particular organizations that require installing Cloud Logging and Monitoring to run external services. If these cannot be installed, then a Google Support API will be provided and Google will offer a fully supported GKE on-prem solution for these use cases.
