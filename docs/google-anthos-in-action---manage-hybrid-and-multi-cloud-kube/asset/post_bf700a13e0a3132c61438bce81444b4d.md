## 4.5.4 Understanding Declarative and Imperative

This section introduces the concept of Kubernetes cluster components. Knowing your components and how they interact with each other will help you understand the issues and understand the cluster architecture as a system. As we progress through the text, the cluster components will be covered in more detail. It is important to understand the underlying Kubernetes resources. For example, you can find more information about Kubernetes resources on the Kubernetes website at https://kubernetes.io/docs/concepts/overview/working-with-objects/kubernetes-objects/

To effectively deploy and operate applications in Kubernetes, you need to understand the features of the various Kubernetes objects. First, we will walk through YAML manifests and Kubernetes cluster objects.

In Kubernetes, an automation framework can be used in two different methods. These methods are referred to as the declarative model and the imperative model.

Understanding the difference between these two approaches, and how they differ from each other, is important for understanding the concept of a control loop.

### Understanding Control Loops

By maintaining the desired state, Kubernetes implements a control loop. A control loop is always checking the actual state of a resource against the desired state.

If you deliberately define a Deployment with three replicas of a Pod, and then the actual number of Pods is less than desired, Kubernetes will take action to create the new Pods to match the desired state.

Let’s look at a high-level representation of the API Server control loop and how the desired state is maintained:

Figure 4.7 – Control loop example

![](img/fb3bebce7b5f593bca1a7f8a1371be06_88_0.png)

In the above diagram, a control loop does not need to be complex to maintain a desired state. The control loop simply keeps looping through the API Server resources in the cluster, comparing the currently available number of resources with the desired number. This means that if a Pod is deleted, Kubernetes will try to create a new Pod to make the current resource count equal to the desired count.

Understanding the features of these components and how Kubernetes manages and maintains the desired state of a deployment is important, and it’s not just a beginning. Applying a resource that has been defined with a desired state and comparing actual state against the workflow, we can understand the benefits of using the declarative system. To understand the fundamental aspects of the architecture, we should understand the basic functionality of the resource components. In this context, the Kubernetes architecture will be covered, including the components of the control plane, worker nodes, and the data plane.

One of the first concepts to understand is the difference between the declarative and imperative models. The table below gives a brief description of each model.

![](img/fb3bebce7b5f593bca1a7f8a1371be06_88_1.png)

| Model | Description |
| --- | --- |
| *Declarative* | Developers declare what they would like the system to do, there is no need to tell the system how to do it. The declarative model uses Kubernetes manifests to declare the application’s desired state. |
| *Imperative* | Developers are responsible for creating each step that is required for the desired end-state. The steps to create the deployment are completely defined by the developer. The imperative model uses kubectl commands like create, run, and delete to tell the API server what resources to manage. |

In a declarative model, you can manage and maintain a number of resources in a single file. For example, if you wanted to deploy a Nginx web server, including a deployment, and a service, you would create a single YAML file with those resources. The manifest would then be applied using the kubectl apply command, which creates the resources and tracks the declared configuration. Because Kubernetes checks the resources in the file, it becomes easier to manage and make changes to the deployment and its resources.

In an imperative model, you need to use multiple commands to create the final deployment. For example, the following example uses kubectl commands to create a Nginx server, a service, and an Ingress:

```
kubectl create ns web-example
kubectl run nginx-web --image=nginx:v1 -n web-example
kubectl create service clusterip nginx-web --tcp=80:80
```

These commands can be combined and deployed using the declarative approach, but it becomes more complicated to maintain. In an imperative model, each kubectl command must specify every option and only available resources can be used. In this example, if we need to create a second container or perform a specialized task, we cannot use a single command to upgrade it because the kubectl commands would need to be re-executed to change the configuration.

It is a common practice to use imperative commands for quick deployment, but without clear requirements, it becomes difficult to maintain and scale. If you are using imperative commands, you should use version control to track changes, so that you can make changes through automation.

To understand how the Kubernetes API and the declarative model work together, you need to understand how the system maintains the desired state and how the control loop works.

## 4.5.5 Understanding Kubernetes resources

Throughout this book, you have seen a variety of Kubernetes resources. In an earlier chapter, we mentioned over 60 resource types, including a few built-in ones, and you can add custom resources through CRDs (Custom Resource Definitions). There are many Kubernetes books available, and these resources can help you understand how to use the resource types effectively.

It’s challenging to remember all the different resource types available. However, there is a command that lists all the available resources in a cluster.

The first command is `kubectl api-resources`, which shows all the available resources in a cluster:

```
kubectl api-resources
```

The output shows the resource names and their short names. If a resource can be included in a namespace, it is shown with a name in a namespace. You can see a lot of resources in this table, but if you need to know more about a resource, Kubernetes provides another command to display the details:

```
kubectl explain <resource name>
```

The `explain` command provides a short description of the resource and all the fields that can be used to create a manifest. For example, in Figure 4.2, you can see a brief description of what a Node is, and the fields used to create resources.
