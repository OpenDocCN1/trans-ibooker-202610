
## 生产中 AI 模型失效的 7 个原因

> 模型在训练时表现良好，但在真实场景中却一败涂地。问题往往不在于模型本身，而在于我们构建模型的方式。

- 数据分布偏移（Data Drift）
- 过度拟合至验证集
- 特征分布不一致

在实际生产中，模型失效的最常见原因是训练数据与真实世界数据之间的分布差异。当数据的统计特性随时间发生变化时，模型的性能会急剧下降。

```python
skew = abs(train_mean - live_mean)
if skew > threshold:
    trigger_retraining()
```

持续监控数据分布，并在分布偏移超限时触发重新训练，是保证模型长期有效的重要手段。

- 建立特征健康度检查
- 设定模型性能回退机制
- 定期人工审计模型输出

### Load balancer configuration

To use the bundled MetalLB load balancer, specify the `loadBalancer` section in the cluster configuration file. The following example sets a virtual IP for the control plane:

```yaml
loadBalancer:
    vips:
        controlPlaneVIP: "133.23.22.100"
    kind: MetalLB
```

If you use another load balancer type, such as F5 BIG-IP, configure the fields accordingly.

### Anti-affinity groups

`antiAffinityGroups.enabled` controls whether control-plane nodes are placed on separate ESXi hosts. Enabling anti-affinity groups helps protect the control plane from a single host failure or ESXi maintenance event. If you disable this option, you reduce the number of ESXi hosts required, but you increase the risk of control-plane downtime.

```yaml
antiAffinityGroups:
    enabled: true/false
```

### Stackdriver / Cloud Monitoring

To export metrics and logs to Google Cloud, configure the `stackdriver` section:

```yaml
stackdriver:
    projectID: "my-logs-project"
    clusterLocation: "us-central1"
    enableVPC: false
    serviceAccountKeyPath: "my-key-folder/log-mon-key.json"
    disableVsphereResourceMetrics: true
```

The service account key file must have the appropriate Cloud Monitoring and Cloud Logging roles. If VPC is not used, set `enableVPC: false`.

### Cloud Audit Logging

To enable Cloud Audit Logging, configure the `cloudAuditLogging` section:

```yaml
cloudAuditLogging:
    projectID: "my-audit-project"
    clusterLocation: "us-central1"
    serviceAccountKeyPath: "my-key-folder/audit-log-key.json"
```

The audit logging configuration tracks cluster lifecycle changes and requires a service account with appropriate permissions.

### Node auto repair

`autoRepair` controls whether unhealthy nodes are automatically repaired. When enabled, the `cluster-health-controller` checks node health and drains and recreates unhealthy nodes, as shown in Figure 9.5.

```yaml
autoRepair:
    enabled: true/false
```

### Private registry

To use a private container registry, specify the `privateRegistry` section with the registry address, credentials, and optional CA certificate:

```yaml
privateRegistry:
  address: "{{Private_Registry_IP_address}}"
  credentials:
    fileRef:
      path: "{{my-config-folder}}/admin-creds.yaml"
      entry: "private-registry-creds"
    caCertPath: "my-cert-folder/registry-ca.crt"
```

### Secrets encryption

Anthos on VMware supports encrypting Kubernetes secrets at rest. To enable this, set the `secretsEncryption` section:

```yaml
secretsEncryption:
  mode: GeneratedKey
  generatedKey:
    keyVersion: 1
```

> **TIP**: Rotate the generated encryption key using the `gcloud` command or the appropriate update command, and then update the key version in the configuration.

![](img/fb3bebce7b5f593bca1a7f8a1371be06_268_0.png)

> **IMPORTANT**: After deployment, the number of master nodes **cannot** be changed without fully recreating the cluster.

### User cluster namespaces

Each user cluster is deployed in a dedicated namespace in the admin cluster. The namespace contains the user cluster services, deployments, and other Kubernetes resources.

The namespace name is linked to the cluster name, so you can find all deployed resources in a user cluster with:

```
kubectl get all -n {{ clusterName }}
```

The namespace for a user cluster is created automatically when the user cluster is created, and it is managed by the user cluster lifecycle controller. It should not be manually modified.

**Figure 9.7. Anthos on VMware user cluster namespaces**

| Admin Cluster | User Cluster name | User Cluster |
| --- | --- | --- |
| config-management-system | kube-public | default |
| kube-system | gke-connect | knative-serving |
| gke-system | kube-node-lease |  |

Similar to an admin cluster, a user cluster is deployed from a YAML configuration file. The basic resource definition is:

```yaml
apiVersion: v1
kind: UserCluster
```

> **TIP**: You can convert old versions of configuration files using:
>
> ```
> gkectl create-config cluster --config $MyAwesomeClusterConfigFile
> ```

### Network configuration

To define the cluster network, configure the `network` section with either DHCP or static IP mode.

DHCP mode:

```yaml
network:
  ipMode:
    type: dhcp
  serviceCIDR: 10.96.232.0/24
  podCIDR: 192.168.0.0/16
  vCenter:
    networkName: "My Anthos on VMware user network"
  additionalNodeInterfaces:
  - networkName: "My additional network"
    type: dhcp
```

Static IP mode:

```yaml
network:
  ipMode:
    type: "static"
    ipBlockFilePath: "myNodeHostConfFile.yaml"
  additionalNodeInterfaces:
  - networkName: "My additional network"
    type: "static"
    ipBlockFilePath: "mySecondNodeHostConfFile.yaml"
```

Before starting cluster creation, decide whether the master node will use 3 or 1 replicas. A 3-replica control plane provides high availability; a 1-replica control plane does not.

The following example defines the master node resources:

```yaml
masterNode:
  cpus: 4
  memoryMB: 8192
  replicas: 3
```

> **TIP**: The configuration file is YAML. Enum values should be quoted as strings; otherwise YAML may interpret them incorrectly. Numeric fields such as `cpus`, `memoryMB`, and `replicas` should use integer values.
