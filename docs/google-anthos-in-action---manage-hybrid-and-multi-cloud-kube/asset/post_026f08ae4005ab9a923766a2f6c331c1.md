
- ACM also brings in additional components based on open-source tools:
  - Config Connector provides Infrastructure-as-Data capability to a Kubernetes cluster, allowing for the provisioning of Google Cloud resources by declaring a Kubernetes resource.
  - Policy Controller, based on the open-source Open Policy Agent, gives administrators a convenient tool to create and enforce policies across their clusters.
  - Hierarchy Controller is the result of an initiative to provide an alternative method of replicating resources between namespaces in a cluster. Since storing secrets in a git repo is an anti-pattern, Hierarchy Controller definitions allow an organization to define a secret or configuration once and have it replicated to the descendant namespaces automatically.
- Three case studies explored different reasons for using and implementation of ACM:
  - Evermore Industries wants to reduce the number of users directly working in their Production environment, as well as allow development teams to provision certain Google Cloud resources directly. They are currently using, and will continue to use, a templating engine for generating their Kubernetes configurations.
  - Village Linen, LLC is leveraging ACM both on and off-premise, as well as Hierarchy Controller to manage the replication of ConfigMaps and Secrets within both sets of clusters.
  - Ambiguous Rock Feasting is well-versed in Kubernetes, but is making specific use of the ClusterSelectors feature of ACM in order to more precisely control where their applications are deployed.

In this chapter we will guide you on how to develop and deploy Anthos applications. To simplify this, we will use a simple “Hello world” application. This will start with Continuous Development where we will learn how we can start developing an Anthos application and preview them even before we commit the code to the Git repository. We then look at Continuous Integration and finally we will discuss Continuous Development/Delivery.

We need to realize that you might have three different personas that interact with the CI/CD pipelines. Those personas are:

- **Developers:** develop the application code
- **Operators:** configure the application deployments using Kubernetes manifests

In this chapter we will concentrate on the first two personas. If you want to learn more about the Security persona that deals with the Policies, please refer to the *Configuration management chapter*.

Modern software development processes are complex. Producing high-quality software at a consistent pace, in a sustainable manner, involves a number of processes and tools. The implementation of a CI/CD pipeline is one of the best practices to achieve this. **Continuous Integration (CI)** is the practice of software development where developers check in their code frequently, integrating regularly – at least once a day, and each integration is followed by a validation; that is, an automated process to build and test integrated change[^1]. It allows us to achieve reliable, repeatable and reusable builds with constant speed and at a proper level while preventing chaos and improving efficiency.

Continuous Integration is only one aspect of the software delivery process, for a successful pipeline-driven development, CI must be followed by Continuous Delivery (CD). **Continuous Delivery (CD)**[^2] is the ability to get changes of all types, including new features, configuration changes, bug fixes and experiments, into production safely and quickly in a sustainable way. It applies to infrastructure configurations, application deployment and mobile app publishing, database and static resource modifications. Continuous Delivery can be used in any environment, regardless of the regulatory requirements for a particular organization. A Continuous Delivery pipeline improves delivery of software from source to production by making this process more automated, thus improving reliability, predictability and visibility of the pipeline, which reduces risks[^3].

Let's have a look at some features that characterize modern CI/CD platforms:

### Repeatability

Allows automation of requirements and processes around created code and artifacts. Build process should be deterministic, so that developers have confidence in produced artifacts. Repeatable builds and testing allow developers to run the same processes in their local environments as well. Automation of deployment and configuration management helps to provide consistency across environments.

### Reliability

Improves confidence of the development and operational teams in the processes and systems that guarantee availability and suitability of the tools, as well as completeness and sufficiency of integration, testing and operational requirements. Automated testing via defined workflows are key to capture and keep track of components' final success and failure states, increasing team confidence and knowledge during development and release cycles.

### Reusability

Enable teams to scale up, simplify and speed up development workflows. A CI/CD pipeline should be implemented in such a way that allows reusing components of the pipeline for similar applications. This not only reduces cost of setting up new pipelines but also improves developers’ efficiency when working with multiple applications across the enterprise.

### Automated tests

In a high-quality delivery process it is critical to validate developed systems architecture and functionality. That can be achieved by implementation of a robust automated testing flow as an integral part of the Continuous Delivery pipeline. Modern delivery pipelines should have as many automated tests as possible. These include not only unit, component, system functional tests but also non-functional ones that check capability, availability and security compliance. Automated tests provide almost immediate feedback to developers, decreasing the amount of bugs and error rate for production deployments.

### Trunk-based development

Continuous delivery can be significantly slowed down when developers are working in “split brain” environments, where feature or bugfix code branches have a very long lifetime. As a result, in big teams, code changes can cause conflicts when integrating long-lived branches. This may require manual activities, grinding CI processes to a halt.
