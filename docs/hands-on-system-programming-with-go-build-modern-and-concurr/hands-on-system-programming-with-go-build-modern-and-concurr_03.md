## 第 1 章：系统编程简介

本章介绍系统编程，探讨从其最初定义到随系统演变而发生转变的一系列主题。本章提供了一些基本概念，以及 Unix 及其资源（包括内核和**应用程序编程接口**（**API**））的概览。许多概念在此定义，并在本书其余部分中使用。

本章将涵盖以下主题：

- 什么是系统编程？
- 应用程序编程接口
- 理解保护环的工作原理
- 系统调用概览
- POSIX 标准

### 系统编程入门

多年来，IT 格局发生了巨大变化。挑战冯·诺依曼架构的多核 CPU、互联网和分布式系统只是过去 30 年中发生的一些变化。那么，系统编程在这个格局中处于什么位置呢？

### 面向软件的软件

让我们从标准教科书定义开始。

系统编程是编程计算机系统软件的活动。与应用程序编程相比，系统编程的主要区别特征在于：应用程序编程旨在生产直接为用户提供服务的软件（例如文字处理器），而系统编程旨在生产为其他软件提供服务的软件和软件平台，并设计为在性能受限的环境中工作，例如操作系统、计算科学应用、游戏引擎和 3A 视频游戏、工业自动化以及软件即服务应用。

# 系统软件

- 被其他软件使用，而非直接面向最终用户的软件。
- 该软件感知硬件（了解硬件工作原理），并面向性能。

这使得我们能轻易识别出操作系统内核、硬件驱动、编译器和调试器属于系统软件，而聊天客户端或文字处理器则不属于。

历史上，系统程序是使用汇编语言和 C 语言创建的。随后出现了 Shell 和脚本语言，它们被用来将系统程序提供的功能串联起来。系统语言的另一个特征是对内存分配的控制。

## 语言与系统演进

在过去十年中，脚本语言变得流行，以至于其中一些语言获得了显著的性能提升，甚至被用来构建完整的系统。例如，只需看看用于 JavaScript 的 V8 引擎和 Python 的 PyPy 实现，它们极大地提升了这些语言的性能。

其他语言（如 Go）证明了垃圾回收和性能并不互斥。特别是，Go 在 1.5 版本中成功用 Go 编写的原生版本替换了其原本由 C 编写的内存分配器，并将其优化到性能可媲美的程度。

与此同时，系统开始变得分布式，应用程序开始以容器形式交付，并由其他系统软件（如 **Kubernetes**）进行编排。这些系统旨在维持巨大的吞吐量，主要通过以下两种方式实现：

- 通过扩展——增加托管系统的机器数量或资源
- 通过优化软件以使其更有效地利用资源

## 系统编程与软件工程

系统编程的一些实践——例如应用程序与硬件绑定、面向性能、在资源受限的环境中运行——这种方法在构建分布式系统时同样有效，因为限制资源使用可以减少所需的实例数量。看来系统编程是解决通用软件工程问题的一个好途径。

这意味着，学习关于高效利用机器资源（从内存使用到文件系统访问）的系统编程概念，在构建任何类型的应用程序时都将大有裨益。

# 应用程序编程接口

API 是一系列子程序定义、通信协议和构建软件的工具。API 最重要的方面是其提供的功能，结合其文档，这便于用户在另一个软件中使用和实现该软件本身。API 可以是允许应用软件使用系统软件的接口。

API 通常具有特定的发布策略，旨在供特定接收群体使用。这可以是以下几种：

- 私有，仅供内部使用
- 合作伙伴，仅供特定群体使用——这可能包括希望将服务与其集成的公司
- 公开，可供所有用户使用

## API 的类型

我们将看到有多种类型的 API，从用于使不同应用软件协同工作的 API，到操作系统向其他软件暴露的内部 API。

### 操作系统

API 可以规定应用程序与操作系统如何交互。例如，Windows、Linux 和 macOS 都有一个接口，使得操作文件系统和文件成为可能。

### 库与框架

与软件库相关的 API 描述并规定（提供关于如何使用它的说明）其每个元素应如何表现，包括最常见的错误场景。API 的行为和接口通常被称为**库规范**，而库是此类规范中描述规则的实现。库和框架通常与语言绑定，但有一些工具使得在不同语言中使用库成为可能。你可以使用 `CGO` 在 Go 中使用 C 代码，在 Python 中可以使用 `CPython`。

### 远程 API

这些 API 使得使用特定通信标准操作远程资源成为可能，允许不同技术协同工作，无论语言或平台如何。一个很好的例子是 **Java 数据库连接** (`JDBC`) API，它允许使用同一组函数查询多种不同类型的数据库，或者 `Java RMI` API，它允许像使用本地函数一样使用远程函数。

### Web API

Web API 是定义一系列关于所用协议、消息编码、可用端点及其预期输入输出值的规范的接口。这类 API 有两种主要范式——REST 和 SOAP：

- REST API 具有以下特征：
    - 它们将数据视为资源。
    - 每个资源由一个 URL 标识。
    - 操作类型由 HTTP 方法指定。
- SOAP 协议具有以下特征：
    - 它们由 W3C 标准定义。
    - XML 是消息编码的唯一格式。
    - 它们使用一系列 XML 模式来验证数据。

# 理解保护环

**保护环**，也称为**分层保护域**，是用于防止系统故障的机制。其名称源于其权限层级的层次结构，由同心圆环表示，向外环移动时权限递减。每个环之间有特殊的门，允许外环以受限方式访问内环资源。

## 架构差异

环的数量和顺序取决于 CPU 架构。它们通常按权限递减编号，使环 0 成为最特权的一级。这适用于使用四个环（环 0 到环 3）的 i386 和 x64 架构，但不适用于 ARM，后者使用反向顺序（从 EL3 到 EL0）。大多数操作系统并未使用所有四个级别；它们最终采用两级层次结构——用户/应用（环 3）和内核（环 0）。

## 内核空间与用户空间

在操作系统下运行的软件将在用户（环 3）级别执行。为了访问机器资源，它必须与运行在环 0 的操作系统内核交互。以下是环 3 应用程序无法执行的一些操作列表：

- 修改当前段描述符，它决定了当前环级
- 修改页表，防止一个进程查看其他进程的内存
- 使用 `LGDT` 和 `LIDT` 指令，防止它们注册中断处理程序
- 使用 `in` 和 `out` 等 I/O 指令，这些指令会无视文件权限并直接从磁盘读取

例如，对磁盘内容的访问将由内核中介，内核将验证应用程序是否有权限访问数据。这种协商提高了安全性并避免了故障，但伴随着影响应用程序性能的显著开销。

一些应用程序可以被设计为直接在硬件上运行，无需操作系统提供的框架。这适用于实时系统，在这些系统中，响应时间和性能不容妥协。

### 深入系统调用

系统调用是操作系统为应用程序提供资源访问的方式。它是由内核实现的用于安全访问硬件的 API。

#### 提供的服务




我们可以使用一些类别来划分操作系统提供的众多功能。这些类别包括正在运行的应用程序及其流程的控制、文件系统访问以及网络。

## 进程控制

此类服务包括 `load`，它将程序加载到内存中并准备执行，然后将控制权传递给程序本身；或 `execute`，它在预先存在的进程上下文中运行可执行文件。属于此类别的其他操作如下：

*   `end` 和 `abort`——前者要求应用程序退出，后者强制其退出。
*   `CreateProcess`，在 Unix 系统上也称为 `fork`，在 Windows 中称为 `NtCreateProcess`。
*   终止进程。
*   获取/设置进程属性。
*   等待时间、等待事件或发送事件信号。
*   分配和释放内存。

## 文件管理

文件和文件系统的处理属于文件管理系统调用。有用于从文件系统添加或移除条目的 `create` 和 `delete` 文件操作，以及用于获取文件控制权以执行 `read` 和 `write` 操作的 `open` 和 `close` 操作。也可以读取和更改文件属性。

## 设备管理

设备管理处理除文件系统之外的所有其他设备，例如帧缓冲区或显示器。它包括从请求设备开始的所有操作，包括与其通信（`read`、`write`、`seek`）及其释放。它还包括更改设备属性以及逻辑上连接和断开设备的所有操作。

## 信息维护

读写系统日期和时间属于信息维护类别。该类别还负责其他系统数据，例如环境变量。属于此处的另一组重要操作是进程、文件和设备属性的请求与操作。

## 通信

从处理套接字到接受连接的所有网络操作都属于通信类别。这包括连接的创建、删除和命名，以及 `send` 和 `receive` 消息。

# 操作系统之间的差异

Windows 拥有一系列不同的系统调用，涵盖所有内核操作。其中许多与 Unix 对应物完全一致。以下是一些重叠系统调用的列表：

| 类别 | Windows | Unix |
| --- | --- | --- |
| 进程控制 | `CreateProcess()`<br>`ExitProcess()`<br>`WaitForSingleObject()` | `fork()`<br>`exit()`<br>`wait()` |
| 文件操作 | `CreateFile()`<br>`ReadFile()`<br>`WriteFile()`<br>`CloseHandle()` | `open()`<br>`read()`<br>`write()`<br>`close()` |
| 文件保护 | `SetFileSecurity()`<br>`InitializeSecurityDescriptor()`<br>`SetSecurityDescriptorGroup()` | `chmod()`<br>`umask()`<br>`chown()` |
| 设备管理 | `SetConsoleMode()`<br>`ReadConsole()`<br>`WriteConsole()` | `ioctl()`<br>`read()`<br>`write()` |
| 信息维护 | `GetCurrentProcessID()`<br>`SetTimer()`<br>`Sleep()` | `getpid()`<br>`alarm()`<br>`sleep()` |
| 通信 | `CreatePipe()`<br>`CreateFileMapping()`<br>`MapViewOfFile()` | `pipe()`<br>`shmget()`<br>`mmap()` |

# 理解 POSIX 标准

为了确保操作系统之间的一致性，IEEE 为操作系统制定了一些标准。这些标准将在以下章节中描述。

## POSIX 标准与特性

用于 Unix 的 `Portable Operating System Interface` (`POSIX`) 代表了一系列操作系统接口标准。第一个版本可追溯至 1988 年，涵盖文件名、Shell 和正则表达式等一系列主题。

`POSIX` 定义了许多特性，它们被组织在四个不同的标准中，每个标准专注于 Unix 合规性的不同方面。它们都以 `POSIX` 后跟一个数字命名。

## POSIX.1 – 核心服务

`POSIX.1` 是 1988 年的原始标准，最初命名为 `POSIX`，但后来重命名以便在不放弃名称的情况下向该系列添加更多标准。它定义了以下特性：

*   进程创建与控制
*   信号
*   浮点异常
*   分段/内存违规
*   非法指令
*   总线错误
*   定时器
*   文件与目录操作
*   管道
*   C 库（标准 C）
*   I/O 端口接口与控制
*   进程触发器

## POSIX.1b 和 POSIX.1c – 实时与线程扩展

`POSIX.1b` 专注于实时应用程序和需要高性能的应用程序。它关注以下方面：

*   优先级调度
*   实时信号
*   时钟与定时器
*   信号量
*   消息传递
*   共享内存
*   异步与同步 I/O
*   内存锁定接口

`POSIX.1c` 引入了多线程范式并定义了以下内容：

*   线程创建、控制与清理
*   线程调度
*   线程同步
*   信号处理

## POSIX.2 – Shell 与工具

`POSIX.2` 为命令行解释器和实用程序（如 `cd`、`echo` 或 `ls`）指定了标准。

## 操作系统遵循情况

并非所有操作系统都符合 `POSIX` 标准。例如，Windows 诞生于该标准之后，并不合规。从认证角度来看，macOS 比 Linux 更合规，因为后者使用的是构建在 `POSIX` 之上的另一个标准。

## Linux 与 macOS

大多数 Linux 发行版遵循 `Linux Standard Base` (`LSB`)，这是另一个包含 `POSIX` 及更多内容的标准，专注于维护不同 Linux 发行版之间的互兼容性。它不被视为官方合规，因为开发者未经历认证过程。

然而，macOS 自 2007 年 Snow Leopard 发行版起成为完全兼容，并自那时起获得了 `POSIX` 认证。

## Windows

Windows 不符合 `POSIX` 标准，但有许多尝试使其合规。存在开源项目如 Cygwin 和 MinGW，它们提供了一个不太符合 `POSIX` 标准的开发环境，并支持使用 Microsoft Visual C 运行时库的 C 应用程序。Microsoft 本身也尝试过 `POSIX` 兼容性，例如 Microsoft POSIX 子系统。Microsoft 制作的最新兼容层是 Windows Linux Subsystem，这是一项可在 Windows 10 中激活的可选功能，深受开发者好评（包括我自己）。

# 总结

在本章中，我们了解了什么是系统编程——编写具有严格要求的系统软件，例如与硬件绑定、使用低级语言、在资源受限的环境中工作。在构建通常需要优化资源使用的分布式系统时，其实践非常有用。我们讨论了 API，即允许软件被其他软件使用的定义，并列出了不同类型——操作系统中的 API、库和框架、远程和 Web API。

我们分析了操作系统中对资源的访问如何按称为保护环的分层级别排列，以防止不受控制的使用，从而提高安全性并避免应用程序故障。Linux 模型将此层次结构简化为仅两个级别，称为用户空间和内核空间。所有应用程序都在用户空间运行，为了访问机器资源，它们需要内核介入。

然后我们看到了一种特定类型的 API，称为系统调用，它允许应用程序向内核请求资源，并调解进程控制、文件的访问与管理、设备和网络通信。



我们概述了 POSIX 标准，该标准定义了 Unix 系统的互操作性。在所定义的特性中，还包括 C API、CLI 实用程序、Shell 语言、环境变量、程序退出状态、正则表达式、目录结构、文件名以及命令行实用程序 API 惯例。

在下一章中，我们将探索 Unix 操作系统资源，如文件系统和 Unix 权限模型。我们将了解什么是进程，它们如何相互通信，以及如何处理错误。
