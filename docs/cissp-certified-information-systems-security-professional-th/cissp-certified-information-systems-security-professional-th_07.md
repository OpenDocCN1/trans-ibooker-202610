# 进行或促进安全审计
安全从业人员通常负责进行或促进审计，在这两种情况下，目标是相同的：对照标准比较组织的某个方面。进行审计或担任审计员需要对审计中使用的流程、目标和技术有透彻的理解和知识。促进审计不需要那么多的知识，但在审计前准备时，了解审计流程会有所帮助。

## 设计审计计划
组织的审计计划可以设计为进行内部审计、促进外部审计，或根据需要两者兼顾。适当的资源、监督和管理层的支持至关重要，同样重要的是执行审计的现实时间表。一次性、特定时间点的审计提供了安全计划的有用快照，但定期审计计划允许随时间跟踪计划并显示改进。

### 常见审计框架
如果组织正在追求特定类型的审计，例如 FedRAMP 或 SOC 2，则审计计划将由标准决定，因为这是外部审计员必须遵循的内容。审计框架也可以用作设计内部计划时最佳实践的指南。事实上，设计与外部审计员使用的相同标准保持一致的内部计划是有意义的，因为它允许组织发现外部审计员可能发现的相同问题。

这些是提供可据此执行审计标准的常见信息安全框架：
* **SSAE 18** 是《鉴证业务准则声明》，审计员在执行 SOC 2 审计时使用。
* **ISO/IEC 15408-1:2009**，“信息技术 — 安全技术 — 信息技术安全评估准则”，是通用标准认证的基础，通用标准认证是对技术产品按照一组定义的安全功能要求进行的正式评估流程。本文件和 ISO/IEC 18045 可免费获取。
**ISO/IEC 18045:2008**，“信息技术 — 安全技术 — 信息技术安全评估方法”，是 ISO 15048 的配套文件，并提供了一致的准则和评估方法的标准。
* **ISO/IEC 27006:2015**，“信息技术 — 安全技术 — 信息安全管理体系审核和认证机构的要求”，是审计员执行针对 ISO 27001 的认证审核的官方要求和指导集合。
* **NIST 特刊 (SP) 800-53A**，“评估联邦信息系统和组织中的安全和隐私控制”，是评估 NIST SP 800-53 中概述的控制措施的指南。它引入了一套简单的测试程序来评估控制有效性：测试、检查或访谈。虽然适用于美国政府机构，但可免费获取，任何组织都可改编使用。
**NIST 网络安全框架 (CSF)** 和 **FedRAMP 安全评估框架 (SAF)** 也可免费获取，可用于执行与 NIST SP 800-53A 中类似的评估方法进行评估。

## 抽样
在设计审计计划时，收集信息和获得保证的工作成本应与风险可见性的收益相平衡。抽样是审计中使用的技术，用于在保持识别缺陷的保证的同时减少工作量。例如，配置审计可能会从 1,000 台服务器的总体中选择 100 台以减少所需工作量。样本应具有代表性——如果组织在 Windows 和 Linux 之间平均分配，则应检查每种服务器类型各 50 台。

## 内部审计
内部审计由组织员工执行，提供审计员熟悉流程、工具和人员的好处。这种同样的熟悉程度也可能是内部审计的缺点，因为熟悉环境的人可能会无意中忽略问题——对问题进行第二双眼睛的检查通常能发现问题。然而，专门负责执行审计和管理补救的团队成员可能比交付报告后不再有进一步互动的外部审计员更有效。

内部审计员也可能缺乏进行客观评估的足够独立性。发现可能影响财务绩效或审计员与团队成员关系的重要问题可能会产生淡化发现问题的动机。在某些组织中，这可以通过将审计员设为公司内的独立团队来解决，但对于小型组织而言，这可能不是可行的选择。



内部审计在为外部审计做准备时通常很有用，可用于在外部审计前发现并纠正问题。在外部审计对业务有重大影响的情况下，例如 PCI 或其他监管审计，进行内部就绪评估或模拟审计是一种审慎的风险规避措施。内部审计可在组织的治理中发挥关键作用，因为它们向管理层提供报告，显示政策和其他治理措施的实施情况如何。

## 外部审计
外部审计由组织外部的人员执行，通常是监管合规审计的要求。外部审计师的关键优势是对被审计组织的完全独立——审计师完全投入于审计过程，不应存在忽视或压制发现的利益冲突。他们还可能具备执行审计所需的高专业技能，例如使用 SSAE 18 标准执行的 SOC 2 审计需要注册会计师（CPA）的技能；这可能不是大多数组织内部团队所具备的技能组合。

使用外部审计师有两个潜在缺点。首先是成本，对于大型和复杂的审计而言可能十分可观，可能涉及差旅、审计师计费工时以及与所聘审计公司的技能水平相匹配的服务费（通常声誉更高的公司收费更多）。对组织运营缺乏了解也可能是一个缺点，因为外部审计师必须花费比已熟悉情况的内部审计师更多的时间学习，或者外部审计师可能完全遗漏某个细节，例如具体的政策用语。这可能导致假阳性审计发现。

使用外部审计师在许多合规框架中是强制性的，例如 PCI、ISO 27001 以及 Cloud Security Alliance 安全信任保证与风险（CSA STAR）。独立的第三方有助于保证报告中的发现是可靠的，这对业务合作伙伴或客户等各方有利。某些行业和政府组织的监管机构可能拥有自己的审计师来评估其监管的组织。在这些情况下，促进这些外部审计必须成为 CISSP 的高度优先事项，因为大多数监管机构可以采取诸如罚款或因不合规而暂停业务运营等行动。

## 第三方审计
第三方审计是用于外部供应商、厂商和合作伙伴的重要风险管理工具。安全从业人员可能负责执行此类审计，也可能是外部方提供的审计报告的使用者。两者目标相同：识别可能影响贵组织的第三方任何风险，以及已实施的风险缓解措施。常见示例包括 SOC 2 和 CSA STAR 审计，这些审计通常明确出于与第三方共享组织安全计划细节的目的而进行。

对能够访问贵组织敏感数据的第三方的安全实践进行审计尤为关键。许多隐私和数据安全法律明确将数据泄露的法律责任归于数据控制者，即使数据处理者（如云服务）是泄露原因。这些审计可以识别提供商处实施的控制措施，以及这些缓解措施是否将风险降低到组织可接受的水平。

无论是使用 SOC 2 报告还是对第三方控制措施进行审计，安全从业人员都应寻求回答与安全计划相关的以下问题：
*   他们在选择控制措施和审计其有效性时使用什么标准？
*   共享了哪些细节？如果仅有有限信息可用，是否存在被隐藏的缺陷？
*   存在哪些发现，以及第三方对风险的回应是什么？
*   存在哪些计划来补救任何发现？

第三方风险评估可能由于现代供应链的复杂性而迅速变得复杂。在组织的托管服务提供商中运行的信息系统会继承来自第三方托管服务、用于运行系统的软件以及实物商品和服务供应商的风险。这些第三方的供应链中存在的风险也可能对组织构成风险，这是一种第四方关系。识别供应链中的供应商并确保审计和评估的充分覆盖在 第 1 章 中有更详细的讨论。

## 摘要
评估、审计、测试和评估都具有相似的目标，即识别安全控制计划中的问题。目标范围从低级别的项目（如单个硬件组件）一直到高级别的组织范围安全计划。从这些组件收集数据并将其与预期值进行比较，可为组织提供对其所实施的风险缓解控制措施有效性的洞察。这些评估可以使用内部资源或外部资源进行，也可由服务提供商、供应商和业务合作伙伴等第三方提供。

安全评估和测试在很大程度上依赖于收集和管理数据。组织流程如安全意识和 BCDR 应被检查以获取支持这些监督职能所需的数据，但数据本身不足以证明其价值，因此 CISSP 还应审查如何生成指标，即 KPI 和 KRI 的形式，以识别纠正或避免风险所需采取的行动。这些指标应与组织的战略、治理和合规需求相联系。
