# 第 17 章. 模型和二进制的大小优化

无论选择哪个平台，闪存存储和 RAM 都将非常有限。大多数嵌入式系统中的闪存只读存储小于 1MB，其中许多只有几十千字节。内存也是如此，很少有超过 512KB 的静态 RAM（SRAM）可用，在低端设备上这个数字可能在个位数。TensorFlow Lite for Microcontrollers 设计为仅使用 20KB 的闪存和 4KB 的 SRAM 运行，但需要仔细设计应用程序并进行工程权衡以保持占用率低。本章将介绍可用于监控和控制内存和存储需求的几种方法。

## 理解系统的限制

大多数嵌入式系统采用将程序和其他只读数据存储在闪存中，并在新可执行文件上传时才写入的架构。通常还提供使用 SRAM 技术的可变内存。这与大型 CPU 缓存中使用的技术相同，低功耗且访问速度快，但尺寸有限。更先进的微控制器可以提供第二层可变内存，使用动态 RAM（DRAM）等功耗较大但可扩展性强的技术。

需要了解潜在平台提供什么以及权衡是什么。例如，配备大量二级 DRAM 的芯片可能因其灵活性而具有吸引力，但如果启用该额外内存会导致电力预算超支，则可能没有价值。在本书关注的 1mW 以下的功率范围内使用运算符时，通常不可能使用 SRAM 之外的东西。也就是说，两个重要的指标是可用的只读闪存存储有多少，以及可用的 SRAM 有多少。这些数字应该列在您查看的芯片说明中。希望不必深入到数据表的「硬件选择」まで。

## 估算内存使用量

在对硬件选择有了想法后，需要加深对软件所需资源及其需求可控制的权衡的理解。

### Flash 使用

通常，闪存所需容量可以通过编译完整的可执行文件并查看生成的映像大小来准确判断。因为链接器最初生成的工件通常是执行文件的注释版本，如 ELF 格式，包含调试符号和段信息（这将在「代码大小的测量」で詳しく説明する）。您想看的是实际闪存到设备上的文件，通常由 `objcopy` 等工具生成。测量所需闪存内存量的最简单公式是以下各项的总和：

操作系统大小

: 

如果使用某种实时操作系统（RTOS），则需要在可执行文件中为其代码保留空间。估算占用率最简单的方法是构建启用所需功能的示例“hello world”程序。查看映像文件大小即可了解 OS 程序代码的大致基准值。占用程序空间较多的典型模块有 USB、WiFi、Bluetooth、移动无线堆栈等，因此如果使用它们，请确保已启用。

适用于微控制器的 TensorFlow Lite 代码大小

: 

ML 框架需要为加载和运行神经网络模型的程序逻辑提供空间，其中包括执行核心运算的运算符实现。本章后面将介绍如何为特定应用设置框架以减小尺寸，但入门时，只需编译包含框架的标准单元测试之一，例如[（`micro_speech` 测试的](https://oreil.ly/7cafy)这样的），并查看生成的映像大小进行估算即可。

模型数据大小

: 

如果尚未训练模型，可以通过计数权重来估算模型所需的闪存存储容量。例如，全连接层将具有输入向量大小乘以输出向量大小的权重。对于卷积层则更复杂，需要将滤波器框的宽度和高度乘以输入通道数，再乘以滤波器数。还需要为每个层相关的偏置向量添加存储空间。这很快就会变得复杂，因此在 TensorFlow 中创建候选模型并导出为 TensorFlow Lite 文件会更容易。该文件直接映射到 Flash，因此其大小可准确显示占用多少空间。也可以查看[Keras 的 `model.summary()` 方法](https://keras.io/models/about-keras-models)列出的权重数量。

### 注

量化在第 4 章中介绍，并在第 15 章中进一步详细说明，但从模型大小的角度重新确认一下是有价值的。在训练期间，权重通常以浮点值保存，每个占用 4 字节内存。由于移动设备和嵌入式设备空间受限，TensorFlow Lite 支持一种称为*量化*的过程，将这些值压缩为单个字节。它通过跟踪存储在 float 数组中的最小值和最大值，并将所有值线性转换为该范围内等间隔的 256 个值中最接近的一个来工作。这些代码各存储为 1 字节，可以以最小的精度损失执行算术运算。

应用程序代码大小

: 

需要代码来访问传感器数据、为神经网络预处理它并响应其结果。也可能需要除机器学习模块之外的用户界面或业务逻辑。估算这一点可能很困难，但至少需要了解是否需要外部库（例如快速傅里叶变换），并计算其代码空间需求。

### RAM 使用量

因为 RAM 使用量会随编程生命周期而变化。与估算闪存需求的过程类似，需要查看软件的各个层来估算整体使用需求：

操作系统大小

: 

大多数[RTOS（FreeRTOS 等）是](https://www.freertos.org/FAQMem.html)记录不同配置选项需要多少 RAM，您可以使用此信息来规划所需大小。需要特别注意需要缓冲的模块，尤其是 TCP/IP、WiFi、Bluetooth 等通信堆栈。这些需要添加到 OS 核心需求中。

适用于微控制器的 TensorFlow Lite RAM 大小

: 

ML 框架对核心运行时不需要大量内存，因此不应在 SRAM 中为数据结构需要数千字节以上的空间。这些作为解释器使用的类的一部分分配，因此应用程序代码是将其创建为全局对象还是局部对象决定了它放在堆栈还是通用内存中。通常建议创建为全局对象或 `static` 对象。分配在堆栈上的局部对象可能在运行时导致崩溃，但空间不足通常会在链接时引发错误。

模型内存大小

: 

神经网络运行时，一个层的输出需要暂时保留以作为后续运算符的输入。这些激活层的寿命取决于图中的位置，每个所需的内存大小由层写入的数组形状控制。这些变化意味着需要花费时间计算计划，以便将所有临时缓冲区尽可能容纳在较小的内存区域中。目前，这是在模型首次由解释器加载时进行的，因此如果 arena 大小不足，控制台会显示错误。查看错误消息中显示的可用内存和所需内存之间的差异，并相应增加 arena 即可克服错误。

应用程序内存大小

: 

与程序大小一样，应用程序逻辑的内存使用量在创建前也难以计算。但是，可以对内存的大用户进行一定程度的猜测，例如存储输入样本数据所需的缓冲区，或库预处理所需的内存区域。

## 各种问题中模型精度和大小的近似值

为了规划在自己的应用中可能实现的内容，了解各种类型问题的技术现状是有帮助的。机器学习不是魔法，了解其局限性有助于在产品制作时做出明智的权衡。讨论设计过程的第 14 章是，开始培养直觉的好地方，但也需要考虑随着模型受到更严格的资源限制，精度如何下降。为此，这里介绍一些为嵌入式系统设计的架构示例。如果其中一个接近您需要的东西，它可以帮助您想象在模型创建过程的最后可以实现什么。当然，实际结果在很大程度上取决于特定产品或环境，因此请将其用作规划指南，不要指望能达到完全相同的性能。

### 语音唤醒词模型

先前作为代码示例提到的，使用 40 万次算术运算的小型（18KB）模型，在区分四类声音（静音、未知词、“是”、“否”）时，达到了 85% 的 top-1 精度（"建立指标 "参照）。这是一个训练评估指标，意味着向其呈现 1 秒的剪辑并要求模型对其输入进行一次性分类。实际上，模型通常用于流式音频，基于逐步推进的 1 秒窗口重复预测结果，因此实际应用中的精度会低于该数字所暗示的。一般来说，这种大小的音频模型应被视为更大级联处理的第一个阶段的守门员，其错误将由更复杂的模型容忍和处理。

经验法则是，要检测唤醒词以达到语音界面使用的足够精度，可能需要具有 300-400KB 权重和少于数千万次算术运算的模型。不幸的是，标记的语音数据的开放存储库仍然不足，因此学习可能还需要商业质量的数据集，但希望随着时间的推移这一限制也会缓解。

### 加速度传感器的预测性维护模型



预测性维护的问题多种多样，但其中最简单的案例之一是检测电机轴承的故障。它经常表现为一种特征性的晃动，可以作为加速度计数据的模式找到。用于发现此类模式的合理模型可能只需要数千个权重、10KB 以下的尺寸、仅数十万次算术运算。利用此类模型对这些事件进行分类，可以期望达到 95%以上的精度，并且可以想象将模型的复杂性扩展以处理更困难的问题（例如具有许多可动部件的机器或行驶中的机器的故障检测）。当然，参数和运算符的数量也会随之扩展。

## 人物检测

计算机视觉在嵌入式平台上并不是常见的任务，因此目前还不清楚哪些应用程序是合理的。我们经常听到的需求之一是检测附近是否有人员，并唤醒用户界面，或执行无法一直运行的耗电处理。我们曾在[在 Visual Wake Word Challenge 中](https://oreil.ly/E8GoU)尝试正式捕捉该问题的需求。其结果是，使用 250KB 的模型和约 6000 万次算术运算，小型（96×96 像素）单色图像的二值分类大约可以达到 90%的精度。这是使用（本书前面提到的）缩小版 MobileNet v2 架构时的基线，因此随着越来越多研究人员致力于这一专门化需求，精度有望提高，但可以大致估计在微控制器的内存占用范围内能解决多少视觉问题。人们可能会好奇这样的小模型在流行的 ImageNet-1,000 类别问题上会产生什么结果。由于针对 1,000 个类的最终全连接层会立即消耗超过 100 千字节（参数数量为嵌入输入乘以类计数），无法给出确切答案，但如果总大小约为 500KB，预计 Top-1 精度约为 50%。

## 模型的选择

关于模型和二进制大小的优化，强烈建议从现有模型开始。如第 14 章所述，最应投入的领域是数据收集和改进，而不是架构调整，从已知模型开始可以尽早集中于数据改进。由于嵌入式平台上的机器学习软件仍处于早期阶段，使用现有模型可以提高其操作系统在您关心的设备上得到支持并得到充分优化的可能性。本书附带的示例代码有望成为各种应用的良好起点——我们尽可能选择覆盖各种传感器输入的类型，但如果您的用例不匹配，您可能可以在网上搜索替代品。如果找不到针对合适大小优化的架构，您也可以在 TensorFlow 的训练环境中从零开始发现自己的架构，但如第 13 章和 第 19 章所述，将其成功移植到微控制器可能是一个复杂的过程。

## 减小执行文件大小

在微控制器应用程序中，模型很可能成为只读内存的最大消费者之一，但也必须考虑编译后的代码占用多少空间。针对嵌入式平台时，无法直接使用未经修改的 TensorFlow Lite 版本，这就是代码大小限制的原因。TensorFlow Lite for Microcontrollers 可以编译到最小 20KB，但在此情况下可能需要进行更改以排除应用程序不需要的代码部分。

### 测量代码大小

在开始代码大小优化之前，需要知道其大小有多大。因为构建过程的输出通常是包含调试和其他信息的文件，这些文件不会传输到嵌入式设备，因此不应计入总大小限制。在 Arm 或其他现代工具链中，无论后缀是否为`*.elf`，这通常被称为 ELF（Executable and Linking Format）文件。如果您使用 Linux 或 macOS 开发机，可以运行`file`命令来检查工具链的输出。它会显示文件是否为 ELF。

*这就是*实际上传到嵌入式设备闪存存储的代码的二进制快照。它通常与使用的只读闪存内存大小相同，因此可以用来理解实际使用量。您也可以在主机上使用`ls -l`或`dir`等命令行，或通过 GUI 文件查看器检查来发现大小。并非所有工具链都会自动显示此`bin`文件，有时后缀也可能不存在，但在 Mbed 中它是经 USB 下载到设备并拖拽的文件，而在 gcc 工具链中，可以通过运行类似`arm-none-eabi-objcopy app.elf app.bin -O binary`的命令来生成。查看`*.o`中间文件或构建过程生成的`*.a`库没有帮助，因为它们包含大量不会成为最终代码占用空间的元数据，并且代码的许多部分可能在未使用时被删除。

我们假设模型作为 C 数据数组编译到可执行文件中（因为无法依赖文件系统加载），因此包含模型的程序的二进制大小会包含模型数据。要理解实际代码占用多少空间，需要从二进制文件的长度中减去此模型大小。模型大小通常应在包含 C 数据数组的文件中定义（例如[`tiny_conv_micro_features_model_data.cc`的](https://oreil.ly/Vknl2)末尾），因此从二进制文件大小中减去它即可理解实际的代码占用。

### 面向微控制器的 TensorFlow Lite 需要多少空间？

了解整个应用程序的代码占用大小后，您可能想调查 TensorFlow Lite 占用了多少空间。测试的最简单方法是注释掉所有对框架的调用（包括创建`OpResolvers`和解释器等对象的操作），看看二进制文件缩小了多少。至少应该缩小 20～30KB，如果没有这种现象，请重新检查是否捕获了所有引用。链接器会删除所有未调用的代码并从占用中移除。这可以扩展到代码的其他模块，只要确认没有引用，就能更好地了解空间的去向。

### OpResolver

TensorFlow Lite 支持 100 多个运算符，但在单个模型中并不需要全部。每个运算符的单独实现可能只占用几千字节，但如果可用运算符数量多，总量会迅速膨胀。幸运的是，内置了删除不需要运算符代码占用的机制。

TensorFlow Lite 在加载模型时，使用[`OpResolver` 接口](https://oreil.ly/dfwOP)来查找每个 op 的实现。这是传递给解释器以加载模型的类，其中包含从 op 定义发现到 op 实现的函数指针的逻辑。该类存在的原因是为了能够控制实际链接的实现。大多数示例代码中创建并传递了[`AllOpsResolver` 类的](https://oreil.ly/tbzg6)实例。如第 5 章所述，它实现了`OpResolver`接口，并且正如其名称所示，包含 TensorFlow Lite for Microcontrollers 支持的所有运算符的条目。这意味着可以无需关心模型包含哪些运算符即可加载受支持的模型，因此在开始使用时很方便。

然而，一旦代码大小成为关注点，您可能想重新审视该类。与在应用程序主循环中传递`AllOpsResolver`实例不同，将`all_ops_resolver.cc`和`all_ops_resolver.h`文件复制到应用程序中，重命名为`my_app_resolver.cc`和`my_app_resolver.h`，并将类名更改为`MyAppResolver`。在类的构造函数中，删除所有应用于模型中未使用的操作的`AddBuiltin()`调用。遗憾的是，我们不知道如何轻松自动创建模型使用的运算符列表，但[Netron 的](https://oreil.ly/MKqF9)模型查看器是帮助该过程的绝佳工具。

请将传递给解释器的`AllOpsResolver`实例替换为`MyAppResolver`。这样，应用程序编译后，您会立即发现大小明显变小。这种更改的背景是，大多数链接器会尝试自动删除无法调用的代码（*死代码*）。通过删除`AllOpsResolver`中的引用，链接器可以判断不再列出的所有 op 实现可以被排除。

如果只使用少数几个 OPS，就不需要像大型`AllOpsResolver`那样用新类包装注册。相反，可以创建该类的实例并直接添加所需的运算符注册。只需创建`MicroMutableOpResolver`类的实例并将所需的运算符注册添加到目录中即可。`MicroMutableOpResolver`实现了`OpResolver`接口，但添加了可在列表中添加 op 的方法（这就是其名为`Mutable`的原因）。这是用于实现`AllOpsResolver`的类，也适用于作为自定义解析器类的基础，但直接调用它有时更简单。一些示例使用此方法，您可以在[`micro_speech` 示例的](https://oreil.ly/gdZts)片段中看到其工作原理：

```
  static tflite::MicroMutableOpResolver micro_mutable_op_resolver;
  micro_mutable_op_resolver.AddBuiltin(
      tflite::BuiltinOperator_DEPTHWISE_CONV_2D,
      tflite::ops::micro::Register_DEPTHWISE_CONV_2D());
  micro_mutable_op_resolver.AddBuiltin(
      tflite::BuiltinOperator_FULLY_CONNECTED,
      tflite::ops::micro::Register_FULLY_CONNECTED());
  micro_mutable_op_resolver.AddBuiltin(tflite::BuiltinOperator_SOFTMAX,
                                       tflite::ops::micro::Register_SOFTMAX());
```

您可能注意到解析器对象被声明为`static`。这是因为解释器可以随时调用此对象，其生命周期至少需要与为解释器创建的对象一样长。

## 框架常量

库代码中有一些地方为了避免动态内存分配而硬编码了数组的大小。如果 RAM 空间非常紧张，值得尝试是否可以为应用程序减小此大小（或者对于非常复杂的用例，可能需要增大）。其中一个数组是 [`TFLITE_REGISTRATIONS_MAX`](https://oreil.ly/hYTLi) 它控制可以注册多少个不同的运算符。默认值为 128，但对于大多数应用程序来说可能太多。特别是考虑到要创建 128 个 `TfLiteRegistration` 结构体数组，每个至少 32 字节，需要 4KB 的 RAM。此外，还可以关注像 [`kStackDataAllocatorSize`](https://oreil.ly/wIsPm) 这样的较少违规者，也可以尝试减小传递给解释器构造函数的 arena 大小。

## 真正的小型模型

本章的大部分建议与具有足够的余量使用 20 KB 代码占用空间的框架代码来运行机器学习的嵌入式系统有关，并且不试图在 10 KB 以下 RAM 中勉强运行。当资源限制非常严格的设备，例如只有几千字节 RAM 或闪存时，无法使用相同的方法。在这种环境中，需要编写自定义代码，并极其谨慎地手动调整一切以减小尺寸。

然而，我们希望 TensorFlow Lite for Microcontrollers 即使在这种情况下也能有所帮助。即使是小型模型，我们也建议使用 TensorFlow 训练模型，并使用导出工作流程创建 TensorFlow Lite 模型文件。这将成为提取权重的良好起点，并且可以使用现有的框架代码验证自定义版本的結果。所使用 op 的参考实现也应成为您自己的 op 代码的良好起点。即使不是为了延迟而优化，它也应该是可移植的、易于理解的并且内存效率高。

## 总结

本章我们看了一些减少嵌入式机器学习项目所需存储量的最佳技巧。这很可能是你必须克服的最困难的限制之一，但当你获得足够小、足够快、能耗不高的应用程序时，你就获得了出货产品的明确路径。剩下的就是根除导致设备出现意外行为的不可避免的妖精。调试可能是一个令人沮丧的过程（我听说过它被描述为一个杀人悬疑，你既是侦探、受害者，也是凶手），但它是为产品出货而必须学习的重要技能。第 18 章 将介绍有助于理解机器学习系统中发生了什么的基本技巧。
