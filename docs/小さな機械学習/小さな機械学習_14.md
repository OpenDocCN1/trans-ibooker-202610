# 第 15 章. 优化延迟

这部作品是用 AI 翻译的。欢迎提供意见和反馈：translation-feedback@oreilly.com

由于嵌入式系统计算能力不高，因此神经网络所需的集中计算可能比大多数其他平台花费更长时间。嵌入式系统通常实时处理传感器数据流，因此如果运行过慢可能会引起许多问题。例如，假设你想观察可能只出现短暂的东西（例如鸟出现在摄像头的视野中）。如果处理时间过长，传感器的采样可能太慢而错过此类现象。例如，在唤醒词检测示例中，对音频数据执行 1 秒窗口以检测唤醒词，但每次窗口仅推进 100 毫秒或更少，并对结果进行平均。在这种情况下，减少延迟可以提高整体准确性。此外，通过加快模型执行，可以降低设备的 CPU 频率，或在推理之间进入睡眠状态，从而减少整体能耗。

由于延迟是优化中非常重要的领域，本章将重点介绍可用于缩短模型执行时间的各种技术。

## 首先，确认它是否重要

神经网络代码在系统整体延迟中所占比例可能很小，因此加快它可能不会对产品性能产生很大差异。判断是否如此的最简单方法是注释掉应用程序代码中的调用。注释掉 [`tflite::MicroInterpreter::Invoke()`](https://oreil.ly/1dLTn) 的调用。这是一个包含所有推理计算的函数，会阻塞直到 Network+ 执行完成，因此通过删除它可以观察对整体延迟有何差异。在理想世界中，可以使用计时器日志语句或分析器来计算这种变化，但正如简单解释的那样，仅通过让 LED 闪烁并观察频率差异，也足以大致估计速度提升。如果执行网络推理与不执行之间的差异很小，优化代码的深度学习部分可能收获不大，应首先关注应用程序的其他部分。

## 硬件变更



如果需要加速神经网络代码，首先应该问的问题是是否可以使用更强大的硬件设备。对于许多嵌入式产品来说，硬件平台的选择往往在很早阶段就决定了或由外部设定，因此这可能是不可能的，但从软件角度来看这是最容易改变的因素，因此明确考虑其价值。如果有选择，通常最大的限制是能量、速度和成本。如果可能，通过更换使用的芯片来用能量和成本换取速度。在研究过程中，你可能会幸运地发现一个更快的新平台，而不会失去其他主要要素！

### 注
训练神经网络时，通常一次发送大量训练示例进行一次训练步骤。这样可以实现在一次只发送一个样本时不可能实现的许多计算优化。例如，一次训练调用中可能会发送 100 张图像及其标签。这种训练数据集的集合被称为*批*。

嵌入式系统通常需要实时处理一次一组传感器读数，因此不想在开始推理前等待收集更大的批。这 "单批 "关注意味着无法获得训练侧有意义的优化优势。因此，在云中很有用的硬件架构并不一定反映我们的用例。

# 模型的改进
硬件平台切换后，对神经网络延迟影响最大的往往是架构层面。如果能够在保持足够精度的同时创建计算量更少的全新模型，就可以在不更改任何代码的情况下加速推理。通常可以进行精度下降与速度提升的权衡，因此如果能从尽可能高精度的模型开始，这种权衡的余地就会更大。也就是说，即使是看起来毫不相关的任务，如延迟优化，花时间改善和扩展训练数据对整个开发过程也非常有益。

优化过程式代码时，通常把预算花在改变代码所基于的高级算法上，比用汇编重写内部循环更有效。关注模型架构也是基于同样的思路。与其提高工作速度，不如如果可能的话完全消除工作。与传统代码不同的是，用机器学习模型替换模型比在传统代码中替换算法要容易得多。收集到足够的数据集后，用学习脚本将模型换成另一个模型相对简单。也可以从正在使用的模型中删除单个层并观察其效果进行实验。神经网络倾向于非常优雅地退化，因此应该自由地尝试各种破坏性修改，并观察其对精度和延迟的影响。

## 估计模型的延迟
大多数神经网络模型花费的大部分时间都在执行大矩阵的乘法，或与其非常接近的等价操作。这是因为每个输入值必须以不同的权重缩放每个输出值，因此相关的工作量几乎与输入值的数量×网络各层的输出值的数量相同。这通常近似为网络一次推理执行所需的浮点运算次数，即 `FLOPs`。通常，乘加运算在机器代码层面通常为一条指令，被计为 2`FLOPs`，即使在执行 8 位以下量化运算时，浮点数已不再相关，也仍被称为 `FLOPs`。网络所需的 `FLOP` 数可以按层手工计算。例如，对于全连接层，需要输入向量大小乘以输出向量大小个数的 `FLOP`。因此，如果知道这些维度，就能把握相关的工作量。此外，在讨论和比较 [`MobileNet`的](https://arxiv.org/abs/1905.02244) 等模型架构的论文中，通常可以找到 `FLOP` 的估计值。

`FLOP` 作为网络执行所需时间的粗略度量是有用的，因为在其他条件相同的情况下，计算量少的模型会按 `FLOP` 差异成比例地更快执行。例如，需要 1 亿 `FLOP` 的模型会比需要 2 亿 `FLOP` 的模型快 2 倍。由于延迟还受软件针对特定分层架构优化程度等因素影响，实际上这并不完全正确，但作为评估不同网络架构的起点是很好的。也有助于建立对硬件平台的现实预期。如果你的芯片可以在 100ms 内运行 100 万 `FLOP` 的模型，那么可以推测需要 1,000 万 `FLOP` 的另一个模型的计算大约需要 1 秒。

## 如何加速模型
模型架构设计仍是一个活跃的研究领域，因此目前很难为初学者写出好的指南。最好的起点是发现一些以效率为出发点设计的现有模型，并反复进行修改实验。许多模型都有特定参数可以更改以影响所需计算量，例如 `MobileNet` 的深度方向通道系数或预期的输入大小。在其他情况下，可以查看各层所需的 `FLOP`，删除特别慢的层，或用更快的层替代，例如用深度方向卷积代替简单的卷积。如果可能，调查各层在设备上实际运行的延迟，而不是用 `FLOP` 估计，也很有价值。这需要本节后面介绍的代码优化中所述的分析技术。

### 注
模型架构设计困难且耗时，但最近已出现自动化进程，例如使用遗传算法等方法改进网络设计的[`MnasNet`的](https://arxiv.org/abs/1807.11626)做法。它们尚未完全取代人类（通常仍需要播种已知优秀的架构作为起点，或手工制定使用搜索空间的规则），但该领域将看到快速进展。

已经有像[`AutoML`的](https://cloud.google.com/automl/)这样的服务，用户可以避免训练的许多细节。希望这种趋势会持续下去。

# 量化
运行神经网络需要每次预测进行数十万、数百万次计算。执行此类复杂计算的大多数编程对数值精度非常敏感。否则误差会累积，产生使用起来过于不准确的结果。深度学习模型不同。即使中间计算的数值精度大幅下降，也能产生整体上准确的最终结果。这种特性似乎是学习过程的副产品，因为输入通常很大且充满噪声，模型学会对不重要的波动具有鲁棒性，并专注于重要模式。

这实际上意味着，使用 32 位浮点运算符操作运算符在大多数情况下精度高于推理所需的精度。训练稍微严格一些，因为需要对权重进行许多微小更改，但即便如此 16 位表示也被广泛使用。大多数推理应用只需用 8 位保存权重和激活值，就能产生与浮点等价无法区分的结果。考虑到许多平台对这些模型所依赖的 8 位乘法累加器指令提供强力支持，这对嵌入式应用来说是个好消息。

然而，将模型从浮点转换为 8 位并不容易。为了高效计算，需要将 8 位值线性转换为实数。对于权重来说很简单，因为可以从学习值知道各层的范围，从而推导出进行转换的正确缩放系数。但激活值则棘手。即使查看模型的参数或架构，也无法清楚知道各层输出的实际范围。选择范围过小会导致部分输出被裁剪到最小值或最大值，而范围过大则会降低输出精度，从而降低整体结果精度。

量化仍是活跃的研究主题，选择很多，因此 `TensorFlow` 团队在过去几年尝试了各种方法。其中一些实验可以在 ["Quantizing Deep Convolutional Networks for Efficient Inference "](https://arxiv.org/pdf/1806.08342.pdf) 中看到：[由 Raghuraman Krishnamoorthi 撰写的 "A Whitepaper "](https://arxiv.org/pdf/1806.08342.pdf) 和[量化规范中](https://oreil.ly/toF_E) 记载了基于我们经验目前使用的推荐方法。

量化过程被集中到将模型从 `TensorFlow` 训练环境转换为 `TensorFlow Lite` 图的过程。以前推荐过量化感知的训练方案，但使用起来很麻烦，我们发现通过使用一些额外技术可以在导出时获得等价结果。最容易使用的量化类型称为[训练后权重的量子](https://oreil.ly/Tz9D_)化。这会将权重量化为 8 位，但激活层保持浮点。这很有用，因为它可将模型文件大小缩小 75%，速度方面也有好处。由于不需要有关激活层范围的知识，因此是最简单的实现方法，但需要许多嵌入式平台上不存在的快速浮点硬件。

[训练后整数量化是](https://oreil.ly/LDw-y) 意味着可以在不进行浮点计算的情况下运行模型，这对于本书讨论的用例来说是首选方法。最困难的部分是需要在模型导出过程中提供输入示例，通过将典型的图像、音频和其他数据通过图传递，可以观察激活层的输出范围。正如前面解释的那样，如果不估计这些范围，就无法准确量化这些层。过去我们也使用过在训练期间记录范围或在运行时每次推理捕获范围等其他方法，但这些方法存在训练变得非常复杂或产生延迟惩罚等缺点。

回顾第 10 章的人物检测模型的导出步骤，可以看到向 `converter` 对象提供了 `representative_dataset` 函数。这是一个生成激活范围估计处理所需输入的 Python 函数，对于人物检测模型，它从训练数据集中读取一些样本图像。因为预期输入因应用而异。此外，由于难以确定预处理过程中输入如何缩放和转换，因此创建函数需要反复试验。未来我们希望使此过程更简单。

在几乎所有平台上运行完全量化的模型都有很大的延迟优势，但在支持新设备时，可能需要优化最计算密集的运算以利用硬件提供的专用指令。处理卷积网络时，从[`Conv2D` 的运算](https://oreil.ly/NrjSo)子开始和[从内核](https://oreil.ly/V27Q-)是个好主意。你会注意到许多内核都有 `uint8` 和 `int8` 版本。`uint8` 版本是量化旧方法的遗留物，目前已不再使用。所有模型都必须使用 `int8` 路径导出。

# 产品设计
也许你不会把产品设计当作优化延迟的方法，但实际上它是投资回报最佳的地方之一。关键在于判断是否可以放宽网络对速度和精度中的任一方面的要求。例如，你可能想用摄像头每秒追踪数帧手势，但如果身体姿势检测模型执行需要 1 秒，就可以用更快的光学跟踪算法更快地追踪已识别点，并在更准确但频率较低的神经网络结果可用时更新它。另一个例子是，让微控制器将高级语音识别委托给通过网络访问云 API，同时保持唤醒词检测在本地设备上运行。在更广的层面上，通过在用户界面中加入不确定性，可以放宽网络的精度要求。语音识别系统中选择的唤醒词倾向于短语，包含在普通语音中很少出现的音节序列。如果有手势系统，可以要求用户在每个序列末尾竖起大拇指，以确认命令是有意的。

目标是尽可能提供整体最佳的用户体验。因此，如果系统其他部分可以容忍错误，就有更大的余地在准确性与速度或其他需要改进的特性之间进行权衡。

# 代码优化
由于延迟优化还有其他应先尝试的方法，本章将此主题放在相当靠后的位置，但传统代码优化是实现可接受性能的重要方法。特别是，`TensorFlow Lite for Microcontrollers` 的代码是为在尽可能小的二进制占用下在许多模型和系统上良好运行而编写的，因此可能存在仅适用于特定模型或平台的优化。更改硬件平台或所用模型架构会使许多此类更改不再适用。

## 性能分析
代码优化工作的基础是了解程序各部分的执行时间。在嵌入式世界中，这可能出奇地困难，因为默认情况下可能甚至无法使用简单的计时器，即使可以使用，记录和返回所需信息也很困难。这里介绍我们使用过的从最简单到最棘手的各种方法。

### 闪烁灯
几乎所有嵌入式开发板上至少有一个可通过编程控制的 LED。如果要测量约 0.5 秒以上的时间，可以在要测量的代码段开始时点亮该 LED，然后禁用它。用外部秒表手动计数 10 秒内闪烁的次数，就能估算出大致时间。也可以并排放置两个使用不同代码版本的开发板，通过比较闪烁频率来估计哪个更快。

### 霰弹式分析
在大致了解应用程序正常执行所需时间后，估计特定代码部分所需时间的 simplest 方法是注释掉该代码部分，查看整体执行速度提升多少。这被称为*以霰弹调试类比的霰弹分析*，类似于在信息很少时通过删除代码大块来定位崩溃。通常模型的执行代码没有数据依赖分支，因此注释掉内部实现使一个算子变为 no-op 也不会影响模型其他部分的速度，因此对神经网络调试非常有效。

### 调试日志
大多数情况下，嵌入式开发板应该能够向主机计算机输出文本行，这似乎是检测代码部分是否正在执行的理想方法。遗憾的是，与开发机器通信本身非常耗时。`Arm Cortex-M` 芯片的[串行线调试输出有](https://oreil.ly/SdsWk) 最多 500 毫秒的延迟，且延迟有许多变量，因此简单的日志分析方法无用。基于 `UART` 连接的调试日志通常成本更低，但仍不理想。

### 逻辑分析仪



与切换 LED 类似的方法，可以打开/关闭 `GPIO` 引脚，并使用外部逻辑分析仪（过去使用过 [Saleae Logic Pro 16](https://oreil.ly/pig8l)）来可视化并测量该时间。这需要一些布线，设备本身也昂贵，但它提供了一种非常灵活的方法来调查编程延迟，而无需超出一个或多个 `GPIO` 引脚控制的软件支持。

## 计时器

如果有一个计时器能够以足够的精度一致地获取当前时间，则可以记录感兴趣的代码段的开始和结束时间，并将其输出到不受通信延迟影响的日志中。出于这种原因，我们也考虑过为 TensorFlow Lite for Microcontrollers 配备平台无关的计时器接口，但由于计时器的设置可能变得复杂，因此判断移植到不同平台的负担会变大。然而，由于计时器的设置可能变得复杂，因此判断移植到不同平台的负担过大。不幸的是，这意味着你需要自己调查如何在运行的芯片上实现此功能。此外，还有一个缺点，即需要在想要调查的代码周围添加计时器调用。因此，需要进行工作和规划来确定重要部分，同时在调查时间去向时反复重新编译和刷新。

## 分析器

如果运气好，你可以在支持某种外部分析工具的工具链或平台上工作。这类应用程序通常使用你的程序的调试信息，将其与在设备上运行你的程序时收集的执行统计信息进行对照。然后可以可视化哪个函数花费的时间最多，或者哪一行代码花费的时间最多。由于可以快速探索和放大重要函数，因此这是理解代码中速度瓶颈所在的最快方法。

# 操作优化

在确认使用尽可能简单的模型并确定代码的哪一部分花费时间最多后，需要考虑可以做些什么来加快它们的速度。考虑到每个层包含数十万到数百万次计算，神经网络的执行时间大部分应该花费在运算实现内部。

## 查找已优化的实现

TensorFlow Lite for Microcontrollers 中所有运算的默认实现都是为了小巧、易于理解和可移植而编写的，不快，因此预计可以用使用更多代码行和内存的方法相当容易地击败它们。我们准备了一套更快的实现集，使用了 第 13 章中描述的子文件夹 specialization 方法，位于 [`kernels/portable_optimized 目录中`](https://oreil.ly/fmY8R)。这些实现应该没有平台依赖，但可能使用比参考版本更多的内存。由于它们使用子文件夹 specialization，只需传递 `TAGS="portable_optimized"` 参数即可生成使用它们而不是默认的项目。

使用像 `CMSIS-NN` 这样的库等具有平台特定实现的设备，如果在指定目标时它们不会自动选择，则可以通过传递适当的标签来选择使用这些不可移植的版本。要发现它是什么，需要检查平台文档或 TensorFlow Lite for Microcontrollers 的源代码树。

## 自己编写优化实现

如果找不到最耗时算子的优化实现，或者可用实现不够快，你可能想自己编写。好消息是，你可以缩小范围来简化这项工作。因为只需要用一些不同的输入输出大小和参数调用算子，所以只需专注于加速这些路径，而不是泛化。例如，在 `SparkFun Edge` 板的语音唤醒词示例的第一个版本中，发现深度方向卷积参考代码占用了大部分时间，整体运行太慢而没有可用性。调查这段代码在做什么，发现卷积滤波器的宽度始终为 8[。](https://oreil.ly/Kbx22)通过使用 32 位整数并行获取以字节保存的 4 个输入值和 4 个权重，可以一次加载它们。

要开始优化过程，使用前面提到的子文件夹 specialization 方法，在 `カーネル・` 根目录内创建新目录。将参考内核的实现复制到该子文件夹，作为代码的起点。为了确认正确构建，运行与该 `op` 相关的单元测试并确认其通过：

```
make -f tensorflow/lite/micro/tools/make/Makefile test_depthwise_conv_\
  test TAGS="portable_optimized"
```

此时，我们建议在 `op` 的单元测试代码中添加一个新测试，而不是检查正确性，只报告运算执行所花费的时间。通过拥有这样的基准，可以验证你的更改是否按预期提高了性能。为每个在分析中发现速度瓶颈的场景准备基准，并需要将模型设置为与该时点操作具有相同大小或其他参数（不过，在大多数情况下，该数值不会影响执行延迟，因此权重和输入也可以是随机值）。基准代码本身需要依赖于本章前面提到的任何一种分析方法。理想情况下，使用高精度计时器测量持续时间，如果不能，则至少切换 LED 或逻辑输出。如果测量过程的粒度太大，可能需要在循环内多次执行算子并除以迭代次数来测量实际时间。创建基准后，记录更改前的延迟，并确认它与在应用程序分析中看到的几乎一致。

现在有了代表性基准，应该能够快速迭代优化的可能性。作为第一步，找到初始实现的内部最内层循环是好的。因为这是执行最频繁的代码段，所以改进这部分比算法的其他部分影响更大。幸运的是，你应该能够通过浏览代码并发现字面意义上最深嵌套的 `for` 循环（或等价物）来确定它，但通过将其注释掉并再次运行基准来确认适当的段落是有价值的。如果延迟急剧下降（最好超过 50%），则意味着你发现了应该关注的适当部分。例如，从 [深度方向卷积的参考实现](https://oreil.ly/8S4kS) 中取出这段代码：

```
    for (int b = 0; b < batches; ++b) {
      for (int out_y = 0; out_y < output_height; ++out_y) {
        for (int out_x = 0; out_x < output_width; ++out_x) {
          for (int ic = 0; ic < input_depth; ++ic) {
            for (int m = 0; m < depth_multiplier; m++) {
              const int oc = m + ic * depth_multiplier;
              const int in_x_origin = (out_x * stride_width) - pad_width;
              const int in_y_origin = (out_y * stride_height) - pad_height;
              int32 acc = 0;
              for (int filter_y = 0; filter_y < filter_height; ++filter_y) {
                for (int filter_x = 0; filter_x < filter_width; ++filter_x) {
                  const int in_x =
                      in_x_origin + dilation_width_factor * filter_x;
                  const int in_y =
                      in_y_origin + dilation_height_factor * filter_y;
                  // If the location is outside the bounds of the input image,
                  // use zero as a default value.
                  if ((in_x >= 0) && (in_x < input_width) && (in_y >= 0) &&
                      (in_y < input_height)) {
                    int32 input_val =
                        input_data[Offset(input_shape, b, in_y, in_x, ic)];
                    int32 filter_val = filter_data[Offset(
                        filter_shape, 0, filter_y, filter_x, oc)];
                    acc += (filter_val + filter_offset) *
                           (input_val + input_offset);
                  }
                }
              }
              if (bias_data) {
                acc += bias_data[oc];
              }
              acc = DepthwiseConvRound<output_rounding>(acc, output_multiplier,
                                                        output_shift);
              acc += output_offset;
              acc = std::max(acc, output_activation_min);
              acc = std::min(acc, output_activation_max);
              output_data[Offset(output_shape, b, out_y, out_x, oc)] =
                  static_cast<uint8>(acc);
            }
          }
        }
      }
    }
```

由于这段代码位于所有循环的中间，因此执行次数比函数中的其他行多得多，通过注释掉可以确认它占用了大部分时间。如果有行级分析信息的人幸运的话，这也有助于发现准确的段落。

既然发现了影响大的部分，目标就是将尽可能多的工作转移到外部、重要性较低的部分。例如，中间有一个 `if` 语句。这意味着必须对内层循环的每次迭代执行条件检查，但通过将该工作提升到该部分之外，可以大幅减少在外层循环中执行检查的频率。此外，你可能会注意到在特定模型或基准中存在不必要的条件或计算。在语音航迹模型中，扩展系数始终为 1，因此可以跳过包含该系数的乘法，从而节省更多工作。我们建议在顶层检查此类参数特定的优化，如果参数不是优化所需的，则回退到纯参考实现。这样可以实现已知模型的加速，并且即使存在不符合这些标准的运算，也至少能保证正确运行。为了避免错误地破坏正确性，经常运行 `op` 的单元测试是有价值的。

涵盖所有数值处理代码优化方法超出了本书范围，但查看 [`portable_optimized`](https://oreil.ly/tQkJm) 文件夹中的内核，可以看到一些有用的技巧。

## 利用硬件优势

到目前为止，只讨论了平台无关的可移植优化。这是由于为了完全避免工作而重构代码通常是最简单且影响最大的方法。此外，还可以简化并缩小更专门化优化的焦点。如果发现像具有 [`SIMD`指令](https://oreil.ly/MBxf5) 的 `Cortex-M` 设备这样的平台，通常对占神经网络推理时间大部分的迭代计算有很大帮助。你可能想使用内在函数或汇编来重写内部循环，但请忍住！至少检查厂商提供的库实现文档，确认是否已有适合实现算法大部分的内容。如果可能，不要编写自己的版本，而是尝试调用现有函数来计算快速傅里叶变换等通用内容。

经过这些阶段，是时候尝试平台的汇编级别了。我们推荐的方法是从用汇编的机械等价物替换单个代码行开始，这样一开始不必担心加速，同时进行验证正确性。一旦必要的代码转换完成，就可以尝试融合运算等技术来减少延迟。嵌入式系统的优点是行为往往比具有深指令流水线和缓存的复杂处理器更简单。

## 加速器和协处理器



随着机器学习工作负载在嵌入式领域变得越来越重要，提供专用硬件以加速它们或降低所需电力的系统也越来越多。然而，由于尚不存在明确的编程模型或标准 API，因此将它们与软件框架集成的方法并不总是明确的。`TensorFlow Lite for Microcontrollers`希望支持与主处理器同步运行的硬件的直接集成，但异步组件超出了当前项目的范围。

同步是指加速硬件与主 CPU 紧密耦合并共享内存空间，运算符实现可以非常快速地调用加速器并在结果返回前被阻塞。`TensorFlow Lite` 之上的线程层有可能在此阻塞期间将工作分配给另一个线程或进程，但在当前大多数嵌入式平台上似乎无法实现。从程序员的角度来看，这种加速器更类似于早期 x86 系统中存在的浮点协处理器，而非接近 GPU 的替代模型。我们关注这种同步加速器的原因在于，我们认为它最适合我们目标的低能耗系统，并且通过避免异步协作可以保持运行时更简单。

像协处理器一样的加速器要以这种低延迟响应，在系统架构上必须位于 CPU 非常接近的位置。相反的模型是最新 GPU 中使用的模型，它是一个完全独立的系统，具有位于总线另一侧的自己的控制逻辑。这种处理器的编程中，CPU 会将需要相对较长时间执行的大量命令列表排队，并在批处理准备好后发送，但不会等待加速器完成就立即继续其他工作。在此模型中，CPU 与加速器之间的通信延迟可以忽略不计。因为命令发送并不频繁，也没有结果阻塞。通过一次查看许多命令，加速器可以获得更多机会来重新排序或优化相关工作，而这在任务需要更精细、按顺序执行时是困难的。因此加速器可以从这种方法中获益。图形渲染非常适合此方法，因为渲染结果不需要返回到 CPU，只需将渲染的显示缓冲区显示给用户即可。深度学习的训练通过发送大量训练样本以便一次完成大量工作，并尽可能在卡上保留以避免复制到 CPU 来进行适配。随着嵌入式系统变得更复杂并承担更大的工作负载，框架的需求可能会被重新审视，并可能使用类似移动 `TensorFlow Lite` 委托接口的东西来支持此流程，但这超出了此版本库的范围。

## 总结

本章介绍了为提高模型执行速度而需要了解的最重要的内容。最快的代码是不执行的代码。因此，重要的是要记住，在开始优化单个函数之前，先在模型和算法层面缩小你正在做的事情。在将应用程序部署到实际设备并测试其是否按预期工作之前，你可能需要解决延迟问题。之后，下一个优先事项是确保设备具有使其有用的寿命。
