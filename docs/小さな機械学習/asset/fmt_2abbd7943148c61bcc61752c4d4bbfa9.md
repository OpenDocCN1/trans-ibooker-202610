
```
TfLiteTensor* output = interpreter.output(0);
```

出力は入力と同じく、浮動小数点スカラー値で、2次元テンソルの中にある。テストのために、出力テンソルが期待通りのサイズ、次元、型を持っていることをダブルチェックする：

```
TF_LITE_MICRO_EXPECT_EQ(2, output->dims->size);
TF_LITE_MICRO_EXPECT_EQ(1, input->dims->data[0]);
TF_LITE_MICRO_EXPECT_EQ(1, input->dims->data[1]);
TF_LITE_MICRO_EXPECT_EQ(kTfLiteFloat32, output->type);
```

うん、すべて良さそうだ。では、出力値を取得し、それが我々の高い基準を満たしていることを確認する。まず、`float`変数に代入する：

```
// Obtain the output value from the tensor
float value = output->data.f[0];
```

推論が実行されるたびに、出力テンソルは新しい値で上書きされる。つまり、推論を実行し続けながらプログラミングの中で出力値を保持したい場合は、先ほどのように出力テンソルからコピーする必要がある。

次に、`TF_LITE_MICRO_EXPECT_NEAR`、その値が期待値に近いことを証明する：

```
// Check that the output value is within 0.05 of the expected value
TF_LITE_MICRO_EXPECT_NEAR(0., value, 0.05);
```

先に見たように、`TF_LITE_MICRO_EXPECT_NEAR`は、第1引数と第2引数の差が第3引数の値より小さいことを引数としている。このin文では、出力が0の0.05以内であることをテストしている。これは、入力である0の数学的正弦である。

### 注

正確な値ではなく、望んだ値に*近い*数値を期待する理由は2つある。1つ目は、我々のモデルは実際の正弦値を*近似して*いるだけなので、正確な値にはならないことがわかっている。もうひとつは、コンピュータの浮動小数点演算には誤差があるからだ。例えば、ノートPCのCPUはArduinoとはわずかに異なる結果を出すかもしれない。柔軟な期待値を持つことで、どのプラットフォームでもテストがパスする可能性が高くなる。

このテストがパスすれば、順調だ。残りのテストは、モデルが機能していることをさらに証明するために、推論をさらに数回実行する。推論をもう一度実行するために必要なことは、入力テンソルに新しい値を代入し、次のように呼び出すことだ。`interpreter.Invoke()`を呼び出し、出力テンソルから出力を読み取る：

```
// Run inference on several more values and confirm the expected outputs
input->data.f[0] = 1.;
interpreter.Invoke();
value = output->data.f[0];
TF_LITE_MICRO_EXPECT_NEAR(0.841, value, 0.05);

input->data.f[0] = 3.;
interpreter.Invoke();
value = output->data.f[0];
TF_LITE_MICRO_EXPECT_NEAR(0.141, value, 0.05);

input->data.f[0] = 5.;
interpreter.Invoke();
value = output->data.f[0];
TF_LITE_MICRO_EXPECT_NEAR(-0.959, value, 0.05);
```

同じ`input`と`output`のテンソル・ポインターを再利用していることに注意しよう。すでにポインタを持っているので、`interpreter.input(0)`や`interpreter.output(0)`を呼び出す必要はない。

この時点で、TensorFlow Lite for Microcontrollersがうまくモデルをロードし、適切な入力テンソルと出力テンソルを割り当て、推論を実行し、期待通りの結果を返すことが証明された。最後に、マクロを使ってテストの終わりを示す：

```
}

TF_LITE_MICRO_TESTS_END
```

これでテストの説明は終わった。次はテストを実行しよう！

## テストを実行する

このコードが最終的にマイクロコントローラー上で実行されることになっても、開発マシン上でテストをビルドして実行することができる。そのため、コードを書いたりデバッグしたりするのが非常に簡単になる。マイコンに比べ、パソコンにはログ出力やコードステップスルーのための便利なツールがある。さらに、デバイスにコードをデプロイするのは時間がかかるので、ローカルでコードを実行する方がずっと速い。

組み込みアプリケーション（あるいは、正直なところ、どんな種類のソフトウェアでも）を構築するための良いワークフローは、通常の開発マシンで実行できるテストをできるだけ多く使ってロジックを書くことだ。実行するために実際のハードウェアを必要とする部分は常にあるだろうが、ローカルでテストを実行できればできるほど、あなたの生活は楽になる。

現実的には、デバイス上で動作させる前に、入力を前処理し、モデルで推論を実行し、出力をテストセットで処理するコードを書いてみることを意味する。[第7章](#ch07.html#chapter_speech_wake_word_example)では、この例よりもはるかに複雑な音声認識アプリケーションについて説明する。各コンポーネントの詳細な単体テストがどのように書かれているかがわかるだろう。

### コードをつかむ

これまでColabとGitHubの間では、すべてをクラウド上で行ってきた。テストを実行するには、開発用のコンピューターにコードをプルダウンしてコンパイルする必要がある。

そのためには、以下のソフトウェア・ツールが必要だ：

* `Terminal`のようなターミナル・エミュレータ
* `bash`シェル
* [`Git`](https://git-scm.com/)
* `Make`, バージョン3.82以降

すべてのツールを入手したら、ターミナルを開き、以下のコマンドを入力して、TensorFlowのソースコードをダウンロードする。このコマンドを実行すると、ソースコードを含むディレクトリが作成される：

```
git clone https://github.com/tensorflow/tensorflow.git
```

次に、先ほど作成した`TensorFlow`ディレクトリに移動する：

```
cd tensorflow
```

これでコードを実行する準備が整った！

### Makeを使ってテストを実行する

ツールのリストで見たように、テストを実行するために`Make`というプログラミングを使っている。`Make`はソフトウェアのビルド作業を自動化するツールだ。1976年から使われており、コンピューター用語で言えば、ほとんど永遠に使われている。開発者は、`Makefile`と呼ばれるファイルに書かれた特殊化言語を使用して、`Make`にコードのビルドと実行を指示する。TensorFlow Lite for Microcontrollersには、[`micro/tools/make/Makefile`](https://oreil.ly/6Kvx5)に定義された`Makefile`がある。

`Make`を使ってテストを実行するには、`Git`でダウンロードした`TensorFlow`ディレクトリのルートから以下のコマンドを実行する。最初に使用する`Makefile`を指定し、その後にビルドするコンポーネントのターゲットを指定する：

```
make -f tensorflow/lite/micro/tools/make/Makefile test_hello_world_test
```

`Makefile`は、テストを実行するために、`test_`という接頭語の後にビルドしたいコンポーネントの名前をつけたターゲットを指定するようにセットアップされている。我々の場合、そのコンポーネントは`hello_world_test`なので、完全なターゲット名は`test_hello_world_test`。

このコマンドを実行してみよう。大量の出力が飛び交い始めるはずだ！まず、必要なライブラリーとツールがダウンロードされる。次に、すべての依存ファイルとともにテスト・ファイルがビルドされる。`Make`ファイルは、C++コンパイラーにコードをビルドしてバイナリーを作成し、それを実行するように指示している。

処理が完了するまでしばらく待つ必要がある。テキストのズームが止まると、最後の数行はこのようになるはずだ：

```
Testing LoadModelAndPerformInference
1/1 tests passed
~~~ALL TESTS PASSED~~~
```

ナイスだ！この出力は、テストが期待通りにパスしたことを示している。ソース・ファイルの一番上に定義されているテストの名前、`LoadModelAndPerformInference`が見える。まだマイクロコントローラー上にないとしても、我々のコードは推論を正常に実行している。

テストが失敗したときに何が起こるかを見るために、エラーを導入してみよう。テストファイル`hello_world_test.cc`を開く。ディレクトリのルートからの相対パスで、このパスにあるはずだ：

```
tensorflow/lite/micro/examples/hello_world/hello_world_test.cc
```

テストを失敗させるために、モデルに別の入力を与えてみよう。これによってモデルの出力が変わるので、出力の値をチェックするアサーションは失敗する。次の行を発見する：

```
input->data.f[0] = 0.;
```

代入値を次のように変更する：

```
input->data.f[0] = 1.;
```

ファイルを保存し、以下のコマンドでテストを再度実行する（`TensorFlow`ディレクトリのルートから実行することを忘れずに）：

```
make -f tensorflow/lite/micro/tools/make/Makefile test_hello_world_test
```

コードが再構築され、テストが実行される。最終的な出力はこのようになるはずだ：

```
Testing LoadModelAndPerformInference
0.0486171 near value failed at tensorflow/lite/micro/examples/hello_world/\
  hello_world_test.cc:94
0/1 tests passed
~~~SOME TESTS FAILED~~~
```

この出力には、テストが失敗したファイルや行番号など、失敗した原因に関する有益な情報が含まれている（`hello_world_test.cc:94`）。もしこれが実際のバグに起因するものであれば、この出力は問題の追跡に役立つだろう。

# プロジェクトファイルの構造

テストを実行することで、TensorFlow Lite for Microcontrollersライブラリを使用してC++で推論を実行する方法を学んだ。次は、実際のアプリケーションのソースコードを見ていこう。

前述したように、我々が構築しているプログラミングは、`x`の値をモデルに入力し、推論を実行し、その結果をプラットフォームに応じて何らかの目に見える出力（LEDの点滅パターンなど）を生成するための連続ループで構成されている。

このアプリケーションは複雑で、複数のファイルにまたがっているため、その構造とすべてがどのように組み合わされているかを見てみよう。

アプリケーションのルートは`tensorflow/lite/micro/examples/hello_world`にある。以下のファイルがコンテナになっている：

ビルド

: 

このファイルには、アプリケーションのソースコードを使ってビルドできる様々なものがリストアップされている。この時点ではあまり気にする必要はない。

`Makefile.inc`

: 

先ほど実行したテストである`hello_world_test`や、メインのアプリケーションバイナリである`hello_world`など、アプリケーション内のビルドターゲットに関する情報を含む`Makefile`である。どのソースファイルがそれらの一部であるかを定義している。

`README.md`

: 

アプリケーションのビルドと実行に関する説明を含むReadmeファイル。

`constants.h`、`constants.cc`

: 

プログラムの振る舞いを定義するのに重要な、さまざまな定数（プログラムの存続期間中は変化しない変数）を含むファイルのペア。

`create_sine_model.ipynb`を作成する。

: 

前章で使用したJupyterノートブック。

`hello_world_test.cc`

: 

我々のモデルを使って推論を実行するテストを行う。

`main.cc`

: 

プログラムのエントリポイントで、アプリケーションがデバイスにデプロイされたときに最初に実行される。

`main_functions.h`、`main_functions.cc`

: 

`setup()`関数を定義したファイルのペア。この関数はプログラムに必要なすべての初期化を行う。`loop()`関数はプログラムのコア・ロジックを含み、ループ内で繰り返し呼び出されるように設計されている。これらの関数は、プログラム開始時に`main.cc`によって呼び出される。

`output_handler.h`、`output_handler.cc`

: 

推論が実行されるたびに出力を表示する関数を定義したファイル群。`output_handler.cc`のデフォルト実装は、結果をスクリーンに表示する。この実装をオーバーライドすることで、異なるデバイスで異なる動作をさせることができる。

`output_handler_test.cc`

: 

`output_handler.h`と`output_handler.cc`のコードが正しく動作していることを証明するテスト。

`sine_model_data.h`、`sine_model_data.cc`

: 

この章の最初の部分で`xxd`を使ってエクスポートされた、モデルを表すデータの配列を定義するファイルのペア。

* `Arduino/`
* `disco_f76ng/`
* `sparkfun_edge/`

マイクロコントローラー・プラットフォームによって機能やAPIが異なるため、プロジェクト構造では、アプリケーションがそのデバイス用にビルドされた場合にデフォルトの代わりに使用される、デバイス固有のバージョンのソース・ファイルを提供できるようにしている。例えば、`arduino`ディレクトリには`main.cc`、`constants.cc`、`output_handler.cc`のカスタム・バージョンがあり、Arduinoで動作するようにアプリケーションをカスタマイズしている。これらのカスタム実装については後で詳しく説明する。
