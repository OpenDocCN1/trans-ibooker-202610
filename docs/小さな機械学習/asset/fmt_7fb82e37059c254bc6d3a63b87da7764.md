
最初の引数には、データを書き込むメモリ上の場所へのポインタを渡す。変数 `g_audio_capture_buffer` は、オーディオ・キャプチャ・バッファが始まるメモリ上のアドレスへのポインタである。この場所に `capture_index` を追加することで、新しいデータを書き込むメモリ上の正しい場所を計算することができる。番目の引数は、どれだけのデータを読み取るかを定義するもので、ここでは最大値の `DEFAULT_PDM_BUFFER_SIZE` 。

最後に、`g_latest_audio_timestamp` を更新する：

```
 // This is how we let the outside world know that new audio data has arrived.
 g_latest_audio_timestamp = time_in_ms;
```

これは `LatestAudioTimestamp()` メソッドを通じてプログラミングの他の部分に公開され、新しいデータが利用可能になったことを知らせる。なぜなら `g_latest_audio_timestamp` が `volatile` として宣言されているため、その値はアクセスされるたびにメモリから検索される。これは重要なことで、そうしないと変数がプロセッサにキャッシュされてしまうからである。その値はコールバックでセットされるため、プロセッサはキャッシュされた値をリフレッシュすることを知らず、その変数にアクセスするコードは現在の値を受け取ることができない。

`CaptureSamples()` がコールバック関数として動作するのはなぜなのか、不思議に思うかもしれない。新しいオーディオが利用可能になったことをどうやって知るのだろうか？オーディオ・キャプチャを開始する関数である：

```
TfLiteStatus InitAudioRecording(tflite::ErrorReporter* error_reporter) {
  // Hook up the callback that will be called with each sample
  PDM.onReceive(CaptureSamples);
  // Start listening for audio: MONO @ 16KHz with gain at 20
  PDM.begin(1, kAudioSampleFrequency);
  PDM.setGain(20);
  // Block until we have our first audio sample
  while (!g_latest_audio_timestamp) {
  }

  return kTfLiteOk;
}
```

この関数は、誰かが最初に `GetAudioSamples()` を呼び出したときに呼び出される。まず、`PDM` ライブラリを使用して、`PDM.onReceive()` を呼び出し、`CaptureSamples()` コールバックをフックアップする。次に、`PDM.begin()` が2つの引数とともに呼び出される。最初の引数は、録音する音声のチャンネル数を示す。モノラル音声だけが欲しいので、`1` を指定する。2番目の引数は、1秒間に受信したいサンプル数を指定する。

次に、`PDM.setGain()` 、マイクの音声をどれだけ増幅するかを定義する*ゲインを*設定する。`20` のゲインを指定するが、これはいくつかの実験の後に選ばれたものである。

最後に、`g_latest_audio_timestamp` が真と評価されるまでループする。`g_latest_audio_timestamp` は、`0` から始まるので、コールバックによってオーディオがキャプチャされるまで、実行をブロックする効果がある。

先ほど説明した2つの関数は、オーディオのキャプチャプロセスを開始し、キャプチャしたオーディオをバッファーに格納する。次の関数、`GetAudioSamples()` は、コードの他の部分（つまり、フィーチャー・プロバイダー）がオーディオ・データを取得するためのメカニズムを提供する：

```
TfLiteStatus GetAudioSamples(tflite::ErrorReporter* error_reporter,
                             int start_ms, int duration_ms,
                             int* audio_samples_size, int16_t** audio_samples) {
  // Set everything up to start receiving audio
  if (!g_is_audio_initialized) {
    TfLiteStatus init_status = InitAudioRecording(error_reporter);
    if (init_status != kTfLiteOk) {
      return init_status;
    }
    g_is_audio_initialized = true;
  }
```

この関数は、ログを書き込むための `ErrorReporter` 、要求しているオーディオを指定する2つの変数（ `start_ms` と `duration_ms` ）、オーディオデータを受け渡すための2つのポインタ（ `audio_samples_size` と `audio_samples` ）で呼び出される。関数の最初の部分では、`InitAudioRecording()` を呼び出している。先に見たように、これはオーディオの最初のサンプルが到着するまで実行をブロックする。変数 `g_is_audio_initialized` を使って、このセットアップコードが一度だけ実行されるようにしている。

この点以降は、キャプチャバッファにオーディオが保存されていると仮定できる。私たちの仕事は、正しいオーディオデータがバッファのどこにあるかを知ることである。これを行うには、まず、欲しい最初の*サンプルの全サンプルのヒストリ内の*インデックスを決定する：

```
const int start_offset = start_ms * (kAudioSampleFrequency / 1000);
```

次に、取得したいサンプルの合計数を決定する：

```
const int duration_sample_count =
    duration_ms * (kAudioSampleFrequency / 1000);
```

この情報を得たので、オーディオキャプチャバッファのどこで読み取りを行うかを考えることができる。データをループで読み取る：

```
for (int i = 0; i < duration_sample_count; ++i) {
  // For each sample, transform its index in the history of all samples into
  // its index in g_audio_capture_buffer
  const int capture_index = (start_offset + i) % kAudioCaptureBufferSize;
  // Write the sample to the output buffer
  g_audio_output_buffer[i] = g_audio_capture_buffer[capture_index];
}
```

先ほど、modulo 演算子を使って、最新のサンプルしか格納できないバッファ内の正しい位置を発見する方法を見た。*すべてのサンプルのヒストリ内の*現在のインデックスをオーディオキャプチャバッファのサイズ `kAudioCaptureBufferSize` で割ると、その余りがバッファ内のデータの位置を示す。次に、単純な代入を使って、データをキャプチャバッファから出力バッファに読み取ることができる。

次に、この関数からデータを取り出すために、引数として与えられた2つのポインタを使う。これらは、オーディオサンプル数を指す `audio_samples_size` と、出力バッファを指す `audio_samples` である：

```
  // Set pointers to provide access to the audio
  *audio_samples_size = kMaxAudioSampleSize;
  *audio_samples = g_audio_output_buffer;

  return kTfLiteOk;
}
```

`kTfLiteOk` 、呼び出し元に演算子が成功したことを知らせて関数を終了する。

そして最後に、`LatestAudioTimestamp()` を定義する：

```
int32_t LatestAudioTimestamp() { return g_latest_audio_timestamp; }
```

これは常に最新のオーディオのタイムスタンプを返すので、新しいオーディオデータが到着したかどうかを判断するために、コードの他の部分でループの中でチェックすることができる。

オーディオプロバイダーについては以上だ！これで、機能プロバイダーが新鮮なオーディオサンプルを安定して供給できるようになった。
