
予知保全の問題は多岐にわたるが、最も単純なケースのひとつは、モーターのベアリングの不具合を検出することだ。これは、加速度計データのパターンとして見つけることができる特徴的な揺れとして現れることが多い。このようなパターンを発見するための合理的なモデルは、わずか数千個の重み、10KB以下のサイズ、数十万回の算術演算子しか必要としないかもしれない。このようなモデルでこれらの事象を分類すれば、95％以上の精度が期待でき、より難しい問題（可動部の多いマシンや走行中のマシンの故障検出など）を扱うために、モデルの複雑さをスケールアップすることも想像できる。もちろん、パラメータや演算子の数もスケールアップするだろう。

## 人物検出

コンピュータ・ビジョンは、組み込みプラットフォームでは一般的なタスクではないため、どのようなアプリケーションが理にかなっているのか、まだわかっていない。我々がよく耳にする要望の1つは、人が近くにいることを検知し、ユーザ・インタフェースをウェイクアップさせたり、常時稼動させておくことができないような電力を消費する処理を行う機能である。我々は、[Visual Wake Word Challengeで](https://oreil.ly/E8GoU)この問題の要件を正式に捉えようとした。その結果、250KBのモデルと約6000万回の算術演算子を使えば、小さな（96×96ピクセル）モノクロ画像の2値分類でおよそ90％の精度が期待できることがわかった。これは、（本書で前述したように）縮小されたMobileNet v2アーキテクチャを使用した場合のベースラインであるため、この特殊化された要件に取り組む研究者が増えるにつれて精度が向上することを期待しているが、マイクロコントローラのメモリフットプリント内で視覚的な問題をどの程度解決できるかを大まかに見積もることができる。このような小さなモデルが、人気のあるImageNet-1,000カテゴリ問題でどのような結果を出すのか疑問に思うかもしれない。1,000クラスに対する最終的な完全連結層はすぐに100キロバイト以上（パラメータ数は埋め込み入力にクラスカウントを掛けたもの）を消費するため、正確なことは言えないが、合計500KB程度のサイズであれば、トップ1の精度は50％程度になると予想される。

## モデルの選択

モデルとバイナリーサイズの最適化に関しては、既存のモデルから始めることを強く推奨する。[第14](#ch14.html#designing_your_own_tinyml_applications)章で述べたように、最も投資すべき領域は、アーキテクチャの調整よりもデータの収集と改善であり、既知のモデルから始めることで、可能な限り早い段階でデータの改善に集中することができる。組込みプラットフォーム上の機械学習ソフトウェアもまだ初期段階にあるため、既存のモデルを使用することで、そのオペレーティングシステムが、あなたが気にかけているデバイス上でサポートされ、十分に最適化されている可能性が高まる。本書に付属しているコードサンプルが、様々なアプリケーションの良い出発点になることを期待している-できる限り様々な種類のセンサー入力をカバーするように選んだが、もしあなたのユースケースに合わない場合は、オンラインで代替品を検索できるかもしれない。適切なサイズに最適化されたアーキテクチャが見つからない場合は、TensorFlowの学習環境でゼロから独自のアーキテクチャを発見することもできるが、[第13章と](#ch13.html#chapter_tensorflow_lite_for_microcontrollers) [第19](#ch19.html#ch19)章で説明するように、マイクロコントローラにうまく移植するのは複雑なプロセスになる可能性がある。

## 実行ファイルのサイズを小さくする

マイクロコントローラ・アプリケーションでは、モデルは読み取り専用メモリの最大消費者の1つになる可能性が高いが、コンパイルされたコードがどれだけのスペースを取るかも考えなければならない。組み込みプラットフォームをターゲットにする場合、TensorFlow Liteの無修正バージョンをそのまま使うことができないのは、このコードサイズに対する制約があるからだ。TensorFlow Lite for Microcontrollersは、最小20KBまでコンパイルできるが、その場合、アプリケーションに不要なコード部分を除外するための変更が必要になることがある。

### 測定コード サイズ

コードサイズの最適化を始める前に、そのサイズがどれくらいかを知る必要がある。なぜなら、ビルドプロセスの出力は、デバッグやその他の情報を含むファイルであることが多く、組み込みデバイスに転送されないため、合計サイズの制限にカウントされないはずだからだ。Armや他の最新のツールチェーンでは、接尾辞が`*.elf`であろうとなかろうと、これはしばしばELF（Executable and Linking Format）ファイルとして知られている。LinuxやmacOSの開発マシンであれば、`file` コマンドを実行してツールチェーンの出力を調べることができる。ファイルがELFかどうかを表示してくれる。

*これは*、組み込みデバイスのフラッシュストレージに実際にアップロードされるコードのバイナリスナップショットである。これは通常、使用される読み取り専用フラッシュメモリのサイズと同じなので、実際の使用量を理解するために使うことができる。ホスト上で`ls -l` や`dir` のようなコマンドラインを使ったり、GUIのファイルビューアで検査することでもサイズを発見できる。すべてのツールチェーンが自動的にこの`bin`ファイルを表示するわけではないし、接尾辞がない場合もあるが、MbedではUSB経由でデバイスにダウンロードしてドラッグするファイルであり、gccツールチェーンでは、`arm-none-eabi-objcopy app.elf app.bin -O binary` のようなコマンドを実行してプロデューサを作成する。`*.o`中間ファイルや、ビルドプロセスが生成する`*.a`ライブラリを見ることは役に立たない。なぜなら、最終的なコードフットプリントにならないメタデータがたくさん含まれており、コードの多くが未使用のまま削除される可能性があるからだ。

私たちは、モデルをCデータ配列として実行ファイルにコンパイルすることを想定しているため（ファイルシステムからのロードに頼ることができないため）、モデルを含むプログラムのバイナリ・サイズにはモデル・データが含まれることになる。実際のコードがどれだけのスペースを取っているかを理解するには、バイナリファイルの長さからこのモデルサイズを減算する必要がある。モデル・サイズは通常、Cデータ配列を含むファイル（[`tiny_conv_micro_features_model_data.cc`の](https://oreil.ly/Vknl2)最後など）で定義されているはずなので、バイナリ・ファイル・サイズからそれを減算することで、実際のコード・フットプリントを理解することができる。

### マイコン向けTensorFlow Liteはどれくらいのスペースを取っているのか？

アプリケーション全体のコード・フットプリント・サイズがわかったら、TensorFlow Liteにどれだけのスペースを取られているかを調査したいかもしれない。これをテストする最も簡単な方法は、フレームワークへの呼び出し（`OpResolvers` やインタプリタなどのオブジェクトの生成を含む）をすべてコメントアウトして、バイナリがどれだけ小さくなるかを見ることだ。少なくとも20～30KBは小さくなるはずなので、もしそのような現象が見られない場合は、すべての参照をキャッチしたかどうか再確認してほしい。リンカは、呼び出しのないコードをすべて削除し、フットプリントから取り除くからだ。これはコードの他のモジュールにも拡張でき、参照がないことを確認すれば、スペースの行き先をよりよく理解することができる。

### OpResolver

TensorFlow Liteは100以上の演算子をサポートしているが、1つのモデル内でその全てが必要になることはまずないだろう。各演算子の個々の実装は数キロバイトしかとらないかもしれないが、利用可能な演算子の数が多ければ、合計はすぐに膨れ上がる。幸運なことに、必要のない演算子のコードフットプリントを削除するメカニズムが組み込まれている。

TensorFlow Liteがモデルをロードするとき、[`OpResolver` インタフェースを](https://oreil.ly/dfwOP)使用して、各opの実装を検索する。これは、モデルをロードするためにインタプリタに渡すクラスで、opの定義からopの実装への関数ポインタを発見するロジックが含まれている。このクラスが存在する理由は、実際にリンクされる実装を制御できるようにするためだ。サンプルコードの大部分では、[`AllOpsResolver` クラスの](https://oreil.ly/tbzg6)インスタンスを作成して渡している。[第5](#ch05.html#chapter_building_an_application)章で説明したように、これは`OpResolver` インタフェースを実装しており、その名前付けの通り、TensorFlow Lite for Microcontrollersでサポートされているすべての演算子のエントリを持っている。これは、どのモデルがどの演算子を含んでいるかを気にすることなく、サポートされているモデルをロードできることを意味するので、使い始めるのに便利である。

しかし、コード・サイズが気になる点が出てきたら、このクラスを見直したくなるだろう。アプリケーションのメインループで`AllOpsResolver` のインスタンスを渡す代わりに、`all_ops_resolver.cc`と`all_ops_resolver.h`ファイルをアプリケーションにコピーして、`my_app_resolver.cc`と`my_app_resolver.h`にリネームし、クラス名を`MyAppResolver` に変更する。クラスのコンストラクタ内で、モデル内で使用しないオペレーションに適用される`AddBuiltin()` 呼び出しをすべて削除する。残念ながら、モデルが使用する演算子のリストを簡単に自動作成する方法は知らないが、[Netronの](https://oreil.ly/MKqF9)モデル・ビューワはそのプロセスを手助けしてくれる素晴らしいツールだ。

インタプリタに渡していた`AllOpsResolver` インスタンスを`MyAppResolver` に置き換えてほしい。これで、アプリをコンパイルするとすぐに、サイズが明らかに小さくなっているのがわかるはずだ。この変更の背景には、ほとんどのリンカーが自動的に呼び出しできないコード（*デッドコード*）を削除しようとすることがある。`AllOpsResolver` にあった参照を削除することで、リンカは、もはやリストされていないすべてのop実装を除外できると判断できるようになる。

いくつかのOPSしか使わないのであれば、大規模な`AllOpsResolver` のように、登録を新しいクラスでラップする必要はない。代わりに、このクラスのインスタンスを作成し、必要なオペレーションの登録を直接追加することができる。 `MicroMutableOpResolver`クラスのインスタンスを作成し、必要なオペレーションの登録をディレクトリに追加すればよい。 `MicroMutableOpResolver`は`OpResolver` インタフェースを実装しているが、リストにオペを追加できるメソッドが追加されている（これが`Mutable` という名前付けの理由である）。これは、`AllOpsResolver` を実装するために使用されるクラスであり、独自のリゾルバークラスのベースとしても適しているが、これを直接呼び出す方が単純な場合もある。いくつかの例ではこの方法を使用しており、[`micro_speech` の例の](https://oreil.ly/gdZts)スニペットでその動作を見ることができる：

```
  static tflite::MicroMutableOpResolver micro_mutable_op_resolver;
  micro_mutable_op_resolver.AddBuiltin(
      tflite::BuiltinOperator_DEPTHWISE_CONV_2D,
      tflite::ops::micro::Register_DEPTHWISE_CONV_2D());
  micro_mutable_op_resolver.AddBuiltin(
      tflite::BuiltinOperator_FULLY_CONNECTED,
      tflite::ops::micro::Register_FULLY_CONNECTED());
  micro_mutable_op_resolver.AddBuiltin(tflite::BuiltinOperator_SOFTMAX,
                                       tflite::ops::micro::Register_SOFTMAX());
```

リゾルバー・オブジェクトを`static` と宣言していることにお気づきだろうか。これは、インタプリタがいつでもこのオブジェクトを呼び出すことができるためで、その寿命は、少なくともインタプリタ用に作成したオブジェクトと同じ長さである必要がある。

### 個々の関数の大きさを理解する

GCCツールチェーンを使用している場合、`nm` のようなツールを使って、オブジェクト（`*.o`）中間ファイルの関数やオブジェクトのサイズに関する情報を得ることができる。以下は、バイナリをビルドし、コンパイルされた`audio_provider.cc`オブジェクトファイルのアイテムのサイズを検査する例である：

```
nm -S tensorflow/lite/micro/tools/make/gen/ \
  sparkfun_edge_cortex-m4/obj/tensorflow/lite/micro/ \
  examples/micro_speech/sparkfun_edge/audio_provider.o
```
