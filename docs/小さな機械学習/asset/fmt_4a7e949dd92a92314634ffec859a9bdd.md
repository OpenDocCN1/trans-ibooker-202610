
# TensorFlow Lite FlatBuffers スキーマ解説

```
  if (model->version() != TFLITE_SCHEMA_VERSION) {
    error_reporter->Report(
        "Model provided is schema version %d not equal "
        "to supported version %d.\n",
        model->version(), TFLITE_SCHEMA_VERSION);
    return 1;
  }
```

[スキーマの`Model` 定義の冒頭を](https://oreil.ly/vPpDw)見れば、このコードが参照している`version` プロパティの定義がわかる：

```
  // Version of the schema.
  version:uint;
```

これは、`version` プロパティが32ビットの符号なし整数であることを知らせているので、`model->version()` に対して生成されるC++コードは、その型の値を返す。ここでは、バージョンが理解できるものであることを確認するためのエラーチェックを行っているだけだが、スキーマで定義されているすべてのプロパティに対して、同じ種類のアクセサ関数が生成される。

ファイル形式のより複雑な部分を理解するために、`MicroInterpreter` クラスがモデルをロードし、実行の準備をするまでの流れを追ってみる価値がある。コンストラクタには、前の例の`g_tiny_conv_micro_features_model_data` のような、メモリ上のモデルへのポインタが渡される。最初にアクセスするプロパティは[バッファ](https://oreil.ly/nQjwY)である：

```
  const flatbuffers::Vector<flatbuffers::Offset<Buffer>>* buffers =
      model->buffers();
```

型定義の`Vector` の名前を見て、標準テンプレート・ライブラリ（STL）型に似たオブジェクトを動的メモリ管理のない組み込み環境で使おうとしているのではないかと心配するかもしれない。しかし、幸いなことに、FlatBuffers`Vector` クラスは、基礎となるメモリの単なる読み取り専用ラッパーであるため、ルート`Model` オブジェクトと同様に、オブジェクトの作成に解析やメモリ確保は必要ない。

この`buffers` 配列が何を表しているのかをより理解するためには、[スキーマ定義を見て](https://oreil.ly/QOTlY)みる価値がある：

```
// Table of raw data buffers (used for constant tensors). Referenced by tensors
// by index. The generous alignment accommodates mmap-friendly data structures.
table Buffer {
  data:[ubyte] (force_align: 16);
}
```

各バッファは、符号なし8ビット値の生の配列として定義され、最初の値はメモリ上で16バイトにアライメントされる。これは、グラフに保持される重み（およびその他の定数値）のすべての配列に使用されるコンテナ型である。テンソルの型と形状は別々に保持される。この配列は、配列内のデータをバックアップする生のバイトを保持するだけである。演算子はこのトップレベル・ベクトル内のインデックスによってこれらの定数バッファを参照する。

次にアクセスするのは、[部分グラフのリスト](https://oreil.ly/9Fa9V)である：

```
  auto* subgraphs = model->subgraphs();
  if (subgraphs->size() != 1) {
    error_reporter->Report("Only 1 subgraph is currently supported.\n");
    initialization_status_ = kTfLiteError;
    return;
  }
  subgraph_ = (*subgraphs)[0];
```

サブグラフとは、演算子、演算子間の接続、演算子が使用するバッファ、入力、出力のセットである。将来的には、制御フローをサポートするために複数のサブグラフを必要とするような高度なモデルもあるだろうが、現時点でマイクロコントローラーでサポートしたいネットワークは、すべて単一のサブグラフを持つ。サブグラフの中身をもっと知るために、[スキーマを振り返って](https://oreil.ly/Z9mLn)みよう：

```
// The root type, defining a subgraph, which typically represents an entire
// model.
table SubGraph {
  // A list of all tensors used in this subgraph.
  tensors:[Tensor];

  // Indices of the tensors that are inputs into this subgraph. Note this is
  // the list of non-static tensors that feed into the subgraph for inference.
  inputs:[int];

  // Indices of the tensors that are outputs out of this subgraph. Note this is
  // the list of output tensors that are considered the product of the
  // subgraph's inference.
  outputs:[int];

  // All operators, in execution order.
  operators:[Operator];

  // Name of this subgraph (used for debugging).
  name:string;
}
```

すべてのサブグラフが持つ最初のプロパティはテンソルのリストであり、`MicroInterpreter` [：](https://oreil.ly/EsO7M)

```
  tensors_ = subgraph_->tensors();
```

先に述べたように、`Buffer` オブジェクトは、重みの生の値を保持するだけで、その型や形状に関するメタデータは一切ない。テンソルは、定数バッファのためにこの余分な情報が格納される場所である。また、入力、出力、活性化レイヤーのような一時的な配列についても、同じ情報が保持される。このメタデータは、[スキーマファイルの一番上にある](https://oreil.ly/mH0IL)定義で見ることができる：

```
table Tensor {
  // The tensor shape. The meaning of each entry is operator-specific but
  // builtin ops use: [batch size, height, width, number of channels] (That's
  // Tensorflow's NHWC).
  shape:[int];
  type:TensorType;
  // An index that refers to the buffers table at the root of the model. Or,
  // if there is no data buffer associated (i.e. intermediate results), then
  // this is 0 (which refers to an always existent empty buffer).
  //
  // The data_buffer itself is an opaque container, with the assumption that the
  // target device is little-endian. In addition, all builtin operators assume
  // the memory is ordered such that if `shape` is [4, 3, 2], then index
  // [i, j, k] maps to data_buffer[i*3*2 + j*2 + k].
  buffer:uint;
  name:string;  // For debugging and importing back into tensorflow.
  quantization:QuantizationParameters;  // Optional.

  is_variable:bool = false;
}
```

`shape` は、テンソルの次元を示す単純な整数リストであり、`type` は、TensorFlow Liteでサポートされる可能性のあるデータ型にマッピングされた列挙型である。`buffer` プロパティは、このテンソルがファイルから読み込まれた定数である場合は、ルートレベルのリストのどの`Buffer` が実際の値を持つかを示し、値が動的に計算される場合はゼロになる（例えば、活性化レイヤの場合）。`name` はテンソルに人間が読めるラベルを付けるためだけに存在し、デバッグに役立つ。`quantization` プロパティは、低精度の値を実数にマッピングする方法を定義している。最後に、`is_variable` メンバは、将来のトレーニングやその他の高度なアプリケーションをサポートするために存在するが、マイクロコントローラ・ユニット（MCU）で使用する必要はない。

`MicroInterpreter` のコードに戻ると、サブグラフから引き出す2番目の主要なプロパティは[演算子のリスト](https://oreil.ly/6Yl8d)である：

```
operators_ = subgraph_->operators();
```

このリストはモデルのグラフ構造を保持している。これがどのようにエンコーディングされているかを理解するために、 [`Operator` のスキーマ定義に戻って](https://oreil.ly/xTs7j)みよう：

```
// An operator takes tensors as inputs and outputs. The type of operation being
// performed is determined by an index into the list of valid OperatorCodes,
// while the specifics of each operations is configured using builtin_options
// or custom_options.
table Operator {
  // Index into the operator_codes array. Using an integer here avoids
  // complicate map lookups.
  opcode_index:uint;

  // Optional input and output tensors are indicated by -1.
  inputs:[int];
  outputs:[int];

  builtin_options:BuiltinOptions;
  custom_options:[ubyte];
  custom_options_format:CustomOptionsFormat;

  // A list of booleans indicating the input tensors which are being mutated by
  // this operator.(e.g. used by RNN and LSTM).
  // For example, if the "inputs" array refers to 5 tensors and the second and
  // fifth are mutable variables, then this list will contain
  // [false, true, false, false, true].
  //
  // If the list is empty, no variable is mutated in this operator.
  // The list either has the same length as `inputs`, or is empty.
  mutating_variable_inputs:[bool];
}
```

`opcode_index` メンバは、`Model` 内のルートレベル`operator_codes` ベクトルへのインデックスである。`Conv2D` のような特定の演算子は、1つのグラフに何度も現れる可能性があり、いくつかの演算子はそれらを定義するために文字列を必要とするため、すべての演算子定義を1つのトップレベル配列に保持し、サブグラフから間接的に参照することで、シリアライゼーションのサイズを節約することができる。

`inputs` 、`outputs` 配列は、グラフ内の演算子とその近傍の演算子との接続を定義する。これらは親サブグラフのテンソル配列を参照する整数リストであり、モデルから読み込まれる定数バッファ、アプリケーションからネットワークに入力される入力、他の演算子の実行結果、または計算終了後にアプリケーションによって読み込まれる出力先バッファを参照することができる。

サブグラフに保持されている演算子のリストについて知っておくべき重要なことの1つは、それらが常に位相的順序で並んでいるということである。つまり、配列の先頭から末尾に向かって演算子を実行すれば、ある演算子の入力のうち、前の演算子に依存するものは、その演算子に到達するまでにすべて計算されていることになる。実行ループは事前にグラフ演算をする必要がなく、リスト順に演算を実行すればよいので、インタプリタの記述が非常に簡単になる。しかし、TensorFlow Liteは推論に重点を置いているので、これはトレードオフとして価値がある。

また演算子は通常、`Conv2D` カーネルのフィルターの形状やストライドのようなパラメータを必要とする。これらの表現は残念ながらかなり複雑だ。歴史的な理由から、TensorFlow Liteは2つの異なる演算子をサポートしている。組み込み演算子が最初に登場し、モバイル・アプリケーションで最もよく使われる演算子だ。[スキーマで](https://oreil.ly/HjdHn)リストを見ることができる。2019年11月現在、122個しかないが、TensorFlowは800以上の演算子をサポートしている。カスタム演算子は、ビルトインのように固定された列挙型ではなく、文字列名で定義されるため、スキーマに触れることなく、より簡単に追加できる。

ビルトインOPSの場合、パラメータ構造はスキーマにリストされている。以下は`Conv2D` の例である：

```
table Conv2DOptions {
  padding:Padding;
  stride_w:int;
  stride_h:int;
  fused_activation_function:ActivationFunctionType;
  dilation_w_factor:int = 1;
  dilation_h_factor:int = 1;
}
```

願わくば、リストアップされたメンバーのほとんどが見覚えのあるものであってほしいが、それらは他のFlatBuffersオブジェクトと同じ方法でアクセスされる：各`Operator` オブジェクトの`builtin_options` ユニオンを通して、演算子コードに基づいて適切なタイプが選択される（ただし、そのためのコードは[モンスター`switch` ステートメントに基づいて](https://oreil.ly/SkzaA)いる[）](https://oreil.ly/SkzaA)。

演算子コードがカスタム演算子であることが判明した場合、前もってパラメータリストの構造を知っているわけではないので、コードオブジェクトを生成することはできない。その代わり、引数の情報は[FlexBufferに](https://oreil.ly/qPwo9)パッキングされる。これはFlatBufferライブラリが提供する形式で、事前に構造がわからない場合に任意のデータをエンコーディングするためのものだ。つまり、演算子を実装するコードは、結果として得られるデータに型が何であるかを指定してアクセスする必要があり、組み込みのものよりも面倒な構文になる。[オブジェクト検出コードの](https://oreil.ly/xQoTR)例を挙げよう：

```
  const flexbuffers::Map& m = flexbuffers::GetRoot(buffer_t, length).AsMap();
  op_data->max_detections = m["max_detections"].AsInt32();
```

この例で参照されているバッファ・ポインタは、最終的には `custom_options` `Operator` このプロパティからパラメータ・データにアクセスできることを示している。

`Operator` の最後のメンバーは`mutating_variable_inputs` である。これは、Long Short-Term Memory (LSTM)や、入力を変数として扱いたい他のオペレーションの管理を助けるための実験的な機能であり、ほとんどのMCUアプリケーションには関係ないはずである。
