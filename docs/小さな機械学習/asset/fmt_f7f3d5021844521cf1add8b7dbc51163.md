
# PDD

PDDの最初のセクションでは、どのようなデータを収集するのか、どのように収集するのか、なぜ収集するのかを説明する。できるだけ具体的に、わかりやすい英語を使うべきである。たとえば、"環境大気情報を得る "ではなく、"温度と湿度を収集する "といった具合である。このセクションに取り組んでいる間は、実際に何を収集するのかを考え、それが製品に最低限必要なものであることを確認する機会にもなる。より複雑なデバイスを目覚めさせるために大きな音を聞くだけなら、マイクを使って16KHzで音声をサンプリングする必要が本当にあるのか、あるいは、セキュリティ違反があっても音声を録音できないようにするためのより粗雑なセンサーを使うことができるのか。このセクションでは、製品内の異なるコンポーネント（クラウドAPIを含む）間の情報の流れを示す、シンプルなシステム図が役に立つ。このセクションの全体的なゴールは、技術者でない聴衆（それが弁護士であれ、経営陣であれ、取締役会メンバーであれ）に対して、何を収集するのかの優れた概要を提供することである。それを考える一つの方法は、新聞の一面で、無愛想なジャーナリストが書いた記事の中で、それがどのように見えるかを考えることである。他者による悪意ある行為にユーザがさらされるのを最小限に抑えるために、できることはすべてやっておくこと。具体的には、「このテクノロジーを使って、虐待する元パートナーが何をしでかすか」といったシナリオを考え、できる限り想像力を働かせて、提供できる限りの保護が組み込まれていることを確認しよう。

## データ使用量

データを収集した後はどうするのか？例えば、多くのスタートアップ企業はユーザデータを活用して機械学習モデルをトレーニングしたいと考えるが、これはプライバシーの観点から非常に危険なプロセスである。我々は、トレーニングデータの取得を全く別のプログラムとして扱い、製品使用の副作用としてデータを収集するのではなく、明確な同意を得た上で有料のプロバイダーを利用することを強く推奨する。

オンデバイス・マシンラーニングの利点のひとつは、機密データをローカルで処理し、集計結果のみを共有できることだ。例えば、毎秒画像をキャプチャする歩行者カウント・デバイスがあるかもしれないが、送信されるデータは目撃された人と車のカウントのみである。できることなら、これらの保証が破られないようにハードウェアを設計することだ。分類アルゴリズムへの入力として224×224ピクセルの画像しか使わないのであれば、顔やナンバープレートを認識することが物理的に不可能になるような低解像度のカメラセンサーを使う。歩行者カウントのように）数個の値だけをサマリーとして送信するつもりなら、デバイスがハッキングされてもソース映像を送信できないように、低ビットレートの無線技術だけをサポートする。将来的には、[特殊化ハードウェアが](https://oreil.ly/6E2Ya)これらの保証を強化するのに役立つことを期待しているが、現時点でも、過剰なエンジニアリングを避け、悪用をより困難にするために、システム設計レベルでできることはまだたくさんある。

## データの共有と保管

収集したデータにアクセスできるのは誰か？その人たちだけがデータを見ることができるように、どのようなシステムを導入しているか？データはどれくらいの期間、デバイス上またはクラウド上に保管されるのか？もしいつまでも保管するのであれば、それを削除する際のポリシーはどうなっているのか？メールアドレスや名前のような明らかなユーザIDを取り除いた情報を保存することは安全だと思うかもしれないが、IDはIPアドレス、認識可能な声、あるいは歩幅のような多くのソースから導き出される可能性があるため、収集したセンサーデータはすべて、個人識別可能情報（PII）であると考えるべきである。最善の方針は、この種のPIIを放射性廃棄物のように扱うことである。できる限り収集は避け、必要な間は厳重に保護し、収集が終わったらできるだけ早く処分する。

誰がアクセスできるかについて考えるとき、政府の圧力によってすべての許可システムが上書きされる可能性があり、抑圧的な国ではユーザに深刻な被害を与える可能性があることを忘れてはならない。その責任を回避し、ユーザの目に触れる機会を制限するために、送信や保存されるものを可能な限り最小限に制限するもう一つの理由がこれだ。

あなたの製品を使用している人々は、その製品がどのような情報を収集しているのかを理解しているだろうか？ここには、クリックスルーのエンドユーザ使用許諾契約書によって答えられると思うかもしれない狭い法的な疑問があるが、マーケティングの課題としてもっと広く考えることをお勧めする。おそらくあなたは、製品の利点が、より多くのデータを収集するトレードオフに値すると確信しているはずだ。もしそのようなメッセージを思いつくのに苦労しているのであれば、それはプライバシーへの影響を減らすか、製品の利点を増やすためにデザインを見直すべきサインである。

## PDDの使用

PDDは生きた文書として扱うべきで、製品の進化に合わせて常に更新される。PDDは、製品の詳細を弁護士やその他のビジネス利害関係者に伝えるために有用であることは明らかだが、それ以外にも多くの場面で役に立つ。インスタンスンスでは、マーケティング・チームと協力して、そのメッセージングがあなたのやっていることを確実に反映するようにすべきだし、（広告のような）サードパーティ・サービスのプロバイダと協力して、彼らがあなたの約束していることを遵守していることを確認する必要がある。実装レベルでしか見えない隠れたプライバシーの影響があるかもしれないので、チームのエンジニア全員がそれにアクセスし、コメントを追加できるようにすべきである。例えば、ジオコーディングのクラウドAPIを使っていて、デバイスのIPアドレスが漏れてしまうとか、マイクロコントローラーにWiFiチップが搭載されていて、使っていないが、理論的には機密データを送信できるようになっているかもしれない 。

# セキュリティ

組込み機器のセキュリティを合計で確保することは非常に難しい。攻撃者は簡単にシステムの物理的な所有権を得ることができ、そして情報を引き出すためにあらゆる種類の侵入テクニックを使うことができる。第一の防衛行は、組込みシステムに機密情報をできるだけ残さないようにすることであり、これが PDD が非常に重要な理由である。クラウドサービスとのセキュアな通信に依存しているのであれば、鍵が安全に保持されるように、[セキュアな暗号プロセッサの](https://oreil.ly/lGLzA)調査を考えるべきである。これらのチップはセキュアブートにも使用でき、フラッシュしたプログラムだけがデバイス上で実行されるようにすることができる。

プライバシーと同様、攻撃者の機会を制限するようなハードウェア設計を心がけるべきだ。WiFiやBluetoothが不要なら、それらの機能を持たないデバイスを作る。出荷製品に[SWDのようなデバッグ・インタフェースを提供せず](https://oreil.ly/X1I7x)、[Armプラットフォームではコードの読み出しを無効にする](https://oreil.ly/ag5Vc)ことを検討する。これらの対策は[完璧ではないに](https://oreil.ly/R3YG-)せよ、攻撃のコストを引き上げることになる。

また、セキュリティや暗号化については、確立されたライブラリやサービスに頼るようにすべきである。なぜなら、見つけるのは難しいが、システムのセキュ リティを破壊するようなミスを犯しやすいからだ。組込みシステムのセキュリティの完全な課題については、本書の範囲を超えていますが、私たちがプライバシについて推奨しているものと同じようなセキュリティ設計書を作成することを考えるべきでしょう。あなたが考える攻撃の可能性、その影響、そして、それらに対してどのように防御するかを網羅する必要がある。

## モデルを守る

機械学習モデルの作成には多くの労力を要するが、デバイス上で出荷され、通常は理解しやすい形式になっているため、不誠実な競合他社から自分の機械学習モデルを保護することを懸念するエンジニアの声をよく耳にする。悪いニュースは、コピーに対する絶対的な保護はないということだ。この意味では、モデルは他のソフトウェアと同じで、通常のマシンコードと同じように盗まれたり調べられたりする可能性がある。しかし、ソフトウェアと同様、この問題は最初に考えるほど悪いものではない。手続き型プログラムを逆アセンブルしても真のソースコードがわからないように、量子化されたモデルを調べても、学習アルゴリズムやデータにアクセスすることはできない。また、競合他社のデバイスに搭載されたモデルの直接コピーを発見し、競合他社があなたの知的財産を盗んだことを法的に証明することは、他のソフトウェアと同様に非常に簡単なはずだ。

それでも、気軽な攻撃者があなたのモデルにアクセスしにくくすることは価値がある。簡単なテクニックは、シリアライゼーションしたモデルを秘密鍵とXORしてフラッシュに保存し、それをRAMにコピーして使用する前に暗号化を解除することだ。そうすれば、フラッシュをダンプするだけで、あなたのモデルにアクセスすることはできなくなるが、実行時にRAMにアクセスできる攻撃者は、そのモデルにアクセスすることができる。TensorFlow LiteのFlatBufferから独自形式に切り替えれば解決すると思うかもしれないが、ウェイトパラメータ自体は数値の大きな配列であり、どの演算子がどの順序で呼び出されるかはデバッガをステップ実行すれば一目瞭然であるため、この種の難読化の価値は非常に限定的であることがわかった。

### 注

モデルの不正流用を発見するための楽しいアプローチのひとつは、訓練プロセスの一部として微妙な欠陥を意図的に組み込み、違反の疑いをチェックする際にその欠陥に注意することである。例えば、ウェイクワード検出モデルを訓練して、"Hello "を聞き分けるだけでなく、密かに "Ahoy, sailor!"も聞き分けるようにする。独立して訓練されたモデルが、同じフレーズに対してレスポンスを示す可能性は極めて低い。このテクニックは、地図、ディレクトリ、辞書などの参考文献に、著作権侵害を発見しやすくするために架空のエントリを含めるという古い考えに基づいている。これは、コピーを識別しやすくするために[架空の山](https://oreil.ly/OpY2G)「Mountweazel」を地図に配置する習慣にちなんで、*mountweazelingとして*知られるようになった。

# デプロイ

最近のマイクロコントローラーでは、OTA（Over-the-Air）アップデートを有効にすることで、デバイス上で実行されているコードをいつでも、たとえ出荷後であっても修正できるようにすることは非常に魅力的だ。これは、セキュリティとプライバシー侵害のための広い攻撃面を開くので、我々は、それがあなたの製品に本当に不可欠であるかどうかを検討することを強く勧める。よく設計されたセキュアなブートシステムやその他の保護なしに、あなただけが新しいコードをアップロードできるようにするのは難しい。デフォルトとして、デバイスが製造された後は、いかなる種類のコード更新も許可しないことを推奨する。これは、例えばセキュリティホールを修正するアップデートができなくなることを考えると、強引に聞こえるかもしれないが、ほとんどすべての場合において、攻撃者のコードがシステム上で実行される可能性を排除することは、セキュリティにとって害になるどころか、はるかに助けになる。また、アップデートを "リッスン "するプロトコルが不要になるため、ネットワークアーキテクチャもシンプルになる。

これは、特にモデルの精度に関して、デバイスがリリースされる前にコードを正しくする負担が大きくなることを意味する。単体テストや、専用のテストセットに対する全体的なモデル精度の検証のようなアプローチについて先に話したが、それらですべての問題をキャッチできるわけではない。リリースの準備をする際には、ドッグフーディング・アプローチを使うことを強く推奨する。つまり、組織内部の人間の監督の下、実際の環境でデバイスを試すのだ。なぜなら、テストは作成者の想像力によって制限されるものであり、現実の世界は誰も事前に予測できないほど驚くべきものだからだ。良い知らせは、望ましくない振る舞いに遭遇した後、それをテストケースに変えることができ、通常の開発プロセスの一環として取り組むことができるということだ。実際、このようなテストにコード化された、製品の深い要件に関する組織的記憶を開発することは、痛みを伴う試行錯誤によってしかそれを獲得する方法がない以上、最大の競争上の利点のひとつとなりうる。

## 開発ボードから製品へ

開発ボード上で動作するアプリケーションを出荷製品にする全プロセスは、本書の範囲を超えているが、開発プロセス中に考える価値のあることがいくつかある。例えば[Digi-Keyの](https://digikey.com)ようなサイトで、使用を検討しているマイクロコントローラのバルク価格を調査[し、](https://digikey.com)最終的にターゲットにしているシステムが予算に合うことを確認する必要がある。開発中に使用していたチップと同じであれば、量産デバイスにコードを移行するのはかなり簡単なはずである。したがって、プログラミングの観点からは、開発ボードが量産ターゲットと一致していることを確認することが主な必要条件となる。問題が発生した場合のデバッグは、コードが最終的なフォームファクターにデプロイされた後では、特に先に説明したステップを踏んでプラットフォームをセキュアにした場合、かなり難しくなるので、そのステップはできるだけ遅らせた方が良い。
