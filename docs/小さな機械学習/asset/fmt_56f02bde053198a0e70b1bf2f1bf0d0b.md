
これまでの章とは異なり、このアプリケーションを実行するにはいくつかのハードウェアが追加で必要になる。どちらのボードにもカメラが内蔵されていないため、カメラモジュールを購入することを推奨する。この情報は各デバイスのセクションで発見できる。

まずはアプリケーションの構造から見ていこう。思ったよりずっとシンプルだ。

# アプリケーションアーキテクチャ

ここまでで、組み込みマシン学習アプリケーションは以下のシーケンスを実行することがわかった：

1. 入力を得る。
2. モデルへの入力に適した特徴を抽出するために、入力を前処理する。
3. 処理された入力に対して推論を実行する。
4. モデルの出力を後処理して意味を持たせる。
5. その結果得られた情報を使って、物事を起こす。

[第7章](#ch07.html#chapter_speech_wake_word_example)では、これを音声を入力とするウェイクワード検出に応用した。今回は画像データを入力とする。より複雑に聞こえるかもしれないが、実際には音声よりもはるかに単純な作業だ。

画像データは一般的にピクセル値の配列として表現される。私たちは組み込みカメラモジュールから画像データを取得するが、それらはすべてこの形式でデータを提供する。我々のモデルも、入力がピクセル値の配列であることを想定している。このため、モデルにデータを入力する前に前処理をする必要はあまりない。

前処理をあまりする必要がないことを考えると、我々のアプリはかなり単純なものになるだろう。カメラからのデータのスナップショットを取り、それをモデルに入力し、どの出力クラスが検出されたかを判断する。そして、その結果を簡単な方法で表示する。

次に進む前に、今回使用するモデルについてもう少し学んでおこう。

## モデル紹介

[第7章](#ch07.html#chapter_speech_wake_word_example)で、畳み込みニューラルネットワークは多次元テンソルをうまく扱うように設計されたニューラルネットワークであり、隣接する値のグループ間の関係に情報が含まれていることを学んだ。特に画像データを扱うのに適している。

我々の人物検出モデルは、[Visual Wake Wordsデータセットで](https://oreil.ly/EC6nd)学習した畳み込みニューラルネットワークである。このデータセットは115,000枚の画像から構成されており、それぞれの画像に人物が含まれているかどうかがラベル付けされている。

このモデルは250KBで、我々の音声モデルよりかなり大きい。より多くのメモリを占有するだけでなく、この追加サイズは、1回の推論を実行するのに多くの時間がかかることを意味する。

このモデルは、96×96ピクセルのグレースケール画像を入力として受け付ける。各画像は形状`(96, 96, 1)` を持つ3次元テンソルとして提供され、最終次元には1つのピクセルを表す8ビットの値が含まれる。この値はピクセルのシェードを指定し、0（完全な黒）から255（完全な白）の範囲である。

カメラモジュールはさまざまな解像度の画像を返すので、96×96ピクセルにリサイズする必要がある。また、フルカラー画像をグレースケールに変換し、モデルで使えるようにする必要がある。

96×96ピクセルは小さな解像度と思われるかもしれないが、各画像から人物を検出するには十分すぎる解像度なのだ。画像を扱うモデルは、驚くほど小さな解像度を受け入れることが多い。モデルの入力サイズを大きくすればするほど、収穫は逓減し、入力サイズが大きくなればなるほど、ネットワークの複雑さは大幅に増大する。このため、最先端の画像分類モデルでさえ、最大320×320ピクセルで動作するのが一般的だ。

1つは入力に人がいる確率を示し、もう1つは誰もいない確率を示す。確率の範囲は0から255である。

我々の人物検出モデルは、`MobileNet`アーキテクチャを使用している。このアーキテクチャは、携帯電話のようなデバイスでの画像分類用に設計された、よく知られた、実績のあるアーキテクチャである。[第10章](#ch10.html#chapter_person_detection_training)では、このモデルがどのようにしてマイクロコントローラーに適合するようになったか、また、どのようにして独自のモデルをトレーニングできるかを学ぶ。とりあえず、我々のアプリケーションがどのように動作するかを探求し続けよう。

前述したように、画像データを直接モデルに渡すことができるため、前処理は必要ない。

物事をシンプルに保つもうひとつの側面は、モデルの出力を平均化しないことだ。私たちのウェイクワード・モデルは1秒間に複数回実行されるため、安定した結果を得るためには出力を平均化する必要があった。人物検出モデルはもっと大きく、推論を実行するのに時間がかかる。つまり、出力を平均化する必要はない。

コードには5つの主要部分がある：

メインループ

: 

他の例と同様、このアプリケーションは連続ループで実行される。しかし、我々のモデルははるかに大きく複雑であるため、推論を実行するのに時間がかかる。デバイスにもよるが、1秒間に数回の推論ではなく、数秒に1回の推論が期待できる。

イメージプロバイダー

: 

このコンポーネントはカメラから画像データをキャプチャし、入力テンソルに書き込む。画像をキャプチャするメソッドはデバイスによって異なるので、このコンポーネントをオーバーライドしてカスタマイズすることができる。

TensorFlow Liteインタプリタ

: 

インタプリタはTensorFlow Liteモデルを実行し、入力画像を確率のセットに変換する。

モデル

: 

モデルはデータ配列として含まれ、インタプリタによって実行される。このモデルは250KBと、TensorFlow GitHubリポジトリにコミットするには大きすぎる。そのため、プロジェクトのビルド時に`Makefile`によってダウンロードされる。ご覧になりたい方は、[`tf_lite_micro_person_data_grayscale.zip`から](https://oreil.ly/Ylq9m)ダウンロードできる。

検出レスポンダー

: 

検出レスポンダはモデルによって出力された確率を受け取り、それを表示するためにデバイスの出力機能を使用する。このレスポンダは、デバイスの種類に応じてオーバーライドすることができる。このコード例ではLEDを点灯させるが、これを拡張してほとんど何でもできるようにすることもできる。

これらのパーツがどのように組み合わされているかを知るために、それぞれのテストを見てみよう。

## 基本的な流れ

まずは`person_detection_test.cc`だ。まず、モデルが必要とするオペアを取り込むところから始める：

```
namespace tflite {
namespace ops {
namespace micro {
TfLiteRegistration* Register_DEPTHWISE_CONV_2D();
TfLiteRegistration* Register_CONV_2D();
TfLiteRegistration* Register_AVERAGE_POOL_2D();
}  // namespace micro
}  // namespace ops
}  // namespace tflite
```

次に、モデルに適したサイズのテンソルアリーナを定義する。例によって、この数値は試行錯誤で決定した：

```
const int tensor_arena_size = 70 * 1024;
uint8_t tensor_arena[tensor_arena_size];
```

次に、`MicroMutableOpResolver` を使って必要なopsを登録するなど、インタプリタを準備するための典型的なセットアップ作業を行う：

```
// Set up logging.
tflite::MicroErrorReporter micro_error_reporter;
tflite::ErrorReporter* error_reporter = &micro_error_reporter;

// Map the model into a usable data structure. This doesn't involve any
// copying or parsing, it's a very lightweight operation.
const tflite::Model* model = ::tflite::GetModel(g_person_detect_model_data);
if (model->version() != TFLITE_SCHEMA_VERSION) {
error_reporter->Report(
    "Model provided is schema version %d not equal "
    "to supported version %d.\n",
    model->version(), TFLITE_SCHEMA_VERSION);
}

// Pull in only the operation implementations we need.
tflite::MicroMutableOpResolver micro_mutable_op_resolver;
micro_mutable_op_resolver.AddBuiltin(
    tflite::BuiltinOperator_DEPTHWISE_CONV_2D,
    tflite::ops::micro::Register_DEPTHWISE_CONV_2D());
micro_mutable_op_resolver.AddBuiltin(tflite::BuiltinOperator_CONV_2D,
                                     tflite::ops::micro::Register_CONV_2D());
micro_mutable_op_resolver.AddBuiltin(
    tflite::BuiltinOperator_AVERAGE_POOL_2D,
    tflite::ops::micro::Register_AVERAGE_POOL_2D());

// Build an interpreter to run the model with.
tflite::MicroInterpreter interpreter(model, micro_mutable_op_resolver,
                                     tensor_arena, tensor_arena_size,
                                     error_reporter);
interpreter.AllocateTensors();
```

次のステップは入力テンソルを検査することである。入力テンソルが期待される次元数を持っているかどうか、そしてその次元が適切な大きさかどうかをチェックする：

```
// Get information about the memory area to use for the model's input.
TfLiteTensor* input = interpreter.input(0);

// Make sure the input has the properties we expect.
TF_LITE_MICRO_EXPECT_NE(nullptr, input);
TF_LITE_MICRO_EXPECT_EQ(4, input->dims->size);
TF_LITE_MICRO_EXPECT_EQ(1, input->dims->data[0]);
TF_LITE_MICRO_EXPECT_EQ(kNumRows, input->dims->data[1]);
TF_LITE_MICRO_EXPECT_EQ(kNumCols, input->dims->data[2]);
TF_LITE_MICRO_EXPECT_EQ(kNumChannels, input->dims->data[3]);
TF_LITE_MICRO_EXPECT_EQ(kTfLiteUInt8, input->type);
```

ここから、入力は厳密には5次元テンソルであることがわかる。最初の次元は1つの要素を含むラッパーに過ぎない。続く2つの次元は、画像のピクセルの行と列を表す。最後の次元は、各ピクセルを表現するのに使われる色チャンネルの数を保持する。

予想寸法を示す定数、`kNumRows`、`kNumCols`、`kNumChannels` は[`model_settings.h`で](https://oreil.ly/ae2OI)定義されている：

```
constexpr int kNumCols = 96;
constexpr int kNumRows = 96;
constexpr int kNumChannels = 1;
```

ご覧のように、このモデルは96×96ピクセルのビットマップを受け付ける。画像はグレースケールで、各ピクセルに1つのカラーチャンネルがある。

次に、`for` のループを使って、テスト画像を入力テンソルにコピーする：

```
// Copy an image with a person into the memory area used for the input.
const uint8_t* person_data = g_person_data;
for (int i = 0; i < input->bytes; ++i) {
    input->data.uint8[i] = person_data[i];
}
```

画像データをストアする変数、`g_person_data` は、`person_image_data.h`で定義されている。リポジトリにこれ以上大きなファイルを増やさないために、データ自体はテストを最初に実行するときに、`tf_lite_micro_person_data_grayscale.zip`の一部としてモデルとともにダウンロードされる。

入力テンソルに入力が終わったら、推論を実行する。これまでと同じようにシンプルだ：

```
// Run the model on this input and make sure it succeeds.
TfLiteStatus invoke_status = interpreter.Invoke();
if (invoke_status != kTfLiteOk) {
    error_reporter->Report("Invoke failed\n");
}
TF_LITE_MICRO_EXPECT_EQ(kTfLiteOk, invoke_status);
```

ここで出力テンソルをチェックして、それが期待通りのサイズと形状であることを確認する：

```
TfLiteTensor* output = interpreter.output(0);
TF_LITE_MICRO_EXPECT_EQ(4, output->dims->size);
TF_LITE_MICRO_EXPECT_EQ(1, output->dims->data[0]);
TF_LITE_MICRO_EXPECT_EQ(1, output->dims->data[1]);
TF_LITE_MICRO_EXPECT_EQ(1, output->dims->data[2]);
TF_LITE_MICRO_EXPECT_EQ(kCategoryCount, output->dims->data[3]);
TF_LITE_MICRO_EXPECT_EQ(kTfLiteUInt8, output->type);
```

モデルの出力には4つの次元がある。最初の3つは、4つめの次元のラッパーにすぎず、モデルがトレーニングされた各カテゴリの要素が1つずつ入っている。

カテゴリの合計数は、定数`kCategoryCount`、他の有用な値とともに`model_settings.h`にある：

```
constexpr int kCategoryCount = 3;
constexpr int kPersonIndex = 1;
constexpr int kNotAPersonIndex = 2;
extern const char* kCategoryLabels[kCategoryCount];
```
