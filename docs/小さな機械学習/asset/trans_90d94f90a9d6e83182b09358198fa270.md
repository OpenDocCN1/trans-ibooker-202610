
# 图像预处理

图像预处理不仅仅是重缩放的步骤。还有一个问题，即如何将通常以 0 到 255 编码的图像值转换为在训练时使用的浮点数。出于一些原因，这些值通常线性缩放为较小的范围，如 -1.0 到 1.0 或 0.0 到 1.0。如果输入浮点值，则应用程序也需要以相同的方式缩放值。如果直接输入 8 位值，则在运行时无需执行此操作。原始 8 位值可以不经转换直接使用，但需要通过 `--mean_values` 和 `--std_values` 标志传递给 `toco` 导出工具。如果范围是 -1.0 到 1.0，则为 `--mean_values=128 --std_values=128`。

因为这个细节经常被埋在使用的 API 的实现中。Google 公开的许多模型使用的 `Slim` 框架的默认值为 -1.0 到 1.0。

更糟糕的是，即使重缩放或值缩放稍有错误，也*几乎*可以得到正确的结果，但会降低精度。也就是说，你的应用程序在随意查看时似乎工作正常，但最终整体印象会变差。此外，与图像预处理相关的问题实际上比其他领域要简单得多，例如音频或加速度传感器数据，这些领域存在将原始数据转换为神经网络用数值数组的复杂特征生成管道。查看 [`micro_speech` 示例的前处理代码](https://oreil.ly/tedw1) 可知，为了从语音样本获得可输入模型的频谱图，必须实现多阶段的信号处理。如果此代码与训练时使用的版本之间存在差异，结果精度会下降。

## 调试预处理

这种输入数据的转换很容易出错，因此可能甚至难以察觉问题。怎么办？我们发现了一些方法。

即使外设被 stub 出来，也始终最好准备可在尽可能多的桌面机器上运行的代码版本。在 Linux、macOS、Windows 环境中可以使用更好的调试工具，并且在训练工具和应用程序之间传输测试数据也很简单。TensorFlow Lite for Microcontrollers 的示例代码将应用程序的各个部分拆分为模块，并启用了 Linux 和 macOS 目标的 `Makefile` 构建，以便可以单独运行推理阶段和预处理阶段。

调试预处理问题的最重要工具是训练环境和应用程序中看到的结果的比较。在此过程中最困难的是在训练期间提取感兴趣节点的正确值并控制其输入。详细说明这种方法超出了本书范围，但需要确定与核心神经网络阶段（文件解码后、预处理，以及接收预处理结果的第一个操作）相对应的操作名称。接收预处理结果的第一个操作对应于 `toco` 的参数 `--input_arrays`。如果能确定这些操作，则插入设置了操作的。[`tf.print`](https://oreil.ly/JYT_m)`summarize` `-1` 插入。执行训练循环时，可以在调试控制台中查看各阶段张量的内容打印。

然后，将这些张量的内容转换为 C 数据数组，以便可以编译到程序中。`micro_speech`，作为此示例，[有人说“是”的一秒语音样本和](https://oreil.ly/qFoMn)、[对其输入进行预处理时的预期结果](https://oreil.ly/uKYWo) 都有。获得这些基准值后，应该可以将它们作为输入发送到保持管道各阶段（预处理、神经网络推理）的模块，并确认输出与预期一致。如果时间紧迫，也可以用一次性代码来完成，但将其转变为即使代码随时间变化也能保证预处理和模型推理持续得到验证的[单元测试](https://oreil.ly/t2E03) 是值得的额外投资。

## 在设备上评估

训练结束时，神经网络使用输入测试集进行评估，预测与预期结果进行比较，以表征模型的整体精度。这作为训练过程的常规部分进行，但很少在部署到设备的代码中进行相同的评估。很多情况下，最大的障碍是将构成典型测试数据集的数千个输入样本传输到资源受限的嵌入式系统。然而，这很遗憾。确认设备上的精度与训练结束时看到的一致，是确认模型正确部署的唯一方法。`micro_speech` 演示的完整测试集评估无法实现，但至少有 [端到端测试](https://oreil.ly/4372z) 可以确认对两个不同输入获得正确的标签。

# 数值差异

神经网络是针对大量数组进行的复杂数学运算链。原始训练通常使用浮点数进行，但为了嵌入式应用程序，我们将其转换为低精度整数表示。运算符本身可以根据平台和优化权衡以各种方式实现。所有这些因素意味着，即使给定相同的输入，也不能期望不同设备上的网络产生逐位相同的结果。也就是说，必须决定允许多少差异，以及如果差异变得过大，如何追踪其来源。

## 差异是问题吗？

我们有时开玩笑说真正重要的指标只有应用商店的评分。我们的目标是打造用户满意的产品，而其他指标只是用户满意度的代理。由于与生产环境实验的数值差异始终存在，第一个挑战是理解它是否会损害产品体验。如果网络输出的值毫无意义，这很明显，但如果与预期值仅相差几个百分点，则值得作为具有现实用例的完整应用程序的一部分来尝试结果网络。精度下降可能不是问题，也可能有更重要、更优先的问题。

## 建立指标

如果确信存在真正的问题，将其量化会有所帮助。你可能想选择一个数值度量，例如输出分数向量与预期结果的差异百分比。然而，这可能无法很好地反映用户体验。例如，在进行图像分类时，即使所有分数都比预期低 5%，结果的相对顺序也不会改变。

相反，我们建议设计反映产品需求的指标。对于图像分类，可以选择称为*top1*分数的指标。`top-one` 指标是模型将其最高得分预测作为 ground truth 标签选择的频率*（`top-five`也*类似，但涵盖 ground truth 标签包含在 5 个最高得分预测中的频率）。然后使用 top1 指标跟踪进度，重要的是知道所做的更改何时变得足够。

此外，应注意组装反映实际输入到神经网络处理的标准输入集。正如前面提到的，预处理可能导致许多错误。

## 与基线比较

TensorFlow Lite for Microcontrollers 设计为具有所有功能的功能参考实现。这样做的原因之一是为了能够将优化代码和结果与之比较，以便调试潜在差异。如果有几个标准输入，请在框架的桌面构建中，在未启用优化的情况下，使参考运算符实现被调用来运行这些输入。如果需要这种独立测试的起点，请查看 [`micro_speech_test.cc`](https://oreil.ly/x5QYp)。使用设置的指标运行结果，应该会显示预期的分数。如果没有，则可能在转换过程中发生了某种错误，或者工作流程的早期阶段存在问题，因此需要返回训练进行调试以了解问题所在。

如果使用参考代码获得了良好的结果，则应在目标平台上构建并在启用所有优化的情况下运行相同的测试。当然，这可能并不那么简单。嵌入式设备通常没有足够的内存来保存所有输入数据，而且如果只有调试日志连接，输出结果会很麻烦。即使必须分多次运行测试，也值得坚持。获得结果后，将其通过指标传递，以了解实际的赤字是什么。

## 替换实现

许多平台默认启用优化。这是因为参考实现在嵌入式设备上运行可能非常耗时，实际上不可用。有很多方法可以禁用这些优化，但最简单的方法是找到当前使用的所有内核实现，通常在 [`TensorFlow/lite/micro/kernels`](https://oreil.ly/k3lln) 的子文件夹中，并用其父目录中的参考版本覆盖它们。作为第一步，用优化实现全部替换，然后在设备上重新运行测试。

在进行这种整体替换后，尝试仅覆盖一半的优化内核，看看它对指标有何影响。在大多数情况下，可以通过二进制搜索方法确定哪个优化内核实现导致了分数的最大下降。一旦缩小到特定的优化内核，就应该能够通过捕获*坏*运行的一个输入值以及参考实现对这些输入的预期输出值来创建最小的可重现案例。执行此操作最简单的方法是在测试运行时从内核实现内部进行调试日志记录。

有了可重现的案例后，应该可以从中创建单元测试。首先查看 [标准内核测试之一](https://oreil.ly/0rnPW)，创建新的独立测试或将其添加到该内核的现有文件中。这样就可以为负责优化实现的团队提供工具来传达问题。他们可以显示其代码与参考版本的结果存在差异，并且会影响应用程序。此外，还可以将相同的测试添加到主代码库中，以防止其他优化实现引起相同问题。这也是调试实现的绝佳工具，因为可以隔离代码进行实验并快速迭代。

# 神秘的崩溃和挂起

在嵌入式系统中，最难修复的情况之一是程序未运行，但没有明显的日志输出或错误来解释发生了什么。理解问题的最简单方法是附加（`GDB` 的ような）调试器，如果挂起则查看堆栈跟踪，或逐步执行代码以查看执行在哪里出错。但是设置调试器并不总是容易，而且即使使用调试器，问题的原因也可能不明确。

## 桌面调试

由于 Linux、macOS、Windows 等完整操作系统具有广泛的调试工具和错误报告机制，因此尽可能将程序移植到这些平台之一，即使通过用虚拟实现 stub 出硬件特定功能也是如此。TensorFlow Lite for Microcontrollers 就是这样设计的，可以首先在 Linux 机器上重现无法正常工作的情况。如果在此环境中出现相同的错误，通常使用标准工具跟踪会更快、更容易，并且无需刷新设备，从而提高迭代速度。即使维护整个应用程序的桌面构建过于困难，至少也应检查是否可以为可在桌面上编译的模块创建单元测试或集成测试。然后，给它们提供与你关注的情况相似的输入，看看是否会引发类似的错误。

## 日志跟踪

TensorFlow Lite for Microcontrollers 所需的唯一平台特定功能是 `DebugLog()` 的实现。之所以有此要求，是因为在开发过程中理解正在发生什么的工具是必不可少的。尽管部署平台不需要它。在理想世界中，崩溃或编程错误应触发日志输出。例如，STM32 设备的裸机支持具有执行此操作的[故障处理程序](https://oreil.ly/dsHG8)。

但是，你始终可以自己在代码中插入日志语句。它们不需要有意义，只需描述到达代码的哪个位置即可。这样也可以定义自动跟踪宏：

```
#define TRACE DebugLog(__FILE__ ":" __LINE__)
```

然后在代码中这样使用：

```
int main(int argc, char**argv) {
  TRACE;
  InitSomething();
  TRACE;
  while (true) {
    TRACE;
    DoSomething();
    TRACE;
  }
}
```

调试控制台应显示代码进展到何处的输出。通常最好从代码的最顶层开始，查看日志在何处停止。这样可以了解崩溃或挂起发生的粗略范围。然后可以添加 `TRACE` 语句来精确缩小问题发生的位置。

## 霰弹调试

有时跟踪无法提供足够的信息来了解出了什么问题，或者问题仅在无法访问日志的生产环境等环境中出现。在这种情况下，我们建议使用称为“霰弹调试”的方法。这与[第15](#ch15.html#optimizing_latency)章中描述的“霰弹分析”类似，只需注释掉代码的一部分，看看错误是否仍然发生。从应用程序的顶层开始向下工作，通常可以通过等效于二进制搜索的方法来隔离导致问题的行。例如，可以从主循环开始这样做：

```
int main(int argc, char**argv) {
  InitSomething();
  while (true) {
    // DoSomething();
  }
}
```

如果在注释掉 `DoSomething()` 的情况下正常运行，则问题出在该函数内部。接下来，取消注释该函数，并在其函数体内递归地执行相同操作，可以将焦点缩小到有问题的代码。

## 内存损坏

最痛苦的错误是由内存中的值被错误覆盖引起的。由于嵌入式系统不像桌面或移动 CPU 那样具有防止这种情况的硬件，因此调试尤其困难。即使跟踪或注释代码，也可能得到混乱的结果，因为覆盖可能发生在很久之前，而损坏的值才被使用，因此崩溃可能远离原因。崩溃也可能受传感器输入或硬件时序影响，间歇性且难以重现。
