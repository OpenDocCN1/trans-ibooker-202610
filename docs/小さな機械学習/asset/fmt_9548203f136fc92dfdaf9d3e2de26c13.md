## テストを通して歩く

アプリケーション・コードで手を汚す前に、テストを書いておくのは良い考えだ。テストとは、特定のロジックの一部を示す短いコードの断片のことである。動作するコードからできているので、テストを実行することで、そのコードが想定通りの動作をすることを証明することができる。テストを書いた後、プロジェクトがコードに変更を加えても期待通りに動いているかどうかを継続的に検証する方法として、テストを自動的に実行することがよくある。また、テストは物事の進め方の実例としても非常に役に立つ。

`hello_world`サンプルには、[`hello_world_test.cc`](https://oreil.ly/QW0SS)で定義されたテストがあり、モデルをロードし、それを使って推論を実行し、その予測が期待通りであることをチェックする。このテストには、これを実行するために必要な正確なコードがコンテナとして含まれており、他には何も含まれていない。従って、TensorFlow Lite for Microcontrollersの学習を始めるには最適な場所となるだろう。このセクションでは、テストを通して、その各パーツが何をするのかを説明する。コードの読み取りが終わったら、テストを実行してそれが正しいことを証明しよう。

それでは、セクションごとに見ていこう。もしあなたがコンピューターにいるのなら、[`hello_world_test.cc`](https://oreil.ly/s0f6Q)を開いて一緒に見ていくといいだろう。

### 依存関係を含める

最初の部分は、ライセンス・ヘッダ（[Apache 2.0](https://oreil.ly/Xa5_x)オープンソース・ライセンスのもと、誰でもこのコードを使用または共有できることを明記したもの）の下にあり、次のようになっている：

```
#include "tensorflow/lite/micro/examples/hello_world/sine_model_data.h"
#include "tensorflow/lite/micro/kernels/all_ops_resolver.h"
#include "tensorflow/lite/micro/micro_error_reporter.h"
#include "tensorflow/lite/micro/micro_interpreter.h"
#include "tensorflow/lite/micro/testing/micro_test.h"
#include "tensorflow/lite/schema/schema_generated.h"
#include "tensorflow/lite/version.h"
```

`#include`指令は、C++コードが依存する他のコードを指定する方法である。あるコード・ファイルが`#include`で参照されると、そのファイルが定義しているロジックや変数が利用できるようになる。このセクションでは、`#include`を使用して、以下の項目をインポートする：

`TensorFlow/lite/micro/examples/hello_world/sine_model_data.h`

:

この正弦モデルをトレーニングし、変換し、C++に変換した。`xxd`

`TensorFlow/lite/micro/kernels/all_ops_resolver.h`

:

インタプリタが我々のモデルで使われる演算子をロードできるようにするクラス。

`TensorFlow/lite/micro/micro_error_reporter.h`

:

デバッグに役立つエラーや出力をログに記録するクラス。

`TensorFlow/lite/micro/micro_interpreter.h`

:

TensorFlow Lite for Microcontrollersインタプリタが、我々のモデルを実行する

`TensorFlow/lite/micro/testing/micro_test.h`

:

`TensorFlow/lite/schema/schema_generated.h`

:

`tensorflow/lite/version.h`

これらの依存関係については、コードを掘り下げながら詳しく説明しよう。

###### 注

慣例として、`#include`ディレクティブを使用するように設計されたC++コードは、*ソース・ファイルとして*知られる`.cc`ファイルと、*ヘッダ・ファイルとして*知られる`.h`ファイルの2つのファイルとして記述される。ヘッダファイルは、コードがプログラムの他の部分に接続するためのインタフェースを定義する。ヘッダーファイルには変数やクラス宣言のようなものがコンテナとして含まれているが、ロジックはほとんど含まれていない。ソースファイルは、計算を実行し、物事を実現する実際のロジックを実装する。依存関係を`#include`、そのヘッダファイルを指定する。例えば、今説明しているテストには[`micro_interpreter.h`](https://oreil.ly/60uYt)が含まれている。このファイルを見てみると、クラスは定義されているが、ロジックはあまり含まれていない。その代わりに、ロジックは[`micro_interpreter.cc`](https://oreil.ly/twN7J)に含まれている。

### テストのセットアップ

次の部分は、TensorFlow Lite for Microcontrollersテスト・フレームワークで使用されるコードだ。次のようになる：

```
TF_LITE_MICRO_TESTS_BEGIN

TF_LITE_MICRO_TEST(LoadModelAndPerformInference) {
```

C++では、特別な名前を付けたコードの塊を定義することができ、その名前を他の場所に含めることで再利用することができる。このようなコードの塊は*マクロと*呼ばれる。ここにある2つの文、`TF_LITE_MICRO_TESTS_BEGIN`と`TF_LITE_MICRO_TEST`はマクロの名前付けである。これらは[`micro_test.h`](https://oreil.ly/NoGm4)ファイルで定義されている。

これらのマクロは、TensorFlow Lite for Microcontrollersテストフレームワークによって実行されるために必要な装置で、コードの残りの部分をラップする。具体的にどのように機能するかについて心配する必要はない。テストをセットアップするためのショートカットとして、これらのマクロを使用できることだけを知っていればよい。

番目のマクロは`TF_LITE_MICRO_TEST`という名前で、引数を受け付ける。この場合、渡される引数は`LoadModelAndPerformInference`である。この引数はテストの名前であり、テストを実行すると、テスト結果とともに出力され、テストの合否がわかるようになる。

### データを記録する準備をする

ファイル内の残りのコードは、テストの実際のロジックである。最初の部分を見てみよう：

```
// Set up logging
tflite::MicroErrorReporter micro_error_reporter;
tflite::ErrorReporter* error_reporter = &micro_error_reporter;
```

最初の行では、`MicroErrorReporter`インスタンスを定義している。`MicroErrorReporter`クラスは[`micro_error_reporter.h`](https://oreil.ly/AkZrm)で定義されている。これは推論中にデバッグ情報をロギングするメカニズムを提供する。デバッグ情報を表示するためにこのクラスを呼び出し、TensorFlow Lite for Microcontrollersインタプリタが遭遇したエラーを表示するために使用する。

###### 注

`tflite::MicroErrorReporter`のように、型名の前に`tflite::`という接頭辞がついていることにお気づきだろう。これは*名前空間*であり、C++コードの組織化を助ける方法に過ぎない。TensorFlow Liteは、すべての有用なものを名前空間`tflite`の下で定義している。つまり、他のライブラリが同じ名前のクラスを実装していたとしても、TensorFlow Liteが提供するクラスと衝突することはない。

最初の宣言はわかりやすいが、2行目の`*`と`&`の文字はどうだろう？すでに`MicroErrorReporter`があるのに、なぜ`ErrorReporter`を宣言しているのだろうか？

```
tflite::ErrorReporter* error_reporter = &micro_error_reporter;
```

ここで何が起きているのかを説明するには、少し背景を知っておく必要がある。

`MicroErrorReporter`は、クラスのサブクラスであり、TensorFlow Liteでこの種のデバッグロギング機構がどのように動作すべきかのテンプレートを提供する。`ErrorReporter`は、`MicroErrorReporter`のメソッドの1つをオーバーライドし、マイクロコントローラで使用するために特別に記述されたロジックに置き換える。

先のコード行では、`error_reporter`という変数を作成し、`ErrorReporter`という型を持っている。これはポインタでもあり、宣言で`*`が使われている。

ポインターは、値を保持する代わりに、値を発見できるメモリ上の場所への参照を保持する特殊化変数である。C++では、あるクラス（`ErrorReporter`など）のポインタは、その子クラス（`MicroErrorReporter`など）の値を指すことができる。

前述したように、`MicroErrorReporter`のメソッドの1つをオーバーライドする。`ErrorReporter`.詳細は省くが、このメソッドをオーバーライドする過程で、他のメソッドのいくつかが見えなくなってしまうという副作用がある。

`ErrorReporter`のオーバーライドされていないメソッドにアクセスするには、`MicroErrorReporter`インスタンスを`ErrorReporter`のように扱う必要がある。`ErrorReporter`ポインターを作成し、`micro_error_reporter`変数を指すことで、これを実現する。代入の際、`micro_error_reporter`の前にアンパサンド(`&`)が付いているのは、値ではなくポインタを代入していることを意味している。

ふぅ！複雑そうだ。C++は少し扱いにくいかもしれない。今回の目的では、デバッグ情報を表示するには`error_reporter`、それがポインターであることだけを知っていればいい。

### モデルのマッピング

デバッグ情報を表示する仕組みをすぐにセットアップするのは、残りのコードで発生した問題を記録するためだ。次のコードでは、これを利用する：

```
// Map the model into a usable data structure. This doesn't involve any
// copying or parsing, it's a very lightweight operation.
const tflite::Model* model = ::tflite::GetModel(g_sine_model_data);
if (model->version() != TFLITE_SCHEMA_VERSION) {
error_reporter->Report(
    "Model provided is schema version %d not equal "
    "to supported version %d.\n",
    model->version(), TFLITE_SCHEMA_VERSION);
    return 1;
}
```

最初の行では、モデル・データ配列（[`sine_model_data.h`](https://oreil.ly/m68Wj)で定義）を`GetModel()`という名前のメソッドに渡している。このメソッドは`Model`ポインターを返し、`model`という変数に代入される。予想通り、この変数はモデルを表している。

型`Model`は*構造体で*、C++ではクラスとよく似ている。これは[`schema_generated.h`](https://oreil.ly/SGNtU)で定義されており、モデルのデータを保持し、それに関する情報をクエリすることができる。

`model`、準備が整い次第、モデルのバージョン番号を取得するメソッドを呼び出す：

```
if (model->version() != TFLITE_SCHEMA_VERSION) {
```

次に、モデルのバージョン番号を、現在使用しているTensorFlow Liteライブラリのバージョンを示す`TFLITE_SCHEMA_VERSION`と比較する。番号が一致すれば、モデルは互換性のあるバージョンのTensorFlow Liteコンバータで変換されたことになる。モデルのバージョンを確認するのは良い習慣だ。不一致の場合、デバッグが厄介な奇妙な振る舞いが発生する可能性があるからだ。

###### 注

先のコード行で、`version()`は`model`に属するメソッドである。`model`から`version()`を指す矢印（`->`）に注目してほしい。これはC++の*矢印演算子で*、ポインターを持つオブジェクトのメンバにアクセスしたいときに使われる。もし（ポインタだけでなく）オブジェクトそのものがあれば、そのメンバにアクセスするためにドット（`.`）を使うだろう。

バージョン番号が一致しない場合は、とりあえず続行するが、`error_reporter`を使って警告を記録する：

```
error_reporter->Report(
    "Model provided is schema version %d not equal "
    "to supported version %d.\n",
    model->version(), TFLITE_SCHEMA_VERSION);
```
