
私たちの経験上、この原因の第一は、プログラミング・スタックのオーバーランである。これはローカル変数が格納される場所であり、TensorFlow Lite for Microcontrollersは比較的大きなオブジェクトのためにこれらを広範囲に使用するため、他の多くの組み込みアプリケーションで一般的なサイズよりも大きなスペースを必要とする。そのため、他の多くの組み込みアプリケーションよりも多くのスペースを必要とする。必要な正確なサイズを確認するのは、残念ながら簡単ではない。多くの場合、最大の要因は、`SimpleTensorAllocator` に渡す必要のあるメモリ領域である。[例では](https://oreil.ly/Pb9Pa)、ローカル配列として割り当てられている：

```
  // Create an area of memory to use for input, output, and intermediate arrays.
  // The size of this will depend on the model you're using, and may need to be
  // determined by experimentation.
  const int tensor_arena_size = 10 * 1024;
  uint8_t tensor_arena[tensor_arena_size];
  tflite::SimpleTensorAllocator tensor_allocator(tensor_arena,
                                                 tensor_arena_size);
```

同じ方法を使うのであれば、スタックサイズをそのアリーナのサイズとほぼ同じにし、ランタイムが使う雑多な変数のために数キロバイトを加える必要がある。アリーナを別の場所に保持する場合（グローバル変数として保持する場合など）、必要なスタック容量は数キロバイトで済むだろう。必要なメモリの正確な量は、アーキテクチャやコンパイラ、実行しているモデルによって異なるので、残念ながら正確な値を先に出すのは簡単ではない。もし謎のクラッシュが起きているのなら、この値をできるだけ増やして、それが役に立つかどうか試してみる価値はあるだろう。

それでもまだ問題があるようなら、まず上書きされている変数やメモリ領域を特定することから始めるべきだ。うまくいけば、先に説明したロギングやコード消去のアプローチを使って、問題を破損していると思われる値の読み取りに絞り込むことができるはずだ。どの変数や配列エントリが破損しているかがわかれば、`TRACE` マクロのバリエーションを書いて、そのメモリ位置の値と、呼び出されたファイルや行を出力することができる。そのメモリーアドレスをグローバル変数に格納し、ローカル変数であればより深いスタックフレームからアクセスできるようにするといった特殊化が必要になるかもしれない。そうすれば、通常のクラッシュを追跡するのと同じように、プログラムを実行しながらその場所の内容を `TRACE` 、どのコードがその場所を上書きしたのかを特定することができる。

## どのような作戦が必要かを理解する

本書は、著者がGoogleのチームに所属しているため、TensorFlowで作成されたモデルに焦点を当てているが、単一フレームワークの中にも、様々なモデルの作成方法がある。[音声コマンドの学習スクリプトを](https://oreil.ly/ZTYu7)見ると、TensorFlowのコアとなるオペアを構成要素として直接使ってモデルを構築し、手動で学習ループを回していることがわかる。このスクリプトは元々2017年に書かれたものだ）。TensorFlow 2.0を使った最新の例では、Kerasを高レベルAPIとして使い、細部の多くを処理しているようだ。

この欠点は、モデルが使用する基礎となる演算子が、コードを見ただけではわからなくなることだ。その代わりに、これらは、1回の呼び出しでグラフの大きな塊を表現するレイヤーの一部として作成される。モデルがどのTensorFlow演算子を使用しているかを知ることは、モデルがTensorFlow Liteで動作するか、リソース要件はどうなるかを理解する上で非常に重要だからだ。幸運なことに、`Session` オブジェクトを取得できる限り、Keras からでも基礎となる低レベル演算子にアクセスできる。[`tf.keras.backend.get_session()`](https://oreil.ly/4zurk).TensorFlowで直接コーディングしている場合、セッションはすでに変数に格納されている可能性が高いので、以下のコードでも動作するはずだ：

```
for op in sess.graph.get_operations():
  print(op.type)
```

`sess` という変数にセッションを代入した場合、モデル内の全オペの型が出力される。また、`name` のような他のプロパティにアクセスして、より多くの情報を得ることもできる。どのようなTensorFlow演算子が存在するのかを理解することは、TensorFlow Liteへの変換プロセスで大いに役立つだろう。そうでなければ、表示されるエラーはより理解しづらくなる。

## TensorFlow Liteで既存のOpカバレッジを見る

TensorFlow Liteは、TensorFlowの演算子のサブセットのみをサポートしており、いくつかの制限がある。最新のリストは[ops compatibility guideで](https://oreil.ly/Pix9U)見ることができる。つまり、新しいモデルを計画している場合は、サポートされていない機能や演算に依存していないことを最初に確認する必要がある。特に、`LSTM`、`GRU`、その他のリカレントニューラルネットワークはまだユーザビリティがない。また、TensorFlow Liteのフルモバイルバージョンで利用できるものと、マイクロコントローラ・ブランチとの間にもギャップがある。現時点でTensorFlow Lite for Microcontrollersがサポートしている演算子を理解する最も簡単な方法は、[`all_ops_resolver.cc`を](https://oreil.ly/HNpmM)見ることだ。

TensorFlowのトレーニングセッションで表示される演算と、TensorFlow Liteでサポートされている演算を比較すると、少し混乱するかもしれない。例えば、変数として格納されていた重みを定数に変換したり、浮動小数点演算を最適化として整数演算に量子化したりする。また、バックプロパゲーションのようにトレーニングループの一部としてのみ存在する演算もあり、これらは完全に取り除かれる。どのような問題が発生するかを把握する最善の方法は、見込みモデルを作成したらすぐに、学習する前にエクスポートしてみることで、学習プロセスに多くの時間を費やす前にその構造を調整することができる。

## 前処理と後処理をアプリケーションコードに移す

ディープラーニングモデルには3つの段階があるのが一般的だ。ディスクから画像とラベルをロードしてJPEGをデコードするような単純なものから、音声データをスペクトログラムに変換するスピーチの例のような複雑なものまである。次に、値の配列を取り込み、同様の形式で結果を出力するコアとなるニューラルネットワークがある。最後に、後処理のステップでこれらの値の意味を理解する必要がある。多くの分類問題では、これはベクトル内のスコアを対応するラベルにマッチングさせるという単純なものだが、[`MobileSSD`の](https://oreil.ly/QT_dS)ようなモデルを見ると、ネットワークの出力は重なり合ったバウンディング・ボックスのスープであり、結果として有用であるためには「非最大抑制」と呼ばれる複雑なプロセスを経る必要がある。

コアとなるニューラルネットワークモデルは通常最も計算量が多く、畳み込みや活性化のような比較的少数の演算子で構成されることが多い。前処理ステージと後処理ステージは、計算負荷がかなり低いにもかかわらず、制御フローを含むより多くの演算子を必要とすることが多い。つまり、TensorFlow Liteモデルにベイクするのではなく、アプリケーションに通常のコードとして実装する方が理にかなっていることが多い。例えば、マシン構想モデルのニューラルネットワーク部分は、縦224ピクセル×横224ピクセルのような特定のサイズの画像を取り込む。トレーニング環境では、`DecodeJpeg` 演算子に続いて、`ResizeImages` 演算子を使用して、結果を正しいサイズに変換する。しかし、デバイス上で実行する場合は、ほぼ間違いなく、解凍の必要がない固定サイズのソースから入力画像を取得することになるため、ニューラルネットワークの入力を作成するカスタムコードを書くことは、ライブラリの汎用演算に頼るよりもはるかに理にかなっている。また、おそらく非同期キャプチャを扱うことになるだろうから、作業をスレッド化することで利点が得られるかもしれない。音声コマンドの場合、FFTの中間結果をキャッシュして、ストリーミング入力で実行しているときにできるだけ多くの計算を再利用できるようにするために、多くの作業を行っている。

すべてのモデルがトレーニング環境において重要な後処理段階を持つわけではないが、デバイス上で実行している場合、ユーザに表示される結果を改善するために、時間の経過とともにコヒーレンシーを利用したいと思うことはよくあることだ。モデルは単なる分類器であるにもかかわらず、ウェイクワード検出コードは1秒間に複数回実行され、[平均化を使って](https://oreil.ly/E68Q4)結果の精度を高めている。この種のコードも、TensorFlow Liteの演算子として表現するのは難しく、利点も多くないことから、アプリケーション・レベルで実装するのがベストだ。[`detection_postprocess.cc`を](https://oreil.ly/IMlsT)見ればわかるように、それは可能だが、TensorFlowの小さなオペレーションとして表現する方法は、デバイス上で実装する効率的な方法ではないため、エクスポート処理中に基礎となるTensorFlowグラフから配線する作業が必要になる。

これはすべて、グラフの非コア部分を除外しようとする必要があることを意味し、どの部分がどの部分であるかを決定する作業が必要になる。[`Netron`は](https://oreil.ly/qoQNY)、TensorFlow Liteのグラフを探索し、どのような処理が存在するのかを理解し、それらがニューラルネットワークのコアの一部なのか、それとも単なる処理ステップなのかを把握するのに適したツールであることを発見した。内部で何が起こっているかを理解すれば、コアネットワークを分離し、それらのオペだけをエクスポートし、残りをアプリケーションコードとして実装することができるはずだ。

## 必要に応じて必要な作戦を実装する

どうしても必要なTensorFlowの演算子で、TensorFlow Liteがサポートしていないものが発見された場合、それをTensorFlow Liteのファイル形式内に*カスタム*演算子として保存し、フレームワーク内で自分で実装することができる。完全なプロセスは本書の範囲を超えるが、以下に主要な手順を示す：

* `allow_custom_ops` を有効にして`toco` を実行し、サポートされていない演算子がカスタム演算子としてシリアライズされたモデルファイルに保存されるようにする。
* その演算子を実装したカーネルを書き、アプリケーションで使用しているopリゾルバに`AddCustom()` 。
* `Init()` メソッドが呼び出されたときに、`FlexBuffer` 形式で格納されているパラメータを解凍する。

## オペレーションを最適化する

新しいモデルでサポートされている演算子を使っていても、まだ最適化されていない方法で使っているかもしれない。TensorFlow Liteチームの優先順位は、特定のユースケースによって決定されるため、新しいモデルを実行していると、まだ最適化されていないコードパスに遭遇する可能性がある。この点については[第15](#ch15.html#optimizing_latency)章で取り上げたが、モデルのトレーニングを行う前であっても、できるだけ早くエクスポートの互換性を確認することを推奨するのと同様に、開発スケジュールを計画する前に、必要なパフォーマンスが得られることを確認する価値がある。
