
# オーディオプロバイダの実装とMakefile

```
TfLiteStatus GetAudioSamples(tflite::ErrorReporter* error_reporter,
                             int start_ms, int duration_ms,
                             int* audio_samples_size, int16_t** audio_samples);
int32_t LatestAudioTimestamp();
```

![](assets/timl_1301.png)

最初の関数は、指定された期間のオーディオデータで満たされたバッファを出力し、何か問題があればエラーを返す。2番目の関数は、最新のオーディオデータがいつキャプチャされたかを返すので、クライアントは正しい時間範囲を要求し、新しいデータがいつ到着したかを知ることができる。

デフォルトの実装ではマイクが存在することに依存できないため、[`audio_provider.cc`](https://oreil.ly/8V1Ll)の2つの関数の実装は非常にシンプルだ：

```
namespace {
int16_t g_dummy_audio_data[kMaxAudioSampleSize];
int32_t g_latest_audio_timestamp = 0;
}  // namespace

TfLiteStatus GetAudioSamples(tflite::ErrorReporter* error_reporter,
                             int start_ms, int duration_ms,
                             int* audio_samples_size, int16_t** audio_samples) {
  for (int i = 0; i < kMaxAudioSampleSize; ++i) {
    g_dummy_audio_data[i] = 0;
  }
  *audio_samples_size = kMaxAudioSampleSize;
  *audio_samples = g_dummy_audio_data;
  return kTfLiteOk;
}

int32_t LatestAudioTimestamp() {
  g_latest_audio_timestamp += 100;
  return g_latest_audio_timestamp;
}
```

タイムスタンプは関数が呼び出されるたびに自動的にインクリメントされるため、クライアントはあたかも新しいデータが入ってきたかのように振る舞うが、キャプチャルーチンからは毎回同じゼロの配列が返される。この利点は、システム上でマイクを動作させる前であっても、サンプルコードのプロトタイプを作成し、実験することができることである。`kMaxAudioSampleSize`はモデルヘッダで定義され、関数が要求される最大のサンプル数である。

実際のデバイスでは、コードはもっと複雑になるため、新しい実装が必要になる。先に、このサンプルをSTM32F746NG Discovery kitボード用にコンパイルした。STM32F746NG Discovery kitボードにはマイクが内蔵されており、それらにアクセスするために別のMbedライブラリを使用する。そのコードは[`disco_f746ng/audio_provider.cc`](https://oreil.ly/KrdSO)にある。サイズが大きすぎるため、ここではインラインに含めていないが、そのファイルを見ると、デフォルトの`audio_provider.cc`と同じ2つのパブリック関数`GetAudioSamples()`、`LatestAudioTimestamp()`を実装していることがわかる。関数の定義はもっと複雑だが、クライアントから見た振る舞いは同じだ。また、毎回ゼロの配列を受け取る代わりに、キャプチャされたオーディオが返されたバッファに表示される。

この特殊化実装のフルパス、`tensorflow/lite/micro/examples/micro_speech/disco_f746ng/audio_provider.cc`を見ると、デフォルト実装の`tensorflow/lite/micro/examples/micro_speech/audio_provider.cc`とほぼ同じだが、元の`.cc`ファイルと同じレベルの`disco_f746ng`サブフォルダ内にあることがわかる。STM32F746NG Mbedプロジェクトをビルドするコマンド・ラインを振り返ってみると、`TARGET=disco_f746ng`を渡してプラットフォームを指定していることがわかる。ビルド・システムは常に、特殊化実装の可能性があるターゲット名を持つサブフォルダーにある`.cc`ファイルを探すので、この場合、親フォルダーにあるデフォルトの`audio_provider.cc`バージョンではなく、`disco_f746ng/audio_provider.cc`が使われる。Mbedプロジェクトのコピーのためにソースファイルをアセンブルするとき、その親レベルの`.cc`ファイルは無視され、サブフォルダー内のものがコピーされる。

オーディオのキャプチャはほぼすべてのプラットフォームで異なる方法で行われるため、このモジュールにはさまざまな特殊化が実装されている。[`osx/audio_provider.cc`](https://oreil.ly/ZaMtF)というmacOSバージョンもあり、MacのノートPCでローカルにデバッグする場合に便利だ。

しかし、このメカニズムは移植性のためだけに使われているわけではない。実際に音声航跡の例では、深さ方向の畳み込み演算を高速化するためにこのアプローチを使用している。[`tensorflow/lite/micro/kernels`](https://oreil.ly/0yHNd)を見ると、TensorFlow Lite for Microcontrollersがサポートするすべての演算子の実装が見られる。これらのデフォルト実装は、短く、理解しやすく、どのプラットフォームでも動作するように書かれているが、これらの目標を達成することは、可能な限り高速に動作する機会をしばしば逃すことを意味する。最適化には通常、アルゴリズムをより複雑にし、理解しにくくすることが含まれるため、これらのリファレンス実装は比較的遅くなることが予想される。私たちの考えは、開発者がまず可能な限りシンプルな方法でコードを実行し、正しい結果が得られることを確認し、その後インクリメンタルにコードを変更してパフォーマンスを向上させることができるようにしたいということだ。つまり、どんな小さな変更も、それが正しさを破壊しないことを確認するためにテストすることができ、デバッグがずっと簡単になるのだ。

このモデルは、[`tensorflow/lite/micro/kernels/depthwise_conv.cc`](https://oreil.ly/a16dw)に最適化されていない実装がある。コアとなるアルゴリズムは[`tensorFlow/lite/kernels/internal/reference/depthwiseconv_uint8.h`](https://oreil.ly/2gQ-e)に実装されており、ネストされたループのセットとして書かれている。コード自体は以下の通りだ：

```
   for (int b = 0; b < batches; ++b) {
      for (int out_y = 0; out_y < output_height; ++out_y) {
        for (int out_x = 0; out_x < output_width; ++out_x) {
          for (int ic = 0; ic < input_depth; ++ic) {
            for (int m = 0; m < depth_multiplier; m++) {
              const int oc = m + ic * depth_multiplier;
              const int in_x_origin = (out_x * stride_width) - pad_width;
              const int in_y_origin = (out_y * stride_height) - pad_height;
              int32 acc = 0;
              for (int filter_y = 0; filter_y < filter_height; ++filter_y) {
                for (int filter_x = 0; filter_x < filter_width; ++filter_x) {
                  const int in_x =
                      in_x_origin + dilation_width_factor * filter_x;
                  const int in_y =
                      in_y_origin + dilation_height_factor * filter_y;
                  // If the location is outside the bounds of the input image,
                  // use zero as a default value.
                  if ((in_x >= 0) && (in_x < input_width) && (in_y >= 0) &&
                      (in_y < input_height)) {
                    int32 input_val =
                        input_data[Offset(input_shape, b, in_y, in_x, ic)];
                    int32 filter_val = filter_data[Offset(
                        filter_shape, 0, filter_y, filter_x, oc)];
                    acc += (filter_val + filter_offset) *
                           (input_val + input_offset);
                  }
                }
              }
              if (bias_data) {
                acc += bias_data[oc];
              }
              acc = DepthwiseConvRound<output_rounding>(acc, output_multiplier,
                                                        output_shift);
              acc += output_offset;
              acc = std::max(acc, output_activation_min);
              acc = std::min(acc, output_activation_max);
              output_data[Offset(output_shape, b, out_y, out_x, oc)] =
                  static_cast<uint8>(acc);
            }
          }
        }
      }
    }
```

ざっと見ただけでも、高速化するチャンスがたくさんありそうだ。例えば、内部ループで毎回計算する配列のインデックスをすべて事前に計算するとか。このような変更はコードの複雑さを増すので、このリファレンス実装では避けた。しかし、音声ウェイクワードの例はマイクロコントローラー上で1秒間に何度も実行する必要があり、SparkFun Edge Cortex-M4プロセッサーでは、この素朴な実装がそれを妨げる主な速度ボトルネックになっていることが判明した。この例をユーザビリティのある速度で実行させるには、いくつかの最適化を加える必要があった。

最適化された実装を提供するために、`TensorFlow/lite/micro/kernels`の中に`portable_optimized`という新しいサブフォルダを作成し、[`depthwise_conv.cc`](https://oreil.ly/BYRho)という新しいC++ソースファイルを追加した。これは、リファレンス実装よりもはるかに複雑で、音声モデルの特定の利点を利用して特殊化最適化を可能にしている。例えば、畳み込みウィンドウの幅は8の倍数であるため、値を8バイトとしてではなく、2つの32ビットワードとしてメモリからロードすることができる。

サブフォルダーの名前を、前の例のようにプラットフォーム固有のものではなく、`portable_optimized`としていることにお気づきだろう。配列のインデックスを事前に計算したり、複数バイトの値をより大きなワードとしてロードするなど、さまざまなプロセッサで役立つことが期待される汎用的な最適化である。次に、[`ALL_TAGS`](https://oreil.ly/XSWFk)のリストに`portable_optimized`を追加することで、この実装を`make`プロジェクト・ファイル内で使用するように指定する。このタグがあり、同じ名前のサブフォルダー内に`depthwise_conv.cc`の実装があるため、デフォルトのリファレンスバージョンではなく、最適化された実装がリンクされる。

これらの例から、サブフォルダーのメカニズムを利用して、コア実装を小さく理解しやすいものに保ちながら、ライブラリー・コードを拡張・最適化する方法がわかるといいのだが。

## メイクファイル

理解しやすいという話題では、Makefileはそうではない。[`Makeビルドシステムは`](https://oreil.ly/8Ft1J)もう40年以上前のもので、タブを意味のある構文として使ったり、ビルドターゲットを宣言規則で間接的に指定するなど、混乱させるような機能がたくさんある。私たちは、BazelやCmakeのような代替ではなく、Makeを使用することを選択した。それは、プロジェクト生成のような複雑な振る舞いを実装するのに十分な柔軟性があったからであり、TensorFlow Lite for Microcontrollersのほとんどのユーザが、Makefileと直接対話するのではなく、よりモダンなIDEで生成されたプロジェクトを使用することを望んでいる。

もしコア・ライブラリに変更を加えるのであれば、Makefileのフードの下で何が起こっているのかをもっと理解する必要があるかもしれない。

### 注

LinuxやmacOSでbashターミナルを使っている場合、通常の`make -f tensorflow/lite/micro/tools/make/Makefile`コマンドをタイプしてからTabキーを押すことで、利用可能なターゲット（ビルドできるものの名前）をすべて表示できるはずだ。このオートコンプリート機能は、ターゲットの発見やデバッグの際に非常に役に立つ。

特殊化したバージョンのモジュールor演算子を追加するだけなら、Makefileを更新する必要はまったくないはずだ。というカスタム関数呼び出しがある。[`specialize()`](https://oreil.ly/teIF6)というカスタム関数があり、`ALL_TAGS`の文字列リスト（プラットフォーム名と任意のカスタムタグが入力されている）とソースファイルのリストを自動的に受け取り、正しい特殊化バージョンをオリジナルに置換したリストを返す。これによって、コマンドラインでタグを手動で指定する柔軟性も得られる。たとえば、こんな感じだ：

```
make -f tensorflow/lite/micro/tools/make/Makefile \
  TARGET="bluepill" TAGS="portable_optimized foo" test
```

のような`ALL_TAGS`リストを作成し、すべてのソースファイルについて、サブフォルダーを検索して、代替する特殊化バージョンを発見する。

また、標準フォルダに新しいC++ファイルを追加するだけなら、Makefileを変更する必要はない。[`MICROLITE_CC_BASE_SRCS`](https://oreil.ly/QAtDk)。

Makefileは、ルートレベルでビルドするソースファイルとヘッダファイルのリストを定義し、指定されたプラットフォームとタグに応じてそれらを修正することに依存している。これらの修正は、親ビルドプロジェクトからインクルードされたサブMakefileで行われる。例えば、[`tensorflow/lite/micro/tools/make/targets`](https://oreil.ly/79zOB)フォルダにあるすべての`.inc`ファイルは、自動的にインクルードされる。AmbiqやSparkFun Edgeプラットフォームで使われている[`apollo3evb_makefile.inc`](https://oreil.ly/gKKXO)のように、これらのファイルを見てみると、対象となるチップがこのビルドで指定されているかどうかをチェックしていることがわかる。以下は、最も興味深い部分を省略したものである：
