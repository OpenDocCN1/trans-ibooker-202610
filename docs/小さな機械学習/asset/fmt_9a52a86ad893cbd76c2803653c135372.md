# TensorFlow Lite Mobile OpsをMicroに移植する

モバイルデバイスをターゲットとしたTensorFlow Liteのメインラインには、100以上の「組み込み」演算子がある。TensorFlow Lite for Microcontrollersは、コードのほとんどを再利用しているが、これらのオペレーションのデフォルト実装は、`pthreads`、動的メモリ割り当て、組み込みシステムで利用できないその他の機能などの依存関係をもたらすため、オペレーションの実装（カーネルとも呼ばれる）は、Microで利用できるようにするためにいくつかの作業を必要とする。

最終的には、2つの`op`の実装を統一したいと考えているが、そのためにはフレームワーク全体の設計とAPIを変更する必要があるため、短期的には実現できないだろう。ほとんどの`op`はすでにMicroの実装を持っているはずだが、モバイルTensorFlow Liteでは利用可能だが組み込み版では利用できない`op`を発見した場合、このセクションでは変換プロセスを説明する。移植しようとしている演算子を特定した後、いくつかの段階がある。

## 参照コードを分ける

リストアップされたすべての`ops`はすでにリファレンス・コードを持っているはずだが、関数は[`reference_ops.h`](https://oreil.ly/QmW4H)に ある可能性が高い。これは、ほぼ5,000行に及ぶモノリシックなヘッダファイルである。非常に多くの演算子をカバーしているため、組み込みプラットフォームでは利用できない依存関係を多く含んでいる。移植作業を始めるには、まず、作業中の演算に必要な参照関数を別のヘッダファイルに抽出する必要がある。[`_conv.h`](https://oreil.ly/vH-6) と [`pooling.h`](https://oreil.ly/pwP_0) で、これらの小さなヘッダの例を見ることができる。参照関数自体は、実装する演算子にマッチした名前を持つべきで、通常は異なるデータ型に対して複数の演算子が存在し、時にはテンプレートを使用する。

ファイルが大きなヘッダから分離されたらすぐに、`reference_ops.h`からそのファイルをインクルードして、そのヘッダの既存のユーザがまだあなたが移動した関数を見ることができるようにする必要がある（ただし、我々のMicroコードは分離されたヘッダだけを個別にインクルードする）。`conv2d` 、この方法は[こちらで](https://oreil.ly/jtXLU)見ることができる。また、`kernels/internal/BUILD:reference_base` と `kernels/internal/BUILD:legacy_reference_base` のビルド規則にヘッダを追加する必要がある。これらの変更を行った後、テストスイートを実行し、既存のモバイルテストがすべてパスしていることを確認できるはずだ：

```
bazel test tensorflow/lite/kernels:all
```

これは、レビューのための初期プルリクエストを作成する良い点である。あなたはまだ`micro` ブランチに何も移植していないが、変更のために既存のコードを準備している。次のステップに取り組んでいる間に、この作業をレビューして提出することを試みる価値がある。

## 演算子のマイクロコピーを作成する。

各マイクロ演算子の実装は、`tensorflow/lite/kernels/`にあるモバイル版の修正コピーである。例えば、`micro_conv.cc`は`mobile_conv.cc`をベースにしている。いくつかの大きな違いがある。まず、組み込み環境では動的なメモリ割り当てが厄介であるため、推論中に使用される計算のための計算値をキャッシュする`OpData`構造体の作成は、`Prepare()` から戻されるのではなく、`Invoke()` の間に呼び出されるように、別の関数に移動される。これは、`Invoke()` の呼び出しごとに少し多くの作業を伴うが、メモリのオーバーヘッドを削減することは、通常、マイクロコントローラにとって理にかなっている。

第二に、`Prepare()` のパラメータ・チェック・コードのほとんどは、通常削除される。これを完全に削除するよりも、`#if defined(DEBUG)` で囲む方がよいかもしれないが、削除することでコードサイズを最小限に抑えることができる。外部フレームワーク (`Eigen`,`gemmlowp`,`cpu_backend_support`) への参照は、インクルードとコードからすべて削除する。`Eval()` 関数では、`reference_ops::` 名前空間の関数を呼び出すパス以外はすべて削除する。

結果として得られる修正された演算子実装は、`tensorflow/lite/micro/kernels/`フォルダ内のモバイル版と同じ名前のファイル（通常は演算子名の小文字版）に保存する必要がある。

## テストをマイクロフレームワークに移植する

組み込みプラットフォームではGoogle Testフレームワークをフルに実行することができないので、代わりにMicro Testライブラリを使う必要がある。このライブラリはGTestのユーザにはなじみがあると思うが、動的なメモリ割り当てやC++のグローバル初期化を必要とする構造を避けている。本書の別の場所に、より詳しいドキュメントがある。

モバイルで実行するのと同じテストを組み込み環境でも実行したいので、`tensorflow/lite/kernels/<your op name>_test.cc`のバージョンを出発点として使う必要がある。例えば、[`tensorflow/lite/kernels/conv_test.cc`](https://oreil.ly/76KXK)と移植版の[`tensorflow/lite/micro/kernels/conv_test.cc`](https://oreil.ly/r1wKh)を見てみよう。ここに大きな違いがある：

*   モバイル・コードは、`std::map` や `std::vector` のようなC++ STLクラスに依存しており、これらは動的メモリ割り当てを必要とする。
*   モバイル・コードもヘルパー・クラスを使用し、割り当てを伴う方法でデータ・オブジェクトを渡している。
*   マイクロ・バージョンは、すべてのデータをスタック上に確保する。 `std::initializer_list`を使って、`std::vectors` によく似たオブジェクトを渡すが、動的なメモリ確保は必要ない。
*   テストを実行する呼び出しは、オブジェクトの割り当てではなく、関数呼び出しとして表現される。これは、割り当ての問題にぶつかることなく、多くのコードを再利用するのに役立つからである。
*   ほとんどの標準エラーチェック・マクロが利用できるが、接尾辞は`TF_LITE_MICRO_` となる。例えば、`EXPECT_EQ` は`TF_LITE_MICRO_EXPECT_EQ` になる。

テストはすべて1つのファイルにまとめ、`TF_LITE_MICRO_TESTS_BEGIN`/`TF_LITE_MICRO_TESTS_END` のペアで囲む必要がある。テストがスタンドアロン・バイナリとして実行されるように、`main()` 関数を作成する。

また、テストはカーネルのコードとAPIだけに依存し、インタプリタのような他のクラスを持ち込まないようにする。テストは、`GetRegistration()` から返されるC APIを使用して、カーネルの実装を直接呼び出すべきである。 これは、カーネルが完全にスタンドアロンで使用でき、フレームワークの他の部分を必要としないことを保証したいためである。

## バゼル・テストを構築する

さて、演算子の実装とテスト・ファイルを作成したので、それらが動作するかどうかをチェックしたい。そのためには、Bazelオープンソース・ビルド・システムを使う必要がある。[`BUILD`](https://oreil.ly/CbwMI)ファイルに`tflite_micro_cc_test` ルールを追加し、このコマンドライン（`conv` をあなたの演算子名に置き換えて）をビルドして実行してみる：

```
bazel test ttensorflow/lite/micro/kernels:conv_test --test_output=streamed
```

コンパイルエラーやテストの失敗は間違いなくあるだろうから、その修正に時間を費やすことになるだろう。

## AllOpsResolverにあなたのOpを追加する

アプリケーションはバイナリサイズの都合上、特定の演算子実装だけを取り込むこともできるが、簡単に始められるように、利用可能なすべての演算子を取り込むopリゾルバが用意されている。[`all_ops_resolver.cc`](https://oreil.ly/0Nq06)のコンストラクタに演算子実装を登録する呼び出しを追加し、実装とヘッダファイルが`BUILD`規則に含まれていることを確認する必要がある。

## Makefileテストをビルドする

これまでのところ、TensorFlow Liteの`micro` ブランチ内で、x86上でビルドとテストを行ってきた。これは最も簡単な開発方法であり、初期タスクはポータブルで最適化されていない実装を作成することである。しかし、この時点で、デスクトップLinux上で完全に動作し、テストされた演算子の実装が実行されているはずなので、組み込みデバイス上でのコンパイルとテストを開始する時が来た。

Googleオープンソースプロジェクトの標準的なビルドシステムはBazelだが、残念ながらそれを使ってクロスコンパイルや組み込みツールチェーンのサポートを実装するのは容易ではないため、デプロイには由緒あるMakeに頼らざるを得ない。Makeファイル自体は内部的に非常に複雑だが、うまくいけば、新しい演算子は実装ファイルの名前と場所、テストに基づいて自動的にピックアップされるはずだ。唯一の手動ステップは、作成したリファレンスヘッダを`MICROLITE_CC_HDRS` ファイルリストに追加することだ。

この環境であなたの演算子をテストするには、`cd` 、そのフォルダに移動し、次のコマンドを実行する（`conv` の代わりに、あなた自身の演算子名を指定する）：

```
make -f tensorflow/lite/micro/tools/make/Makefile test_conv_test
```

うまくいけばコンパイルされ、テストはパスする。そうでない場合は、通常のデバッグ手順を実行し、何が間違っているのかを突き止める。

組み込みターゲットと同じビルド・マシンを使っているが、これはまだローカルのIntel x86デスクトップ・マシン上でネイティブに動作している。SparkFun Edgeのような本物のマイクロコントローラーにコードをコンパイルしてフラッシュすることもできる（Makefileの行で`TARGET=sparkfun_edge` を渡すだけで十分だ）が、より簡単にするために、Cortex-M3デバイスのソフトウェア・エミュレーションも用意している。以下のコマンドを実行することで、テストを実行することができるはずだ：

```
make -f tensorflow/lite/micro/tools/make/Makefile TARGET=bluepill test_conv_test
```

エミュレーターの実行に時間がかかりすぎてタイムアウトになることがあるので、少し不安定かもしれないが、うまくいけば2回目のトライで直るだろう。ここまで来たら、可能であれば、オープンソース・ビルドにあなたの変更をコントリビュートすることをお勧めする。コードをオープンソースにする全プロセスは少し複雑だが、[TensorFlow Communityのガイドが](https://oreil.ly/YcbFB)手始めに良いだろう。

## デザイン・プロセス

モデルのトレーニングには数日から数週間かかることがあり、新しい組込みハードウェアプラットフォームの立ち上げにも非常に時間がかかる。そのため、組込み機械学習プロジェクトにおける最大のリスクの1つは、何かを動作させる前に時間切れになってしまうことだ。このリスクを減らす最も効果的な方法は、計画、調査、実験を通じて、プロセスのできるだけ早い段階で、未解決の疑問点のできるだけ多くに答えることだ。トレーニングデータやアーキテクチャを変更するたびに、コーディングと再トレーニングに1週間を費やすことになりかねない。また、デプロイメント・ハードウェアの変更は、ソフトウェアスタック全体に波及し、以前動作していたコードの書き換えを大量に伴う。開発プロセスの後半で必要な変更の回数を減らすために、最初にできることは何でもしておくと、それらの変更に費やす時間を節約できる。この章では、最終的なアプリケーションのコーディングを開始する前に、重要な質問に答えるた めに推奨するテクニックのいくつかに焦点を当てる。

## マイクロコントローラーが必要なのか、それとももっと大きなデバイスが必要なのか？

あなたが本当に答えなければならない最初の質問は、組み込みシステムの利点が必要なのか、少なくとも初期プロトタイプの場合は、バッテリー寿命、コスト、サイズなどの要件を緩和できるのか、ということだ。Linuxのような完全なモダンOSを搭載したシステムでのプログラミングは、組み込みの世界で開発するよりもずっと簡単だ（そして速い）。`Raspberry Pi`のような完全なデスクトップレベルのシステムは、カメラやその他のセンサーなど多くの周辺機器とともに25ドル以下で手に入る。計算量の多いニューラルネットワークを実行する必要がある場合、`NVIDIA`の`Jetson`シリーズのボードは99ドルからで、小さなフォームファクターに強力なソフトウェア・スタックをもたらす。これらのデバイスの最大の欠点は、数ワットを消費するため、エネルギー貯蔵の物理的サイズにもよるが、バッテリー駆動の寿命がせいぜい数時間から数日程度になることだ。遅延が困難な制約でない限り、ニューラルネットワークのワークロードを処理するために必要なだけの強力なクラウドサーバを起動し、クライアントデバイスにインタフェースとネットワーク通信を任せることもできる。

私たちは、どこにでもデプロイできることの力を強く信じているが、アイデアがうまくいくかどうかを判断しようとしているのであれば、簡単で素早く実験できるデバイスを使ってプロトタイプを作ってみることを強くお勧めする。組込みシステムの開発は、背後で大きな痛みを伴うので、飛び込む前に、アプリケーションの本当の要件をより詳しく知ることができればできるほど、成功する可能性が高くなる。
