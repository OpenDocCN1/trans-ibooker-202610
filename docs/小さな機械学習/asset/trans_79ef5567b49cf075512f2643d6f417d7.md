
几乎所有嵌入式处理器都具有进入睡眠模式的功能。在睡眠模式下，不执行计算，几乎不消耗电量。也就是说，减少功耗最简单的方法之一是在推理调用之间插入睡眠，使处理器在低功耗模式下花费更多时间。这在嵌入式领域通常被称为*作为占空比循环*。可能会担心持续的传感器数据采集会被排除，但最近的许多微控制器都配备了直接内存访问（DMA）功能，可以在不涉及主处理器参与的情况下持续采样模拟-数字转换器（ADC）并将结果存储到内存中。

同样，通过降低处理器执行指令的频率，可以有效地减慢运行速度并显著降低功耗。先前所示的数据表示例展示了时钟频率下降时所需能量如何降低。

占空比循环和频率降低提供的是一种用计算交换电力使用量的能力。这实际上意味着什么，如果可以减少软件延迟，就可以用它来换取电力预算的削减。即使可以在分配的时间内执行，如果希望降低功耗，也应考虑优化延迟的方法。

## 级联设计

与传统过程式编程相比，机器学习的一个重要优势是所需计算资源和存储资源可以轻松增减，且精度通常优雅下降。用手工编码的算法实现这一点更困难。通常是因为没有可以微调以影响这种特性的明显参数。这意味着可以创建所谓的*模型级联*。传感器数据可以送入计算需求极小的非常小的模型中，即使不够精确，也可以调优使其在特定条件存在时更可能触发（即使假阳性增多）。结果，一旦发现有有趣的事情发生，就可以用相同的输入输入到更复杂的模型中，得到更准确的结果。此过程可以重复数个阶段。

之所以有用，是因为不准确但小的模型可以容纳在电力效率极高的嵌入式设备中，因此即使持续运行也不会消耗太多能量。一旦发现潜在事件，更强大的系统就会启动并运行更大的模型。更强大的系统只运行极短的时间，因此其功耗不会给预算带来压力。这就是手机常时连接语音界面的工作原理。DSP持续监控麦克风，有一个监听“Alexa”、“Siri”、“Hey Google”或类似唤醒词的模型。主CPU可以保持在睡眠模式，但当DSP判断听到合适的短语时，会发送信号启动CPU。然后CPU运行更大更准确的模型，确认是否真的为正确的短语，如果是，则可以将后续语音发送到云端更强大的处理器。

也就是说，嵌入式产品即使无法托管足够精确以自行采取行动的模型，也可能实现目标。可以训练一个能够发现大多数真阳性的网络，如果假阳性发生频率足够低，则可以将剩余工作卸载到云端。无线电非常耗电，但如果将其使用限制在稀有机会和短时间内，则可能在能量预算内。

## 总结

对于我们许多人（包括作者在内）来说，能耗优化是一个不熟悉的过程。幸运的是，延迟优化中描述的许多技能只需监控的指标不同，在这里也可以应用。一般来说，优先考虑延迟而非能量的优化是一个好主意。因为即使寿命不足以在现实世界中使用，也经常需要使用提供短期用户体验的版本来验证产品是否运行。同样，在延迟和能量之后，着手处理[第17章的](#ch17.html#chapter_17)主题——空间优化，通常也是合理的。实际上，为了满足约束，你将在所有不同的权衡之间来回移动，但通常在其他方面相当稳定之后再处理大小会更容易。

无论选择哪个平台，闪存存储和 RAM 都将非常有限。大多数嵌入式系统中的闪存只读存储小于 1MB，其中许多只有几十千字节。内存也是如此，很少有超过 512KB 的静态 RAM（SRAM）可用，在低端设备上这个数字可能在个位数。TensorFlow Lite for Microcontrollers 设计为仅使用 20KB 的闪存和 4KB 的 SRAM 运行，但需要仔细设计应用程序并进行工程权衡以保持占用率低。本章将介绍可用于监控和控制内存和存储需求的几种方法。

## 理解系统的限制

大多数嵌入式系统采用将程序和其他只读数据存储在闪存中，并在新可执行文件上传时才写入的架构。通常还提供使用 SRAM 技术的可变内存。这与大型 CPU 缓存中使用的技术相同，低功耗且访问速度快，但尺寸有限。更先进的微控制器可以提供第二层可变内存，使用动态 RAM（DRAM）等功耗较大但可扩展性强的技术。

需要了解潜在平台提供什么以及权衡是什么。例如，配备大量二级 DRAM 的芯片可能因其灵活性而具有吸引力，但如果启用该额外内存会导致电力预算超支，则可能没有价值。在本书关注的 1mW 以下的功率范围内使用运算符时，通常不可能使用 SRAM 之外的东西。也就是说，两个重要的指标是可用的只读闪存存储有多少，以及可用的 SRAM 有多少。这些数字应该列在您查看的芯片说明中。希望不必深入到数据表的[「硬件选择」まで](#ch16.html#hard_choice)。

## 估算内存使用量

在对硬件选择有了想法后，需要加深对软件所需资源及其需求可控制的权衡的理解。

### Flash 使用

通常，闪存所需容量可以通过编译完整的可执行文件并查看生成的映像大小来准确判断。因为链接器最初生成的工件通常是执行文件的注释版本，如 ELF 格式，包含调试符号和段信息（这将在[「代码大小的测量](#ch17.html#measuring_code_size)」で詳しく説明する）[。](#ch17.html#measuring_code_size)您想看的是实际闪存到设备上的文件，通常由 `objcopy` 等工具生成。测量所需闪存内存量的最简单公式是以下各项的总和：

操作系统大小

: 

如果使用某种实时操作系统（RTOS），则需要在可执行文件中为其代码保留空间。估算占用率最简单的方法是构建启用所需功能的示例“hello world”程序。查看映像文件大小即可了解 OS 程序代码的大致基准值。占用程序空间较多的典型模块有 USB、WiFi、Bluetooth、移动无线堆栈等，因此如果使用它们，请确保已启用。

适用于微控制器的 TensorFlow Lite 代码大小

: 

ML 框架需要为加载和运行神经网络模型的程序逻辑提供空间，其中包括执行核心运算的运算符实现。本章后面将介绍如何为特定应用设置框架以减小尺寸，但入门时，只需编译包含框架的标准单元测试之一，例如[（`micro_speech` 测试的](https://oreil.ly/7cafy)这样的），并查看生成的映像大小进行估算即可。

模型数据大小

: 

如果尚未训练模型，可以通过计数权重来估算模型所需的闪存存储容量。例如，全连接层将具有输入向量大小乘以输出向量大小的权重。对于卷积层则更复杂，需要将滤波器框的宽度和高度乘以输入通道数，再乘以滤波器数。还需要为每个层相关的偏置向量添加存储空间。这很快就会变得复杂，因此在 TensorFlow 中创建候选模型并导出为 TensorFlow Lite 文件会更容易。该文件直接映射到 Flash，因此其大小可准确显示占用多少空间。也可以查看[Keras 的 `model.summary()` 方法](https://keras.io/models/about-keras-models)列出的权重数量。

###### 注

量化在[第4章中](#ch04.html#chapter_hello_world_training)介绍，并在[第15](#ch15.html#optimizing_latency)章中进一步详细说明，但从模型大小的角度重新确认一下是有价值的。在训练期间，权重通常以浮点值保存，每个占用 4 字节内存。由于移动设备和嵌入式设备空间受限，TensorFlow Lite 支持一种称为*量化*的过程，将这些值压缩为单个字节。它通过跟踪存储在 float 数组中的最小值和最大值，并将所有值线性转换为该范围内等间隔的 256 个值中最接近的一个来工作。这些代码各存储为 1 字节，可以以最小的精度损失执行算术运算。

应用程序代码大小

: 

需要代码来访问传感器数据、为神经网络预处理它并响应其结果。也可能需要除机器学习模块之外的用户界面或业务逻辑。估算这一点可能很困难，但至少需要了解是否需要外部库（例如快速傅里叶变换），并计算其代码空间需求。

### RAM 使用量

因为 RAM 使用量会随编程生命周期而变化。与估算闪存需求的过程类似，需要查看软件的各个层来估算整体使用需求：

操作系统大小

: 

大多数[RTOS（FreeRTOS 等）是](https://www.freertos.org/FAQMem.html)记录不同配置选项需要多少 RAM，您可以使用此信息来规划所需大小。需要特别注意需要缓冲的模块，尤其是 TCP/IP、WiFi、Bluetooth 等通信堆栈。这些需要添加到 OS 核心需求中。

适用于微控制器的 TensorFlow Lite RAM 大小

: 

ML 框架对核心运行时不需要大量内存，因此不应在 SRAM 中为数据结构需要数千字节以上的空间。这些作为解释器使用的类的一部分分配，因此应用程序代码是将其创建为全局对象还是局部对象决定了它放在堆栈还是通用内存中。通常建议创建为全局对象或 `static` 对象。分配在堆栈上的局部对象可能在运行时导致崩溃，但空间不足通常会在链接时引发错误。

模型内存大小

: 

神经网络运行时，一个层的输出需要暂时保留以作为后续运算符的输入。这些激活层的寿命取决于图中的位置，每个所需的内存大小由层写入的数组形状控制。这些变化意味着需要花费时间计算计划，以便将所有临时缓冲区尽可能容纳在较小的内存区域中。目前，这是在模型首次由解释器加载时进行的，因此如果 arena 大小不足，控制台会显示错误。查看错误消息中显示的可用内存和所需内存之间的差异，并相应增加 arena 即可克服错误。

应用程序内存大小

: 

与程序大小一样，应用程序逻辑的内存使用量在创建前也难以计算。但是，可以对内存的大用户进行一定程度的猜测，例如存储输入样本数据所需的缓冲区，或库预处理所需的内存区域。

## 各种问题中模型精度和大小的近似值

为了规划在自己的应用中可能实现的内容，了解各种类型问题的技术现状是有帮助的。机器学习不是魔法，了解其局限性有助于在产品制作时做出明智的权衡。讨论设计过程的[第14章是](#ch14.html#designing_your_own_tinyml_applications)，开始培养直觉的好地方，但也需要考虑随着模型受到更严格的资源限制，精度如何下降。为此，这里介绍一些为嵌入式系统设计的架构示例。如果其中一个接近您需要的东西，它可以帮助您想象在模型创建过程的最后可以实现什么。当然，实际结果在很大程度上取决于特定产品或环境，因此请将其用作规划指南，不要指望能达到完全相同的性能。

### 语音唤醒词模型

先前作为代码示例提到的，使用 40 万次算术运算的小型（18KB）模型，在区分四类声音（静音、未知词、“是”、“否”）时，达到了 85% 的 top-1 精度（["建立指标 "](#ch18.html#establish_a_metric)参照）。这是一个训练评估指标，意味着向其呈现 1 秒的剪辑并要求模型对其输入进行一次性分类。实际上，模型通常用于流式音频，基于逐步推进的 1 秒窗口重复预测结果，因此实际应用中的精度会低于该数字所暗示的。一般来说，这种大小的音频模型应被视为更大级联处理的第一个阶段的守门员，其错误将由更复杂的模型容忍和处理。

经验法则是，要检测唤醒词以达到语音界面使用的足够精度，可能需要具有 300-400KB 权重和少于数千万次算术运算的模型。不幸的是，标记的语音数据的开放存储库仍然不足，因此学习可能还需要商业质量的数据集，但希望随着时间的推移这一限制也会缓解。

### 加速度传感器的预测性维护模型
