
# 画像の前処理

画像の前処理は、再スケーリングのステップだけにとどまらない。通常0から255でエンコーディングされる画像値を、学習時に使用する浮動小数点数にどのように変換するかという問題もある。いくつかの理由から、これらは通常、-1.0から1.0または0.0から1.0という小さな範囲にリニアにスケーリングされる。浮動小数点値を入力する場合、アプリケーションでも同じように値をスケーリングする必要がある。8ビット値を直接入力する場合は、ランタイムでこれを行う必要はない。元の8ビット値は変換せずに使用できるが、`--mean_values` および`--std_values` フラグを通して`toco` エクスポート・ツールに渡す必要がある。1.0から1.0の範囲なら、`--mean_values=128 --std_values=128`。

というのも、この詳細は使用するAPIの実装に埋もれていることが多いからだ。Googleが公開しているモデルの多くが使用している`Slim`フレームワークのデフォルトは-1.0から1.0である。

さらに悪いことに、リサイズや値のスケーリングを多少間違えても、*ほぼ*正しい結果を得ることができるが、精度を落とすことになる。つまり、あなたのアプリケーションは、何気なく見たときにはうまくいっているように見えても、最終的には全体的な印象が悪くなってしまうのだ。また、画像の前処理に関する課題は、音声や加速度センサーのデータのように、生データをニューラルネットワーク用の数値の配列に変換するための複雑な特徴生成のパイプラインが存在するような他の分野よりも、実際にはずっと単純だ。[`micro_speech` の例の前処理コードを](https://oreil.ly/tedw1)見ると、音声サンプルからモデルに入力できるスペクトログラムを得るために、多くの段階の信号処理を実装しなければならなかったことがわかる。このコードとトレーニングで使用したバージョンとの間に違いがあると、結果の精度が低下する。

## デバッグ前処理

このような入力データの変換はエラーになりやすいため、問題があることに気づくことさえ難しいかもしれない。どうすればいいのか？私たちは、いくつかの方法があることを発見した。

ペリフェラルがスタブアウトされていたとしても、可能な限りデスクトップマシンで実行できるバージョンのコードを用意するのが常にベストだ。Linux、macOS、Windows環境では、より優れたデバッグ・ツールが使えるし、トレーニング・ツールとアプリケーションの間でテスト・データを転送するのも簡単だ。TensorFlow Lite for Microcontrollersのサンプルコードでは、アプリケーションのさまざまな部分をモジュールに分割し、LinuxとmacOSターゲット用の`Makefile`ビルドを有効にして、推論ステージと前処理ステージを別々に実行できるようにしている。

プリプロセッシングの問題をデバッグするための最も重要なツールは、トレーニング環境とアプリケーションで見ている結果との比較である。これを行う上で最も難しいのは、トレーニング中に気になるノードの正しい値を抽出し、その入力を制御することである。この方法を詳しく説明することは本書の範囲外であるが、中核となるニューラルネットワークのステージ（ファイルデコードの後、前処理、および前処理の結果を取り込む最初のオペ）に対応するオペの名前を特定する必要がある。前処理の結果を取り込む最初のオペは、`toco` の引数`--input_arrays` に対応する。これらのオペを特定できる場合は、を設定したオペを挿入する。[`tf.print`](https://oreil.ly/JYT_m)`summarize` `-1` を挿入する。トレーニングループを実行すると、デバッグコンソールで各ステージでのテンソルの内容のプリントアウトを見ることができる。

そして、これらのテンソルの内容をCのデータ配列に変換し、プログラミングにコンパイルできるようにする。`micro_speech`、この例として、[誰かが「イエス」と言った1秒間の音声サンプルと](https://oreil.ly/qFoMn)、[その入力を前処理した場合の期待される結果が](https://oreil.ly/uKYWo)ある。これらの基準値を手に入れたら、パイプラインの各段階（前処理、ニューラルネットワーク推論）を保持するモジュールに入力として送り込み、出力が期待したものと一致することを確認できるはずだ。時間がない場合は、使い捨てのコードでこれを行うこともできるが、時間の経過とともにコードが変更されても、前処理とモデル推論が検証され続けることを保証する[単体テストに](https://oreil.ly/t2E03)変えることは、余分な投資をする価値がある。

## オンデバイス評価

トレーニングの最後に、ニューラルネットワークは入力のテストセットを使用して評価され、予測はモデルの全体的な精度を特徴付けるために期待される結果と比較される。これはトレーニングプロセスの通常の部分として行われるが、デバイスにデプロイされたコードで同じ評価を行うことは稀である。多くの場合、最大の障壁は、典型的なテストデータセットを構成する何千もの入力サンプルを、リソースの限られた組み込みシステムに転送することだ。しかし、これは残念なことだ。デバイス上の精度がトレーニング終了時に見られたものと一致することを確認することは、モデルが正しくデプロイされたことを確認する唯一の方法である。`micro_speech` デモの完全なテストセット評価を実装することはできなかったが、少なくとも、2つの異なる入力に対して正しいラベルが得られることを確認する[エンドツーエンドテストは](https://oreil.ly/4372z)ある。

# 数値的な違い

ニューラルネットワークは、大きな数の配列に対して行われる複雑な数学演算の連鎖である。元のトレーニングは通常浮動小数点数で行われるが、組み込みアプリケーションのために低精度の整数表現に変換するようにしている。演算子自体は、プラットフォームや最適化のトレードオフに応じて、さまざまな方法で実装することができる。これらすべての要因は、たとえ同じ入力が与えられたとしても、異なるデバイス上のネットワークからビット単位で同一の結果を期待することはできないことを意味する。つまり、どの程度の違いが許容できるか、また、その違いが大きくなりすぎた場合、その違いがどこから来たのかを追跡する方法を決めなければならない。

## 違いは問題か？

私たちは時々、本当に重要なメトリックはアプリストアの評価だけだと冗談を言う。我々のゴールは、ユーザが満足するプロデューサを作ることであり、それ以外のメトリックはユーザ満足度のプロキシに過ぎない。本番環境実験との数値的な違いは常に存在するため、最初の課題は、それが製品体験を損なうかどうかを理解することだ。ネットワークから得られる値が無意味なものであれば、これは明らかだが、予想される値から数パーセントの点差しかないのであれば、現実的なユースケースを持つ完全なアプリケーションの一部として、結果のネットワークを試してみる価値がある。精度の低下は問題ではないかもしれないし、もっと重要で優先すべき問題が他にあるかもしれない。

## メトリックを確立する

本当に問題があると確信したら、それを数値化することが役に立つ。期待される結果からの出力スコアベクトルの差の割合のような、数値的な尺度を選びたくなるかもしれない。しかし、これはユーザ体験をあまり反映していないかもしれない。例えば、画像分類をしていて、すべてのスコアが期待値より5％低かったとしても、結果の相対的な順序は変わらない。

その代わりに、製品が必要とするものを反映したメトリックを設計することを推奨する。画像分類の場合、テスト画像セット全体で*トップ1*スコアと呼ばれるものを選ぶかもしれない。`top-one`メトリックは、モデルがその最高得点予測として、どれくらいの頻度でground truthラベルを選ぶかである*（`top-five`も*同様であるが、ground truthラベルが5つの最高得点予測にどれくらいの頻度で含まれるかをカバーする）。そして、トップ1メトリックを使って進捗を追跡し、重要なこととして、行った変更がいつ十分なものになったかを知ることができる。

また、実際にニューラルネットワークの処理に投入されるものを反映した標準的な入力セットを組み立てるように注意すべきである。先に述べたように、前処理がエラーを引き起こす可能性はたくさんあるからだ。

## ベースラインと比較する

TensorFlow Lite for Microcontrollersは、すべての機能のリファレンス実装を持つように設計されている。このようにした理由の1つは、潜在的な違いをデバッグするために、最適化されたコードと結果を比較できるようにするためだ。標準的な入力がいくつかできたら、フレームワークのデスクトップビルドで、リファレンス演算子の実装が呼び出されるように最適化を有効にしていない状態で、その入力を実行してみてほしい。この種のスタンドアロン・テストの出発点が必要な場合は、[`micro_speech_test.cc`を見て](https://oreil.ly/x5QYp)ほしい。設定したメトリックで結果を実行すると、期待通りのスコアが表示されるはずだ。そうでない場合は、変換処理中に何らかのエラーが発生したか、ワークフローの初期段階で何か問題が発生した可能性があるので、問題が何であるかを理解するためにトレーニングに戻ってデバッグする必要がある。

リファレンスコードを使用して良い結果が得られたら、ターゲットプラットフォーム上で、同じテストをビルドし、すべての最適化を有効にして実行してみるべきである。もちろん、これほど単純ではないかもしれない。組み込みデバイスには、すべての入力データを保持するメモリがないことが多いし、デバッグのロギング接続しかない場合、結果を出力するのは厄介なことだからだ。テストを複数回に分けて実行しなければならないとしても、辛抱する価値はある。結果が得られたら、それをメトリックに通し、実際の赤字が何であるかを理解する。

## 実装を入れ替える

多くのプラットフォームでは、デフォルトで最適化が有効になっている。これは、リファレンス実装が組み込みデバイス上で実行するのに非常に時間がかかり、実質的に使用できない可能性があるためだ。これらの最適化を無効にする方法はたくさんあるが、最も単純な方法は、現在使用されているすべてのカーネル実装を、通常は[`TensorFlow/lite/micro/kernels`の](https://oreil.ly/k3lln)サブフォルダで発見し、その親ディレクトリにあるリファレンスバージョンで上書きすることである。最初のステップとして、最適化された実装をすべて置き換えて、デバイス上のテストを再実行する。

このように全体的な置き換えを行った後、最適化カーネルの半分だけを上書きしてみて、それがメトリックにどのように影響するかを見てみる。たいていの場合、どの最適化カーネル実装がスコアの最大の低下を引き起こしているのかを、バイナリ検索アプローチで特定できるだろう。特定の最適化カーネルに絞り込むことができたら、次に、*悪い*実行の1つの入力値と、参照実装からそれらの入力に対する期待出力値をキャプチャすることによって、最小限の再現可能なケースを作成することができるはずである。これを行う最も簡単な方法は、テストを実行している間にカーネル実装内からデバッグロギングを行うことである。

これで再現可能なケースができたので、そこから単体テストを作成できるはずだ。手始めに[標準的なカーネルテストの1つを見て](https://oreil.ly/0rnPW)、新しいスタンドアロンテストを作成するか、そのカーネル用の既存のファイルに追加することができる。そうすれば、最適化実装を担当するチームに問題を伝えるためのツールができる。彼らのコードとリファレンス・バージョンの結果に違いがあり、それがアプリケーションに影響していることを示すことができるからだ。また、同じテストをメインのコードベースに追加し、他の最適化実装が同じ問題を引き起こさないようにすることもできる。また、実装を自分でデバッグするのにも最適なツールだ。コードを分離して実験でき、素早く反復できるからだ。

# 謎のクラッシュとハング

組込みシステムで修正するのが最も難しい状況の一つは、プログラミングが実行されないのに、何が間違っていたのかを説明する明らかなロギング出力やエラーがない場合である。問題を理解する最も簡単な方法は、(`GDB` のような) デバッガをアタッチし、ハングしている場合はスタックトレースを見るか、実行がどこで間違っているかを確認するためにコードをステップスルーすることである。しかし、デバッガをセットアップするのは必ずしも簡単ではないし、デバッガを使っても問題の原因がはっきりしないこともある。

## デスクトップデバッグ

Linux、macOS、Windowsのようなフル・オペレーティング・システムには、広範なデバッグ・ツールとエラー・レポート・メカニズムがあるため、可能な限り、ダミー実装でハードウェア固有の機能の一部をスタブアウトしてでも、これらのプラットフォームのいずれかにプログラムを移植できるようにしておこう。TensorFlow Lite for Microcontrollersはこのように設計されており、まずLinuxマシンでうまくいかないことを再現してみることができる。この環境で同じエラーが発生した場合、通常、標準的なツールを使って追跡する方がはるかに簡単で速く、デバイスをフラッシュする必要もないため、反復のスピードが上がる。アプリケーション全体をデスクトップビルドとして維持するのは難しすぎるとしても、少なくとも、デスクトップ上でコンパイルするモジュールの単体テストや統合テストが作成できるかどうかを確認しよう。そして、あなたが問題視している状況と同じような入力を与えてみて、同じようなエラーを引き起こすかどうかを発見することができる。

## ログトレース

TensorFlow Lite for Microcontrollersが必要とする唯一のプラットフォーム固有の機能は、`DebugLog()` の実装である。この要件があるのは、開発中に何が起こっているかを理解するために不可欠なツールだからである。デプロイプラフォームには必要ないものであるにもかかわらず。理想的な世界では、クラッシュやプログラミング・エラーはログ出力のトリガーになるはずだ。例えば、STM32デバイスのベアメタル・サポートには、これを実行する[フォールト・ハンドラが](https://oreil.ly/dsHG8)ある。

しかし、常に自分でコードにログ文を入れることはできるはずだ。これらは意味のあるものである必要はなく、コードのどの場所に到達したかを記述するだけでよい。このように、自動トレースマクロを定義することもできる：

```
#define TRACE DebugLog(__FILE__ ":" __LINE__)
```

そして、それをコードで次のように使う：

```
int main(int argc, char**argv) {
  TRACE;
  InitSomething();
  TRACE;
  while (true) {
    TRACE;
    DoSomething();
    TRACE;
  }
}
```

デバッグ・コンソールに、コードがどこまで進んだかを示す出力が表示されるはずだ。通常、コードの最上位レベルから始めて、ロギングがどこで止まるかを確認するのがベストだ。そうすることで、クラッシュやハングが起こっている大まかな範囲を知ることができる。その後、`TRACE` 文を追加して、問題が起こっている場所を正確に絞り込むことができる。

## ショットガン・デバッグ

トレースでは何が間違っているのか十分な情報が得られないこともあるし、本番環境のようにログにアクセスできない環境でのみ問題が発生することもある。そのような場合は、"ショットガン・デバッグ "と呼ばれるものを推奨する。これは[第15](#ch15.html#optimizing_latency)章で説明した "ショットガンプロファイリング "に似ており、コードの一部をコメントアウトして、それでもエラーが発生するかどうかを確認するだけの簡単なものである。アプリケーションのトップレベルから始めて、下へ下へと作業していけば、通常はバイナリ検索と等価性で、どの行が問題を引き起こしているかを切り分けることができる。例えば、メインループの中で次のようなことから始めるかもしれない：

```
int main(int argc, char**argv) {
  InitSomething();
  while (true) {
    // DoSomething();
  }
}
```

`DoSomething()` をコメントアウトした状態で正常に実行されれば、問題はその関数内で起きていることがわかる。次に、その関数のコメントを外し、再帰的にその関数本体内で同じことをすれば、問題のあるコードに焦点を絞ることができる。

## メモリ破損

最も手痛いエラーは、メモリ上の値が誤って上書きされることによって引き起こされる。組込みシステムには、デスクトップやモバイルのCPUのようにこれを防ぐハードウェアがないため、デバッグは特に難しい。コードをトレースしたりコメントアウトしたりしても、混乱した結果になることがある。なぜなら、上書きは、破損した値を使用するコードが実行されるずっと前に発生する可能性があるため、クラッシュが原因から遠く離れてしまう可能性があるからだ。クラッシュはセンサーの入力やハードウェアのタイミングに左右されることもあり、断続的で再現が難しい。
