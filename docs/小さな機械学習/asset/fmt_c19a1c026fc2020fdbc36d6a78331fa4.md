
LEDをトグルするのと同じような方法で、`GPIO`ピンをオン／オフさせ、外部ロジック・アナライザ（過去に[Saleae Logic Pro 16を](https://oreil.ly/pig8l)使用したことがある）を使ってその時間を視覚化し、測定することができる。これには少し配線が必要で、機器自体も高価になるが、1つまたは複数の`GPIO`ピンの制御以上のソフトウェア・サポートを必要とせずに、プログラミングの遅延を調査する非常に柔軟な方法を提供する。

## タイマー

十分な精度で一貫した現在時刻を取得できるタイマーがあれば、興味のあるコードセクションの開始時と終了時の時刻を記録し、通信遅延が結果に影響しないようなログに出力することができる。このような理由から、TensorFlow Lite for Microcontrollersにプラットフォームに依存しないタイマー・インタフェースを搭載することも検討したが、タイマーのセットアップが複雑になる可能性があることから、異なるプラットフォームに移植する際の負担が大きくなると判断した。しかし、タイマーの設定が複雑になる可能性があるため、異なるプラットフォームへの移植には負担が大きすぎると判断したのだ。残念ながら、この関数は、実行中のチップに対してこの機能を実装する方法を自分で調べる必要があることを意味する。また、調査したいコードの周囲にタイマーの呼び出しを追加する必要があるという欠点もある。そのため、重要な部分を特定するための作業と計画が必要となり、時間の行き先を調査しながら再コンパイルとフラッシュを繰り返す必要がある。

## プロファイラー

運がよければ、何らかの外部プロファイリングツールをサポートしているツールチェーンやプラットフォームで作業できるだろう。このようなアプリケーションは通常、あなたのプログラムのデバッグ情報を使って、あなたのプログラムをデバイス上で実行して収集した実行に関する統計情報と照合する。そして、どの関数に最も時間がかかっているか、あるいはどの行のコードに最も時間がかかっているかを可視化することができる。これは、重要な関数を素早く探索し、ズームすることができるため、コードのどこにスピードのボトルネックがあるかを理解する最も速い方法だ。

# オペレーションの最適化

できるだけシンプルなモデルを使用していることを確認し、コードのどの部分に最も時間がかかっているかを特定したら、次にそれらを高速化するために何ができるかを検討する必要がある。ニューラルネットワークの実行時間のほとんどは、各レイヤーに数十万から数百万の計算が含まれることを考えると、演算実装の内部で費やされるはずである。

## すでに最適化されている実装を探す

TensorFlow Lite for Microcontrollersのすべての演算のデフォルト実装は、小さく、理解しやすく、ポータブルであるように書かれており、高速ではないので、より多くのコード行やメモリを使用するアプローチで、かなり簡単に打ち負かすことができると予想される。私たちは、[第13](#ch13.html#chapter_tensorflow_lite_for_microcontrollers)章で説明したサブフォルダー特殊化アプローチを使った、より高速な実装セットを [`kernels/portable_optimizedディレクトリに`](https://oreil.ly/fmY8R)用意している。これらの実装にはプラットフォーム依存はないはずだが、リファレンス・バージョンよりも多くのメモリを使用する可能性がある。これらはサブフォルダー特殊化を使用しているため、`TAGS="portable_optimized"` 引数を渡すだけで、デフォルトではなくこれらを使用するプロジェクトを生成できる。

`CMSIS-NN`のようなライブラリなど、プラットフォーム固有の実装を持つデバイスを使用していて、ターゲットを指定したときにそれらが自動的に選択されない場合は、適切なタグを渡すことで、これらの移植不可能なバージョンを使用するように選択できる。それが何であるかを発見するには、プラットフォームのドキュメントやTensorFlow Lite for Microcontrollersのソースツリーを調べる必要がある。

## 最適化された実装を自分で書く

最も時間がかかっている演算子について最適化された実装を発見できなかったり、利用可能な実装が十分に高速でない場合、自分で書きたいと思うかもしれない。良い知らせは、その作業を簡単にするために範囲を狭めることができるということだ。いくつかの異なる入出力サイズとパラメータで演算子を呼び出すだけなのだから、一般化ではなく、それらのパスを高速化することだけに集中すればいいのだ。例えば、`SparkFun Edge`ボードの音声ウェイクワード例の最初のバージョンでは、深さ方向の畳み込みリファレンスコードがほとんどの時間を占め、全体的に動作が遅すぎてユーザビリティがないことが発見された。このコードが何をやっているのか調べてみると、畳み込みフィルターの幅が常に8であることがわかった[。](https://oreil.ly/Kbx22)バイトで保持された4つの入力値と4つの重みを、32ビット整数を使って並列にフェッチすることで、一度にロードすることができた。

最適化プロセスを開始するには、前述のサブフォルダー特殊化手法を使用して、`カーネル・`ルート内に新しいディレクトリを作成する。リファレンス・カーネルの実装をそのサブフォルダーにコピーし、コードの出発点とする。正しくビルドされていることを確認するために、その`op`に関連する単体テストを実行し、それがパスしていることを確認する：

```
make -f tensorflow/lite/micro/tools/make/Makefile test_depthwise_conv_\
  test TAGS="portable_optimized"
```

その際、`op`の単体テストコードに、正しさをチェックするのではなく、演算実行にかかった時間を報告するだけの新しいテストを追加することを推奨する。このようなベンチマークを持つことで、あなたの変更が期待通りにパフォーマンスを向上させているかを検証することができる。プロファイリングでスピードのボトルネックが見つかったシナリオごとにベンチマークを用意し、その時点でオペが持っているパラメータと同じサイズやその他のパラメータをモデルに設定する必要がある（ただし、ほとんどの場合、この数値は実行遅延に影響しないため、重みと入力はランダムな値でも構わない）。ベンチマークコード自体は、この章で前述したプロファイリングメソッドのいずれかに依存する必要がある。理想的には、高精度タイマーを使用して継続時間を測定するが、そうでない場合は、少なくともLEDまたはロジック出力をトグルする。測定プロセスの粒度が大きすぎる場合は、ループ内で演算子を複数回実行し、その反復回数で割ることで実時間を測定する必要があるかもしれない。ベンチマークを作成したら、変更を加える前の遅延をメモし、それがアプリケーションのプロファイリングで見たものとほぼ一致していることを確認する。

代表的なベンチマークが利用できるようになったので、最適化の可能性を素早く反復できるようになったはずだ。最初のステップとして、初期実装の最も内側のループを発見するのが良いだろう。これは最も頻繁に実行されるコードセクションであるため、この部分を改善することは、アルゴリズムの他の部分よりも大きな影響を与えるだろう。うまくいけば、コードに目を通し、文字通り最も深くネストされた`for`-ループ（または等価性）を発見することによってこれを特定することができるはずであるが、それをコメントアウトし、ベンチマークを再度実行することによって、適切なセクションがあることを確認する価値がある。遅延が劇的に（うまくいけば50％以上）低下すれば、焦点を当てるべき適切な部分を発見したことになる。例として、[深度方向の畳み込みのリファレンス実装から](https://oreil.ly/8S4kS)このコードを取り上げる：

```
    for (int b = 0; b < batches; ++b) {
      for (int out_y = 0; out_y < output_height; ++out_y) {
        for (int out_x = 0; out_x < output_width; ++out_x) {
          for (int ic = 0; ic < input_depth; ++ic) {
            for (int m = 0; m < depth_multiplier; m++) {
              const int oc = m + ic * depth_multiplier;
              const int in_x_origin = (out_x * stride_width) - pad_width;
              const int in_y_origin = (out_y * stride_height) - pad_height;
              int32 acc = 0;
              for (int filter_y = 0; filter_y < filter_height; ++filter_y) {
                for (int filter_x = 0; filter_x < filter_width; ++filter_x) {
                  const int in_x =
                      in_x_origin + dilation_width_factor * filter_x;
                  const int in_y =
                      in_y_origin + dilation_height_factor * filter_y;
                  // If the location is outside the bounds of the input image,
                  // use zero as a default value.
                  if ((in_x >= 0) && (in_x < input_width) && (in_y >= 0) &&
                      (in_y < input_height)) {
                    int32 input_val =
                        input_data[Offset(input_shape, b, in_y, in_x, ic)];
                    int32 filter_val = filter_data[Offset(
                        filter_shape, 0, filter_y, filter_x, oc)];
                    acc += (filter_val + filter_offset) *
                           (input_val + input_offset);
                  }
                }
              }
              if (bias_data) {
                acc += bias_data[oc];
              }
              acc = DepthwiseConvRound<output_rounding>(acc, output_multiplier,
                                                        output_shift);
              acc += output_offset;
              acc = std::max(acc, output_activation_min);
              acc = std::min(acc, output_activation_max);
              output_data[Offset(output_shape, b, out_y, out_x, oc)] =
                  static_cast<uint8>(acc);
            }
          }
        }
      }
    }
```

インデントを見ただけで、正しい内部ループがこのセクションであることがわかる：

```
                  const int in_x =
                      in_x_origin + dilation_width_factor * filter_x;
                  const int in_y =
                      in_y_origin + dilation_height_factor * filter_y;
                  // If the location is outside the bounds of the input image,
                  // use zero as a default value.
                  if ((in_x >= 0) && (in_x < input_width) && (in_y >= 0) &&
                      (in_y < input_height)) {
                    int32 input_val =
                        input_data[Offset(input_shape, b, in_y, in_x, ic)];
                    int32 filter_val = filter_data[Offset(
                        filter_shape, 0, filter_y, filter_x, oc)];
                    acc += (filter_val + filter_offset) *
                           (input_val + input_offset);
                  }
```

このコードは、すべてのループの真ん中に位置するため、関数内の他の行よりも何度も実行されており、コメントアウトすることで大部分の時間がかかっていることが確認できる。行ごとのプロファイリング情報を持っている幸運な人なら、正確なセクションを発見するのにも役立つだろう。

影響の大きい部分を発見したのだから、その外側の、より重要度の低い部分にできるだけ多くの作業を移動させることが目標だ。例えば、`if` という文が途中にある。これは、内側ループの繰り返しごとに条件付きチェックを実行しなければならないことを意味するが、この部分の外側にその作業を吊り上げることで、外側ループでチェックを実行する頻度を大幅に減らすことができる。また、特定のモデルやベンチマークでは不要な条件や計算があることに気づくかもしれない。音声航跡モデルでは、拡張係数は常に1であるため、その係数を含む乗算をスキップすることができ、より多くの作業を節約できる。私たちは、このようなパラメータ固有の最適化をトップレベルでチェックし、引数が最適化に必要なものでない場合は、プレーンなリファレンス実装にフォールバックすることを推奨する。こうすることで、既知のモデルのスピードアップが可能になり、これらの基準を満たさないオペレーションがあったとしても、少なくとも正しく動作することが保証される。間違って正しさを壊してしまわないように、`op`の単体テストを頻繁に実行する価値がある。

数値処理コードを最適化する方法をすべて網羅するのは本書の範囲を超えているが、[`portable_optimized`](https://oreil.ly/tQkJm)フォルダーにあるカーネルを見れば、役に立つテクニックのいくつかを見ることができる。

## ハードウェアの利点を活かす

ここまでは、プラットフォームに依存しないポータブルな最適化についてだけ述べてきた。というのも、作業を完全に回避するためにコードを再構築することは、通常、大きな影響を与える最も簡単な方法だからだ。また、より特殊化した最適化の焦点を単純化し、絞り込むこともできる。[`SIMD`命令を](https://oreil.ly/MBxf5)持つ`Cortex-M`デバイスのようなプラットフォームを発見した場合、ニューラルネットワーク推論にかかる時間の大半を占める反復計算に大きな助けになることが多い。内部ループを書き換えるために、イントロインシックやアセンブリを使いたくなるかもしれないが、それは我慢してほしい！少なくともベンダが提供するライブラリの実装ドキュメントをチェックして、アルゴリズムの大部分を実装するのに適したものがすでに書かれていないかどうかを確認すること。もし可能なら、独自のバージョンを書くのではなく、高速フーリエ変換のような一般的なものを計算するために既存の関数を呼び出してみよう。

これらの段階を経て、プラットフォームのアセンブリ・レベルを試す時が来た。私たちが推奨するアプローチは、個々のコード行をアセンブリの機械的等価性に置き換えることから始めることで、最初はスピードアップを心配することなく、やりながら正しさを検証することができる。必要なコードが変換できたら、遅延を減らすために融合演算やその他のテクニックを試すことができる。組み込みシステムの利点は、深い命令パイプラインやキャッシュを持たない複雑なプロセッサよりも振る舞いが単純になりがちなことだ。
