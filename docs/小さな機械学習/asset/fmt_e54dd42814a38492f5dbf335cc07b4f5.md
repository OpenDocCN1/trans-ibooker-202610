
ニューラルネットワークコードを高速化する必要がある場合、最初に尋ねるべき質問は、より強力なハードウェアデバイスを使用できるかどうかである。多くの組み込み製品では、どのハードウェアプラットフォームを使用するかは非常に早い段階で決定されるか、外部で設定されていることが多いため、これは不可能であるが、ソフトウェアの観点から変更するのが最も簡単な要因であるため、明確に検討する価値がある。選択肢がある場合、最大の制約は通常、エネルギー、スピード、コストである。もし可能なら、使用しているチップを変更することで、エネルギーやコストをスピードとトレードオフしよう。研究しているうちに、他の主要な要素を失うことなく、より高速な新しいプラットフォームを発見する幸運に恵まれるかもしれない！

### 注
ニューラルネットワークを訓練する場合、訓練ステップごとに一度に大量の訓練例を送信するのが一般的だ。これにより、一度に1つのサンプルしか送信されない場合には不可能な、多くの計算最適化が可能になる。例えば、1回のトレーニング呼び出しで100枚の画像とラベルが送信されるかもしれない。このようなトレーニングデータの集合を*バッチと*呼ぶ。

組込みシステムでは通常、一度に1グループのセンサー読み取りをリアルタイムで扱うため、推論を開始する前に、より大きなバッチを収集するのを待つことはしたくない。この "シングルバッチ "フォーカスは、トレーニング側では意味のある最適化の利点が得られないことを意味する。そのため、クラウドでは有用なハードウェアアーキテクチャが、我々のユースケースには必ずしも反映されない。

# モデルの改良
ハードウェアプラットフォームを切り替えた後、ニューラルネットワークの遅延に大きな影響を与えやすいのはアーキテクチャレベルである。十分な精度を持ちながら計算回数の少ない新しいモデルを作成できれば、コードを全く変更することなく推論を高速化できる。通常、精度の低下とスピードの向上をトレードオフにすることは可能なので、最初にできる限り精度の高いモデルから始めることができれば、このようなトレードオフの余地が大きくなる。つまり、遅延最適化のような一見無関係に見えるタスクであっても、トレーニングデータの改善と拡張に時間を費やすことは、開発プロセス全体を通して非常に有益なのだ。

手続き型コードを最適化する場合、アセンブリで内部ループを書き直すよりも、コードのベースとなっている高レベルのアルゴリズムを変更することに時間を費やした方が、予算を有効に使えるのが一般的だ。モデル・アーキテクチャに注目するのも同じ考えに基づいている。作業速度を向上させるよりも、できることなら作業を完全になくした方がいい。我々のケースと違うのは、機械学習モデルを入れ替えるのは、従来のコードでアルゴリズムを入れ替えるよりもずっと簡単だということだ。十分なデータセットが集まったら、学習スクリプトでモデルを別のものに置き換えるのは比較的簡単だ。使用しているモデルから個々のレイヤーを削除して、その効果を観察する実験もできる。ニューラルネットワークは非常に優雅に劣化する傾向があるため、自由にさまざまな破壊的変更を試し、精度と遅延への影響を観察するべきだ。

## モデルの遅延を推定する
ほとんどのニューラルネットワーク・モデルは、その時間の大半を、大きな行列の乗算、またはそれに非常に近い等価性の実行に費やしている。これは、各入力値は各出力値に対して異なる重みでスケーリングされなければならないため、関係する作業は入力値の数×ネットワークの各レイヤーの出力値の数とほぼ同じになるためである。これはしばしば、ネットワークが1回の推論実行に必要とする浮動小数点演算（or `FLOPs`）の数で近似される。通常、乗加算演算（マシンコードレベルでは1命令であることが多い）は2`FLOPs`とカウントされ、8ビット以下の量子化演算を実行している場合でも、浮動小数点数はもはや関係ないにもかかわらず、`FLOPs`と呼ばれることがある。ネットワークに必要な`FLOP`数は、レイヤーごとに手作業で計算することができる。例えば、完全連結レイヤーの場合、入力ベクトルの大きさに出力ベクトルの大きさを掛け合わせた数の`FLOP`が必要となる。したがって、これらの次元が分かれば、関係する作業を把握することができる。また、[`MobileNet`の](https://arxiv.org/abs/1905.02244)ようなモデルアーキテクチャを議論・比較した論文では、通常`FLOP`の見積もりを発見することができる。

`FLOP`は、ネットワークの実行にかかる時間の大まかなメトリックとして有用である。なぜなら、他のすべての条件が同じであれば、計算回数が少ないモデルは、`FLOP`の差に比例して速く実行されるからである。例えば、1億`FLOP`を必要とするモデルは、2億`FLOP`のモデルの2倍の速さで実行される。遅延には、ソフトウェアが特定の階層化アーキテクチャに対してどれだけ最適化されているかといった他の点も影響するため、実際にはこれが完全に正しいとは言えないが、異なるネットワークアーキテクチャを評価する際の出発点としては良いだろう。また、ハードウェア・プラットフォームに期待される現実的なものを確立するのにも役立つ。あなたのチップで100万`FLOP`のモデルを100msで実行できるなら、1,000万`FLOP`を必要とする別のモデルの計算には約1秒かかると推測できるだろう。

## モデルをスピードアップさせる方法
モデルアーキテクチャ設計はまだ活発な研究分野であるため、現時点では初心者向けの良いガイドを書くのは容易ではない。最良の出発点は、効率を念頭に置いて設計された既存のモデルをいくつか発見し、変更を繰り返し実験することだ。多くのモデルには、`MobileNet`の深さ方向のチャンネル係数や、予想される入力サイズなど、必要な計算量に影響を与えるために変更できる特定のパラメータがある。他のケースでは、各レイヤーに必要な`FLOP`を見て、特に遅いものを削除したり、より高速なもの（例えば、単純な畳み込みの代わりに深さ方向の畳み込みなど）で代用してみることもできる。もし可能であれば、`FLOP`で推定するのではなく、各レイヤーをオンデバイスで実行した場合の実際の遅延を調べることも価値がある。これには、この後のセクションでコードの最適化について説明するプロファイリング・テクニックが必要になる。

### 注
モデル・アーキテクチャの設計は困難で時間がかかるが、最近では、遺伝的アルゴリズムのようなアプローチを使ってネットワーク設計を改善する[`MnasNet`の](https://arxiv.org/abs/1807.11626)ように、プロセスの自動化が進んでいる。これらはまだ人間に完全に取って代わるまでには至っていないが（出発点として既知の優れたアーキテクチャを播種したり、使用する検索空間について手作業で規則を決めたりする必要がある場合が多い）、この分野で急速な進歩が見られるだろう。

すでに[`AutoML`の](https://cloud.google.com/automl/)ようなサービスがあり、ユーザはトレーニングの細かい部分の多くを避けることができる。この傾向が続くことを期待したい。

# 量子化
ニューラルネットワークを実行するには、予測のたびに何十万、何百万もの計算が必要になる。そのような複雑な計算を行うほとんどのプログラミングは、数値精度に非常に敏感である。そうでなければ、エラーが蓄積し、使用するには不正確すぎる結果を出してしまう。ディープラーニング・モデルは違う。中間計算で数値精度が大きく損なわれても、全体として正確な最終結果を出すことができるのだ。この性質は、入力が大きくノイズに満ちているため、モデルが重要でない変動に堅牢性を持ち、重要なパターンに集中することを学習する学習プロセスの副産物のようだ。

このことが実際に意味するのは、32ビット浮動小数点演算子で演算子を操作することは、ほとんどの場合、推論に必要な精度よりも精度が高いということである。学習には重みに多くの小さな変更を加える必要があるため、トレーニングは少し厳しいが、それでも16ビット表現が広く使われている。ほとんどの推論アプリケーションは、重みと活性化値の保存にわずか8ビットを使用することで、浮動小数点等価値と見分けがつかない結果を出すことができる。多くのプラットフォームが、これらのモデルが依存する8ビット乗算・アキュムレータ命令を強力にサポートしていることを考えると、これは組込みアプリケーションにとって朗報である。

しかし、モデルを浮動小数点から8ビットに変換するのは簡単ではない。計算を効率的に行うには、8ビットの値を実数に線形変換する必要がある。重みの場合は、学習した値から各レイヤーの範囲がわかっているので、変換を行うための正しいスケーリング係数を導き出すことができるので簡単だ。しかしアクティベーションの場合は厄介だ。モデルのパラメータやアーキテクチャを見ても、各レイヤーの出力の範囲が実際にはどの程度なのかは明らかではないからだ。小さすぎる範囲を選ぶと、一部の出力が最小値や最大値でクリップされてしまうが、大きすぎると出力の精度が低くなり、全体的な結果の精度が低下する危険性がある。

量子化はまだ活発な研究テーマであり、様々な選択肢があるため、`TensorFlow`チームは過去数年にわたって様々なアプローチを試してきた。これらの実験のいくつかは、["Quantizing Deep Convolutional Networks for Efficient Inference "](https://arxiv.org/pdf/1806.08342.pdf)で見ることができる：[Raghuraman Krishnamoorthiによる "A Whitepaper "](https://arxiv.org/pdf/1806.08342.pdf)と[量子化仕様には](https://oreil.ly/toF_E)、我々の経験に基づいて現在我々が使用している推奨アプローチが記載されている。

量子化プロセスは、`TensorFlow`トレーニング環境から`TensorFlow Lite`グラフにモデルを変換するプロセスで行われるように一元化した。以前は、量子化を意識した学習スキームを推奨していたが、これは使いにくく、いくつかの追加テクニックを使用することで、エクスポート時に等価性の結果が得られることを発見した。最も簡単に使用できる量子化のタイプは、[学習後の重みの量子](https://oreil.ly/Tz9D_)化と呼ばれるものだ。これは重みを8ビットに量子化するものだが、活性化層は浮動小数点のままである。これは、モデルのファイルサイズを75%縮小し、速度面でも利点があるため有用である。活性化層の範囲に関する知識を必要としないため、実行するのが最も簡単なアプローチであるが、多くの組み込みプラットフォームには存在しない高速な浮動小数点ハードウェアを必要とする。

[トレーニング後の整数量子化は](https://oreil.ly/LDw-y)、浮動小数点計算をすることなくモデルを実行できることを意味し、本書で取り上げるユースケースには好ましいアプローチである。最も難しい点は、モデルエクスポートの過程で入力例を提供する必要があることで、典型的な画像、音声、その他のデータをグラフに通すことで、活性化層の出力の範囲を観察することができる。先に説明したように、これらの範囲を推定しなければ、これらのレイヤーを正確に量子化することはできない。過去には、トレーニング中にレンジを記録したり、実行時に推論のたびにレンジをキャプチャしたりといった他のメソッドも使ったが、これらはトレーニングが非常に複雑になったり、遅延ペナルティが課されたりといった欠点があった。

[第10章の](#ch10.html#chapter_person_detection_training)人物検出モデルのエクスポート手順を振り返ると、`converter` オブジェクトに`representative_dataset` 関数を提供していることがわかる。これは活性化範囲推定処理が必要とする入力を生成するPython関数で、人物検出モデルについては、学習データセットからいくつかのサンプル画像を読み込む。というのも、想定される入力はアプリケーションごとに変わるからだ。また、前処理の一環として入力がどのように拡大縮小され、変換されるかを見極めるのは難しいため、関数の作成には試行錯誤が必要になる。将来的には、このプロセスをより簡単にしたいと考えている。

完全に量子化されたモデルを実行することは、ほとんどすべてのプラットフォームで大きな遅延利点があるが、新しいデバイスをサポートする場合は、ハードウェアが提供する特殊化命令を利用するために、最も計算集約的な演算を最適化する必要がある可能性が高い。畳み込みネットワークに取り組む場合、[`Conv2D` の演算](https://oreil.ly/NrjSo)子と[カーネルから](https://oreil.ly/V27Q-)始めるのが良いだろう。多くのカーネルに`uint8` と`int8` のバージョンがあることに気づくだろう。`uint8` のバージョンは、量子化に対する旧アプローチの名残であり、現在では使用されていない。すべてのモデルは、`int8` のパスを使用してエクスポートする必要がある。

# 製品デザイン
遅延を最適化する方法として製品設計を考えることはないかもしれないが、実は時間を投資するのに最適な場所のひとつだ。重要なのは、スピードと精度のどちらかについて、ネットワークへの要求を緩めることができるかどうかを見極めることだ。例えば、カメラを使ってハンドジェスチャーを1秒間に何フレームも追跡したいと思うかもしれないが、実行に1秒かかるボディポーズ検出モデルがあれば、より高速なオプティカルトラッキングアルゴリズムを使って、識別された点をより高速に追跡し、より正確だが頻度の低いニューラルネットワークの結果が利用可能になった時点でそれを更新することができるかもしれない。別の例として、マイクロコントローラーに高度な音声認識をネットワーク経由でアクセスするクラウドAPIに委譲させ、一方でウェイクワード検出はローカル・デバイスで実行したままにすることもできる。より広いレベルでは、ユーザ・インタフェースに不確実性を組み込むことで、ネットワークの精度要件を緩和できるかもしれない。音声認識システムで選択されるウェイクワードは、通常のスピーチでは表示されにくい音節のシーケンスを含む短いフレーズになる傾向がある。ハンドジェスチャーシステムがあれば、すべてのシーケンスの最後に親指を立てて、コマンドが意図的なものであることを確認するよう要求できるかもしれない。

ゴールは、できる限り全体的に最高のユーザ体験を提供することである。そのため、ミスに寛容になるようにシステムの他の部分でできることがあれば、正確さとスピードやその他の改善すべき特性をトレードオフできる余地が増える。

# コードの最適化
遅延の最適化には、最初に試すべき他のアプローチがあるため、この章ではこのトピックをかなり後半に位置づけたが、従来のコードの最適化は、許容可能なパフォーマンスを達成するための重要な方法である。特に、`TensorFlow Lite for Microcontrollers`のコードは、できるだけ小さなバイナリフットプリントで、多くのモデルやシステムでうまく動作するように書かれているため、特定のモデルやプラットフォームにのみ適用される最適化があるかもしれない。ハードウェアプラットフォームや使用しているモデルのアーキテクチャを変更すると、この種の変更の多くは適用できなくなる。

## パフォーマンス・プロファイリング
コードの最適化作業の基本は、プログラムのさまざまな部分の実行時間を知ることだ。組み込みの世界では、これを把握するのは驚くほど難しいかもしれない。なぜなら、デフォルトでは単純なタイマさえ利用できないかもしれないし、たとえ利用できたとしても、必要な情報を記録して返すのは大変なことだからだ。ここでは、実装が最も簡単なものから最も厄介なものまで、我々が使用した様々なアプローチを紹介する。

### ブリンキー
ほとんどすべての組み込み開発ボードには、プログラミングから制御できるLEDが少なくとも1つ付いている。もし約0.5秒以上の時間を測定するのであれば、測定したいコードセクションの開始時にそのLEDを点灯させ、その後で無効にしてみるといい。外付けのストップウォッチを使って、10秒間に何回点滅するかを手動でカウントすれば、おおよその時間は推定できるだろう。また、コードのバージョンが異なる2つの開発ボードを並べ、点滅の頻度の比較からどちらが速いかを推定することもできる。

### ショットガンプロファイリング
アプリケーションの通常の実行にどれくらいの時間がかかっているかを大まかに把握した後、特定のコード部分にどれくらいの時間がかかっているかを見積もる最も簡単な方法は、そのコード部分をコメントアウトして、実行全体がどれくらい速くなるかを見ることである。これは*ショットガン・デバッグになぞらえてショットガン・プロファイリングと*呼ばれ、他の情報がほとんど得られないときにクラッシュを特定するためにコードの大きな塊を削除する。通常、モデルの実行コードにはデータ依存のブランチがないため、内部実装をコメントアウトすることで1つの演算子をno-opにしてもモデルの他の部分の速度には影響しないため、ニューラルネットワークのデバッグには驚くほど効果的である。

### デバッグロギング
ほとんどの場合、組み込み開発ボードからホストコンピュータにテキスト行を出力する機能があるはずなので、コードの一部が実行されていることを検出する理想的な方法に思えるかもしれない。残念ながら、開発マシンと通信すること自体が非常に時間のかかることなのだ。`Arm Cortex-M`チップの[シリアル・ワイヤー・デバッグ出力には](https://oreil.ly/SdsWk)最大500ミリ秒かかることがあり、遅延には多くの変数があるため、単純化されたログ・プロファイリング・アプローチには役に立たない。`UART`接続に基づくデバッグ・ロギングは、通常、より低コストだが、それでも理想的ではない。

### ロジックアナライザ
