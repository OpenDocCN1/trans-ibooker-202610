
### 2. この新しいファイル一式をフォルダーに解凍し、新しいフォルダーと、修正したプロジェクト・ファイルを含むフォルダーとの間で、フォルダー構造が一致していることを確認する。例えば、どちらもトップレベルに`TensorFlow`のサブフォルダーがあるはずだ。

### 3. 2つのフォルダ間でマージツールを実行する。どのツールを使うかはOSによるが、Linux、Windows、macOSで動作する[`Meld`](https://meldmerge.org/)は良い選択だ。マージ処理の複雑さは、ローカルで変更したファイルの数によるが、差分のほとんどはフレームワーク側のアップデートであることが予想されるので、通常は "accept theirs" と等価性を選択できるはずだ。

ローカルで1つか2つのファイルしか変更していない場合は、旧バージョンから変更したコードをコピーし、新しいエクスポート・プロジェクトに手動でマージする方が簡単かもしれない。

変更したコードを `Git` にチェックインして、最新のプロジェクトファイルを新しいブランチとしてインポートし、`Git` 組み込みのマージ機能を使って統合を行うという、より高度な方法もある。私たちはまだこの方法についてアドバイスできるほど高度な[`Gitマスター`](https://oreil.ly/sIe1F)ではないので、私たち自身は使ったことがない。

このプロセスと、より伝統的なコード生成アプローチとの大きな違いは、コードが多くの論理ファイルに分割されたままであり、そのパスは時間が経っても一定であることだ。一般的なコード生成では、すべてのソースを1つのファイルに連結してしまうため、順序やレイアウトの些細な変更によって過去の比較が不可能になり、マージや変更の追跡が非常に困難になる。

プロジェクトのファイルからメインのソースツリーにマージする。このメインのソースツリーは[`GitHub`](https://oreil.ly/o8Ytb)の公式リポジトリである必要はない。私たちは、メインリポジトリに修正やアップグレードのプルリクエストをもらうのが大好きだが、プロプライエタリな組み込み開発では必ずしもそうできないことも知っている。注意すべき重要な点は、開発ファイルの「信頼できる情報源」を1つにすることだ。特に複数の開発者がいる場合、プロジェクトアーカイブ内のソースファイルの異なるローカルコピーに互換性のない変更が加えられるのは簡単で、アップデートやデバッグが悪夢のようになる。社内だけであれ、社外で共有されているものであれ、複数のバージョンをチェックするのではなく、各ファイルのコピーを1つにまとめたソース管理システムを持つことを強く推奨する。

信頼できる情報源に変更を戻すには、どのファイルを変更したかを記録しておく必要がある。その情報が手元にない場合は、最初にダウンロードしたり生成したりしたプロジェクトファイルにいつでも戻って `diff` を実行し、変更点を確認できる。どのファイルが変更されたのか、あるいは新しく追加されたのかがわかったら、`Git`（あるいはその他のソース管理システム）のリポジトリに、プロジェクトファイルのパスと同じ場所にコピーすればいい。

このアプローチの唯一の例外は、`TensorFlow`リポジトリに存在しないサードパーティライブラリの一部であるファイルである。しかし、最後の手段として、変更が受け入れられない場合は、`GitHub`でプロジェクトをフォークし、プラットフォームのビルドシステムに、元のURLではなく新しいURLを指定することができる。`TensorFlow`のソースファイルだけを変更するのであれば、ローカルに変更内容を含むリポジトリができるはずだ。変更が正常に統合されたことを確認するには、`Make`を使用して`generate_projects()` を実行し、IDEとターゲットのプロジェクトに、期待どおりに更新が適用されていることを確認する必要がある。それが完了し、テストを実行して他に破壊的な変更がないことを確認したら、`TensorFlow`のフォークに変更を提出することができる。それが完了したらすぐに、最終段階として、変更を公開したい場合はプルリクエストを提出する。

# オープンソースに貢献する

`TensorFlow`への貢献者は、すでにGoogle内部よりもGoogle外部の方が多く、マイクロコントローラの作業は、他のほとんどの分野よりも共同作業に依存している。私たちはコミュニティからの協力を強く望んでおり、協力する最も重要な方法の1つがプルリクエストだ（[`Stack Overflow`](https://oreil.ly/7btPw)のような他の方法もたくさんあるが）。`GitHub`には、プルリクエストの基本を網羅した素晴らしい[`ドキュメント`](https://oreil.ly/8rDKL)があるが、`TensorFlow`で作業する際に知っておくと便利な詳細がいくつかある：

* Google内外のプロジェクトメンテナによるコードレビューがある。これは`GitHub`のコードレビューシステムで管理されているので、あなたの投稿に関するディスカッションがそこで行われることを期待してほしい。
* バグフィックスや最適化以上の変更には、通常まず設計書が必要だ。[`SIG Micro`](https://oreil.ly/JKiwD)というグループがあり、外部のコントリビューターが優先順位やロードマップの定義を手伝ってくれている。プルリクエストの背景にある文脈や動機を理解するのに役立つ。
* パブリックフォークを維持することで、メインブランチに提出する前に実験的な変更に対するフィードバックを得ることができる。
* すべてのプルリクエストに対して実行される自動テストがあり、公開されているものと、これに依存している私たち自身のプロジェクトとの統合をチェックするGoogleの内部ツールが追加されている。残念なことに、これらのテストの結果は時に解釈が難しく、さらに悪いことに、あなたの変更とは無関係な理由でテストが失敗する「flakey」なこともある。しかし、テストの失敗を理解するのに問題がある場合は、会話スレッドでメンテナに質問してほしい。
* 私たちは100％のテストカバレッジを目指しているので、もし変更が既存のテストで実施されない場合は、新しいテストをお願いすることになる。これらのテストは非常に単純なものでよい。私たちは、私たちが行うすべてのことをある程度カバーしていることを確認したいだけなのだ。
* 読みやすさのため、`TensorFlow`のコードベース全体で一貫して、`C`と`C++`のコード形式にはGoogleスタイルガイドを使用している。そのため、新しいコードや修正されたコードはすべてこのスタイルにすることを要求している。 [`clang-format`](https://oreil.ly/KkRKL)を`google` style引数とともに使用することで、コードを自動的に形式化することができる。

`TensorFlow`への貢献と、変更を提出する作業への忍耐に感謝する。それは常に簡単なことではないが、世界中の多くの開発者に変化をもたらすだろう！

# 新しいハードウェア・アクセラレータをサポートする

`TensorFlow Lite for Microcontrollers` の目標の1つは、ハードウェア開発者が設計をより速く進めるためのリファレンス・ソフトウェア・プラットフォームになることだ。私たちが観察してきたのは、機械学習で有用なことを行う新しいチップを手に入れるための作業の多くは、学習環境からin演算子を記述するような作業であり、特に量子化のようなトリッキーな詳細や、典型的な機械学習モデルに必要な「ロングテール」演算の実装に関する作業であるということだ。これらのタスクは時間がかからないため、ハードウェアの最適化には向いていない。

これらの問題に対処するため、ハードウェア開発者が最初に取るべきステップは、`TensorFlow Lite for Microcontrollers`の最適化されていないリファレンス・コードをプラットフォーム上で動作させ、正しい結果を出すことである。これによって、ハードウェアの最適化以外のすべてが機能していることが証明される。1つの課題は、チップがアクセラレーターの場合、従来のCPUではなく特殊化された機能しか持たないため、一般化`C++`コンパイルをサポートしないことだ。多くのユーザのグラフは、任意の`C++`実装でなければコンパクトに表現できない演算子を持っているからだ。また、`TensorFlow Lite for Microcontrollers`インタプリタは、サブグラフの非同期実行をサポートしないという設計上の決定も行った。これは、コードがかなり複雑になることと、組み込みの領域では（Androidの`Neural Network API`が普及しているモバイルの世界とは異なり）珍しいと思われるからだ。

つまり、`TensorFlow Lite for Microcontrollers`がサポートするアーキテクチャの種類は、従来のプロセッサと同期して動作する同期コプロセッサのように見える。アクセラレータは、そうでなければ時間がかかる計算集約的な関数を高速化するが、より柔軟な要件を持つ小規模な処理はCPUに委ねる。実際には、カーネルレベルでの個々の演算子の実装を、特殊化されたハードウェアへの呼び出しに置き換えることから始めることをお勧めする。これは、結果と入力がCPUによってアドレス指定可能な通常のメモリにあることが期待されることを意味する（後続のopsがどのプロセッサ上で実行されるかについて何の保証もないため）。また、続行する前にアクセラレータの完了を待つか、プラットフォーム固有のコードを使用してMicroフレームワーク外のスレッドに切り替える必要がある。これらの制限は、少なくとも迅速なプロトタイプ作成を可能にするはずであり、うまくいけば、インクリメント的な変更を行いつつ、それぞれの小さな変更の正しさを常にテストできる能力を提供することになる。

# ファイル形式を理解する

`TensorFlow Lite`がモデルの保存に使う形式には多くの長所があるが、残念ながらシンプルさはその1つではない。とはいえ、複雑さに気を取られる必要はない。基本的なことをいくつか理解すれば、実際に扱うのはかなり簡単だ。

[第3](#ch03.html#chapter_get_up_to_speed)章で触れたように、ニューラルネットワークモデルは入力と出力を持つ演算のグラフである。演算子への入力は、重みと呼ばれる学習値の大きな配列である場合もあれば、それ以前の演算結果やアプリケーションレイヤーから入力された入力値配列である場合もある。これらの入力は、画像ピクセル、オーディオサンプルデータ、加速度センサーの時系列データかもしれない。モデルの1パスが終了すると、最終演算子はその出力に値の配列を残し、通常は異なるカテゴリの分類予測などを表す。

モデルは通常、デスクトップ・マシンで学習されるため、携帯電話やマイコンのような他のデバイスに転送する方法が必要になる。`TensorFlow`の世界では、学習済みのモデルを`Python`から取得し、`TensorFlow Lite`ファイルとしてエクスポートできるコンバーターを使ってこれを行う。`TensorFlow`では、デスクトップ環境の機能（`Python`のコード・スニペットを実行できるとか、高度な演算子が使えるとか）に依存したモデルを作成しやすく、シンプルなプラットフォームではサポートされていないからだ。また、学習で変数となる値（重みなど）をすべて定数に変換したり、勾配バックプロパゲーションにのみ必要な演算子を削除したり、隣接する演算子を融合したり、バッチ正規化のようなコストのかかる演算子をよりコストのかからない形に折り畳んだりといった最適化も必要だ。これがさらに厄介なのは、メインラインの`TensorFlow`には800以上の演算子があり、さらに常に追加されていることだ。つまり、小さなモデル・セットのために独自のコンバータを書くのはかなり簡単だが、ユーザが`TensorFlow`で作成できる幅広いネットワークを確実に扱うのはずっと難しいということだ。新しい演算子に対応し続けるだけでもフルタイムの仕事になる。

変換プロセスで得られる`TensorFlow Lite`ファイルは、これらの問題のほとんどに悩まされていない。明確な入力と出力、重みに`凍結さ`れた変数、フュージングのような一般的なグラフ最適化がすでに適用されている。つまり、`TensorFlow Lite for Microcontrollers`を使うつもりがなくても、`Python`レイヤから独自のコンバータを書く代わりに、推論のために`TensorFlow`モデルにアクセスする方法として`TensorFlow Lite`ファイル形式を使うことを推奨する。

## フラットバッファ

シリアライゼーション・ライブラリには[`FlatBuffers`](https://oreil.ly/jfoBx)を使っている。`FlatBuffers`はパフォーマンスが重要なアプリケーション向けに設計されているので、組み込みシステムに適している。素晴らしい特徴のひとつは、実行時のメモリ内表現がシリアライゼーションされた形とまったく同じであることだ。そのため、モデルをフラッシュ・メモリに直接埋め込むことができ、パースやコピーの必要がなく、すぐにアクセスできる。このため、プロパティを読み取るために生成されるコードクラスは、間接的なレイヤーがいくつかあるため少し難しいかもしれないが、重要なデータ（重みなど）はリトルエンディアンのブロブとして直接格納され、生の`C`配列のようにアクセスすることができる。また、無駄なスペースがほとんどないため、`FlatBuffers`を使ってもサイズのペナルティはない。

`FlatBuffers`は、シリアライゼーションしたいデータ構造を定義する`スキーマ`と、そのスキーマを情報の読み取りと書き込みのためのネイティブ`C++`（または`C`、`Python`、`Java`など）コードに変換するコンパイラを使って動作する。`TensorFlow Lite`の場合、スキーマは[`tensorflow/lite/schema/schema.fbs`](https://oreil.ly/JoDE9)にあり、生成された`C++`アクセッサコードは[`tensorflow/lite/schema/schema_generated.h`](https://oreil.ly/LjxOp)にキャッシュされる。ソース管理に保存するのではなく、新しいビルドを行うたびに`C++`コードを生成することも可能だが、その場合、ビルドするプラットフォームごとに、`flatc` コンパイラとツールチェーンの他の部分を含める必要があるため、自動生成の利便性と移植の容易さを引き換えにすることにした。

形式をバイト単位で理解したい場合は、`FlatBuffers` `C++`プロジェクトの[`内部ページ`](https://oreil.ly/EBg3-)か、[`Cライブラリ`](https://oreil.ly/xXkZg)の等価性を見ることをお勧めする。しかし、ほとんどのニーズはさまざまな高級言語インタフェースで満たされるはずであり、そのような粒度で作業する必要はないだろう。形式の背後にある概念を紹介するために、スキーマと`MicroInterpreter`、モデルを読み取るコードについて説明する。具体的な例があることで、すべてが理解しやすくなることを願っている。

皮肉なことに、始めるには[`スキーマの一番`](https://oreil.ly/aHYM-)最後までスクロールする必要がある。ここには、`root_type` を`Model` と宣言している行がある：

```
root_type Model;
```

`FlatBuffers`は、ファイル内に保持される他のデータ構造のツリーのルートとなる単一のコンテナオブジェクトを必要とする。この文は、この形式のルートが`Model` になることを示している。この意味を知るために、さらに数行スクロールして`Model` の定義を見てみよう：

```
table Model {
```

これは、`Model` が`FlatBuffers`でいうところの`table` であることを物語っている。`Python`でいうところの`Dict`、`C`や`C++`でいうところの`struct` のようなものだと思えばいい（それよりも柔軟性は高いが）。オブジェクトが持つことのできるプロパティを、名前と型とともに定義している。`FlatBuffers`には、`struct` という、オブジェクトの配列に対してよりメモリ効率の良い、柔軟性の低い型もあるが、`TensorFlow Lite`では今のところ使っていない。

これが実際にどのように使われるかは、[`micro_speech` の例の`main()` 関数を](https://oreil.ly/StkFf)見ればわかる：

```
  // Map the model into a usable data structure. This doesn't involve any
  // copying or parsing, it's a very lightweight operation.
  const tflite::Model* model =
      ::tflite::GetModel(g_tiny_conv_micro_features_model_data);
```

`g_tiny_conv_micro_features_model_data` 変数は、シリアライズされた`TensorFlow Lite`モデルを含むメモリ領域へのポインタであり、`::tflite::GetModel()` への呼び出しは、実質的に、その基礎となるメモリによってバックアップされた`C++`オブジェクトを取得するためのキャストでしかない。メモリ割り当てやデータ構造のウォーキングを必要としないため、非常に迅速で効率的な呼び出しとなる。その使い方を理解するために、データ構造に対して行う次の演算子を見てみよう：
