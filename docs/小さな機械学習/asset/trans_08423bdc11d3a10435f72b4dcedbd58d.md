
# PDD

PDD 的第一个部分需要说明收集什么数据、如何收集、为什么收集。应尽可能使用具体且易懂的英语。例如，不要写“获取环境大气信息”，而应写“收集温度和湿度”。在处理这一部分时，也是思考实际收集什么内容并确认其为产品所必需的最低限度的好机会。如果只是为了听到大声唤醒更复杂的设备，真的有必要用麦克风以 16KHz 采样音频吗，或者是否可以使用更粗糙的传感器，即使发生安全违规也无法录音？本节中，一个简单的系统图有助于展示产品内不同组件（包括云 API）之间信息的流动。本节的总体目标是为非技术受众（无论是律师、管理层还是董事会成员）提供关于收集什么内容的良好概述。思考的一种方法是想象它在报纸头版上，由一位不友好的记者撰写的文章中会是什么样子。为了最大限度地减少用户因他人恶意行为而暴露的风险，要做一切可能。具體來說，請思考诸如“使用这项技术，虐待的前伴侣会干什么”之类的场景，充分发挥想象力，确保尽可能多的保护措施已内置。

## 数据使用

收集数据后怎么办？例如，许多初创公司希望利用用户数据来训练机器学习模型，但从隐私角度来看，这是一个非常危险的过程。我们强烈建议将训练数据的获取作为一个完全独立的项目来处理，而不是作为产品使用的副作用来收集数据，而是在获得明确同意后使用付费提供商。

设备端机器学习的一个优点是可以在本地处理敏感数据，仅共享汇总结果。例如，可能存在每秒捕获图像的行人计数设备，但传输的数据仅为目击到的人数和车辆数。如果可能，应设计硬件以确保这些保证不会被破坏。如果分类算法的输入仅为 224×224 像素的图像，则应使用低分辨率的摄像头传感器，使其物理上不可能识别人脸或车牌。如果像行人计数那样只打算发送几个值的摘要，则应仅支持低比特率的无线技术，即使设备被黑客攻击也无法发送源视频。将来，我们期望[专用硬件](https://oreil.ly/6E2Ya)有助于加强这些保证，但即使现在，在系统设计层面仍有很多事情可以做，以避免过度工程化并使滥用更困难。

## 数据共享与存储

谁可以访问收集到的数据？为了确保只有他们可以看到数据，实施了什么系统？数据在设备上或云端保存多长时间？如果一直保存，删除时的政策是什么？你可能会认为删除明显的用户 ID（如电子邮件地址或姓名）后保存的信息是安全的，但 ID 可以从 IP 地址、可识别的声音或步态等许多来源推导出来，因此应将收集到的所有传感器数据都视为个人身份信息（PII）。最佳做法是将此类 PII 视为放射性废物。尽可能避免收集，在需要期间严格保护，并在收集结束后尽快处置。

思考谁可以访问时，切勿忘记政府的压力可能覆盖所有许可系统，在压制性国家中可能对用户造成严重伤害。为了避免这种责任并限制用户暴露的机会，将传输或保存的内容限制在尽可能最小的范围内是另一个原因。

## 同意

使用你产品的人是否了解该产品收集了哪些信息？这里可能有一个狭隘的法律问题，你可能会认为可以通过点击式最终用户许可协议来回答，但我们建议更广泛地将其作为营销挑战来思考。你可能确信产品的优势值得以收集更多数据作为权衡。如果你在想出这样的信息时感到困难，那就是应该减少隐私影响或重新设计以增加产品优势的信号。

## PDD 的使用

PDD 应作为活文档处理，并随着产品的演进不断更新。PDD 显然有助于向律师和其他商业利益相关者传达产品的细节，但在许多其他场合也很有用。例如，应与营销团队合作，确保其信息传达准确反映你的做法，并与第三方服务提供商（如广告）合作，确认他们遵守你的承诺。由于可能存在只有在实现层面才能看到的隐藏隐私影响，因此应让团队所有工程师都能访问并添加评论。例如，使用地理编码的云 API 时，设备的 IP 地址可能会泄露，或者微控制器上配备了 WiFi 芯片，虽然未使用，但理论上可以发送敏感数据。

# 安全

确保嵌入式设备的整体安全性非常困难。攻击者可以轻松获得系统的物理所有权，并使用各种入侵技术提取信息。第一道防线是尽可能不在嵌入式系统中保留敏感信息，这也是 PDD 非常重要的原因。如果依赖与云服务的通信安全，则应考虑[安全加密处理器](https://oreil.ly/lGLzA)，以确保密钥安全保存。这些芯片也可用于安全启动，确保只有刷写的程序才能在设备上运行。

与隐私一样，应注意硬件设计以限制攻击者的机会。如果不需要 WiFi 或 Bluetooth，则制造不具备这些功能的设备。考虑不在出厂产品中提供[SWD 等调试接口](https://oreil.ly/X1I7x)，并在[Arm 平台上禁用代码读取](https://oreil.ly/ag5Vc)。这些措施即使[不完美](https://oreil.ly/R3YG-)也会增加攻击成本。

此外，关于安全和加密，应依赖已建立的库和服务。因为虽然难以发现，但容易犯下破坏系统安全的错误。嵌入式系统安全的完整挑战超出了本书范围，但应考虑创建与我们对隐私的建议类似的安全设计文档。需要涵盖你认为可能的攻击、其影响以及如何防御它们。

## 保护模型

创建机器学习模型需要大量工作，但由于它们在设备上出厂且通常以易于理解的格式存在，因此经常听到工程师担心保护自己的机器学习模型免受不诚实竞争对手的侵害。坏消息是，没有绝对的复制保护。在这种意义上，模型与其他软件相同，可能像普通机器代码一样被窃取或检查。然而，与软件一样，这个问题并没有想象中那么糟糕。就像反汇编过程型程序也无法得知真正的源代码一样，研究量化模型也无法访问学习算法或数据。此外，发现竞争对手设备上安装的模型的直接副本并在法律上证明竞争对手窃取了你的知识产权，与其他软件一样应该非常简单。

尽管如此，使轻易的攻击者难以访问你的模型仍然是有价值的。一个简单的技巧是将序列化后的模型与密钥进行 XOR 后保存到闪存中，并在复制到 RAM 使用前解密。这样，仅通过转储闪存就无法访问你的模型，但能够在运行时访问 RAM 的攻击者可以访问该模型。你可能会认为切换到从 TensorFlow Lite 的 FlatBuffer 到自己的格式就能解决问题，但权重参数本身就是大数值数组，哪些运算符按什么顺序调用只需通过调试器单步执行即可一目了然，因此这种混淆的价值非常有限。

### 注

发现模型被非法使用的有趣方法之一是在训练过程中故意植入细微缺陷，并在检查违规嫌疑时注意该缺陷。例如，训练唤醒词检测模型不仅能区分 “Hello”，还能秘密区分 “Ahoy, sailor!”。独立训练的模型对同一短语做出响应的可能性极低。该技术基于在地图、目录、词典等参考资料中加入虚构条目以便更容易发现版权侵权的旧想法。这因为了便于识别复制品而在地图上放置虚构山脉[Mountweazel](https://oreil.ly/OpY2G)的习惯而得名，被称为 *mountweazeling作为*。

# 部署

在最近的微控制器中，通过启用 OTA（Over-the-Air）更新，使能够随时修复设备上运行的代码，即使在出厂后也是非常诱人的。这会打开安全和隐私违规的广泛攻击面，因此我们强烈建议你考虑它是否对你的产品真正不可或缺。如果没有设计良好的安全启动系统或其他保护，很难确保只有你才能上传新代码。作为默认值，我们建议在设备制造后不允许任何类型的代码更新。这听起来可能很强硬，考虑到例如无法进行修复安全漏洞的更新，但在几乎所有情况下，消除攻击者代码在系统上运行的可能性对安全是有益的，而非有害。此外，由于不需要“监听”更新的协议，网络架构也会变得更简单。

这意味着在设备发布前使代码正确，特别是关于模型精度，负担会更大。我们之前谈到了单元测试和对专用测试集的整体模型精度验证等方法，但它们无法捕获所有问题。在准备发布时，我们强烈建议使用狗食式方法，即在组织内部人员监督下，在真实环境中试用设备。因为测试受制于创建者的想象力，而现实世界令人惊讶到无人能提前预测。好消息是，在遇到不期望的行为后，可以将其转变为测试用例，并在常规开发流程中处理。事实上，开发将此类测试编码为关于产品深层需求的组织记忆，可能成为最大的竞争优势之一，因为除非通过痛苦的试错，否则无法获得它。

## 从开发板到产品

将开发板上运行的应用程序转变为出厂产品的整个过程超出了本书范围，但在开发过程中仍有一些值得考虑的事情。例如，需要在像[Digi-Key](https://digikey.com)这样的网站上调查你考虑使用的微控制器的批量价格[并](https://digikey.com)确认最终目标系统符合预算。如果与开发期间使用的芯片相同，则将代码迁移到量产设备应该相当简单。因此，从编程角度来看，确保开发板与量产目标一致是主要要求。调试问题在代码部署到最终形态因子后会变得相当困难，特别是如果你遵循前面描述的步骤使平台安全，因此应尽可能推迟该步骤。

# 总结

保护用户的隐私和安全是工程师最重要的职责之一，但如何确定最佳方法并不总是明确的。本章介绍了思考和设计保护的基本流程以及更高级的安全考虑事项。现在，构建和部署嵌入式机器学习应用程序的基础已经完成，但我们知道该领域有太多内容无法在一本书中涵盖。最后一章将介绍继续学习可用的资源。
