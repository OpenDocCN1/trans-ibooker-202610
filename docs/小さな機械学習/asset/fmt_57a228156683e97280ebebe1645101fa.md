
# TensorFlow Lite Micro デバッグログ移植ガイド

```
#include "Arduino.h"

// The Arduino DUE uses a different object for the default serial port shown in
// the monitor than most other models, so make sure we pick the right one. See
// https://github.com/arduino/Arduino/issues/3088#issuecomment-406655244
#if defined(__SAM3X8E__)
#define DEBUG_SERIAL_OBJECT (SerialUSB)
#else
#define DEBUG_SERIAL_OBJECT (Serial)
#endif

// On Arduino platforms, we set up a serial port and write to it for debug
// logging.
void DebugLog(const char* s) {
  static bool is_initialized = false;
  if (!is_initialized) {
    DEBUG_SERIAL_OBJECT.begin(9600);
    // Wait for serial port to connect. Only needed for some models apparently?
    while (!DEBUG_SERIAL_OBJECT) {
    }
    is_initialized = true;
  }
  DEBUG_SERIAL_OBJECT.println(s);
}

int main(int argc, char** argv) {
  DebugLog("Hello World!\n");
}
```

これらの例はどちらもシリアル・オブジェクトを作成し、ユーザがUSB経由でマイクロコントローラーにシリアル接続し、ホスト・マシンに接続することを想定している。

移植作業における重要な最初のステップは、使用したいIDEで動作し、文字列を何らかの方法でホストコンソールに出力する、プラットフォーム用の最小限のサンプルを作成することだ。これがうまくいけば、そのコードはTensorFlow Liteのコードに追加する特殊化関数のベースになる。

## DebugLog()を実装する

[`TensorFlow/lite/micro/debug_log.cc`を](https://oreil.ly/Lka3T)見ると、最初に紹介した "hello world "の例とよく似た`DebugLog()`関数の実装があり、`stdio.h`と`fprintf()`を使って文字列をコンソールに出力している。もしあなたのプラットフォームが標準Cライブラリを完全にサポートしており、余分なバイナリ・サイズを気にしないのであれば、このデフォルト実装を使用し、このセクションの残りを無視しても構わない。しかし、残念ながら、別のアプローチを使う必要がある可能性の方が高い。

最初のステップとして、すでに存在する`DebugLog()`関数のテストを使うことにする。まず、次のコマンドラインを実行する：

```
make -f tensorflow/lite/micro/tools/make/Makefile \
  generate_micro_error_reporter_test_make_project
```

[`TensorFlow/lite/micro/tools/make/gen/linux_x86_64/prj/micro_error_reporter_test/make/`](...)（`Linux`を`osx`や`Windows`に置き換えてみてほしい）の中を見ると、`tensorflow`や`third_party`といったフォルダがあるはずだ。これらのフォルダにはC++のソースコードが含まれており、IDEやビルド・システムにドラッグしてすべてのファイルをコンパイルすれば、エラー・レポート機能をテストする実行ファイルが完成するはずだ。このコードを最初にビルドしようとすると失敗する可能性が高い。なぜなら、このコードはまだ[`debug_log.cc`の](https://oreil.ly/fDkLh)デフォルトの`DebugLog()`実装を使用しており、`stdio.h`とC標準ライブラリに依存しているからだ。この問題を回避するには、`debug_log.cc`を変更して、`#include <cstdio>`の文を削除し、`DebugLog()`の実装を何もしないものに置き換える：

```
#include "tensorflow/lite/micro/debug_log.h"

extern "C" void DebugLog(const char* s) {
  // Do nothing for now.
}
```

これを変更した状態で、ソースファイルのセットを正常にコンパイルできるようにする。それができたら、出来上がったバイナリを組み込みシステムにロードする。もし可能なら、まだ出力は見られないが、プログラムがクラッシュせずに実行されることをチェックすること。

プログラムが正しくビルドされ、実行されているように見えたら、デバッグ・ロギングが機能するかどうかを確認する。前のセクションで "hello world "プログラムに使ったコードを、`debug_log.cc`の`DebugLog()`実装に入れる。

実際のテストコードは[`tensorflow/lite/micro/micro_error_reporter_test.cc`に](https://oreil.ly/0jD00)あり、以下のようになっている：

```
int main(int argc, char** argv) {
  tflite::MicroErrorReporter micro_error_reporter;
  tflite::ErrorReporter* error_reporter = &micro_error_reporter;
  error_reporter->Report("Number: %d", 42);
  error_reporter->Report("Badly-formed format string %");
  error_reporter->Report("Another % badly-formed %% format string");
  error_reporter->Report("~~~%s~~~", "ALL TESTS PASSED");
}
```

`DebugLog()`を直接呼び出しているわけではなく、引数の変数数などを最初に処理する`ErrorReporter`インタフェースを経由しているのだが、その基礎となる実装は、今書いたコードに依存している。すべてが正しく動作していれば、デバッグ・コンソールにこのようなものが表示されるはずだ：

```
Number: 42
Badly-formed format string
Another  badly-formed  format string
~~~ALL TESTS PASSED~~~
```

これができたら、`DebugLog()`の実装をメイン・ソース・ツリーに戻したい。そのためには、以前に説明したサブフォルダーの特殊化テクニックを使うことになる。プラットフォームを識別するために使用する短い名前（大文字、スペース、その他の特殊化文字を含まない）を決める必要がある。例えば、すでにサポートしているプラットフォームには、`arduino`、`sparkfun_edge`、`linux`を使っている。このチュートリアルでは、`my_mcu`を使うことにする。`TensorFlow/lite/micro/`に、GitHubからチェックアウトしたソースコードのコピー（生成したものでもダウンロードしたものでもない）に、`my_mcu`という新しいサブフォルダーを作成することから始める。実装を含む`debug_log.cc`ファイルをその`my_mcu`フォルダにコピーし、Gitを使ってソース・トラッキングに追加する。生成したプロジェクト・ファイルをバックアップ場所にコピーし、以下のコマンドを実行する：

```
make -f tensorflow/lite/micro/tools/make/Makefile TARGET=my_mcu clean
make -f tensorflow/lite/micro/tools/make/Makefile \
  TARGET=my_mcu generate_micro_error_reporter_test_make_project
```

[`tensorflow/lite/micro/tools/make/gen/my_mcu_x86_64/prj/micro_error_reporter_test/make/tensorflow/lite/micro/`を](...)見ると、デフォルトの`debug_log.cc`はもはや存在しないが、実装は`my_mcu`サブフォルダにあることがわかるはずだ。このソースファイルのセットをIDEやビルド・システムにドラッグ・バックすると、ビルド、実行、デバッグ・コンソールへの出力に成功したプログラミングが表示されるはずだ。

## すべての目標を実行する

これで、TensorFlowのテストターゲットと実行可能ターゲットはすべて有効になった！デバッグ・ロギングの実装は、あなたが行う必要がある唯一のプラットフォーム固有の変更である。コードベースの他のすべては、`math`ライブラリを超える標準ライブラリ・リンクの必要なく、C++11をサポートするツールチェーン上でビルドして実行できるように、十分に移植性のある方法で記述する必要がある。IDEで試せるようにすべてのターゲットを作成するには、ターミナルから次のコマンドを実行する：

```
make -f tensorflow/lite/micro/tools/make/Makefile generate_projects \
  TARGET=my_mcu
```

これにより、生成されたエラーレポーターテストと同じような場所に、それぞれライブラリの異なる部分を演習する多数のフォルダが作成される。もしあなたのプラットフォームで音声ウェイクワードのサンプルを動かしたいなら、`tensorflow/lite/micro/tools/make/gen/my_mcu_x86_64/prj/micro_speech/make/`を見ればいい。

これで、`DebugLog()`が実装され、プラットフォーム上で動作するようになった。しかし、デフォルトの`audio_provider.cc`の実装は、常にゼロでいっぱいの配列を返すため、役に立つことは何もできない。正しく動作させるには、先に説明したサブフォルダー特殊化アプローチを使って、キャプチャした音を返す特殊化`audio_provider.cc`モジュールを作成する必要がある。動作するデモにこだわらないのであれば、同じサンプルコードを使って、プラットフォーム上のニューラルネットワークの推論遅延などを調べたり、他のテストを行うこともできる。

センサーやLEDのような出力デバイスのハードウェア・サポートだけでなく、あなたのプラットフォームの特殊機能を利用して、より高速に動作するバージョンのニューラルネットワーク演算子を実装したいと思うかもしれない。私たちは、このような特殊化された最適化を歓迎し、サブフォルダー特殊化テクニックが有用であることが証明された場合、それらをメイン・ソース・ツリーに統合する良い方法となることを願っている。

## Makefileビルドと統合する

多くの組み込みプログラマにとって、`Make`システムを使うよりもIDEを使う方がシンプルで馴染みがあることが多いからだ。継続的インテグレーションビルドでコードをテストしたり、特定のIDE以外でもコードを利用できるようにしたい場合は、変更を`Makefile`とより完全に統合したいかもしれない。そのために必要なことのひとつは、あなたのプラットフォーム用に一般にダウンロード可能なツールチェーンを発見することであり、SDKやその他の依存関係についても一般にダウンロードすることである。例えば、`GCC Embedded`ツールチェーンのmacOS版とLinux版をArmからダウンロードし、そのURLを[`tensorflow/lite/micro/tools/make/third_party_downloads.inc`に](https://oreil.ly/WBrIy)記載する。

そして、コンパイラーとリンカーに渡す正しいコマンドラインフラグを決定し、サブフォルダー特殊化では発見できない、追加で必要なソースファイルがあれば、その情報を[`tensorflow/lite/micro/tools/make/targets`の](https://oreil.ly/zusVM)サブ`Makefile`にエンコーディングする必要がある。もし追加クレジットが欲しければ、`Renode`のようなツールを使ってx86サーバ上でマイクロコントローラーをエミュレートする方法を考え、ビルドの確認だけでなく継続的インテグレーション中にテストを実行できるようにする。`Renode`を使って"Bluepill"バイナリをテスト実行するスクリプトの例を、[`tensorflow/lite/micro/testing/test_bluepill_binary.sh`で](https://oreil.ly/A80CN)見ることができる。

すべてのビルドセットが正しく設定されていれば、このようなものを実行して、フラッシュ可能なバイナリを生成することができるだろう（プラットフォームに応じて適切なターゲットを設定する）：

```
make -f tensorflow/lite/micro/tools/make/Makefile \
  TARGET=bluepill micro_error_reporter_test_bin
```

テストを実行するためのスクリプトと環境が正しく動作しているのであれば、これを実行してプラットフォームのテストをすべて実行することができる：

```
make -f tensorflow/lite/micro/tools/make/Makefile TARGET=bluepill test
```

# 新しいIDEやビルドシステムをサポートする

TensorFlow Lite for Microcontrollersは、`Arduino`、`Mbed`、`Keil`ツールチェーン用のスタンドアロンプロジェクトを作成できるが、組み込みエンジニアが他の多くの開発環境を使用していることも知っている。新しい環境でフレームワークを実行する必要がある場合、最初にお勧めするのは、`Make`プロジェクトを生成したときに生成される「生の」ファイルセットをIDEにインポートできるかどうかを確認することだ。この種のプロジェクトアーカイブには、サードパーティの依存関係を含め、特定のターゲットに必要なソースファイルだけが含まれている。

###### 注

数個のファイルしかないとき、生成プロジェクトにエクスポートするときに、元のソースツリーのネストしたサブフォルダ（`tensorflow/lite/micro/examples/micro_speech`のような）にそれらを保持するのは奇妙に思えるかもしれない。ディレクトリ階層をフラットにする方が理にかなっているのではないか？

深くネストしたフォルダーを維持することにした理由は、生成されたプロジェクト・ファイルを扱うときに多少不便になるとしても、メインのソース・ツリーにマージするのをできるだけ簡単にするためだ。`GitHub`からチェックアウトしたオリジナルのコードと、各プロジェクト内のコピーとのパスが常に一致していれば、変更と更新の追跡がずっと簡単になる。

この方法は、残念ながらすべてのIDEで機能するわけではない。例えば、`Arduino`ライブラリは、TensorFlowのデフォルトの`.cc`ではなく、すべてのC++ソースコードファイルの接尾辞が`.cpp`であることを要求する。また、インクルードパスを指定することもできないので、元のファイルを`Arduino`にコピーするときに、コード内のパスを変更する必要がある。このような複雑な変換をサポートするために、`Makefile`のビルドにいくつかの規則とスクリプトを用意した。[`generate_microlite_projects()`](https://oreil.ly/YYoHm)を呼び出し、各IDE用に特殊化し、さらに[規則](https://oreil.ly/KHo7G)、[Pythonスクリプト](https://oreil.ly/BKLhn)、[テンプレートファイルに](https://oreil.ly/tDFhh)依存して最終的な出力を作成している。自分のIDEで同じようなことをする必要がある場合は、`Makefile`を使って同じような機能を追加する必要がある。

# プロジェクトとリポジトリ間でコード変更を統合する

コード生成システムの最大の欠点のひとつは、ソースの複数のコピーが異なる場所に散在することになり、コードの更新に対処するのが非常に厄介になることだ。変更のマージにかかるコストを最小限に抑えるために、私たちはいくつかの慣例と推奨手順を採用している。最も一般的なユースケースは、プロジェクトのローカルコピー内のファイルに変更を加えた後、TensorFlow Liteフレームワークの新しいバージョンにアップデートして、追加機能やバグフィックスを入手したい場合だ。ここでは、そのような場合の対処法を提案する：

1. あなたのIDEとターゲット用にプロジェクトファイルのビルド済みアーカイブをダウンロードするか、興味のあるフレームワークのバージョンを使って`Makefile`から手動でプロジェクトファイルを生成する。
