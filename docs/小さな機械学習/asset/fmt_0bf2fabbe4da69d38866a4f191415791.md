
TensorFlow Liteは、モバイル開発者に広く採用されているが、そのエンジニアリングのトレードオフは、すべてのプラットフォームの要件を満たしていなかった。チームは、組み込みプラットフォームで構築される機械学習から利点を得ることができるGoogleや外部の製品が多く存在し、既存のTensorFlow Liteライブラリでは適合しないことに気づいた。ここでも最大の制約はバイナリサイズだった。これらの環境では、数百キロバイトでも大きすぎる。20キロバイト以内に収まるものが必要だった。C標準ライブラリーのような、モバイル開発者が当たり前のように使っている依存関係の多くも存在しないため、これらのライブラリに依存するコードは使用できなかった。しかし、多くの要件は非常に似ていた。推論が主なユースケースであり、量子化されたネットワークがパフォーマンスにとって重要であり、開発者が探索し修正するのに十分シンプルなコードベースを持つことが優先事項だった。

このようなニーズを念頭に、2018年、Googleのチーム（本書の著者を含む）は、このような組み込みプラットフォームに特化したTensorFlow Liteの実験を開始した。その目標は、組み込み環境の厳しい要件を満たしながら、モバイルプロジェクトのコード、ツール、ドキュメントをできるだけ再利用することだった。Googleが実用的なものを構築していることを確認するため、チームは、商用音声インタフェースの「Hey Google」や「Alexa」の例と同様に、話し言葉の「ウェイクワード」を認識するという実際のユースケースに焦点を当てた。Googleは、この問題に取り組む方法のエンドツーエンドの例を目指し、私たちが設計したシステムが本番システムでユーザビリティを確保できるよう取り組んだ。

## 必要条件

Googleチームは、組み込み環境での動作がコードの記述方法に多くの制約を課すことを知っていたため、ライブラリの主要要件をいくつか特定した：

### オペレーティングシステムに依存しない

機械学習モデルは基本的に数学的ブラックボックスであり、数字が入力され、結果として数字が返される。これらの演算子を実行するためにシステムの他の部分へのアクセスは必要ないはずなので、基盤となるオペレーティングシステムへの呼び出しなしで機械学習フレームワークを書くことは可能だ。対象となるプラットフォームの中にはOSを全く持たないものもあり、基本コードでファイルやデバイスへの参照を避けることで、それらのチップへの移植が可能になった。

### リンカ時に標準CまたはC++ライブラリに依存しない

これはOSの要件と比べると少し微妙だが、チームがデプロイを目指したのは、プログラミングを保存するメモリが数十キロバイトしかないようなデバイスだったため、バイナリのサイズは非常に重要だった。`sprintf()` のような一見単純な関数でさえ、それだけで20KBを簡単に使ってしまうため、チームはCやC++の標準ライブラリの実装を保持するライブラリ・アーカイブから引っ張ってこなければならないものは避けることを目指した。ヘッダのみの依存関係（データ型のサイズを保持する `stdint.h` など）と、標準ライブラリのリンカ時間部分（文字列関数の多くや `sprintf()` ）との境界が明確に定義されていないため、これは厄介だった。実際には、一般的にコンパイル時の定数やマクロは問題ないが、それ以上複雑なものは避けるべきだということを理解するために、チームは常識を働かせる必要があった。このリンカー回避の1つの例外は、標準C `math` ライブラリで、三角関数のようなリンクが必要なもののために利用されている。

### 浮動小数点ハードウェアは期待されていない

多くの組み込みプラットフォームはハードウェアで浮動小数点演算をサポートしていないため、コードではパフォーマンスを重視する浮動小数点演算の使用を避ける必要があった。つまり、8ビット整数のパラメータを持つモデルに集中し、演算子には8ビット演算子を使うということだ（ただし、互換性を保つために、フレームワークは必要であれば浮動小数点演算子もサポートしている）。

### 動的メモリ割り当てがない

マイクロコントローラーを使用するアプリケーションの多くは、数ヶ月から数年にわたり継続的に実行する必要がある。プログラムのメインループが、`malloc()`/`new` と `free()`/`delete` を使ってメモリの割り当てと解放を行っている場合、ヒープが最終的に断片化された状態になり、割り当ての失敗やクラッシュを引き起こさないことを保証するのは非常に難しい。また、ほとんどの組込みシステムでは利用可能なメモリが非常に少ないため、この限られたリソースを前もって計画することは他のプラットフォームよりも重要であり、OSがなければヒープやアロケーションルーチンすら存在しないかもしれない。このため、組み込みアプリケーションは動的メモリ割り当ての使用を 完全に避けることが多い。ライブラリはそのようなアプリケーションに使用されるように設計されているため、同じようにする必要がある。実際には、フレームワークは呼び出し元のアプリケーションに、初期化時にフレームワークが一時的な割り当て（アクティブ化バッファのような）に使用できる小さな固定サイズのアリーナを渡すように要求する。アリーナが小さすぎる場合、ライブラリは即座にエラーを返し、クライアントはより大きなアリーナで再コンパイルする必要がある。そうでなければ、推論を実行するための呼び出しは、それ以上メモリーを確保することなく行われるので、ヒープの断片化やメモリー・エラーのリスクを負うことなく、繰り返し行うことができる。

チームはまた、組み込みコミュニティで一般的な他の制約についても、コードの共有やモバイルTensorFlow Liteとの互換性の維持が難しくなりすぎるため、反対することにした。そのためだ：

### C++11が必要である

組み込みプログラミングはCで書くのが一般的で、プラットフォームによっては、C++をサポートするツールチェーンがまったくなかったり、2011年の標準改訂版よりも旧バージョンをサポートしていなかったりする。TensorFlow Liteは、ほとんどがC++で書かれており、いくつかのプレーンなC APIを備えているため、他の言語からの呼び出しが容易になっている。複雑なテンプレートのような高度な機能には頼っていない。そのスタイルは、コードのモジュール化を助けるクラスを備えた「より良いC」の精神に則っている。C言語でフレームワークを書き直すことは、モバイルプラットフォームのユーザにとって多くの労力を要し、一歩後退することになる。我々が最も人気のあるプラットフォームを調査したところ、それらはすべてすでにC++11をサポートしていたため、チームは古いデバイスのサポートと、TensorFlow Liteのすべてのフレーバーでコードを共有しやすくすることを交換することにした。

### 32ビットプロセッサーを想定している

組み込みの世界では、膨大な数の異なるハードウェア・プラットフォームが利用可能だが、近年のトレンドは、以前は一般的だった16ビットや8ビットのチップではなく、32ビット・プロセッサに向かっている。エコシステムを調査した結果、Googleは新しい32ビット・デバイスに開発を集中させることにした。その理由は、C言語の `int` データ型が32ビットであるというような前提が、フレームワークのモバイル版と組み込み版で同じに保たれるからだ。いくつかの16ビットプラットフォームへの移植に成功したという報告もあるが、それらは制限を補う最新のツールチェーンに依存しており、私たちの主な優先事項ではない。

## なぜモデルはインタプリタなのか？

よく出てくる質問のひとつに、なぜモデルからコードを生成するのではなく、実行時にモデルをインタプリタすることにしたのか、というものがある。この決断を説明するには、さまざまなアプローチの利点と問題点を明らかにする必要がある。

コード生成では、モデルを直接CまたはC++コードに変換する。コードでは、すべてのパラメータがデータストアとして格納され、アーキテクチャは、1つのレイヤーから次のレイヤーにアクティベーションを渡す一連の関数呼び出しとして表現される。このコードは多くの場合、少数のエントリ点を持つ1つの大きなソースファイルに出力される。このファイルは、IDEやツールチェーンに直接取り込むことができ、他のコードと同じようにコンパイルすることができる。以下に、コード生成の主な利点をいくつか挙げる：

### 建築の容易さ

ユーザは、ビルド・システムへの統合がいかに簡単であるかが、一番の利点であると語ってくれた。外部ライブラリに依存することなく、数個のCまたはC++ファイルさえあれば、ほとんどのIDEにドラッグ＆ドロップするだけで、簡単にプロジェクトをビルドすることができる。

### 修正可能性

少なくとも、どんな実装が使われているのかさえ最初に確認する必要がある大規模なライブラリーに比べれば。

### インライン・データ

モデル自体のデータは実装ソースコードの一部としてストアできるので、追加ファイルは必要ない。また、インメモリデータ構造として直接ストアすることもできるため、ロードや解析のステップも必要ない。

### コードサイズ

事前にどのようなモデルやプラットフォーム向けに作っているかがわかっていれば、呼び出されることのないコードを含めずに済むので、プログラムセグメントのサイズを最小限に抑えることができる。

モデルのインタプリタは異なるアプローチで、モデルを定義するデータ構造をロードすることに依存している。実行されるコードは静的で、モデルのデータだけが変化し、モデル内の情報によって、どの演算子が実行され、パラメータがどこから引き出されるかが制御される。これはPythonのようなインタプリタ言語でスクリプトを実行するようなもので、コード生成はC言語のような伝統的なコンパイル言語に近いと言える：

### アップグレード可能性

ローカルで生成されたコードを修正したが、新しい機能や最適化を得るためにフレームワーク全体の新しいバージョンにアップグレードしたい場合はどうなるのか？手動で変更をローカルファイルにチェリーピックするか、完全に再生成してローカルの変更をパッチで戻す必要がある。

### 複数のモデル

一度に複数のモデルをコード生成でサポートするのは、多くのソースを重複させなければ難しい。

### モデルを置き換える

各モデルは、プログラム内のソースコードとデータ配列の混合式で表現されるため、プログラム全体を再コンパイルすることなくモデルを変更することは難しい。

チームが気づいたのは、私たちが*プロジェクト・ジェネレーションと*呼んでいるものを使えば、コード・ジェネレーションの利点の多くを、欠点を負うことなく得ることが可能だということだった。

## プロジェクト・ジェネレーション

TensorFlow Liteでは、プロジェクト生成は、特定のモデルをビルドするために必要なソースファイルのコピーを作成するプロセスである。これはコード生成の利点のほとんどを保持しているが、いくつかの主な利点がある：

### アップグレード可能性

すべてのソースファイルは、メインのTensorFlow Liteコードベースからのオリジナルのコピーに過ぎず、フォルダ階層内の同じ場所に表示される。そのため、ローカルで修正を加えても、オリジナルのソースに簡単に戻すことができ、ライブラリのアップグレードは、標準のマージツールを使って簡単にマージできる。

### 複数モデルと交換モデル

基礎となるコードはインタプリタなので、再コンパイルすることなく、複数のモデルを持ったり、データファイルを簡単に入れ替えたりすることができる。

### インライン・データ

また、`FlatBuffers` シリアライゼーション形式を使用することで、アンパックやパースの必要がなく、この表現をメモリ内で直接使用することができる。

### 外部依存

プロジェクトのビルドに必要なヘッダファイルやソースファイルはすべて、通常のTensorFlowコードと一緒にフォルダにコピーされるため、依存関係を別途ダウンロードしたりインストールしたりする必要はない。

自動的にもたらされない最大の利点は、コードサイズである。インタプリタ構造によって、呼び出されることのないコードパスを見つけることが難しくなるからだ。TensorFlow Liteでは、`OpResolver` メカニズムを手動で使用して、アプリケーションで使用するカーネル実装のみを登録することで、この問題に対処している。

## ビルド・システム

TensorFlow Liteは、もともとLinux環境で開発された。そのため、我々のツールの多くは、シェルスクリプト、`Make`、`Python`のような伝統的なUnixツールに基づいている。しかし、組込み開発者にとっては一般的な組み合わせではないことは承知しているので、他のプラットフォームやコンパイルツールチェーンを一流の市民としてサポートすることを目指している。

その方法は、前述のプロジェクト生成だ。GitHubからTensorFlowのソースコードを入手すれば、Linux上で標準的な`Makefile`のアプローチを使って、多くのプラットフォーム用にビルドすることができる。例えば、このコマンド行でx86バージョンのライブラリをコンパイルし、テストすることができる：

```
make -f tensorflow/lite/micro/tools/make/Makefile test
```

SparkFun Edgeプラットフォームの音声ウェイクワードの例のように、次のようなコマンドで特定のターゲットを構築することができる：

```
make -f tensorflow/lite/micro/tools/make/Makefile \
  TARGET="sparkfun_edge" micro_speech_bin
```

Windowsマシンを使っている場合や、`Keil`、`Mbed`、`Arduino`、その他の特殊化ビルド・システムなどのIDEを使いたい場合はどうすればいいのだろう？そこでプロジェクト生成の出番だ。Linuxから以下のコマンドラインを実行すれば、`Mbed` IDEですぐに使えるフォルダを生成できる：

```
make -f tensorflow/lite/micro/tools/make/Makefile \
  TARGET="disco_f746ng" generate_micro_speech_mbed_project
```

これで、`TensorFlow/lite/micro/tools/make/gen/disco_f746ng_x86_64/prj/micro_speech/mbed/`に、`Mbed`環境でビルドするために必要な依存関係やプロジェクトファイルとともに、ソースファイルのセットが表示されるはずだ。同じアプローチが`Keil`や`Arduino`にも有効で、プロジェクトのメタ情報なしでソースファイルのフォルダ階層を出力するだけの汎用バージョンもある（ただし、いくつかのビルド規則を定義したVisual Studio Codeファイルが含まれている）。

このLinuxのコマンドラインアプローチが、他のプラットフォームの人たちにどのように役立っているのか不思議に思うかもしれない。私たちは、継続的インテグレーションワークフローの一環として、またメジャーリリースを行うたびに、このプロジェクト生成プロセスを自動的に実行している。このプロセスが実行されるたびに、出来上がったファイルは自動的に公開ウェブサーバにアップされる。つまり、すべてのプラットフォームのユーザは、自分の好みのIDE用のバージョンを発見し、GitHubを経由する代わりに、自己完結型のフォルダとしてプロジェクトをダウンロードできるはずだ。

## 特殊化コード

コード生成の利点のひとつは、特定のプラットフォームでうまく動作するようにライブラリの一部を書き換えたり、ユースケースで一般的だとわかっている特定のパラメータ・セットに対して関数を最適化したりすることが簡単にできることだ。私たちは、このような変更のしやすさを失いたくなかったが、より一般的に有用な変更がメインフレームワークのソースコードにマージされるのをできるだけ簡単にしたかった。さらに、ビルド環境によっては、コンパイル時にカスタム `#define` マクロを簡単に渡すことができないという制約もあった。そのため、マクロガードを使ったコンパイル時の異なる実装への切り替えに頼ることはできなかった。

この問題を解決するために、私たちはライブラリを小さなモジュールに分割した。各モジュールは、デフォルトバージョンの機能を実装した単一のC++ファイルと、他のコードがモジュールを使用するために呼び出すことができるインタフェースを定義したC++ヘッダを持つ。そして、あるモジュールの特殊化バージョンを書きたい場合は、新しいバージョンをオリジナルと同じ名前のC++実装ファイルとして、オリジナルがあるディレクトリのサブフォルダーに保存するという慣例を採用した。このサブフォルダーには、特殊化するプラットフォームや機能の名前を付けておく（[図13-1](#ch13.html#specialize_screenshot)参照）。そして、そのプラットフォームや機能のためにビルドするときに、`Makefile`や生成されたプロジェクトが、元の実装の代わりに自動的に使用するようにする。かなり複雑に聞こえるかもしれないので、具体的な例をいくつか見ていこう。

音声ウェイクワードのサンプル・コードでは、マイクから音声データを取得する必要があるが、残念ながらクロスプラットフォームで音声を取得する方法はない。少なくとも幅広いデバイスでコンパイルする必要があるため、マイクを使わず、ゼロ値でいっぱいのバッファを返すだけのデフォルト実装を書いた。[`audio_provider.h`から](https://oreil.ly/J5N0N)、そのモジュールへのインタフェースを以下に示す：
