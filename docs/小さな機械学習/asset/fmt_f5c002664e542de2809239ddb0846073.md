関数を使って、異なるIDE用のスタンドアローン・プロジェクトを生成することができる。[`generate_microlite_projects()`](https://oreil.ly/iv94T)関数を使う。これはソース・ファイルとフラグのリストを受け取り、必要なファイルを新しいフォルダにコピーし、ビルド・システムが必要とする追加プロジェクト・ファイルも一緒にコピーする。IDEによってはこれは非常に簡単だが、例えば`Arduino`の場合、すべての`*.cc`ファイルを`*.cpp`にリネームし、コピーされるソースファイルのインクルードパスを変更する必要がある。

組み込みArmプロセッサ用のC++ツールチェーンなどの外部ライブラリは、`Makefile`のビルドプロセスの一部として自動的にダウンロードされる。これは[`add_third_party_download`](https://oreil.ly/E9tS-)規則が必要なライブラリごとに呼び出され、URLとMD5の合計が渡され、アーカイブが正しいかどうかチェックされるからだ。これらは`ZIP`、`GZIP`、`BZ2`、または`TAR`ファイルであることが期待され、ファイル拡張子に応じて適切なアンパッカーが呼び出される。ビルドターゲットでヘッダやソースファイルが必要な場合は、生成されるプロジェクトにコピーできるように、`Makefile`のファイルリストに明示的に含める必要がある。ヘッダの場合、インクルードパスを設定するだけで、インクルードされたファイルを明示的に記述しなくても `Makefile` のコンパイルがうまくいくので、これを忘れがちだが、生成されたプロジェクトはビルドに失敗する。また、外部ライブラリのコピーが適切な帰属を保持するように、ライセンスファイルがファイルリストに含まれていることを確認する必要がある。

# 筆記試験

TensorFlowは、すべてのコードに対して単体テストを持つことを目指しており、すでに[第5](#ch05.html#chapter_building_an_application)章でこれらのテストのいくつかを詳細に述べた。テストは通常、`_test.cc`ファイルとして、テスト対象のモジュールと同じフォルダに、元のソースファイルと同じ接頭辞で配置される。例えば、深度方向の畳み込み演算の実装は、[`tensorflow/lite/micro/kernels/depthwise_conv_test.cc`で](https://oreil.ly/eIiRO)テストされる。新しいソース・ファイルを追加する場合、その変更をメイン・ツリーに戻したいのであれば、それを実行する単体テストを追加しなければならない。これは、私たちが多くの異なるプラットフォームやモデルをサポートする必要があり、多くの人が私たちのコードの上に複雑なシステムを構築しているため、私たちのコアコンポーネントが正しいかどうかをチェックできることが重要だからだ。

`Tensorflow/tensorFlow/lite/experimental/micro`の直接のサブフォルダにファイルを追加する場合、`<something>_test.cc`という名前を付ければ、自動的にピックアップされるはずだ。サンプルの中でモジュールをテストする場合は、`microlite_test` `Makefile`ヘルパー関数を明示的に呼び出す必要がある[：](https://oreil.ly/wkYgu)

```
# Tests the feature provider module using the mock audio provider.
$(eval $(call microlite_test,feature_provider_mock_test,\
$(FEATURE_PROVIDER_MOCK_TEST_SRCS),$(FEATURE_PROVIDER_MOCK_TEST_HDRS)))
```

テスト自体はマイクロコントローラー上で実行する必要があるため、動的メモリ割り当て、OSや外部ライブラリ依存の回避など、フレームワークが満足させようとするのと同じ制約に従わなければならない。残念ながら、これは[`Google Test`](https://oreil.ly/GZWdj)のような一般的な単体テストシステムは受け入れられないことを意味する。その代わりに、私たちは、[`micro_test.h`](https://oreil.ly/GcIbP)ヘッダで定義・実装された、非常に最小限のテスト・フレームワークを独自に書いた。

使用するには、ヘッダを含む`*.cc`ファイルを作成する。新しい行に`TF_LITE_MICRO_TESTS_BEGIN` を定義してから、一連のテスト関数を定義し、それぞれに`TF_LITE_MICRO_TEST()` マクロを定義する。各テストの内部では、`TF_LITE_MICRO_EXPECT_EQ()` のようなマクロを呼び出し、テストされる関数から期待される結果をアサートする。すべてのテスト関数のエンドツーエンドテストでは、`TF_LITE_MICRO_TESTS_END` が必要になる。以下に基本的な例を示す：

```
#include "tensorflow/lite/micro/testing/micro_test.h"

TF_LITE_MICRO_TESTS_BEGIN

TF_LITE_MICRO_TEST(SomeTest) {
  TF_LITE_LOG_EXPECT_EQ(true, true);
}

TF_LITE_MICRO_TESTS_END
```

これをあなたのプラットフォーム用にコンパイルすれば、実行可能な通常のバイナリが得られるはずだ。これを実行すると、このようなログ情報が`stderr` （または、あなたのプラットフォームで`ErrorReporter` によって利用可能で書き込まれる等価性）に出力される：

```
----------------------------------------------------------------------------
Testing SomeTest
1/1 tests passed
~~~ALL TESTS PASSED~~~
----------------------------------------------------------------------------
```

これは人間が読めるように設計されているので、テストを手動で実行するだけでよい。しかし、文字列`~~~ALL TESTS PASSED~~~` は、実際にすべてのテストがパスした場合にのみ表示される。これにより、出力ログをスキャンして魔法の値を探すことで、自動テストシステムと統合することが可能になる。このようにして、マイクロコントローラー上でテストを実行することができる。デバッグ・ログの接続がある限り、ホストはバイナリをフラッシュし、出力ログを監視して、テストが成功したかどうかを示す期待される文字列が表示されるようにすることができる。

# 新しいハードウェアプラットフォームをサポートする

TensorFlow Lite for Microcontrollersプロジェクトの主な目標の1つは、さまざまなデバイス、オペレーティングシステム、アーキテクチャで機械学習モデルを簡単に実行できるようにすることだ。コア・コードは可能な限りポータブルになるように設計されており、ビルド・システムは新しい環境を簡単に立ち上げられるように書かれている。このセクションでは、TensorFlow Lite for Microcontrollersを新しいプラットフォームで動作させるためのステップバイステップのガイドを紹介する。

## ログに印刷する

TensorFlow Liteが絶対に必要とする唯一のプラットフォーム依存は、外部から、通常はデスクトップ・ホスト・マシンから検査できるログに文字列を出力する機能だ。これは、テストが正常に実行されたかどうかを確認したり、実行しているプログラムの内部で何が起きているかを一般化したりするためだ。これは難しい要求であるため、プラットフォームで最初に行う必要があるのは、どのようなロギング機能が利用可能かを判断し、それを行使するために何かを出力する小さなプログラムを書くことである。

Linuxや他のほとんどのデスクトップオペレーティングシステムでは、これは多くのC言語トレーニングカリキュラムの冒頭を飾る典型的な "hello world "の例となる。これは通常、次のようなものだ：

```
#include <stdio.h>

int main(int argc, char** argv) {
  fprintf(stderr, "Hello World!\n");
}
```

Linux、macOS、Windows上でこれをコンパイル・ビルドし、実行ファイルをコマンドラインから実行すると、ターミナルに "Hello World!"と出力されるはずだ。高度なOSが動作していればマイクロコントローラーでも動作するかもしれないが、組み込みシステムにはディスプレイやターミナル自体がないため、少なくともテキストそのものが表示される場所を特定する必要がある。通常、コンパイル時に`fprintf()` がサポートされていたとしても、ログを見るにはUSBか他のデバッグ接続でデスクトップマシンに接続する必要がある。

マイクロコントローラーの観点から見ると、このコードにはいくつか厄介な部分がある。その1つは、`stdio.h`ライブラリーは関数をリンクする必要があり、その中にはかなり大きなものもあるため、小さなデバイスで利用できるリソース以上にバイナリーサイズが大きくなる可能性があることだ。このライブラリはまた、動的メモリ割り当てや文字列関数のような、通常のC標準ライブラリ機能がすべて利用可能であることを前提としている。そして、組み込みシステム上で`stderr` がどこに行くべきかについての自然な定義がないため、APIが不明確である。

その代わりに、ほとんどのプラットフォームは独自のデバッグログインタフェースを定義している。これらがどのように呼び出されるかは、多くの場合、ホストとマイクロコントローラ間でどのような接続が使用されているか、ハードウェアアーキテクチャや組み込みシステム上で実行されているOS（もしあれば）に依存する。例えば、Arm Cortex-Mマイコンは[`セミホスト`](https://oreil.ly/LmC4k)をサポートしている。[`セミホスト`](https://oreil.ly/LmC4k)は、開発プロセス中にホストとターゲットシステム間で通信するための標準規格である。ホストマシンから[`OpenOCD`](https://oreil.ly/lSn0n)のような接続を使用する場合、マイコンからシステムコールを呼び出す。[`SYS_WRITE0`](https://oreil.ly/6IyrK)システムコールをマイコンから呼び出すと、`OpenOCD` 端末にレジスタ 1 のゼロ終端の文字列引数が表示される。この場合、同等の「hello world」プログラムのコードは次のようになる：

```
void DebugLog(const char* s) {
  asm("mov r0, #0x04\n"  // SYS_WRITE0
      "mov r1, %[str]\n"
      "bkpt #0xAB\n"
      :
      : [ str ] "r"(s)
      : "r0", "r1");
}

int main(int argc, char** argv) {
  DebugLog("Hello World!\n");
}
```

ここでのアセンブリの必要性は、このソリューションがいかにプラットフォームに特化したものであるかを示しているが、外部ライブラリ（たとえ標準のCライブラリであっても）を持ち込む必要はまったくない。

正確な方法はプラットフォームによって大きく異なるが、一般的な方法のひとつは、ホストへのシリアルUART接続を使うことだ。ここでは`Mbed`での方法を紹介する：

```
#include <mbed.h>

// On mbed platforms, we set up a serial port and write to it for debug logging.
void DebugLog(const char* s) {
  static Serial pc(USBTX, USBRX);
  pc.printf("%s", s);
}

int main(int argc, char** argv) {
  DebugLog("Hello World!\n");
}
```

そしてこちらは`Arduino`用の少し複雑な例だ：
