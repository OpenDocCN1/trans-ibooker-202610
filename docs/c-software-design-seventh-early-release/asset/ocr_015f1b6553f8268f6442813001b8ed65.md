+   - *Command*: if you ever want to abstract from different kinds of operations, possibly undoable operations, then you should utilize the *Command* design pattern.
+   - *Observer*: if you ever need to observe state change in some entities, it is time to choose the observer design pattern.
+   - *Adapter*: if you ever want to adapt one interface to another one, non-intrusively, i.e. without changing code, you should recall the *Adapter* design pattern.
+   - *CRTP*: if you ever want a static abstraction, free of virtual functions (and you cannot employ C++20 concepts yet), then it is time to apply the *CRTP* design pattern. *CRTP* might also prove to be useful to create compile time mixin classes.
+   - *Bridge*: if you ever need to hide implementation details and reduce physical dependencies, you should make use of the *Bridge* design pattern.
+   - *Prototype*: if you ever want to create a virtual copy, then the *Prototype* design pattern is the right choice.
+   - *External Polymorphism*: if you ever want to promote loose coupling by adding polymorphic behavior externally, then make sure to remember the *External Polymorphism* design pattern.
+   - *Type Erasure*: if you ever need the power of *External Polymorphism* in combination with the advantages of *value semantics*, consider the *Type Erasure* design pattern.
+   - *Decorator*: if you ever want to non-intrusively add responsibilities to an object, then opt for the benefits of the *Decorator* design pattern.
