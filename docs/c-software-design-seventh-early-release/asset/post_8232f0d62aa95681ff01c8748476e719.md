And C++ is a wonderful language to use for that purpose, as C++ takes *value semantics* seriously: it allows you, the developer, to live a happy life in the realm of *value semantics*. Surprisingly, as we have seen with `std::variant` and *Type Erasure*, this philosophy does not necessarily have a negative performance impact, but may even increase performance.

In addition to these general pieces of advice about software design, you have gained insight into the purpose of design patterns. Now you know what a design pattern is.

A design pattern ...

- ... has a name;
- ... carries an intent;
- ... introduces an abstraction;
- ... has been proven.

Equipped with this information you will no longer fall for false claims about some implementation detail being a design pattern (as I have been confronted with multiple times in my career), as for instance the claim that smart pointers (`std::unique_ptr`, `std::shared_ptr`, etc.) or factory functions such as `std::make_unique()` are implementations of design patterns. Also, you are now familiar with several of the most important and useful design patterns, which will prove to be useful again and again:

- *Visitor*: if you ever need to extend operations on a closed set of types, reach for the *Visitor* design pattern (possibly realized by means of `std::variant`).
- *Strategy*: if you ever want to configure the behavior and want to “inject” it from outside, you should pick the *Strategy* design pattern (aka *Policy-Based Design*).

- *Command*: if you ever want to abstract from different kinds of operations, possibly undoable operations, then you should utilize the *Command* design pattern.
- *Observer*: if you ever need to observe state change in some entities, it is time to choose the observer design pattern.
- *Adapter*: if you ever want to adapt one interface to another one, non-intrusively, i.e. without changing code, you should recall the *Adapter* design pattern.
- *CRTP*: if you ever want a static abstraction, free of virtual functions (and you cannot employ C++20 concepts yet), then it is time to apply the *CRTP* design pattern. *CRTP* might also prove to be useful to create compile time mixin classes.
- *Bridge*: if you ever need to hide implementation details and reduce physical dependencies, you should make use of the *Bridge* design pattern.
- *Prototype*: if you ever want to create a virtual copy, then the *Prototype* design pattern is the right choice.
- *External Polymorphism*: if you ever want to promote loose coupling by adding polymorphic behavior externally, then make sure to remember the *External Polymorphism* design pattern.
- *Type Erasure*: if you ever need the power of *External Polymorphism* in combination with the advantages of *value semantics*, consider the *Type Erasure* design pattern.
- *Decorator*: if you ever want to non-intrusively add responsibilities to an object, then opt for the benefits of the *Decorator* design pattern.

However, there are more design patterns. Many more! Also a lot of important and useful design patterns. Therefore you should continue to learn about design patterns. And there are two ways to do that. One is getting to know more patterns: learn about their intent and about their

similarities and differences compared to other design patterns. Also, do not forget that design patterns are about a dependency structure, not about implementation details. Second, you should also get a better understanding about each one of them, experience their advantages and shortcomings. For that purpose you should also keep an eye out for design patterns used in the code bases you work on. I promise you, you will find many of them: any attempt to manage and reduce dependencies is very likely proof of a design pattern. So yes: design patterns are everywhere!

## GUIDELINE 39: CONTINUE TO LEARN ABOUT DESIGN PATTERNS

- Get to know more design patterns and understand their intent;
- Learn more about the advantages and disadvantages of each design pattern;
- Find design patterns in the wild to experience them hands-on.
