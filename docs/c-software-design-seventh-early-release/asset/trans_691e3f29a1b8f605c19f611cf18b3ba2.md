然而，说实话，虽然这些解决方案在数据库示例中以及在管理内存的上下文中可能效果非常好，但它可能并不是解决每一个 *Singleton* 问题的正确方法。所以不要认为这是唯一可能的解决方案。毕竟，这取决于具体情况。然而，它是软件设计一般流程的一个很好的例子：识别发生变化或导致依赖的方面，然后通过提取合适的抽象来分离关注点。根据你的意图，你只是在应用一种设计模式。因此请相应地命名你的解决方案，并借此为他人留下你的推理痕迹。

总之：*Singleton* 模式绝对不是那些光鲜的设计模式之一。它带来的缺点实在太多，最重要的是全局状态的常见缺陷。但即便如此，尽管存在诸多负面方面，如果谨慎使用，*Singleton* 在某些情况下可以成为表示代码中少数全局方面的正确解决方案。如果是这样，优先使用具有单向数据流的 *Singletons*，并通过反转依赖关系并利用 *Strategy* 设计模式实现 *dependency injection* 来为变化和可测试性设计你的 *Singletons*。

## GUIDELINE 38: DESIGN *SINGLETONS* FOR CHANGE AND TESTABILITY

- 要意识到 *Singleton* 代表全局状态，有其所有缺陷；
- 尽可能避免全局状态；
- 谨慎使用 *Singleton*，仅用于我们代码中少数全局方面；
- 优先使用具有单向数据流的 *Singletons*；
- 使用 *Strategy* 设计模式反转对 *Singleton* 的依赖，以消除对可变性和可测试性的通常阻碍。

## Guideline 39: Continue to Learn About Design Patterns

“就这样？这就是你所有的？来吧，还有那么多设计模式。我们才刚刚触及表面！”，你抱怨道。好吧，坦白说，你完全正确，我对此无话可说。但作为辩护，我原本计划包含更多模式，直到现实击中了我：你只能在一本 400 页的书中容纳这么多信息。但不要担心：在这 400 页中，我带你走过了任何设计在你软件开发职业生涯中任何时间、任何地方都需要的最重要的建议：

- 最小化依赖：处理依赖是软件设计的核心。无论你编写何种软件，如果你真心想让它持久，你就必须处理依赖：必要的依赖，但主要是人为的依赖。当然你的主要目标是减少依赖，最好是最小化依赖。为了实现这一目标，你不可避免地会处理设计模式。
- 分离关注点：这可能是你可以从本书中带走的最重要、最核心的设计指导方针。分离关注点，你的软件结构就会解耦，更容易理解，更容易更改，更容易测试。所有设计模式，无一例外，都为你提供了某种分离关注点的方式。不同模式之间的主要区别是它们分离关注点的方式，其 *intent*。尽管设计模式在结构上可能相似，但其意图始终是独特的。
- 优先使用组合而非继承：虽然继承是一个强大的特性，但许多设计模式的真正力量来自于构建在组合之上。例如，*Strategy* 设计模式，是被 *到处* 使用的模式之一（希望这现在已经很明显了），主要建立在组合之上以分离关注点，但随后也为你提供了使用继承来扩展功能的选择。*Bridge*、*Adapter*、*Decorator*、*External Polymorphism* 和 *Type Erasure* 也是如此。
- 优先使用非侵入式设计：真正的灵活性和可扩展性来自于无需修改现有代码，而是只需添加新代码。因此，任何非侵入式设计都优于侵入式修改现有代码的设计。因此，诸如 *Decorator*、*Adapter*、*External Polymorphism* 和 *Type Erasure* 等设计模式是你的设计模式工具箱中如此宝贵的补充。
