Even if you are not familiar with the idea yet, you very likely have some experience with helpful observers from real-life. For instance, you may have noticed that in your favorite messenger app the sender of a text message is immediately informed once you have read a new text message. That means that the message is displayed as “read” instead of just as “delivered”. This little service is essentially the work of a real-life *Observer*: as soon as the status of the new message changes, the sender is notified, providing the opportunity to respond to the state change.

# The Observer Design Pattern Explained

In many software situations it is desirable to get feedback as soon as some state change occurs: a new job that is added to a task queue, a setting that is changed in some configuration object, a result that is ready to be picked up, etc. But at the same time it would be highly undesirable to introduce explicit dependencies between the subject (i.e. the observed entity that changes) and its observers (i.e. the callbacks that are notified based on a state change). On the contrary: the subject should be oblivious to the potentially many different kinds of observers. And that is for the simple reason that any direct dependency would make the software harder to change and harder to extend. This decoupling between the subject and its potentially many observers is the intent of the *Observer* design pattern:

> **THE *OBSERVER* DESIGN PATTERN**
> 
> Intent: “Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.” (GoF)

As all design patterns, the *Observer* design pattern identifies one aspect as a *variation point* (i.e. an aspect that changes or is expected to change) and extracts it in form of an abstraction. It thus helps to decouple software entities. In case of *Observer*, the need to introduce new observers, the need to extend a one-to-many dependency, is recognized to be the *variation*
