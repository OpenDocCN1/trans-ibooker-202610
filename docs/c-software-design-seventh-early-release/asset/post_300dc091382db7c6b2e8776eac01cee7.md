In summary: function overloading is a powerful compile time abstraction mechanism, that you should not underestimate. In particular, generic programming heavily exploits this power. However, do not take this power too lightly: remember that just as with base classes and concepts, an overload set represent a set of semantic requirements and thus is subject to the LSP. The expected behavior of an overload set must be adhered to, or things will not work well.

## GUIDELINE 8: UNDERSTAND THE SEMANTIC REQUIREMENTS OF OVERLOAD SETS

- Be aware that function overloading is a compile time abstraction mechanism;
- Keep in mind that there are expectations on the behavior of functions within an overload set;
- Pay attention to existing names and conventions.

## Guideline 9: Pay Attention to the Ownership of Abstractions

As stated in “Guideline 2: Design for Change” change is the one constant in software development. Meaning your software should be prepared for change. One of the essential ingredients for dealing with change is the introduction of abstractions (see also “Guideline 6: Adhere to the Expected Behavior of Abstractions”). Abstractions help to reduce dependencies and thus make it easier to change details in isolation. However, there is more to introducing abstractions than just adding base classes or templates.

### The Dependency Inversion Principle

The need for abstractions is also expressed by Robert Martin: 16

> The most flexible systems are those in which source code dependencies refer only to abstractions, not to concretions.
> 
> —Robert C. Martin

This piece of wisdom is commonly known as the Dependency Inversion Principle (DIP), which is the fifth of the SOLID principles. Simply stated, it advises that for the sake of dependencies you should not depend on concrete types nor on implementation details, but that you should depend on abstractions instead. Note that this statement does not say anything about inheritance hierarchies, but only mentions abstractions in general.

Let us take a look at the the situation illustrated in Figure 2-1. 17 Imagine you are implementing the logic for an automated teller machine (ATM). An ATM machine provides several kinds of operations: you can withdraw money, you can deposit money, and you can transfer money. Since all of these operations deal with real money, they should either run to a full completion, or in case of any kind of error should be aborted and all changes should be rolled back. This kind of behavior (either 100% success or a complete rollback) is what we commonly call a transaction. Consequently we can introduce an abstraction named Transaction. All abstractions (i.e. Deposit, Withdrawal, and Transfer) inherit from the Transaction class (depicted by the UML inheritance arrow).

All transactions are in need of input data entered by a bank customer via the user interface. This user interface is provided by the UI class, which provides many different functions to query for the entered data:
`requestDepositAmount()`, `requestWithdrawalAmount()`, `requestTransferAmount()`, `informInsufficientFunds()`, and potentially more functions. All three abstractions directly call these functions whenever they are in need of information. This relationship is depicted by means of the little solid arrow, which indicates that the abstractions depend on the UI class.

While this setup may work for some time, your trained eye might have already spotted a potential problem: what happens if something changes? For instance, what happens if a new transaction is added to the system?

Let us assume that we are required to add a `SpeedTransfer` transaction for VIP customers. This might require us to change and extend the UI class with a couple of new functions (for instance `requestSpeedTransferAmount()` and `requestVIPNumber()`). That, in turn, also affects all of the other transactions, since they directly depend on the UI class. In the best case, these transactions simply have to be recompiled and retested (still, this takes time!), in the worst case, they might have to be redeployed in case they are delivered in separate shared libraries.

The underlying reason for all of that extra effort is a broken architecture. All transactions indirectly depend on each other via the concrete dependency on the UI class. And that is a very unfortunate situation from an architectural point of view: the transaction classes reside in the high-level of our architecture, while the UI class resides on the low-level. Hence in this example, the high-level depends on the low-level. And that is just wrong: in a proper architecture, this dependency should be inverted.¹⁸

All transactions indirectly depend on each other due to the dependency on the UI class. Furthermore, the high-level of our architecture depends on the low-level. This is a pretty unfortunate situation indeed, a situation that we should resolve properly. “But that’s simple!”, you say. “We just introduce an abstraction!” That is exactly what Robert Martin expressed in his statement: we need to introduce an abstraction in order not to depend on the concrete implementation in the UI class. However, a single abstraction would not solve the problem. The three kinds of transactions would still be indirectly coupled. No, as Figure 2-2 illustrates, we need three abstractions: one for each transaction.¹⁹

By means of the introduction of the DepositUI, WithdrawalUI and TransferUI classes, we have broken the dependency between the three transactions. The three transactions are no longer depending on the concrete UI class, but only on a lightweight abstraction that represents only those operations that the relevant transaction truly requires. If we would now introduce the SpeedTransfer transaction, we would also introduce the SpeedTransferUI abstraction, so none of the other transactions will be affected by the changes introduced in the UI class.

“Oh, yes, I get it! This way we have fulfilled three design principles!” You sound impressed. “We have introduced an abstraction to cut the dependency on the implementation details of the user interface. That must be the DIP. And we have followed the ISP and thus removed the dependencies between the different transactions. And as a bonus we have also nicely grouped the things that truly belong together. That is the SRP, right? That’s amazing! Let’s celebrate!”

Wait, wait, wait… Before you now go off to uncork your best bottle of champagne to celebrate solving this dependency problem, let us take a closer look at the problem. So yes, you are correct, we follow the ISP by separating the concerns of the UI class. By segregating it into three client-specific interfaces, we have resolved the dependency situation between the three transactions. This is indeed the ISP. Very nice!

Unfortunately we have not resolved our architectural problem yet, so no, we do not follow the DIP (yet). But I get the misunderstanding: it does appear as if we have inverted the dependencies. Figure 2-3 shows that we have really introduced an inversion of dependencies: instead of depending on the concrete UI class we now depend on abstractions.
