Serialization depends on all types of documents (PDF, Word, XML, ...), but none of the types of documents depends on Serialization. In addition, none of the types of documents is aware of any other type of document (as it should be).

“Wait a second!”, you say, “In the code for the serialization, we are still in need of the enumeration, aren’t we? How else would I store the information about what the stored bytes represent?” I am glad that you are making this observation. Yes, inside the Serialization component we will still (very likely) need something like the DocumentType enumeration. However, by means of separating concerns we have properly resolved this dependency problem. None of the different types of documents depends on the DocumentType enumeration anymore. All dependency arrows now go from the low-level (the Serialization component) to the high-level (PDF and Word). And that property is decisive for a proper, for a good architecture.

“But what about adding a new type of document? Doesn’t that require a modification in the Serialization component?” Again, you are absolutely correct. Still, this is not a violation of OCP. OCP advises that we should not have to modify existing code on the same architectural level or on higher levels. However, there is no way you can control or prevent modifications on the lower levels. Serialization must depend on all types of documents and therefore must be adapted for every new type of document. For that reason, it is even required for Serialization to reside on a lower level (think depending level) of our architecture.

As also discussed in “Guideline 2: Design for Change”, the solution in this example is the separation of concerns. Thus it appears as if the real solution is to adhere to the Single-Responsibility Principle (SRP). For that reason, there are some critical voices that do not consider the OCP as a separate principle, but consider it to be the same as the SRP. I admit that I understand this reasoning.
