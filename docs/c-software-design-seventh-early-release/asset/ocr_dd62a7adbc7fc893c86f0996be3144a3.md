All four functions (①, ②, ③ and ④) are built on the Shape abstraction. All of these functions are coupled only to the common interface of all kinds of shapes, but not to any specific shape. That means that all kinds of shapes can be rotated around a point, merged, written to file, and sent via RPC. Every shape “reuses” this functionality.

It is the ability to express functionality by means of an abstraction that creates the opportunity to reuse code. And this functionality is expected to create a vast amount of code, in comparison to the little amount of code the base class contains. Real reusability therefore is created by the polymorphic use of a type, not by polymorphic types.¹¹

Second, inheritance is said to help decoupling software entities. While that is most certainly true (remember for instance the discussion about the Dependency Inversion Principle (DIP) in “Guideline 9: Pay Attention to the Ownership of Abstractions”), it is often not explained, that inheritance itself also creates coupling. You have seen evidence of that before. While implementing the Visitor design pattern you have experienced that inheritance forces certain implementation details on you. In a classic visitor, you have to implement the pure virtual functions of a Visitor base class as they are required, even if this is not optimal for your application. Additionally, you do not have a lot of choices with respect to the function arguments or return types. These things are fixed.¹²

You have also experienced this coupling at the beginning of the discussion of the Strategy design pattern. In this case, inheritance forced a structural coupling that caused a deep(er) inheritance hierarchy, it resulted in questionable naming of classes, and impaired reuse.
