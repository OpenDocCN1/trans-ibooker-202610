do_draw() and do_clone() and it would not have any consequence on the ShapeT types. The real requirement on the ShapeT types is defined by the implementation of the draw() and clone() functions.

As ShapeConcept is again the base class for the external hierarchy, the draw() function, the clone() function, and also the destructor represent the set of requirements for all kinds of shapes. This means that all shapes must provide some drawing behavior, they must be copyable, and destructible. Note that these three functions are only the choice of requirements for this example. In particular, copyability is not a general requirement for all implementations of Type Erasure.

The OwningShapeModel class (4) again represents the one and only implementation of the ShapeConcept class. As before, OwningShapeModel takes a concrete shape type and a drawing Strategy in its constructor (5) and uses these to initialize its two data members (6 and 7). Since OwningShapeModel inherits from ShapeConcept, it must implement the two pure virtual functions. The draw() function is implemented by applying the given drawing Strategy (8), while the clone() function is implemented to return an exact copy of the corresponding OwningShapeModel (9).

NOTE
If you are right now thinking: “Oh no, a std::make_unique(). That means dynamic memory. Then I cannot use that in my code!”, do not worry.
std::make_unique() is merely an implementation detail, a choice to keep the example simple. In “Guideline 33: Know about the Optimization Potential of Type Erasure” you will see how to avoid dynamic memory by means of the Small Buffer Optimization (SBO).
