A similar implementation inflexibility is the return type of the visit() functions. The decision what the function returns is made in the ShapeVisitor base class. Derived classes cannot change that. The usual approach is to store the result in the visitor and to access it later.

The second disadvantage is, that with the Visitor design pattern in place, it becomes difficult to add new types. Previously we have made the assumption that you are certain you have all the shapes you will ever need. This assumption has now become a restriction. Adding a new shape in the Shape hierarchy would require the entire ShapeVisitor hierarchy to be updated: you would have to add a new pure virtual function to the ShapeVisitor base class and this virtual function would have to be implemented by all derived classes. Of course this comes with all the disadvantages that we have discussed before. In particular, you would force other developers to update their operations.¹⁰ Thus the Visitor design pattern requires a closed set of types and in exchange provides an open set of operations.

The underlying reason for this restriction is that there is a cyclic dependency between the ShapeVisitor base class, the concrete shapes (i.e. Circle, Square, etc.) and the Shape base class (see Figure 4-3). The ShapeVisitor base class depends on the concrete shapes, since it provides a visit() function for each of these shapes.
