This is exactly the point of an architectural document: one common document that unifies the ideas, visions, and essential decisions in one place, helps to maintain and communicate the state of the architecture and helps to avoid any misunderstanding.

This document also serves the purpose to preserve ideas, visions, and decisions. Imagine that one of your leading software architects, one of the brains behind the architecture of your code base, leaves the organization. Without a document of the fundamental decisions, this loss of manpower will also cause a loss of essential information about your code base. As a consequence, you will loose consistency in the vision of your architecture, but also, and more importantly, some confidence to adapt or change architectural decisions. No new hire will ever be able to replace that knowledge and experience, and no one will be able to extract all that information from the code. Thus the code gets more rigid, more “legacy”. This promotes decisions to rewrite large parts of the code, with questionable outcome, as the new code initially lacks a lot of the wisdom of the old code.²⁴ Thus without an architectural document, your long term success is at stake.

That there is value in such an architectural document, becomes obvious if we take a look at how serious architecture is taken at construction sites. Construction is not even going to start without a plan. A plan, that everyone agrees to. Or let us imagine what would happen if there was no plan: “Hey, I said the garage should be left of the house!” “But I built it left of the house.” “Yes, but I meant my left, not your left!”

This is exactly the kind of problem that can be avoid by investing time into an architectural document. “Yes, yes, you are right”, you start to admit, “but such a document is soooo much work. And all of this information is in the code anyway. It adapts with the code, while the document goes out of date soooo quickly!” Well, not if you doing it properly. An architectural document should not go out of date quickly because it should primarily reflect the big picture of your code base. It should not contain the little details that indeed can change very often, but instead the overall structure, the connections between key players, and major technological decisions.
