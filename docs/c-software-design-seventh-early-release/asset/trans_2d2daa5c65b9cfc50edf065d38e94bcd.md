

使用值而不是指针和引用。并且 C++ 是实现这一目的的绝佳语言，因为 C++ 认真对待 *值语义*：它允许你，作为开发者，在 *值语义* 的领域里过上幸福的生活。令人惊讶的是，正如我们通过 `std::variant` 和 *类型擦除* 所看到的那样，这种哲学不一定会带来负面的性能影响，反而可能提升性能。

除了这些关于软件设计的一般性建议之外，你还对设计模式的目的有了深入的了解。现在你知道什么是设计模式了。

一个设计模式 ...

- ... 有一个名称；
- ... 承载着意图；
- ... 引入了一个抽象；
- ... 已经被证明有效。

有了这些信息，你将不再会被关于某些实现细节是设计模式的虚假说法所迷惑（我在职业生涯中多次遇到过这种情况），例如声称智能指针（`std::unique_ptr`、`std::shared_ptr` 等）或工厂函数如 `std::make_unique()` 是设计模式的实现。此外，你现在已经熟悉了许多最重要的、最有用的设计模式，它们将一次又一次地证明其价值：

- *Visitor*：如果你需要对一组封闭的类型扩展操作，请使用 *Visitor* 设计模式（可能通过 `std::variant` 实现）。
- *Strategy*：如果你想配置行为并希望从外部“注入”它，你应该选择 *Strategy* 设计模式（又名 *Policy-Based Design*）。

- *Command*：如果你想从不同种类的操作中抽象出来，可能包括可撤销的操作，那么你应该利用 *Command* 设计模式。
- *Observer*：如果你需要观察某些实体的状态变化，就该选择观察者设计模式。
- *Adapter*：如果你想在不侵入式地，即不修改代码的情况下将一个接口适配到另一个接口，你应该回想 *Adapter* 设计模式。
- *CRTP*：如果你想要一个静态抽象，不使用虚函数（并且你还不能使用 C++20 概念），那么就该应用 *CRTP* 设计模式。*CRTP* 也可能被证明对于创建编译时混入类很有用。
- *Bridge*：如果你需要隐藏实现细节并减少物理依赖，你应该使用 *Bridge* 设计模式。
- *Prototype*：如果你想创建虚拟副本，那么 *Prototype* 设计模式就是正确的选择。
- *External Polymorphism*：如果你想通过在外部添加多态行为来促进松耦合，那么请确保记住 *External Polymorphism* 设计模式。
- *Type Erasure*：如果你需要 *External Polymorphism* 的能力结合 *值语义* 的优势，请考虑 *Type Erasure* 设计模式。
- *Decorator*：如果你想以非侵入式的方式为对象添加职责，那么就选择 *Decorator* 设计模式的好处。

然而，还有更多的设计模式。更多！而且还有很多重要且有用的设计模式。因此你应该继续学习设计模式。有两种方法可以做到这一点。一种是了解更多模式：学习它们的意图以及它们与其它设计模式的相似性和差异。此外，不要忘记设计模式是关于依赖结构，而不是实现细节。第二，你还应该更好地理解每一个模式，体验它们的优点和缺点。为此，你也应该留意你在工作中使用的代码库中使用的设计模式。我向你保证，你会发现很多：任何试图管理和减少依赖的尝试都非常可能是设计模式的证明。所以是的：设计模式无处不在！
