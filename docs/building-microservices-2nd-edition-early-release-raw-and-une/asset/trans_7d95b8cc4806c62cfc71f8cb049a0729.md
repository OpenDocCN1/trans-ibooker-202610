
不过，要计算公司的估值，财务员工需要我们持有的股票信息。此时，库存项就成为两个上下文之间的共享模型。然而，请注意，我们不需要盲目地从仓库上下文中暴露有关库存项的所有信息。在 [图 2-18](#ch02.xhtml#stock_item_representations) 中，我们可以看到仓库有界上下文内的 `Stock Item` 包含对货架位置的引用，但共享表示仅包含一个计数。因此，存在仅限内部的表示，以及我们公开的外部表示。通常，当你有不同的内部和外部表示时，为避免混淆，将它们命名为不同名称可能有益——在这种情况下，一种方法可以是将共享的 `Stock Item` 称为 `Stock Count`。

![](Images/stock_item_representations.png)

## 共享模型

我们还可以拥有出现在多个有界上下文中的概念。在 [图 2-17](#ch02.xhtml#a30-context-diagram) 中我们看到 `customer` 同时存在于两个位置。这意味着什么？`customer` 被复制了吗？思考这个问题的方式是，从概念上讲，`finance` 和 `warehouse` 都需要了解一些关于我们的 `customer` 的信息。`Finance` 需要了解对 `customer` 支付的财务款项，而 `Warehouse` 需要了解 `customer` 的程度在于它知道已发送了哪些包裹，以便追踪交付。

在这种情况下，像 `customer` 这样的共享模型在不同的有界上下文中可能具有不同的含义，因此可能被称为不同的名称。我们可能很乐意在 `Finance` 中保留名称“`customer`”，但在 `Warehouse` 中我们可能称他们为“`recipient`”，因为那是他们在该上下文中扮演的角色。我们在两个位置都存储有关 `customer` 的信息，但信息是不同的。`Finance` 存储有关 `customer` 的财务付款（或退款）的信息，`warehouse` 存储与已发货商品相关的信息。我们仍可能需要将这两个本地概念链接到全局 `customer`，并且可能希望查找有关该 `customer` 的通用共享信息，如其姓名或电子邮件地址——我们可以使用 [图 2-16](#ch02.xhtml#customer_references) 中所示的技术来实现这一点。

## 将聚合和有界上下文映射到微服务

`aggregate` 和 `bounded context` 都为我们提供了具有明确界面的内聚单元，与更广泛的系统交互。`aggregate` 是一个自包含的状态机，专注于我们系统中单一的领域概念，而 `bounded context` 则代表一组相关的聚合，同样具有对外部世界的明确接口。

因此两者都可以作为服务边界良好地工作。在起步阶段，正如我已经提到的，你希望减少处理的服务数量。因此，你可能应该以涵盖整个 `bounded contexts` 的服务为目标。随着你逐渐熟悉，并决定将这些服务拆分为更小的服务，请围绕 `aggregate` 边界进行拆分。

## 一直到底都是乌龟

起初，你可能会识别出若干粗粒度的有界上下文。但这些有界上下文本身又可以包含进一步的有界上下文。例如，你可以将 `warehouse` 分解为与订单履行、库存管理或货物接收相关的能力。在考虑微服务的边界时，首先以更大、更粗粒度的上下文为出发点，然后在希望获得拆分这些缝隙带来的好处时，沿着这些嵌套上下文进行细分。

这里的一个技巧是，即使你后来决定将建模整个有界上下文的服务拆分为更小的服务，你仍然可以将其决策隐藏在外部世界之外——也许是通过向消费者提供更粗粒度的 API。将服务分解为更小部分的决定可以说是实现层面的决策，因此如果可以的话，我们不妨将其隐藏。在 [图 2-19](#ch02.xhtml#nested-services) 中我们看到了一个例子。我们已将 `Warehouse` 拆分为 `Inventory` 和 `Shipping`。就外部世界而言，仍然只有 `Warehouse` 微服务。不过在内部，我们进一步分解了事物，以便让 `Inventory` 管理 `Stock Items`，并让 `Shipping` 管理 `Shipments`。记住，我们希望将单个 `aggregate` 的所有权保留在单个微服务内部。

![](Images/nested-services.png)

这又是另一种信息隐藏形式——我们以这样的方式隐藏了关于内部实现的决策，以至于如果未来此实现细节再次发生变化，我们的消费者将不会察觉。

偏好嵌套方法另一个原因可能是将架构分块以简化测试。例如，在测试消费仓库的服务时，我不必为仓库上下文内的每个服务创建存根，只需为更粗粒度的 API 创建存根即可。这也可以在考虑更大范围的测试时为你提供一个隔离单元。例如，我可能会决定进行端到端测试，在其中启动仓库上下文内的所有服务，但对于所有其他协作方，我可能会为其创建存根。我们将在 \[Link to Come\] 中进一步探讨测试和隔离。

## 过早分解的危险

基于对领域理解不清而分解微服务存在危险。一个这样的例子来自我之前的公司 `ThoughtWorks`。他们的一款产品名为 `SnapCI`，这是一款托管的持续集成和持续交付工具（我们将在 \[Link to Come\] 中稍后讨论这些概念）。该团队之前曾在另一款类似工具 `Go-CD` 上工作过，这是一款现在开源的持续交付工具，可以在本地部署而不是托管在云中。

尽管 `SnapCI` 和 `Go-CD` 项目在早期有一些代码复用，但最终 `SnapCI` 证明是一个完全新的代码库。尽管如此，团队在 CD 工具领域之前的经验使他们更有信心更快地识别边界，并将系统构建为一组微服务。

不过几个月后，很明显 `SnapCI` 的用例有细微的不同，以至于最初对服务边界的把握并不完全正确。这导致在各服务之间进行了大量更改，并伴随着较高的变更成本。最终团队将服务合并回一个单体系统中，给了他们更多时间来更好地理解边界应该存在于何处。一年后，团队随后能够将单体系统拆分为微服务，其边界被证明更加稳定。这远非我见过的唯一一个这种情况的例子。过早地将系统分解为微服务可能代价高昂，尤其是在你对该领域不熟悉的情况下。在许多方面，拥有一个你想要分解为微服务的现有代码库，比从一开始就尝试转向微服务要容易得多，正是出于这个原因。

## 以业务概念进行沟通

我们对系统实施的更改通常是关于业务希望对系统行为做出的更改。我们正在更改向客户公开的功能——能力。如果我们的系统沿着代表我们领域的边界上下文进行分解，我们想要做出的更改更有可能被隔离到单个微服务边界。这减少了我们需要进行更改的地方数量，并允许我们快速部署该更改。
