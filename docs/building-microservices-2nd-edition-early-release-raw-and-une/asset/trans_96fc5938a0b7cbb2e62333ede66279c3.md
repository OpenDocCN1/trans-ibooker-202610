
# 渐进式交付

Jez 认为通过将这两个概念分开，我们可以确保我们的软件在生产环境中正常运行，而不会让用户看到故障。蓝绿部署是这一概念最简单的示例之一——你有一个正在运行的软件版本（蓝色），然后在生产环境中将新版本与旧版本并行部署（绿色）。你会检查新版本是否按预期工作，如果是，就将客户重定向到现在查看软件的新版本。如果在切换前发现问题，则不会影响任何客户。

虽然蓝绿部署是这一原则中最简单的示例之一——事实证明，当我们接受这一概念时，还有许多更复杂的技巧可以使用。

## 转向渐进式交付

James Governor，开发者导向的行业分析公司 RedMonk 的联合创始人，最早创造^([16](#ch07.xhtml#idm46534869506968))了“渐进式交付”这一术语，用来涵盖该领域使用的多种不同技术。他后来将渐进式交付描述为“对爆炸半径进行精细控制的持续交付”^([17](#ch07.xhtml#idm46534869505032))——因此是持续交付的扩展，但是一种使我们能够控制新发布软件潜在影响的技术。

承接这一主题，LaunchDarkly 的 Adam Zimman 描述了^([18](#ch07.xhtml#idm46534869502888))渐进式交付如何影响“业务”。从这个角度来看，我们需要转变对新功能如何到达客户的思考方式。它不再是一次性发布——现在可以是一个分阶段的活动。重要的是，渐进式交付可以赋能业务利益相关者，正如 Adam 所说“将功能的控制权委托给对结果负有最直接责任的所有者”。不过要实现这一点，相关利益相关者需要了解所使用的渐进式交付技术的机制。因此，这要求我们的产品负责人等在技术上更能理解如何最好地使用渐进式交付。

我们已经提到蓝绿部署是一种渐进式交付技术。让我们简要看看其他几种

## 功能开关

使用功能开关（也称为功能标志），我们将已部署的功能隐藏在开关后面，可用于打开或关闭功能。这最常作为主干分支开发的一部分使用，其中尚未完成的功能可以签入并部署，但仍对终端用户隐藏，但它在这些之外也有很多应用。这可以用于在指定时间打开功能，或关闭导致问题的功能。

你也可以以更细粒度的方式使用功能开关，也许可以根据发出请求的用户的性质让标志具有不同的状态。例如，你可以让一组客户看到功能已打开（也许是一个 Beta 测试组），而大多数人看到功能处于关闭状态——这可以帮助你实现金丝雀发布，我们接下来会讨论。用于管理功能开关的完全托管解决方案已存在，包括 LaunchDarkly^([19](#ch07.xhtml#idm46534869496888)) 和 Split^([20](#ch07.xhtml#idm46534869495336))。尽管这些平台令人印象深刻，但我认为你可以用更简单的方式开始——一开始只需一个配置文件即可，然后在你开始推动想要如何使用开关时再考虑这些技术。

对于更深入地了解功能开关的世界，我强烈推荐 Pete Hodgson 的文章“Feature Toggles (aka Feature Flags)”^([21](#ch07.xhtml#idm46534869493032))，其中详细介绍了如何实现它们以及它们可以使用的多种不同方式。

## 金丝雀发布

> 犯错是人类的本性，但要真正搞砸事情，你需要一台计算机^([22](#ch07.xhtml#idm46534869489304))。
>
> Paul Ehrlich

我们都会犯错，而计算机可以让我们比以往任何时候都更快、更大规模地犯错。鉴于错误是不可避免的（相信我，它们确实如此），那么做一些可以限制这些错误影响的事情是有意义的。金丝雀发布就是其中一种技术。

金丝雀发布的名字来源于矿工带入矿井的金丝雀，作为早期预警系统，警告他们危险气体的存在。在金丝雀发布中，想法是让我们客户的有限子集看到新功能。如果发布出现问题，则只有该部分客户受到影响。如果该功能对金丝雀组有效，则可以将其推广到更多客户，直到每个人都看到新版本。

对于微服务架构，可以在单个微服务级别配置开关，对来自外部世界或其他微服务的该功能请求打开（或关闭）功能。另一种技术是并排运行两个不同版本的微服务，并使用开关路由到旧版本或新版本。在这里，金丝雀实现必须位于路由/网络路径中的某个位置，而不是位于一个微服务中。

当我第一次进行金丝雀发布时，我们手动控制发布。我们可以配置看到新功能的流量百分比，并在一周的时间内逐渐增加，直到每个人都看到新功能。在一周内，我们会关注错误率、错误报告等。现在，更常见的是以自动化方式处理此过程。例如，像 Spinaker^([23](#ch07.xhtml#idm46534869483160)) 这样的工具可以根据指标自动增加调用，例如如果错误率在可接受水平，则增加对新微服务版本的调用百分比。

## 并行运行

在金丝雀发布中，对某项功能的一次请求将由旧版本或新版本提供服务。但这并不能让我们直接比较两个不同的实现。如果您想确保新功能与已知基线完全相同的方式工作，这可能很重要。实现这一点的较简单方法之一是对旧实现和新实现都运行任何请求，并比较结果。

在并行运行中，你就是这样做的——你并排运行同一功能的两个不同实现，并向两个实现发送对该功能的请求。在微服务架构中，最明显的方法可能是将服务调用分派到同一服务的两个不同版本并比较结果。另一种选择是在同一服务内部共存该功能的两个实现，这通常可以使比较更容易。

在执行两个实现时，重要的是要意识到你可能只想要其中一次调用的结果。其中一个实现被认为是真实来源——这是你当前信任的实现，通常是现有实现。根据你使用并行运行比较的功能的性质，你可能需要仔细考虑这种细微差别——例如，你不希望向客户发送两次相同的订单更新，或两次支付同一张发票！
