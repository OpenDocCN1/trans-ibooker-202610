
# 同步调用

同步调用的主要挑战在于发生的固有时间耦合，我们在[第2章](#ch02.xhtml#modelling-services-chapter)中简要探讨过这一主题。当上面的示例中 `Order Processor` 向 `Loyalty` 发出调用时，`Loyalty` 微服务需要可达，调用才能工作。如果 `Loyalty` 微服务不可用，则调用将失败，`Order Processor` 需要弄清楚要执行何种补偿操作——这可能涉及立即重试，将调用缓冲以便稍后重试，或者干脆放弃。

由于调用发送方处于阻塞状态并等待下游微服务响应，因此如果下游微服务响应缓慢，或者网络延迟存在问题，则调用发送方将被阻塞很长时间等待响应。如果 `Loyalty` 微服务处于显著负载下，对请求响应缓慢，这反过来会导致 `Order Processor` 响应缓慢。

因此，与异步调用相比，使用同步调用会使系统更容易受到下游中断引发的级联问题的影响。

## 何时使用

对于简单的微服务架构，我对使用同步阻塞调用并没有太大的问题。对许多人来说，它们的熟悉性是在掌握分布式系统时的一大优势。

对我而言，这类调用开始变得有问题的地方在于当你开始出现更多调用链时——例如在[图3-3](#ch03.xhtml#fraud-detection-long-chain)中，我们有一个来自 MusicCorp 的示例流程，其中我们正在检查可能存在欺诈活动的付款。`Order Processor` 调用 `Payment` 服务以完成付款。`Payment` 服务随后希望与 `Fraud Detection` 微服务核实是否应允许此操作。`Fraud Detection` 微服务随后需要从 `Customer` 微服务获取信息。

![](Images/fraud-detection-long-chain.png)

如果所有这些调用都是同步且阻塞的，我们可能会面临许多问题。任意四个相关微服务中的一个出现问题，或它们之间的网络调用出现问题，都可能导致整个操作失败——我们可说故障面更大。这还不包括这类长链可能导致显著的 *资源竞争* 这一事实。在幕后，`Order Processor` 很可能有一个网络连接处于打开状态，等待 `Payment` 的回复。`Payment` 随后也有一个网络连接处于打开状态，等待 `Fraud Detection` 的响应，以此类推。需要保持打开的大量连接会对运行中的系统产生影响——你更有可能遇到可用连接耗尽的问题，或因此遭受网络拥塞增加。

为了改善这种情况，我们可以首先重新审视微服务之间的交互。例如，也许我们可以将 `Fraud Detection` 的使用从主要购买流程中移除，如[图3-4](#ch03.xhtml#fraud-detection-background)所示，而让它在后台运行。如果它发现某个特定客户存在问题，其记录会相应更新，并且这可以在付款流程的更早阶段进行检查。实际上，这意味着我们将部分工作并行化。通过缩短调用链的长度，我们会看到操作整体延迟改善，并将我们的一个微服务（`Fraud Detection`）从购买流程的关键路径中移除，对于关键操作而言，这减少了一个需要担心的依赖。

![](Images/fraud-detection-background.png)

我们当然也可以在不改变此处工作流程的情况下，用某种非阻塞交互方式替换阻塞调用的使用，我们接下来会探讨这一点。

# 模式：异步非阻塞
