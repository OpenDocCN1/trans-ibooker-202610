
三层架构是这一点的良好体现。过去，IT 组织将人员分组的主要方式是基于其核心能力：数据库管理员与其它数据库管理员组成一个团队；Java 开发者与其它 Java 开发者组成一个团队；而前端开发者（如今他们掌握像 JavaScript 和原生移动应用开发这样时髦的技术）则在另一个团队。我们基于核心能力对人员进行分组，因此我们创建可以与这些团队对应起来的 IT 资产。

这就解释了为什么这种架构如此常见。它并不糟糕；它只是围绕一组力量进行优化——我们传统上如何按熟悉程度对人员进行分组。但力量已经改变。我们对软件的期望也发生了改变。我们现在将人员分组为多技能团队，以减少交接和信息孤岛。我们希望比以往任何时候都更快地交付软件。这促使我们在团队组织方式上做出不同的选择，因此也在系统拆分方式上进行组织。

大多数我们被要求对系统进行的更改都与业务功能的变化有关。但在 [图 1-5](#ch01.xhtml#ch01-musiccorp-three-tiered-change) 中，我们的业务功能实际上分散在所有三层中，增加了功能变更跨越层级的可能性。这是一种具有高度相关技术内聚性但业务功能内聚性低的架构。如果我们想让更改更容易进行，那么我们需要改变代码的分组方式——我们选择业务功能的内聚性而非技术。每个服务最终可能包含这三层的混合，也可能不包含，但这是一个本地服务实现问题。

让我们将其与一种潜在的替代架构进行比较，该架构在 [图 1-6](#ch01.xhtml#ch01-customer-service) 中进行了说明。我们有一个专用的 Customer 服务，它公开了一个 UI 以允许客户更新其信息，并且客户的状态也存储在此服务中。喜爱的类型选择与特定客户相关联，因此这种更改更加本地化。在 [图 1-6](#ch01.xhtml#ch01-customer-service) 中，我们还展示了从 Catalog 服务获取的可用类型列表，这很可能已经存在。我们还看到一个新的 Recommendations 服务访问我们的喜爱的类型信息，这在后续版本中很容易实现。

![](Images/wams_0106.png)

在这种情况下，我们的 Customer 服务封装了三层中的每一层的一小部分——它有一点 UI，一点应用逻辑和一点数据存储——但这些层都封装在单个服务中。我们的业务领域成为驱动系统架构的主要力量，希望这能使更改更容易进行，同时也使我们更容易将团队与组织内的业务线保持一致。

# 单体

我们已经讨论过微服务，但微服务最常被讨论为一种替代单体架构的架构方法。为了更好地区分微服务架构，并帮助你更好地理解是否值得考虑微服务，我还应该讨论我所说的 *单体* 到底是什么意思。

当我在整本书中谈论单体时，我主要指的是部署单元。当系统的所有功能必须一起部署时，我们认为它是一个单体。坦率地说，有多种架构符合这一定义，但我将讨论我最常看到的几种：单进程单体、模块化单体和分布式单体。

## 单进程单体

讨论单体时最常见的例子是所有代码都作为 *单进程* 部署的系统，如 [图 1-7](#ch01.xhtml#ch01-single-process-monolith) 所示。你可能出于健壮性或扩展原因拥有该进程的多个实例，但从根本上说所有代码都打包在一个进程中。实际上，这些单进程系统本身可以是简单的分布式系统，因为它们几乎总是最终从数据库读取数据或将数据存储到数据库中，或向 Web 或移动应用呈现信息。

![](Images/wams_0107.png)

虽然这符合大多数人对经典单体的理解，但我遇到的大多数系统比这更复杂一些。你可能有两个或多个紧密耦合的单体，可能还混杂了一些厂商软件。

## 模块化单体

作为单进程单体的子集，*模块化单体* 是一种变体，其中单个进程由独立的模块组成。每个模块可以独立工作，但所有模块仍需要在部署时组合在一起，如 [图 1-8](#ch01.xhtml#ch01-modular-monolith) 所示。将软件分解为模块的概念并非新事物；模块化软件的根源可追溯到 1970 年代围绕结构化编程所做的工作，甚至更早。尽管如此，这仍然不是我看到足够多的组织正确采用的方法。

![](Images/wams_0108.png)

对于许多组织而言，模块化单体可能是一个极佳的选择。如果模块边界定义良好，它可以实现高度的并行工作，同时通过更简单的部署拓扑避免更分布式微服务架构的挑战。Shopify 就是一个很好的例子，该组织使用这种技术作为微服务分解的替代方案，并且似乎对该公司非常有效。^([3](#ch01.xhtml#idm46534878369192))

模块化单体面临的一个挑战是，数据库往往缺乏我们在代码层面找到的分解，这导致如果未来想拆分单体时会带来重大挑战。我见过一些团队尝试进一步推进模块化单体的想法，将数据库沿着与模块相同的思路进行分解，如 [图 1-9](#ch01.xhtml#ch01-modular-monolith-and-db) 所示。

![](Images/wams_0109.png)

## 分布式单体

> 一个分布式系统是指你甚至不知道存在的计算机的故障会使你自己的计算机无法使用。^([4](#ch01.xhtml#idm46534878361960))
>
> Leslie Lamport

一个 *分布式单体* 是一个由多个服务组成的系统，但由于某种原因，整个系统必须一起部署。分布式单体完全可能符合 SOA 的定义，但太多的情况下，它未能兑现 SOA 的承诺。在我的经验中，分布式单体具有分布式系统的所有缺点，*和* 单进程单体的所有缺点，而没有任一方的足够优势。在工作中遇到许多分布式单体在很大程度上影响了我对微服务架构的兴趣。

分布式单体通常出现在对信息隐藏和业务功能内聚等概念关注不足的环境中。相反，高度耦合的架构会导致更改在服务边界之间扩散，而看似无害且范围局限的更改会破坏系统的其他部分。

## 单体与交付竞争

随着越来越多的人在同一个地方工作，他们会互相妨碍。例如，不同的开发者想要更改同一段代码；不同的团队想要在不同时间将功能上线（或延迟部署）；对谁拥有什么以及谁做决策感到困惑。大量研究表明了所有权界限混乱带来的挑战。^([5](#ch01.xhtml#idm46534878355128)) 我将此问题称为 *交付* *竞争*。
