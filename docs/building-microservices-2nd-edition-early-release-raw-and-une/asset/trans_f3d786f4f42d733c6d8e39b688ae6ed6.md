
让我解释一下这种方法的一些显著缺点。如果我对单个服务进行一行修改——例如在[图 6-5](#ch06.xhtml#a61-one-build-for-all-ms)中更改 `User` 服务的行为——*全部*其他服务都会被验证和构建。这可能比所需花费更多时间——我在等待那些可能不需要测试的东西。这会影响我们的周期时间，即将单个更改从开发推进到生产的速度。更令人担忧的是，知道应该部署哪些构件或不应该部署哪些构件。我现在是否需要部署所有构建服务才能将我的小更改推送到生产环境？这很难判断；仅通过阅读提交信息来猜测哪些服务*真正*发生了变化是困难的。使用这种方法的组织通常会退回到一起部署所有内容，而我们真的想避免这种情况。

此外，如果我对 `user` 服务的一行更改破坏了构建，在该问题修复之前就无法对其他服务进行其他更改。再想想这样一个场景：多个团队都在共享这个庞大的构建。谁负责？实际上，我几乎从未见过这种方法被使用，除了在项目的最早阶段。说实话，接下来的两种方法都明显更可取，所以我们将重点关注它们。

## 模式：每个微服务一个仓库（又称多仓库）

采用每个微服务一个仓库模式（在与单仓库模式比较时更常被称为多仓库模式），每个微服务的代码都存储在其自己的源代码仓库中，如[图 6-6](#ch06.xhtml#one-repo-per-microservice)所示。这种方法在源代码更改和 CI 构建之间建立了直接的映射关系。

![](Images/06-one-repo-per-microservice.png)

对 `User` 源代码仓库的任何更改都会触发匹配的构建，如果构建通过，我将拥有可用于部署的 `User` 微服务的新版本。为每个微服务拥有单独的仓库也允许你按仓库为基础更改所有权，如果你希望为微服务考虑强所有权模型，这是有意义的（稍后会详细介绍）。

这种模式的直接性虽然带来了某些挑战。具体来说，开发人员可能会同时处理多个仓库，特别是在尝试同时对多个仓库进行更改时，这尤其痛苦。此外，无法以原子方式在单独的仓库之间进行更改，至少使用 `Git` 时不行。

### 跨仓库复用代码

使用这种模式时，没有任何东西可以阻止微服务依赖于在不同仓库中管理的其他代码。一个简单的实现机制是将想要复用的代码打包成库，然后使其成为下游微服务的显式依赖。我们可以在[图 6-7](#ch06.xhtml#reusing-code-across-repos)中看到一个例子，其中 `Invoice` 和 `Payroll` 服务都使用了 `Connection` 库。

![](Images/reusing-code-across-repos.png)

如果你想推出对 `Connection` 库的更改，你必须在匹配的源代码仓库中进行更改，并等待其构建完成以获得新的版本化构件。要实际部署使用此新版本库的 `Invoice` 或 `Payroll` 服务的新版本，你需要更改它们使用的 `Connection` 库的版本。这可能需要手动更改（如果你依赖特定版本），也可以根据你使用的 CI 工具的性质配置为动态发生。这些概念在 Jez Humble 和 Dave Farley 所著的书籍《Continuous Delivery》中得到了更详细的阐述^([4](#ch06.xhtml#idm46534870002824))。

当然需要记住的重要一点是，如果你想推出 `Connection` 库的新版本，那么我们也需要部署新构建的 `Invoice` 和 `Payroll` 服务。请记住，我们在[“DRY 与微服务世界中代码复用的风险”](#ch04.xhtml#a50-dry)中探讨的关于复用和微服务的所有注意事项仍然适用——如果你选择通过库复用代码，那么你必须接受这些更改无法以原子方式推出的事实，否则我们就会破坏独立部署的目标。你还必须意识到，可能更难知道某些微服务是否使用库的特定版本，如果你试图弃用旧版本库的使用，这可能会有问题。

### 跨多个仓库工作

那么，除了通过库复用代码之外，我们还能如何对一个以上的仓库进行更改？让我们看另一个例子。在[图 6-8](#ch06.xhtml#commit-across-repos)中，我想更改 `Inventory` 服务公开的 API，并且我还需要更新 `Shipping` 服务以便它可以使用新的更改。如果 `Inventory` 和 `Shipping` 的代码在同一个仓库中，我可以一次性提交代码。现在，我必须将更改拆分为两部分——一个提交用于 `Inventory`，另一个提交用于 `Shipping`。

![](Images/commit-across-repos.png)

如果一个提交失败而另一个成功，这种拆分更改可能会导致问题——例如，我可能需要进行两次更改来回滚更改，如果在此期间其他人已签入，这可能会变得复杂。实际上，在这种特定情况下，我无论如何都可能希望对提交进行一定程度的分阶段处理。我希望在更改 `Shipping` 服务中的任何客户端代码之前，确保更改 `Inventory` 服务的提交有效——如果 API 中没有新的功能，就没有必要拥有使用它的客户端代码。

我与多个人交谈过，他们认为这种缺乏原子部署的情况是一个重大问题。我当然可以理解这带来的复杂性，但我认为在大多数情况下，这指向了一个更大的潜在问题。如果你不断在多个微服务之间进行更改，这表明你的服务边界可能不在正确的位置，并且可能意味着服务之间耦合过多。正如我们已经讨论过的，我们试图优化我们的架构和微服务边界，以便更改更有可能在微服务边界内应用。跨切更改应该是例外，而不是常态。

#### 提示

如果你不断在多个微服务之间进行更改，这很可能表明你的微服务边界位置错误。如果发现这种情况发生，考虑将微服务重新合并可能值得一试。

然后还有在正常工作流程中必须从多个仓库拉取并推送到多个仓库的麻烦。根据我的经验，这可以通过使用支持多个仓库的 IDE 来简化（这是我在过去 5 年中使用过的所有 IDE 都能处理的事情），你也可以编写简单的包装脚本来简化命令行工作。

### 何时使用此模式

使用每个微服务一个仓库的方法对于小型团队和大型团队同样有效，但如果你发现自己在微服务边界之间进行大量更改，那么它可能不适合你，我们接下来讨论的单仓库模式可能更合适——尽管在服务边界之间进行大量更改可以被视为某种不正常情况的警告信号，正如我们之前讨论过的。它还可能使代码复用比使用单仓库方法更复杂，因为你需要依赖代码被打包成版本构件。
