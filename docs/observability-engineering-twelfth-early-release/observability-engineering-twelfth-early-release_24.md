本书的大部分内容都聚焦于向软件工程团队介绍可观测性实践。但就全组织范围的应用而言，工程团队不能也不应该孤军奋战。一旦你为丰富、宽泛的事件完成埋点，你的遥测数据集就包含了关于你的服务在市场中行为的宝贵信息。

可观测性擅长快速回答任意问题的特点，意味着它也能填补组织中各类非工程利益相关者的知识空白。传播可观测性文化的一个成功策略是：通过帮助工程邻近团队弥补这些空白，来在这些团队中建立盟友。在本章中，你将了解可观测性在工程邻近领域的用例、哪些团队很可能成为采纳盟友，以及帮助他们如何帮助你积累势头，使可观测性成为组织实践的核心部分。

### 识别非工程领域的可观测性需求

工程团队拥有一系列工具、实践、习惯、目标、抱负、职责和要求，它们以各种方式结合，为客户创造价值。有些工程团队可能更专注于软件开发，而另一些则更侧重于运维。尽管不同的工程团队有不同的专长，但为使用贵公司软件的用户创造卓越的客户体验绝不仅仅是“别人的事”。这是一项共同责任，也是每个人的工作。

可观测性也可以这样理解。正如你在本书中所看到的，可观测性是一面透镜，能快速向你展示你*认为*你的软件应该如何表现，或你*声称*你的软件应该如何表现（通过代码、文档、知识库、博客文章等），以及它在真实用户手中*实际*表现之间的差异。借助可观测性，你可以在任意时间点了解客户在真实世界中使用你的软件的体验。理解和改善这种体验是每个人的工作。

工程团队基于多种原因认识到可观测性的需求。功能缺口可能在存在相当一段时间后才被识别，而一个催化事件——通常是严重的中断——可能促使变革需求的出现。或者，这种需求也可能是被更主动地认识到，比如意识到不断追逐难以捉摸的 bug 所带来的持续救火式工作正在扼杀开发团队的创新能力。无论哪种情况，都存在一个支撑性的业务案例，推动可观测性采纳举措的推进。

同样，对于非工程团队的可观测性采纳，你必须问自己它能支持哪些业务案例。在任意时间点了解客户在真实世界中使用你的软件的体验，存在哪些业务案例？你组织中的哪些人需要理解和改善客户体验？

让我们明确一点：并非每个团队都会专门研究可观测性。即使在专门研究可观测性的工程团队中，有些团队也会比其他人做更多的编码和埋点工作。但贵公司几乎每个人都能从查询你的可观测性数据以分析生产环境当前状态的细节中受益。

由于可观测性允许你跨多个维度任意拆分和切分数据，你可以用它来理解单个用户、用户群体或整个系统的行为。这些视图可以被比较、对比或进一步挖掘，以回答与组织中非工程业务单元极其相关的各种问题组合。

可观测性支持的一些业务用例可能包括：

- 了解新功能的采用情况。哪些客户正在使用你新发布的功能？这与表示感兴趣的客户名单是否一致？活跃功能用户的使用模式与那些尝试过但后来放弃体验的用户有何不同？

- 为新客户寻找成功的产品使用趋势。销售团队是否了解哪些功能组合能引起那些最终成为客户的潜在客户的共鸣？你是否了解未能激活你产品的用户在产品使用上的共性？这些共性是否指向了需要通过某种方式消除的阻力？

- 通过最新的服务状态页面，准确地向客户和内部支持团队传递服务可用性信息。你能提供模板化查询，以便在用户报告故障时支持团队可以自助服务吗？

- 了解短期和长期的可靠性趋势。你的软件用户的可靠性体验是否在提升？可靠性图的形状是否与其他数据来源（如客户投诉）相匹配？你遇到的问题是在减少还是增加？这些问题的恢复是否更慢了？

- 主动解决问题。你是否能在客户通过支持工单大量报告之前，发现并解决影响客户的问题？你是在主动解决问题，还是依赖客户为你发现问题？

- 更快速、更可靠地向客户交付功能。是否密切监控生产环境部署以发现并修复性能异常？你能否将部署与发布解耦，从而让新功能的交付不太可能引发大规模中断？

在贵公司，理解和改善客户体验应该是每个人的工作。你可以通过自问：谁关心你的应用程序的可用性、交付给客户的新功能、产品内的使用趋势以及你所提供的数字服务的客户体验，来识别非工程团队的可观测性需求。

进一步推进全组织可观测性采纳举措的最佳方式是主动接触能够从这些知识中受益的邻近团队。借助可观测性，你可以让组织中的每个人（无论技术能力如何）都能自如地使用这些数据，并能够自如地谈论这些数据，从而帮助他们做出构建更好客户体验的明智决策。

换句话说，让你的可观测性数据民主化。让每个人都能看到正在发生的事情，以及你的软件在真实用户手中是如何表现的。与任何其他新加入的团队一样，你可能需要提供初始的指导和辅导，向他们展示如何从数据中获得问题的答案。但很快你就会发现，每个邻近团队都会带来自己独特的视角和问题。

与邻近团队的利益相关者合作，确保他们的问题能够得到回答。如果他们的提问今天无法回答，那么明天能否通过添加新的自定义埋点来回答？与邻近利益相关者一起迭代埋点，也将帮助工程团队更好地理解与业务其他部分相关的问题。这种合作水平提供了学习机会，有助于消除沟通孤岛。

与安全性和可测试性类似，可观测性必须作为一种持续实践来对待。实践可观测性的团队必须养成习惯，确保任何代码变更都附带适当的埋点，就像必须附带测试一样。代码评审应确保新代码的埋点达到适当的可观测性标准，就像确保其满足安全标准一样。这些评审还应确保，当为支持业务功能而添加埋点时，非工程业务单元的需求得到满足。

可观测性需要持续的关注和维护，但通过观察本章所概述的文化行为和关键结果，你将知道自己已经达到了足够的可观测性水平。

### 在实践中建立可观测性盟友

现在你已经学会了如何识别可观测性可以帮助解决业务问题的知识空白，下一步是与各种利益相关者合作，向他们展示如何做到这一点。你的可观测性采纳工作很可能首先在工程内部开始，然后由于共同责任和工作流程的性质，扩展到邻近团队（例如支持团队）。只需相对较少的工作量，一旦你的采纳工作顺利开展，你就可以接触其他利益相关者——无论是财务、销售、市场营销、产品开发、客户成功、高管团队还是其他部门——向他们展示在真实世界中，关于客户如何使用你的应用程序，有哪些可能理解到的信息。





相反，使用可观测性后，支持团队有几种选择。最简单的方法是瞥一眼你的 SLO 仪表板，看看是否检测到任何影响客户的问题（见 [第 12 章](#)）。虽然这可能比传统监控更精细，并能更早提供有用的反馈，但远非完美。现代系统是模块化、 resilient 且自愈的，这意味着停机很少是二元的：它看起来不像整个站点是否正常运行，而更像是“你的‘购物车结账’在欧洲的 Android 用户中 50% 的时间出现故障”或“只有启用了我们新 ACL 功能的客户才会看到部分故障”。

让支持团队成员能够利用可观测性调试客户报告的问题，可以帮助他们采取更主动的方法。对于客户 ID 为 5678901 的这个特定客户的交易现在看起来如何？他们是否在欧洲使用 Android 设备使用购物车功能？他们是否启用了访问控制列表（ACL）？支持团队可以快速确认或否认收到的支持请求是否与已知问题相关，并进行适当的分类。或者，在具备足够的熟练程度和对可观测性工具的培训后，团队可以帮助识别可能未被自动检测到的新问题——例如使用参数不足的 SLI。

## 客户成功和产品团队

在以产品为导向的组织中，越来越常见的是拥有客户成功团队。与支持团队对客户问题的被动应对方式不同，*客户成功团队*采取更主动的方法，通过有效使用你的产品来帮助客户避免问题。该团队通常提供诸如入职、规划、培训、协助升级等帮助。

客户支持和客户成功团队在日常工作中听到最直接的客户反馈。他们知道人们最抱怨的是应用程序的哪些部分。但那些最吵闹的“刺耳的轮子”是否真的是对整体成功至关重要的客户旅程部分？

例如，你可能最近发布了一个新功能，但客户的采用率并不高。为什么？用户是否将此功能用作现场演示，只是象征性地试用一下？还是他们将其作为产品工作流程的一部分使用？该功能何时以及如何被调用，使用哪些参数？以及在什么事件序列中？

可观测性解决方案捕获的事件数据类型对于了解产品使用情况非常有用，这对产品团队来说极具价值。产品和客户成功团队都非常关心了解贵公司的软件在真实客户操作下表现如何。能够任意地按任何相关维度对可观测性数据进行切片和切分以找到有趣的模式，意味着其用途远远超出了仅支持生产环境中的可用性和弹性问题。

此外，当某些产品功能被弃用并设定了停用日期时，拥有可观测性的成功团队可以看到哪些用户仍在积极使用即将退役的功能。他们还可以衡量新功能是否被采用，并主动帮助可能受产品退役时间表影响的客户，但这些客户在月度同步会议中优先处理其他问题。

成功团队还可以通过分析当前使用模式，了解哪些特征可能预示着对新产品功能的激活。就像你可以在数据中找到性能异常值一样，你也可以使用可观测性在性能数据中找到采用率异常值。对数据进行任意切片和切分意味着你可以做诸如比较那些进行特定请求超过特定次数的用户与未进行的用户。是什么区分了这些用户？

例如，你可能会发现，采用新分析功能的用户的主要区别在于，他们创建自定义报告的可能性高出 10 倍。如果你的目标是提高分析功能的采用率，成功团队可以通过创建培训材料来响应，展示客户为何以及如何使用包含创建自定义报告的深入演练的分析。他们还可以衡量培训在研讨会前后的效果，以判断其是否产生预期效果。

## 销售和执行团队

*销售团队*也是你在可观测性采用工作中非常有帮助的盟友。根据贵公司的组织结构，工程和销售团队在日常工作中可能并不经常互动。但销售团队是你推动可观测性采用的最强大的盟友之一。销售团队有兴趣了解和支持销售的产品功能。

据传闻，销售团队会传递在推介或演示中收到的反馈，以建立对产品中哪些内容引起共鸣的集体理解。定性理解对于发现趋势和形成关于如何进一步实现销售目标的假设很有用。但该团队可以从可观测性数据中提取的定量分析类型对于指导和验证销售执行策略非常有用。

例如，哪些客户使用哪些功能以及使用频率如何？哪些功能使用最频繁，因此需要最高的可用性目标？哪些功能是你的战略客户最依赖的，何时以及在他们工作流程的哪些部分？哪些功能在销售演示中使用最频繁，因此应始终可用？潜在客户最感兴趣的哪些功能具有惊艳效果，应始终性能最快？

这些类型的问题，以及更多问题，都可以用你的可观测性数据来回答。这些问题的答案对销售有帮助，但它们也是关于在何处进行战略投资的关键业务决策的核心。

*执行层利益相关者*希望明确了解如何产生最大的业务影响，而可观测性数据可以帮助实现这一点。你数字业务今年最重要需要做的事情是什么？例如，哪些工程投资将推动销售方面的成效？

一种传统的自上而下的控制和指挥方法来表达工程的战略业务目标可能很模糊——例如，尽可能接近 100% 可用性——但它通常无法说明如何以及为何这样做。相反，通过使用可观测性数据来连接这些要点，目标可以用技术术语表达，并深入到用户体验、架构、产品功能以及使用它们的团队。清晰地定义目标并使用共同的跨领域语言，这才是真正实现团队之间组织对齐的关键。你究竟在何处进行投资？这将影响谁？是否投入了适当的工程投资水平以实现你的可用性和可靠性目标？

## 使用可观测性与业务智能工具

你们中的一些人可能读了前面章节后问自己，业务智能（BI）工具是否能完成同样的任务。事实上，我们描述的对公司各个组成部分的各种理解有点像是准 BI 用例。为什么不直接使用 BI 工具呢？

很难对 BI 工具进行概括，因为它们包括联机分析处理（OLAP）、移动 BI、实时 BI、运营 BI、位置智能、数据可视化和图表映射、构建仪表板的工具、计费系统、临时分析和查询、企业报告等。你能想到的各种数据，某个地方就有工具对其进行优化分析。很难（虽然没那么难）概括为这些工具提供动力的数仓的特征，但我们可以至少说这些数仓是非易失性和时变的，并包含原始数据、元数据和汇总数据。

但 BI 工具非常通用，而可观测性工具则专门针对特定用例进行了超专业化：理解代码、基础设施、用户和时间之间的交集。让我们来看看可观测性工具所做的一些具体权衡。





## 查询执行时间

可观测性工具必须快速，查询时间从亚秒级到几秒不等。可观测性的一个关键原则是可探索性，因为你并不总是知道自己要找什么。你会花更少时间反复运行相同的查询，更多时间沿着线索追踪下去。在调查过程中，如果不得不坐等一分钟甚至更久才能拿到结果，这种中断可能意味着你完全失去了思路。

相比之下，BI 工具通常针对运行报表或构建会被反复使用的复杂查询进行优化。这些查询运行时间长一点也没关系，因为这些数据并非用于实时响应，而是用于输入其他工具或系统。你通常在数周、数月或数年的时间尺度上做出业务方向决策，而不是分钟或秒。如果你每隔几秒就做出战略性业务决策，那一定是出了大问题。

## 准确性

对于可观测性工作负载，如果必须选择的话，返回快速但不完美的结果（只要非常接近正确）比返回完美但缓慢的结果更好。对于迭代性调查，你几乎总是更愿意在一秒内得到扫描 99.5% 事件的结果，而不是在一分钟内得到扫描 100% 的结果。在跨越不完美且不稳定的网络的大规模并行分布式系统中，这是一个真实且常见的权衡（见第 16 章）。

此外（如第 17 章所述），通常采用某种形式的动态采样来实现大规模可观测性。这两种方法都以牺牲一点准确性来换取巨大的性能提升。而对于 BI 工具和业务数据仓库，采样和“接近正确”的做法通常是绝对禁止的。例如，在计费场景中，无论花费多长时间，你总是希望得到准确的结果。

## 时效性

你通过可观测性工具回答的问题具有强烈的时效性偏向，最重要的数据往往是最新的。生产环境中发生的事情与你能查询到这些结果之间的延迟如果超过几秒，是不可接受的，尤其是在处理事件时。

随着数据逐渐淡出到数月之前，你往往更关心历史事件的聚合和趋势，而不是细粒度的单个请求。当你确实关心特定请求时，花稍长一点时间找到它们是可以接受的。但当数据是新鲜的时候，你需要查询结果是原始、丰富且精确到秒的。

BI 工具通常处于这个光谱的另一端。在 BI 工具中处理数据花费更长时间通常是可以接受的。通常可以通过缓存更新的结果，或通过预处理、索引或聚合旧数据来提高性能。但一般来说，使用 BI 工具，你希望（实际上）永远保留数据的完整保真度。使用可观测性工具，你永远不会去搜索五年前甚至两年前发生的事情。现代 BI 数据仓库被设计为永久存储数据并无限增长。

## 结构

可观测性数据由任意宽且结构化的数据块构成：每个服务每个请求一个事件（或在长期运行的批处理过程中每个轮询间隔一个事件）。为了满足可观测性需求（回答关于任何时间正在发生什么的任何问题），你需要附加尽可能多的事件细节，以提供尽可能多的上下文，以便调查人员能够发现未来可能相关的东西。随着团队了解哪些数据可能有帮助，这些细节通常会迅速变化和演进。预先定义数据模式将违背这一目的。

因此，对于可观测性工作负载，模式必须在事后推断或动态更改（随时开始发送新维度或停止发送）。索引同样没有帮助（见第 16 章）。

相比之下，BI 工具通常将大量非结构化数据收集并处理为结构化、可查询的形式。如果没有结构和预定义模式，BI 数据仓库将变成无法管理的混乱。你需要一致的模式才能随时间进行任何有用的分析。而且 BI 工作负载倾向于以可重复的方式提出类似问题，以支持仪表板等应用。BI 数据可以通过索引、复合索引、汇总等进行优化。

由于 BI 数据仓库被设计为永久增长，因此预定义模式并以可预测的速度增长非常重要。可观测性数据则专为快速反馈循环和灵活性而设计：它在压力时期通常最为重要，而当时效性远比可预测性重要。

## 时间窗口

可观测性和 BI 工具都有会话或追踪的概念。但可观测性往往局限于以秒或最多分钟计的时间跨度。BI 工具可以处理长期旅程，或需要数天或数周才能完成的追踪。这种类型的追踪持续时间通常不是可观测性工具支持的用例。对于可观测性工具，长时间运行的进程（如导入/导出作业或队列）通常通过轮询或心跳进程来处理，而不是通过单个追踪。

## 短暂性

总结以上几点，调试数据本质上比业务数据更具短暂性。例如，你可能需要完全精确地检索两年前的特定交易记录或计费记录。相比之下，你不太可能需要知道两年前某个特定用户请求中服务 A 和服务 B 之间的延迟是否很高。

然而，你可能想知道过去一两年内服务 A 和服务 B 之间的延迟是否增加，或者第 95 百分位延迟是否在那段时间内上升。这类问题很常见，实际上既不是 BI 工具/数据仓库也不是可观测性工具最适合回答的。聚合的历史性能数据最适合由我们的好朋友——监控——来处理（见第 9 章）。

## 实践中的可观测性与 BI 工具结合使用

BI 工具有多种形式，通常旨在分析来自财务、客户关系管理（CRM）、企业资源规划（ERP）、营销漏斗或供应链系统的各种业务指标。这些指标由许多工程师制作成仪表板和报表。但是，尤其是对于技术驱动型公司，当应用服务体验至关重要时，通常需要进一步深入 BI 系统设计提供之外的细节。

BI 工具的数据粒度任意大，通常按月或按周报告指标。你的 BI 工具可以帮助你了解哪些功能在二月份被使用最多。你的可观测性工具可以提供更细的粒度，一直到单个请求级别。就像可观测性和监控相互结合一样，商业智能和可观测性也通过确保你始终拥有可用于构建宏观世界视图的微观数据而结合在一起。

BI 工具通常依赖聚合指标，使你只能看到业务世界的整体超级大图。这些视图在可视化整体业务趋势时很有用，但在尝试回答关于产品使用或用户行为的问题（本章前面已详述）时，它们就没那么有用了。

跨部门共享可观测性工具是推广单一领域语言的好方法。可观测性在服务和 API 这一抽象级别捕获数据，从运维工程师到高管，每个人都能理解。通过这种共享，工程师被鼓励使用业务语言来描述其领域模型，而业务人员则接触到其用户群中广泛（且真实）的用例多样性（超越他们通常看到的少数抽象综合用户角色）。

## 结论

通过可观测性，你可以了解客户在真实世界中使用你的软件的体验。由于业务中的多个团队对理解客户体验并改进或利用它有着既得利益，你可以利用可观测性帮助组织内的各个团队更好地实现其目标。

除了工程团队之外，产品、支持和客户成功等相邻技术团队可以成为强大的盟友，推动你的组织级可观测性采用计划。销售和高管等不太技术性的团队，如果得到你的一些额外支持，也可以成为盟友。本章中作为示例列出的团队绝非定论。希望你能将本章作为入门指南，思考哪些类型的业务团队可以通过使用你正在捕获的可观测性数据获得更好的信息并实现更好的期望结果。帮助更多业务团队实现他们的目标将创造利益相关者和盟友，他们反过来可以帮助优先推进你的可观测性采用工作。
