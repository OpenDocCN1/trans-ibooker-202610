

## 查询执行时间

可观测性工具必须快速，查询时间从亚秒级到几秒不等。可观测性的一个关键原则是可探索性，因为你并不总是知道自己要找什么。你会花更少时间反复运行相同的查询，更多时间沿着线索追踪下去。在调查过程中，如果不得不坐等一分钟甚至更久才能拿到结果，这种中断可能意味着你完全失去了思路。

相比之下，BI 工具通常针对运行报表或构建会被反复使用的复杂查询进行优化。这些查询运行时间长一点也没关系，因为这些数据并非用于实时响应，而是用于输入其他工具或系统。你通常在数周、数月或数年的时间尺度上做出业务方向决策，而不是分钟或秒。如果你每隔几秒就做出战略性业务决策，那一定是出了大问题。

## 准确性

对于可观测性工作负载，如果必须选择的话，返回快速但不完美的结果（只要非常接近正确）比返回完美但缓慢的结果更好。对于迭代性调查，你几乎总是更愿意在一秒内得到扫描 99.5% 事件的结果，而不是在一分钟内得到扫描 100% 的结果。在跨越不完美且不稳定的网络的大规模并行分布式系统中，这是一个真实且常见的权衡（见第 16 章）。

此外（如第 17 章所述），通常采用某种形式的动态采样来实现大规模可观测性。这两种方法都以牺牲一点准确性来换取巨大的性能提升。而对于 BI 工具和业务数据仓库，采样和“接近正确”的做法通常是绝对禁止的。例如，在计费场景中，无论花费多长时间，你总是希望得到准确的结果。

## 时效性

你通过可观测性工具回答的问题具有强烈的时效性偏向，最重要的数据往往是最新的。生产环境中发生的事情与你能查询到这些结果之间的延迟如果超过几秒，是不可接受的，尤其是在处理事件时。

随着数据逐渐淡出到数月之前，你往往更关心历史事件的聚合和趋势，而不是细粒度的单个请求。当你确实关心特定请求时，花稍长一点时间找到它们是可以接受的。但当数据是新鲜的时候，你需要查询结果是原始、丰富且精确到秒的。

BI 工具通常处于这个光谱的另一端。在 BI 工具中处理数据花费更长时间通常是可以接受的。通常可以通过缓存更新的结果，或通过预处理、索引或聚合旧数据来提高性能。但一般来说，使用 BI 工具，你希望（实际上）永远保留数据的完整保真度。使用可观测性工具，你永远不会去搜索五年前甚至两年前发生的事情。现代 BI 数据仓库被设计为永久存储数据并无限增长。

## 结构

可观测性数据由任意宽且结构化的数据块构成：每个服务每个请求一个事件（或在长期运行的批处理过程中每个轮询间隔一个事件）。为了满足可观测性需求（回答关于任何时间正在发生什么的任何问题），你需要附加尽可能多的事件细节，以提供尽可能多的上下文，以便调查人员能够发现未来可能相关的东西。随着团队了解哪些数据可能有帮助，这些细节通常会迅速变化和演进。预先定义数据模式将违背这一目的。

因此，对于可观测性工作负载，模式必须在事后推断或动态更改（随时开始发送新维度或停止发送）。索引同样没有帮助（见第 16 章）。

相比之下，BI 工具通常将大量非结构化数据收集并处理为结构化、可查询的形式。如果没有结构和预定义模式，BI 数据仓库将变成无法管理的混乱。你需要一致的模式才能随时间进行任何有用的分析。而且 BI 工作负载倾向于以可重复的方式提出类似问题，以支持仪表板等应用。BI 数据可以通过索引、复合索引、汇总等进行优化。

由于 BI 数据仓库被设计为永久增长，因此预定义模式并以可预测的速度增长非常重要。可观测性数据则专为快速反馈循环和灵活性而设计：它在压力时期通常最为重要，而当时效性远比可预测性重要。

## 时间窗口

可观测性和 BI 工具都有会话或追踪的概念。但可观测性往往局限于以秒或最多分钟计的时间跨度。BI 工具可以处理长期旅程，或需要数天或数周才能完成的追踪。这种类型的追踪持续时间通常不是可观测性工具支持的用例。对于可观测性工具，长时间运行的进程（如导入/导出作业或队列）通常通过轮询或心跳进程来处理，而不是通过单个追踪。

## 短暂性

总结以上几点，调试数据本质上比业务数据更具短暂性。例如，你可能需要完全精确地检索两年前的特定交易记录或计费记录。相比之下，你不太可能需要知道两年前某个特定用户请求中服务 A 和服务 B 之间的延迟是否很高。

然而，你可能想知道过去一两年内服务 A 和服务 B 之间的延迟是否增加，或者第 95 百分位延迟是否在那段时间内上升。这类问题很常见，实际上既不是 BI 工具/数据仓库也不是可观测性工具最适合回答的。聚合的历史性能数据最适合由我们的好朋友——监控——来处理（见第 9 章）。

## 实践中的可观测性与 BI 工具结合使用

BI 工具有多种形式，通常旨在分析来自财务、客户关系管理（CRM）、企业资源规划（ERP）、营销漏斗或供应链系统的各种业务指标。这些指标由许多工程师制作成仪表板和报表。但是，尤其是对于技术驱动型公司，当应用服务体验至关重要时，通常需要进一步深入 BI 系统设计提供之外的细节。

BI 工具的数据粒度任意大，通常按月或按周报告指标。你的 BI 工具可以帮助你了解哪些功能在二月份被使用最多。你的可观测性工具可以提供更细的粒度，一直到单个请求级别。就像可观测性和监控相互结合一样，商业智能和可观测性也通过确保你始终拥有可用于构建宏观世界视图的微观数据而结合在一起。

BI 工具通常依赖聚合指标，使你只能看到业务世界的整体超级大图。这些视图在可视化整体业务趋势时很有用，但在尝试回答关于产品使用或用户行为的问题（本章前面已详述）时，它们就没那么有用了。

跨部门共享可观测性工具是推广单一领域语言的好方法。可观测性在服务和 API 这一抽象级别捕获数据，从运维工程师到高管，每个人都能理解。通过这种共享，工程师被鼓励使用业务语言来描述其领域模型，而业务人员则接触到其用户群中广泛（且真实）的用例多样性（超越他们通常看到的少数抽象综合用户角色）。

## 结论

通过可观测性，你可以了解客户在真实世界中使用你的软件的体验。由于业务中的多个团队对理解客户体验并改进或利用它有着既得利益，你可以利用可观测性帮助组织内的各个团队更好地实现其目标。

除了工程团队之外，产品、支持和客户成功等相邻技术团队可以成为强大的盟友，推动你的组织级可观测性采用计划。销售和高管等不太技术性的团队，如果得到你的一些额外支持，也可以成为盟友。本章中作为示例列出的团队绝非定论。希望你能将本章作为入门指南，思考哪些类型的业务团队可以通过使用你正在捕获的可观测性数据获得更好的信息并实现更好的期望结果。帮助更多业务团队实现他们的目标将创造利益相关者和盟友，他们反过来可以帮助优先推进你的可观测性采用工作。
