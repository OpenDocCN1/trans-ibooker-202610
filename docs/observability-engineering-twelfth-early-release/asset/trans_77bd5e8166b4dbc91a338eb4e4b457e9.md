本书的大部分内容都聚焦于向软件工程团队介绍可观测性实践。但就全组织范围的应用而言，工程团队不能也不应该孤军奋战。一旦你为丰富、宽泛的事件完成埋点，你的遥测数据集就包含了关于你的服务在市场中行为的宝贵信息。

可观测性擅长快速回答任意问题的特点，意味着它也能填补组织中各类非工程利益相关者的知识空白。传播可观测性文化的一个成功策略是：通过帮助工程邻近团队弥补这些空白，来在这些团队中建立盟友。在本章中，你将了解可观测性在工程邻近领域的用例、哪些团队很可能成为采纳盟友，以及帮助他们如何帮助你积累势头，使可观测性成为组织实践的核心部分。

### 识别非工程领域的可观测性需求

工程团队拥有一系列工具、实践、习惯、目标、抱负、职责和要求，它们以各种方式结合，为客户创造价值。有些工程团队可能更专注于软件开发，而另一些则更侧重于运维。尽管不同的工程团队有不同的专长，但为使用贵公司软件的用户创造卓越的客户体验绝不仅仅是“别人的事”。这是一项共同责任，也是每个人的工作。

可观测性也可以这样理解。正如你在本书中所看到的，可观测性是一面透镜，能快速向你展示你*认为*你的软件应该如何表现，或你*声称*你的软件应该如何表现（通过代码、文档、知识库、博客文章等），以及它在真实用户手中*实际*表现之间的差异。借助可观测性，你可以在任意时间点了解客户在真实世界中使用你的软件的体验。理解和改善这种体验是每个人的工作。

工程团队基于多种原因认识到可观测性的需求。功能缺口可能在存在相当一段时间后才被识别，而一个催化事件——通常是严重的中断——可能促使变革需求的出现。或者，这种需求也可能是被更主动地认识到，比如意识到不断追逐难以捉摸的 bug 所带来的持续救火式工作正在扼杀开发团队的创新能力。无论哪种情况，都存在一个支撑性的业务案例，推动可观测性采纳举措的推进。

同样，对于非工程团队的可观测性采纳，你必须问自己它能支持哪些业务案例。在任意时间点了解客户在真实世界中使用你的软件的体验，存在哪些业务案例？你组织中的哪些人需要理解和改善客户体验？

让我们明确一点：并非每个团队都会专门研究可观测性。即使在专门研究可观测性的工程团队中，有些团队也会比其他人做更多的编码和埋点工作。但贵公司几乎每个人都能从查询你的可观测性数据以分析生产环境当前状态的细节中受益。

由于可观测性允许你跨多个维度任意拆分和切分数据，你可以用它来理解单个用户、用户群体或整个系统的行为。这些视图可以被比较、对比或进一步挖掘，以回答与组织中非工程业务单元极其相关的各种问题组合。

可观测性支持的一些业务用例可能包括：

- 了解新功能的采用情况。哪些客户正在使用你新发布的功能？这与表示感兴趣的客户名单是否一致？活跃功能用户的使用模式与那些尝试过但后来放弃体验的用户有何不同？

- 为新客户寻找成功的产品使用趋势。销售团队是否了解哪些功能组合能引起那些最终成为客户的潜在客户的共鸣？你是否了解未能激活你产品的用户在产品使用上的共性？这些共性是否指向了需要通过某种方式消除的阻力？

- 通过最新的服务状态页面，准确地向客户和内部支持团队传递服务可用性信息。你能提供模板化查询，以便在用户报告故障时支持团队可以自助服务吗？

- 了解短期和长期的可靠性趋势。你的软件用户的可靠性体验是否在提升？可靠性图的形状是否与其他数据来源（如客户投诉）相匹配？你遇到的问题是在减少还是增加？这些问题的恢复是否更慢了？

- 主动解决问题。你是否能在客户通过支持工单大量报告之前，发现并解决影响客户的问题？你是在主动解决问题，还是依赖客户为你发现问题？

- 更快速、更可靠地向客户交付功能。是否密切监控生产环境部署以发现并修复性能异常？你能否将部署与发布解耦，从而让新功能的交付不太可能引发大规模中断？

在贵公司，理解和改善客户体验应该是每个人的工作。你可以通过自问：谁关心你的应用程序的可用性、交付给客户的新功能、产品内的使用趋势以及你所提供的数字服务的客户体验，来识别非工程团队的可观测性需求。

进一步推进全组织可观测性采纳举措的最佳方式是主动接触能够从这些知识中受益的邻近团队。借助可观测性，你可以让组织中的每个人（无论技术能力如何）都能自如地使用这些数据，并能够自如地谈论这些数据，从而帮助他们做出构建更好客户体验的明智决策。

换句话说，让你的可观测性数据民主化。让每个人都能看到正在发生的事情，以及你的软件在真实用户手中是如何表现的。与任何其他新加入的团队一样，你可能需要提供初始的指导和辅导，向他们展示如何从数据中获得问题的答案。但很快你就会发现，每个邻近团队都会带来自己独特的视角和问题。

与邻近团队的利益相关者合作，确保他们的问题能够得到回答。如果他们的提问今天无法回答，那么明天能否通过添加新的自定义埋点来回答？与邻近利益相关者一起迭代埋点，也将帮助工程团队更好地理解与业务其他部分相关的问题。这种合作水平提供了学习机会，有助于消除沟通孤岛。

与安全性和可测试性类似，可观测性必须作为一种持续实践来对待。实践可观测性的团队必须养成习惯，确保任何代码变更都附带适当的埋点，就像必须附带测试一样。代码评审应确保新代码的埋点达到适当的可观测性标准，就像确保其满足安全标准一样。这些评审还应确保，当为支持业务功能而添加埋点时，非工程业务单元的需求得到满足。

可观测性需要持续的关注和维护，但通过观察本章所概述的文化行为和关键结果，你将知道自己已经达到了足够的可观测性水平。

### 在实践中建立可观测性盟友

现在你已经学会了如何识别可观测性可以帮助解决业务问题的知识空白，下一步是与各种利益相关者合作，向他们展示如何做到这一点。你的可观测性采纳工作很可能首先在工程内部开始，然后由于共同责任和工作流程的性质，扩展到邻近团队（例如支持团队）。只需相对较少的工作量，一旦你的采纳工作顺利开展，你就可以接触其他利益相关者——无论是财务、销售、市场营销、产品开发、客户成功、高管团队还是其他部门——向他们展示在真实世界中，关于客户如何使用你的应用程序，有哪些可能理解到的信息。
