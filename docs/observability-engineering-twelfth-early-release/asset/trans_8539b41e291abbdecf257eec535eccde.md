
作为一名工程师，你可能习惯于凭直觉调试。为了找到问题的根源，你可能会顺着一个灵感摸索，或借助对一次早已过去故障的短暂记忆来指导调查。然而，过去对你很有用的技能在这个世界中已不再适用。直觉方法只有在遇到的大部分问题都是你过去曾遇到过的少数几个可预测主题的变体时，才能奏效。

同样，基于指标的监控方法依赖于过去曾遇到过已知故障模式。监控有助于检测系统何时超出或低于先前被某人认定为异常的预测阈值。但当你*甚至不知道这种异常是否可能存在*时，会发生什么？

从历史上看，软件工程师遇到的大多数问题都是某种程度可预测的故障模式的变体。也许人们并不知道你的软件会以它实际发生的方式失败，但如果你对该情境及其组成部分进行推理，发现一个新 bug 或故障模式并不需要逻辑跳跃。大多数软件开发人员很少遇到真正不可预测的逻辑跳跃，因为他们通常不必处理那种让这些跳跃司空见惯的复杂性（到目前为止，开发人员面临的大部分复杂性都被封装在单体应用内部）。

> *每个应用都有一定量无法简化的复杂性。唯一的问题是：谁必须来处理它——用户、应用开发者，还是平台开发者？*
> 
> *拉里·特斯勒*

现代分布式系统架构以新颖的方式失败是出了名的，这些方式既无人能预测，也无人经历过。这种情况发生得足够频繁，以至于人们针对新手分布式计算程序员常犯的[错误假设](#)创造了一整套说法。现代分布式系统还以*抽象基础设施平台*的形式提供给应用开发者。作为这些平台的用户，应用开发者现在不得不处理一定量无法简化的复杂性，而这正好落在了他们的肩上。

以前，应用代码子程序之间相互交互的复杂性被掩盖在一台物理机器内部隐藏的随机存取存储器之中；如今，这种复杂性已浮出水面，变成了主机之间的服务请求。这种新暴露出来的复杂性接着会在多个服务之间跳跃，在单个函数的执行过程中多次穿越不可预测的网络。当现代架构开始倾向于把单体分解为微服务时，软件工程师失去了使用传统调试器逐步调试代码的能力。与此同时，他们的工具尚未完全应对这种巨变。

简而言之：我们炸掉了单体应用。现在，每个请求都必须在网络中跳跃多次，每个软件开发人员都需要更精通系统和运维，才能完成日常工作。

这种巨变的例子体现在以下趋势中：容器化趋势、容器编排平台的兴起、向微服务的转变、多语言持久化的普遍使用、服务网格的引入、临时自动扩缩实例的流行、无服务器计算、Lambda 函数，以及软件开发人员典型工具集中无数其他 SaaS 应用。将这些不同工具串联成现代系统架构，意味着一个请求在到达你所控制范围的边缘后，可能会执行 20 到 30 次跳跃（如果请求包含数据库查询，这个数字很可能还要乘以二）。

在现代云原生系统中，调试最困难的地方不再是理解代码如何运行，而是*在系统中找出*有问题的代码究竟在哪里。想通过仪表盘或服务地图来查看哪个节点或服务变慢？祝你好运，因为这些系统中的分布式请求常常会自我循环。在这些系统中寻找性能瓶颈极具挑战性。当某个部分变慢时，*一切都会变慢*。更具挑战性的是，由于云原生系统通常以平台方式运作，代码可能存在于这个团队根本无法控制的系统部分。

在现代世界中，使用指标调试要求你将执行任何一个特定请求期间记录下来的数十个互不相关的指标连接起来，这些指标可能跨任意数量的服务或机器，从而推断为完成该请求所需的各个跳跃过程中可能发生了什么。这数十条线索是否有用，完全取决于是否有人能够提前预测：该测量值是否高于或低于某个阈值，而正是这个阈值意味着该操作促成了一个前所未有、从未遇到过的未知异常故障模式的产生。

相比之下，使用可观测性进行调试始于一个截然不同的基础：即对该动作发生时正在发生情况的深度上下文。使用可观测性调试的目标是尽可能多地保留任何给定请求周围的上下文，以便你能够重建触发 bug 并导致新故障模式的环境和情境。监控针对的是“已知的未知”，而可观测性针对的是“未知的未知”。

## 基数的作用

在数据库上下文中，*基数*指集合中数据值的唯一性程度。*低基数*意味着一个列在其集合中有大量重复值。*高基数*意味着该列包含很大比例的完全唯一的值。一个只包含单个值的列，其基数总是可能达到的最低值。一个包含唯一 ID 的列，其基数总是可能达到的最高值。

例如，在一亿条用户记录的集合中，你可以假设任何通用唯一标识符（UUID）都具有尽可能高的基数。高基数的另一个例子可能是公钥签名。First Name 和 Last Name 会具有较高的基数，但由于有些名字会重复，所以比 UUID 低。像 Gender 这样的字段，如果模式是 50 年前编写的，那么基数会很低；但鉴于近代对性别的理解，也许不再如此。像 Species 这样的字段，其基数可能处于最低水平——前提是你的所有用户都是人类。

基数对可观测性很重要，因为*高基数信息几乎总是最有用的*，可用于识别调试或理解系统所需的数据。想想按用户 ID、购物车 ID、请求 ID 或任何其他无数 ID（如实例、容器、主机名、构建号、跨度（spans）等）进行排序的用处吧。能够针对唯一 ID 进行查询，是在任何给定的干草堆中精确定位单根针的最佳方法。你总是可以把高基数的值降采样为较低基数的东西（例如，按前缀对姓氏进行分桶），但你永远无法反向操作。

不幸的是，基于指标的工具系统在任何合理的规模下只能处理低基数维度。即使你只有几百台主机需要比较，在基于指标的系统中，如果你将主机名用作标识标签，就必然会触及基数键空间的限制。

这些固有限制给数据查询方式带来了非预期的限制。使用指标调试时，对于你可能想向数据提出的每个问题，你都必须—*提前*，在 bug 发生之前—决定需要查询什么，以便在写入该指标时记录其值。

这有两个重大影响。第一，如果在调查过程中，你决定必须提出额外的问题才能发现潜在问题的根源，那么事后无法做到这一点。你必须先设置可能回答该问题的指标，然后等待问题再次发生。第二，由于回答这个额外问题需要另一组指标，大多数基于指标的工具供应商会向你收取记录这些数据的费用。每当你决定采用一种新的方式来查询数据，以查找你事先不可能预测到的隐藏问题时，你的成本就会线性增加。
