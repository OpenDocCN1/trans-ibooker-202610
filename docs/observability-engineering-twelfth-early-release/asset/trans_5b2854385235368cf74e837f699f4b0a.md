

跨职能实践，开发人员对其代码在生产环境中的责任保持不变。与其从列举停机潜在原因的众多告警开始，成熟的 DevOps 和 SRE 团队都会衡量用户痛苦的任何可见症状，然后使用可观测性工具深入了解停机原因。

从基于原因的监控转向基于症状的监控意味着你需要能够解释实践中看到的故障的能力，而不是传统上列举日益增长的已知故障模式的方法。与其花费大部分时间响应对终端用户可见性能毫无影响的一系列误报，团队可以专注于系统地缩小假设范围并为实际系统故障制定缓解措施。我们将在第 12 章中更详细地介绍这一点。

除了为故障排除/修复用例采用可观测性之外，具有前瞻性的 DevOps 和 SRE 团队还使用诸如功能开关、持续验证和事件分析等工程技术。可观测性通过提供有效实践这些用例所需的数据来增强这些用例。让我们探讨可观测性如何赋能每一种：

### Chaos engineering and continuous verification

这些要求你具备可观测性，以便“检测系统何时处于正常状态，以及在执行实验方法时系统如何偏离该稳态”。² 在没有理解系统基线状态、预测测试下预期行为以及解释与预期行为偏差的能力的情况下，你无法有意义地执行混沌实验。“当你实际上不知道在注入混沌之前系统当前状态下的行为时，进行混沌工程毫无意义。”³

### Feature flagging

这会在生产环境中引入预生产环境中无法穷举测试的新颖的标志状态组合。因此，你需要可观测性来了解每个功能标志对每个用户的单独影响和集体影响。当端点可以根据调用它的用户和启用的功能标志以多种方式执行时，按组件监控行为的概念不再适用。

### *Progressive release patterns*

这些模式，例如金丝雀发布和蓝绿部署，需要可观测性来有效地知道何时停止发布，以及分析系统与预期的偏差是否由发布引起。

### *Incident analysis and blameless postmortems*

这些要求你构建关于社会技术系统的清晰模型——不仅仅是故障技术系统内部发生了什么，而且人类操作员在事件期间*认为*发生了什么。因此，强大的可观测性工具通过提供事后纸质轨迹和细节来提示回顾性撰写者，从而促进进行优秀的回顾。

### Conclusion

随着 DevOps 和 SRE 实践的不断发展，以及平台工程作为一个伞形学科的成长，你的工具链中不可避免地会出现更多创新的工程实践。但所有这些创新都将取决于将可观测性作为核心感知来理解现代复杂系统。向 DevOps、SRE 和云原生实践的转变创造了对可观测性等解决方案的需求。反过来，可观测性也增强了采用其实践的团队的能力。

在本章中，我们检查可观测性的基本构建块：结构化事件。可观测性是你能够理解和解释系统可能进入的任何状态的程度，无论多么新颖或奇怪。为了做到这一点，你必须能够回答任何可以提出的问题，而无需提前预测或预测需要回答该问题的需求。为此，首先必须满足几个技术前提。

在本書中，我们解决了可观测性所需的许多技术前提。在本章中，我们从理解和解释系统可能处于的任何状态所需的遥测开始。询问*任何*问题，关于任何组合的遥测细节，需要能够沿任意数量的维度任意切片和切分数据。它还要求你的遥测以完整分辨率收集，精确到保留收集上下文的最低逻辑粒度级别。对于可观测性而言，这意味着在每个请求或每个服务级别收集遥测。

使用老式指标，你必须预先定义自定义指标，如果你想开始提出新问题并收集新遥测来回答它。在指标世界中，获得对任何可能问题的答案的方法是收集和存储每一种可能的指标——这根本不可能（即使可能，也 prohibitively expensive）。此外，指标不保留事件的上下文，只是特定时间发生情况的聚合测量。凭借这种聚合视图，你无法对现有数据集提出新问题或寻找新异常值。

使用可观测性，你可以在任何时候对现有遥测数据提出新问题，而无需先预测这些问题可能是什么。在可观测系统中，你必须能够迭代地探索系统方面，从高级别聚合性能一直到单个请求中使用的原始数据。

使这成为可能的技术要求从可观测性所需的数据格式开始：任意宽度的结构化事件。收集这些事件不是可选的。它不是实现细节。它是使在该广泛视图中进行任何级别分析成为可能的必要条件。
