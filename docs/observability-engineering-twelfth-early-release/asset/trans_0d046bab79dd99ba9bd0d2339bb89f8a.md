

## 维度的作用

*基数*指的是数据中值的唯一性，而*维度*指的是该数据中键的数量。在可观测系统中，遥测数据以任意宽度的结构化事件生成（参见 [第 8 章](Chapter 8)）。这些事件被称为“宽”，因为它们可以并且应该包含数百甚至数千个键值对（或维度）。事件越宽，事件发生时捕获的上下文就越丰富，因此在后续调试时你能发现的关于发生了什么的信息就越多。

假设你有一个事件模式，为每个事件定义了六个高基数维度：`time`、`app`、`host`、`user`、`endpoint` 和 `status`。有了这六个维度，你可以创建查询来分析维度的任意组合，以揭示可能导致异常的相关模式。例如，你可以检索，“过去半小时内主机 `foo` 发生的全部 502 错误”，或，“用户 `bar` 对 `/export` 端点发出的请求产生的全部 403 错误”，或，“应用程序 `baz` 发送到 `/payments` 端点的请求中发生的全部超时以及它们来自哪个主机”。

仅凭六个基本维度，你就可以检查一组有用的条件来确定应用程序系统中可能发生了什么。现在想象一下，如果你能检查的不是只有六个维度，而是数百或数千个维度，这些维度包含任何在未来某个调试目的中可能有帮助的细节、值、计数器或字符串。例如，你可以包含看起来像这样的维度：

```
app.api_key
app.batch
app.batch_num_data_sets
app.batch_total_data_points
app.dataset.id
app.dataset.name
app.dataset.partitions
app.dataset.slug
```

```
app.event_handler
app.raw_size_bytes
app.sample_rate
app.team.id
...
response.content_encoding
response.content_type
response.status_code
service_name
trace.span_id
trace.trace_id
```

有了更多维度可用，你可以检查事件以在任何一组服务请求之间建立高度复杂的关联（参见第 8 章）。你的数据维度越高，就越有可能找到应用程序行为中隐藏或难以捉摸的模式。在现代系统中，可能发生的故障排列组合实际上是无限的，仅在遥测数据中捕获几个基本维度是不够的。

你必须收集关于用户、代码和系统交汇处发生的一切的极其丰富的细节。高维度数据提供了关于这些交汇如何展开的更多上下文。在后面的章节中，我们将介绍如何分析高维度数据（通常包含高基数数据）以揭示你关心的系统问题发生的位置和原因。

## 使用可观测性进行调试

与其限制遥测数据的基数和维度，可观测性工具鼓励开发者为可能发生的每一种事件收集丰富的遥测数据，传递任何给定请求的完整上下文并将其存储起来以备将来使用。可观测性工具专门设计用于查询高基数、高维度数据。

因此，对于调试，你可以以任意方式 interrogate 你的事件数据。有了可观测性，你可以迭代地调查

你关心的条件，通过探索数据来了解它能揭示
关于系统状态的什么信息。你提出一个问题，这个问题你事先不需要预测，以找到答案或线索，从而引导你提出下一个问题，再下一个，再下一个。你一次又一次地重复这种模式，直到找到你在比喻的干草堆中寻找的那根针。
可观测系统的关键功能是能够以开放式的方式探索你的系统。

系统的可探索性取决于你提出任何问题并检查其对应内部状态的能力。*可探索性*意味着你可以迭代地调查并最终理解系统所处的任何状态——即使你从未见过该状态——而无需事先预测这些状态可能是什么。同样，可观测性意味着你可以理解并解释系统可能进入的任何状态——无论多么新颖或奇怪——而无需发布新代码。

监控之所以能长期有效，是因为系统往往简单到工程师能够推理出他们可能需要查找问题的位置以及这些问题可能如何表现。例如，当套接字填满时，CPU 会过载，解决方案是增加容量，通过扩展应用程序节点实例，或调整数据库，等等，相对简单地就能把点连起来。工程师在很大程度上可以预先预测大多数可能的故障状态，并在应用程序在生产环境中运行时以艰难的方式发现其余部分。

然而，监控对系统管理造成了根本性的被动方法。你可以捕获你预测并知道要检查的故障条件。如果你知道会发生，你就检查它。对于你不知道要寻找的每个条件，你必须先看到它，处理不愉快的意外，尽力调查它，可能到达一个需要多次看到相同条件才能正确诊断的死胡同，然后你才能为其开发检查。在这种模式下，工程师被扭曲地激励去强烈回避可能导致不可预测故障的情况。这也是为什么一些团队害怕部署新代码的部分原因（稍后会详细介绍该主题）。

一个微妙的额外观点：硬件/基础设施问题与你的代码或用户产生的问题相比是简单的。从“我的大部分问题是组件故障”转变为“我的大部分问题都与用户行为或微妙的代码错误和交互有关”正是为什么即使拥有单体和更简单架构的人也可能追求从监控转向可观测性。

## 可观测性适用于现代系统

生产软件系统在你能够在无需做出任意猜测、预先预测这些故障模式或发布新代码来理解该状态的情况下理解新的内部系统状态的程度上是可观测的。在这种方式上，我们将控制理论中的可观测性概念扩展到软件工程领域。

在其软件工程上下文中，可观测性确实为那些采用更传统架构或单体系统的人提供了好处。能够追踪你的代码并查看时间花费在哪里，或从用户角度重现行为，*始终*是有帮助的。这种能力无论你的架构如何，都可以让团队免于在生产环境中发现不可预测的故障模式。但对于现代分布式系统来说，可观测性工具提供的手术刀和探照灯变得绝对不可或缺。

在分布式系统中，可预测的故障模式与全新从未见过的故障模式的比例严重偏向于奇怪和不可预测。这些不可预测的故障模式发生的频率如此之高，且重复的次数如此之少，以至于大多数团队无法设置足够适当和相关的监控仪表板，以便轻松地向负责确保其生产应用程序持续正常运行、可靠性和可接受性能的工程团队展示该状态。

我们怀着对这类现代系统的考虑写了这本书。任何由许多松散耦合、动态且难以推理的组件组成的系统都是实现可观测性相对于传统管理方法优势的良好契合。如果你管理符合该描述的生产软件系统，本书描述了可观测性对你、你的团队、你的客户和你的业务意味着什么。我们还重点关注在工程流程的关键领域发展可观测性实践所需的人为因素。

## 结论

尽管 *可观测性* 一词已被定义了数十年，但将其应用于软件系统是一种新的改编，带来了几个新的考虑和特征。与其更简单的早期对应物相比，现代系统引入了如此多的额外复杂性，以至于故障比以往任何时候都更难预测、检测和排除故障。

为了缓解这种复杂性，工程团队现在必须能够以灵活的方式不断收集遥测数据，以便在无需先预测故障可能如何发生的情况下调试问题。可观测性使工程师能够以灵活的方式切片和切分遥测数据，从而以前所未有的方式深入到发生的任何问题的根源。

可观测性经常被误认为是当你拥有“三种支柱”的不同遥测数据类型时才实现，因此我们不喜欢这种模型。然而，如果我们必须有可观测性的三个支柱，那么它们应该是支持高基数、高维度和可探索性的工具。接下来，我们将研究可观测性与传统系统监控方法有何不同。
