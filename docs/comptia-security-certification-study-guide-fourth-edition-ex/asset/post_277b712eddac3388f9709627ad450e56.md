## Software Diversity

You will encounter various types of software environments. For example, you will come across *compiled code*, which is when a developer develops an application that is then compiled into a binary file (an executable file that is unreadable).

This is different from programs created in a script environment. A script is not compiled, so it can be easily opened in an editor, modified, saved, and then run again. The script is parsed and run by a scripting engine that has been installed on the system.

*Software diversity* is the use of different compilers to create different compiled versions of binary code. This also includes randomization of binaries, where you could have runtime randomization applied to the binary files to make the code more difficult to exploit.

## Automation/Scripting

A big part of security today is to automate as much as possible so that you do not have to perform repetitive tasks over and over again. Automation is the concept of creating scripts to perform the tasks for us. The benefit of automation is that once the scripts are created and tested, you can be sure that the process is performed in a consistent manner each time you run the script. The following are common areas where automation is used (note that the word *continuous* in this list refers to a repeatable, ongoing process):

- **Automated courses of action** The goal of automation is to automate tasks, or courses of action, that you must perform on a regular basis so that the chances of human error while performing those tasks are reduced.
- **Continuous delivery** A programming term where software development teams update software in short cycles in order to ensure that they can release a new version at any time.
- **Continuous validation** Automating the process of validating code using scripts that perform code checks before the application is compiled and eventually deployed.
- **Continuous deployment** When the compiled application is then deployed to the production system.
- **Continuous integration** A process where each time code is checked back in to the system, it triggers the continuous validation, which then compiles the code if the validation is successful. Once the build is successful (the application compiled), it may then trigger the automated deployment of the application into production through continuous deployment.
- **Continuous monitoring** Once a system or application is deployed, you have scripts automate the monitoring of the health of that system or application.

## Elasticity and Scalability

Common terms we hear today, especially with cloud computing, are *elasticity* and *scalability*. Placing applications in the cloud will provide you with the benefits of elasticity and scalability. *Elasticity* is the fact that the cloud environment can adjust the resources allocated to the application dynamically based on the workload. If there is a heavy load, the cloud environment can allocate more RAM or processing power, and then lower those resources when they are not needed. *Scalability* is the fact that the cloud provider can manually supply more servers in the background as demand increases over longer periods of time.

## Implement Host and Application Security

Now that you understand the common attacks against software, and understand some of the secure coding techniques that can be used to help prevent attacks through software, let’s take a look at some common techniques that can be used to protect the host system and applications from attacks.

## Host Security

There are a number of ways to help protect the host system from malicious code running on that system. The following are three key security features to be aware of for the Security+ exam:

- **Allow list** Formerly known as whitelisting. You can create a list of applications that are allowed to run on the system. Any other application would be prevented from running. This helps ensure that only tested and approved applications can run on company systems.
- **Block list/deny list** Formerly known as blacklisting. You can create an application block list (or deny list). All applications would be allowed to run on the system except any application you place on the block/deny list. This is a great way to handle a malicious application that is being sent to people through e-mail and you want to ensure your users do not run it.
- **Secure coding practices** Following the secure coding practices we talked about earlier is critical, including testing the application before deploying it to the production environment.

## Application Security

To help improve application security, you can follow these best practices:

- **Input validations** Many of the attacks against applications can be prevented if the programmers of the software validate input sent to the application before processing it. This is how to prevent the many types of injection attacks and cross-site scripting attacks.
- **Secure cookies** Cookies are used to store preferences for users when they visit a web site. The cookies are sent from the client to the web server to read the information and tailor the site to the user’s preference. Using secure cookies puts a flag on a cookie so that it is only sent to the web server if the site is using HTTPS.
- **Hypertext Transfer Protocol (HTTP) headers** HTTP now supports header values that can improve the security of web applications and protect against clickjacking and cross-site scripting attacks. For example, you could use the Content-Security-Policy header to control sources allowed for scripts, styles, and images.
- **Code signing** Code signing is an important feature for validating the integrity of application code. For security reasons, many environments will only execute code that has been digitally signed with a code-signing HTTP certificate by a trusted source.

## Code Quality and Testing

A key to creating secure applications is to make sure you implement proper code quality checks and testing. The following are different code quality checks and application testing that should be performed:

- **Static code analysis** Static code analysis is typically the first type of code testing performed and involves reviewing code to identify issues without running it. The code could be reviewed manually, with a team reading through it, but there are also tools available called static code analyzers that can review the code and look for potential vulnerabilities.
- **Dynamic code analysis** Dynamic analysis involves testing code by executing it and seeing how the application responds when used on the system. Examples of dynamic analysis include running unit tests, integration tests, system tests, and acceptance tests.
- **Stress testing** Stress testing is a form of testing that puts a lot of load on the application to determine how it would respond in production if a large number of users were to use the application at the same time.
- **Sandboxing** *Sandboxing* is the term for running code that has been changed in an isolated environment, away from production systems, to test the effect of the code changes.

## Understanding Application Attacks

- An SQL injection attack involves the hacker inserting SQL statements into forms in an application to try to control what the application does.
- A buffer overflow attack is when the hacker sends too much data to an application, which typically results in the hacker obtaining shell access to the system with administrative permissions.
- A zero-day exploit is an exploit that is unknown to the vendor of the vulnerable application but is known to the hacker community.
- To prevent application attacks, developers must ensure validation of any input sent to the application before acting on that input. Network administrators can prevent application attacks by patching all software and operating systems on a regular basis.

## Secure Application Development Concepts

- Remember that an application should be deployed to the following environment in this order: Development → Test → Staging → Production → Quality Assurance (QA).
- Developers implement error handling within most programming environments by implementing **try/catch** blocks.
- Any data inputted into an application should be validated before being processed.
- Stored procedures should be used to help prevent against SQL injection attacks.
- In distributed applications, implement input validation on the client side and the server side (especially on the server side).

## Implement Host and Application Security

- You can control what applications are allowed to run on a system by using an allow list (formerly known as whitelisting).
- You can deny a specific application from running on a system by using a block/deny list (formerly known as blacklisting).
- Fuzzing is a way to test how an application responds to random input.
