
## Why Application Vulnerabilities Exist

You may be asking why these attacks are successful. There are a number of reasons, but it is key to remember that hackers learn technologies in order to figure out how to break them or use them maliciously.

The following are key reasons why application attacks are successful:

- **Improper input handling** Input handling is another job for software programmers. Any time data is passed into an application, the programmer is supposed to validate that data and ensure it is appropriate for the task. If the data is invalid, an error is displayed to the user instead of processing the information. If the programmer does not validate input, hackers can inject malicious data into the application to control the software in a manner that is not desired.
- **Improper error handling** Error handling is yet another job of software programmers and includes ensuring that the application traps any errors that occur and then handles those errors appropriately so that the application doesn’t crash. When testing the software, developers are looking for the existence of errors. Improper error handling could lead to the program being exploited.
- **Default configuration** When installing software or systems, always make sure to change the default configuration as much as possible. Hackers know the default configurations of products and learn how to exploit systems based on the default configurations. You should change the defaults to make hackers more likely to give up and look for easier targets.
- **Misconfiguration/weak configuration** Most vulnerabilities exist because software or the operating system has been misconfigured by the administrator and placed in a nonsecure state. Review the configuration of any newly deployed systems and look to following hardening procedures for those systems.
- **Weak cipher suites and implementations** Another common vulnerability in systems today is the use of weak encryption technologies or protocols. For example, you may find that an application is encrypting data with the DES or 3DES symmetric algorithm. This is considered weak encryption, and you should upgrade to a stronger algorithm such as AES. Another example would be to replace the use of weaker encryption protocols such as TLS 1.0 and TLS 1.1 with the newer implementation, TLS 1.3.
- **New threats/zero-day** One of the biggest types of vulnerabilities to be aware of is the zero-day threat, which is an undisclosed or unknown vulnerability that the vendor is not aware of yet, or just became aware of, and thus has had no opportunity to provide a patch to fix it.

## CERTIFICATION OBJECTIVE 15.02

### Secure Application Development Concepts

An overlooked aspect of security is the security in the applications we use day in and day out. It is important to understand how hackers are compromising systems through applications that are running on company systems. The key lesson here is to understand that, as a network administrator, you can do your job and harden the system and ensure that it is up to date with patches, but if one application installed on the system does not follow secure coding concepts, the system could be easily compromised. In this section you learn about the secure coding concepts used to protect against application attacks.

### Secure Coding Concepts

As mentioned, a big part of securing systems is to ensure that the applications running on the systems have been developed in a secure way. This is up to the application developers—they need to learn secure ways of developing applications so that hackers cannot hack through the application to gain access to the system.

### Development Life Cycle Models

A software development life cycle (SDLC) outlines the major phases to developing an application. There are six phases to the software development life cycle:

- **Requirements gathering and analysis** The first phase involves collecting the requirements for the application.
- **Design** After the requirements are collected, you then work on designing the application based on the requirements.
- **Implementation (coding)** The implementation phase is also known as the coding phase. During this phase, you write the code for the application.
- **Testing** After the coding phase, you then must test the code to verify it does what it is supposed to.
- **Deployment** After testing, you are ready to install (deploy) the application to the system or systems that need to have the application.
- **Maintenance** During maintenance, you typically receive feedback from the persons using the application. You will need to fix any problems that arise with the application in this phase.

There are different software development life cycle models to choose from. Two of the more popular models are the waterfall model and the agile model. They have the same phases but differ in how you move from one phase to the other:

- **Waterfall** With the waterfall model, you progress through each phase of the SDLC without the capability of going backward in phases at any time. The point is that you must be sure to complete each phase to its fullest so that there is no need to go back (which was viewed as costly when this model was created).
- **Agile** With the agile model, you can take a more iterative approach and go to a previous phase if you realize something was missed or needs to be reworked. For example, you could do some requirements gathering, do some design, and then implement a prototype for the customer to review. Then, based on feedback from the customer, you may have to revisit the first few phases to complete requirements gathering and the design of the application. During testing, you may find that you need to change the design or change the code. The agile model views the capability to go back to a phase as critical to application development.

### Application Environments

It is critical to run your newly created software through a large number of tests to ensure the software was developed following secure programming concepts. This means that the application is to move through different stages or environments within its lifetime. The following is the order of environments the application moves through:

1. **Development** The development environment is where the application is created and debugged to fix any application errors.
2. **Test** After the application is developed, it should be deployed to a test environment, which has all of the essential elements, such as a test database server, for the application to use as it runs in this environment.
3. **Staging** After testing, the application moves to a staging environment, which is as close to the production environment that you can get (think of it as a “fake production” environment). This is essentially the last testing environment for the application before it moves to production.
4. **Production** Once the application has been tested within all the environments, including the staging environment, you can then deploy the application to the production environment—which means the application is live and ready to use!
5. **Quality assurance** The quality assurance (QA) environment is used to test that the application is meeting customer expectations. The quality assurance environment is where all QA testing occurs.

### Version Control and Change Management

Larger organizations that have teams of developers creating applications will benefit from using version control features that identify the version of the application a developer is working on. This is done using a version number or revision number. The version number helps you keep track of which files represent the most recent changes made to the document. Version control software automates tracking changes and allows you to easily revert to a previous version at any given time, if you wish.

Change management is the process you should follow to implement changes. Most companies have a change management policy that specifies how the changes are to be made. The change management process typically involves planning for change, testing the change, applying the change, and then verifying the change. Change management also includes a change management approval process, where before a change is implemented it must be approved, typically by a change advisory board (CAB).

### Provisioning and Deprovisioning

When planning to deploy an application, it is important to ensure that you have a process in place to provision the systems that will be running the application. Provisioning is the setting up of a new system. This is a critical part of application security these days because applications are complex and typically involve using multiple servers. You may need to provision an application server, a web server, and a database server in order to deploy the application. Ensure that you provision the system to support the application, but at the same time make sure you follow security best practices such as hardening the system. The goal of provisioning is to ensure the system is compliant, thereby reducing vulnerabilities to attacks. As part of the provisioning process you will grant users access to the application.

Deprovisioning a system is the process you take to remove the system from the application environment. When deprovisioning an application or system, you first alter the access control to ensure users do not have access to the system or application. It is important to note that if you do not deprovision, or remove, old systems from the network, they may end up not being patched, which makes those systems vulnerable to attack.

Another example is deprovisioning user accounts for employees that leave the company. As part of the exit process you should deprovision the accounts used by the exiting employees and ensure they no longer have access to the systems.

### Integrity Measurement

Integrity measurement is a technique used to verify whether a file has been modified by software on the system. Integrity measurement systems store file hashes of critical operating system files in a central list so that the current file hash of each file can be verified by comparing it to the file hash list at a later time.
