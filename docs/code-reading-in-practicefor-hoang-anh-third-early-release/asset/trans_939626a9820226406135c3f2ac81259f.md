
# 代码规范与代码审查

您可能会好奇，为什么要在关于代码审查的章节中谈论代码规范。因为在代码审查期间您必须阅读他人编写的代码，所以如果能事先就命名和文件布局等事项达成一致，会容易得多。打开文件却发现完全不同的命名方式或布局会让人非常困惑。您想专注于阅读代码，却不得不花时间去适应文件的布局。您希望尽可能消除障碍，以提高可读性。

但是！团队应该遵循哪些规范呢？这在我的一些过往团队中曾引发过多次激烈的讨论。每个程序员都有自己的偏好。每个程序员都认为自己的偏好是正确的，而其他的都是错误的。我自己也这样想了很长时间，我必须承认，我有时仍会陷入这种讨论的陷阱。一般来说，我的建议是使用您所用语言提供的指南，并将争论自动化解决掉。

## 代码格式化工具

`代码格式化工具` 是一种将代码格式化为特定布局的工具。大多数 `IDE` 都内置了代码格式化工具和快捷键，可根据您设置中的一组规范来格式化代码。在更通用的代码编辑器（如 `Visual Studio Code`）中，您需要为您的语言安装插件。

有几种方法可以自动化代码格式化。您可以启用保存时格式化，如 [图 5-6](#ch05.html#fig_6_5_add_a_comment_to_the_line_that_is_incorrect_acco) 所示。

![](assets/reading_for_code_reviews_309317_01.png)

遗憾的是，并非每个 `IDE` 都提供保存时自动格式化功能。此时您可以在将更改提交到版本控制时进行格式化。`Git` 提供了 `Hooks`（钩子），这是一种在执行特定 `git` 命令前或后自动执行脚本的方式。其中一种 `Hook` 是“`pre-commit hook`”（预提交钩子）。您可以向此钩子添加任何内容，但常见的做法是在此处添加代码格式化工具。

如果您使用自动代码格式化工具，代码审查就不再是检查代码布局规范的控制机制。审查者也能专注于重要的事情：寻找改进点和理解代码。

## 代码检查工具

`代码检查工具` 比代码格式化工具更进一步。它们根据一组规则分析您的代码，以查找 Bug、检测代码异味和漏洞。它们还能为您找出风格违规，但与代码格式化工具不同，它们不会自动修复这些违规。不过，当您开始寻找检查工具时，会发现情况有点模糊。有些检查工具可以自动修正风格违规和代码异味，而有些则不能。它们能分析的内容也各不相同。例如，`SonarQube` 可以分析多种编程语言、`Docker` 的配置文件，甚至您的 `SQL` 语句。而 `Pylint` 则是专门为分析 `Python` 而开发的。

与代码格式化工具一样，您可以在 `IDE` 中安装（部分）检查工具，或使用 `pre-commit hook` 来运行它们。

# 分析维度

在代码审查期间，您会分析为了理解代码而进行的代码阅读的四个维度：结构、业务领域、编程概念和上下文。它们共同需要形成一个清晰、连贯的整体图景。

根据我对变更代码库部分的熟悉程度，我喜欢以不同的方式开始代码审查。让我们看一个我为本书创建的示例。我选择了 `Marten`，这是一个 `.NET` 库，允许 `PostgreSQL` 作为文档数据库或事件存储运行。该开源项目可在此处找到：[https://github.com/JasperFx/marten](https://github.com/JasperFx/marten)。我复制了其中一个我将要评估的合并请求：[https://github.com/codereadinginpractice/marten/pull/1](https://github.com/codereadinginpractice/marten/pull/1)

如果您想开始为开源项目做贡献，但不确定如何着手，进行代码审查是一个很好的切入点。

## 对合并请求的整体把握

首先，我对 `MR`（合并请求）有一个大致的了解。我会查看对话、提交，并快速检查文件变更的折叠视图，如 [图 5-6](#ch05.html#fig_6_5_add_a_comment_to_the_line_that_is_incorrect_acco).2 所示。在这里我可以看到这是一个较小的 `MR`，主要是新增代码行，因为蓝色在这个概览中占主导地位。

![](assets/reading_for_code_reviews_309317_02.png)

如果我看侧边栏，可以获得更多信息。每个文件名旁边都有一个符号，指示该文件发生了什么情况（[图 5-6](#ch05.html#fig_6_5_add_a_comment_to_the_line_that_is_incorrect_acco).3）。我可以轻松地看到新增了 4 个文件，修改了 3 个文件。此 `MR` 中没有删除文件。

![](assets/reading_for_code_reviews_309317_03.png)

您还可以通过查看 `MR` 中显示的信息获得大量信息。如 [图 5-6](#ch05.html#fig_6_5_add_a_comment_to_the_line_that_is_incorrect_acco) 所示，您可以了解两个文件之间变更的程度。在本例中，文件 `docs/.vitepress/config.ts` 有 3 处变更。此文件的新增行数多于删除行数。您可以通过查看变更数旁边的颜色指示来判断：蓝色表示代码行被添加到了右侧文件中（左侧文件中没有这些行）。红色表示代码行从左侧文件中被移除。有两个蓝色方块和一个红色方块，所以添加到 `config.ts` 的代码行比移除的多。

![](assets/reading_for_code_reviews_309317_04.png)

让我们更深入地了解一下。查看文件名下方两个 `@@` 之间的数字。这会给您提供关于每个文件显示内容的信息。我们可以按如下方式解读 `-173,7 +173, 8`：

```
-173,7 +173, 8
```

*   减号表示出现在左侧文件中的代码行从右侧文件中被移除了。
*   数字 173 是差异视图中显示的第一行代码的行号。
*   数字 7 表示左侧文件显示了 7 行代码。
*   加号表示代码行被添加到了右侧文件中，这些行在左侧文件中不存在。
*   右侧文件也从第 173 行开始显示，但显示了 8 行代码。

审查完差异后，您可以将文件标记为“已查看”。我喜欢这个功能，因为审查变更可能非常耗费精力，并不总能一次完成。这个 `MR` 很小，只修改了 7 个文件，其中一个是 `gitignore` 文件，所以我可以一次性审查完。然而，我曾遇到过修改超过 15 个文件的审查请求，那一次做完太多了。我将较大的合并请求分成小块进行审查，并使用“已审查”标记来跟踪我已经完成的部分。

我还会尝试理解代码变更的目的。这个合并请求是：

*   修复 Bug？
*   新增功能？
*   修改或扩展现有功能？
*   重构现有代码？
*   ……？

这对您来说可能很正常，但我遇到过一些合并请求，需要花费一些力气才能弄清到底发生了什么。通常，人们应该将这些类型的代码变更分开，并为每种变更创建一个合并请求，但情况并非总是如此。示例中的 `MR` 向代码库添加了一个新功能，如 [图 5-6](#ch05.html#fig_6_5_add_a_comment_to_the_line_that_is_incorrect_acco) 所示。
