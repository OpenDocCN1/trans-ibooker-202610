

左侧的 [图 3-1](#ch03.html#fig_1_traditional_versus_adaptive_architecture) 显示了传统架构。人工操作员手动与各个基础设施组件——服务器、交换机、网络电缆等——交互，并做出必要的更改以适应组织不断变化的需求。如果需要额外的服务器资源，就有人 physically 进入机架添加一台新服务器，布线并使其运行起来。这个过程在某些情况下可能需要几天、几周甚至几个月的时间。相比之下，在自适应架构中，例如云计算服务提供商提供的架构 [图 3-1](#ch03.html#fig_1_traditional_versus_adaptive_architecture) 右侧所示，软件程序确定应用程序的需求并动态地、实时地更改分配给该应用程序的 IT 基础设施并调整其配置。所有这些都是自动完成的，无需人工干预。如果需要一台新服务器，云服务提供商会分配一台并自动将其附加到基础设施中的正确位置。使用传统架构需要数小时或数天才能实现的修改，使用自适应架构只需几分钟或几秒钟。这使得应用程序的架构能够不断地、创造性地实时修改以满足其不断变化的需求。

![](assets/oitc_0301.png)

如果一项服务流量增加并且需要额外的资源来处理该流量，则可以根据需要自动动态添加这些资源，并在流量下降时释放。需要执行长时间的复杂操作，例如计算月度报告或处理新数据集？使用自适应架构，您可以临时分配额外的资源，根据需要进行配置，执行工作，然后释放它们。

想在正在运行的应用程序中尝试一个新想法吗？分配所需的资源并进行测试：如果可行，您可以将资源纳入 IT 基础设施集合中；如果不可行，您可以删除它们，它们就会消失。

想在生产环境中发布新功能之前看看它在重负载下的表现吗？启动一些服务器运行该功能，再启动一些服务器生成虚假流量，然后试试看。完成后，只需删除不需要的资源即可。

需要将流量从受损系统绕开吗？启动一个替换补丁并将受损组件从基础设施中移除。试着用传统架构快速做到这一点。

# 自适应架构的实际应用

自适应架构赋予我们灵活性和适应性。它们使我们能够轻松尝试新想法，为意外负载添加新资源，并快速替换损坏、失败或易受攻击的组件。

自适应架构如何融入现代应用程序架构？它们可以在多个地方提供帮助。

## 自动扩缩容

大多数现代在线应用程序的资源需求并不是恒定的。通常，它们会根据使用情况而变化，无论是同时用户数量、每个用户的处理量，还是每个用户处理的数据量来衡量。一般来说，应用程序使用得越多，运行该应用程序所需的资源就越多。这在 [图 3-2](#ch03.html#fig_2_resource_requirements_go_up_as_application_usage_i) 中以通用方式说明。

![](assets/oitc_0302.png)

在传统应用程序架构中，这造成了两难境地。需要为应用程序分配资源，但分配多少资源呢？鉴于历史上 [云出现之前] 资源分配昂贵且耗时，资源分配往往是静态的。由于资源使用是动态的，这导致了要么大量资源闲置很长时间，要么由于容量不足而导致应用程序资源耗尽的情况。 [图 3-3](#ch03.html#fig_3_static_resource_allocation_results_in_excess_capac) 说明了这一点。

![](assets/oitc_0303.png)

如果资源是静态分配的，它们不会随着应用程序使用量的变化而变化。这意味着要么您拥有闲置的过剩容量，要么容量不足，应用程序处于饥饿状态。然而，使用自适应架构，分配给应用程序的资源水平不必是静态的。它可以是动态的——自适应的——并根据应用程序的需求而变化。随着应用程序使用量的增加，可以添加额外的容量以满足这些需求，并在使用量下降时缩减资源。

这在 [图 3-4](#ch03.html#fig_4_adaptive_architectures_dynamically_change_allocate) 中有所说明。理想情况下，您始终拥有比应用程序需求略多一点的资源可用，这样就不会有显著的过剩容量或容量不足。

迄今为止最著名的自适应架构示例是 *自动扩缩容* 架构。自动扩缩容是一种云机制，它监控应用程序的资源需求并自动添加或删除资源以满足这些需求。例如，AWS 具有 Auto Scaling 服务，可以动态更改服务器池中的服务器数量：它监控各种指标以确定是否需要更多或更少的容量，并添加或删除服务器以满足现有需求。

![](assets/oitc_0304.png)

一些基于云的服务会在幕后自动处理分配。例如，AWS Elastic Load Balancer 会动态更改分配给给定应用程序的服务器的大小和数量，以处理传入请求的速度。随着请求数量的增加，会自动添加额外的容量。当请求数量减少时，该容量会被移除。所有这些对消费者来说都是完全透明的；由 AWS 的控制系统内部处理。

## 自愈

想象一个运行在服务器池上的应用程序。如果服务器池中的一台服务器开始故障或损坏会怎样？此场景在 [图 3-5](#ch03.html#fig_5_a_server_begins_to_fail_in_a_server_pool_for_an_ap) 中有所说明。

在传统的非云环境中，应用程序将开始运行缓慢或可能开始间歇性失败。需要人工介入，登录到故障服务器，并修复其出现的问题。如果进程已终止，则需要重新启动它们。如果文件已损坏，则必须修复它。这些修复可能很快完成，也可能耗时。如果耗时，服务器可能在维修期间暂时从池中移除，导致应用程序以降低的容量运行。

![](assets/oitc_0305.png)

在以云为中心的应用程序中，可以使用自适应架构技术来协助修复过程。如果一台服务器开始出现问题，而不是召唤人工尝试修复它，故障服务器可以自动终止并从池中移除。自适应架构技术会意识到池中需要额外的资源，并会自动启动一台新服务器并将其添加到池中。 [图 3-6](#ch03.html#fig_6_adaptive_architecture_can_spin_up_a_replacement_se) 说明了这一点。

![](assets/oitc_0306.png)

与其让人工尝试修复病态服务器，服务器会被算法简单地放弃，并自动放置一台替换服务器。

这种方法有两个主要优势：

*   无需人工响应事件。问题已自动动态修复。
*   由于无需人工响应和解决问题，因此问题得到解决的速度更快，并且可能对应用程序用户造成的干扰更小。
