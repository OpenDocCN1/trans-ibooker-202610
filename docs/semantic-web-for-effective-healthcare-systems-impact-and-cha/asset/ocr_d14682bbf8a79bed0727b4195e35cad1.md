In other words, hypernodes are simple graphs nested within graphs. Again, due to the additional complexity involved, the hypernodes, like the hypergraphs, are rarely used as a graph database. The two popularly used graph databases are the Labelled Property Graph Model (LPG) or simply called the property graphs and the Resource Description Framework (RDF), which we will deal with more elaborately in section 2 of the chapter. LPG has additional graph properties or attributes to deal with various complex real-world problems. The labels attached to the nodes or edges of the LPG define different subsets or classes. Every node or edge can have any number of such properties, each containing a key to identify the property and the value associated with the property. The restriction and use of the labels create variants in the LPG [38–40].

Physical storage of the graph database is executed using different methods. Dividing the data into records or smaller units are followed by record-based graph database systems. For the sake of data locality, the records are physically stored in contiguous memory or disk clusters. The records could be of variable or fixed lengths. Each vertex of the graph is stored as one or more records which are sometimes called the vertex or node records and the edges are either stored in the same record that contains their corresponding source and destination vertices or is stored in separate edge records. In these record base systems, the pointers to the connecting memory location are held within each record so that the query concerning the destination vertex can be found faster. To save space, the labels or properties of edges are not stored in the record in some systems. These are the lightweight edges. The lightweight edges contain only the information or the memory address of the destination vertex. Index-based graph database systems store data in index structures that locate data that is stored in different parts and use the location information for faster retrieval. When physical location changes it is enough to update the index rather than to change all the pointers associated with the data locations [39].

Although graph databases have gained a lot of popularity in recent years, they are restricted in certain aspects since they are not yet fully evolved as in the case of the relational database. Functionally they lack query optimization capacity, when partitioned query need access to multiple partitions, unlike NoSQL, graph databases cannot read and write from multiple buffers, graph database has restrictions regarding schema and constraint definitions leading to inconsistencies in the data and finally, graph databases have querying restrictions that do not allow transitive closure.
