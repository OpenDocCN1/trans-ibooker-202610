An intelligent database is one that can not only store data in a perfectly linked relational manner but one that will also be able to produce knowledge for solving various problems. The relational database system has benefits such as being able to share data without compromising data consistency and integrity. Without a tool to extract knowledge from the data, the database cannot be useful for any knowledgebase system. A knowledgebase system is one in which data is stored in the form of knowledge that could be useful to the system. Structured query language (SQL) is a tool that could be utilized to convert data in a relational database system to knowledge. To do that the data is stored in relational database tables and the SQL queries are used to extract knowledge out of the database. So, the system does not operate as a knowledge base system but rather a database system from which knowledge can be extracted [12]. Although the possibility of building an intelligent system using an already existing database system seems to be attractive, their limitations in terms of knowledge and their time and space complexities are far greater than the advantages.

A method of circumventing the problem of using SQL in a programming language is the use of Horn clauses. ProLog is built on Horn clauses and is used to define and query a rational database that is limited to First-Order Logic. The non-terminal relation symbols that restrict first-order formulas could be expressed as sets of Horn clauses by making use of a fix-point operator that is applied to positive existential queries. One drawback of using Horn clauses is that adding a relation tuple to a database using the Horn clause program cannot delete the output of the query. To overcome the deficiency, an extension of the Horn clause to include negated terminal relation symbols could be thought of but universal quantification cannot be express by it. The other possibility is to let arbitrary first-order formulas with non-terminals as programs which are no solution at all [13].

Attempts were also made to infuse taxonomy and semantic interpretation using Horn clauses by making use of the idea of concepts and relations. It was a step towards merging Semantic Networks with logical programming and a relational database to create the knowledge base for a system. These attempts were seen as a stop-gap solution to the problem of constraint satisfaction. The use of domains of concepts greatly helped the reduction of time and space complexities by avoiding redundant computation and backtracking checks through an early deduction of failures [14]. The use of a relational database to store semantic networks has been studied with practical examples of how two-dimensional tables could be used to store nodes that could point to non-structural multidimensional knowledge [15]. Such solutions reduce the time and space complexities of the storage and knowledge query processes but fail in efficiency and robustness that is required of a good knowledge base. When the database reaches the upper limits of its performing capacity, they tend to fail to reduce the efficiency which in the case of any knowledge system is important. Moreover, there is no uniformity in the knowledge representation especially when it comes to the variety of knowledge-sharing activities and therefore relational database storage is insufficient [16]. Another reason why the relational database is bound to fail as the knowledge base is that a complete large-scale knowledge system cannot be effectively represented using a relational database [15].

Although the relational database was a well-developed system and is quite efficient with queries using SQL, it lacks efficiency when it comes to representing and storing knowledge. Knowledge comes from both structured and unstructured sources and so they must be represented in a manner that knowledge acquisition, knowledge base creation, and formation of inferred knowledge is possible without compromising on the time and space complexity.

## 10.2.2 NoSQL Databases

Relational and SQL databases go beyond data storage and query processing. They offer processing logic with vigorous constructs in declarative language using schemas and metadata and with assured consistency. They are also quick in recovery with logging, allow multiuser operation and synchronization with adequate user roles and security and more importantly, allow indexing for fast searches. All these benefits of the database result in complex processing that makes it quickly reach its limits when dealing with huge data. So the emphasis on data integrity and security compromises its performance, efficiency and flexibility especially when dealing with big data available on the web [17]. Other problems with relational or SQL databases are the slow reading and writing speeds, limited capacity and difficulty in scalability especially when a large amount of data is involved [18].

The term NoSQL was introduced by Carlo Strozzi in 1998 as a modified version of the relational database with open-source, relational, lightweight characteristics without SQL. NoSQL was then standing for “no SQL.” It was later converted into a non-relational distributed structured data storage by Johan Oskarsson in early 2009¹. NoSQL then was updated to mean “not only SQL.” The rapid expansion of the internet since the early 2000s assisted the growing popularity of NoSQL especially in the web-scale databases that involve the management of an enormous amount of data [17, 19]. The growth of NoSQL was, heavily influenced by Google’s Bigtable and Amazon’s Dynamo systems [20].

The obsession with NoSQL among big data users is primarily its non-relational model that avoids the complex join operations of the relational database. Moreover, NoSQL allows data to be distributed in a different location and is managed using metadata. The distributed nature of NoSQL also allows it to be horizontally scalable as necessary. The freedom from schemas in inserting data makes it flexible in adding data. Being open-source software, the possibility for customization and improvement of the model is highly preferred by data users. The data replication is in NoSQL is effortless ensuring high availability of data. The application programming interface (API) provided by NoSQL is simple and is an attractive component for programmers. The ACID (Atomicity, Consistency, Isolation, Durability) properties of the relational database are replaced by BASE (basically available, soft-state, and eventual consistency) property of NoSQL [17–28].

CAP (Consistency, Availability and tolerance to network Partitions) theorem, according to Eric Brewer of University of California, Berkeley, first appeared in 1998 and was published first in 1999 and later in 2000. It is considered midway between the ACID property of relational database and BASE property of NoSQL. According to the theorem only any one of the properties, that is, either consistency or availability or partition tolerance have to be compromised in the database. That is because if network partition is present, then either availability (by replication) or consistency (by holding on to only one set of databases) can be guaranteed as shown in Figure 10.1. If network partitioning is not a requirement, then consistency and availability can co-exist. The consistency spoken of in CAP differs from the consistency in ACID in the sense that consistency in CAP is about the physical consistency of data in all the nodes while the consistency in ACID is the logical consistency or integrity of the data in the database [18, 19, 21, 29].
