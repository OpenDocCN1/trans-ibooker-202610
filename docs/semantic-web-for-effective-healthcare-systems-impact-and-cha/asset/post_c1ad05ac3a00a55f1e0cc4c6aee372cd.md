## 10.2.3 Graph Database

The outstanding feature of a Graph Database is the Relationship. Relational databases and nearly all models of NoSQL databases have linked data. Linked data expresses the relation between data but does not go deeper. Graph Database on the other hand expresses the relationship between the data. The data in Graph Database is expressed as nodes of a graph and the relationship between the data is expressed as the edge between two nodes. The greatest advantage of establishing a relationship between nodes is that the time complexity of search reduces in comparison with linked data in proposition to the depth between the initial and final nodes [36, 37].

There are some unique characteristics of graphs that make the graph database valuable. A graph can have vector values attached to its nodes or edges that could be used to indicate properties of the nodes or edges and can be critical in influencing an algorithm or analysis of the graphs. Such values, known as attributes, are properties of the nodes or their edges. The relationship between nodes in a graph could also be symmetric or asymmetric depending on the requirement of the problem. If the relation is symmetric, then the graph is directed and the corresponding edges indicate the tail and head node. The tail node is the node from which the edge begins and the head node is where the edge ends. The distinction between directed and undirected graphs are used for measurements such as connectivity or path lengths. In certain graphs, the nodes and edges are labelled to indicate a particular type which could influence the outcome of the algorithm that works on the graph. For example, the nodes or edges may be labeled positive or negative to change the operations on that nodes or edges [38].

Different models of graph databases are in use. A Simple Graph Model is commonly used as a framework for graph processing. They are not commonly used as a database but rather is more often used in designing a more complex model such as the Labelled Property Graph. Hypergraphs, where an edge is connected to any number of nodes and is called hyperedges, is a generalization of a simple graph model. It used mostly to represent networks and rarely used as database storage. Hypernodes are another generalized simple graph model where a hypernode, which is an entity containing a set of nodes and edges, substitute the nodes of a simple graph. In other words, hypernodes are simple graphs nested within graphs. Again, due to the additional complexity involved, the hypernodes, like the hypergraphs, are rarely used as a graph database. The two popularly used graph databases are the Labelled Property Graph Model (LPG) or simply called the property graphs and the Resource Description Framework (RDF), which we will deal with more elaborately in section 2 of the chapter. LPG has additional graph properties or attributes to deal with various complex real-world problems. The labels attached to the nodes or edges of the LPG define different subsets or classes. Every node or edge can have any number of such properties, each containing a key to identify the property and the value associated with the property. The restriction and use of the labels create variants in the LPG [38–40].

Physical storage of the graph database is executed using different methods. Dividing the data into records or smaller units are followed by record-based graph database systems. For the sake of data locality, the records are physically stored in contiguous memory or disk clusters. The records could be of variable or fixed lengths. Each vertex of the graph is stored as one or more records which are sometimes called the vertex or node records and the edges are either stored in the same record that contains their corresponding source and destination vertices or is stored in separate edge records. In these record base systems, the pointers to the connecting memory location are held within each record so that the query concerning the destination vertex can be found faster. To save space, the labels or properties of edges are not stored in the record in some systems. These are the lightweight edges. The lightweight edges contain only the information or the memory address of the destination vertex. Index-based graph database systems store data in index structures that locate data that is stored in different parts and use the location information for faster retrieval. When physical location changes it is enough to update the index rather than to change all the pointers associated with the data locations [39].

Although graph databases have gained a lot of popularity in recent years, they are restricted in certain aspects since they are not yet fully evolved as in the case of the relational database. Functionally they lack query optimization capacity, when partitioned query need access to multiple partitions, unlike NoSQL, graph databases cannot read and write from multiple buffers, graph database has restrictions regarding schema and constraint definitions leading to inconsistencies in the data and finally, graph databases have querying restrictions that do not allow transitive closure. A graph database is meant to help with Big Data requirements but there are some limitations in that. Extraction of data from non-graphical resources is complex, the complexity and wide distribution of the huge data set lead to high cost in a query, batch processing that is usually carried out in graph database do not work always in real-time processing, graph algorithms are not adequate for Big Data processing, the performance of graph algorithms used for parallel processing are not optimum and heterogeneous, incomplete and inconsistent Big Data sets need to be semantically integrated for effective querying which is not fully functional in any of the present graph database systems. There are many other similar challenges in the use of graph database systems that have to be taken care of in its future evolutions [41].

Graph databases are an ideal solution to the world of Big Data but unlike the relational database systems, the graph database systems are far from a full evolution. Yet, their popularity has not diminished as it can be seen from the increasing number of systems that are developed using a graph database. With further research and development, a system without the present limitations could be developed.

## 10.3 RDF

Big Data is characterized by five elements, namely, volume, velocity, variety, value and veracity, that intrinsically form the huge and complex data-sets that cannot be handled by relational database and the traditional SQL. Big Data, especially in its unstructured form and containing petabytes of data, is analyzed for quick results by leading internet applications like Google, Facebook, Amazon, and the like [42]. In 1995, the Worldwide Web Consortium (W3C) started experimenting with a platform for Internet Content Selection (PICS) that was developed by the Internet Engineering Task Force (IETF) for rating the content of the web pages for the use of various communities that required it specially to monitor the web content. Due to various limitations in PICS, W3C formed the PICS Next Generation (PICSNG) working group to work on the common problem regarding resource description. The specifications worked out by the group could be applied to many applications which were later consolidated by W3C as the RDF working group. Although a lot of contribution was made by PICSNG in the creation of RDF, the RDF as at its present stage of evolution is shaped by the influence of many W3C member companies and several metadata efforts [43–45]. RDF has the five elements of the Big Data and it allows streaming, that is, continuous changes in the data. So even though, RDF might be inconsistent at times, it is popularly used [46].
